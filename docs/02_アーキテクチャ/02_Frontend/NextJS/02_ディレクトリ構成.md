# 02_ディレクトリ構成

## 1. 目的

Frontendのディレクトリ構成は、Next.js App Routerとの親和性を保ちつつ、Feature単位で変更しやすい構造とする。

本プロジェクトでは、以下を重視する。

- `app/` を薄く保つ
- Feature単位でコードをまとめる
- Server / Clientの責務を追いやすくする
- Laravel API通信を共通化する
- OpenAPI Generated Codeと手書きコードを分離する
- 共通ComponentとFeature専用Componentを明確に分ける
- 不要な抽象化や過度なディレクトリ分割を避ける
- Feature間の不要な依存を防ぐ
- 将来的な機能追加でも構造が崩れにくい状態を保つ

Frontend内部は、技術レイヤー単位ではなくFeature単位を中心に構成する。

---

# 2. 基本構成

基本構成は以下とする。

```text
src/
├── app/
├── features/
├── components/
├── lib/
├── types/
└── styles/
```

各ディレクトリの責務は以下のとおりとする。

```text
app/
=
Next.js Framework Boundary

features/
=
Feature固有の実装

components/
=
Feature非依存の共通UI

lib/
=
Feature非依存の技術的共通処理

types/
=
Application全体で共有するFrontend固有型

styles/
=
Global Style
```

---

# 4. app/

`app/` はNext.js App Routerとの接点となるFramework Boundaryとして扱う。

主な責務は以下とする。

```text
app/
├─ Routing
├─ Layout
├─ Metadata
├─ Page Entry Point
├─ Loading UI
├─ Error Boundary
├─ Not Found
├─ Route Handler
└─ Feature Composition
```

Feature固有の処理やBusiness Logicを大量に配置しない。

---

# 5. page.tsx

`page.tsx` は可能な限り薄く保つ。

基本的にはFeature ComponentのCompositionを担当する。

例：

```tsx
import { EmployeeList } from "@/features/employees";

export default function EmployeesPage() {
  return <EmployeeList />;
}
```

以下のような処理を`page.tsx`へ集中させない。

- 複雑なデータ変換
- Form Logic
- Validation Logic
- API通信の詳細
- Feature固有Utility
- 大量のUI実装

`page.tsx` はRoute Entry Pointとして扱う。

---

# 6. Route Group

画面構成やLayout、認証境界などによってRoute Groupを利用する。

例：

```text
app/
├── (auth)/
└── (dashboard)/
```

`(auth)` は認証画面群、`(dashboard)` はログイン後のApplication画面群として使用する。

Route GroupはURL Pathへ影響しない構造整理のために利用する。

---

# 7. app/api/

`app/api/` はNext.js Route Handlerを配置する。

```text
app/
└── api/
```

主に以下の用途で使用する。

- Client ComponentからのBFF Endpoint
- Auth.js関連Endpoint
- BrowserからNext.js Serverを経由する必要がある処理
- 必要なRequest / Response Adaptation

すべてのLaravel API通信をRoute Handler経由にする必要はない。

Server ComponentからLaravel APIを呼ぶ場合は、共通API Clientを利用して直接通信する。

---

# 8. features/

`features/` をFrontend Architectureの中心とする。

Featureは、ユーザーから見た機能・変更単位を基準に定義する。

本プロジェクトでは、例として以下を配置する。

```text
features/
├── employees/
├── skills/
├── skill-categories/
└── access-control/
```

BackendのBounded ContextやAggregate構成と完全一致させる必要はない。

FrontendではUI上の機能単位を優先する。

---

# 9. Feature内部構成

Feature内部の基本形は以下とする。

```text
features/
└── employees/
    ├── components/
    ├── server/
    ├── actions/
    ├── schemas/
    ├── mappers/
    ├── types/
    └── index.ts
```

ただし、すべてのFeatureでこれらを必須としない。

必要なディレクトリだけ作成する。

---

# 10. Feature / components

Feature専用Componentを配置する。

例：

```text
features/
└── employees/
    └── components/
        ├── employee-list.tsx
        ├── employee-table.tsx
        ├── employee-detail.tsx
        └── employee-form.tsx
```

ここに配置するComponentは、そのFeature固有の意味を持つものとする。

例えば、

```text
EmployeeTable
EmployeeSkillForm
EmployeeDetail
```

などである。

汎用的なUI Primitiveは配置しない。

---

# 11. Feature / server

Server専用処理を配置する。

例：

```text
features/
└── employees/
    └── server/
        ├── get-employees.ts
        └── get-employee.ts
```

主な用途は以下とする。

- Laravel APIからのServer-side Data Fetching
- Server Component向けQuery
- Server上でのみ利用するFrontend固有処理

Server専用であることを明確にする必要がある場合は、`server-only` の利用を検討する。

例：

```ts
import "server-only";
```

`server/` 内のコードをClient Componentから直接利用しない。

---

# 12. Feature / actions

Server Actionを使用する場合に配置する。

例：

```text
features/
└── employees/
    └── actions/
        ├── create-employee.ts
        ├── update-employee.ts
        └── delete-employee.ts
```

`actions/` は必須ではない。

Server Actionを利用するFeatureにのみ作成する。

Server ActionとRoute Handlerの具体的な使い分けは、`04_Server・Client 境界.md` および `05_データ取得・更新.md` で定義する。

---

# 13. Feature / schemas

Feature固有のFrontend Validation Schemaを配置する。

例：

```text
features/
└── employees/
    └── schemas/
        ├── employee-form-schema.ts
        └── employee-search-schema.ts
```

主な用途は以下とする。

- Form Validation
- Search Parameter Validation
- Client UX向上
- Frontend入力形式の検証

Laravel DomainのBusiness Ruleを再実装する場所にはしない。

---

# 14. Feature / mappers

API DTOからView Modelなどへの変換処理を配置する。

```text
API DTO
   ↓
Mapper
   ↓
View Model
```

例：

```text
features/
└── employees/
    └── mappers/
        └── to-employee-view-model.ts
```

主な用途は以下とする。

- 日付表示形式への変換
- Label変換
- Table表示形式への変換
- API ResponseからUI向けDataへの変換

単純な変換しかない場合は、無理に`mappers/`を作成しない。

---

# 15. Feature / types

Feature固有のFrontend Typeを配置する。

例：

```ts
type EmployeeListItem = {
  id: number;
  name: string;
  departmentName: string;
};
```

対象は以下とする。

- View Model
- UI Model
- Form Model
- Feature固有State
- Feature固有Utility Type

OpenAPI Generated Typeをコピーして再定義しない。

API Contract Typeは`lib/api/generated/`を正とする。

---

# 16. Feature / index.ts

FeatureのPublic APIとして`index.ts`を利用する。

例：

```ts
export { EmployeeList } from "./components/employee-list";
export { EmployeeDetail } from "./components/employee-detail";
```

`app/`などからFeatureを利用する場合は、原則としてPublic API経由とする。

```ts
import { EmployeeList } from "@/features/employees";
```

以下のようなDeep Importは原則避ける。

```ts
import { EmployeeList } from "@/features/employees/components/internal/foo";
```

Feature内部構造を外部へ過度に公開しない。

---

# 17. components/

`components/` はFeatureに依存しない共通Componentを配置する。

基本構成は以下とする。

```text
components/
├── ui/
└── layout/
```

---

# 18. components/ui

Design SystemやUI Primitiveを配置する。

例：

```text
components/
└── ui/
    ├── button.tsx
    ├── input.tsx
    ├── select.tsx
    ├── dialog.tsx
    ├── table.tsx
    ├── badge.tsx
    └── pagination.tsx
```

主な対象は以下とする。

- Button
- Input
- Select
- Checkbox
- Dialog
- Table
- Badge
- Pagination
- Tooltip
- Form Control

Feature固有のBusiness Meaningを持たせない。

例えば、

```text
EmployeeDeleteButton
```

はFeature側へ配置する。

一方、

```text
Button
```

は`components/ui/`へ配置する。

---

# 19. components/layout

Application全体で利用するLayout系Componentを配置する。

例：

```text
components/
└── layout/
    ├── header.tsx
    ├── sidebar.tsx
    ├── navigation.tsx
    └── page-container.tsx
```

Application全体の画面構造に関わるComponentを対象とする。

---

# 20. lib/

`lib/` はFeatureに依存しない技術的共通処理を配置する。

基本構成は以下とする。

```text
lib/
├── api/
├── auth/
├── validation/
├── navigation/
└── utils/
```

`lib/`を「どこにも置けないコードを置く場所」として使用しない。

Feature固有処理はFeature側へ配置する。

---

# 21. lib/api

Laravel APIとの通信に関する共通処理を配置する。

```text
lib/
└── api/
    ├── generated/
    ├── client.ts
    ├── errors.ts
    └── index.ts
```

基本的な通信構造は以下とする。

```text
Feature
   ↓
API Client
   ↓
Generated Client
   ↓
Laravel API
```

---

# 22. lib/api/generated

OpenAPIから生成されたコードを配置する。

```text
OpenAPI
   ↓
Code Generation
   ↓
lib/api/generated/
```

以下を原則とする。

- Generated Codeは直接編集しない
- 手書きコードと分離する
- API Contract Typeの正として使用する
- 再生成可能な状態を維持する

---

# 23. lib/api/client.ts

Laravel API通信の共通Clientを配置する。

主に以下を扱う。

- Base URL
- Authentication
- Common Header
- Request設定
- Error normalization
- Generated Clientとの接続

各Featureから無秩序に`fetch()`を利用せず、共通API Client経由を基本とする。

---

# 24. lib/api/errors.ts

API Errorに関する共通表現や変換処理を配置する。

具体的なError設計は`10_エラーハンドリング.md`で定義する。

---

# 25. lib/auth

Auth.jsおよび認証・認可に関するFrontend共通処理を配置する。

例：

```text
lib/
└── auth/
    ├── auth.ts
    ├── session.ts
    ├── permissions.ts
    └── index.ts
```

具体的なファイル構成は、Auth.jsの採用Versionや設定方式に合わせて調整する。

詳細は`08_認証・認可.md`で定義する。

---

# 26. lib/validation

Feature非依存の共通Validation処理のみ配置する。

例：

- 年月形式
- Pagination Parameter
- 共通文字列制約
- URL Query Parameter

Employee固有などFeature固有のValidationは、各Featureの`schemas/`へ配置する。

---

# 27. lib/navigation

Application全体のNavigationに関する共通処理を配置する。

例：

- Route Definition
- Navigation Helper
- Breadcrumb共通処理
- URL生成Helper

ただし、単純なNavigationでは無理に作成しない。

---

# 28. lib/utils

Feature非依存のUtilityを配置する。

例：

```text
format-date.ts
format-year-month.ts
cn.ts
```

`utils/`は肥大化しやすいため、Feature固有処理をここへ移動しない。

原則として、

```text
Feature固有
↓
features/

Feature非依存
↓
lib/utils/
```

と判断する。

---

# 29. types/

Application全体で共有するFrontend固有Typeを配置する。

例：

```text
types/
└── common.ts
```

対象例：

- Pagination
- SelectOption
- 共通UI Type
- Application共通Result Type

ただしFeature固有Typeは各Featureへ配置する。

OpenAPI Generated Typeもここへコピーしない。

---

# 30. styles/

Global Styleを配置する。

基本構成は以下とする。

```text
styles/
└── globals.css
```

Component固有Styleについては、採用するUI LibraryやStyling方式に応じて各Component側へ配置する。

---

# 31. Feature間依存

Feature同士の直接依存は原則避ける。

例えば、

```text
features/employees
       ↓
features/skills
```

のような依存を安易に作らない。

Feature間で共通利用したいものが発生した場合は、以下を確認する。

```text
本当にFeature共通の概念か
```

共通概念である場合のみ、

```text
components/
lib/
types/
```

などへの昇格を検討する。

ただし、共通化を急がない。

少量の重複よりも、誤った抽象化を避けることを優先する。

---

# 32. 共通化方針

共通化は以下の順番で判断する。

```text
まずFeature内部に置く
       ↓
複数Featureで必要になる
       ↓
責務が本当に共通か確認する
       ↓
共通領域へ昇格する
```

最初から共通化を前提としない。

Frontendでは早すぎる共通化を避ける。

---

# 33. ファイル命名規則

ファイル名は原則として`kebab-case`を使用する。

例：

```text
employee-list.tsx
employee-form.tsx
get-employees.ts
employee-form-schema.ts
to-employee-view-model.ts
```

TypeScript Symbolは通常のTypeScript Conventionに従う。

例：

```ts
EmployeeList
EmployeeForm
EmployeeViewModel

getEmployees
toEmployeeViewModel
```

---

# 34. ディレクトリ命名規則

Feature名は原則として複数形を使用する。

例：

```text
employees/
skills/
skill-categories/
```

Application上の概念として単数形の方が自然な場合は例外を許容する。

命名規則は一貫性を優先する。

---

# 35. 初期段階で作成しないディレクトリ

以下のようなディレクトリは、必要性が明確になるまで作成しない。

```text
hooks/
services/
repositories/
stores/
contexts/
constants/
helpers/
models/
```

これらを禁止するわけではない。

必要になった時点で適切なScopeへ追加する。

例えばFeature専用Hookであれば、

```text
features/
└── employees/
    └── hooks/
```

とする。

Global State Libraryが必要になった場合のみ、適切な`store/`構成を追加する。

---

# 36. ディレクトリ作成原則

空のArchitecture Directoryを先に大量作成しない。

以下を原則とする。

```text
必要になったら作る
```

Feature内部についても同様とする。

例えばMapperが不要なFeatureでは、

```text
mappers/
```

を作成しない。

Server Actionを使用しなければ、

```text
actions/
```

を作成しない。

これにより、Architectureの形だけを維持するための不要な構造を避ける。

---

# 37. 基本依存方向

ディレクトリ構成上の基本依存方向は以下とする。

```text
app
 ↓
features
 ↓
components / lib / types
```

概念的には以下とする。

```text
Framework Boundary
       ↓
Feature
       ↓
Shared / Technical Foundation
```

逆方向の依存は原則禁止する。

例えば以下は避ける。

```text
lib
 ↓
features
```

```text
components/ui
 ↓
features
```

```text
types
 ↓
features
```

詳細なDependency Ruleは`03_レイヤー・依存関係.md`で正式に定義する。

# 39. 決定事項

Frontendのディレクトリ構成として、以下を正式採用する。

- `src/` 配下にFrontend実装を配置する
- `app/` をNext.js Framework Boundaryとする
- `app/` はRouting / Layout / Entry Point / Compositionを中心とする
- `page.tsx` を薄く保つ
- Route Groupを認証境界・Layout整理に利用する
- `features/` をFrontend Architectureの中心とする
- FeatureはUI上の機能・変更単位で定義する
- Feature内部は必要に応じて`components / server / actions / schemas / mappers / types`等へ分ける
- Feature内部ディレクトリは必要になった時点で作成する
- `components/ui/` にFeature非依存のUI Primitiveを配置する
- `components/layout/` にApplication共通Layoutを配置する
- `lib/` にFeature非依存の技術的共通処理を配置する
- Laravel API通信は`lib/api/`へ集約する
- OpenAPI Generated Codeは`lib/api/generated/`へ配置する
- Generated Codeを直接編集しない
- Auth.js関連共通処理は`lib/auth/`へ配置する
- Feature固有Validationは各Featureの`schemas/`へ配置する
- Feature固有型は各Featureの`types/`へ配置する
- Application共通型のみ`src/types/`へ配置する
- FeatureのPublic APIとして`index.ts`を利用する
- Feature内部へのDeep Importを原則避ける
- Feature同士の直接依存を原則避ける
- 共通化は必要性が確認されてから行う
- ファイル名は原則`kebab-case`とする
- `hooks / services / repositories / stores / contexts`等は必要になるまで作成しない
- 空のArchitecture Directoryを先に大量作成しない
- 基本依存方向を`app → features → components / lib / types`とする

以上をFrontendのディレクトリ構成とする。
