# 11_キャッシュ戦略

## 1. 目的

本プロジェクトでは、Next.jsのCache機能を無条件に利用せず、Dataの性質・更新頻度・User Scope・Consistency要件に応じて適切に利用する。

目的は以下とする。

- 古いDataによる誤操作を防ぐ
- Authentication / AuthorizationとCacheを混同しない
- User固有Dataを誤って他Userへ共有しない
- 不要なLaravel API Requestを削減する
- Server Component Firstの構成と整合させる
- Mutation後に必要なDataのみ更新する
- Cache InvalidationをFeature単位で理解可能にする
- Cache Key / Cache Tagを過度に複雑化しない
- CacheをBusiness CorrectnessのAuthorityにしない
- Next.jsのVersion依存仕様をApplication Architectureへ過剰に漏らさない

基本方針を以下とする。

```text
Default
=
Dynamic / Fresh Data

Cache
=
明確なBenefitがあるReadのみOpt-in
```

また、

```text
Laravel
=
Source of Truth

Next.js Cache
=
Performance Optimization
```

とする。

---

## 2. Cache First Architectureを採用しない

本ApplicationではCache First Architectureを採用しない。

主要Dataには以下が含まれる。

```text
Employee
EmployeeSkill
Skill
SkillCategory
Department
Permission
Assignment
```

これらは、

- User操作によって変更される
- Authorization結果へ影響する
- 管理画面ではCurrent Stateが重要
- Mutation直後に最新値が期待される

という性質を持つ。

したがって、

```text
Cache Everything
```

ではなく、

```text
Fresh by Default
Cache Intentionally
```

を採用する。

---

## 3. CacheはCorrectnessを保証しない

Cacheされた値をBusiness RuleやAuthorizationの最終判定には利用しない。

例えば、

```text
Cached Permission
↓
編集可能と表示
```

されていても、実際のRequestではLaravelが最新状態を使ってAuthorizationする。

```text
Cache
=
Hint / Performance

Laravel
=
Current Authority
```

とする。

---

## 4. Data分類

Cache Strategyを検討する際、Dataを概ね以下へ分類する。

```text
A. User / Permission Sensitive Data
B. Frequently Updated Business Data
C. Relatively Stable Master Data
D. Static Application Data
```

Data分類に応じてCache Strategyを変える。

---

## 5. User / Permission Sensitive Data

以下はSecurity-sensitiveなDataとして扱う。

```text
Current User
Role
Permission
Sub Manager Assignment
Team Leader Assignment
User固有Navigation
```

DefaultではRequest時に最新状態を確認できる設計を優先する。

特にAuthorizationをCacheのみで保証しない。

---

## 6. Frequently Updated Business Data

代表例：

```text
Employee
EmployeeSkill
Permission Setting
Assignment
```

これらはMutation後のFreshnessが重要である。

MVPではDynamic Readを基本とし、必要性が確認された場合のみ明示的Cacheへ移行する。

---

## 7. Relatively Stable Master Data

比較的Cache候補となりやすいDataは以下とする。

```text
SkillCategory
Skill Master
Department
```

ただし、

```text
Master Data
=
必ずCache
```

とはしない。

更新頻度・Data量・Laravel負荷・Cache Hit Benefitを確認して判断する。

---

## 8. Static Application Data

Application Buildに含められる固定DataはBackend Data Cacheとは分離して扱う。

例：

```text
固定UI Label
Frontend-only Option
Static Navigation Metadata
```

Backend Master DataをFrontendへ静的に複製しない。

---

## 9. Server Component Read

Server Componentからの基本Read Flowを以下とする。

```text
Server Component
      ↓
Feature Server Query
      ↓
API Client
      ↓
Laravel API
```

Cache有無の判断をPage Componentへ無秩序に散在させない。

---

## 10. Dynamic ReadをDefaultとする

業務DataについてはDynamic Readを第一候補とする。

```text
Request
 ↓
Next.js
 ↓
Laravel API
 ↓
Current Data
```

MVP段階ではこれによりCache Invalidation Complexityを抑える。

---

## 11. Dynamic Readが向くData

以下ではDynamic Readを優先する。

```text
User固有Data
Permission依存Data
Mutation頻度が高いData
Mutation直後に最新値が必要なData
Current Stateが業務上重要なData
```

---

## 12. Cache導入条件

以下のBenefitが明確な場合にCacheを検討する。

```text
同一Readが高頻度
Data更新頻度が低い
Laravel API負荷削減効果が高い
Response生成Costが高い
一定のStalenessを許容できる
```

Next.jsにCache機能が存在すること自体を導入理由とはしない。

---

## 13. Cache Components

Next.jsのCache Componentsを利用する場合も、Application全体のBusiness Dataを自動的にCache対象とはしない。

Cache ComponentsはRendering / Navigation Performance改善のための技術として扱う。

Data自体をCache可能とするかはApplication側で判断する。

---

## 14. `use cache`

明示的にCache可能と判断したServer-side Readでは、`use cache`を利用候補とする。

```text
Stable Server Read
      ↓
"use cache"
      ↓
Cached Result
```

全Server Queryへ一律適用しない。

---

## 15. `use cache`導入基準

以下が明確な場合のみ利用を検討する。

```text
ResultがCache可能
User Secretへ依存しない
Permission Scopeが安全
Invalidation Strategyが明確
許容Stalenessが明確
```

---

## 16. User固有Dataの共有Cache

UserやPermissionによって結果が変化するDataを共有Cacheへ安易に入れない。

例：

```text
getEmployees()
```

でも、

```text
Administrator
→ 全社員

Sub Manager
→ 担当社員のみ
```

となり得る。

User Scopeを無視したCacheはData Leakageにつながるため禁止する。

---

## 17. Authorization依存Data

以下はAuthorization Contextに依存する代表例とする。

```text
Employee List
Employee Detail
Access Control
Assigned Employee
```

MVPではDynamic Readを基本とする。

Cache導入時はCache ScopeとAuthorization Scopeが一致することを確認する。

---

## 18. CredentialをCache Keyにしない

以下をCache Keyへ利用しない。

```text
Sanctum Token
Session Token
Cookie
Authorization Header
```

CredentialをCache Metadataへ露出させない。

---

## 19. Sensitive DataをCacheしない

以下をApplication Data Cacheへ保存しない。

```text
Password
Sanctum Token
Session Token
Authorization Header
Secret
Credential
```

CacheをCredential Storeとして使用しない。

---

## 20. Request Scopeの重複排除

同一Server Rendering内の重複Read削減とPersistent Cacheを区別する。

```text
Request内Deduplication
≠
RequestをまたぐPersistent Cache
```

Request内の重複削減だけで十分な場合、Persistent Cacheへ昇格させない。

---

## 21. Cache Key

Cache KeyはData Identityを明確に表現する。

概念：

```text
employees
employee:{employeeId}

skills
skill:{skillId}

skill-categories
skill-category:{skillCategoryId}

departments
department:{departmentId}
```

実際の実装では採用Next.js Versionの標準APIに従う。

---

## 22. Query条件を考慮する

一覧DataをCacheする場合、以下の条件でResultが変化する。

```text
keyword
department
page
sort
filter
```

したがって、

```text
employees
```

だけで全条件を同一Cache Resultとして扱わない。

---

## 23. Cache Key Frameworkを作りすぎない

以下のような巨大抽象化をMVPから導入しない。

```text
CacheKeyFactory
CacheNamespaceManager
CacheDependencyGraph
```

標準機能と小さなHelperで十分な範囲に留める。

---

## 24. Cache Tag

複数Route / Queryから同じBusiness Dataを参照する場合、TagによるInvalidationを利用候補とする。

概念：

```text
employees
employee:123
employee-skills:123
```

---

## 25. Cache Tagの粒度

Tagは大きすぎても細かすぎても管理が困難になる。

Employee Updateの場合、

```text
employee:123
```

だけでなくEmployee Listにも影響する可能性がある。

必要に応じて、

```text
employee:123
employees
```

等を組み合わせる。

---

## 26. Cache Tag命名

概念的には以下のNamingを基準とする。

```text
employees
employee:{id}

skills
skill:{id}

skill-categories
skill-category:{id}

departments
department:{id}

employee-skills:{employeeId}
```

実装時に必要なら小さな共通Utilityへ集約する。

---

## 27. Cache TagをEvent Busにしない

Cache Tagを、

```text
EmployeeUpdatedEvent
SkillChangedEvent
```

のようなFrontend Event Architectureへ発展させない。

Cache TagはCache Invalidation Metadataとしてのみ扱う。

---

## 28. Revalidation基本方針

Mutation成功後は以下を基本とする。

```text
Mutation
 ↓
Laravel Success
 ↓
Affected CacheのみInvalidate / Revalidate
 ↓
Fresh Read
```

---

## 29. Laravel成功前にInvalidateしない

以下の順序を採用しない。

```text
Cache Invalidate
 ↓
Laravel Mutation
 ↓
Failure
```

Laravel Mutation成功後にInvalidationする。

---

## 30. Validation Failure時

422等ではBackend Stateは通常変更されていない。

```text
422
↓
No Cache Invalidation
```

を基本とする。

---

## 31. Authentication / Authorization Failure時

401 / 403でも通常Mutationは成立していない。

そのためMutation起因のCache Invalidationは行わない。

---

## 32. Conflict Failure時

409 Conflictでは原則としてMutation起因のInvalidationを行わない。

ただし、

```text
Server Stateが既に変更されている
```

ことがConflict理由の場合、UX上最新Dataを再取得することは許可する。

---

## 33. `revalidatePath`

特定Routeに関連するDataを再取得させる場合、`revalidatePath`を利用候補とする。

概念：

```ts
revalidatePath("/employees");
```

---

## 34. `revalidatePath`の粒度

以下を標準にしない。

```text
Mutation
↓
Application全体をRevalidate
```

変更されたDataへ関連するPathへ限定する。

---

## 35. `revalidateTag`

同一Dataが複数Routeにまたがる場合、Tag単位のRevalidationを利用候補とする。

例：

```text
EmployeeSkill Update
        ↓
employee:123
employee-skills:123
employees
```

---

## 36. `updateTag`

Mutation直後に対象Dataの即時Freshnessを必要とする場合、採用Next.js Versionで提供されるImmediate Invalidation用APIを利用する。

Next.js 16系では`updateTag()`を利用候補とする。

```text
Server Action
 ↓
Laravel Mutation Success
 ↓
updateTag(...)
 ↓
次のReadでFresh Data
```

---

## 37. `updateTag` / `revalidateTag`の責務

Architecture上は以下で区別する。

```text
即時Freshnessが必要
→ Immediate Invalidation

一定のStalenessを許容
→ Revalidation
```

具体的なAPI Semanticは採用Next.js Versionの公式仕様に従う。

---

## 38. Read-your-own-writes

User自身がMutationした直後に古いDataが表示される状態を可能な限り避ける。

以下を標準挙動としない。

```text
Update
 ↓
Success
 ↓
Detailへ戻る
 ↓
Old Value
```

Mutation対象Dataは即時Freshnessを優先する。

---

## 39. MutationとAffected Data

MutationごとにAffected Dataを意識する。

```text
Create
→ List / Count

Update
→ Detail / List

Disable
→ Detail / List / Selection Option

Permission変更
→ Authorization関連Data
```

ただし、実際にCacheしているDataのみInvalidation対象とする。

---

## 40. Employee Create

Employee作成は以下へ影響する可能性がある。

```text
Employee List
Dashboard Count
Department Statistics
```

実際にCacheを導入している箇所だけInvalidateする。

---

## 41. Employee Update

Employee Updateでは概念的に、

```text
employee:{id}
employees
```

等がAffected Cache候補となる。

CacheしていないDataへ形式的なInvalidation処理を追加しない。

---

## 42. EmployeeSkill Mutation

EmployeeSkillは複数画面へ影響しやすい。

例：

```text
Employee Detail
Skill Detail
Dashboard
Search Result
```

Cache導入時はTag-based Invalidationを利用候補とする。

---

## 43. Skill Master Mutation

Skill名・有効状態等の変更は以下へ影響する可能性がある。

```text
Skill List
Skill Detail
EmployeeSkill Form Option
Search Filter
```

Cache導入時はAffected Dataを明示する。

---

## 44. Permission Mutation

以下の変更ではFreshnessを特に重視する。

```text
Role
canManagePermissions
Sub Manager Assignment
Team Leader Assignment
```

古いAuthorization UIを長時間残さない。

ただしBackend Authorizationは常にLaravelで最新Stateを使って最終保証する。

---

## 45. Better Auth SessionとData Cache

Better Auth SessionおよびBackend CredentialとNext.js Data Cacheを別責務として扱う。

```text
Redis
├── better-auth:*
│   └── Better Auth Session
│
└── backend-credential:*
    └── Encrypted Backend Credential

≠

Next.js Data Cache
```

Better Auth SessionとBackend CredentialはRedisで管理する。

Session Lifecycle、Backend Credential Lifecycle、Business Data Cache Lifecycleを混同しない。

Better Auth SessionやBackend CredentialをNext.js Data Cacheへ保存しない。

Next.js Data CacheのInvalidationによって、Better Auth SessionやBackend Credentialが失効したものとして扱わない。

認証情報の失効はAuthentication設計に従って管理する。

---

## 46. Permission Dataの長期Cache

PermissionはSecurity-sensitiveであるため長時間のStale CacheをDefaultにしない。

```text
Permission
↓
Long TTL Cache
```

は慎重に扱う。

---

## 47. Time-based Revalidation

一定時間のStalenessを許容できるDataではTime-based Revalidationを利用候補とする。

候補：

```text
SkillCategory
Department
比較的安定したSkill Master
```

更新後即時反映が必要ならOn-demand Invalidationを優先する。

---

## 48. TTL

全Dataへ一律TTLを設定しない。

```text
All Data
=
5 Minutes
```

のようなGlobal Policyを避ける。

以下を考慮する。

```text
Update Frequency
Freshness Requirement
Cost
Security Sensitivity
```

---

## 49. TTLを技術都合で決めない

Business / NFRとして許容Stalenessが定義されていない場合、

```text
とりあえず60秒Cache
```

のような設定を行わない。

Cache導入理由とFreshness要件を説明可能にする。

---

## 50. Static Rendering

以下を満たすContentではStatic Renderingを利用できる。

```text
Login不要
UserによってResultが変化しない
更新頻度が低い
```

本Applicationの主要Dashboard / Employee Dataでは基本的に優先しない。

---

## 51. Personalized Dashboard

DashboardはRole / Assignment等によって表示内容が変化する可能性が高い。

```text
Administrator
Manager
Sub Manager
Team Leader
```

したがってPersonalized Dashboard DataはDynamic Readを基本とする。

---

## 52. Dashboard Aggregation

Dashboardで複数APIをAggregationする場合も一括長期CacheをDefaultとしない。

```text
Dashboard
 ↓
Employee Count
Skill Count
Statistics
```

Performance問題が確認された場合に個別Cacheを検討する。

---

## 53. Search Result

検索結果はDefaultではCacheしない。

例：

```text
/employees?keyword=php&department=3&page=2
```

Query組み合わせが多くCache Hit率が低い可能性があるためである。

---

## 54. Pagination

Pagination ResultもSearch / Filter / Sortと同様にDynamic Readを基本とする。

Performance Bottleneckが確認された場合のみCacheを検討する。

---

## 55. Autocomplete

AutocompleteではPersistent Cacheより先にRequest自体を削減する。

```text
Debounce
Minimum Characters
Request Cancellation
```

等を優先する。

---

## 56. Client-side Server State Cache

TanStack Query / SWR等のClient Cache LibraryはMVPでは採用しない。

既存方針：

```text
Server Component
+
URL State
+
Route Handler
```

を基本とする。

---

## 57. Client Cache Library再検討条件

以下が増加した場合に再検討する。

```text
Polling
Background Refetch
Infinite Scroll
Client-side Server State共有
Optimistic Update
複雑なDeduplication
Offline-like UX
```

---

## 58. Browser Cache

Browser HTTP Cacheへ業務Dataを無自覚に依存しない。

Route HandlerでResponseを返す場合は必要に応じてCache Policyを明示する。

User固有DataをPublic Cache可能にしない。

---

## 59. Public Cache

以下のようなPolicyを設定する場合、

```text
Cache-Control: public
```

全User間で安全に共有可能なDataであることを必ず確認する。

Authenticated Business Dataでは原則利用しない。

---

## 60. Private / No-store

以下のDataではPrivate / DynamicなCache Policyを優先する。

```text
User固有Data
Security-sensitive Data
Freshness重要Data
```

具体的なHTTP HeaderはRoute Handler / Deployment Architectureと合わせて決定する。

---

## 61. CDN Cache

本ApplicationはAuthenticated Internal Applicationであるため、User固有Business DataをCDN共有Cacheへ載せることを基本戦略としない。

Static AssetではCDN Cacheを通常どおり活用する。

---

## 62. Static Asset Cache

以下はBusiness Dataと分離して長期Cacheを積極的に活用する。

```text
Hashed JavaScript
CSS
Static Images
Build Assets
```

---

## 63. Server ActionとRevalidation

Mutation成功後の基本Flowを以下とする。

```text
Server Action
 ↓
Laravel API
 ↓
Success
 ↓
Invalidate / Revalidate
 ↓
Redirect / Return
```

---

## 64. Revalidation責務

Mutation後のRevalidationは、そのMutationとFrontendへの影響を知るFeature Action側でTriggerすることを基本とする。

```text
Feature Action
↓
Affected Cacheを判断
```

---

## 65. API ClientでInvalidateしない

以下を標準にしない。

```text
lib/api/client
 ↓
updateEmployee()
 ↓
Employee Cacheを自動Invalidate
```

API ClientはTransport Infrastructureであり、Frontend View Dependencyを知るべきではない。

---

## 66. Feature ActionでInvalidationする

推奨Flow：

```text
UpdateEmployeeAction
 ↓
API Client
 ↓
Laravel Success
 ↓
Affected Employee Cache Invalidation
```

Feature / Mutation BoundaryがAffected Cacheを判断する。

---

## 67. Cache Utility

共通Cache Tag等が必要な場合は、小さなUtilityを導入してよい。

例：

```text
lib/
└── cache/
    └── tags.ts
```

巨大なCache Frameworkは構築しない。

---

## 68. Cache Dependency

以下の依存を許可する。

```text
Feature Action
    ↓
lib/cache
```

逆方向は禁止する。

```text
lib/cache
 ↓
features
```

---

## 69. Feature固有Cache定義

Feature固有のCache Tag / Cache Policyが増えた場合、Feature内へ配置してよい。

例：

```text
features/
└── employees/
    └── server/
        └── cache.ts
```

ただし低LevelなNext.js Cache UtilityはShared側へ配置できる。

---

## 70. Generated API Client

Generated OpenAPI ClientはCache Policyを知らないものとする。

```text
Generated Client
=
API Contract Transport

Cache Strategy
=
Frontend Application Concern
```

Generated CodeへCache Logicを追加しない。

---

## 71. View Model Cache

View Model Transformation Resultを細かくCacheすることをDefaultとしない。

MVPでは、

```text
API Result
Server Query Result
```

程度の粒度を基本とする。

Derived Cacheを増やす場合は元DataとのInvalidation関係を明確にする。

---

## 72. Duplicate Fetch

Cache導入前に同一画面内のDuplicate Requestを削減する。

確認対象：

```text
Duplicate Query
N+1-like API Request
Unnecessary API Call
```

悪いFetch設計をCacheで隠さない。

---

## 73. Waterfall

WaterfallはCacheだけで解決しない。

独立Readは、

```text
Promise.all
Suspense
Streaming
```

等を利用して並列化する。

`05_データ取得・更新.md`の方針に従う。

---

## 74. Stale Data

Cacheを利用する場合、UserがStale Dataを見て操作する可能性を考慮する。

特に以下では注意する。

```text
Permission
Employee State
Skill Activation State
Assignment
```

Backend側で必ず再Validation / Authorizationする。

---

## 75. Optimistic Update

Cache StrategyのためだけにOptimistic Updateを導入しない。

EmployeeSkill等Business Ruleが重要なMutationでは、

```text
Submit
 ↓
Laravel Success
 ↓
Invalidate
 ↓
Fresh Data
```

を基本とする。

---

## 76. Cache Invalidation Failure

Frontend Cache Invalidationが失敗してもLaravel DB StateのCorrectnessを最優先する。

Cache Invalidation FailureによってBackend MutationをRollbackするような分散Transaction設計は採用しない。

---

## 77. Laravel TransactionとのBoundary

Laravel TransactionとNext.js Cache Invalidationは別Transactionとして扱う。

```text
Laravel Transaction Commit
        ↓
API Success
        ↓
Next.js Cache Invalidation
```

このBoundaryを明確にする。

---

## 78. Invalidation Failure時

Mutation成功後のCache InvalidationでUnexpected Errorが発生した場合はLogging対象とする。

Backend Mutationが既に成功している場合、無条件のMutation Retryで二重実行を発生させない。

---

## 79. Deployment Environment

Cache Persistence / Sharing BehaviorはDeployment Environmentに依存し得る。

候補：

```text
Local Docker
Render
AWS ECS
```

Production Infrastructure確定後にCache Storage / Multi-instance要件を確認する。

---

## 80. Multi-instance

AWS ECS等でNext.js Instanceが複数になる場合、

```text
Instance A Cache
Instance B Cache
```

のBehaviorを確認する。

Persistent Cacheを利用する場合はInstance間共有・Invalidation方法を明確にする。

---

## 81. In-memory Cache

Application-level CorrectnessをProcess-local Memory Cacheへ依存させない。

Container Restart / Deployment / Scale-outによって、

```text
消失
分断
```

する可能性を前提とする。

---

## 82. Dedicated Cache Infrastructure

Redis等をFrontend Cache目的だけでMVPから追加しない。

以下が確認された場合のみ検討する。

```text
明確なPerformance Bottleneck
Multi-instance共有Cache要件
高いCache Hit Benefit
Infrastructure Costに見合う
```

---

## 83. Laravel Cacheとの二重Cache

Laravel側でもCacheを利用する場合、

```text
Next.js Cache
+
Laravel Cache
```

の二重Cacheとなる。

Invalidation Complexityが高まるため、各LayerのCache責務を明確にする。

MVPでは不要な二重Cacheを避ける。

---

## 84. Performance改善順序

Performance問題が発生した場合、以下の順で検討する。

```text
1. Query / API改善
2. 不要なFetch削減
3. Parallel Fetch
```

## 97. 決定事項

FrontendのCache Strategyとして、以下を正式採用する。

- LaravelをBusiness DataのSource of Truthとする
- Next.js CacheをPerformance Optimizationとして扱う
- CacheをBusiness Correctness / Authorization Authorityとは扱わない
- Cache First Architectureを採用しない
- Dynamic / Fresh ReadをDefaultとする
- Cacheは明確なBenefitがあるDataへOpt-inで導入する
- User / Permission Sensitive DataではDynamic Readを優先する
- Frequently Updated Business DataではDynamic Readを優先する
- Stable Master Dataを将来的なCache候補とする
- Static Application DataとBackend Master Dataを区別する
- Server Component → Server Query → API Client → Laravelを基本Read Flowとする
- Cache PolicyをPage Componentへ散在させない
- `use cache`を全Server Queryへ無条件適用しない
- Cache導入時はScope / Freshness / Invalidation Strategyを明示する
- User Scopeを無視した共有Cacheを禁止する
- CredentialをCache Keyへ利用しない
- Credential / SecretをData Cacheへ保存しない
- Request内DeduplicationとPersistent Cacheを区別する
- Cache KeyへData Identity / Query Conditionを反映する
- Cache Key Frameworkを過剰に構築しない
- Cache TagをInvalidation Metadataとして利用する
- Cache TagをFrontend Event Busとして扱わない
- Mutation成功後のみ原則Cache Invalidationを実施する
- 422 / 401 / 403 Failureでは通常Invalidateしない
- 409ではMutation結果とCurrent Stateに応じて判断する
- `revalidatePath`をPath単位Revalidation候補とする
- `revalidateTag`をTag単位Revalidation候補とする
- `updateTag`等のImmediate Invalidation APIを即時Freshnessが必要なMutationで利用候補とする
- Cache APIの具体的Semanticは採用Next.js Versionの公式仕様に従う
- Mutation直後のRead-your-own-writesを優先する
- MutationごとにAffected Dataを明確にする
- 実際にCacheしているDataのみInvalidateする
- Permission変更はFreshnessを特に重視する
- Better Auth Session StoreとNext.js Data Cacheを別責務とする
- Backend Credential StoreとNext.js Data Cacheを別責務とする
- Better Auth SessionとBackend CredentialをNext.js Data Cacheへ保存しない
- Session、Backend Credential、Business Data CacheのLifecycleを分離する
- Permission Dataを長時間Stale Cacheしない
- Time-based RevalidationはStalenessを許容できるDataのみ利用する
- TTLを全Dataへ一律設定しない
- TTLを技術都合だけで決めない
- Personalized DashboardはDynamic Readを基本とする
- Search / Filter / Sort / Pagination ResultはDefaultではCacheしない
- AutocompleteではPersistent CacheよりRequest削減を先に検討する
- TanStack Query / SWR等のClient-side Server State CacheをMVPでは採用しない
- Browser / CDN共有CacheへUser固有Business Dataを載せない
- Static Asset Cacheは積極的に活用する
- Server Action Mutation成功後に必要なRevalidationを行う
- API Client自身ではCache Invalidationを行わない
- Feature ActionがAffected Cacheを判断する
- 必要なら小さなCache Utilityを利用する
- Generated OpenAPI ClientへCache Logicを追加しない
- Duplicate Fetch / WaterfallをCacheで隠さない
- Optimistic UpdateをCache Strategyのためだけに導入しない
- Laravel TransactionとNext.js Cache Invalidationを別Boundaryとして扱う
- Cache Invalidation FailureによってBackend MutationをRollbackしない
- Multi-instance Deployment時のCache Behaviorを本番Infrastructure確定後に確認する
- Process-local CacheへApplication Correctnessを依存させない
- Redis等のDedicated Cache InfrastructureをMVPから追加しない
- Laravel Cacheとの不要な二重Cacheを避ける
- Performance改善はQuery / API / Fetch設計を先に行い、Cacheを後から検討する
- Cache利用FeatureではUser Scope Leakageを重点Testする
- Production相当環境でもCache BehaviorをTestする
- Next.js Upgrade時にCache / Revalidation BehaviorをRegression Testする
- MVPでは主要Business API Dataを積極的にPersistent Cacheしない
- 最初のCache候補は比較的StableなMaster Dataとする
- Performance上の明確な問題がなければ不要なCacheを追加しない

以上をFrontendのCache Strategyとする。
