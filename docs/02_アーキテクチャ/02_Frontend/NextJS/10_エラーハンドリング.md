# 10_エラーハンドリング

## 1. 目的

本プロジェクトでは、Frontendで発生するErrorを一律に処理せず、Errorの種類・発生Boundary・Userへの影響に応じて適切に扱う。

目的は以下とする。

- Expected ErrorとUnexpected Errorを分離する
- Laravel API ErrorをFrontend共通形式へ正規化する
- HTTP Statusの意味を維持する
- Server Component / Server Action / Route Handler / Client ComponentごとにError処理を分ける
- Validation ErrorとSystem Errorを混同しない
- Userへ内部情報を露出しない
- Authentication / Authorization Errorを正しく扱う
- ConflictをForm Validationとは分離する
- Error Boundaryを適切な粒度で配置する
- Retry可能ErrorとRetryすべきでないErrorを区別する
- Error LoggingとUser Messageを分離する
- Sensitive DataをErrorへ含めない
- Observabilityと連携できる構造にする

基本原則を以下とする。

```text
Expected Error
=
Application Flowとして明示的に処理

Unexpected Error
=
Error Boundary
+
Logging
+
Generic User Message
```

---

## 2. Error分類

FrontendではErrorを概ね以下へ分類する。

```text
Validation Error
Authentication Error
Authorization Error
Not Found Error
Conflict Error
Rate Limit Error
Network / Transport Error
Upstream Error
Unexpected System Error
```

すべてを単一のGeneric Errorへ潰さない。

一方で、Userへ内部実装Errorをそのまま表示しない。

---

## 3. Expected Error

Expected Errorとは、Application上発生し得ることが事前に想定されているErrorを指す。

例：

```text
401 Authentication Error
403 Authorization Error
404 Not Found
409 Conflict
422 Validation Error
429 Rate Limit
```

これらは可能な限り明示的なControl Flowとして扱う。

---

## 4. Unexpected Error

Unexpected Errorとは、正常なApplication Flowとして想定していないFailureを指す。

例：

```text
Programming Error
Unexpected Exception
Malformed Response
Infrastructure Failure
Unhandled Runtime Error
```

これらは原則として、

```text
Logging
+
Error Boundary
+
Generic Error UI
```

で扱う。

---

## 5. HTTP Status Mapping

Laravel APIからの代表的なStatusを以下のように扱う。

| Status | Frontend上の意味 |
|---|---|
| 400 | 不正Request / Contract Error |
| 401 | Authentication失効・未認証 |
| 403 | Authorization不足 |
| 404 | Resource Not Found |
| 409 | Conflict |
| 422 | Validation Error |
| 429 | Rate Limit |
| 5xx | Backend / Infrastructure Error |

Error normalization後もHTTP Statusの意味を維持する。

---

## 6. 401 Authentication Error

401はAuthenticationが必要、またはCredentialが無効・失効した状態として扱う。

```text
Laravel
 ↓
401
 ↓
API Client
 ↓
Authentication Error
 ↓
Next.js
 ↓
Re-authentication
```

Better Auth Sessionが有効でもSanctum Tokenだけが失効している可能性を考慮する。

Laravel Backend APIから401が返された場合は、
Backend Credentialを利用不能として扱う。

必要に応じて以下を実施する。

- Backend Credentialの削除
- Better Auth Sessionの失効
- Browser Session Cookieの無効化
- 再Loginの要求

具体的な失効順序、再試行、部分失敗時のRecoveryは
認証詳細設計に従う。

---

## 7. 401のContext

401には複数のContextが存在し得る。

```text
Login時の認証失敗
Session / Token失効
Protected APIへの未認証Access
```

すべてを同一UI Messageへ機械的に変換しない。

Contextに応じて扱う。

---

## 8. 403 Authorization Error

403はAuthentication済みだがPermission不足の状態として扱う。

```text
Authenticated
+
Not Allowed
=
403
```

基本的にはForbidden UIへMappingする。

---

## 9. 403でLoginへRedirectしない

403を通常LoginへRedirectしない。

UserはAuthentication済みであるため、

```text
この操作を行う権限がありません
```

等のForbidden UIとして扱う。

---

## 10. 404 Not Found

404はResourceが存在しない、またはBackend Security Policy上存在を公開しない場合に利用される。

PageとしてNot FoundへMapping可能な場合は`notFound()` / `not-found.tsx`を利用する。

```text
Laravel 404
 ↓
Next.js
 ↓
Not Found UI
```

---

## 11. 403 / 404をFrontendで推測しない

BackendがSecurity Policy上404を返している場合、Frontendで、

```text
実際には403だろう
```

と推測して変更しない。

Backend / API ContractのStatus Semanticsを尊重する。

---

## 12. 409 Conflict

409は現在のServer StateとのConflictとして扱う。

例：

```text
Unique Conflict
State Conflict
Concurrent Update
既に無効化済み
現在状態では操作不可
```

422 Validation Errorとは分離する。

---

## 13. Conflict ErrorのUI

Conflictの場合、

```text
入力が間違っています
```

とは扱わない。

必要に応じて、

```text
現在の状態が変更されています
最新情報を確認してください
```

等、Conflictの意味に対応したMessageを表示する。

---

## 14. 422 Validation Error

422はRequest / Form Validation Errorとして扱う。

```text
Laravel
 ↓
422
 ↓
API Error
 ↓
Server Action
 ↓
Field Error / Form Error
```

`09_フォーム・Validation.md`の方針に従う。

---

## 15. 422をError Boundaryへ送らない

Validation ErrorはExpected Errorである。

通常、

```text
422
↓
throw
↓
error.tsx
```

とはしない。

Form Action Result等へ変換し、Userが修正可能なUIとして扱う。

---

## 16. 429 Rate Limit

429は一時的なRate Limitとして扱う。

必要に応じて、

```text
しばらく待ってから再試行してください
```

等を表示する。

無制限な自動Retryは行わない。

---

## 17. 5xx Error

5xxはBackend / Infrastructure側のFailureとして扱う。

例：

```text
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout
```

Userへ内部詳細を表示しない。

---

## 18. API Error Normalization

Laravel API / Generated Client / Transport固有ErrorをFrontend共通形式へ変換する。

```text
Laravel Error
      ↓
Generated Client / Transport Error
      ↓
lib/api/errors.ts
      ↓
Frontend ApiError
```

Transport Layerの詳細をFeatureへ漏らさない。

---

## 19. `ApiError`

概念的には以下のような型を持つ。

```ts
type ApiError = {
  status: number;
  code?: string;
  message: string;
  details?: unknown;
  requestId?: string;
};
```

実際の型はLaravel Error ContractおよびOpenAPIと合わせて確定する。

---

## 20. Application Error Code

可能であればHTTP StatusだけでなくApplication Error Codeを利用する。

例：

```text
EMPLOYEE_NOT_FOUND
PERMISSION_DENIED
EMPLOYEE_SKILL_CONFLICT
VALIDATION_FAILED
```

User-facing MessageやUI分岐をBackendの生Message文字列へ依存させない。

---

## 21. Error MessageをControl Flowへ使用しない

以下のような実装は禁止する。

```ts
if (error.message === "Employee not found") {
  // ...
}
```

基本的には、

```text
HTTP Status
+
Application Error Code
```

を利用して判定する。

---

## 22. Error Details

`details`には必要に応じて以下を含められる。

```text
Validation Fields
Conflict Metadata
Retry Information
```

ただし以下は含めない。

```text
Sensitive Data
Internal Stack Trace
Credential
Database Detail
```

---

## 23. Server Component Error Handling

Server ComponentのRead Errorは種類に応じて処理する。

```text
Server Component
      ↓
Server Query
      ↓
API Error
```

その後、

```text
401
→ Authentication Flow

403
→ Forbidden UI

404
→ notFound()

Expected Error
→ Appropriate UI

Unexpected Error
→ throw
```

とする。

---

## 24. Server Componentですべてをcatchしない

以下のような処理を標準としない。

```ts
try {
  // ...
} catch {
  return <ErrorMessage />;
}
```

Unexpected Errorまで握り潰すとError BoundaryやMonitoringが機能しにくくなる。

---

## 25. Expected Errorのみ明示的に処理する

基本的には、

```text
catch ApiError
   │
   ├── 401 → Authentication Flow
   ├── 403 → Forbidden
   ├── 404 → Not Found
   └── Expected → Appropriate UI

その他
→ rethrow
```

とする。

---

## 26. `error.tsx`

Route Segment単位のUnexpected Errorには`error.tsx`を利用する。

```text
Route Segment
    ↓
Unexpected Error
    ↓
error.tsx
```

Error UIをFeature / Routeの意味に合わせて適切な粒度で配置する。

---

## 27. Error Boundaryの粒度

すべてをRoot Error Boundaryだけで処理しない。

例えば、

```text
employees/
├── page.tsx
└── error.tsx
```

のように、Failure ScopeをRoute Segment単位へ閉じ込める。

---

## 28. `global-error.tsx`

Application全体の重大なUnexpected Errorに備えて`global-error.tsx`を用意する。

```text
通常のSegment Boundaryで処理不能
        ↓
global-error.tsx
```

Expected Error処理には利用しない。

---

## 29. `not-found.tsx`

Resource Not Foundや存在しないRouteには`not-found.tsx`を利用する。

```text
404
↓
notFound()
↓
not-found.tsx
```

ForbiddenとNot Foundを同一UIとして扱わない。

---

## 30. Loading / Error / Not Foundを分離する

Route Stateを以下のように分ける。

```text
loading.tsx
=
Loading

error.tsx
=
Unexpected Error

not-found.tsx
=
Not Found
```

1つのGeneric State Componentへ無理にまとめない。

---

## 31. Server Action Error Handling

Server ActionではExpected Mutation ErrorをAction Resultへ変換する。

例：

```text
422
→ Field / Form Error

409
→ Conflict Result

401
→ Authentication Flow

403
→ Forbidden
```

Unexpected ErrorをForm Errorへ変換しない。

---

## 32. Action Result

概念例：

```ts
type ActionResult = {
  success: boolean;
  fieldErrors?: Record<string, string[]>;
  formError?: string;
  errorCode?: string;
};
```

具体形はForm実装方式に合わせて調整する。

---

## 33. Server ActionでUnexpected Errorを握り潰さない

以下を避ける。

```ts
catch {
  return {
    success: false,
    formError: "更新に失敗しました",
  };
}
```

Programming ErrorやInfrastructure FailureまでExpected Error扱いになるためである。

Expected Errorのみ明示的に処理する。

---

## 34. Route Handler Error Handling

Route HandlerはHTTP EndpointとしてHTTP Semanticsを維持する。

```text
Route Handler
 ↓
API Client
 ↓
Laravel Error
 ↓
HTTP ResponseへMapping
```

すべて200で返し、BodyだけでSuccess / Errorを区別する設計は採用しない。

---

## 35. Route HandlerのStatus

基本的にStatusを維持する。

```text
401 → 401
403 → 403
404 → 404
409 → 409
422 → 422
429 → 429
5xx → 適切な5xx
```

Next.js Route HandlerでLaravelのStatus Semanticsを不必要に潰さない。

---

## 36. Route Handlerで内部Errorを漏らさない

Unexpected Error時は以下をResponseへ含めない。

```text
Stack Trace
Internal Exception Message
Database Detail
Secret
Credential
```

安全な5xx Responseへ変換する。

---

## 37. Client Component Error

Client Component内のInteraction Errorは必要に応じてLocal UI Stateとして扱う。

例：

```text
Autocomplete取得失敗
一時的Client-side Fetch失敗
Clipboard操作失敗
Browser API失敗
```

Server State全体のError ManagementをClient Local Stateへ移さない。

---

## 38. Client-side Read Error

Client-side ReadではRoute Handler越しにLaravelへアクセスする。

```text
Client Component
      ↓
Route Handler
      ↓
Laravel
```

Error Statusを保持してClientへ返す。

Client側では必要に応じて、

```text
Inline Error
Retry Button
Partial Error State
```

等を表示する。

---

## 39. Error BoundaryとEvent Handler

Error BoundaryですべてのClient Interaction Errorを捕捉できるとは考えない。

Event Handlerや非同期処理など、必要なBoundaryで明示的にError Handlingする。

---

## 40. Retry基本方針

RetryはError種別とOperation特性に基づいて判断する。

```text
Retry
=
Default Behaviorではない
```

特にMutation Retryは慎重に扱う。

---

## 41. Mutation Retry

以下を無条件に自動Retryしない。

```text
POST
PUT
PATCH
DELETE
```

二重実行の危険があるためである。

Idempotencyが保証されている場合のみ別途検討する。

---

## 42. Read Retry

GET等のRead Operationでは、一時的Failureに対するRetryを検討できる。

候補：

```text
Network Failure
502
503
504
```

Retry回数には上限を設定する。

---

## 43. 通常RetryしないError

通常、以下は自動Retryしない。

```text
400
401
403
404
409
422
```

同一Requestを繰り返しても改善しない可能性が高いためである。

---

## 44. 429 Retry

429でBackendが`Retry-After`等を返す場合、その値を尊重することを検討する。

無条件の短周期Retryを行わない。

---

## 45. Timeout

TimeoutはNetwork / Transport Errorとして区別する。

```text
Request
 ↓
Timeout
 ↓
Transport Error
```

Userへ内部Timeout値そのものを表示しない。

---

## 46. Network Error

LaravelからHTTP Response自体を取得できないFailureはHTTP Status Errorと区別する。

例：

```text
DNS Failure
Connection Refused
Network Interruption
Timeout
```

---

## 47. Developer MessageとUser Message

Error Messageは以下を分離する。

```text
Developer / Log Message

User-facing Message
```

同一文字列をそのまま両用途へ利用しない。

---

## 48. User-facing Message

User向けMessageは以下を満たすものとする。

- 理解可能
- 次に何をすべきか判断できる
- Internal Implementation Detailを含まない
- 過度に技術的でない
- 必要に応じRetryや再Login等のActionを案内する

---

## 49. Generic System Error

Unexpected Errorでは安全なGeneric Messageを表示する。

例：

```text
処理中に問題が発生しました。
時間をおいて再度お試しください。
```

以下は表示しない。

```text
Exception Class
Stack Trace
SQL
Internal URL
Credential
```

---

## 50. Error CodeとFrontend Message

FrontendではError CodeからUser-facing MessageへMappingできる。

```text
EMPLOYEE_NOT_FOUND
↓
対象の社員が見つかりません

PERMISSION_DENIED
↓
この操作を行う権限がありません
```

Error Message自体をApplication LogicのKeyとして使用しない。

---

## 51. Error Logging

Unexpected ErrorはServer側でLoggingする。

必要な情報の例：

```text
Timestamp
Request ID
Trace ID
User ID
Route
Operation
HTTP Method
HTTP Status
Error Code
Exception
```

Sensitive Dataは除外する。

---

## 52. User ID Logging

Authentication済みの場合、Investigation / AuditのためUser IDをLogへ含めることを許可する。

ただし必要以上の個人情報を含めない。

---

## 53. Sensitive Data

以下をError Logへ出力しない。

```text
Password
Session Token
Sanctum Token
Cookie
Authorization Header
Secret
Credential
Sensitive Form Data
```

---

## 54. Request / Response Body Logging

Request / Response Bodyを無条件にLoggingしない。

調査目的で必要な場合でもSensitive FieldをMaskする。

---

## 55. Request ID

Next.js ↔ Laravel間でRequest IDを可能な限り引き継ぐ。

```text
Browser Request
   ↓
Next.js Request ID
   ↓
Laravel Request ID
```

Frontend / Backend双方のLogを関連付けられるようにする。

---

## 56. Trace Context

Observability基盤を導入する場合は、API Clientを通じてTrace Contextを伝播する。

```text
Next.js
 ↓
API Client
 ↓
Laravel
```

具体的な方式はMonitoring / Observability設計に従う。

---

## 57. User向けReference ID

Support用途で必要な場合は、安全なReference IDをError UIへ表示してよい。

例：

```text
お問い合わせ番号: ABC123
```

内部Trace情報やSensitive Identifierをそのまま表示しない。

---

## 58. Console Logging

ProductionではClientの`console.error`だけに依存しない。

Browser Consoleを正式なError Monitoring Sourceとはしない。

必要なErrorはServer Logging / Monitoringへ集約する。

---

## 59. Error Monitoring

Unexpected Frontend Errorは必要に応じてError Monitoring基盤へ送信する。

例：

```text
Unhandled Server Error
Client Runtime Error
Route Handler Unexpected Error
API Contract Failure
```

具体的なMonitoring Toolは別途決定する。

---

## 60. Validation ErrorをSystem Incident扱いしない

422等のUser入力ErrorをApplication Failureとして大量Monitoringしない。

```text
Expected Validation Failure
≠
System Incident
```

必要に応じてMetricとして別途集計する。

---

## 61. 403 Monitoring

403も通常はExpected Authorization Resultとして扱う。

ただし異常な頻度や攻撃兆候を検知したい場合はSecurity Monitoring側で扱う。

---

## 62. 404 Monitoring

通常の存在しないPageアクセスをすべてSystem Errorとして扱わない。

API上で異常に増加した404等は必要に応じてMetric化する。

---

## 63. Error StateとEmpty Stateを分離する

以下を明確に区別する。

```text
Dataが0件
=
Empty State

Data取得失敗
=
Error State
```

Employee一覧が0件であるだけならError UIを表示しない。

---

## 64. Permissionによる非表示とErrorを分離する

以下も区別する。

```text
Permissionにより非表示
≠
API Failure
```

UI Semanticsを明確にする。

---

## 65. Partial Failure

1画面で複数の独立したReadを行う場合、1つのFailureで画面全体を落とす必要がないケースを許可する。

例：

```text
Employee Detail
├── Basic Info
├── Skills
└── Related Data
```

Skillsだけ取得失敗した場合、Skills領域だけError表示することを検討できる。

---

## 66. Partial Failureの判断基準

以下の場合は局所的Error Handlingを検討する。

```text
Data同士が独立している
Failureしても主要操作が継続可能
Failure範囲をUserへ明確に示せる
```

Page成立に必須なDataならPage Errorとして扱う。

---

## 67. `Promise.all`とPartial Failure

独立Readを`Promise.all`で取得した場合、1件のFailureで全体がRejectされる。

Partial Failureを許容する必要がある場合だけ、`Promise.allSettled`等を検討する。

Defaultで`allSettled`へ統一しない。

---

## 68. Error Handlingを過剰にService Layer化しない

以下のような巨大抽象化を作らない。

```text
ErrorService
ErrorManager
ErrorHandlerFactory
```

共通化対象は主に以下とする。

```text
API Error Normalization
Common Error Types
Shared Message Mapping
Logging Infrastructure
```

---

## 69. Feature固有Expected Error

Feature固有のExpected Error MappingはFeature側へ置いてよい。

例：

```text
EmployeeAlreadyRetired
EmployeeSkillConflict
```

ただしTransport Error normalizationは`lib/api`へ置く。

---

## 70. Error Dependency

基本Dependencyを以下とする。

```text
Feature
   ↓
lib/api/errors
```

必要に応じてFrontend共通Error定義を別途`lib/errors`へ配置してよい。

Shared LayerからFeatureへの逆依存は禁止する。

---

## 71. Error Typeを乱立させない

Featureごとにほぼ同一の、

```text
EmployeeApiError
SkillApiError
DepartmentApiError
```

を作らない。

API / Transport Errorは共通化し、Feature固有の意味がある場合のみ専用Errorを導入する。

---

## 72. Throwする基準

Throwは主に以下へ利用する。

```text
Unexpected Error
Page継続不能Error
Error Boundaryへ委ねるFailure
```

Expected Form ErrorをすべてException Flowへしない。

---

## 73. Resultで返す基準

Result Objectは主に以下へ利用する。

```text
Validation Error
Expected Conflict
Userが修正可能なFailure
Form Submission Result
```

ExceptionとResultを用途で分ける。

---

## 74. Error判断フロー

```text
Error発生
   │
   ▼
Expected Error？
   │
   ├── Yes
   │    ↓
   │ Error種別を判定
   │    ├── 401 → Authentication
   │    ├── 403 → Forbidden
   │    ├── 404 → Not Found
   │    ├── 409 → Conflict
   │    ├── 422 → Validation
   │    └── 429 → Rate Limit
   │
   └── No
        ↓
   Unexpected Error
        ↓
   Logging
        ↓
   Error Boundary / Generic Error UI
```

---

## 75. Server Component Flow

```text
Server Component
      ↓
Server Query
      ↓
API Client
      ↓
Error
      │
      ├── 401 → Authentication Flow
      ├── 403 → Forbidden UI
      ├── 404 → notFound()
      ├── Expected → Appropriate UI
      └── Unexpected → throw
                           ↓
                        error.tsx
```

---

## 76. Server Action Flow

```text
Form
 ↓
Server Action
 ↓
API Client
 ↓
Error
 │
 ├── 422 → Field / Form Error
 ├── 409 → Conflict Result
 ├── 401 → Authentication Flow
 ├── 403 → Forbidden
 └── Unexpected
       ↓
     Logging
       ↓
     throw
```

---

## 77. Route Handler Flow

```text
Client
 ↓
Route Handler
 ↓
API Client
 ↓
Laravel
 ↓
Error
 ↓
HTTP Statusを維持
 ↓
Client
```

Unexpected Errorのみ安全な5xx Responseへ変換する。

---

## 78. Client Component Flow

```text
Client Interaction
      ↓
Route Handler / Browser API
      ↓
Failure
      │
      ├── Expected
      │     ↓
      │ Inline Error / Retry
      │
      └── Unexpected
            ↓
         Error Reporting
            ↓
         Safe UI
```

## 81. 決定事項

Frontendのエラーハンドリングとして、以下を正式採用する。

- Expected ErrorとUnexpected Errorを明確に分離する
- ErrorをValidation / Authentication / Authorization / Not Found / Conflict / Rate Limit / Transport / Systemへ分類する
- HTTP Statusの意味をError normalization後も維持する
- 401をAuthentication失効・未認証として扱う
- 401はContextに応じてLogin FailureとSession失効を区別する
- 403をForbiddenとして扱う
- 403を通常LoginへRedirectしない
- 404をNot FoundへMappingする
- Backendの403 / 404 Security PolicyをFrontendで勝手に変更しない
- 409をConflictとして422と分離する
- 422をForm Validation ErrorへMappingする
- 422を通常Error Boundaryへ送らない
- 429をRate Limitとして明示的に扱う
- 429では`Retry-After`等を考慮する
- 5xxでは内部情報をUserへ表示しない
- Generated / Transport ErrorをFrontend共通`ApiError`へNormalizeする
- HTTP Statusに加えてApplication Error Codeを利用することを推奨する
- Error Message StringをControl Flowへ利用しない
- Sensitive Data / Stack TraceをError Detailsへ含めない
- Server ComponentではExpected Errorのみ明示的に処理する
- Unexpected Errorを握り潰さずError Boundaryへ委ねる
- Route Segment単位で`error.tsx`を利用する
- `global-error.tsx`をApplication-level Unexpected Error用に用意する
- `not-found.tsx`をNot Found専用として扱う
- Loading / Error / Not Foundを分離する
- Server ActionではExpected Mutation ErrorをAction Resultへ変換する
- Server ActionでUnexpected ErrorをGeneric Form Errorへ握り潰さない
- Route HandlerではHTTP Status Semanticsを維持する
- Route Handlerで内部Exception DetailをResponseへ漏らさない
- Client Interaction Errorは必要なComponent Scopeで扱う
- RetryをDefault Behaviorとはしない
- Mutationを無条件に自動Retryしない
- Read Retryは一時的Failureに限定して検討する
- 400 / 401 / 403 / 404 / 409 / 422は通常自動Retryしない
- Timeout / Network ErrorをHTTP Errorと区別する
- Developer / Log MessageとUser-facing Messageを分離する
- Unexpected ErrorではGeneric User Messageを利用する
- Error CodeとFrontend MessageをMappingする
- Unexpected ErrorをServer-side Loggingする
- Password / Token / Cookie / CredentialをLoggingしない
- Request / Response Bodyを無条件Loggingしない
- Request ID / Trace IDをError Investigationへ活用する
- Browser Consoleを正式なError Monitoring Sourceとはしない
- Validation ErrorをSystem Incidentとして大量Monitoringしない
- 403 / 404等のExpected ResultはMonitoring上もSystem Failureと区別する
- Empty StateとError Stateを区別する
- Permissionによる非表示とAPI Failureを区別する
- 独立Dataについては必要に応じPartial Failureを許可する
- Partial Failureが不要な箇所で`Promise.allSettled`を乱用しない
- Error Handlingを巨大な汎用Serviceへ集約しない
- Transport Errorは共通化しFeature固有Expected ErrorのみFeatureで意味付けする
- Featureごとに重複ApiError Typeを作らない
- Unexpected Error / Page継続不能ErrorはThrowする
- Validation等Userが修正可能なFailureにはResult Objectを利用する
- LaravelをAPI Error ContractのSourceとし、Next.js側でFrontend向けに安全にNormalizationする

以上をFrontendのエラーハンドリング方針とする。
