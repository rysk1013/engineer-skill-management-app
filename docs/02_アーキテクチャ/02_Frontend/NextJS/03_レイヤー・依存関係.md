# 03_レイヤー・依存関係

## 1. 目的

Frontendでは、Backendのような厳密なClean ArchitectureのLayer構造をそのまま適用せず、Feature-based Architectureを中心に据える。

そのうえで、ディレクトリ間の依存方向を明確にし、以下を防ぐ。

- Feature間の過度な結合
- Shared領域からFeatureへの逆依存
- Next.js Framework層への不要な依存
- 循環依存
- Feature内部構造の外部露出
- Server専用コードのClient側への混入
- Generated Codeと手書きコードの逆依存

Frontend Architectureでは、依存関係を可能な限り単方向に保つ。

---

# 2. 基本レイヤー

Frontendの概念的なLayerは、以下の3段階とする。

```text
Framework Layer
    ↓
Feature Layer
    ↓
Shared / Technical Layer
```

ディレクトリに対応させると以下となる。

```text
app/
  ↓
features/
  ↓
components/ + lib/ + types/
```

下位Layerから上位Layerへの依存は原則禁止する。

---

# 3. Framework Layer

Framework Layerは主に以下を対象とする。

```text
app/
```

`app/` はNext.jsとの接点となるFramework Boundaryである。

主な責務は以下とする。

```text
Routing
Layout
Metadata
Page Entry Point
Loading
Error Boundary
Route Handler
Feature Composition
```

Framework LayerはFeature LayerおよびShared / Technical Layerへ依存できる。

```text
app
 ├──→ features
 ├──→ components
 ├──→ lib
 └──→ types
```

一方、FeatureやShared領域から`app/`への依存は禁止する。

```text
features
   ↓ NG
app
```

```text
lib
 ↓ NG
app
```

FeatureがRoute構造やPage構造を直接知る状態を避ける。

---

# 4. Feature Layer

Feature Layerは以下を対象とする。

```text
features/
```

Frontend Architectureの中心となるLayerであり、ユーザーから見た機能・変更単位を表現する。

Feature内部には、必要に応じて以下を配置する。

```text
components/
server/
actions/
schemas/
mappers/
types/
hooks/
```

Feature LayerはShared / Technical Layerへ依存できる。

```text
features
 ├──→ components
 ├──→ lib
 └──→ types
```

Featureから`app/`へは依存しない。

---

# 5. Shared / Technical Layer

Shared / Technical Layerは以下を対象とする。

```text
components/
lib/
types/
```

これらは特定Featureに依存しない。

したがって、以下のような依存は禁止する。

```text
components
   ↓ NG
features
```

```text
lib
 ↓ NG
features
```

```text
types
  ↓ NG
features
```

Shared / Technical LayerはFeature固有の概念を知らない状態を維持する。

---

# 6. 基本Dependency Rule

基本依存方向を以下とする。

```text
app
 ├──→ features
 ├──→ components
 ├──→ lib
 └──→ types

features
 ├──→ components
 ├──→ lib
 └──→ types

components
 ├──→ lib
 └──→ types

lib
 └──→ types

types
 └──→ 原則依存なし
```

逆方向の依存は原則禁止する。

---

# 7. 禁止する依存

以下の依存は禁止する。

```text
features → app
components → app
components → features
lib → app
lib → features
types → app
types → features
```

また、Layerを跨ぐ循環依存も禁止する。

---

# 8. Dependency Matrix

Dependency Ruleを以下のMatrixとして定義する。

| From \ To | app | features | components | lib | types |
|---|---:|---:|---:|---:|---:|
| app | △ | ○ | ○ | ○ | ○ |
| features | × | △ | ○ | ○ | ○ |
| components | × | × | △ | ○ | ○ |
| lib | × | × | × | △ | ○ |
| types | × | × | × | × | △ |

意味は以下とする。

```text
○
=
依存可能

×
=
依存禁止

△
=
同一領域内で循環しない範囲で依存可能
```

---

# 9. Feature間依存

Feature同士の直接依存は原則避ける。

例えば以下のような依存を安易に作らない。

```text
features/employees
       ↓
features/skills
```

Feature間依存を増やすと、以下の問題が発生しやすい。

- 変更影響範囲の拡大
- 循環依存
- Feature境界の曖昧化
- 共通化責務の不明確化

Feature間で共通して必要なものが発生した場合は、本当に共通概念かを確認する。

共通概念である場合のみ、以下への昇格を検討する。

```text
components/
lib/
types/
```

ただし、早すぎる共通化は避ける。

少量の重複よりも、誤った抽象化を避けることを優先する。

---

# 10. Feature Composition

複数Featureを組み合わせる必要がある場合は、上位側でCompositionすることを基本とする。

例えば、

```text
Employee Feature
+
Skill Feature
```

を1画面で利用する場合、

```text
app/
  ↓
Employee Feature
  +
Skill Feature
```

のようにFramework LayerでCompositionする。

一方で、

```text
Employee Feature
      ↓
Skill Feature
```

という直接依存は原則避ける。

---

# 11. Feature内部の依存

Feature内部は厳密なLayer構造を強制しない。

例えば、

```text
features/employees/
├── components/
├── server/
├── actions/
├── schemas/
├── mappers/
├── types/
└── index.ts
```

内部では、責務上必要な依存を許可する。

例：

```text
components → types
components → schemas
components → actions

server → mappers
server → types
server → lib/api

actions → schemas
actions → lib/api
actions → types

mappers → types
```

Feature内部では固定されたLayer階層よりも、依存を単方向に保つことを優先する。

---

# 12. Feature内部の循環依存

Feature内部であっても循環依存は禁止する。

例えば以下は禁止する。

```text
components
    ↓
actions
    ↓
components
```

また、

```text
server
  ↓
mappers
  ↓
server
```

のような循環も禁止する。

循環が発生した場合は、責務配置を見直す。

---

# 13. Feature Public API

Feature外部からFeatureを利用する場合は、原則としてFeatureのPublic APIを経由する。

Public APIには以下を利用する。

```text
features/<feature>/index.ts
```

例：

```ts
export { EmployeeList } from "./components/employee-list";
export { EmployeeDetail } from "./components/employee-detail";
```

利用側は以下とする。

```ts
import { EmployeeList } from "@/features/employees";
```

これによりFeature内部構造を外部へ露出させない。

---

# 14. Feature外部からのDeep Import

Feature外部からFeature内部へのDeep Importは原則禁止する。

以下は避ける。

```ts
import { EmployeeList } from "@/features/employees/components/employee-list";
```

さらに以下のような内部構造への依存は禁止する。

```ts
import { something } from "@/features/employees/components/internal/foo";
```

Feature内部のディレクトリ構造変更が外部へ波及しないようにする。

---

# 15. Feature内部Import

同一Feature内部では、無理に`index.ts`を経由しない。

例えば以下は許可する。

```ts
import { getEmployees } from "../server/get-employees";
```

基本方針を以下とする。

```text
Feature外部
↓
Public API経由

Feature内部
↓
Internal Import可
```

Feature内部でのBarrel Exportの乱用は避ける。

---

# 16. components/ui の依存

`components/ui/` は最も低レベルなUI共通領域として扱う。

主に以下への依存を許可する。

```text
React
Styling Library
lib/utils
Shared Type
```

Feature固有概念へ依存させない。

例えば以下は禁止する。

```text
Button
 ↓
Employee
```

```text
Table
 ↓
Skill
```

UI PrimitiveはBusiness Meaningを持たない状態を維持する。

---

# 17. components/layout の依存

`components/layout/` はApplication共通Layoutを扱うため、`components/ui/`よりもApplication寄りの依存を許可する。

例えば以下への依存を許可する。

```text
components/layout
 ├──→ components/ui
 ├──→ lib/auth
 ├──→ lib/navigation
 ├──→ lib/utils
 └──→ types
```

ただしFeature固有ロジックには依存しない。

```text
components/layout
       ↓ NG
features/employees
```

---

# 18. lib/ の依存

`lib/` はFeature非依存の技術的基盤として扱う。

主な対象は以下とする。

```text
lib/api
lib/auth
lib/validation
lib/navigation
lib/utils
```

`lib/` からFeatureへの依存は禁止する。

例えば以下は禁止する。

```ts
// lib/api/client.ts

import type { EmployeeViewModel } from "@/features/employees";
```

API ClientやAuth処理などの技術基盤はFeatureを知らない状態を維持する。

---

# 19. lib内部の依存

`lib/` 内部でも不要な循環依存を避ける。

例えば、

```text
lib/api
   ↓
lib/utils
```

などの依存は許容する。

一方で、

```text
lib/api
   ↓
lib/auth
   ↓
lib/api
```

のような循環は避ける。

必要な場合は責務をより低レベルなModuleへ分離する。

---

# 20. types/ の依存

`src/types/` はApplication全体で利用するFrontend共通型を配置するため、Feature固有領域へ依存しない。

以下は禁止する。

```ts
// src/types/common.ts

import type { EmployeeViewModel } from "@/features/employees";
```

Feature固有型はFeature内部へ配置する。

```text
features/employees/types/
```

Application共通型のみ`src/types/`へ配置する。

---

# 21. OpenAPI Generated Code

OpenAPIから生成されたコードは以下へ配置する。

```text
lib/api/generated/
```

Generated CodeはFrontend手書きコードへ依存させない。

基本方向は以下とする。

```text
Feature
   ↓
lib/api/client
   ↓
lib/api/generated
```

または、

```text
Handwritten Code
       ↓
Generated Code
```

とする。

以下は禁止する。

```text
Generated Code
       ↓
Feature
```

```text
Generated Code
       ↓
Application固有Handwritten Code
```

Generated Codeは再生成可能な独立領域として扱う。

---

# 22. API Contract Type

Laravel APIとの契約型はOpenAPI Generated Typeを正とする。

Feature側で同一API DTOをコピーして再定義しない。

例えば以下は避ける。

```text
Generated EmployeeResponse

↓

Feature側で同じEmployeeResponseを再定義
```

必要に応じて、

```text
API DTO
  ↓
Mapper
  ↓
View Model
```

へ変換する。

View ModelはFeature固有型としてFeature内部へ配置する。

---

# 23. Server / Client依存

Server / Client境界については`04_Server・Client 境界.md`で詳細を定義する。

ただしDependency Ruleとして、以下を採用する。

```text
Client Component
       ↓ NG
Server-only Module
```

例えばClient Componentから、

```text
features/employees/server/
```

を直接importしない。

Server専用ModuleはBrowser Bundleへ混入させない。

---

# 24. server-only

Server専用処理であることを明示する必要がある場合は、`server-only`の利用を検討する。

例：

```ts
import "server-only";
```

主な対象は以下とする。

- Laravel API用Credentialを扱うModule
- Backend Credentialの暗号化・復号・保存・取得を行うModule
- Server-side API Client
- Better Auth Server Session参照
- Redis接続を扱うModule
- Server専用Environment Variableを扱う処理
- Server専用Data Fetching

Client側からこれらへ依存させない。

---

# 25. Client Boundary

Client Componentは、その依存先もClientから利用可能なModuleに限定する。

概念的には以下とする。

```text
Client Component
 ├──→ Client Component
 ├──→ UI Primitive
 ├──→ Client-safe Utility
 ├──→ Schema
 ├──→ Shared Type
 └──→ Server Action
```

Server Actionの具体的な扱いは次章以降で定義する。

---

# 26. 型だけの依存

TypeScriptの`import type`であっても、Architecture上のFeature境界を無視しない。

例えば、

```ts
import type { EmployeeType } from "@/features/employees";
```

を`lib/`から行うことは、Runtime Dependencyが発生しなくても原則禁止する。

型依存もDependency Ruleの対象とする。

---

# 27. 循環依存

循環依存は禁止する。

例：

```text
employees
 ↓
skills
 ↓
employees
```

```text
components
 ↓
lib
 ↓
components
```

```text
api
 ↓
auth
 ↓
api
```

循環依存が発生した場合は、以下を検討する。

- 共通概念の抽出
- 責務の再配置
- Feature Composition位置の変更
- API Boundaryの見直し
- Module分割

---

# 28. 共通化と依存関係

複数Featureから利用されるという理由だけで、即座にShared Layerへ移動しない。

以下の順番で判断する。

```text
Feature内部で実装
      ↓
複数Featureで必要になる
      ↓
意味・責務が本当に同じか確認
      ↓
共通概念ならSharedへ昇格
```

使用箇所の数ではなく、意味と責務が共通かどうかを基準とする。

---

# 29. Framework依存

Next.js固有APIへの依存は、必要な場所に限定する。

特にFeature内のPureな処理へ、不要に以下を持ち込まない。

```text
next/navigation
next/headers
next/cache
next/server
```

Next.js固有処理を必要以上にFeature内部へ拡散させない。

ただし、Server ComponentやServer ActionなどNext.js機能そのものを利用するFeatureでは必要な依存を許容する。

完全なFramework非依存化を目的とはしない。

---

# 30. React依存

FrontendであるためReactへの依存そのものは問題としない。

ただし、

```text
Mapper
Formatter
Schema
Pure Utility
```

などReactに依存する必要のないModuleへ、不要にReact依存を持ち込まない。

Pureな処理はPureなModuleとして維持する。

---

# 31. Dependency Ruleの自動検証

Dependency RuleはDocumentationだけでなく、可能な範囲でToolによる自動検証を行う。

候補として以下を利用する。

```text
ESLint
```

必要に応じて、

- import restriction
- restricted path
- dependency boundary rule
- circular dependency detection

などを導入する。

具体的なToolおよびRuleはFrontendのLint設定時に決定する。

---

# 32. Import Alias

Project内ImportではPath Aliasを利用する。

例：

```ts
import { EmployeeList } from "@/features/employees";
import { Button } from "@/components/ui/button";
import { apiClient } from "@/lib/api";
```

Feature外から深いRelative Importを行うことは避ける。

Feature内部については近距離のRelative Importを許容する。

---

# 33. Dependency設計原則

Frontend全体で以下を原則とする。

```text
依存は上から下へ流す
```

```text
FeatureはFramework Layerを知らない
```

```text
Shared LayerはFeatureを知らない
```

```text
Feature間の直接依存を避ける
```

```text
Feature外部からはPublic APIを利用する
```

```text
Generated CodeはApplication Codeを知らない
```

```text
Server-only CodeをClientへ流さない
```

```text
型依存もArchitecture Dependencyとして扱う
```

```text
循環依存を作らない
```

---

# 34. 全体Dependency

最終的な依存構造を以下とする。

```text
                 ┌─────────────────┐
                 │      app/       │
                 │ Framework Layer │
                 └────────┬────────┘
                          │
                          ▼
                 ┌─────────────────┐
                 │    features/    │
                 │  Feature Layer  │
                 └────────┬────────┘
                          │
             ┌────────────┼────────────┐
             │            │            │
             ▼            ▼            ▼
      ┌────────────┐ ┌──────────┐ ┌──────────┐
      │components/ │ │   lib/   │ │  types/  │
      │ Shared UI  │ │Technical │ │  Shared  │
      └─────┬──────┘ └────┬─────┘ └──────────┘
            │              │
            └──────┬───────┘
                   │
                   ▼
             Lower-level
             Dependencies
```

OpenAPI Generated Codeは`lib/api/`配下のさらに低レベルな依存先として扱う。

```text
features
   ↓
lib/api
   ↓
generated
```

---

# 35. 決定事項

Frontendのレイヤー・依存関係として、以下を正式採用する。

- FrontendはFramework / Feature / Shared・Technicalの3段階で整理する
- 基本依存方向を`app → features → components / lib / types`とする
- 下位Layerから上位Layerへの依存を原則禁止する
- `app/`からFeature・Shared領域への依存を許可する
- Featureから`app/`への依存は禁止する
- `components / lib / types`からFeatureへの依存は禁止する
- Feature間の直接依存は原則避ける
- 複数FeatureのCompositionは原則として上位Layerで行う
- Feature内部は厳密なLayer構造を強制しない
- Feature内部でも依存を単方向に保つ
- 循環依存は禁止する
- Feature外部からは`index.ts`によるPublic API経由を基本とする
- Feature外部からのDeep Importは原則禁止する
- Feature内部ではInternal Importを許可する
- `components/ui/`はFeature非依存とする
- `components/layout/`はApplication共通処理への限定的な依存を許可する
- `lib/`はFeature非依存の技術的基盤とする
- `types/`はFeatureへ依存しない
- OpenAPI Generated Codeは手書きApplication Codeへ依存しない
- Laravel API契約型はOpenAPI Generated Typeを正とする
- Feature固有View ModelはFeature内部に配置する
- Client ComponentからServer-only Moduleへの直接依存は禁止する
- Server専用処理には必要に応じて`server-only`を利用する
- 型だけの依存もDependency Ruleの対象とする
- Next.js固有依存を不要に低レベルModuleへ拡散させない
- 共通化は責務・意味が共通であることを確認してから行う
- Path Aliasを利用して依存元を明確にする
- Dependency Ruleは可能な範囲でESLint等によって自動検証する

以上をFrontendのレイヤー・依存関係とする。
