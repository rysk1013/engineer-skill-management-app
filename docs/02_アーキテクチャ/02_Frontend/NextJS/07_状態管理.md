# 07_状態管理

## 1. 目的

本プロジェクトでは、Frontend Stateを一律にGlobal Storeへ集約せず、Stateの性質に応じて適切な場所へ配置する。

目的は以下とする。

- 不要なClient Stateを減らす
- Server Component Firstと整合させる
- Server StateをClientへ重複保持しない
- Search / Filter / PaginationをURLと同期する
- Form StateをFeature内部へ閉じ込める
- UI Stateを必要最小限のComponent Scopeへ配置する
- Contextの乱用を防ぐ
- Redux / Zustand等のGlobal State Libraryを必要になるまで導入しない
- Stateの二重管理による不整合を防ぐ
- StateのOwnershipを明確にする

基本優先順位を以下とする。

```text
1. Server State
2. URL State
3. Form State
4. Local UI State
5. Context
6. Global State Library
```

Stateが必要になった場合、上から順番に適用可能かを判断する。

---

## 2. 基本原則

Frontendでは、

```text
Stateを持たない
```

ことを第一候補とする。

Stateが必要な場合のみ、適切なScopeへ配置する。

避ける考え方：

```text
Dataがある
↓
useStateへ入れる
```

推奨：

```text
Dataがある
↓
本当にClient Stateとして保持する必要があるか？
↓
State種別を判断
↓
適切な場所へ配置
```

---

## 3. State分類

本プロジェクトではStateを主に以下へ分類する。

| State | 主な管理場所 |
|---|---|
| Server State | Laravel / Server Component |
| URL State | URL Search Params / Path |
| Form State | Form Component |
| Local UI State | Client Component |
| Shared UI State | React Context |
| Global Client State | Global State Library |

この分類を混在させないことを基本とする。

---

## 4. Server State

Server Stateとは、Backend側がSource of TruthとなるDataを指す。

例：

```text
Employee
Skill
Skill Category
Department
EmployeeSkill
User
Permission
```

これらの正はLaravel API / Databaseに存在する。

FrontendではServer Stateを必要以上にClient Stateへ複製しない。

---

## 5. Server Stateの基本Flow

Readでは以下を基本とする。

```text
Laravel API
    ↓
Server Query
    ↓
Server Component
    ↓
UI
```

例えばEmployee一覧を取得した後、

```ts
const [employees, setEmployees] = useState(initialEmployees);
```

と無条件でClient Stateへコピーしない。

表示だけであればServerから取得したDataをそのまま利用する。

---

## 6. Server StateをClientへ複製しない

以下のような二重管理を避ける。

```text
Laravel
↓
Server Component
↓
Client State
```

Client側のDataを編集していないにもかかわらずServer StateをClientへコピーすると、

```text
Server Data
≠
Client Data
```

となる可能性が生まれる。

Server StateのSource of TruthはServerに維持する。

---

## 7. Server State更新

Server Stateを更新する場合は、

```text
Client / Form
     ↓
Server Action
     ↓
Laravel API
     ↓
Server State更新
     ↓
Revalidation
     ↓
UI更新
```

を基本とする。

Client Storeを直接更新することをServer State更新のAuthorityとはしない。

---

## 8. URL State

以下のようなNavigationと関連するStateはURLへ置くことを第一候補とする。

```text
Search Keyword
Filter
Sort
Pagination
Selected Tab
表示対象ID
```

例：

```text
/employees
  ?keyword=php
  &department=3
  &sort=name
  &page=2
```

---

## 9. URL Stateを採用する理由

URL Stateには以下の利点がある。

```text
Share可能
Bookmark可能
Reloadしても維持
Back / Forward対応
Server Renderingと統合
Navigationと同期
Global Client State不要
```

一覧画面の状態は可能な限りURLへ表現する。

---

## 10. Search State

Search InputはClient Componentにできる。

ただし検索条件のSource of TruthはURLとする。

```text
Search Input
     ↓
URL更新
     ↓
Server Component
     ↓
Laravel API
```

つまり、

```text
Input Interaction
=
Client

Search State
=
URL

Search Result
=
Server State
```

とする。

---

## 11. Filter State

一覧FilterもURL Stateを基本とする。

例：

```text
/employees?department=3
```

複数Filterの場合も、

```text
/employees
  ?department=3
  &status=active
  &skill=php
```

のようにURLへ表現する。

Filter条件をRedux / Zustand等に置くことを標準としない。

---

## 12. Pagination State

PaginationはURL Stateへ配置する。

```text
/employees?page=3
```

Pagination PageをLocal Stateだけで保持しない。

これによりBrowser Navigationとの整合性を維持する。

---

## 13. Sort State

Sort条件もURLへ配置する。

例：

```text
/employees?sort=name&direction=asc
```

Sort状態が一覧画面の表示結果を決定する場合、URL Stateとして扱う。

---

## 14. Tab State

Tabについては、その状態がNavigationとして意味を持つかで判断する。

例えば、

```text
Employee Detail
├── Profile
├── Skills
└── Permissions
```

で直接URL共有したい場合は、

```text
/employees/10?tab=skills
```

などのURL Stateを利用する。

一方、

```text
一時的な表示切替
```

にすぎない場合はLocal UI Stateを利用できる。

---

## 15. URLへ置く判断基準

以下のいずれかに該当する場合、URL Stateを優先する。

```text
Reload後も維持したい
URL共有したい
Bookmarkしたい
Back / Forwardしたい
Server Data Fetching条件になる
Navigationとして意味がある
```

---

## 16. URLへ置かないState

以下のような短命なUI Stateは通常URLへ置かない。

```text
Modal Open / Close
Dropdown Open / Close
Tooltip表示
Accordion展開
Hover
Temporary Selection
```

これらはLocal UI Stateを基本とする。

---

## 17. Form State

Form入力中のStateはForm Stateとして管理する。

例：

```text
Employee Form
Skill Form
EmployeeSkill Form
Permission Form
```

Form Stateには、

```text
Input Value
Touched
Dirty
Field Error
Submitting
```

等が含まれる。

---

## 18. Form StateのScope

Form Stateは原則としてそのForm Feature内部へ閉じ込める。

```text
EmployeeForm
     ↓
Employee Form State
```

Global StoreへForm Stateを置かない。

避ける構成：

```text
Global Store
├── employeeForm
├── skillForm
├── permissionForm
└── ...
```

---

## 19. Formの初期値

Edit Formの初期値はServer側から取得する。

```text
Server Component
      ↓
Employee Data
      ↓
EmployeeForm
      ↓
Form Initial Values
```

初期値を受け取った後の入力中DataのみForm Stateとして管理する。

---

## 20. Form StateとServer State

Form StateはServer Stateの一時的な編集表現として扱う。

```text
Server State
    ↓
Form Initial Value
    ↓
Form State
    ↓
Server Action
    ↓
Server State
```

Form StateそのものをServer StateのSource of Truthとはしない。

---

## 21. Form Validation State

Frontend Validation ErrorはForm Stateに保持できる。

例：

```text
name:
  "必須です"

experienceMonths:
  "1か月以上を入力してください"
```

Laravelから返されたValidation ErrorもForm ErrorへMappingできる。

具体的なValidation設計は`09_フォーム・Validation.md`で定義する。

---

## 22. Local UI State

Browser上だけで意味を持つ短命なStateはLocal UI Stateとして扱う。

例：

```text
Modal Open / Close
Dropdown Open / Close
Accordion
Popover
Tooltip
Selected Row
Temporary Toggle
Local Loading
Preview
```

基本的には`useState` / `useReducer`等を利用する。

---

## 23. Local Stateは最も近いComponentへ置く

Local UI Stateは、そのStateを必要とするComponentに最も近い場所へ配置する。

例えば、

```text
EmployeeDeleteDialog
```

だけがDialog Stateを必要とする場合、

```text
EmployeeDeleteDialog
└── isOpen
```

とする。

Page全体へLift Upしない。

---

## 24. State Lift Up

複数Sibling Componentが同じStateを必要とする場合のみ、共通ParentへLift Upする。

```text
Parent
├── Component A
└── Component B
```

AとBが同じStateを利用するなら、

```text
Parent
└── State
    ├── A
    └── B
```

とする。

---

## 25. Stateを必要以上にLift Upしない

以下の理由だけでPageやLayoutへStateを移動しない。

```text
将来使うかもしれない
他でも必要になるかもしれない
共通化した方がきれいそう
```

Stateは実際に共有が必要になった段階でScopeを広げる。

---

## 26. Derived State

既存Stateから計算できる値を別Stateとして持たない。

避ける例：

```ts
const [firstName, setFirstName] = useState("");
const [lastName, setLastName] = useState("");
const [fullName, setFullName] = useState("");
```

`fullName`は、

```ts
const fullName = `${firstName} ${lastName}`;
```

のように導出する。

重複Stateは同期不整合の原因になるため避ける。

---

## 27. PropsからStateを無条件に作らない

以下を安易に行わない。

```ts
const [employee, setEmployee] = useState(props.employee);
```

PropsとLocal Stateという2つのSource of Truthが生まれるためである。

編集目的など明確な理由がある場合のみLocal Stateへ変換する。

---

## 28. StateのSource of Truth

1つのDataに対してSource of Truthを1つにする。

避ける例：

```text
URL
+
Context
+
Zustand
```

ですべて同じ`departmentFilter`を管理する。

推奨：

```text
departmentFilter
=
URL State
```

のようにOwnershipを一意にする。

---

## 29. React Context

Contextは、Component Tree内の複数箇所で同じClient Stateを共有する必要がある場合に利用する。

候補例：

```text
UI Theme
Feature内Wizard State
Feature内Shared Interaction State
```

ただしContextをGlobal Store代替として乱用しない。

---

## 30. Contextを利用する条件

以下をすべて検討してからContextを採用する。

```text
複数階層で共有する必要があるか？
Propsで渡すと過度なProp Drillingになるか？
URL Stateではないか？
Server Stateではないか？
Form Stateではないか？
Local Stateでは足りないか？
```

Local Stateで十分ならContextを使用しない。

---

## 31. ContextへServer Stateを置かない

以下のようなContextをServer State Storeとして使用することを標準としない。

```text
EmployeeContext
SkillContext
DepartmentContext
```

Server StateはServer Component / Server Queryを基本とする。

---

## 32. ContextへAuthentication Dataを複製しない

Auth.js Sessionを独自Contextへ丸ごと複製することを基本としない。

```text
Auth.js Session
↓
Custom Auth Context
↓
さらにLocal State
```

のような多重管理を避ける。

Authentication StateはAuth.jsをSource of Truthとする。

具体的な扱いは`08_認証・認可.md`で定義する。

---

## 33. Providerの配置

Context Providerは必要な最小範囲へ配置する。

避ける構成：

```text
Root Layout
 ↓
Application全体Provider
```

必要がない場合までRootへ配置しない。

推奨：

```text
Feature Boundary
 ↓
必要な範囲だけProvider
```

---

## 34. Provider Hellを避ける

以下のような構成を避ける。

```tsx
<AuthProvider>
  <ThemeProvider>
    <EmployeeProvider>
      <SkillProvider>
        <FilterProvider>
          <ModalProvider>
            {children}
          </ModalProvider>
        </FilterProvider>
      </SkillProvider>
    </EmployeeProvider>
  </ThemeProvider>
</AuthProvider>
```

Providerが増え始めた場合はState Ownership自体を再評価する。

---

## 35. Global State Library

Redux / Zustand等のGlobal Client State LibraryはMVP開始時には導入しない。

```text
Initial State Management
=
React
+
URL
+
Server Component
+
Form State
```

を基本とする。

---

## 36. Global State Libraryを初期導入しない理由

今回のApplicationでは大半のStateを以下へ分類できる。

```text
Employee Data
→ Server State

Search / Filter
→ URL State

Form
→ Form State

Modal
→ Local State

Auth
→ Auth.js
```

そのため初期段階でGlobal Storeを導入する明確な必要性がない。

---

## 37. Global Store導入条件

以下のような状況が継続的に発生した場合のみGlobal State Libraryを再評価する。

```text
離れた多数のClient Component間で
同一Stateを共有する必要がある

Contextでは更新頻度・規模が扱いづらい

State LifetimeがRouteをまたぐ

Local / URL / Form / Server Stateでは
自然に表現できない

Complex Client Workflowが存在する
```

---

## 38. Global Storeを導入しない理由にしないもの

以下だけを理由としてGlobal Storeを導入しない。

```text
Component間でDataを渡したくない
Propsを書くのが面倒
Redux / Zustandを使ってみたい
将来必要そう
```

具体的なProblemが発生してから導入する。

---

## 39. Global Store候補

Global State Libraryが必要になった場合、要件を再評価したうえでToolを選定する。

初期Architectureでは特定Libraryへ固定しない。

候補として、

```text
Zustand
Redux Toolkit
```

等はあり得るが、MVPの標準依存には含めない。

---

## 40. Server State Library

TanStack Query / SWR等についても初期段階では必須としない。

Server Component / Server Actionを中心とするため、

```text
Server State
↓
Client Cache Library
```

へ全面的に移す必要はない。

---

## 41. Client-side Server State Library導入条件

以下のClient-side Data Accessが増えた場合に再評価する。

```text
Polling
Background Refetch
Infinite Scroll
Client Cache
Request Deduplication
Optimistic Update
Complex Retry
Frequent Client-side Fetch
```

これらが限定的であれば、Route Handler + Local State等で対応する。

---

## 42. Authentication State

AuthenticationのSource of TruthはAuth.jsとする。

```text
Browser
 ↓
Auth.js Session
 ↓
Next.js Server
```

UserやSession情報を独自Global Storeへ重複保存しない。

Authorization表示に必要なFrontend向け情報のみ利用する。

詳細は`08_認証・認可.md`で定義する。

---

## 43. Permission State

PermissionもBackend / Authentication ContextをSource of Truthとする。

以下のような独自Global Permission Storeを標準としない。

```text
Global Store
└── permissions[]
```

必要なPermission DataをServer側で取得し、表示制御へ利用する。

Client Interactionで必要な場合のみ必要最小限の情報をClientへ渡す。

---

## 44. Loading State

Server Data FetchingのLoadingは、

```text
loading.tsx
Suspense
```

を基本とする。

Server RequestのLoadingをClient `useState`へ無理に再実装しない。

Mutation中の、

```text
Submitting
Pending
```

などはForm / Local UI Stateとして管理する。

---

## 45. Error State

Server Read Errorは、

```text
Error Boundary
error.tsx
```

等を基本とする。

Form Validation ErrorはForm Stateへ置く。

Local Interaction Errorは必要なComponent Scopeへ置く。

ErrorをすべてGlobal Storeへ集約しない。

---

## 46. Success Message State

Mutation後のFeedbackはUXに応じて、

```text
Redirect先で表示
Toast
Inline Message
```

等を利用できる。

ただしApplication全体のSuccess Messageを永続的なGlobal Stateとして管理しない。

具体的なFeedback方式はUI / Error Handling設計で決定する。

---

## 47. Modal State

Modal Open / Closeは原則Local UI Stateとする。

```text
EmployeeDeleteButton
       ↓
DeleteDialog
       ↓
isOpen
```

複数の離れたComponentから同じModalを制御する必要が出た場合のみScope拡大を検討する。

---

## 48. Selection State

Table Row Selectionなどは用途に応じて判断する。

Page内で完結する一時的Selection：

```text
Local UI State
```

URL共有やNavigationとして意味があるSelection：

```text
URL State
```

Serverに保存すべきSelection：

```text
Server State
```

Stateの性質によって決める。

---

## 49. Wizard State

複数Step Formなど、同一Client Workflow内で複数ComponentがStateを共有する場合は、

```text
Form Library
Local Parent State
Context
```

の順に検討する。

Wizardだからという理由だけでGlobal Storeを利用しない。

---

## 50. Browser Storage

`localStorage` / `sessionStorage`をState Managementの標準手段としない。

利用する場合は、Browserへ永続化する明確な理由を必要とする。

候補例：

```text
非機密なUI Preference
一時的Draft
```

---

## 51. Browser Storageへ保存しないもの

以下はBrowser Storageへ保存しない。

```text
Sanctum Token
Server Secret
Password
Credential
機密性の高い認証情報
```

AuthenticationについてはAuth.jsの設計に従う。

---

## 52. URLとLocal Stateを二重管理しない

例えばSearch Inputで、

```text
URL keyword
+
useState keyword
```

を常に同期し続ける構成は、必要がなければ避ける。

URLをSource of Truthとして利用できる場合はURLへ寄せる。

一時的なDebounce Inputなど、明確な理由がある場合のみLocal Stateを併用する。

---

## 53. Debounce

Search Inputでは必要に応じてDebounceを利用できる。

概念的には、

```text
Input
 ↓
Temporary Client Value
 ↓
Debounce
 ↓
URL更新
 ↓
Server Read
```

となる。

この場合でも最終的なSearch ConditionのSource of TruthはURLとする。

---

## 54. Reset

State Resetの責務もState Ownerへ置く。

例えば、

```text
Filter Reset
→ URLを初期状態へ戻す

Form Reset
→ Form Stateを初期値へ戻す

Modal Close
→ Local UI Stateをfalseへ戻す
```

Application全体を対象とした汎用Global Reset機構は作らない。

---

## 55. State Lifetime

Stateを配置するときはLifetimeを考慮する。

```text
Component Lifetime
→ Local State

Form Lifetime
→ Form State

URL / Navigation Lifetime
→ URL State

Server Persisted Lifetime
→ Server State

Feature Tree Lifetime
→ Context

Application-wide Client Lifetime
→ Global Store
```

State LifetimeとScopeを一致させる。

---

## 56. State Ownership

Stateは、それを変更する責務を持つ場所がOwnershipを持つ。

例えば、

```text
Employee登録値
→ Laravel

Employee Search条件
→ URL

Employee Form入力
→ Form

Delete Dialog Open
→ Delete Dialog Component
```

Ownershipが曖昧なStateを作らない。

---

## 57. State判断フロー

Stateが必要になった場合は以下で判断する。

```text
Stateが必要
   │
   ▼
BackendがSource of Truth？
   │
   ├── Yes
   │    ↓
   │ Server State
   │
   └── No
        │
        ▼
URLで表現すべき？
        │
        ├── Yes
        │    ↓
        │ URL State
        │
        └── No
             │
             ▼
Form入力？
             │
             ├── Yes
             │    ↓
             │ Form State
             │
             └── No
                  │
                  ▼
単一Component周辺だけ？
                  │
                  ├── Yes
                  │    ↓
                  │ Local UI State
                  │
                  └── No
                       │
                       ▼
Component Tree内で共有？
                       │
                       ├── Yes
                       │    ↓
                       │ Context
                       │
                       └── No
                            │
                            ▼
本当にApplication-wide
Client Stateが必要？
                            │
                            ├── Yes
                            │    ↓
                            │ Global State Libraryを検討
                            │
                            └── No
                                 ↓
                            設計を再確認
```

## 58. State Architecture全体像

本プロジェクトのState Architectureを以下とする。

```text
┌───────────────────────────────────┐
│ Laravel / Database                │
│                                   │
│ Server State                      │
└──────────────────┬────────────────┘
                   │
                   ▼
┌───────────────────────────────────┐
│ Next.js Server                    │
│                                   │
│ Server Component                  │
│ Server Query                      │
│ Server Action                     │
└──────────────────┬────────────────┘
                   │
                   ▼
┌───────────────────────────────────┐
│ Browser                           │
│                                   │
│ URL State                         │
│ Form State                        │
│ Local UI State                    │
│ Context（必要時のみ）             │
│ Global Store（最終手段）          │
└───────────────────────────────────┘
```

---

## 59. State優先順位

Stateを持つ必要がある場合、以下の順番で検討する。

```text
Server State
     ↓
URL State
     ↓
Form State
     ↓
Local UI State
     ↓
Context
     ↓
Global State Library
```

この順番は、

```text
すべてのStateをServerへ置く
```

という意味ではない。

Stateの性質を判断するときの優先的な検討順序とする。

## 60. 代表例

本Applicationでは以下のように分類する。

| Data / State | 管理場所 |
|---|---|
| Employee一覧 | Server State |
| Employee詳細 | Server State |
| Skill一覧 | Server State |
| EmployeeSkill | Server State |
| Search Keyword | URL State |
| Department Filter | URL State |
| Page番号 | URL State |
| Sort条件 | URL State |
| Employee Form入力 | Form State |
| Skill Form入力 | Form State |
| Form Validation Error | Form State |
| Delete Dialog Open | Local UI State |
| Dropdown Open | Local UI State |
| Table一時Selection | Local UI State |
| Auth Session | Auth.js |
| Feature Tree内の共有Client State | Contextを検討 |
| Application-wide Client State | Global Storeを必要時のみ検討 |

## 61. 採用しない初期構成

MVP開始時点では以下のような構成を採用しない。

```text
Redux Store
├── employees
├── skills
├── filters
├── auth
├── forms
└── ui
```

また、

```text
Zustand Store
├── employees
├── employeeSearch
├── employeeForm
└── ...
```

のようにServer StateやURL StateまでGlobal Storeへ集約しない。

---

## 62. 基本State Model

最終的には以下を基本形とする。

```text
Business Data
→ Server State

Navigation / Search Condition
→ URL State

Form Editing
→ Form State

Temporary Interaction
→ Local UI State

Tree-wide Client Sharing
→ Context

Complex Application-wide Client State
→ Global Store
```

## 63. 決定事項

Frontendの状態管理として、以下を正式採用する。

- Stateを持たない設計を最初に検討する
- StateをServer / URL / Form / Local UI / Context / Globalに分類する
- State管理の検討順序を`Server → URL → Form → Local UI → Context → Global Store`とする
- Employee / Skill等の業務DataはServer Stateとして扱う
- Server Stateを不要にClient Stateへ複製しない
- Mutation後はServer Stateを更新しRevalidationでUIへ反映する
- Search / Filter / Sort / PaginationはURL Stateを基本とする
- Navigationとして意味のあるTab StateはURL Stateを検討する
- Modal / Dropdown等の短命なUI StateはLocal Stateとする
- Form入力はForm StateとしてFeature内部へ閉じ込める
- Form StateをGlobal Storeへ置かない
- Edit Formの初期値はServer Stateから渡す
- Derived Stateを不要にStateとして保持しない
- Propsを無条件でLocal Stateへコピーしない
- 1つのDataに複数のSource of Truthを作らない
- Local UI Stateは利用箇所に最も近いComponentへ配置する
- State共有が必要な場合のみ共通ParentへLift Upする
- 将来予測だけでStateを上位へLift Upしない
- Contextは複数階層で共有が必要なClient Stateに限定する
- ContextをServer State Storeとして使用しない
- Auth.js Sessionを独自Contextへ不要に複製しない
- Context Providerは必要最小限の範囲へ配置する
- Provider Hellを避ける
- Redux / Zustand等のGlobal State LibraryをMVP開始時には導入しない
- Global Storeは具体的なApplication-wide Client State問題が発生した場合のみ再評価する
- TanStack Query / SWR等のClient-side Server State LibraryもMVP開始時には必須としない
- Client-side Server State管理が複雑化した場合にLibrary導入を再評価する
- AuthenticationのSource of TruthはAuth.jsとする
- Permissionを独自Global Storeへ不要に複製しない
- Server Read Loadingは`loading.tsx` / Suspenseを基本とする
- Mutation PendingはForm / Local UI Stateとして扱う
- Error StateをGlobal Storeへ一律集約しない
- Modal StateはLocal UI Stateを基本とする
- Browser StorageをState Managementの標準手段としない
- Sanctum TokenやCredentialをBrowser Storageへ保存しない
- URL StateとLocal Stateを理由なく二重管理しない
- Debounce時でも最終的な検索条件のSource of TruthはURLとする
- StateのLifetimeとScopeを一致させる
- State Ownershipを明確にする

以上をFrontendの状態管理方針とする。
