# 13_テスト戦略

## 1. 目的

本プロジェクトでは、Frontend Testを単なるCoverage確保ではなく、UI Behavior・Server Boundary・API Contract・Authentication / Authorization Flowを安全に変更するための仕組みとして設計する。

目的は以下とする。

- Test Levelごとの責務を明確にする
- 同じBehaviorを複数Levelで過剰に重複Testしない
- User-visible Behaviorを中心にTestする
- Implementation Detailへの依存を避ける
- Server Component First構成に適したTest Strategyとする
- Client Component Interactionを適切にTestする
- Server Action / Route Handler等のServer BoundaryをTestする
- Form / Validationを適切なLevelでTestする
- Authentication / Authorizationの重要Flowを保証する
- OpenAPI Contractとの不整合を早期検知する
- E2E Testを重要Flowへ集中させる
- Test Suiteを高速かつ保守可能に保つ
- CIで再現可能なTest Environmentを構築する

基本方針を以下とする。

```text id="7zgfkd"
Many
↓
Fast / Focused Tests

Few
↓
Slow / End-to-End Tests
```

また、

```text id="1sy03q"
Test
=
Behavior Verification

Not
=
Implementation Verification
```

を基本とする。

---

## 2. Test Pyramid

Frontend Testを概ね以下のLayerへ分ける。

```text id="bh2odh"
          E2E
        ─────────
      Integration
    ───────────────
 Component / Unit
─────────────────────
```

下位Testを多く、上位Testを重要Flowへ限定する。

ただしTest数自体を目的化しない。

## 36. Better Auth自体をTestしない

Better Auth Library内部挙動をFrontend Application側で再Testしない。

Test対象は、

```text
Better Auth Configuration
Application Authentication Flow
Laravel Authentication連携
Better Auth SessionとBackend Credentialの対応
Redis Session / Credential Storage連携
Backend Credentialの暗号化・復号
Protected Route Behavior
Logout / Session Expiration
```

とする。

Better Authの内部実装ではなく、
Applicationが構築するAuthentication Boundaryを検証する。

特に以下を確認する。

- Laravel Authentication成功後にBrowser Sessionが成立する
- Laravel Authentication失敗時にSessionを作成しない
- Better Auth SessionとBackend Credentialが適切に対応付けられる
- Sanctum TokenをBetter Auth Sessionへ直接保存しない
- Sanctum TokenをBrowserへ公開しない
- RedisからSessionまたはCredentialを取得できない場合は認証済みとして扱わない
- Logout時にSessionとBackend Credentialを失効・削除する
- Sanctum Token失効時に再Loginを要求する

具体的なTest実装はBetter Authの採用Versionと公式APIを確認して決定する。

## 54. Contract Breaking Change

```text id="7vla0j"

```

でContract Errorを隠さない。

## 66. Deterministic Test

## 67. Date / Time Test

Current Date依存処理は固定可能な設計を優先する。

Year-Month表示等もTimezone差によってFlakyにならないようにする。

---

## 68. External Service

外部Serviceを利用する場合、通常のFrontend Testでは直接依存しない。

必要に応じてBoundaryをMockする。

---

## 69. Flaky Test

Flaky Testを放置しない。

```text id="c1mrmv"
たまにFailする
↓
Retryで隠す
```

を標準対応としない。

Root Causeを修正する。

---

## 70. Test Retry

E2E RunnerのRetry機能はInfrastructure等の一時的Failure対策として限定的に利用できる。

Application BugをRetryによって隠さない。

---

## 71. Parallel Test

独立Testは可能な限りParallel実行可能にする。

共有DB State / Global Stateに強く依存するTest Architectureを避ける。

---

## 72. Test Isolation

各Testは独立して成立することを基本とする。

```text id="ehw7se"

```

## 82. Open Redirect

---

## 83. CSRF

Browser → Next.js Boundaryに必要なCSRF Protectionは利用するFramework / Auth Mechanismの標準機構に従う。

Application Testでは重要なMutation Flowが正しくProtection下で動くことを確認する。

Framework内部CSRF実装そのものを再Testしない。

---

## 84. Accessibility E2E

重要FlowではKeyboardのみで主要操作を完了できることをE2E / Manual Testで確認する。

Automated Component Testだけへ依存しない。

## 117. 決定事項

Frontend Test Strategyとして以下を正式採用する。

- TestをStatic Analysis / Unit / Component / Integration / Contract / E2Eへ分類する
- FastでFocusedなTestを多く、E2Eを重要Flowへ限定する
- Test数やCoverage Percentageそのものを目的化しない
- User-visible BehaviorをTestの中心とする
- Implementation Detailへ過剰に依存しない
- TypeScriptを重要Quality Gateとして利用する
- OpenAPI変更によるCompile ErrorをContract Change Signalとして活用する
- ESLint等でArchitecture Boundaryを可能な限り自動検出する
- Formatter / Mapper / Schema / Utility等のPure LogicをUnit Testする
- 単純なRe-exportやFramework Wrapperを機械的にUnit Testしない
- Client Component / Form / Dialog / Table等をComponent Testする
- DOM TestではRole / Label / Accessible Nameを優先する
- `data-testid`をDefault Selectorとしない
- Shared UIではInteraction / Accessibilityを中心にTestする
- Feature UIではFeature固有BehaviorをTestする
- EmployeeSkillのFrontend UX RuleをComponent / Schema Testする
- Business Invariantの最終保証はLaravel Domain Testへ置く
- Server ComponentのFramework内部挙動を細かくUnit Testしない
- Server QueryをIntegration寄りにTestする
- Frontend Testから実Laravel Backendへ常時依存しない
- API ResponseをNetwork Boundaryで制御可能なTest方式を採用候補とする
- Generated API Client自体を大量にUnit Testしない
- Generated Code Drift / Type Check / Adapter Integrationを重視する
- Handwritten API ClientのAuthentication / Error Normalization等をTestする
- `lib/api/errors.ts`を重要Test対象とする
- Server ActionでAuthentication / Validation / Normalization / API Call / Error Mapping / RevalidationをTestする
- Client ValidationをBypassしたServer Actionも安全であることをTestする
- Route HandlerのHTTP SemanticsをTestする
- Authentication FlowをApplication LevelでTestする
- Better Auth Library内部を再Testしない
- Laravel AuthenticationとBetter Auth Sessionの連携をTestする
- Better Auth SessionとBackend Credentialの対応関係をTestする
- Redis障害時に認証がFail ClosedとなることをTestする
- Backend Credentialの暗号化・復号とServer-only境界をTestする
- Sanctum TokenがBrowserへ公開されないことをTestする
- Frontend AuthorizationはUI BehaviorとしてTestする
- Laravel AuthorizationをFrontend Testで代替しない
- Role全組み合わせではなく重要Capability Differenceを中心にComponent Testする
- Resource-level Authorizationは代表FlowをE2Eでも確認する
- Error / Empty / Loading / Pendingを別StateとしてTestする
- AccessibilityをComponent Testへ組み込む
- Automated Accessibility CheckだけでAccessibilityを完全保証したことにしない
- 巨大UI Snapshotを大量に利用しない
- Integration TestでFrontend Module間Boundaryを確認する
- OpenAPIをContract Testの中心とする
- CIでGenerated Code Driftを検出する
- `any`等でContract Errorを隠さない
- E2EはCritical Business Flowへ集中する
- Login / Employee / EmployeeSkill / Skill / Permissionを主要E2E候補とする
- Browser → Next.js → Laravel → PostgreSQLを組み合わせた実Integration E2Eを重要Flowで実施する
- Docker方針とTest Environmentを整合させる
- Test DatabaseをDevelopment / Productionから分離する
- Test Dataを明示的かつ独立して構築する
- 巨大な共有Fixtureへの依存を避ける
- TestをDeterministicにする
- Flaky TestをRetryだけで隠さない
- Test間のExecution Order Dependencyを禁止する
- MockはExternal / Expensive Boundaryを中心に利用する
- Internal Moduleを過剰にMockしない
- Server-only Boundary ViolationをStatic Analysis / Buildで検知する
- Production Build成功をCI Quality Gateとする
- DevelopmentだけでなくProduction相当Behaviorを確認する
- Sensitive SecretがClient Bundleへ露出しないことを確認する
- Frontend Security TestはBackend Security Testを代替しない
- `dangerouslySetInnerHTML`をMVPでは原則利用しない
- Open Redirect等Authentication BoundaryをTestする
- Framework内部Security実装そのものを再Testしない
- 重要FlowではKeyboard操作等のManual / E2E Accessibility確認も行う
- Manual Testを必要に応じて許可する
- Test NamingはBehaviorを表現する
- Test Fileは対象Code付近へのCo-locationを基本候補とする
- E2Eは専用Directoryへ分離する
- Test Directoryを過剰に分類しない
- Coverageは補助指標として扱う
- MVPでは厳格な高Coverage Thresholdを必須としない
- Mutation Testing等の高度なTest ToolをMVP必須としない
- Test RunnerはApplication全体で1つへ統一する
- Testing Library系ApproachをComponent Test候補とする
- PlaywrightをE2E Toolの有力候補とする
- Tool / Versionは実装時に現行状況を確認して正式決定する
- CIではGenerated Code Check / Lint / Type Check / Tests / Build / E2Eを実施する
- Pull RequestではFast Feedbackを優先する
- Main / Deployment前にはより広いRegression Testを実施できる
- Deployment後のSmoke Testを導入候補とする
- Production Data / Production CredentialをAutomated Testへ利用しない
- E2E Failure Investigation用Artifactを安全に保存できるようにする
- FrontendではUX Behavior、LaravelではBusiness Correctnessを中心にTestする
- Validation / Authorization / Error HandlingについてFrontendとLaravelの責務を分けてTestする
- 同一Ruleを意味なくすべてのTest Levelへ重複させない

以上をFrontend Test Strategyとする。
