# 05_データ取得・更新

## 1. 目的

本プロジェクトでは、Server Component Firstの方針をデータ取得・更新にも適用する。

FrontendでのData Flowを明確にし、以下を実現する。

- Server-side Data Fetchingを基本とする
- Client-side Fetchingの乱用を防ぐ
- 不要なNetwork Waterfallを避ける
- Mutationの責務をServer Actionへ集約する
- URL StateとServer Renderingを活用する
- 再取得範囲を必要最小限にする
- Suspense / Streamingを適切に利用する
- Request DuplicationやOver-fetchingを避ける
- Frontend固有のData TransformationとBusiness Ruleを分離する
- Laravel APIとの通信経路を統一する

基本方針を以下とする。

```text
Read
  → Server Component / Server Query

Mutation
  → Server Action

Client-side Read
  → Route Handler

再取得
  → 必要な範囲だけRevalidation

複数Read
  → 並列化を優先

遅いRead
  → Suspense / Streamingで分離
```

---

# 2. Data Accessの基本分類

Frontend上のData Accessを、大きく以下に分類する。

```text
Server Read
Client-side Read
Mutation
```

基本的な選択基準を以下とする。

| 処理 | 第一候補 |
|---|---|
| Page初期表示 | Server Component / Server Query |
| 一覧取得 | Server Component / Server Query |
| 詳細取得 | Server Component / Server Query |
| 検索 | URL State + Server Read |
| Filter | URL State + Server Read |
| Sort | URL State + Server Read |
| Pagination | URL State + Server Read |
| Create | Server Action |
| Update | Server Action |
| Delete | Server Action |
| Form Submit | Server Action |
| Autocomplete | Client-side Read |
| Infinite Scroll | Client-side Read |
| Polling | Client-side Read |
| Browser Interaction後の追加取得 | Client-side Read |

基本原則は以下とする。

```text
Serverで取得できるDataを
不要にClientへ持ち込まない
```

---

# 3. Readの基本フロー

通常のReadでは以下を標準とする。

```text
Page
 ↓
Server Component
 ↓
Feature Server Query
 ↓
API Client
 ↓
Generated Client
 ↓
Laravel API
```

Laravel API ResponseをそのままUIで利用できない場合は、必要に応じてMapperを利用する。

```text
Laravel API
 ↓
API DTO
 ↓
Mapper
 ↓
View Model
 ↓
Server Component
```

例：

```text
app/(dashboard)/employees/page.tsx
                  ↓
            EmployeeList
                  ↓
            getEmployees()
                  ↓
             API Client
                  ↓
          GET /employees
```

---

# 4. Server Query

Server Componentから利用するRead処理は、Feature内の`server/`へ配置する。

例：

```text
features/
└── employees/
    └── server/
        ├── get-employees.ts
        └── get-employee.ts
```

概念例：

```ts
import "server-only";

export async function getEmployees(params: EmployeeSearchParams) {
  const response = await apiClient(/* ... */);

  return response;
}
```

Server Queryの主な責務を以下とする。

- Laravel API呼び出し
- Query Parameter構築
- Request Parameter normalization
- Frontend向けの軽いResponse変換
- Mapper呼び出し
- View Model生成

Server QueryをBusiness Logic Layerとして使用しない。

---

# 5. Server QueryとBusiness Rule

Server QueryにはFrontend表示のための処理を置くことはできる。

例：

```text
API DTO
 ↓
表示用Date変換
 ↓
View Model
```

一方、以下のようなBusiness RuleのAuthorityとはしない。

```text
未経験ならLevel 1のみ登録可能
```

Business IntegrityはLaravel Domainで保証する。

```text
Frontend Server Query
=
Data Access / Presentation Transformation

Laravel Domain
=
Business Correctness
```

---

# 6. Data Fetchingを利用箇所の近くへ配置する

Data Fetchingは、必要なServer Componentの近くへ配置できる。

例えば、

```tsx
async function EmployeeSkillList({ employeeId }: Props) {
  const skills = await getEmployeeSkills(employeeId);

  return (
    // ...
  );
}
```

のような構成を許可する。

概念的には以下となる。

```text
Page
├── EmployeeProfile
│      ↓
│   getEmployee()
│
└── EmployeeSkills
       ↓
    getEmployeeSkills()
```

PageですべてのDataを取得してPropsを深く流すことを必須としない。

---

# 7. PageへのData Fetching集中を避ける

以下のようにPageで必要なDataをすべて取得し、大量のPropsとして下位Componentへ配布する構成は避ける。

```text
Page
 ↓
Employee
Skills
Departments
Permissions
Categories
...
 ↓
大量のProps
```

必要なServer Componentの近くで取得できる場合は、以下のような構成を許可する。

```text
Page
├── EmployeeSection
│      ↓
│   Employee API
│
├── SkillSection
│      ↓
│   Skill API
│
└── PermissionSection
       ↓
    Permission API
```

ただし、同一Request内で同じDataを無秩序に重複取得することも避ける。

---

# 8. Network Waterfall

依存関係のないAPI Requestを不要に逐次実行しない。

例えば、

```ts
const employee = await getEmployee();
const skills = await getSkills();
const departments = await getDepartments();
```

がすべて独立している場合、不要なWaterfallとなる。

```text
Employee API
    ↓ 完了待ち
Skill API
    ↓ 完了待ち
Department API
```

独立しているReadは並列取得を基本とする。

---

# 9. 独立したReadの並列化

相互に依存しない複数Readでは、並列実行を基本とする。

例：

```ts
const [
  employee,
  skills,
  departments,
] = await Promise.all([
  getEmployee(employeeId),
  getSkills(),
  getDepartments(),
]);
```

概念的には以下となる。

```text
          ┌─ Employee API
          │
Request ──┼─ Skill API
          │
          └─ Department API
```

不要なLatency累積を避ける。

---

# 10. 逐次Readを許可するケース

前のQuery結果が次のQueryに必要な場合は逐次取得を許可する。

例：

```text
Employee取得
   ↓
departmentId取得
   ↓
Department取得
```

判断基準は以下とする。

```text
前の結果が
次のRequestに必要か？
```

必要であれば逐次取得する。

不要であれば並列化する。

---

# 11. Promise.all

複数Dataがすべて揃わなければ画面を成立させられない場合は、`Promise.all()`を基本とする。

```text
Employee Form
├── Employee
├── Departments
└── Skill Categories
```

すべて必須であれば、一括して並列取得する。

---

# 12. 一部失敗を許容するRead

例えばDashboardのように、

```text
Dashboard
├── Employee Summary
├── Skill Ranking
└── Recent Updates
```

各Sectionが独立している場合、一部のRead失敗によって画面全体を失敗させる必要はない。

この場合は必要に応じて、

- Suspense Boundary
- Error Boundary
- Component単位のData Fetching
- `Promise.allSettled()`

を検討する。

`Promise.allSettled()`を全Data FetchingのDefaultとはしない。

---

# 13. Frontend BFFでのAPI Aggregation

1画面で複数のLaravel APIを利用することを許可する。

例：

```text
Dashboard
   ↓
Next.js Server
   ├── Employee API
   ├── Skill API
   └── Department API
```

Frontend表示のためのAggregationはNext.js BFFの責務として許可する。

ただし、

```text
複数APIを呼ぶ
=
必ず専用BFF Serviceを作る
```

とはしない。

単純なCompositionであればServer Component / Server Queryで処理する。

複雑化した場合のみFrontend固有のOrchestrationへの切り出しを検討する。

---

# 14. Search / Filter / Sort / Pagination

一覧系画面ではURL Stateを第一候補とする。

例：

```text
/employees
  ?keyword=php
  &department=3
  &sort=name
  &page=2
```

基本フローを以下とする。

```text
URL
 ↓
searchParams
 ↓
Server Component
 ↓
Server Query
 ↓
Laravel API
 ↓
一覧表示
```

---

# 15. 一覧条件をGlobal Client Stateへ保持しない

通常のSearch / Filter / Sort / Paginationでは、以下のようなGlobal Client Stateを第一候補としない。

```text
Redux
Zustand
Context
```

URL Stateを利用することで以下を実現する。

- Reload時の状態維持
- URL共有
- Bookmark
- Browser Back / Forward
- Server Renderingとの統合
- Client Global State削減

---

# 16. Search Input

Search InputそのものはClient Componentとして実装できる。

```text
Search Input
=
Client Interaction
```

検索結果の取得はServer側を基本とする。

```text
Client Search Form
       ↓
URL更新
       ↓
Server Component
       ↓
Server Query
       ↓
Laravel API
```

つまり、

```text
入力UI
=
Client

検索結果
=
Server
```

と分離する。

---

# 17. Mutationの基本フロー

Create / Update / DeleteではServer Actionを第一候補とする。

```text
Form
 ↓
Server Action
 ↓
Frontend Validation
 ↓
API Client
 ↓
Laravel API
 ↓
Laravel Application
 ↓
Laravel Domain
 ↓
Response
 ↓
Revalidation
 ↓
Redirect / UI更新
```

---

# 18. Server Actionの配置

Mutation処理は必要に応じてFeatureの`actions/`へ配置する。

例：

```text
features/
└── employees/
    └── actions/
        ├── create-employee.ts
        ├── update-employee.ts
        └── delete-employee.ts
```

ReadとMutationを物理的にも分離する。

```text
Read
↓
server/

Mutation
↓
actions/
```

---

# 19. Mutation成功後の処理

Mutation成功後は主に以下を使い分ける。

```text
Revalidation
Redirect
Result返却
```

例えばEmployee更新では、

```text
Employee Edit
    ↓
updateEmployee()
    ↓
PUT /employees/{id}
    ↓
成功
    ↓
関連DataをRevalidate
    ↓
Employee DetailへRedirect
```

というFlowを利用できる。

---

# 20. Revalidationの基本方針

Mutation後は、影響するDataだけをFreshにする。

例えばSkill更新なら、

```text
Skill更新
 ↓
関連するSkill Data
 ↓
Revalidate
```

とする。

以下のような全体再取得を基本としない。

```text
Mutation
 ↓
Application全体を再取得
```

具体的なCache Key、Tag、Path、Lifetimeについては`11_キャッシュ戦略.md`で定義する。

本章では、

```text
Mutation後は
影響範囲に応じて
必要なDataだけ更新する
```

ことを原則とする。

---

# 21. Redirect

Create / Update後に別Pageへ遷移するUXの場合、Server側Redirectを第一候補とする。

例：

```text
/employees/new
      ↓
Create
      ↓
/employees/123
```

同一画面で完結する以下のような操作では、Redirectしない。

```text
Dialog Edit
Inline Edit
Toggle
```

判断基準は以下とする。

```text
画面遷移を伴う
→ Redirect

同一画面で完結
→ Revalidation / UI更新
```

---

# 22. Mutation中のClient State

Mutation中の一時的なUI StateはClient側で保持してよい。

例：

```text
Idle
Submitting
Success
Error
```

主な用途は以下とする。

- Submit Button無効化
- Loading表示
- 二重送信防止
- Validation Error表示
- 一時的なFeedback表示

Server StateそのものをClient側へ恒久的に複製して保持しない。

---

# 23. Optimistic Update

Optimistic UpdateはDefaultでは採用しない。

基本Flowは以下とする。

```text
Mutation
 ↓
Server Action
 ↓
Laravel
 ↓
成功
 ↓
UI更新
```

Optimistic Updateは以下の場合に限定して検討する。

- Toggle等の軽量操作
- Rollbackが単純
- Server側Validationが比較的単純
- UX改善効果が大きい

Domain Validationの強いMutationでは安易に採用しない。

特にEmployeeSkillのようなBusiness Invariantを伴う更新では、Laravelの成功結果を確認してからUIを確定することを基本とする。

---

# 24. Client-side Read

ReadはServer-sideを基本とする。

ただし以下の場合はClient-side Readを許可する。

- Autocomplete
- Infinite Scroll
- Load More
- Polling
- Dependent Select
- Interactive Search Suggestion
- Server Navigationなしの追加取得
- Client専用Libraryとの統合

基本フローは以下とする。

```text
Client Component
      ↓
Route Handler
      ↓
API Client
      ↓
Laravel API
```

BrowserからLaravel APIへ直接通信しない。

---

# 25. Client-side Data Fetching Library

初期段階ではTanStack Query / SWR等のClient-side Server State Libraryを必須としない。

まず以下を基本構成とする。

```text
Server Component
+
Server Query
+
Server Action
+
Route Handler
```

Client-side Server State管理が増え、以下が継続的に必要となった場合に再評価する。

- Client Cache
- Refetch
- Request Deduplication
- Polling
- Retry
- Optimistic Update
- Background Refetch

具体的なState Management Libraryの採否は`07_状態管理.md`で決定する。

---

# 26. Page Loading

Page Segment全体のLoading UIには`loading.tsx`を利用できる。

例：

```text
app/
└── (dashboard)/
    └── employees/
        ├── page.tsx
        └── loading.tsx
```

Page全体が同じDataへ依存する場合に利用する。

---

# 27. Suspense Boundary

画面内で独立してDataを取得できるSectionには、必要に応じてSuspense Boundaryを利用する。

例：

```text
Dashboard
├── EmployeeSummary
├── SkillSummary
└── SkillRanking
```

これを、

```text
Dashboard

├── Suspense
│    └── EmployeeSummary
│
├── Suspense
│    └── SkillSummary
│
└── Suspense
     └── SkillRanking
```

のように分離できる。

---

# 28. Streaming

Streamingは、画面全体を最も遅いData Fetchingに合わせて待機させないために利用する。

例えば、

```text
Dashboard Header       100ms
Employee Summary       200ms
Skill Ranking         1500ms
```

の場合、

```text
1500ms後に全部表示
```

ではなく、

```text
Header
 ↓
Employee Summary
 ↓
Skill Ranking
```

のような段階表示を可能にする。

---

# 29. Suspenseを乱用しない

すべてのComponentへSuspense Boundaryを配置しない。

判断基準は以下とする。

```text
そのUI領域が
独立してLoadingできるか？
```

例えば同一Employee API Responseから取得する、

```text
Employee Name
Department
Employment Status
```

を別々のSuspense Boundaryに分割する必要はない。

---

# 30. Loading Boundaryの単位

Loading / Suspense Boundaryは、API Endpoint単位ではなくユーザーから見たUI単位で設計する。

避ける考え方：

```text
API A
API B
API C

↓

Suspense A
Suspense B
Suspense C
```

推奨する考え方：

```text
Employee Overview
Skill Summary
Access Control
```

UIとして意味のある単位でBoundaryを設ける。

---

# 31. Error Boundaryとの組み合わせ

独立したSectionでは、Read失敗時にPage全体を失敗させる必要がない場合がある。

例：

```text
Dashboard
├── EmployeeSummary  OK
├── SkillSummary     ERROR
└── RecentUpdates    OK
```

必要に応じてSuspense BoundaryとError Boundaryを組み合わせる。

具体的な、

- 401
- 403
- 404
- Validation Error
- API Error
- Retry
- Error Boundary

については`10_エラーハンドリング.md`で定義する。

---

# 32. Request Duplication

同一Render内で同じDataを複数箇所から取得する場合、無駄なLaravel API Requestが発生しないようにする。

例：

```text
EmployeeHeader
      ↓
getEmployee(10)

EmployeeDetail
      ↓
getEmployee(10)
```

重複が発生する場合は以下を検討する。

- 親Server Componentで取得して共有
- Request単位のDeduplication
- Data Fetching位置の見直し
- Cache / Memoization

ただしRequest Duplication回避のためだけに、PageへすべてのData Fetchingを集中させない。

具体的なCaching方針は`11_キャッシュ戦略.md`で定義する。

---

# 33. Over-fetching

一覧表示などで不要なDataまで取得しない。

例えばEmployee一覧で、

```text
Employee詳細
全Skill情報
Permission詳細
その他詳細情報
```

まで取得するAPIを利用することは避ける。

一覧では一覧に必要なDataを返すAPIを利用する。

```text
Employee List API
```

FrontendとBackend API Designの両方でOver-fetchingを防ぐ。

---

# 34. View Model

API DTOをそのままUIで利用できる場合は、不要なView Modelを作成しない。

```text
API DTO
 ↓
UI
```

で十分な場合はそのまま利用する。

一方でFrontend表示用の変換が必要な場合は、

```text
API DTO
 ↓
Mapper
 ↓
View Model
 ↓
UI
```

とする。

例：

```text
last_used_year = 2026
last_used_month = 8

↓

"2026年8月"
```

View ModelはPresentationのためのModelであり、Domain Modelとして扱わない。

---

# 35. Form初期Data

Edit Formの初期DataはServer側で取得することを基本とする。

```text
Edit Page
 ↓
Server Component
 ↓
getEmployee()
 ↓
EmployeeForm
 ↓
initialValues
```

以下をDefault Patternにはしない。

```text
Client Component Mount
 ↓
useEffect
 ↓
GET /employee
 ↓
Form表示
```

初期表示に必要なDataはServerで取得する。

---

# 36. Select Option

DepartmentやSkill Categoryなど、Form初期表示時から必要なSelect OptionもServer側で取得する。

例：

```text
Edit Page
   ├── getEmployee()
   ├── getDepartments()
   └── getSkillCategories()
```

独立している場合は並列取得する。

```ts
const [
  employee,
  departments,
  skillCategories,
] = await Promise.all([
  getEmployee(employeeId),
  getDepartments(),
  getSkillCategories(),
]);
```

---

# 37. Dependent Select

Browser Interaction後に取得条件が決定する場合はClient-side Readを許可する。

例：

```text
Skill Category選択
      ↓
Category ID決定
      ↓
該当Skill一覧取得
```

Flowは以下とする。

```text
Client Component
      ↓
Route Handler
      ↓
Laravel API
```

すべてのData Fetchingを無理にServer Componentへ寄せない。

---

# 38. Refresh

ユーザー操作による明示的なRefreshが必要な場合、Server Componentを再取得する仕組みを利用できる。

ただし、

```text
Mutation
 ↓
必ずFull Refresh
```

とはしない。

Mutation後は適切なRevalidationを第一候補とする。

Refreshは明示的な再取得が必要なケースで利用する。

---

# 39. Polling

Pollingは必要性が明確なFeatureでのみ採用する。

本プロジェクトのMVPでは、通常のEmployee / Skill管理画面で秒単位のRealtime性を要求しない。

したがって、以下を標準Data Fetching方式とはしない。

```text
Polling
WebSocket
Realtime Subscription
```

将来的にRealtime要件が発生した場合にFeature単位で再検討する。

---

# 40. Prefetch

NavigationについてはNext.jsが提供する標準的なPrefetch機構を活用する。

独自API Prefetchは初期段階では積極的に導入しない。

以下を基準に再検討する。

- 実測Performance
- UX上の必要性
- API負荷
- Data size
- Cache方針

---

# 41. Retry

API Requestの無条件な自動Retryを標準としない。

特にMutationでは、

```text
POST
PUT
PATCH
DELETE
```

を安易にRetryすると二重実行や意図しない更新につながる可能性がある。

ReadのRetryについてはError種類・Idempotency・UXを踏まえて判断する。

具体的なRetry Policyは`10_エラーハンドリング.md`で定義する。

---

# 42. FrontendにおけるRead / Mutation分離

BackendではLightweight CQRSを採用するが、FrontendへCQRS Architectureをそのまま再構築しない。

Frontendでは概念的にReadとMutationを分ける。

```text
Read
 ↓
server/get-*.ts

Mutation
 ↓
actions/*.ts
```

例：

```text
features/
└── employees/
    ├── server/
    │   ├── get-employees.ts
    │   └── get-employee.ts
    │
    └── actions/
        ├── create-employee.ts
        └── update-employee.ts
```

これ以上のCommand Bus / Query Bus等はFrontendには導入しない。

---

Frontend全体の基本Data Flowを以下とする。

```text
                    ┌─────────────────────┐
                    │      Browser        │
                    └──────────┬──────────┘
                               │
                 ┌─────────────┴─────────────┐
                 │                           │
                 ▼                           ▼
          URL Navigation                UI Mutation
                 │                           │
                 ▼                           ▼
        Server Component               Server Action
                 │                           │
                 ▼                           │
          Server Query                      │
                 │                           │
                 └─────────────┬─────────────┘
                               ▼
                          API Client
                               │
                               ▼
                          Laravel API
```

Client-side Readが必要な場合のみ、以下を追加する。

```text
Browser
 ↓
Client Component
 ↓
Route Handler
 ↓
API Client
 ↓
Laravel API
```

# 44. Read判断フロー

Dataが必要になった場合は以下の順番で判断する。

```text
Dataが必要
   │
   ▼
初期表示で必要か？
   │
   ├── Yes
   │    ↓
   │ Server Component / Server Query
   │
   └── No
        │
        ▼
Browser Interaction後に必要か？
        │
        ├── Yes
        │    ↓
        │ Client-side Read
        │    ↓
        │ Route Handler
        │
        └── No
             ↓
        Server-side Readを検討
```

```text
        │

        │    ↓

        │
        └── No

```

# 47. 決定事項

Frontendのデータ取得・更新として、以下を正式採用する。

- ReadはServer Component / Server Queryを第一候補とする
- Server QueryはFeatureの`server/`へ配置する
- Server QueryをBusiness Logic Layerとして使用しない
- Data Fetchingは利用するServer Componentの近くへ配置できる
- PageへすべてのData Fetchingを集中させない
- 同一Dataの不要な重複取得は避ける
- 独立した複数Readは並列取得を基本とする
- 不要なNetwork Waterfallを避ける
- 後続Queryが前の結果へ依存する場合は逐次取得を許可する
- 全Dataが必要な並列取得では`Promise.all()`を基本とする
- 一部失敗を許容するUIではComponent分割・Error Boundary等を検討する
- Frontend表示のためのAPI AggregationをNext.js BFFで許可する
- 単純なAggregationのために不要なService Layerを作らない
- Search / Filter / Sort / PaginationはURL State + Server Readを基本とする
- 一覧条件をGlobal Client Stateへ置かない
- Search InputはClient、検索結果取得はServerという分離を許可する
- MutationはServer Actionを第一候補とする
- Readは`server/`、Mutationは`actions/`へ概念的に分離する
- Mutation後は影響するDataだけをRevalidateする
- Cacheの具体的なTag / Path / Lifetimeは`11_キャッシュ戦略.md`で定義する
- 画面遷移を伴うCreate / Updateでは必要に応じてRedirectする
- Mutation中の一時的UI StateのみClient側で保持する
- Optimistic UpdateはDefault採用しない
- Domain Validationが強いMutationではServer成功後にUIを確定する
- Client-side Readは必要な場合だけ使用する
- Client-side ReadはRoute Handler経由でLaravel APIへアクセスする
- Client-side Data Fetching Libraryは初期段階では必須としない
- Client-side Server State管理が複雑化した場合にLibrary導入を再評価する
- Page Segment Loadingには`loading.tsx`を利用できる
- 独立して遅延するUIにはSuspense / Streamingを利用する
- Suspense BoundaryはAPI単位ではなく意味のあるUI単位で設計する
- Suspenseを無秩序に配置しない
- 独立Sectionでは必要に応じてError Boundaryと組み合わせる
- Request Duplicationを避ける
- Over-fetchingを避ける
- API DTOをそのまま利用できる場合は不要なView Modelを作らない
- Frontend表示変換が必要な場合のみMapper / View Modelを利用する
- Edit Formの初期DataはServer側で取得する
- 初期表示時に必要なSelect OptionもServer側で取得する
- Browser Interaction後に条件が決まるDependent Select等ではClient-side Readを許可する
- Mutation後のFull RefreshをDefaultとしない
- Polling / WebSocket / Realtime SubscriptionはMVPの標準方式として採用しない
- 独自PrefetchはPerformance測定と必要性に基づいて導入する
- Mutationの無条件Retryは行わない
- FrontendにはBackendのCQRS Architectureを再構築しない
- FrontendではReadとMutationを軽量に分離する

以上をFrontendのデータ取得・更新方針とする。
