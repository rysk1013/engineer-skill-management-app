# Laravel 内部アーキテクチャ 方針変更

## 1. 基本方針

今回のProjectでは学習・挑戦を目的として、
一般的なLaravel CRUD構成よりも明確なLayer分離を行う。

以下の考え方を取り入れる。

- Clean Architecture
- Domain Driven Design
- UseCase / Application Service
- Repository Pattern
- Domain Model
- Value Object
- Domain Service
- Dependency Inversion

ただし、DDD / Clean Architectureを形式的に完全再現することは目的としない。

Project規模に合わせて必要な要素を選択する。

---

# 2. 基本Architecture

基本的に以下のLayerへ分割する。

    Presentation
         ↓
    Application
         ↓
       Domain
         ↑
         |
    Infrastructure

Dependencyの方向：

    Presentation
         ↓
    Application
         ↓
       Domain

    Infrastructure
         ↓
       Domain

Domain LayerはLaravelやDatabase等の
Infrastructureへ依存しないことを目標とする。

---

# 3. Layer構成

## Presentation Layer

HTTP / APIを担当する。

Laravelでは主に以下。

- Controller
- Form Request
- API Resource
- Middleware

役割：

- HTTP Request受付
- Input変換
- Authentication
- Authorization呼び出し
- UseCase呼び出し
- HTTP Response生成

Business Logicを持たせない。

---

## Application Layer

Application固有の処理の流れを担当する。

主な構成：

- UseCase
- Command
- Query
- DTO
- Transaction Boundary

例：

    CreateEmployee
    UpdateEmployee
    RegisterEmployeeSkill
    DisableEmployeeSkill

Application Layerは、

    「何をするか」

を表現する。

---

## Domain Layer

Business Ruleの中心。

主な構成：

- Entity
- Value Object
- Domain Service
- Domain Exception
- Repository Interface
- Domain Enum

Domain LayerはFrameworkへ依存しないことを目指す。

例：

    Employee
    EmployeeSkill
    Skill
    ExperienceMonths
    SkillLevel
    LastUsedMonth

---

## Infrastructure Layer

外部技術との接続を担当する。

Laravelでは主に以下。

- Eloquent
- Repository Implementation
- PostgreSQL
- Laravel Sanctum
- Logging
- External API Client

InfrastructureはDomain側で定義したInterfaceを実装する。

---

# 4. Dependency Rule

重要な原則：

    Domain
       ↑
    Application
       ↑
    Presentation

Infrastructure：

    Infrastructure
         ↓
      Domain Interface

Domainから、

    Eloquent
    Laravel
    PostgreSQL

へ依存しない。

---

# 5. Repository Pattern

今回はRepository Patternを採用する。

Domain側：

    EmployeeRepository

Infrastructure側：

    EloquentEmployeeRepository

例：

    Domain
    └── Repositories
        └── EmployeeRepository.php

    Infrastructure
    └── Repositories
        └── EloquentEmployeeRepository.php

Application Layerは、

    EmployeeRepository

Interfaceへ依存する。

Eloquentへ直接依存しない。

---

# 6. Entity

Domain EntityはBusiness上のIdentityを持つObjectとして扱う。

例：

    Employee

    EmployeeSkill

Laravel Eloquent ModelとDomain Entityは
分離することを第一候補とする。

つまり：

    Domain Employee
        ≠
    Eloquent EmployeeModel

とする。

---

# 7. Eloquent Model

Eloquent ModelはInfrastructure Layerへ配置する。

役割：

- PostgreSQL Mapping
- Eloquent Relation
- DB Cast
- Query

Business Ruleの中心にはしない。

概念：

    PostgreSQL
        ↕
    Eloquent Model
        ↕
    Repository
        ↕
    Domain Entity

---

# 8. Value Object

DDDの学習要素としてValue Objectを積極的に利用する。

ただしすべてのPrimitiveをValue Object化しない。

Business Ruleを持つ値を中心とする。

候補：

    EmployeeNumber

    ExperienceMonths

    SkillLevel

    LastUsedMonth

    RetirementDate

例：

    ExperienceMonths

Business Rule：

    0以上

    実務経験ありの場合は1以上

などを表現できる。

---

# 9. SkillLevel

Primitiveの、

    int $skillLevel

ではなく、

    SkillLevel

Value Object / Enumとして扱う。

例：

    SkillLevel::Level1
    SkillLevel::Level2
    SkillLevel::Level3
    SkillLevel::Level4
    SkillLevel::Level5

---

# 10. ExperienceMonths

ExperienceMonthsをValue Objectとして扱う。

例：

    ExperienceMonths::fromYearsAndMonths(
        3,
        6
    )

内部：

    42 months

Application / Domainでは、

    42

という裸のintegerを扱う箇所を減らす。

---

# 11. EmployeeSkill Domain Rule

例えば以下をDomainで表現する。

    実務経験なし
        ↓
    Level 1
    ExperienceMonths = 0
    LastUsedMonth = null

    実務経験あり
        ↓
    ExperienceMonths >= 1
    Level 1〜5
    LastUsedMonth required

このRuleをControllerやForm Requestだけへ置かない。

---

# 12. Factory

複雑なEntity生成にはDomain Factoryを検討する。

例：

    EmployeeSkillFactory

ただしConstructorだけで十分な場合は
Factoryを無理に導入しない。

---

# 13. Domain Service

1 Entityだけに自然に所属しないBusiness Logicで利用する。

例：

    PermissionAssignmentService

など。

単なる処理の置き場としてDomain Serviceを乱用しない。

---

# 14. Domain Exception

Business Rule違反を表現する。

候補：

    InvalidSkillLevelException

    InvalidWorkExperienceException

    EmployeeSkillAlreadyExistsException

ただしValidation ErrorとDomain Errorを区別する。

---

# 15. Application UseCase

1つのUser Story / Application操作に対して
1つのUseCase Classを作る。

例：

    Employees/
    ├── CreateEmployee
    ├── UpdateEmployee
    └── GetEmployee

    EmployeeSkills/
    ├── RegisterEmployeeSkill
    ├── UpdateEmployeeSkill
    └── DisableEmployeeSkill

User StoryとCode構造を対応させる。

---

# 16. Command / Query

学習目的として、

    Command
    Query

の分離も取り入れる。

ただしCQRSを完全導入するわけではない。

例：

    CreateEmployeeCommand
    UpdateEmployeeCommand

    GetEmployeeQuery
    SearchEmployeesQuery

---

# 17. CQRSとの関係

MVPでは、

    Write Model
    Read Model

を完全に分離するCQRSは採用しない。

ただしApplication Layerで、

    Command
    Query

という概念を分ける。

これにより将来的なCQRS理解にもつなげる。

---

# 18. DTO

Layer間のData TransferにはDTOを利用する。

例：

    CreateEmployeeInput

    EmployeeOutput

Presentation Layerから
Domain Entityへ直接Requestを渡さない。

---

# 19. Mapper

Domain EntityとEloquent Modelを分離するため、
Mappingが必要になる。

例：

    EmployeeMapper

    EloquentEmployee
        ↓
    Employee Domain Entity

逆方向：

    Employee Domain Entity
        ↓
    EloquentEmployee

ただしMapping Codeが増えることは
意図的な学習コストとして許容する。

---

# 20. Transaction

Transaction BoundaryはApplication Layerで管理する。

概念：

    CreateEmployee UseCase
        ↓
    Transaction
        ↓
    Repository
        ↓
    PostgreSQL

Domain EntityはTransactionを意識しない。

---

# 21. Authorization

Authentication / Authorizationは
完全なDomain Logicとして扱わず、
Application / Presentationとの境界で設計する。

Laravel Policyを利用しつつ、
複雑な権限RuleはDomain / Applicationへ移動できる構成とする。

---

# 22. OpenAPIとの関係

OpenAPI：

    External API Contract

Presentation DTO：

    API Input / Output

Application DTO：

    UseCase Input / Output

Domain：

    Business Model

を区別する。

OpenAPI SchemaをそのままDomain Entityにしない。

    CreateEmployeeHandler

# 25. 今回あえて採用する要素

学習目的として以下を採用する。

- Clean Architecture Layering
- DDD Entity
- Value Object
- Repository Pattern
- Dependency Inversion
- Application UseCase
- Command / Query分離
- DTO
- Mapper
- Domain Exception

---

# 26. MVPでも採用しないもの

学習目的でも以下までは最初から導入しない。

- Event Sourcing
- Full CQRS
- Eventual Consistency
- Microservices
- Distributed Transaction
- Saga
- Message Broker

これらは現在のDomain規模に対して
学習コストが大きすぎるため。

---

# 27. Architectureの目的

今回のArchitectureは、

    「最小コード量」

を目的としない。

目的：

- Clean Architectureを理解する
- DDDを実際に適用する
- Dependency Inversionを経験する
- Domain Modelを設計する
- Repository Patternを経験する
- Testableな設計を学ぶ
- Layer Boundaryを理解する

---

# 28. 注意点

Over Engineeringを許容するが、
以下は避ける。

- Interfaceを作ること自体が目的になる
- すべてのClassにInterfaceを作る
- すべてのPrimitiveをValue Object化する
- Domain ServiceへLogicを集めすぎる
- UseCaseからさらに意味のないLayerを増やす
- Laravelを敵視する

Laravelの便利な機能も活用しつつ、
Domain Boundaryを意識する。

---

# 29. 推奨決定

今回のLaravel Backendでは、

**Clean Architecture + DDD Lite〜Medium**

を採用する。

採用：

- Presentation Layer
- Application Layer
- Domain Layer
- Infrastructure Layer
- Domain Entity
- Value Object
- Repository Interface
- Repository Implementation
- UseCase
- Command / Query
- DTO
- Mapper
- Domain Exception

採用しない：

- Full CQRS
- Event Sourcing
- Microservices

学習目的として、
一般的なLaravel Applicationより明確にLayerを分離する。
