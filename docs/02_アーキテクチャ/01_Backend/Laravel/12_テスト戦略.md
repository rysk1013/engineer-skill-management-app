# テスト戦略

## 1. 目的

本システムのTestは、単にCode Coverageを高めることではなく、

- Business Ruleの正しさを保証する
- UseCaseの振る舞いを保証する
- PostgreSQL / EloquentなどInfrastructureとのIntegrationを保証する
- HTTP API Contractを保証する
- Authorization / Authenticationを保証する
- ConcurrencyによるBusiness Invariant破壊を防ぐ
- Refactoringを安全に行える状態を維持する

ことを目的とする。

本システムでは、

> 各Layerの責務に応じたTest Levelを使い分け、重要なBusiness RuleほどInner Layerで高速かつ詳細に検証する

ことを基本方針とする。

---

## 2. 基本方針

- Domain LayerはUnit Testを中心とする
- Application LayerはHandler単位のUnit Testを中心とする
- Infrastructure LayerはPostgreSQLを利用したIntegration Testを行う
- Presentation LayerはLaravel Feature Testを利用する
- PostgreSQL固有仕様をSQLiteで代替しない
- OpenAPI Contractとの整合を確認する
- ConcurrencyがBusiness Invariantへ影響する箇所はConcurrency Testを行う
- Authentication / AuthorizationはFeature Testで確認する
- Eloquent ModelそのものではなくRepository / Query Serviceの振る舞いを検証する
- Test Doubleは責務に応じてFake / Stub / Mockを使い分ける
- Unit TestではLaravel Containerを原則起動しない
- Implementation Detailへ過剰に依存したTestを書かない
- Private Methodを直接Testしない
- Code Coverage 100%を目的化しない
- 重要なBusiness Rule / Failure Pathを優先する
- Test Dataは読みやすく最小限に保つ
- Flaky Testを許容しない

---

## 3. Test Pyramid

本システムでは概念的に以下の構造を目指す。

```text
                ┌──────────────┐
                │   E2E Test   │
                │   少数のみ    │
                └──────┬───────┘
                       │
              ┌────────▼────────┐
              │ Feature / API   │
              │      Test       │
              └────────┬────────┘
                       │
            ┌──────────▼──────────┐
            │ Infrastructure       │
            │ Integration Test     │
            └──────────┬──────────┘
                       │
        ┌──────────────▼──────────────┐
        │ Domain / Application Unit   │
        │            Test             │
        └─────────────────────────────┘
```

Test数はInner Layerほど多くし、Outer Layerほど代表Scenarioへ絞る。

---

## 4. LayerとTest Level

基本対応は以下とする。

| Layer | 主なTest |
|---|---|
| Domain | Unit Test |
| Application | Unit Test |
| Infrastructure | Integration Test |
| Presentation | Feature Test |
| API Contract | Contract Test |
| Concurrency | PostgreSQL Integration / Concurrency Test |
| System全体 | 必要最小限のE2E Test |

---

## 5. Domain Unit Test

Domain TestではBusiness Ruleそのものを検証する。

対象例:

- Entity
- Aggregate
- Value Object
- Enumに関係するBusiness Rule
- Domain Policy
- Domain Service

Laravel Applicationは起動しない。

PostgreSQLも利用しない。

Plain PHP ObjectとしてTestできる状態を維持する。

---

## 6. Domain Testで確認するもの

Domain Testでは主に以下を確認する。

- Aggregate生成
- Valid State
- Invalid State
- Business Invariant
- State Transition
- Domain Behavior
- Value Object Validation
- Domain Exception
- Boundary Value

Business Ruleの組み合わせを重点的にTestする。

## 8. Domain Exception Test

Business Invariant違反では、期待するDomain Exceptionが発生することを確認する。

例:

```php
$this->expectException(
    InvalidSkillLevelForNoExperience::class,
);
```

Exception Message全文への依存は原則避ける。

Exception ClassとBusiness Outcomeを中心に検証する。

---

## 9. Value Object Test

Value Objectでは以下を確認する。

- 正常値
- 最小値
- 最大値
- Boundary
- Invalid Value
- Equality
- Normalizationがある場合その挙動

例:

```text
ExperiencePeriod
    ↓
1か月
    ↓
有効
```

```text
ExperiencePeriod
    ↓
0か月
    ↓
無効
```

## 10. `register()` のTest

Aggregateの新規生成では `register()` をTestする。

確認事項:

- 必須Invariant
- Initial State
- Initial Value
- ID保持
- Business Rule違反時のException

Persistenceに関することはここではTestしない。

---

## 11. `reconstitute()` のTest

`reconstitute()` はPersistenceから既存Aggregateを再構築するためのMethodである。

必要に応じて、

- Persisted Stateを正しく復元できる
- MapperとのRound-tripでStateが失われない

ことを確認する。

ただしDomain Unit TestでDatabase MappingまでTestしない。

Mapper Integration Testと責務を分ける。

---

## 12. Domain Policy Test

例えば、

```text
Permission Managerを最低1人維持する
```

というPolicyについては、Domain Policy単体でBusiness判断をTestする。

例:

```text
Permission Managerが2人
    ↓
1人解除可能
```

```text
Permission Managerが1人
    ↓
解除不可
```

Concurrent LockそのものはInfrastructure / Concurrency Testで確認する。

---

## 13. Application Unit Test

Application LayerではCommand / Query HandlerのUseCase FlowをTestする。

Application Testでは主に、

> 正しいDependencyを利用し、期待するUseCase結果になるか

を確認する。

Laravel Applicationは原則起動しない。

---

## 14. Command Handler Test

Command Handlerでは以下を確認する。

- Authorization
- RepositoryからAggregate取得
- Not Found処理
- Domain Behavior呼び出し
- Repository保存
- Transaction利用
- Application Exception
- Domain Exception伝播
- Result返却

---

## 15. Command Handler Test例

EmployeeSkill登録では例えば以下を確認する。

```text
Command
    ↓
Actor確認
    ↓
Employee存在確認
    ↓
Skill存在確認
    ↓
Duplicate確認
    ↓
ID生成
    ↓
EmployeeSkill::register()
    ↓
save()
    ↓

```

全内部Method Callを逐一Mock Verificationするのではなく、UseCase Outcomeを中心に確認する。

---

## 16. Transaction Test

Application Unit Testでは、

```text
Write UseCase
    ↓
TransactionManager
```

を通して処理されることを確認する。

Test用TransactionManagerではCallbackをそのまま実行できる。

例:

```php
final class ImmediateTransactionManager
    implements TransactionManager
{
    public function run(
        callable $callback,
    ): mixed {
        return $callback();
    }
}
```

実際のCommit / RollbackはInfrastructure Integration Testで確認する。

---

## 17. Repository Fake

Application Unit TestではRepository Fakeを利用できる。

例:

```text
EmployeeSkillRepository
    ↓
InMemoryEmployeeSkillRepository
```

Fakeを利用することでApplication FlowをDatabaseなしで確認できる。

ただしFakeが本物のPostgreSQL Repositoryと同じ挙動を完全に再現すると考えない。

Concrete Repositoryは別途Integration Testを行う。

---

## 18. Mockの利用

Mockは、

> DependencyとのInteraction自体がRequirementである場合

に利用する。

例えば、

- External Gatewayが呼ばれないこと
- Audit Portが特定条件で呼ばれること

など。

RepositoryのMethod Call回数を過剰にMock Verificationし、Implementation Detailへ強く結合するTestは避ける。

---

## 19. Fake / Stub / Mockの使い分け

基本:

### Fake

軽量な動作するImplementation。

例:

```text
InMemoryEmployeeSkillRepository
FixedClock
FakeIdGenerator
```

### Stub

決まった値を返す。

例:

```text
ActorContext
```

### Mock

Interactionを検証する。

例:

```text
External Gateway
```

Test Doubleは目的に応じて選ぶ。

---

## 20. Query Handler Test

Query Handlerでは以下を確認する。

- Authorization
- Query条件生成
- Query Service呼び出し
- Read Model返却
- Pagination Result
- Query-specific Failure

SQLそのものはApplication Testでは確認しない。

---

## 21. Query ServiceのIntegration Test

Query Service ImplementationはInfrastructure TestとしてPostgreSQLで確認する。

対象:

- JOIN
- Filter
- Sort
- Pagination
- Aggregate Function
- Subquery
- CTE
- PostgreSQL固有SQL
- Dashboard集計

Read Modelの値が正しいことを確認する。

---

## 22. Infrastructure Integration Test

Infrastructureでは実際のLaravel / PostgreSQLを利用したIntegration Testを行う。

主な対象:

- Repository Implementation
- Mapper
- Query Service
- Transaction Manager
- ID Generator
- Authentication Adapter
- External Adapter

Technical Integrationを実環境に近い条件で確認する。

---

## 23. PostgreSQLを利用する

Database Integration TestにはPostgreSQLを利用する。

SQLiteへ置き換えない。

理由:

- SQL Dialect差異
- Constraint挙動
- Sequence
- `FOR UPDATE`
- Transaction Isolation
- PostgreSQL型
- `timestamptz`
- Index
- PostgreSQL固有SQL
- Constraint Error
- Concurrent Transaction

などが異なるためである。

---

## 24. Test Database

Integration / Feature Testでは専用PostgreSQL Databaseを利用する。

Production / Development Databaseを共有しない。

概念:

```text
PostgreSQL
├── development
├── test
└── production
```

Test Databaseは自動的に初期化可能な状態にする。

---

## 25. Migration

Integration / Feature TestのSchemaはLaravel Migrationから構築する。

Manual SQLでTest専用Schemaを別管理しない。

これにより、

```text
Migration
    ↓
Test Schema
```

を本番Schemaと一致させる。

---

## 26. Test間のDatabase Isolation

各Testが別TestのDataへ依存しないようにする。

LaravelのDatabase Test Supportを利用し、TestごとにDatabase StateをIsolationする。

ただしConcurrency Testなど複数Connection / Transactionを必要とするTestでは、通常のTransaction-based Test Isolationと相性が悪い場合があるため、個別にSetup / Cleanupを設計する。

---

## 27. Repository Integration Test

Repository TestではInterface Contractとして以下を確認する。

- `find()`
- `save()` Insert
- `save()` Update
- `remove()` が存在する場合
- `exists...()`
- Lock-aware Method
- Mapper Integration
- Constraint Violation
- Aggregate State復元

Eloquent Model内部Implementationを直接Testすることが目的ではない。

---

## 28. `save()` Insert Test

新規Aggregateを、

```text
register()
    ↓
Repository::save()
```

したときDatabaseへ正しく保存されることを確認する。

さらに、

```text
Repository::find()
    ↓
Aggregate
```

でStateが復元できることを確認する。

---

## 29. `save()` Update Test

既存Aggregateを、

```text
find()
    ↓
Domain Behavior
    ↓
save()
```

した場合、既存RowがUpdateされることを確認する。

Application側がInsert / Updateを判定しなくても `save()` が期待通り動作することを確認する。

---

## 30. Mapper Test

Mapperでは以下を確認する。

```text
Persistence
    ↓
toDomain()
    ↓
Domain
```

および、

```text
Domain
    ↓
fillModel()
    ↓
Persistence Model
```

主要Fieldが正しく変換されることを確認する。

---

## 31. Mapper Round-trip Test

必要なAggregateではRound-tripを確認する。

```text
Model
    ↓
toDomain()
    ↓
Domain
    ↓
fillModel()
    ↓
Model
```

によってBusiness Stateが失われないことを確認する。

ただしTimestampやEloquent内部Stateなど、Domainと無関係な値まで完全一致を要求しない。

---

## 32. MapperでLazy Loadingへ依存しないこと

MapperがRelationship Lazy Loadingへ暗黙依存しないことをTest / Code Reviewで確認する。

Aggregate復元に必要なDataはRepository側で明示的に取得する。

N+1をMapperの隠れた挙動として発生させない。

---

## 33. Constraint Test

PostgreSQL ConstraintをIntegration Testで確認する。

対象:

- Primary Key
- Foreign Key
- UNIQUE
- CHECK
- NOT NULL

特にBusiness Integrityの最終防衛として利用するConstraintはTest対象とする。

---

## 34. EmployeeSkill UNIQUE Test

EmployeeSkillでは、

```text
employee_id
+
skill_id
```

の重複をDatabaseが拒否することを確認する。

ApplicationのDuplicate CheckだけでTestを終わらせない。

---

## 35. Constraint Exception Mapping Test

例えば、

```text
uq_employee_skills_employee_id_skill_id
```

違反時にInfrastructure側で意味あるExceptionへ変換する設計なら、そのMappingもTestする。

Application側の事前Duplicate CheckとDatabase側のConstraint Violationのどちらから発生しても、最終的なAPI Semanticsが同一になることを確認する。

SQLSTATEやDriver Message全文へTestを強く依存させない。

---

## 36. ID Generator Test

PostgreSQL Sequenceを利用するID Generatorでは以下を確認する。

- ID取得可能
- 連続してUnique IDを取得可能
- Expected Value Objectへ変換される

Sequence番号が完全に連続していることはTestしない。

Rollbackによる欠番をFailureとしない。

---

## 37. Transaction Integration Test

LaravelTransactionManagerについてはPostgreSQLを利用して以下を確認する。

### Commit

```text
Transaction
    ↓
INSERT
    ↓
Commit
    ↓
Data存在
```

### Rollback

```text
Transaction
    ↓
INSERT
    ↓
Exception
    ↓
Rollback
    ↓
Data不存在
```

---

## 38. Concurrency Test

Concurrent RequestによってBusiness Invariantが破壊され得る箇所はConcurrency Testを行う。

本システムでは特に、

> Permission管理可能なAdministratorを最低1人維持する

Ruleを重要Test対象とする。

---

## 39. Permission Manager Concurrency Test

Initial State:

```text
Permission Manager A
Permission Manager B
```

Concurrent Operation:

```text
Transaction 1
    ↓
AのPermission解除
```

```text
Transaction 2
    ↓
BのPermission解除
```

Expected:

```text
片方
    ↓
成功

もう片方
    ↓
最新状態を確認
    ↓
PermissionManagerRequired
```

Final State:

```text
Permission Manager >= 1
```

を保証する。

---

## 40. Concurrency Testでは実PostgreSQLを利用する

Concurrency Testでは、

- 複数Database Connection
- 実Transaction
- `SELECT FOR UPDATE`
- Commit / Rollback
- Lock待機

を利用する。

Mockで、

```text
lockForUpdate() が呼ばれた
```

ことだけを確認してConcurrencyが正しいと判断しない。

---

## 41. Deadlock Test

Deadlockそのものを毎回再現するTestはMVPでは必須としない。

Deadlock回避については、

- Lock順序
- Transaction Scope
- Code Review

を中心とする。

実際にDeadlock Retry等を実装した場合のみ、そのBehavior Testを追加する。

---

## 42. Last Write Wins Test

通常更新ではOptimistic Lockを採用しないため、Last Write Winsを許容する。

一般的なCRUDすべてについてConcurrent Update Testを書く必要はない。

Business Requirement上Lost Updateが問題となった場合のみ追加する。

---

## 43. Presentation Feature Test

Presentation LayerではLaravel Feature Testを利用し、HTTP Boundary全体を確認する。

対象:

- Routing
- Request Validation
- Authentication
- Authorization
- Controller
- Handler Integration
- Exception Mapping
- API Resource
- HTTP Status
- JSON Structure

---

## 44. Feature Testの範囲

Feature Testでは、

```text

    ↓
Laravel
    ↓
Controller
    ↓
Application
    ↓

    ↓
PostgreSQL
    ↓
```

## 45. Request Validation Test

- Type

- Year-Month Format

- camelCase Field Name

代表:

- Administrator
- Manager

- Team Leader

## 49. Authorization Matrix

Role × Operationが増える場合はAuthorization MatrixをTest設計の基準として利用する。

例:

| Operation | Admin | Manager | Sub Manager | Team Leader |
|---|---:|---:|---:|---:|
| 社員閲覧 | ○ | ○ | 担当のみ | 担当のみ |
| 社員更新 | ○ | ○ | 担当のみ | × |

すべてのEndpoint × Roleを機械的に重複Testするのではなく、Policy単位と代表Endpointを組み合わせる。

## 58. OpenAPIをSource of Truthとする

Test設計でも、

```text
OpenAPI
    ↓
Implementation
```

という方向を維持する。

Laravel ImplementationからOpenAPIを生成して、

```text
Implementation
    ↓
OpenAPI
```

を正としない。

---

## 59. Contract Testの導入範囲

MVPでは、すべてを独自Contract Frameworkで複雑化しない。

最低限、

- CIでOpenAPI Validation
- Representative API ResponseのSchema Validation
- Request / Response Contract確認

を行う。

必要に応じてOpenAPI対応Test Toolを導入する。

---

## 60. OpenAPI Error Contract

成功ResponseだけでなくError ResponseもContract対象とする。

特に、

- `401`
- `403`
- `404`
- `409`
- `422`
- `500`

について共通SchemaとEndpointごとのExpected Errorを確認する。

---

## 61. E2E Test

E2E Testは少数のCritical User Flowへ限定する。

例えば、

```text
Login
    ↓
社員検索
    ↓
EmployeeSkill登録
    ↓
登録結果確認
```

など。

Backend ArchitectureのTest StrategyではE2Eを中心にしない。

---

## 62. E2Eを増やしすぎない理由

E2E Testは、

- 実行が遅い
- Failure Cause特定が難しい
- Flakyになりやすい
- Setup Costが高い

ため、Business Logicの詳細確認には利用しない。

細かいRuleはDomain / Application Testへ寄せる。

---

## 63. Test Data Strategy

Test DataはTestごとに意味が明確になるように作成する。

避ける:

```text
巨大な共通Fixture
```

すべてのTestが大量の共通Dataへ依存すると、Test意図が分かりにくくなる。

必要最小限のDataを各Testで用意する。

---

## 64. Factory

Presentation / Infrastructure TestではLaravel Factoryを利用できる。

例:

```php
EmployeeModel::factory()->create();
```

ただしDomain Unit TestではEloquent Factoryを利用しない。

Domain ObjectはDomain APIから生成する。

---

## 65. Test Builder

Domain TestでAggregate生成Parameterが多くなった場合はTest Builderを導入できる。

例:

```php
EmployeeSkillTestBuilder::valid()
    ->withoutWorkExperience()
    ->withLevel(SkillLevel::LEVEL_1)
    ->build();
```

ただしBuilderによってTest Dataの重要値が隠れすぎないようにする。

---

## 66. Factory Defaultへの依存

Testの意味に重要な値はFactory Defaultへ隠さずTest内で明示する。

例えば、

```text
employment_status = ACTIVE
```

がTest Outcomeに重要なら明示する。

関係ない値だけDefaultへ任せる。

---

## 67. Test Naming

Test Nameから、

```text
Given
When
Then
```

が理解できるようにする。

例:

```text
実務未経験でLevel2を指定した場合は登録できない
```

または英語Naming Conventionを採用する場合でもBusiness意味を明確にする。

単なる、

```text
test_register_1
```

のような名前は避ける。

---

## 68. AAA Pattern

Unit Testでは必要に応じて、

```text
Arrange
Act
Assert
```

を意識する。

Testが長くなりすぎた場合は、

- Setup過多
- Responsibility過多
- Test Data過多

のSignalとして設計を見直す。

---

## 69. 1 Test 1 Concept

原則として1 Testで1つのBehavior / Scenarioを確認する。

ただし、

```text
HTTP Status
+
Error Code
+
Response Schema
```

のように1つのAPI Outcomeを構成する複数Assertはまとめてよい。

「1 Test = 1 Assert」を厳密Ruleにはしない。

---

## 70. Implementation DetailをTestしない

以下への過剰依存を避ける。

- Private Method
- 内部Method Call順
- Local Variable
- SQL文字列全文
- Eloquent内部実装
- Framework内部Behavior

可能な限りPublic BehaviorをTestする。

---

## 71. Private Method

Private Methodを直接Testしない。

Private Methodが複雑で独立Testしたくなった場合は、

> 独立したDomain Concept / Classへ抽出すべき責務ではないか

を検討する。

---

## 72. Coverage

Code Coverageは品質指標の1つとして利用できるが、目標値達成を目的化しない。

特に重要なのは、

- Core Domain
- Business Invariant
- Authorization
- Transaction
- Exception Mapping
- Concurrency
- Constraint

のCoverageである。

---

## 73. Coverage 100%を目標にしない

100% Coverageでも、

```text
Assertが弱い
Business Scenarioが不足
BoundaryをTestしていない
```

場合は品質を保証できない。

Coverageは、

> Testされていない重要箇所を探す補助指標

として扱う。

---

## 74. Mutation Testing

Mutation Testingは学習・品質向上のため将来的に導入を検討できる。

ただしMVP必須とはしない。

Core DomainのTest品質を測る用途として特に相性がよい。

---

## 75. Static Analysisとの役割分担

Testですべての問題を検出しようとしない。

Static Analysis / Linter / Complexity / Maintainability Monitoring等で検出できるものはそちらへ任せる。

TestはRuntime BehaviorとBusiness Outcomeに集中する。

---

## 76. TestとCode Quality

複雑なTest Setupが増えた場合はProduction Code側の設計問題を疑う。

例えば、

```text
Handler生成にDependency 15個必要
```

であればTest Helperで隠す前にResponsibilityを見直す。

TestabilityをArchitecture Feedbackとして利用する。

---

## 77. Performance Test

MVPでは大規模Load Testを常時実施しない。

ただしNFRで定義した重要Endpointについて必要になった場合、

- Response Time
- Query Count
- Index利用
- Pagination
- Dashboard Aggregate

を検証する。

---

## 78. Query Count / N+1

N+1がRiskとなるQueryではQuery Countの確認を検討する。

特に、

- Employee一覧
- EmployeeSkill一覧
- Dashboard
- Related Master表示

など。

ただしすべてのFeature TestへQuery Count Assertを入れない。

Performance-sensitiveな箇所だけ対象とする。

---

## 79. SQL Execution Plan

Performance Issueが発生したQueryではPostgreSQL `EXPLAIN` / `EXPLAIN ANALYZE` を利用して調査する。

Execution Planそのものを通常のAutomated Testで固定的にAssertしない。

Plannerの細部へTestを強く結合しない。

---

## 80. Security Test

Backend TestではSecurity上重要なBoundaryも確認する。

例:

- Authentication Required
- Authorization
- Assigned Employee Scope
- Permission Management
- Invalid Input
- Sensitive Error Detail非公開

Security ToolによるDynamic Testとは別にApplication Testでも保証する。

---

## 81. Permission Test

特に以下は重要Test対象とする。

```text
ADMINISTRATOR
+
can_manage_permissions = true
```

のみPermission管理可能。

そして、

```text
Permission Manager >= 1
```

を常に維持する。

Role CheckだけでなくConcurrent Operationまで含めて検証する。

---

## 82. Retired Employee Test

退職Employeeに関するRequirementとして、

- Dashboard集計対象外
- Retention対象
- 通常の在籍者Queryからの除外条件

などを該当UseCase / Query Testで確認する。

3年後削除Workflowを実装する段階ではClockを利用したBoundary Testを追加する。

---

## 83. Disabled Skill Test

Skill無効化について、

```text
完全削除しない
```

RequirementをTestする。

代表Scenario:

- 無効化後も既存EmployeeSkillとのReferenceが維持される
- 新規登録候補では除外される
- 必要なReadでは表示可能

UseCase Requirementに応じてTestする。

## 100. 最終方針

本システムのTest Strategyは、

> Business RuleはDomain、UseCase FlowはApplication、技術IntegrationはInfrastructure、HTTP ContractはPresentationで検証する

方針とする。

基本構造は、

```text
Domain
    ↓
Unit Test

Application
    ↓
Unit Test

Infrastructure
    ↓
PostgreSQL Integration Test

Presentation
    ↓
Laravel Feature Test

OpenAPI
    ↓
Contract Test
```

とする。

特にPostgreSQLへ依存する、

```text
Sequence
Constraint
Transaction
SELECT FOR UPDATE
Concurrency
```

についてはSQLiteやMockで代替せず、実PostgreSQLで検証する。

ConcurrencyによってBusiness Invariantが破壊される、

```text
Permission Managerを最低1人維持する
```

Ruleについては実際の複数Transactionを利用したConcurrency Testを行う。

一方で、すべてをFeature / E2E Testへ寄せず、

> 最もBusiness意味を理解しているLayerで最も詳細にTestする

ことを原則とする。

最終的な設計基準は、

> TestをImplementation Detailの固定装置ではなく、Business BehaviorとArchitecture Boundaryを安全に変更し続けるためのSafety Netとして設計すること

とする。
