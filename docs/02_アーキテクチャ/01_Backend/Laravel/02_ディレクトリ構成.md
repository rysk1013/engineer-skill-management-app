# Backend ディレクトリ構成

## 1. 目的

Backendのディレクトリ構成は、Laravelの標準構成を活かしながら、DDDおよびClean Architectureの責務分離をコード上でも明確にすることを目的とする。

本プロジェクトでは、以下を基本方針とする。

- Laravel標準構成を無理に捨てない
- `app/` 配下で主要Layerを明示する
- Domain / ApplicationはBounded Context単位で整理する
- DomainはBounded Context → Aggregate単位で整理する
- ApplicationはBounded Context → UseCase単位で整理する
- Infrastructureへ技術的詳細を集約する
- PresentationへHTTP固有処理を集約する
- ディレクトリ構成そのものを目的化しない

---

## 2. 全体構成

Backendの基本構成は以下とする。

```text
app/
├── Domain/
├── Application/
├── Presentation/
├── Infrastructure/
└── Providers/

bootstrap/
config/
database/
routes/
tests/
```

Laravel標準の以下のディレクトリはそのまま利用する。

- `bootstrap/`
- `config/`
- `database/`
- `routes/`
- `storage/`
- `tests/`

DDD / Clean ArchitectureのためにLaravel全体の構成を独自形式へ置き換えない。

---

## 4. Domain Layer

Domain LayerはBounded Context単位で整理する。

```text
app/
└── Domain/
    ├── EmployeeManagement/
    ├── SkillManagement/
    ├── AccessControl/
    └── Authentication/
```

Bounded Context配下は、原則としてAggregate単位で整理する。

例えばSkill Managementは以下のように構成する。

```text
app/
└── Domain/
    └── SkillManagement/
        ├── EmployeeSkill/
        │   ├── EmployeeSkill.php
        │   ├── EmployeeSkillId.php
        │   ├── SkillLevel.php
        │   ├── WorkExperience.php
        │   ├── ExperiencePeriod.php
        │   ├── LastUsedMonth.php
        │   └── Exceptions/
        │
        ├── Skill/
        │   ├── Skill.php
        │   ├── SkillId.php
        │   └── Exceptions/
        │
        ├── SkillCategory/
        │   ├── SkillCategory.php
        │   ├── SkillCategoryId.php
        │   └── Exceptions/
        │
        ├── Repositories/
        └── Policies/
```

Domain Layerでは、以下のような横断的な分類を最上位に置かない。

```text
Entities/
ValueObjects/
Enums/
Services/
```

例えば、

```text
Domain/
└── ValueObjects/
    ├── EmployeeId.php
    ├── SkillId.php
    └── SkillLevel.php
```

のような構成は原則として採用しない。

Domain Objectは、それが属するBounded ContextおよびAggregateの近くに配置する。

これにより、技術的な種類ではなく、業務上のまとまりを優先する。

---

## 5. Domain Repository Interface

Repository InterfaceはDomain Layerへ配置する。

```text
app/
└── Domain/
    └── SkillManagement/
        └── Repositories/
            ├── EmployeeSkillRepository.php
            ├── SkillRepository.php
            └── SkillCategoryRepository.php
```

Repository InterfaceはAggregate単位を基本とする。

Eloquent ModelやQuery Builderなど、Infrastructure固有の型をInterfaceへ露出しない。

---

## 6. Application Layer

Application LayerはBounded Context単位で整理し、その配下をUseCase単位で構成する。

```text
app/
└── Application/
    └── SkillManagement/
        ├── Commands/
        └── Queries/
```

Command側は以下のようにUseCase単位でまとめる。

```text
Application/
└── SkillManagement/
    └── Commands/
        ├── RegisterEmployeeSkill/
        │   ├── RegisterEmployeeSkillCommand.php
        │   └── RegisterEmployeeSkillHandler.php
        │
        ├── UpdateEmployeeSkill/
        │   ├── UpdateEmployeeSkillCommand.php
        │   └── UpdateEmployeeSkillHandler.php
        │
        └── DeactivateSkill/
            ├── DeactivateSkillCommand.php
            └── DeactivateSkillHandler.php
```

Query側も同様にUseCase単位で構成する。

```text
Application/
└── SkillManagement/
    └── Queries/
        ├── GetEmployeeSkill/
        │   ├── GetEmployeeSkillQuery.php
        │   ├── GetEmployeeSkillHandler.php
        │   └── GetEmployeeSkillResult.php
        │
        └── SearchEmployeeSkills/
            ├── SearchEmployeeSkillsQuery.php
            ├── SearchEmployeeSkillsHandler.php
            └── SearchEmployeeSkillsResult.php
```

以下のような完全な技術分類による横割りは原則として採用しない。

```text
Commands/
Handlers/
DTOs/
Queries/
```

CommandとHandlerなど、同じUseCaseに属するObjectは近くに配置する。

---

## 7. Application Port

Application LayerからInfrastructure機能を利用する必要がある場合は、Application側にPortとなるInterfaceを定義する。

例えば以下を対象とする。

- Transaction Manager
- ID Generator
- Current Actor Context
- 外部サービス連携

例:

```text
app/
└── Application/
    └── Shared/
        └── Ports/
            ├── TransactionManager.php
            └── EmployeeSkillIdGenerator.php
```

ただし、`Shared` は必要になった時点で導入し、最初から汎用Objectを大量に集約しない。

---

## 8. Presentation Layer

HTTP固有処理はPresentation Layerへ配置する。

```text
app/
└── Presentation/
    └── Http/
        ├── Controllers/
        ├── Requests/
        ├── Resources/
        └── Middleware/
```

ControllerはUseCaseとの対応関係を把握しやすい構成とする。

例えば以下とする。

```text
Presentation/
└── Http/
    └── Controllers/
        └── SkillManagement/
            ├── RegisterEmployeeSkillController.php
            ├── UpdateEmployeeSkillController.php
            └── GetEmployeeSkillController.php
```

Single Action Controllerを基本とし、

```text
1 Controller = 1 HTTP Action
```

とする。

Form Requestも対象Contextに合わせて整理する。

```text
Presentation/
└── Http/
    └── Requests/
        └── SkillManagement/
            ├── RegisterEmployeeSkillRequest.php
            └── UpdateEmployeeSkillRequest.php
```

API Resourceについても同様とする。

---

## 9. Infrastructure Layer

Infrastructure LayerにはFramework・Database・外部サービスなどの技術的詳細を配置する。

基本構成を以下とする。

```text
app/
└── Infrastructure/
    ├── Persistence/
    │   ├── Eloquent/
    │   ├── Repositories/
    │   ├── Mappers/
    │   └── QueryServices/
    │
    ├── Authentication/
    ├── Transaction/
    ├── IdGeneration/
    └── External/
```

---

## 10. Eloquent

Eloquent ModelはInfrastructure Layerへ配置する。

```text
Infrastructure/
└── Persistence/
    └── Eloquent/
        └── Models/
            ├── EmployeeModel.php
            ├── SkillModel.php
            └── EmployeeSkillModel.php
```

Laravel標準の `app/Models` は使用せず、EloquentをPersistenceの技術詳細として明示する。

ただし、Laravelや利用Packageの都合で標準配置が実質的に必要なModelがある場合は例外を許容する。

その場合もDomain Modelとは明確に区別する。

---

## 11. Repository Implementation

Repository実装はInfrastructureへ配置する。

```text
Infrastructure/
└── Persistence/
    └── Repositories/
        ├── EloquentEmployeeSkillRepository.php
        ├── EloquentSkillRepository.php
        └── EloquentSkillCategoryRepository.php
```

依存関係は以下とする。

```text
Domain
EmployeeSkillRepository
        ↑
        │ implements
        │
Infrastructure
EloquentEmployeeSkillRepository
```

DomainはInfrastructure側のRepository実装を知らない。

---

## 12. Mapper

Eloquent ModelとDomain Modelの変換はMapperへ集約する。

```text
Infrastructure/
└── Persistence/
    └── Mappers/
        ├── EmployeeSkillMapper.php
        ├── SkillMapper.php
        └── EmployeeMapper.php
```

MapperはInfrastructure Layerへ配置する。

主な責務は以下とする。

```text
Eloquent Model
      ↓
   toDomain()
      ↓
Domain Model
```

および、

```text
Domain Model
      ↓
  fillModel()
      ↓
Eloquent Model
```

とする。

具体的なMapper設計は `Repository・Mapper.md` で定義する。

---

## 13. Query Service

CQRSのRead処理に利用するQuery Service実装はInfrastructureへ配置する。

```text
Infrastructure/
└── Persistence/
    └── QueryServices/
        └── SkillManagement/
            ├── EmployeeSkillQueryService.php
            └── EmployeeSearchQueryService.php
```

Query Serviceでは必要に応じて以下を利用できる。

- Eloquent Query Builder
- Laravel Query Builder
- Raw SQL
- PostgreSQL固有機能

Read処理ではDomain Aggregateの復元を必須としない。

---

## 14. Transaction

Laravel / Database固有のTransaction実装はInfrastructureへ配置する。

```text
Infrastructure/
└── Transaction/
    └── LaravelTransactionManager.php
```

Application側で定義されたTransaction Portを実装する。

```text
Application
TransactionManager
        ↑
        │ implements
        │
Infrastructure
LaravelTransactionManager
```

---

## 15. ID Generation

ID生成のInfrastructure実装は以下へ配置する。

```text
Infrastructure/
└── IdGeneration/
    ├── PostgreSqlEmployeeIdGenerator.php
    ├── PostgreSqlSkillIdGenerator.php
    └── PostgreSqlEmployeeSkillIdGenerator.php
```

PostgreSQL Sequenceなどの具体的な仕組みはInfrastructureへ閉じ込める。

---

## 16. Authentication

Laravel Sanctumなど、認証技術に依存する実装はInfrastructureへ配置する。

```text
Infrastructure/
└── Authentication/
```

Authentication Domain / ApplicationがSanctumなどのFramework固有実装へ直接依存しない構成とする。

---

## 17. External Service

外部サービスとの連携実装はInfrastructureへ配置する。

```text
Infrastructure/
└── External/
```

必要になった場合はサービス単位で分割する。

```text
External/
├── SomeApi/
└── SomeNotificationService/
```

MVP時点で不要なディレクトリは事前に作成しない。

---

## 18. Service Provider

Dependency InjectionのBindingはLaravel Service Providerで管理する。

```text
app/
└── Providers/
    ├── AppServiceProvider.php
    └── ArchitectureServiceProvider.php
```

プロジェクト規模に応じて、必要であれば責務別にService Providerを分割する。

ただし、初期段階から過剰にService Providerを細分化しない。

---

## 19. routes

Route定義はLaravel標準の `routes/` を利用する。

```text
routes/
└── api.php
```

API規模が大きくなった場合はBounded ContextやVersion単位で分割できる。

例:

```text
routes/
├── api.php
└── api/
    └── v1/
        ├── employees.php
        ├── skills.php
        └── access-control.php
```

ただし、MVPでは必要になるまで分割しない。

---

## 20. database

Laravel標準の `database/` を利用する。

```text
database/
├── factories/
├── migrations/
└── seeders/
```

MigrationはInfrastructure Layerへ移動しない。

Laravelの標準運用との親和性を優先する。

---

## 21. tests

Testはテスト種別と対象Layerを把握しやすい構成とする。

基本形を以下とする。

```text
tests/
├── Unit/
│   ├── Domain/
│   └── Application/
│
├── Integration/
│   └── Infrastructure/
│
└── Feature/
    └── Presentation/
```

想定する役割は以下とする。

```text
Unit/Domain
    Domain ModelのUnit Test

Unit/Application
    Application HandlerのTest

Integration/Infrastructure
    PostgreSQL / Repository / Mapper等のIntegration Test

Feature/Presentation
    HTTP APIのFeature Test
```

具体的なTesting方針は `テスト戦略.md` で定義する。

## 23. ディレクトリ設計原則

Backend全体で以下の原則を維持する。

```text
Domain / Application
    ↓
Bounded Contextを優先して整理する

Domain
    ↓
Aggregate単位で近接配置する

Application
    ↓
UseCase単位でCommand / Handler等を近接配置する

Presentation
    ↓
HTTP固有処理を集約する

Infrastructure
    ↓
Framework / Database / External Serviceの詳細を集約する
```

ディレクトリの技術分類を細かくすることより、

> 関連する業務概念とUseCaseを近くに配置し、責務と依存方向がコード上から理解できること

を優先する。

また、将来利用する可能性だけを理由として空のDirectoryや抽象化を事前に大量作成しない。

必要になった時点で段階的に追加する。
