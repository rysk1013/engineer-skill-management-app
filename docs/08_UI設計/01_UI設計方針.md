# UI設計方針

## 1. 目的

本ドキュメントは、Engineer Skill Management App のMVPにおけるUI設計の共通方針を定義する。

Phase 1「UI設計」では、Frontend実装を開始する前に、画面構成・画面遷移・共通レイアウト・Design System・共通UIコンポーネント・各画面の状態を設計し、後続のFrontend実装でUIに関する大きな判断を追加で行わなくても実装へ着手できる状態を目指す。

---

## 2. UI設計の対象範囲

Phase 1では、MVPで必要となる以下をUI設計の対象とする。

- 画面一覧
- URL / Route
- 画面遷移
- Navigation
- App Shell
- 共通レイアウト
- Design System
- 共通UIコンポーネント
- 各画面のレイアウト
- 入力フォーム
- 一覧・詳細表示
- Loading状態
- Empty状態
- Error状態
- Validation Error状態
- Disabled状態
- Confirmation状態
- Success Feedback
- 権限による表示制御
- Responsive対応

MVP対象外の機能については、将来拡張を阻害しない範囲で考慮するが、Phase 1では詳細なUI設計を行わない。

---

## 3. UI設計とFrontend実装の責務境界

Phase 1ではUIの仕様を定義し、実際のFrontendコード実装は後続Phaseで行う。

### 3.1 Phase 1で決定するもの

- どの画面が存在するか
- 各画面の目的
- 画面間の遷移
- Route
- Navigation構造
- 各画面に表示する情報
- 各画面で可能な操作
- 共通レイアウト
- 共通UIパターン
- 利用するshadcn/ui Component
- Application固有の共通Componentが必要となる箇所
- UI状態
- 権限による表示・操作差
- Responsive時の基本的な挙動

### 3.2 後続のFrontend実装で決定するもの

以下の技術的な実装詳細は、既存のFrontend設計・技術選定に従い後続Phaseで決定・実装する。

- React Componentの具体的な分割
- Server Component / Client Componentの具体的な境界
- shadcn/ui Componentの具体的なSource Code調整
- Tailwind CSS Classの具体的な記述
- Component内部の実装
- API Clientの具体的な利用
- BFFとの接続処理
- Auth.jsとの接続処理
- State管理の具体的な実装
- Form処理の具体的な実装
- テストコード
- Performance最適化の実装詳細

UI設計では、Frontend実装方式を必要以上に拘束しない。

---

## 4. 基本設計方針

### 4.1 Desktop First

本システムは社員・スキル情報の管理を主目的とする業務システムであるため、MVPではDesktopでの利用を中心に設計する。

設計の優先順位は以下とする。

1. Desktop
2. Tablet
3. Mobile

Mobileについても主要な情報の閲覧・基本操作が破綻しない設計とするが、Desktopと完全に同一の操作性を求めない。

---

### 4.2 一貫性を優先する

個別画面ごとに独自UIを作るのではなく、同じ意味・同じ操作には可能な限り同じUIパターンを使用する。

UI Componentはshadcn/uiを基本とし、個別画面ごとに独自Componentや独自Styleを増やさない。

特に以下は共通化を優先する。

- Page Header
- Navigation
- Breadcrumb
- Button
- Form Control
- Table
- Badge
- Pagination
- Search / Filter
- Dialog
- Alert Dialog
- Confirmation
- Loading
- Empty
- Error
- Notification

---

### 4.3 情報の確認しやすさを優先する

Engineer Skill Management Appでは、社員・スキル・経験情報を確認する操作が中心となる。

そのため、装飾性よりも以下を優先する。

- 情報の読み取りやすさ
- 一覧性
- 操作対象の分かりやすさ
- 状態の識別しやすさ
- 誤操作の防止
- 一貫した情報階層

---

### 4.4 MVPに不要な複雑化を避ける

Phase 1では、MVPに必要なUIを優先する。

将来利用する可能性だけを理由として、以下のような過剰な設計は行わない。

- 不要な高度カスタマイズ
- 過度なAnimation
- 必要性が確定していないDashboard Widget
- 複雑なDrag & Drop
- 多数の表示モード
- MVPで利用しない設定画面
- 必要性が明確でないUI Libraryの追加

---

## 5. App Shell / 共通レイアウト方針

認証後の主要画面は、共通のApp Shellを使用する。

基本構造は以下とする。

```text
+----------------------------------------------------------+
| Header                                                   |
+------------------+---------------------------------------+
|                  |                                       |
| Sidebar          | Main Content                          |
|                  |                                       |
|                  |                                       |
|                  |                                       |
+------------------+---------------------------------------+
```

Main Content内は原則として以下の情報階層を使用する。

```text
Breadcrumb

Page Header
├── Page Title
├── Description
└── Primary Action

Page Content
```

### 5.1 Header

Headerはアプリケーション全体で共通して必要となる情報・操作を配置する。

詳細な項目は共通レイアウト設計で決定する。

### 5.2 Sidebar

主要機能へのNavigationを提供する。

Navigation項目はユーザーの権限に応じて表示を制御する。

### 5.3 Main Content

各画面固有のコンテンツを表示する。

画面ごとに最大幅や余白を独自設定するのではなく、共通レイアウトルールに従う。

---

## 6. Responsive設計方針

### 6.1 Desktop

Desktopを基準UIとする。

- Sidebarを常時表示可能とする
- Tableによる一覧表示を基本とする
- Formは情報量に応じて複数Columnを使用可能とする
- 主要操作を画面上で確認しやすく配置する

### 6.2 Tablet

Tabletでは利用可能な横幅に合わせてレイアウトを調整する。

- Sidebarは必要に応じて縮小・開閉可能な構成とする
- FormのColumn数を減らす
- Tableは重要情報を優先して表示する
- 操作領域を過度に狭くしない

### 6.3 Mobile

Mobileでは1 Columnを基本とする。

- Navigationは折りたたみ可能とする
- Formは原則1 Columnとする
- 横幅依存のUIを避ける
- Tableがそのまま表示困難な場合は、横スクロールまたは情報構造の変更を検討する
- Primary Actionへ到達できる状態を維持する

BreakpointはTailwind CSS v4の既存Breakpointを基本候補とし、Responsive設計との整合を保って管理する。

Application独自のBreakpoint値はPhase 1で固定せず、実装時のLayout・情報量・操作性を基準に必要性を判断する。

---

## 7. UI・Styling技術との関係

UI設計は、Frontend技術選定で決定済みの以下の構成を前提とする。

```text
Next.js + React
       |
       v
Application UI
       |
       +-------------------------+
       |                         |
       v                         v
   shadcn/ui                  Lucide
       |                         |
       v                         v
    Base UI                 lucide-react
       |
       v
Tailwind CSS v4
       |
       v
CSS Variables
       |
       v
Design Token

       +

      cn
       |
       v
Class Composition
```

UI設計フェーズで、これらと責務が重複する別のLibraryを前提とした設計を行わない。

---

## 8. Design System方針

Design Systemは、MVPのUI一貫性を維持するために必要な範囲を定義する。

### 8.1 Foundation

以下をDesign Systemの対象とする。

- Color
- Typography
- Spacing
- Border
- Radius
- Shadow
- Icon
- Breakpoint
- Layout

すべてのCSS値をDesign Token化することを目的とせず、Application全体で共通の意味を持つ値を中心に管理する。

---

### 8.2 Design Token

Design Tokenは以下を基本として管理する。

```text
Tailwind CSS v4
     +
CSS Variables
```

Theme設定専用の追加LibraryはMVPでは導入しない。

Application全体で意味を持つ値をComponentへ直接埋め込むことは可能な限り避ける。

---

### 8.3 Semantic Token

Colorについては、具体的な色名ではなくSemanticな役割を基本とする。

例:

```text
background
foreground
primary
secondary
muted
accent
destructive
border
input
ring
```

基本構造は以下とする。

```text
Component
    ↓
Semantic Token
    ↓
Actual Color
```

UI設計では「青」「赤」などの具体色を状態の意味として定義せず、`primary`、`destructive` 等のSemanticな役割を使用する。

---

### 8.4 Semantic State

以下の状態を視覚的に区別できるようにする。

- Default
- Primary
- Success
- Warning
- Error
- Disabled

色だけに依存した状態表現は避け、必要に応じてText・Icon・Label等を併用する。

---

### 8.5 Dark Mode

Design TokenはDark Modeへ対応可能な構造とする。

ただし、

```text
Dark Modeへ対応可能な設計
```

と、

```text
MVPでDark Mode切り替え機能を提供する
```

ことは分離する。

Dark Mode切り替え機能をMVPへ含めるかは、UI要件として別途決定する。

---

## 9. shadcn/ui利用方針

### 9.1 基本方針

ApplicationのUI Componentにはshadcn/uiを採用する。

共通UIをゼロから独自実装することを基本とせず、まずshadcn/uiで要件を満たせるか確認する。

基本構成は以下とする。

```text
Application Component
        ↓
     shadcn/ui
        ↓
      Base UI
        ↓
 Tailwind CSS v4
```

---

### 9.2 Componentの導入

shadcn/ui Componentを一括導入しない。

個別画面および共通UI設計を進める中で必要性が確認できたComponentのみ導入する。

想定されるComponentの例:

- Button
- Input
- Textarea
- Select
- Checkbox
- Radio Group
- Dialog
- Alert Dialog
- Dropdown Menu
- Table
- Badge
- Tooltip
- Alert
- Breadcrumb
- Pagination

この一覧は導入を確定するものではない。

実際に使用するComponentは、各UI設計で必要性を確認して決定する。

---

### 9.3 Componentのカスタマイズ

shadcn/uiから追加したComponentはApplication側でSource Codeを管理し、UI要件に応じてカスタマイズ可能とする。

ただし、Componentごとに場当たり的な変更を行わない。

カスタマイズには主に以下を利用する。

- Design Token
- Variant
- Application共通Component
- Tailwind CSS

個別画面固有のStyleをshadcn/ui Component本体へ直接持ち込むことは避ける。

---

### 9.4 Application共通Component

shadcn/ui ComponentとApplication固有Componentは責務を分離する。

例:

```text
shadcn/ui
├── Button
├── Input
├── Select
├── Dialog
├── Alert Dialog
└── Table

Application共通Component
├── PageHeader
├── SearchForm
├── DataTable
└── EmptyState
```

Application共通Componentは、複数画面で共通するApplication固有の意味・操作がある場合に作成する。

単にshadcn/ui Componentを別名でWrappingすることを目的としない。

確認UIについても、shadcn/uiの `Alert Dialog` を直接利用して十分な場合は、Application共通の `ConfirmDialog` 等を追加しない。

複数Featureで共通する確認UIの責務が実際に必要になった場合のみ、Application共通Componentとしての抽象化を検討する。

---

### 9.5 Base UI

Primitive / Headless UIには、shadcn/uiが利用するBase UIを採用する。

ApplicationからBase UIを直接利用することは原則として避け、shadcn/ui Componentを経由する。

以下の場合のみ、Base UIを直接利用してApplication固有Componentを構築することを検討する。

- shadcn/uiに必要なComponentが存在しない
- shadcn/ui Componentでは要件を満たせない
- Application固有のPrimitive Componentが必要
- Accessibilityを維持しながら独自UIを構築する必要がある

その場合も、まずshadcn/uiで実現できないか確認する。

---

## 10. Icon方針

Icon LibraryにはLucideを採用し、Reactでは `lucide-react` を使用する。

UI設計でIconが必要な場合は、Lucideで表現可能かを前提として設計する。

複数のIcon Libraryを理由なく併用しない。

### 10.1 Iconの利用

Iconは以下の用途で使用する。

- 操作の補助
- Navigation
- 状態の補助表現
- 情報の視認性向上

Iconのみへ意味を依存しない。

必要に応じて以下を組み合わせる。

```text
Icon
 +
Text
 +
Color
```

IconのみのButtonを使用する場合は、Accessible Nameを提供できる設計とする。

---

## 11. Class Utility方針

Class NameのCompositionには `cn` を使用する。

UI設計段階では具体的なClass Nameを定義しないが、以下の責務分担を前提とする。

```text
Variant Utility
      ↓
Component Variant

cn
      ↓
Class Composition
```

`clsx`、`tailwind-merge`、`classnames` 等を別のApplication向けClass Utilityとして追加利用することを前提としない。

---

## 12. UI状態設計方針

各画面は正常表示だけでなく、必要な状態を明示的に設計する。

### 12.1 Loading

データ取得中であることがユーザーに分かる状態とする。

画面全体・一覧・操作単位など、Loadingの範囲を区別する。

必要に応じてAccessible StatusやTextを提供できる構成とする。

### 12.2 Empty

データが存在しない状態とする。

単に空白を表示するのではなく、以下を可能な範囲で示す。

- データが存在しないこと
- 次に実行可能な操作

### 12.3 Error

データ取得・処理に失敗した状態とする。

可能な範囲で以下を理解できる内容とする。

- 何が失敗したか
- 次に何をすればよいか

ユーザーが必要に応じて再試行または別操作へ進めるようにする。

### 12.4 Validation Error

入力項目とError Messageの対応が分かるように表示する。

画面上部だけにErrorを表示するのではなく、対象Field付近で内容を確認できることを基本とする。

### 12.5 Disabled

操作できない理由がユーザーから理解できない状態を可能な限り避ける。

権限不足など、操作自体を提示する必要がない場合は非表示も検討する。

### 12.6 Confirmation

削除・無効化・退職等、誤操作による影響が大きい操作では、必要に応じてConfirmationを設ける。

重要・破壊的操作のConfirmationには、shadcn/uiの `Alert Dialog` を基本候補とする。

通常の入力・編集用 `Dialog` と、重要操作を確認する `Alert Dialog` の責務を分離する。

すべての操作にConfirmationを設けるのではなく、誤操作による影響を基準として判断する。

具体的なConfirmationの要否はFeature固有設計を正とする。

### 12.7 Success Feedback

登録・更新等の操作が成功したことを適切にフィードバックする。

使用する具体的なUI Componentは共通コンポーネント設計で決定する。

---

## 13. 権限とUIの設計方針

UIは既存のRole・Permission仕様に従う。

権限によって以下を制御する。

- Navigationの表示
- Pageへのアクセス
- Actionの表示
- Formの編集可否
- 管理機能の表示

Frontend上の表示制御のみをSecurity Boundaryとはしない。

最終的な認可はBackend側の認可処理を正とし、Frontendの権限制御はユーザーに利用可能な操作を適切に提示するためのUI制御として扱う。

権限がない操作については、用途に応じて以下を使い分ける。

- 非表示
- Disabled
- Access Denied表示

---

## 14. Form設計方針

Formでは以下を基本とする。

- 必須・任意が判別できる
- Labelと入力項目の対応を明確にする
- PlaceholderのみをLabelの代替として利用しない
- Validation Errorを対象項目付近に表示する
- 入力例や制約が必要な場合は補足を表示する
- 保存・キャンセル等の操作位置を画面間で統一する
- 二重送信を防止する
- Server側Validationを前提とする
- Keyboardで主要操作を実行可能とする

入力項目の具体的な制約は、要件定義・API仕様・Domain仕様を正とする。

UI独自のValidation Ruleを新たに定義しない。

---

## 15. 一覧画面設計方針

社員・スキル等の一覧画面ではSemanticなHTML Tableを基本とする。

一覧画面では必要に応じて以下を設計する。

- Search
- Filter
- Sort
- Pagination
- Detailへの遷移
- Create Action
- Edit Action
- Status表示

一覧画面にすべての情報を表示せず、一覧で判断するために必要な情報を優先する。

詳細情報はDetail画面へ分離する。

Layout目的でTableを使用しない。

---

## 16. 削除・無効化UIの方針

Domain上で物理削除せず無効化・保持する対象については、UI上でもDomain仕様に合わせる。

「削除」「無効化」「退職」等、意味の異なる操作を同一表現にまとめない。

操作Labelは、実際にDomainで発生する変更をユーザーが理解できる表現とする。

影響が大きい操作については、shadcn/uiの `Alert Dialog` を利用したConfirmationを基本候補とする。

ただし、共通確認UIが存在することを理由として、Domain上存在しない削除・無効化・再有効化等の操作をUIへ追加しない。

Confirmationの具体的な内容・実行可否・Domain Ruleは、各Featureの既存仕様および個別画面設計を正とする。

---

## 17. Accessibility方針

Accessibilityはshadcn/uiだけに依存せず、Application全体で担保する。

基本構成は以下とする。

```text
Semantic HTML
      +
   Base UI
      +
  shadcn/ui
      +
Application実装
      ↓
Accessibility
```

少なくとも以下を基本とする。

- 可能な限りSemantic HTMLを使用する
- Keyboard操作を阻害しない
- Formに適切なLabelを設ける
- PlaceholderのみをLabelとして使用しない
- Focus状態を視認可能にする
- Focus Ringを理由なく削除しない
- 色だけで状態を伝えない
- ForegroundとBackgroundのContrastを考慮する
- Iconのみの操作にはAccessible Nameを提供する
- Dialog / Alert DialogではFocus Managementを考慮する
- Dialog / Alert Dialog Close後は必要に応じて起動元へFocusを戻す
- Error Messageと対象Fieldの関係を適切に表現する
- Loading / ErrorをVisualだけに依存して伝えない
- Table形式のデータにはSemanticなHTML Tableを使用する

ARIAはSemantic HTMLだけでは不足する場合に使用し、不要な `role` や `aria-*` 属性を追加しない。

---

## 18. 各画面設計の記述フォーマット

個別画面の設計では、原則として以下の項目を使用する。

```text
# <画面名>

## 1. 目的

## 2. 対象ユーザー・権限

## 3. Route

## 4. 画面構成

## 5. 表示項目

## 6. 操作

## 7. 利用する共通UI
- shadcn/ui Component
- Application共通Component

## 8. 画面遷移

## 9. UI状態
- Loading
- Empty
- Error
- Validation Error
- Success

## 10. Responsive

## 11. Accessibility

## 12. 備考
```

画面の性質上不要な項目は省略してよい。

必要な情報がある場合は項目を追加できるが、同じ種類の情報について画面ごとに異なる構成を増やさない。

---

## 19. Wireframe方針

Phase 1では、各画面について実装可能なレベルまで構造を確認できるWireframeを作成する。

Wireframeでは主に以下を確認する。

- 情報階層
- UI要素の配置
- 主要Action
- Navigation
- 画面間の関係
- 一覧と詳細の役割分担
- Form構成
- 利用する共通UI
- Responsive時の構造変化

Pixel単位の完成デザインを目的としない。

色・余白・Typography等の詳細はDesign Systemで共通化し、個別画面設計で重複定義しない。

---

## 20. UI設計の進め方

Phase 1では以下の順序を基本とする。

```text
UI設計方針
    ↓
画面一覧
    ↓
画面遷移 / Route
    ↓
App Shell / 共通レイアウト
    ↓
Design System
    ↓
shadcn/ui / 共通UI Component
    ↓
各画面Wireframe
    ↓
各画面詳細設計
    ↓
UI状態 / Responsive確認
    ↓
Phase 1 統合確認
```

設計途中で個別画面から共通UIの追加・変更が必要になった場合は、共通設計へフィードバックする。

新しいUI Componentが必要になった場合は、以下の順序で検討する。

1. shadcn/uiで実現できるか
2. Base UIで実現できるか
3. Application共通Componentとして構築すべきか
4. 既存Libraryと責務が重複しないか
5. MVPで本当に必要か

---

## 21. 正式仕様との関係

UI設計は既存の以下の仕様を前提とする。

- 要件定義
- アーキテクチャ
- システム設計
- 技術選定
- MVP実装計画
- 開発・運用ルール
- 非機能要件

特にUI・Stylingの技術選定については、`docs/04_技術選定/Frontend/03_UI・Styling.md` を正とする。

UI設計によって既存仕様を暗黙的に変更しない。

UI設計中に既存仕様との矛盾や不足が判明した場合は、UI側だけで解決せず、正となる既存ドキュメントを確認し、必要に応じて正式仕様を更新する。

## 22. Phase 1完了時の目標

Phase 1完了時には、少なくとも以下を判断できる状態とする。

- MVPにどの画面が存在するか
- 各画面へどのように遷移するか
- 各画面に何を表示するか
- 各画面で何を操作できるか
- 権限によって何が異なるか
- どのshadcn/ui Componentを利用するか
- どのApplication共通Componentが必要か
- Design Tokenをどのように利用するか
- Loading / Empty / Error等でどのように表示するか
- Desktop / Tablet / Mobileでどのように表示するか
- Accessibility上どのような配慮が必要か

これにより、後続PhaseでFrontend実装へ着手できる状態とする。
