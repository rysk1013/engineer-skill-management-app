# 画面一覧

## 1. 目的

本ドキュメントは、Engineer Skill Management App のMVPで必要となる画面を定義する。

各画面について、以下を整理する。

- 画面ID
- 画面名
- Route
- 目的
- 対象ユーザー
- 主な表示内容
- 主な操作

本ドキュメントで定義した画面一覧を、画面遷移・共通レイアウト・個別画面UI設計の基準とする。

---

## 2. 基本方針

### 2.1 Route

FrontendのRouteはNext.js App Routerで管理する。

本ドキュメントでは、ユーザーがブラウザ上でアクセスするFrontend Routeを定義する。

Backend APIのRouteとは分離して扱う。

新規作成画面および編集画面のRouteは、以下を基本とする。

```text
一覧
/resource

詳細
/resource/[resourceId]

新規作成
/resource/create

編集
/resource/[resourceId]/edit
```

Frontend Routeの `create` / `edit` は画面を表す。

実際の登録・更新処理はLaravel Backend APIに対してHTTP Methodで実行する。

例:

```text
Frontend

/employees/create
/employees/[employeeId]/edit

Backend API

POST /api/v1/employees
PUT /api/v1/employees/{employeeId}
```

---

### 2.2 認証

認証が必要な画面は、未認証状態ではアクセスできない。

未認証状態で認証必須画面へアクセスした場合は、ログイン画面へ遷移する。

認証状態はAuth.jsで管理する。

---

### 2.3 権限

画面・操作の表示可否は、既存のRole / Permission仕様に従う。

MVPで利用するRoleは以下を前提とする。

- 管理者
- マネージャー
- サブマネージャー
- チームリーダー

一般社員RoleはMVPでは利用しない。

管理者については、権限管理可能かどうかを `can_manage_permissions` により区別する。

Frontend上の権限制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

MVPの画面を以下の機能に分類する。

```text
認証
├── ログイン

社員管理
├── 社員一覧
├── 社員詳細
├── 社員登録
└── 社員編集

スキル管理
├── スキル一覧
├── スキル登録
└── スキル編集

スキルカテゴリ管理
├── スキルカテゴリ一覧
├── スキルカテゴリ登録
└── スキルカテゴリ編集

社員スキル管理
└── 社員スキル編集

アクセス制御
├── ユーザー・権限一覧
└── ユーザー権限編集

共通
├── Access Denied
└── Not Found
```

# 10. 社員スキル管理

## 10.1 EMP-SKILL-001 社員スキル編集

### Route

```text
/employees/[employeeId]/skills
```

### 目的

対象社員の保有スキル・経験情報を登録・変更する。

### 対象ユーザー

社員スキルを更新可能な権限を持つユーザー。

### 主な表示内容

- 対象社員
- 登録済みスキル
- スキル
- スキルレベル
- 実務経験有無
- 経験期間
- 最終利用時期

### 主な操作

- 社員スキル追加
- 社員スキル更新
- 社員スキル削除
- キャンセル

### 入力ルール

既存仕様に従い、以下を考慮する。

- Skill LevelはLevel 1〜5
- 未経験の場合はLevel 1のみ
- 実務経験ありの場合は経験期間1か月以上
- 実務経験ありの場合は最終利用時期必須
- 未経験の場合は最終利用時期を設定しない
- 同一社員・同一スキルの重複登録は許可しない

# 13. Navigation対象

認証後の主要Navigation候補は以下とする。

```text
Dashboard

Employee
└── 社員一覧

Skill
├── スキル一覧
└── スキルカテゴリ一覧

Administration
└── アクセス制御
```

登録・編集・詳細画面は原則としてSidebarへ直接配置せず、一覧・詳細等の親画面から遷移する。

Navigationに表示する項目はRole / Permissionに応じて制御する。

---

# 14. 画面として分離しない操作

MVPでは、以下の操作について必ずしも独立したRouteを持つ画面として分離しない。

- 削除確認
- 無効化確認
- 再有効化確認
- 単純なConfirmation
- Success Notification
- Error Notification

これらはDialog・Alert・Toast等の共通UIとして扱う。

ただし、操作が複雑化した場合は個別画面設計時に再検討する。
