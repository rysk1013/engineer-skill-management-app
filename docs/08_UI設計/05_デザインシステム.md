# デザインシステム

## 1. 目的

本ドキュメントは、Engineer Skill Management App のMVPにおけるDesign Systemを定義する。

Design Systemでは、Application全体で共通して利用する視覚表現・Design Token・状態表現の基準を定義し、画面やComponentごとの場当たり的なStylingを避ける。

主な対象は以下とする。

- Color
- Semantic Token
- Typography
- Spacing
- Border
- Radius
- Shadow
- Breakpoint
- Icon
- Focus
- UI State
- Theme
- Responsive Designとの関係

具体的なUI Componentについては `06_共通コンポーネント.md` で定義する。

---

## 2. 基本方針

Design Systemは以下の構成を前提とする。

```text
CSS Variables
      ↓
Design Token
      ↓
Tailwind CSS v4
      ↓
shadcn/ui
      ↓
Application Component
```

Design TokenはApplication全体で共通の意味を持つ値を中心に管理する。

すべてのCSS値をToken化すること自体を目的としない。

Design Tokenを追加する場合は以下を基準とする。

1. Application全体で共通の意味を持つか
2. 複数Componentで利用されるか
3. Theme変更時に一括変更する必要があるか
4. UIの一貫性維持に必要か

---

## 3. Stylingとの関係

FrontendのStylingにはTailwind CSS v4を利用する。

Design Systemでは、

```text
どのような意味の値を利用するか
```

を定義し、

```text
どのTailwind Utility Classを記述するか
```

までは固定しない。

具体的なClass実装はFrontend実装時に決定する。

Application全体で意味を持つStyle値を、個別Componentへ理由なく直接埋め込むことは避ける。

---

## 4. Color System

### 4.1 基本方針

Colorは具体的な色名ではなく、Semanticな意味を基本として管理する。

例えば、

```text
blue
red
gray
```

ではなく、

```text
primary
destructive
muted
```

のようにApplication上の役割で扱う。

---

### 4.2 基本Semantic Token

Color Tokenは少なくとも以下を基本候補とする。

```text
background
foreground

card
card-foreground

popover
popover-foreground

primary
primary-foreground

secondary
secondary-foreground

muted
muted-foreground

accent
accent-foreground

destructive
destructive-foreground

border
input
ring
```

shadcn/uiが利用するSemantic Token構造との整合性を優先する。

Application固有のColor Tokenが必要な場合は、既存Tokenで意味を表現できないか確認した上で追加する。

---

## 5. Semantic State

Application内の状態は、以下のSemantic Stateを基本とする。

- Default
- Primary
- Success
- Warning
- Error
- Disabled

---

### 5.1 Default

通常状態。

特別な意味を持たない情報・操作に利用する。

---

### 5.2 Primary

Application内で主要な操作・強調対象に利用する。

例:

- 保存
- 登録
- Primary Action
- 現在選択されている主要Navigation

Primaryを複数箇所へ過度に利用しない。

---

### 5.3 Success

操作成功や正常状態を表す。

例:

- 登録成功
- 更新成功
- 正常状態を明示する必要があるBadge

---

### 5.4 Warning

注意が必要だが、処理自体を禁止する状態ではない場合に利用する。

例:

- 注意事項
- 影響がある操作の事前警告

WarningをErrorの代替として利用しない。

---

### 5.5 Error

Error、Validation Error、失敗状態等に利用する。

破壊的操作については、必要に応じて `destructive` として表現する。

---

### 5.6 Disabled

操作不可状態。

色だけでDisabledを表現せず、Interaction自体も無効化する。

Disabled状態を多用せず、利用できない操作を表示する必要がない場合は非表示も検討する。

---

## 6. Color表現のルール

状態をColorだけで伝えない。

必要に応じて以下を組み合わせる。

```text
Color
  +
Icon
  +
Text
```

例:

```text
[!] 入力内容を確認してください
```

ErrorやStatusを色だけで区別する設計は避ける。

ForegroundとBackgroundのContrastを考慮し、Theme変更によって可読性が大きく低下しない構成とする。

---

## 7. Typography

### 7.1 基本方針

Typographyは、装飾性よりも業務Applicationとしての可読性・情報階層を優先する。

利用者が以下を容易に識別できる構成とする。

- Page Title
- Section Title
- Body
- Label
- Supporting Text
- Table Text
- Error Text

---

### 7.2 Typography階層

基本的な役割は以下とする。

```text
Page Title
    ↓
Section Title
    ↓
Subsection Title
    ↓
Body
    ↓
Supporting Text
```

Heading Levelは見た目だけではなくHTMLのSemantic Structureも考慮する。

---

### 7.3 Page Title

Page Headerで利用する最上位Title。

1画面に複数のPage Titleを設けない。

---

### 7.4 Section Title

画面内の情報Groupを区切るために使用する。

例:

```text
基本情報

保有スキル

権限情報
```

---

### 7.5 Body

通常の説明文・情報表示に利用する。

長文よりも一覧性を重視し、不要に大きなFont Sizeを利用しない。

---

### 7.6 Supporting Text

以下の補足情報に利用する。

- Form説明
- 入力条件
- Secondary Information
- Timestamp
- 補助Label

Primaryな情報より視覚的重要度を下げるが、Contrast不足にならないようにする。

---

## 8. Font

MVPでは、Application専用の特殊なFontを前提としない。

Next.jsおよび既存Frontend方針と整合するFont構成を利用する。

日本語・英数字の双方で可読性を確保する。

Font Family・Weight等の具体値はFrontend実装時に定義する。

---

## 9. Spacing

### 9.1 基本方針

SpacingはTailwind CSSのSpacing Systemと整合する形で管理する。

画面・Componentごとに任意の値を増やさない。

---

### 9.2 Spacingの対象

主に以下で一貫したSpacingを利用する。

- Page Padding
- Section間
- HeadingとContent間
- Form Field間
- Button間
- IconとText間
- Table周辺
- Card内部

---

### 9.3 情報階層との関係

情報の関連性が高い要素ほど近く、異なるGroupほど大きなSpacingを利用する。

例:

```text
Section Title
  ↓ 小さいSpacing
Section Content


次のSection
  ↑ 大きいSpacing
```

Spacingを単なる見た目調整として使用せず、情報構造を表現する手段として利用する。

---

## 10. Layout Token

共通レイアウトで利用する以下の値は、Application全体で一貫して管理する。

- Page Content Width
- Page Horizontal Padding
- Header Height
- Sidebar Width
- Content Gap
- Section Gap

具体値はFrontend実装時に検証しながら決定する。

画面ごとに独自値を定義することは避ける。

---

## 11. Border

Borderは、情報の区切りが必要な場合に利用する。

主な利用対象:

- Input
- Table
- Card
- Dialog
- Separator
- Navigation
- Section区切り

すべてのContainerをBorderで囲む設計は避ける。

SpacingやBackgroundで十分に情報を区別できる場合はBorderを追加しない。

---

## 12. Radius

Border RadiusはDesign Tokenとして管理する。

shadcn/uiとの整合性を優先し、Componentごとに異なるRadiusを理由なく設定しない。

Radiusは主に以下へ適用する。

- Button
- Input
- Card
- Dialog
- Badge
- Popover

Application全体で一貫した視覚表現を維持する。

---

## 13. Shadow

Shadowは階層・Overlayを表現するために必要な場合のみ利用する。

主な対象:

- Dialog
- Dropdown
- Popover
- Floating UI

通常のPage ContentやTableへ過剰なShadowを利用しない。

情報階層をShadowだけへ依存させない。

---

## 14. Breakpoint

### 14.1 基本方針

Responsive DesignのBreakpointは、Tailwind CSS v4の既存Breakpointを基本候補とする。

Phase 1ではApplication独自のBreakpoint値を固定しない。

Application固有のBreakpointが必要になった場合は、共通レイアウト・各画面のContent量・操作性を基準として必要性を判断し、Design Systemとして一貫して管理する。

---

### 14.2 UI設計上の分類

UI設計では以下の3分類を利用する。

```text
Desktop
Tablet
Mobile
```

ただし、

```text
Desktop = 特定の1つのBreakpoint
```

のような単純な対応付けを前提としない。

Desktop / Tablet / MobileはUI設計上の概念的な分類とし、実際のBreakpointとの対応はLayoutが成立する範囲を基準にFrontend実装時に判断する。

---

### 14.3 Responsiveの考え方

Desktop Firstで設計するが、Frontend実装ではTailwind CSS v4のResponsive Utilityに適した構成を採用する。

具体的なResponsive方針は `09_レスポンシブ設計.md` を正とする。

---

## 15. Icon

### 15.1 採用

IconにはLucide / `lucide-react` を利用する。

複数のIcon Libraryを理由なく併用しない。

---

### 15.2 用途

Iconは主に以下で利用する。

- Navigation
- Action
- Status補助
- Menu
- Search
- Filter
- Warning / Error等の補助

---

### 15.3 Icon + Text

意味のある操作では、可能な限りTextと併用する。

例:

```text
[+] 社員登録

[✎] 編集

[Search] 検索
```

Iconだけで意味が十分伝わらない操作では、Icon-only UIを避ける。

---

### 15.4 Icon-only Action

Iconのみを使用する場合はAccessible Nameを提供する。

例:

```text
aria-label="検索条件をクリア"
```

Tooltipが有効な場合でも、TooltipだけをAccessible Nameの代替にしない。

---

## 16. Focus

### 16.1 基本方針

Keyboard利用時に現在Focusしている要素を明確に識別できる状態とする。

Focus Ringを理由なく削除しない。

---

### 16.2 Focus Token

Focus表示は `ring` 等のSemantic Tokenを利用する。

Componentごとに異なるFocus表現を作らない。

---

### 16.3 Focus対象

主に以下を確認する。

- Button
- Link
- Input
- Select
- Checkbox
- Menu
- Dialog
- Pagination
- Navigation Item

---

## 17. Interactive State

操作可能なComponentでは必要に応じて以下の状態を持つ。

- Default
- Hover
- Focus
- Active
- Disabled

Form Componentでは加えて以下を考慮する。

- Invalid
- Readonly

状態ごとのStylingはComponentごとに無秩序に定義せず、Semantic Tokenおよびshadcn/uiの構造を利用する。

---

## 18. Form State

Form Fieldでは以下を視覚的・Semanticに区別できるようにする。

```text
Default
Focus
Disabled
Readonly
Invalid
```

Validation Errorでは、

```text
Field
  +
Error Message
```

の関係が分かるようにする。

Placeholderのみで状態や入力条件を伝えない。

---

## 19. Data Display State

一覧やDetailではStatusをBadge等で表現する場合がある。

例:

- 在籍
- 退職
- 有効
- 無効

Status表現については以下を基本とする。

- Textを表示する
- Colorだけに依存しない
- 同じStatusはApplication全体で同じ表現を使う
- Domain上の異なる状態を同じLabelにまとめない

具体的なBadge Variantは `06_共通コンポーネント.md` で定義する。

---

## 20. Primary / Secondary Action

### 20.1 Primary Action

画面で最も重要な操作はPrimary Actionとして表現する。

例:

- 登録
- 保存
- 作成

同一画面にPrimary Actionを複数並べすぎない。

---

### 20.2 Secondary Action

補助操作はSecondaryな視覚表現とする。

例:

- キャンセル
- 戻る
- Filter
- 詳細補助操作

---

### 20.3 Destructive Action

破壊的または影響の大きい操作はDestructiveとして区別する。

例:

- 無効化
- 削除
- 重要な権限変更

ただしDomain上「無効化」である操作をUI上で「削除」と表現しない。

---

## 21. Theme

### 21.1 基本構成

Themeは以下で管理する。

```text
Tailwind CSS v4
      +
CSS Variables
```

Theme管理専用LibraryはMVPでは導入しない。

---

### 21.2 Theme Token

Theme変更によってComponent側のClassを大量に分岐させない。

以下の構造を基本とする。

```text
Component
    ↓
Semantic Token
    ↓
ThemeごとのActual Value
```

---

## 22. Light Mode

MVPの基本UIはLight Modeを基準として設計する。

Desktop業務Applicationとして、長時間利用時でも情報を読み取りやすい構成を優先する。

具体Colorは実装時にshadcn/uiのToken構造と合わせて決定する。

---

## 23. Dark Mode

Dark Modeへ対応可能なToken構造とする。

ただし、

```text
Dark Modeへ対応可能
```

と、

```text
MVPでDark Mode切り替え機能を提供する
```

ことは分離する。

Phase 1では、Dark Mode対応可能なDesign Token構造までを設計対象とする。

Dark Mode切り替え機能そのものは、MVPの必須要件とはしない。

必要性が明確になった場合に別途追加する。

---

## 24. shadcn/uiとの統合

### 24.1 基本方針

shadcn/ui ComponentはApplicationのDesign Tokenを利用する。

```text
Design Token
     ↓
Tailwind CSS
     ↓
shadcn/ui
     ↓
Application UI
```

shadcn/uiから導入したComponentごとに独自のColor SystemやSpacing Systemを作らない。

---

### 24.2 Component Customization

shadcn/ui Componentの変更が必要な場合は以下を優先する。

1. Design Token
2. Variant
3. Application共通Component
4. Tailwind CSSによる調整

Componentごとの場当たり的なStyle変更を避ける。

---

## 25. Base UIとの関係

Primitive / Headless UIにはshadcn/uiが利用するBase UIを使用する。

Design SystemではBase UI固有の見た目を定義せず、Application側のDesign Tokenによって見た目を管理する。

Base UIのAccessibility機能を損なうようなStylingや構造変更を避ける。

---

## 26. cnとの関係

Class Name Compositionには `cn` を利用する。

Design Systemでは具体的なClass Composition方法は定義しないが、

```text
Design Token / Variant
        ↓
Class
        ↓
cn()
        ↓
Final className
```

という責務分離を前提とする。

---

## 27. Accessibility

Design Systemレベルでは以下を基本とする。

- Colorだけで情報を表現しない
- 十分なContrastを確保する
- Focusを視認可能にする
- Interactive Elementの状態を識別可能にする
- Disabled状態を視覚・操作の両方で表現する
- ErrorをTextでも伝える
- Icon-only ActionにはAccessible Nameを提供する
- Font Sizeを過度に小さくしない
- Hoverのみで利用可能な情報を作らない

Accessibilityの具体的なInteractionについては各Component・個別画面設計でも確認する。

---

## 28. Animation / Motion

MVPではAnimationをUIの中心要素としない。

利用する場合は、以下の目的に限定する。

- 状態変化の補助
- Menu / Dialog等の表示変化
- Navigationの理解補助

過度なAnimationや長時間のTransitionは避ける。

Animationがなくても操作・状態を理解できる設計とする。

Reduced Motionへの配慮が必要な場合はFrontend実装時に考慮する。

---

## 29. Loading表現

Loading状態の具体的なUIは `08_UI状態設計.md` で定義する。

Design Systemとしては、以下の方針とする。

- Page構造を必要以上に変化させない
- Loading状態を認識可能にする
- Spinnerだけに依存しない
- 必要に応じてSkeletonを利用する
- Accessible Statusを考慮する

---

## 30. Error表現

Errorは `destructive` 等のSemantic Tokenを基本として表現する。

ただしColorだけではなく、

- Error Text
- Icon
- Fieldとの関連付け

等を利用する。

Application全体でError表現を統一する。

---

## 31. Empty State

Empty Stateでは、空白だけを表示しない。

必要に応じて以下を表示する。

```text
状態を表すIcon
      +
Message
      +
次のAction
```

例:

```text
登録されている社員がありません。

[ 社員を登録 ]
```

具体的な共通Componentは `06_共通コンポーネント.md` で定義する。

---

## 32. Table

Table Stylingは一覧性を最優先する。

以下を基本とする。

- HeaderとData Rowを明確に区別する
- Row間の識別性を確保する
- 必要以上にBorderを増やさない
- Statusを一貫した表現で表示する
- Action Columnを他のDataと区別する
- Hoverを補助的に利用する
- Focus / Keyboard操作を阻害しない

具体的なTable Component設計は `06_共通コンポーネント.md` で定義する。

---

## 33. Form

Formでは以下を基本とする。

```text
Label

Input

Description

Error
```

必要な要素のみ表示する。

Form Field間のSpacingは一貫させる。

Required / Optionalの表現を画面ごとに変更しない。

具体的なInput・Select等のComponent設計は `06_共通コンポーネント.md` で定義する。

---

## 34. Design Systemで定義しないもの

本ドキュメントでは以下の詳細を固定しない。

- 個別画面の具体的なUI配置
- React Component構造
- Tailwind Utility Class
- CSS Variableの具体値
- Colorの具体的なHEX / RGB値
- Font Sizeの具体値
- Spacingの具体値
- Breakpointの具体値
- shadcn/ui ComponentのSource Code
- Component API

これらはFrontend実装または後続のUI設計ドキュメントで必要に応じて定義する。

---

## 35. Design Token構造

Design Tokenは概念上、以下のように整理する。

```text
Design Token
│
├── Color
│   ├── background
│   ├── foreground
│   ├── primary
│   ├── secondary
│   ├── muted
│   ├── accent
│   ├── destructive
│   ├── border
│   ├── input
│   └── ring
│
├── Typography
│   ├── Page Title
│   ├── Section Title
│   ├── Body
│   └── Supporting Text
│
├── Spacing
│   ├── Page
│   ├── Section
│   ├── Component
│   └── Inline
│
├── Radius
│
└── Shadow
```

BreakpointはTailwind CSS v4の既存Breakpointを基本候補とし、Application固有のBreakpointが必要になった場合のみDesign Systemとして一貫して管理する。

実際のCSS Variable名やTailwind CSS Theme設定はFrontend実装時に決定する。

---

## 36. 技術構成まとめ

Design Systemに関連するFrontend技術構成は以下とする。

```text
Next.js + React
       |
       v
Application UI
       |
       v
   shadcn/ui
       |
       v
     Base UI
       |
       v
Tailwind CSS v4
       |
       v
CSS Variables
       |
       v
Design Token

       +

Lucide / lucide-react
       |
       v
Icon

       +

      cn
       |
       v
Class Composition
```

新しいStyling System、UI Component Library、Primitive Library、Icon Libraryを理由なく追加しない。

---

## 37. 今後の設計との関係

本ドキュメントで定義したDesign Systemを基準として、後続ドキュメントで具体的なUIを定義する。

```text
05_デザインシステム
    ↓
06_共通コンポーネント
    ↓
07_画面設計
    ↓
08_UI状態設計
    ↓
09_レスポンシブ設計
```

後続設計で新しい共通Design Ruleが必要になった場合は、個別画面だけで定義せず、本ドキュメントへの反映を検討する。
