# ログイン

## 1. 目的

Engineer Skill Management App を利用するユーザーを認証し、認証後のApplicationへ遷移させる。

ログイン画面は未認証ユーザー向けの画面であり、認証後に利用するApp Shellは使用しない。

---

## 2. 対象ユーザー・権限

対象ユーザーは未認証ユーザーとする。

認証済みユーザーが `/login` へアクセスした場合は、ダッシュボードへ遷移する。

```text id="7j46ss"
/login
   |
   | 認証済み
   v
   /
```

---

## 3. Route

```text id="77kccf"
/login
```

Next.js App Router上のFrontend Routeとして管理する。

認証処理の具体的な実装はAuth.jsを利用する既存Frontend設計を正とする。

---

## 4. 画面構成

ログイン画面は、認証後画面のApp Shellとは分離した単独Layoutとする。

基本構造は以下とする。

```text id="d6b512"
+----------------------------------------------------------+
|                                                          |
|                                                          |
|                Application Name                          |
|                                                          |
|              +----------------------+                    |
|              | Login                |                    |
|              |                      |                    |
|              | Login Form           |                    |
|              |                      |                    |
|              | Login Action         |                    |
|              +----------------------+                    |
|                                                          |
|                                                          |
+----------------------------------------------------------+
```

Desktopでは、Formを画面中央付近へ配置する。

画面全体へ過度な装飾や複雑なVisualを追加せず、ログイン操作へ集中できる構成とする。

---

## 5. 表示項目

基本的に以下を表示する。

- Application Name
- Login Form
- Login Button
- Validation Error
- Authentication Error

必要に応じてApplicationの簡単な説明を表示してよいが、MVPでは必須としない。

---

## 6. Login Form

Login Formでは、既存の認証仕様で必要となる認証情報を入力する。

具体的な入力項目はAuth.jsおよび既存認証仕様を正とする。

UI設計側で認証方式や認証項目を新たに追加しない。

Formの基本構造は以下とする。

```text id="me194a"
Login Form
├── Field
├── Field
├── Authentication Error
└── Login Button
```

各Fieldは `06_共通コンポーネント.md` で定義したForm方針に従う。

---

## 7. 操作

### 7.1 ログイン

Login Buttonを選択すると認証処理を実行する。

認証成功時:

```text id="u3ou9s"
/login
   |
   | Login成功
   v
   /
```

ダッシュボードへ遷移する。

---

### 7.2 認証失敗

認証に失敗した場合は画面遷移しない。

```text id="sa8b4v"
/login
   |
   | Login失敗
   v
/login
+ Error表示
```

入力内容を可能な範囲で維持する。

---

### 7.3 二重送信防止

認証処理中はLogin Actionの二重実行を防止する。

処理中であることをユーザーが認識できる状態とする。

## 10. UI状態

### 10.1 Default

Login Formを通常表示する。

---

### 10.2 Loading

認証処理中は以下を基本とする。

- Login Buttonを再実行できない状態にする
- 認証処理中であることを表示する
- Form全体を必要以上に非表示へ変更しない

例:

```text id="ms7gnn"
[ ログイン中... ]
```

具体的なLoading表現は `08_UI状態設計.md` で統一する。

---

### 10.3 Validation Error

入力値にValidation Errorがある場合は対象Field付近へError Messageを表示する。

```text id="g10t7i"
Label
[ Input ]
Error Message
```

画面上部のErrorだけで対象Fieldが分からない構成を避ける。

---

### 10.4 Authentication Error

認証情報が正しくない等、Field単位ではなく認証処理全体として扱うErrorはForm内で表示する。

例:

```text id="z1zl5k"
ログインできませんでした。
入力内容を確認してください。
```

具体的な文言はSecurity要件も考慮して決定する。

認証Errorからユーザー情報の存在有無等を必要以上に推測できる表現は避ける。

---

### 10.5 Unexpected Error

予期しないErrorが発生した場合も、可能な限りログイン画面を維持する。

再試行可能な状態を基本とする。

---

## 11. Responsive

### 11.1 Desktop

Form Containerを画面中央付近へ配置する。

Formの横幅を画面いっぱいに広げず、入力しやすい適切な幅を使用する。

---

### 11.2 Tablet

Desktopと同じ情報構造を維持する。

画面幅に応じて左右の余白を縮小する。

---

### 11.3 Mobile

1 Column構成とする。

```text id="zg68nm"
Application Name

Login Form

Login Button
```

画面左右に適切なPaddingを確保し、Form Controlが操作しづらい幅にならないようにする。

Login Buttonは十分な操作領域を確保する。

---

## 12. Accessibility

以下を基本とする。

- 各Inputに適切なLabelを設定する
- PlaceholderのみをLabelの代替としない
- KeyboardのみでForm操作・Login実行が可能
- Focus状態を視認可能にする
- Validation Errorと対象Fieldの関係をSemanticに表現する
- Authentication ErrorをTextで通知する
- Loading状態をVisualだけへ依存させない
- Buttonに明確なAccessible Nameを提供する

Login Formの入力順とTab Orderが自然になる構成とする。

---

## 13. Security

Login画面では認証情報を扱うため、既存の認証・Security設計を正とする。

UIでは以下を基本とする。

- 認証失敗時に不要な内部情報を表示しない
- Backend / Auth.jsから返された技術的なError内容をそのまま表示しない
- 認証処理中の二重送信を防止する
- Password等の機密入力が存在する場合は適切なInput Typeを使用する
- Browser標準のPassword Manager等を不必要に阻害しない

具体的な認証Security要件は既存仕様を正とする。
