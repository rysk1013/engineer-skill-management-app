# スキルカテゴリ編集

## 1. 目的

スキルカテゴリ一覧から、既存Skill Category Masterの情報を編集するDialogとする。

本機能は独立画面ではなく、`/skill-categories` 上の `SkillCategoryEditDialog` として扱う。

Category Name等の更新可能項目を編集し、更新成功後はスキルカテゴリ一覧へ反映する。

---

## 2. 対象ユーザー・権限

対象ユーザーは、Skill Category Masterの更新権限を持つ認証済みユーザーとする。

更新権限がないユーザーには、スキルカテゴリ一覧上の編集Actionを表示しないことを基本とする。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. UI種別

本機能は独立画面ではなくDialogとして扱う。

```text
/skill-categories
        |
        | 編集
        v
SkillCategoryEditDialog
```

独立したFrontend Routeは持たない。

以下のRouteは設けない。

```text
/skill-categories/[categoryId]/edit
```

---

## 4. 起点

SkillCategoryEditDialogはスキルカテゴリ一覧からのみ開くことを基本とする。

起点:

```text
/skill-categories
```

一覧上で編集対象Categoryを指定してDialogを開く。

他画面から直接SkillCategoryEditDialogを開く導線は設けない。

---

## 5. 背景Context

Dialog表示中もスキルカテゴリ一覧のContextを維持する。

以下は変更しない。

- Current Route
- App Shell
- Header
- Sidebar
- Breadcrumb
- Page Header
- 検索条件
- Pagination状態
- Skill Category一覧

Current Routeは以下のままとする。

```text
/skill-categories
```

---

## 6. Breadcrumb

Dialogは独立Routeを持たないため、Breadcrumbを変更しない。

```text
Skill Categories
```

現在実行中の編集操作はDialog Titleで表現する。

---

## 7. Dialog構成

基本構造は以下とする。

```text
SkillCategoryEditDialog
├── Dialog Header
│   ├── Title
│   └── Description
│
├── Dialog Content
│   └── Skill Category Form
│
└── Dialog Footer
    ├── Cancel
    └── Save
```

shadcn/uiの `Dialog` を基本候補とする。

---

## 8. Dialog Header

### 8.1 Title

```text
スキルカテゴリ編集
```

とする。

### 8.2 Description

必要に応じて編集対象Categoryを識別できる補足を表示する。

例:

```text
Frameworkのスキルカテゴリ情報を編集します。
```

Descriptionは必須としない。

---

## 9. 初期データ

Dialogを開く際は、スキルカテゴリ一覧ですでに取得済みのCategory情報を初期値として利用できる場合は再利用することを基本とする。

追加Data取得が必要な場合のみ、Dialog表示後に取得する。

```text
Skill Category List Data
          ↓
SkillCategoryEditDialog
          ↓
Form Initial Values
```

不要な再取得を前提としない。

ただし、更新時点の最新性を保証する必要がある場合は既存Frontend実装方針に従う。

---

## 10. 編集対象

Skill Category Masterで更新可能と定義されている項目を編集対象とする。

MVPでは以下を扱う。

```text
Category Name
```

具体的な更新可能項目は既存Skill Category Domain・API仕様を正とする。

UI設計側で更新可能項目を追加しない。

---

## 11. Category Name

現在のCategory Nameを初期値として表示する。

例:

```text
カテゴリ名
[ Framework ]
```

入力Componentは `Input` を基本とする。

文字数・文字種・重複制約は既存Skill Category Domain・API仕様を正とする。

---

## 12. Form構造

基本構造は以下とする。

```text
Skill Category Form
│
├── Category Name
│
└── Actions
    ├── Cancel
    └── Save
```

入力項目が少ないため1 Columnを基本とする。

---

## 13. Form Field

各Fieldは以下の構造を基本とする。

```text
Label
Input
Description
Error Message
```

必要な要素のみ表示する。

PlaceholderのみをLabelの代替として利用しない。

---

## 14. 重複

Category Nameの重複可否は既存Skill Category Domain・Database Constraint・API仕様を正とする。

Frontendでも早期にFeedbackを提供できる範囲で補助してよいが、最終判定はBackendを正とする。

UI側だけで独自の重複判定Ruleを追加しない。

---

## 15. Validation

Validation RuleはBackend / Domain仕様を正とする。

Frontendでは入力ミスを早期に通知する補助Validationを行ってよいが、Backend Validationを代替しない。

主なRule:

- Category Name必須
- Category Nameの文字数
- Category Nameの重複制約

実際のRuleは既存仕様を正とする。

---

## 16. Validation Error

Validation Errorは対象Field付近へ表示する。

例:

```text
カテゴリ名
[                    ]

カテゴリ名を入力してください。
```

Validation Error発生時はDialogを閉じない。

入力内容を維持する。

---

## 17. 重複Error

Backendから重複Errorが返された場合は、対象Fieldとの関係が分かるFeedbackを表示する。

例:

```text
カテゴリ名
[ Framework ]

同じ名前のスキルカテゴリがすでに登録されています。
```

Backend内部のError Messageをそのまま表示しない。

---

## 18. Dialog全体Error

Field単位で表現できないErrorはDialog内のForm全体Errorとして表示する。

例:

```text
スキルカテゴリを更新できませんでした。
入力内容を確認してもう一度実行してください。
```

Error発生時はDialogを閉じない。

---

## 19. 保存Action

Primary Actionは以下を基本とする。

```text
保存
```

Application全体でより具体的なLabelを採用する場合は、

```text
変更を保存
```

としてよい。

最終Labelは他の編集Dialog・編集画面と統一する。

---

## 20. 更新処理

保存Action実行時はLaravel Backend APIへSkill Category更新Requestを送信する。

概念上:

```text
SkillCategoryEditDialog
          |
          | Update Skill Category
          v
Backend API
```

具体的なEndpoint・HTTP Method・Request Bodyは既存Skill Category API仕様を正とする。

---

## 21. 二重送信防止

更新処理中はPrimary Actionを再実行できない状態にする。

例:

```text
[ キャンセル ] [ 保存中... ]
```

処理中であることをVisualだけに依存せず認識可能にする。

---

## 22. 更新成功

更新成功後はDialogを閉じ、スキルカテゴリ一覧を最新状態へ更新する。

```text
/skill-categories
        |
        | SkillCategoryEditDialog
        | 更新成功
        v
/skill-categories
```

Route変更は発生しない。

対象Categoryの最新情報を一覧へ反映する。

---

## 23. 検索との関係

検索を提供している場合、更新成功後も現在の検索条件を維持することを基本とする。

Category Nameの変更によって対象Categoryが現在の検索条件から外れる場合は、更新後に一覧から見えなくなる可能性がある。

Success Feedbackを表示し、更新失敗と誤認されないようにする。

UI都合で検索条件を自動Resetしないことを基本とする。

---

## 24. Paginationとの関係

Paginationを利用している場合、更新成功後も現在のPagination Contextを維持することを基本とする。

更新によってSort順等が変化し、対象Categoryの表示位置が変わる場合は一覧APIの結果を正とする。

UI側で対象Categoryを現在Pageへ強制的に残さない。

---

## 25. Success Feedback

更新成功後、利用者が成功を認識できるFeedbackを提供してよい。

例:

```text
スキルカテゴリを更新しました。
```

具体的なNotification方式は共通UI・UI状態設計に従う。

---

## 26. キャンセル

Cancel ActionではDialogを閉じる。

```text
/skill-categories
        |
        | SkillCategoryEditDialog
        | Cancel
        v
/skill-categories
```

Route変更は発生しない。

未保存の変更は破棄する。

---

## 27. Close操作

Dialog HeaderにClose Buttonを設ける場合は、Cancelと同じ意味として扱うことを基本とする。

Escape KeyまたはBackdrop ClickによるCloseを許可するかは、未保存入力の扱いと合わせて決定する。

MVPでは複雑なUnsaved Changes Guardを必須としない。

---

## 28. Dialog Footer

Dialog FooterへActionを配置する。

基本形:

```text
[ キャンセル ] [ 保存 ]
```

Primary ActionとCancelの順序は他のDialogと統一する。

---

## 29. Skillとの関係

Skill Categoryの名称変更によって、Categoryを参照するSkillの表示上の分類名が変化する可能性がある。

```text
Skill Category
    ↓
複数のSkillから参照
```

Skill Category一覧・編集DialogからSkill Master自体を編集しない。

---

## 30. 利用中Category

Skillから参照されているCategoryの編集可否は既存Skill Category Domain・API仕様を正とする。

Backend側に制約が存在する場合は、その結果を利用者が理解できるFeedbackとして表示する。

例:

```text
このスキルカテゴリは現在利用されているため変更できません。
```

実際に変更禁止となるかどうかは既存仕様を正とする。

UI側だけで編集可否Ruleを追加しない。

---

## 31. Resource Not Found

更新対象Skill Categoryが存在しない場合はBackendの結果を正とする。

更新時にNot Foundが返された場合は、Dialogを閉じ、一覧を最新化することを候補とする。

必要に応じて以下のFeedbackを提供する。

```text
対象のスキルカテゴリが見つかりませんでした。
一覧を更新しました。
```

具体的なError変換方針は `08_UI状態設計.md` を正とする。

---

## 32. Concurrent Update

同じSkill Categoryが別操作によって更新されていた場合の競合処理が既存仕様に存在する場合は、その仕様に従う。

UI側で独自の楽観Lock・競合Ruleを追加しない。

Backendから競合Errorが返された場合は、利用者が次の操作を理解できるFeedbackを提供する。

---

### 33.1 shadcn/ui Component

### 33.2 Application共通Component

利用候補:

```text
SkillCategoryEditDialog
```

## 34. Feature固有Component

概念上:

```text
SkillCategoryEditDialog
└── SkillCategoryEditForm
```

とする。

DialogとFormは異なる責務として扱ってよい。

具体的なReact Component分割はFrontend実装設計で決定する。

Phase 1では責務のみ定義する。

## 35. UI状態

### 35.1 Default

現在のSkill Category情報を初期値としてFormへ表示する。

---

### 35.2 Submit Loading

更新Request実行中は以下を基本とする。

- Save Actionを再実行不可にする
- 入力内容を維持する
- 処理中であることを表示する
- Dialogを閉じない

---

### 35.3 Validation Error

対象Field付近へErrorを表示する。

Dialogを閉じない。

---

### 35.4 API Error

予期しないAPI Errorの場合もDialogを閉じない。

入力内容を維持し、再試行可能な状態とする。

---

### 35.5 Resource Not Found

対象Skill Categoryが存在しない。

一覧の最新化および適切なFeedbackを行う。

---

### 35.6 Access Denied

編集権限がないユーザーには編集Actionを表示しないことを基本とする。

更新Request時の最終認可はBackendを正とする。

---

## 36. Responsive

### 36.1 Desktop

Desktopでは中央配置のDialogを基本とする。

入力項目が少ないため、過度に大きなDialogにしない。

Formは1 Columnとする。

---

### 36.2 Tablet

Viewport内に収まるDialog幅を利用する。

Label・Description・Error Messageの可読性を維持する。

---

### 36.3 Mobile

Mobileでも操作の意味としてはSkillCategoryEditDialogとして扱う。

Desktopの固定幅Dialogを単純に縮小しない。

以下を候補とする。

- Viewport幅を広く利用するDialog
- Full-screenに近いDialog
- Sheet / Drawer

具体方式は `09_レスポンシブ設計.md` を正とする。

Formは1 Columnとする。

---

## 37. Mobile Action

MobileではFooter Actionを縦配置してよい。

例:

```text
[ 保存             ]
[ キャンセル       ]
```

Primary Actionを識別しやすい構成を維持する。

---

## 38. Accessibility

以下を基本とする。

- Dialog Titleを支援技術から認識可能にする
- 編集対象Skill Categoryを識別可能にする
- Dialog起動時に適切な要素へFocusを移動する
- Dialog表示中は背景へFocusを移動させない
- Dialog Close後は起動元の編集ActionへFocusを戻す
- Form Controlに適切なLabelを設定する
- PlaceholderのみをLabelとして利用しない
- Validation Errorと対象Fieldを関連付ける
- Keyboardのみで入力・保存・キャンセルを操作可能にする
- Focus状態を視認可能にする
- Loading状態をVisualだけで表現しない
- Error MessageをTextで表示する

## 41. MVPで扱わないもの

現時点では以下をSkillCategoryEditDialogの必須機能としない。

- Skill Categoryの削除
- Skill Categoryの無効化・再有効化
- SkillのInline登録
- SkillのInline編集
- Bulk Edit
- Category Icon編集
- Category Color編集
- Display Order編集
- Auto Save
- Draft保存
- 高度なConcurrent Editing UI
- DialogのURL同期

必要性が明確になった場合に別途検討する。

---

## 42. APIとの関係

Skill Category更新項目・Validation Rule・重複制約・更新可能項目は既存Skill Category API仕様を正とする。

MVPの編集UIではCategory Name等の通常情報の更新を扱い、Skill Categoryの状態変更操作は扱わない。

Skillとの参照関係による制約についても既存Domain・API仕様を正とする。

UI設計上必要な操作が既存APIと一致しない場合は、UI側だけで仕様を追加せず、システム設計との整合を確認する。

---

## 43. 本Dialogで定義しないもの

以下は既存仕様またはFrontend実装の責務とする。

- Skill Category API Endpoint
- Update RequestのHTTP Method
- Request Bodyの具体型
- Form Library
- State管理方式
- Server / Client Component境界
- React Component分割
- API Client実装
- Query Cache更新方式
- Dialog Stateの具体実装
- Tailwind CSS Class
- Design Tokenの具体値
- Database Constraint実装
- Concurrent Update実装
