# 社員登録

## 1. 目的

新しい社員情報を登録する画面とする。

社員登録に必要な情報を入力し、登録成功後は作成された社員の詳細画面へ遷移する。

---

## 2. 対象ユーザー・権限

対象ユーザーは、社員登録権限を持つ認証済みユーザーとする。

社員登録権限がないユーザーには、本画面への導線を表示しないことを基本とする。

直接Routeへアクセスした場合は、既存のAccess Denied方針に従う。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. Route

```text
/employees/create
```

Next.js App Router上のFrontend Routeとして管理する。

社員登録処理はLaravel Backend APIへ `POST` Requestを送信して実行する。

---

## 4. 画面構成

基本構造は以下とする。

```text
App Shell
├── Breadcrumb
├── Page Header
│   └── Title
└── Employee Form
    ├── Employee Basic Information
    └── Form Actions
```

社員スキルは社員登録と同時に入力せず、社員作成後に社員詳細・社員スキル編集画面から登録することを基本とする。

これにより、EmployeeとEmployeeSkillの責務を分離する。

---

## 5. Breadcrumb

基本構造は以下とする。

```text
Employees > 登録
```

`Employees` は `/employees` へのLinkとする。

現在ページの `登録` はLinkにしない。

---

## 6. Page Header

### 6.1 Title

```text
社員登録
```

とする。

### 6.2 Description

必要に応じて以下のような補足を表示する。

```text
社員の基本情報を入力してください。
```

Descriptionは必須としない。

---

## 7. Form対象

社員登録Formでは、Employee Domainで定義された登録可能な基本情報を対象とする。

具体的な項目・必須条件・Validation Ruleは以下を正とする。

- 要件定義
- Employee Domain設計
- Employee API仕様

UI設計側で新しいEmployee属性を追加しない。

---

## 8. MVPで扱わないEmployee情報

既存MVP要件に含まれない情報は社員登録Formへ追加しない。

例:

- 役職
- チーム
- 入社年月
- メールアドレス
- プロフィール画像
- ソフトスキル
- 資格

将来必要になる可能性だけを理由としてFieldを追加しない。

---

## 9. Form構造

基本構造は以下とする。

```text
Employee Form
│
├── Basic Information
│   ├── Field
│   ├── Field
│   └── ...
│
└── Actions
    ├── Cancel
    └── Register
```

Fieldの具体的な並び順は、入力頻度・関連性・必須条件を考慮して決定する。

---

## 10. Form Field

各Fieldは以下の構造を基本とする。

```text
Label
Input / Select
Description
Error Message
```

必要な要素のみ表示する。

PlaceholderのみをLabelの代替として利用しない。

---

## 11. 必須・任意

必須項目と任意項目を利用者が判別できるようにする。

具体的な表現はApplication全体で統一する。

例:

```text
氏名 *
```

または、

```text
氏名
必須
```

のような表現を候補とする。

画面ごとに必須表現を変更しない。

---

## 12. 入力Component

入力項目の種類に応じて以下を利用する。

### Text

```text
Input
```

を基本とする。

### 選択値

```text
Select
```

または選択肢数に応じて `Radio Group` を利用する。

### Boolean

```text
Checkbox
```

等を利用する。

具体的なComponentはFieldの意味に応じて決定する。

---

## 13. 所属

所属情報は既存Department仕様に従って入力する。

既存Departmentから選択する形式を基本とする。

UI側で自由入力による新しいDepartment作成を同時に行わせない。

Department追加・管理の既存仕様がある場合は、その仕様を正とする。

---

## 14. 在籍状態

社員登録時のEmployment Statusは既存Domain仕様を正とする。

新規社員登録時の初期状態がDomain側で固定されている場合は、ユーザーへ不要な選択を求めない。

登録時に選択可能な仕様である場合のみFieldとして表示する。

UI設計だけで初期値・選択可否を変更しない。

---

## 15. 社員スキル

社員スキルは本画面では登録しないことを基本とする。

登録フローは以下とする。

```text
社員登録
   ↓
Employee作成
   ↓
社員詳細
   ↓
社員スキル編集
```

これにより社員基本情報の登録とEmployeeSkill管理を分離する。

---

## 16. Validation

Validation RuleはBackend / Domain仕様を正とする。

Frontendでは利用者が入力ミスを早期に把握できる範囲でValidationを行ってよいが、Backend Validationを代替しない。

UI独自のDomain Ruleを追加しない。

---

## 17. Validation Error

Validation Errorは対象Field付近へ表示する。

```text
氏名
[ Input ]

氏名を入力してください。
```

複数FieldでErrorが発生している場合でも、各FieldとErrorの関係が分かるようにする。

---

## 18. Form全体Error

Field単位では表現できないErrorはForm全体のErrorとして表示する。

例:

```text
社員を登録できませんでした。
入力内容を確認してもう一度実行してください。
```

技術的なBackend Error Messageをそのまま表示しない。

---

## 19. 登録Action

Primary Actionは、

```text
登録
```

とする。

またはApplication全体の用語に合わせて、

```text
社員を登録
```

とする。

最終Labelは他の登録画面と統一する。

---

## 20. 登録処理

登録Action実行時はLaravel Backend APIへ社員登録Requestを送信する。

```text
/employees/create
       |
       | POST Employee
       v
Backend API
```

処理中は二重送信を防止する。

---

## 21. 登録成功

登録成功後は、作成された社員の詳細画面へ遷移する。

```text
/employees/create
        |
        | 登録成功
        v
/employees/[employeeId]
```

新しく登録した社員情報を直ちに確認できる状態とする。

---

## 22. Success Feedback

社員詳細へ遷移後、登録成功をユーザーが認識できるFeedbackを提供してよい。

例:

```text
社員を登録しました。
```

具体的なNotification方式は共通UI・UI状態設計に従う。

---

## 23. キャンセル

Cancel Actionを提供する。

```text
/employees/create
        |
        | Cancel
        v
/employees
```

社員一覧へ戻る。

未保存入力が存在する場合の離脱確認については、MVPではすべてのFormへ一律導入しない。

必要性が個別に確認された場合に追加する。

---

## 24. Form Action配置

Form末尾にAction領域を配置することを基本とする。

例:

```text
[ キャンセル ] [ 登録 ]
```

Primary ActionとCancelの並び順はApplication全体で統一する。

画面ごとに順番を変更しない。

---

## 25. 二重送信防止

登録処理中はPrimary Actionを再実行できない状態にする。

例:

```text
[ 登録中... ]
```

またはLoading Indicatorを組み合わせる。

処理中であることをTextまたはAccessibleな状態として認識可能にする。

---

---

## 27. UI状態

### 27.1 Default

入力可能な社員登録Formを表示する。

---

### 27.2 Loading

Form画面自体の初期表示に外部Data取得が必要な場合は、該当部分をLoading状態とする。

例:

- Department一覧取得

Page全体を不要に単一Spinnerへ置き換えない。

---

### 27.3 Submit Loading

登録Request実行中は以下を基本とする。

- Register Actionを再実行不可にする
- 処理中であることを表示する
- 入力内容を維持する
- 不要に画面全体を操作不能にしない

---

### 27.4 Validation Error

対象Field付近へErrorを表示し、画面遷移しない。

入力内容を可能な限り維持する。

---

### 27.5 API Error

予期しないAPI Errorの場合は画面遷移せず、Form内容を維持する。

再試行可能な状態を基本とする。

---

### 27.6 Access Denied

登録権限がない場合は本画面を表示しない。

直接アクセス時はAccess Denied方針に従う。

---

## 28. Department取得Error

所属選択肢等のForm表示に必要なMaster Data取得に失敗した場合は、登録不能な状態であることを明示する。

例:

```text
所属情報を取得できませんでした。

[ 再試行 ]
```

必要なMaster Dataを取得できないまま登録操作を許可しない。

---

## 29. Responsive

### 29.1 Desktop

関連するFieldを複数Columnで配置可能とする。

例:

```text
+----------------------+----------------------+
| Field                | Field                |
+----------------------+----------------------+

+---------------------------------------------+
| Field                                       |
+---------------------------------------------+
```

ただし、単に横幅があることを理由に無理に複数Column化しない。

---

### 29.2 Tablet

画面幅に応じてColumn数を減らす。

Field Label・Description・Error Messageが窮屈にならないことを優先する。

---

### 29.3 Mobile

1 Columnを基本とする。

```text
社員登録

Label
[ Input ]

Label
[ Select ]

Label
[ Input ]

[ キャンセル ]
[ 登録 ]
```

Form Controlは利用可能な横幅を適切に使用する。

---

## 30. Mobile Action

MobileではButtonを横並びにすると操作しづらい場合がある。

その場合は縦配置を許可する。

例:

```text
[ 登録       ]
[ キャンセル ]
```

Primary Actionを識別しやすい構成を維持する。

最終ルールは `09_レスポンシブ設計.md` で統一する。

---

## 31. Accessibility

以下を基本とする。

- 各Form Controlに適切なLabelを設定する
- PlaceholderのみをLabelとして利用しない
- Required / Optionalを認識可能にする
- Validation Errorと対象Fieldを関連付ける
- Keyboardのみで全Fieldへ移動できる
- Keyboardで登録・キャンセルを実行できる
- Focus状態を視認可能にする
- Loading状態をVisualだけで表現しない
- Disabled状態をSemanticにも表現する
- Error MessageをTextで表示する

Validation Error発生時に、利用者がError Fieldへ到達しやすい構成を考慮する。

## 34. MVPで扱わないもの

現時点では以下を社員登録画面の必須機能としない。

- 社員スキル同時登録
- 複数社員一括登録
- CSV Import
- Draft保存
- Multi-Step Wizard
- Profile Image Upload
- Department新規作成のInline実行
- 登録後の自動権限設定
- Auto Save

必要性が明確になった場合に別途検討する。

---

## 35. APIとの関係

社員登録項目・Validation Rule・Request Bodyは既存Employee API仕様を正とする。

Form設計上必要な項目が既存APIと一致しない場合は、UI側だけで項目を追加せず、システム設計との整合を確認する。
