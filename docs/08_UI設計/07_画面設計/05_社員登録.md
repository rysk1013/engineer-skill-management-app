# 社員登録

## 1. 目的

社員一覧から、新しい社員の基本情報を登録するDialogとする。

社員登録に必要な情報を入力し、登録成功後は作成された社員の詳細画面へ遷移する。

EmployeeSkillは本Dialogでは扱わず、社員作成後に社員スキル編集画面で管理する。

---

## 2. 対象ユーザー・権限

対象ユーザーは、社員登録権限を持つ認証済みユーザーとする。

社員登録権限がないユーザーには、社員一覧上の社員登録Actionを表示しないことを基本とする。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. UI種別

本機能は独立画面ではなくDialogとして扱う。

```text id="8x8gpt"
/employees
社員一覧
   |
   | 社員登録
   v
社員登録Dialog
```

独立したFrontend Routeは持たない。

---

## 4. 起点

社員登録Dialogは社員一覧からのみ開くことを基本とする。

起点:

```text id="lkde9m"
/employees
```

社員一覧以外から社員登録Dialogを直接開く導線は設けない。

---

## 5. 背景Context

Dialog表示中も社員一覧のContextを維持する。

以下は変更しない。

- Current Route
- App Shell
- Header
- Sidebar
- Breadcrumb
- Page Header
- Navigation Active State
- 社員一覧

Current Routeは以下のままとする。

```text id="il5cnp"
/employees
```

---

## 6. Breadcrumb

Dialogは独立Routeを持たないため、Breadcrumbを変更しない。

```text id="pf4el2"
Employees
```

現在実行中の登録操作はDialog Titleで表現する。

---

## 8. Dialog Header

### 8.1 Title

```text id="ihfh65"
社員登録
```

とする。

### 8.2 Description

必要に応じて以下のような補足を表示する。

```text id="x6u6on"
社員の基本情報を入力してください。
```

Descriptionは必須としない。

---

## 9. Form対象

社員登録Formでは、Employee Domainで登録可能と定義された基本情報を対象とする。

具体的な項目・必須条件・Validation Ruleは以下を正とする。

- 要件定義
- Employee Domain設計
- Employee API仕様

UI設計側で新しいEmployee属性を追加しない。

---

## 10. MVPで扱わないEmployee情報

既存MVP要件に含まれない情報は社員登録Formへ追加しない。

例:

- 役職
- チーム
- 入社年月
- メールアドレス
- プロフィール画像
- ソフトスキル
- 資格

将来必要になる可能性だけを理由としてFieldを追加しない。

---

## 11. Form構造

基本構造は以下とする。

```text id="34kwwv"
Employee Form
│
├── Basic Information
│   ├── Field
│   ├── Field
│   └── ...
│
└── Actions
    ├── Cancel
    └── Register
```

Dialog内Formは1 Columnを基本とする。

Fieldの具体的な並び順は、入力頻度・関連性・必須条件を考慮して決定する。

---

## 12. Form Field

各Fieldは以下の構造を基本とする。

```text id="8hcq3p"
Label
Input / Select
Description
Error Message
```

必要な要素のみ表示する。

PlaceholderのみをLabelの代替として利用しない。

---

## 13. 必須・任意

必須項目と任意項目を利用者が判別できるようにする。

具体的な表現はApplication全体で統一する。

例:

```text id="xqdq8e"
氏名 *
```

または、

```text id="f3lknb"
氏名
必須
```

のような表現を候補とする。

画面・Dialogごとに必須表現を変更しない。

---

## 14. 入力Component

入力項目の種類に応じて以下を利用する。

### Text

```text id="xqgz64"
Input
```

を基本とする。

### 選択値

```text id="t25pk8"
Select
```

または選択肢数に応じて `Radio Group` を利用する。

### Boolean

```text id="mvyueh"
Checkbox
```

等を利用する。

具体的なComponentはFieldの意味に応じて決定する。

---

## 15. 所属

所属情報は既存Department仕様に従って入力する。

既存Departmentから選択する形式を基本とする。

UI側で自由入力による新しいDepartment作成を同時に行わせない。

Department追加・管理の既存仕様がある場合は、その仕様を正とする。

---

## 16. 在籍状態

社員登録時のEmployment Statusは既存Domain仕様を正とする。

新規社員登録時の初期状態がDomain側で固定されている場合は、ユーザーへ不要な選択を求めない。

登録時に選択可能な仕様である場合のみFieldとして表示する。

UI設計だけで初期値・選択可否を変更しない。

---

## 17. 社員スキル

EmployeeSkillは本Dialogでは登録しない。

登録フローは以下とする。

```text id="hkb6vq"
社員一覧
   |
   | 社員登録Dialog
   | 登録成功
   v
社員詳細
   |
   | 必要に応じて
   v
社員スキル編集
```

社員基本情報の登録とEmployeeSkill管理を分離する。

---

## 18. Validation

Validation RuleはBackend / Domain仕様を正とする。

Frontendでは利用者が入力ミスを早期に把握できる範囲でValidationを行ってよいが、Backend Validationを代替しない。

UI独自のDomain Ruleを追加しない。

---

## 19. Validation Error

Validation Errorは対象Field付近へ表示する。

例:

```text id="t4djrq"
氏名
[ Input ]

氏名を入力してください。
```

複数FieldでErrorが発生している場合でも、各FieldとErrorの関係が分かるようにする。

Validation Error発生時はDialogを閉じない。

入力内容を可能な限り維持する。

---

## 20. Dialog全体Error

Field単位では表現できないErrorはDialog内のForm全体Errorとして表示する。

例:

```text id="tr5ew8"
社員を登録できませんでした。
入力内容を確認してもう一度実行してください。
```

技術的なBackend Error Messageをそのまま表示しない。

Error発生時はDialogを閉じない。

---

## 21. 登録Action

Primary Actionは、

```text id="v3sxxb"
登録
```

を基本とする。

Application全体でより具体的なLabelを採用する場合は、

```text id="d7f219"
社員を登録
```

としてよい。

最終Labelは他の登録Dialogと統一する。

---

## 22. 登録処理

登録Action実行時はLaravel Backend APIへ社員登録Requestを送信する。

概念上は以下とする。

```text id="zras9c"
社員登録Dialog
      |
      | Create Employee
      v
Backend API
```

具体的なEndpoint・Request Bodyは既存API仕様を正とする。

---

## 23. 二重送信防止

登録処理中はPrimary Actionを再実行できない状態にする。

例:

```text id="atvd4k"
[ キャンセル ] [ 登録中... ]
```

またはLoading Indicatorを組み合わせる。

処理中であることをVisualだけに依存せず認識可能にする。

---

## 24. 登録成功

登録成功後はDialogを閉じ、作成された社員の詳細画面へ遷移する。

```text id="t5dj6f"
/employees
   |
   | 社員登録Dialog
   | 登録成功
   v
/employees/[employeeId]
```

新しく登録した社員情報を直ちに確認できる状態とする。

---

## 25. Success Feedback

登録成功後、利用者が成功を認識できるFeedbackを提供してよい。

例:

```text id="imfnab"
社員を登録しました。
```

具体的なNotification方式は共通UI・UI状態設計に従う。

---

## 26. キャンセル

Cancel ActionではDialogを閉じる。

```text id="y4fqfz"
/employees
   |
   | 社員登録Dialog
   | Cancel
   v
/employees
```

Route変更は発生しない。

入力中の値は破棄する。

---

## 27. Close操作

Dialog HeaderにClose Buttonを設ける場合は、Cancelと同じ意味として扱うことを基本とする。

Escape KeyまたはBackdrop ClickによるCloseを許可するかは、未保存入力の扱いと合わせて決定する。

MVPでは複雑なUnsaved Changes Guardを必須としない。

---

## 28. Dialog Footer

Dialog FooterへActionを配置する。

基本形:

```text id="vnt3xu"
[ キャンセル ] [ 登録 ]
```

Primary ActionとCancelの順序は他のDialogと統一する。

## 30. UI状態

### 30.1 Default

登録可能なFormをDialog内に表示する。

---

### 30.2 Initial Loading

Dialog表示に必要なMaster Data取得中の場合は、Dialog構造を維持したままContent部分をLoading状態とする。

例:

- Department一覧取得

必要なDataが取得できるまで登録Actionを実行できない状態とする。

---

### 30.3 Submit Loading

登録Request実行中は以下を基本とする。

- Register Actionを再実行不可にする
- 処理中であることを表示する
- 入力内容を維持する
- Dialogを閉じない

---

### 30.4 Validation Error

対象Field付近へErrorを表示する。

Dialogを閉じず、入力内容を維持する。

---

### 30.5 API Error

予期しないAPI Errorの場合もDialogを閉じない。

Form内容を維持し、再試行可能な状態を基本とする。

---

### 30.6 Access Denied

社員登録権限がないユーザーには、Dialogを開くActionを表示しないことを基本とする。

登録Request時の最終認可はBackendを正とする。

---

## 31. Master Data Error

所属選択肢等、登録に必要なMaster Data取得に失敗した場合は、Dialog内で登録不能な状態であることを明示する。

例:

```text id="in6ap8"
所属情報を取得できませんでした。

[ 再試行 ]
```

必要なMaster Dataを取得できないまま登録を許可しない。

---

## 32. Responsive

### 32.1 Desktop

Desktopでは中央配置のDialogを基本とする。

Dialog内Formは1 Columnを基本とし、必要性が明確な場合のみ関連Fieldを複数Columnで配置する。

Dialogを過度に横長にしない。

---

### 32.2 Tablet

Viewport内に収まるDialog幅を利用する。

Label・Description・Error Messageの可読性を優先する。

---

### 32.3 Mobile

Mobileでも操作の意味としては社員登録Dialogとして扱う。

ただし、Desktopの固定幅Modalを単純に縮小しない。

以下を候補とする。

- Viewport幅を広く利用するDialog
- Full-screenに近いDialog
- Sheet / Drawer

具体的な方式は `09_レスポンシブ設計.md` を正とする。

Formは1 Columnを基本とする。

---

## 33. Mobile Action

MobileではFooter Actionを縦配置してよい。

例:

```text id="a1un0c"
[ 登録             ]
[ キャンセル       ]
```

Primary Actionを識別しやすい構成を維持する。

---

## 34. Scroll

Dialog ContentがViewport Heightを超える場合はScroll可能とする。

HeaderやFooterを固定する場合は、Form Fieldが隠れないようにする。

---

## 35. Accessibility

以下を基本とする。

- Dialog Titleを支援技術から認識可能にする
- Dialog起動時に適切な要素へFocusを移動する
- Dialog表示中は背景へFocusを移動させない
- Dialog Close時は起動元ActionへFocusを戻す
- 各Form Controlに適切なLabelを設定する
- PlaceholderのみをLabelとして利用しない
- Required / Optionalを認識可能にする
- Validation Errorと対象Fieldを関連付ける
- Keyboardのみで全Fieldを操作可能にする
- Keyboardで登録・キャンセルを実行可能にする
- Focus状態を視認可能にする
- Loading状態をVisualだけで表現しない
- Disabled状態をSemanticにも表現する
- Error MessageをTextで表示する

## 38. MVPで扱わないもの

現時点では以下を社員登録Dialogの必須機能としない。

- EmployeeSkill同時登録
- 複数社員一括登録
- CSV Import
- Draft保存
- Multi-Step Wizard
- Profile Image Upload
- Department新規作成のInline実行
- 登録後の自動権限設定
- Auto Save
- DialogのURL同期

必要性が明確になった場合に別途検討する。

## 39. APIとの関係

社員登録項目・Validation Rule・Request Bodyは既存Employee API仕様を正とする。

Form設計上必要な項目が既存APIと一致しない場合は、UI側だけで項目を追加せず、システム設計との整合を確認する。
