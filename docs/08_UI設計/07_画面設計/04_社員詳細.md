# 社員詳細

## 1. 目的

対象社員の基本情報・在籍状態・所属情報・保有スキルを確認できる画面とする。

社員情報の確認を主目的とし、社員編集・社員スキル編集への入口を提供する。

---

## 2. 対象ユーザー・権限

対象ユーザーは、社員情報を閲覧可能な認証済みユーザーとする。

以下のActionはRole / Permissionに応じて表示を制御する。

- 社員編集
- 社員スキル編集

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. Route

```text
/employees/[employeeId]
```

`employeeId` は対象社員を識別するIDとする。

---

## 5. Breadcrumb

基本構造は以下とする。

```text
Employees > 社員名
```

`Employees` は `/employees` へのLinkとする。

## 6. Page Header

### 6.1 Title

対象社員を識別できる氏名を表示する。

例:

```text
山田 太郎
```

社員名が取得できない状態では、Loading / Error / Not Foundの状態設計に従う。

---

### 6.2 Primary Action

社員更新権限がある場合は、以下を表示する。

```text id="8mh5u4"
編集
```

実行時は社員詳細のContextを維持したまま、社員編集Dialogを開く。

```text id="yie3uc"
/employees/[employeeId]
    ↓
社員編集Dialog
```

Frontend Routeは `/employees/[employeeId]` のままとする。

権限がない場合は表示しないことを基本とする。

---

### 6.3 退職Action

対象社員が在籍中で、現在Userが退職処理を実行可能な場合は、退職Actionを表示する。

退職処理を実行可能なRoleは既存Employee API仕様を正とし、MVPでは以下とする。

```text
Administrator
Manager
```

例:

```text
[ 退職 ]
```

退職は通常の社員情報編集とは分離し、専用のDomain Operationとして扱う。

退職Action実行時は、退職日を入力し、実行内容を確認した上で退職処理を実行する。

```text
社員詳細
    ↓
退職Action
    ↓
退職日入力・確認
    ↓
POST /api/v1/employees/{employeeId}/retirement
```

退職処理ではFrontend Routeを変更せず、現在の社員詳細Context上で操作を完結させることを基本とする。

退職成功後は社員詳細を最新状態へ更新し、退職済みであることを表示する。

既に退職済みの社員には退職Actionを表示しない。

Frontend上の表示制御はUX上の制御であり、最終的な認可・Domain RuleはBackendを正とする。

---

## 7. Employee Information

社員の基本情報をSectionとして表示する。

基本候補は以下とする。

- 氏名
- 所属
- 在籍状態
- その他Employee Domainで定義されている基本情報

表示項目は既存Employee要件・API仕様を正とする。

UI設計側で新しいEmployee属性を追加しない。

---

## 8. 基本情報の表示形式

社員基本情報は、LabelとValueの組み合わせで表示することを基本とする。

例:

```text
所属
開発部

在籍状態
在籍
```

Desktopでは複数Columnを利用可能とする。

例:

```text
+----------------------+----------------------+
| 所属                 | 在籍状態             |
| 開発部               | 在籍                 |
+----------------------+----------------------+
```

Mobileでは1 Columnへ変更する。

---

## 9. 在籍状態

在籍状態は `StatusBadge` を利用することを基本とする。

例:

```text
在籍
退職
```

Domain上のEmployment Statusと表示Labelを対応させる。

色だけに依存せずTextを必ず表示する。

---

## 10. 退職社員

退職社員も保持期間中は詳細画面で確認できる前提とする。

退職社員では、在籍社員と区別できるように状態を明示する。

例:

```text
退職
```

退職社員に対して利用可能なActionは、既存のEmployee管理仕様・権限仕様を正とする。

UI設計側で在籍社員と同じ操作を無条件に許可しない。

---

## 11. Employee Skills

対象社員に登録されているスキル情報を表示する。

基本的に以下を表示する。

- スキル名
- スキルカテゴリ
- スキルレベル
- 実務経験有無
- 経験期間
- 最終利用時期

具体的な表示項目はEmployeeSkillの既存仕様・APIを正とする。

---

## 12. スキルレベル

Skill LevelはLevel 1〜5として表示する。

例:

```text
Level 1
Level 2
Level 3
Level 4
Level 5
```

単に数値のみを表示するか、`Level 3` のようにLabel付きで表示するかはApplication全体で統一する。

---

## 13. 実務経験

実務経験の有無を明示する。

例:

```text
あり
なし
```

Boolean値をIconやColorだけで表現しない。

---

## 14. 経験期間

実務経験ありの場合は、既存Domain仕様で管理する経験期間を表示する。

表示形式は既存API・Domain仕様と整合させる。

例:

```text
2年3か月
```

UI側で元データと異なる計算規則を独自に定義しない。

---

## 15. 最終利用時期

実務経験ありの場合は最終利用時期を表示する。

未経験の場合は、既存仕様に従い未設定とする。

未設定値を曖昧な空欄だけで表現せず、必要に応じて以下のような表示を利用する。

```text
-
```

または

```text
未設定
```

最終表記はApplication全体で統一する。

---

## 16. スキルカテゴリ

各スキルにカテゴリ情報が必要な場合は表示する。

一覧性を損なう場合は、スキル名の補助情報として表示することも可能とする。

例:

```text
Laravel
Framework
```

具体的な表示方式はDesktop / Mobileの情報量を踏まえて決定する。

---

## 17. Employee Skills Table

DesktopではTable形式を基本とする。

例:

```text
+--------------------------------------------------------------+
| スキル     | Level | 実務経験 | 経験期間 | 最終利用時期     |
+--------------------------------------------------------------+
| PHP        | L4    | あり     | 4年      | 2026-09          |
| Laravel    | L4    | あり     | 3年      | 2026-09          |
+--------------------------------------------------------------+
```

SemanticなHTML Tableを維持する。

---

## 18. スキル編集Action

社員スキル更新権限がある場合は、Employee Skills Sectionに以下を表示する。

```text
スキル編集
```

遷移先:

```text
/employees/[employeeId]/skills
```

社員編集Actionとは責務を分ける。

```text
社員編集
    ↓
社員基本情報

スキル編集
    ↓
EmployeeSkill
```

とする。

---

## 19. 社員一覧へ戻る

Breadcrumbの `Employees` から一覧へ戻れる構成とする。

必要に応じて明示的な戻るActionを追加してよいが、Navigationを重複させすぎない。

社員一覧へ戻る際は、可能な範囲で元のSearch / Filter / Pagination状態を維持する。

## 21. UI状態

### 21.1 Default

社員基本情報と保有スキルを通常表示する。

---

### 21.2 Loading

対象社員取得中はPage全体の構造を可能な限り維持する。

例:

```text
Employees > █████

████████                        [ ███ ]

基本情報
+--------------------------------------+
| █████████                            |
| █████████                            |
+--------------------------------------+

保有スキル
+--------------------------------------+
| ██████████████████████████████████ |
+--------------------------------------+
```

Skeleton等を利用する。

---

### 21.3 EmployeeSkill Loading

社員基本情報とEmployeeSkillを別に取得する場合は、基本情報表示後にスキルSectionのみLoading状態とすることを許可する。

ただし、MVPで不要な複雑な非同期構成は避ける。

---

### 21.4 EmployeeSkill Empty

社員は存在するがスキルが1件も登録されていない場合は、Empty Stateを表示する。

例:

```text
登録されているスキルがありません。
```

社員スキル更新権限がある場合は、

```text
[ スキルを登録 ]
```

または

```text
[ スキル編集 ]
```

のActionを表示してよい。

実際のLabelは社員スキル編集画面の操作設計と合わせて統一する。

---

### 21.5 Error

社員情報取得に失敗した場合は `ErrorState` を利用する。

例:

```text
社員情報を取得できませんでした。

[ 再試行 ]
```

Navigationは維持する。

---

### 21.6 Skill Error

社員基本情報は取得できたがEmployeeSkill取得に失敗した場合は、画面全体をErrorへ変更せず、Skill Section単位でError表示することを基本とする。

例:

```text
保有スキル

スキル情報を取得できませんでした。

[ 再試行 ]
```

---

### 21.7 Not Found

指定した `employeeId` に対応する社員が存在しない場合はNot Foundとして扱う。

```text
/employees/[employeeId]
        |
        | Employee Not Found
        v
     Not Found
```

## 22. 権限制御

### 22.1 閲覧

閲覧権限がない場合は本画面へアクセスさせない。

直接Routeへアクセスした場合はAccess Denied方針に従う。

---

### 22.2 社員編集

社員更新権限がない場合は `編集` Actionを表示しないことを基本とする。

---

### 22.3 社員スキル編集

EmployeeSkill更新権限がない場合は `スキル編集` Actionを表示しないことを基本とする。

---

## 23. Responsive

### 23.1 Desktop

Desktopでは基本情報を複数Columnで表示可能とする。

Employee SkillsはTable形式を基本とする。

例:

```text
社員名                                [ 編集 ]

+----------------------+----------------------+
| 所属                 | 在籍状態             |
| 開発部               | 在籍                 |
+----------------------+----------------------+

保有スキル                     [ スキル編集 ]

+----------------------------------------------------------+
| スキル | Level | 実務経験 | 経験期間 | 最終利用         |
+----------------------------------------------------------+
```

---

### 23.2 Tablet

基本情報のColumn数を画面幅に応じて減らす。

Employee Skills Tableは必要に応じて横スクロールを許可する。

重要情報を優先して表示する。

---

### 23.3 Mobile

基本情報は1 Columnとする。

```text
社員名

所属
開発部

在籍状態
在籍
```

EmployeeSkillについては、Desktop Tableを単純に縮小しない。

候補:

1. 横スクロールTable
2. Column削減
3. SkillごとのCard表示

EmployeeSkillは1件あたりの情報量が多いため、MobileではCard形式も有力候補とする。

例:

```text
+----------------------------+
| Laravel                    |
| Framework                  |
|                            |
| Level        Level 4       |
| 実務経験     あり          |
| 経験期間     3年           |
| 最終利用     2026-09       |
+----------------------------+
```

最終方式は `09_レスポンシブ設計.md` で統一する。

---

## 24. Accessibility

以下を基本とする。

- Page TitleをSemanticなHeadingとして扱う
- 基本情報のLabelとValueの関係を理解できる構造にする
- StatusをColorだけで表現しない
- Skill TableにはSemanticなTable要素を利用する
- 編集ActionをKeyboardで操作可能にする
- Loading状態をVisualだけに依存させない
- Empty / ErrorをTextで通知する
- Focus Ringを維持する
- Mobile Cardへ変更した場合も情報項目の意味を維持する

## 27. MVPで扱わないもの

現時点では以下を社員詳細の必須機能としない。

- Inline Edit
- SkillのDrag & Drop
- Skill Ranking
- 社員同士の比較
- Skill Chart
- History Timeline
- Audit Log表示
- Export
- Print専用Layout
- Customizable Section

必要性が明確になった場合に別途検討する。

---

## 28. APIとの関係

社員基本情報・EmployeeSkillの表示内容は既存Employee API・EmployeeSkill APIを正とする。

画面設計上必要な情報が既存APIから取得できない場合は、UI側だけで値を仮定せず、システム設計との整合を確認する。

---

## 29. 本画面で定義しないもの

以下は既存仕様またはFrontend実装の責務とする。

- Employee API Endpoint
- EmployeeSkill API Endpoint
- API取得単位
- Cache戦略
- Server / Client Component境界
- React Component分割
- State管理方式
- Tailwind CSS Class
- Design Tokenの具体値
- 経験期間の具体的な計算実装
