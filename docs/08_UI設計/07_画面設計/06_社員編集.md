# 社員編集

## 1. 目的

社員詳細から、既存社員の基本情報・所属情報を編集するDialogとする。

EmployeeSkillは本Dialogでは扱わず、社員スキル編集画面へ責務を分離する。

在籍状態の変更および退職処理は本Dialogでは行わず、既存Employee Domain / API仕様に従って別の操作として扱う。

---

## 2. 対象ユーザー・権限

対象ユーザーは、社員更新権限を持つ認証済みユーザーとする。

社員更新権限がないユーザーには、社員詳細上の編集Actionを表示しないことを基本とする。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. UI種別

本機能は独立画面ではなくDialogとして扱う。

```text
/employees/[employeeId]
社員詳細
    |
    | 編集
    v
社員編集Dialog
```

独立したFrontend Routeは持たない。

---

## 4. 起点

社員編集Dialogは社員詳細からのみ開くことを基本とする。

起点:

```text
/employees/[employeeId]
```

社員一覧等から社員編集Dialogを直接開く導線は設けない。

---

## 5. 背景Context

Dialog表示中も社員詳細のContextを維持する。

以下は変更しない。

- Current Route
- App Shell
- Header
- Sidebar
- Breadcrumb
- Page Header
- Navigation Active State
- 社員詳細の表示内容

Current Routeは以下のままとする。

```text
/employees/[employeeId]
```

---

## 6. Breadcrumb

Dialogは独立Routeを持たないため、Breadcrumbを変更しない。

```text
Employees > 社員名
```

現在実行中の編集操作はDialog Titleで表現する。

---

## 7. Dialog構成

基本構造は以下とする。

```text
EmployeeEditDialog
├── Dialog Header
│   ├── Title
│   └── Description
│
├── Dialog Content
│   └── Employee Form
│
└── Dialog Footer
    ├── Cancel
    └── Save
```

shadcn/uiの `Dialog` を基本候補とする。

---

## 8. Dialog Header

### 8.1 Title

```text
社員編集
```

とする。

### 8.2 Description

必要に応じて対象社員を識別できる補足を表示する。

例:

```text
山田 太郎の社員情報を編集します。
```

Descriptionは必須としない。

---

## 9. 初期データ

Dialogを開く際は、社員詳細ですでに取得済みのEmployee情報を利用できる場合は、そのDataを初期値として利用することを基本とする。

追加Data取得が必要な場合のみ、Dialog表示後に取得する。

```text
Employee Detail Data
        ↓
EmployeeEditDialog
        ↓
Form Initial Values
```

不要な再取得を前提としない。

ただし、最新性を保証する必要がある場合は既存Frontend実装方針に従う。

---

## 10. Form対象

社員編集Formでは、Employee Domainで更新可能と定義されている基本情報を対象とする。

具体的な項目・更新可否・Validation Ruleは以下を正とする。

- 要件定義
- Employee Domain設計
- Employee更新API仕様

UI設計側で更新可能項目を新たに追加しない。

---

## 11. 編集不可項目

Domain上変更不可の情報が存在する場合は、編集可能なForm Controlとして表示しない。

必要に応じてReadonly情報として表示してよい。

```text
Label
Value
```

編集可能FieldとReadonly情報を識別できる構成とする。

Disabled Inputを単なる情報表示目的で多用しない。

---

## 12. Form構造

基本構造は以下とする。

```text
Employee Form
│
├── Basic Information
│   ├── Field
│   ├── Field
│   └── ...
│
├── Reference Information
│   └── Employment Status（Readonly）
│
└── Actions
    ├── Cancel
    └── Save
```

Dialog内Formは1 Columnを基本とする。

情報量が少ない場合はSectionを形式的に増やさない。

---

## 13. Form Field

各Fieldは以下の構造を基本とする。

```text
Label
Input / Select
Description
Error Message
```

必要な要素のみ表示する。

PlaceholderのみをLabelの代替として利用しない。

---

## 14. 所属

所属情報は既存Department仕様に従って編集する。

既存Departmentから選択する形式を基本とする。

UI側でDepartment名を直接変更したり、新しいDepartmentを同時作成したりしない。

Department管理は既存仕様に従う。

---

## 15. 在籍状態

Employment Statusは既存Domain仕様に従う。

本Dialogでは在籍状態を編集対象とせず、現在状態を参照情報として表示する。

例:

```text
在籍状態

在籍
```

`employmentStatus` を通常の社員更新Requestへ含めない。

---

## 16. 退職処理との責務分離

退職は本Dialogの社員情報更新とは分離し、専用のDomain Operationとして扱う。

本Dialogから以下を直接変更しない。

```text
employmentStatus
retirementDate
```

退職処理は社員詳細上の退職Actionから開始し、既存Employee API仕様に従って実行する。

```text
POST /api/v1/employees/{employeeId}/retirement
```

UI側で通常の社員更新処理へ退職操作を統合しない。

---

## 17. 退職社員の編集

退職社員も既存保持方針に従って詳細表示可能な前提とする。

退職社員の基本情報を編集できるかどうかは、既存Employee管理・Authorization仕様を正とする。

編集可能な場合でも、在籍社員と同じ操作がすべて利用できるとは限らない。

UI側だけで再在籍化・退職取消等の操作を追加しない。

---

## 18. 社員スキル

EmployeeSkillは本Dialogでは編集しない。

社員スキルの変更は以下の独立画面で行う。

```text
/employees/[employeeId]/skills
```

責務は以下のように分離する。

```text
EmployeeEditDialog
    ↓
Employee基本情報

Employee Skill Edit Page
    ↓
EmployeeSkill
```

---

## 19. Validation

Validation RuleはBackend / Domain仕様を正とする。

Frontend Validationは入力ミスを早期に通知する補助として利用してよいが、Backend Validationを代替しない。

UI独自のDomain Ruleを追加しない。

---

## 20. Validation Error

Validation Errorは対象Field付近へ表示する。

例:

```text
所属
[ Select ]

所属を選択してください。
```

Validation Error発生時はDialogを閉じない。

入力内容を可能な限り維持する。

---

## 21. Dialog全体Error

Field単位で表現できないErrorはDialog内のForm全体Errorとして表示する。

例:

```text
社員情報を更新できませんでした。
入力内容を確認してもう一度実行してください。
```

技術的なBackend Error Messageをそのまま表示しない。

Error発生時はDialogを閉じない。

---

## 22. 保存Action

Primary Actionは以下を基本とする。

```text
保存
```

Application全体でより具体的なLabelを採用する場合は、

```text
変更を保存
```

としてよい。

最終Labelは他の編集Dialog・編集画面と統一する。

---

## 23. 更新処理

保存Action実行時はLaravel Backend APIへ社員更新Requestを送信する。

概念上:

```text
EmployeeEditDialog
        |
        | Update Employee
        v
Backend API
```

具体的なEndpoint・HTTP Method・Request Bodyは既存API仕様を正とする。

---

## 24. 二重送信防止

更新処理中はPrimary Actionを再実行できない状態にする。

例:

```text
[ キャンセル ] [ 保存中... ]
```

またはLoading Indicatorを組み合わせる。

処理中であることをVisualだけに依存せず認識可能にする。

---

## 25. 更新成功

更新成功後はDialogを閉じ、社員詳細の表示内容を最新状態へ更新する。

```text
/employees/[employeeId]
        |
        | EmployeeEditDialog
        | 更新成功
        v
/employees/[employeeId]
```

Route変更は発生しない。

更新後の社員情報を社員詳細へ反映する。

---

## 26. Success Feedback

更新成功後、利用者が成功を認識できるFeedbackを提供してよい。

例:

```text
社員情報を更新しました。
```

具体的なNotification方式は共通UI・UI状態設計に従う。

---

## 27. キャンセル

Cancel ActionではDialogを閉じる。

```text
/employees/[employeeId]
        |
        | EmployeeEditDialog
        | Cancel
        v
/employees/[employeeId]
```

Route変更は発生しない。

未保存の変更は破棄する。

---

## 28. Close操作

Dialog HeaderにClose Buttonを設ける場合は、Cancelと同じ意味として扱うことを基本とする。

Escape KeyまたはBackdrop ClickによるCloseを許可するかは、未保存入力の扱いと合わせて決定する。

MVPでは複雑なUnsaved Changes Guardを必須としない。

---

## 29. Dialog Footer

Dialog FooterへActionを配置する。

基本形:

```text
[ キャンセル ] [ 保存 ]
```

Primary ActionとCancelの順序は他のDialogと統一する。

---

## 30. 利用する共通UI

### 30.1 shadcn/ui Component

利用候補:

- Dialog
- Alert Dialog
- Button
- Input
- Select
- Checkbox
- Radio Group
- Label
- Alert
- Skeleton

必要になったComponentのみ導入する。

### 30.2 Application共通Component

利用候補:

- FormField
- ErrorState

Dialog全体はEmployee Feature固有Componentとして扱う。

重要操作の確認はshadcn/uiの `Alert Dialog` を基本候補とし、Application共通の `ConfirmDialog` をMVP開始時点の必須Componentとはしない。

---

## 31. UI状態

### 31.1 Default

現在のEmployee情報をForm初期値として表示し、編集可能な状態とする。

---

### 31.2 Initial Loading

Dialog表示に必要な追加Data取得がある場合は、Dialog構造を維持したままContentをLoading状態とする。

例:

- Department一覧

社員詳細ですでに取得済みのEmployee情報まで不要に再Loadingしないことを基本とする。

---

### 31.3 Submit Loading

更新Request実行中は以下を基本とする。

- Save Actionを再実行不可にする
- 処理中であることを表示する
- Form値を維持する
- Dialogを閉じない

---

### 31.4 Validation Error

対象Field付近へErrorを表示する。

Dialogを閉じず、入力内容を維持する。

---

### 31.5 API Error

予期しないAPI Errorの場合もDialogを閉じない。

Form入力内容を維持し、再試行可能な状態を基本とする。

---

### 31.6 Resource Not Found

社員詳細を表示した後、編集実行までの間に対象Employeeが削除等によって存在しなくなった場合は、Backendの結果を基準に社員詳細の状態を再評価する。

必要に応じてNot Foundへ遷移する。

具体的なError変換方針はAPI共通仕様・UI状態設計に従う。

---

### 31.7 Access Denied

社員更新権限がないユーザーには、社員編集Dialogを開くActionを表示しないことを基本とする。

更新Request時の最終認可はBackendを正とする。

---

## 32. Master Data Error

所属選択肢等、更新に必要なMaster Data取得に失敗した場合は、Dialog内で保存不能な状態であることを明示する。

例:

```text
所属情報を取得できませんでした。

[ 再試行 ]
```

必要なMaster Dataを取得できないまま更新を許可しない。

---

## 33. Concurrent Update

同じEmployee情報が別操作によって更新された場合の競合処理が既存仕様に存在する場合は、その仕様に従う。

UI設計側で独自の楽観Lock・競合Ruleを追加しない。

Backendから競合Errorが返された場合は、利用者が次に取るべき操作を理解できるFeedbackを提供する。

具体的なUIは `08_UI状態設計.md` で整理する。

---

## 34. Responsive

### 34.1 Desktop

Desktopでは中央配置のDialogを基本とする。

Dialog内Formは1 Columnを基本とする。

Field同士の関連性が高く、十分な横幅が確保できる場合のみ複数Columnを検討する。

---

### 34.2 Tablet

Viewport内に収まるDialog幅を利用する。

Label・Description・Error Messageの可読性を優先する。

---

### 34.3 Mobile

Mobileでも操作の意味としては社員編集Dialogとして扱う。

Desktopの固定幅Modalを単純に縮小しない。

以下を候補とする。

- Viewport幅を広く利用するDialog
- Full-screenに近いDialog
- Sheet / Drawer

具体的な方式は `09_レスポンシブ設計.md` を正とする。

Formは1 Columnを基本とする。

---

## 35. Mobile Action

MobileではFooter Actionを縦配置してよい。

例:

```text
[ 保存             ]
[ キャンセル       ]
```

Primary Actionを識別しやすい構成を維持する。

---

## 36. Scroll

Dialog ContentがViewport Heightを超える場合はScroll可能とする。

HeaderやFooterを固定する場合は、Form Fieldが隠れないようにする。

---

## 37. Accessibility

以下を基本とする。

- Dialog Titleを支援技術から認識可能にする
- Dialog起動時に適切な要素へFocusを移動する
- Dialog表示中は背景へFocusを移動させない
- Dialog Close時は起動元ActionへFocusを戻す
- 各Form Controlに適切なLabelを設定する
- PlaceholderのみをLabelとして利用しない
- 編集可能 / Readonlyを識別可能にする
- Validation Errorと対象Fieldを関連付ける
- Keyboardのみで全Fieldを操作可能にする
- Keyboardで保存・キャンセルを実行可能にする
- Focus状態を視認可能にする
- Loading状態をVisualだけで表現しない
- Disabled状態をSemanticにも表現する
- Alert Dialog利用時はFocus Managementを維持する
- Error MessageをTextで表示する

## 40. MVPで扱わないもの

現時点では以下を社員編集Dialogの必須機能としない。

- EmployeeSkill編集
- Inline History
- Audit Log表示
- Draft保存
- Auto Save
- Bulk Update
- Department Inline作成
- Profile Image編集
- 高度なVersion Conflict UI
- DialogのURL同期

必要性が明確になった場合に別途検討する。

---

## 41. APIとの関係

社員更新項目・Validation Rule・更新可能項目は既存Employee API仕様を正とする。

本Dialogでは通常の社員更新APIで変更可能な項目のみを編集対象とする。

以下は通常の社員更新Requestでは変更しない。

```text
employmentStatus
retirementDate
```

退職処理は本Dialogとは分離し、社員詳細上の退職Actionから専用のDomain Operationとして実行する。

```text
POST /api/v1/employees/{employeeId}/retirement
```

UI設計上必要な操作が既存APIと一致しない場合は、UI側だけで更新項目を追加せず、システム設計との整合を確認する。

---

## 42. 本Dialogで定義しないもの

以下は既存仕様またはFrontend実装の責務とする。

- Employee API Endpointの具体定義
- Update RequestのHTTP Method
- Request Bodyの具体型
- Form Library
- State管理方式
- Server / Client Component境界
- React Component分割
- API Client実装
- Dialog Stateの具体的な実装方法
- Query Cache更新方式
- Tailwind CSS Class
- Design Tokenの具体値
- Concurrent Update実装
