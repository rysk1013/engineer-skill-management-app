# ログイン

## 1. 目的

未認証ユーザーがEngineer Skill Management Appへログインするための認証画面を提供する。

認証後Applicationへ安全に遷移できることを目的とする。

本画面は認証前専用画面として扱い、認証後のApp Shellは利用しない。

---

## 2. 対象ユーザー

未認証ユーザー。

認証済みユーザーが本画面へアクセスした場合は、Dashboardへ遷移する。

---

## 3. Route

```text
/login
```

---

## 4. 画面種別

独立画面とする。

Dialogでは扱わない。

認証前専用Layoutを利用する。

---

## 5. 基本遷移

### 5.1 未認証ユーザー

```text
/login
    ↓
Login Form
```

---

### 5.2 Login成功

Login成功後はDashboardへ遷移する。

```text
/login
    ↓
Login成功
    ↓
/
```

---

### 5.3 Login失敗

Login失敗時はRouteを変更しない。

```text
/login
    ↓
Login失敗
    ↓
/login
```

入力Contextを可能な限り維持し、認証Errorを表示する。

---

### 5.4 認証済みユーザー

認証済みユーザーが `/login` へアクセスした場合はDashboardへ遷移する。

```text
/login
    ↓
認証済み
    ↓
/
```

---

### 5.5 認証必須Routeからの遷移

未認証ユーザーが認証必須Routeへアクセスした場合は `/login` へ遷移する。

```text
認証必須Route
    ↓
未認証
    ↓
/login
```

Login成功後はDashboardへ遷移する。

```text
/login
    ↓
Login成功
    ↓
/
```

Phase 1では、Login前に要求していたRouteへ自動復帰する仕様は設けない。

---

## 6. Layout

認証後App Shellは利用しない。

基本構造は以下とする。

```text
Authentication Layout
│
├── Application Identification
└── Login Card / Form
```

Desktop例:

```text
+--------------------------------------------------+
|                                                  |
|                                                  |
|             Engineer Skill Management            |
|                                                  |
|             +----------------------+             |
|             | Login                |             |
|             |                      |             |
|             | User / Credential    |             |
|             |                      |             |
|             | Password             |             |
|             |                      |             |
|             | [ Login ]            |             |
|             +----------------------+             |
|                                                  |
|                                                  |
+--------------------------------------------------+
```

具体的な認証Fieldは既存Auth.js・認証仕様を正とする。

---

## 7. Application識別情報

利用者が対象Applicationを識別できる情報を表示する。

候補:

- Application Name
- 必要に応じてLogoまたはIcon

MVPでは過度なBranding要素を追加しない。

---

## 8. Login Form

Login Formには既存認証方式で必要な入力Fieldのみを配置する。

UI設計側で認証情報の種類を追加しない。

Field例は既存認証仕様に従う。

```text
Login Form
├── Credential Field
├── Password Field
└── Login Button
```

Auth.jsのProvider構成によってForm構成が異なる場合は、Frontend実装時に既存認証仕様へ合わせる。

---

## 9. Label

各入力Fieldには明示的なLabelを設ける。

PlaceholderのみをLabelの代替として利用しない。

---

## 10. Password Field

Password等の秘密情報を扱うFieldが存在する場合は、適切な入力Typeを利用する。

表示 / 非表示切り替えを提供する場合も、Keyboardおよび支援技術から操作可能とする。

MVPで必要性がなければPassword表示切り替え機能を必須としない。

---

## 11. Primary Action

LoginをPrimary Actionとする。

例:

```text
[ ログイン ]
```

Login以外のPrimary Actionを同列に増やさない。

---

## 12. Submit Loading

Login処理中は二重送信を防止する。

例:

```text
[ ログイン中... ]
```

入力値を処理開始時にClearしない。

---

## 13. Validation Error

Client / Server Validation Errorが存在する場合は、対象Field付近へ表示する。

例:

```text
ユーザー名
[               ]

ユーザー名を入力してください。
```

入力内容は可能な限り維持する。

---

## 14. Authentication Error

Credentialが正しくない等、認証に失敗した場合はForm内で認証Errorを表示する。

例:

```text
ログインできませんでした。
入力内容を確認してください。
```

具体的なMessageは既存認証仕様を正とする。

Security上不要な情報を表示しない。

---

## 15. Error Message方針

認証Errorでは、以下のような内部情報を表示しない。

- User存在有無
- Password一致 / 不一致の内部判定
- Internal Error Code
- Stack Trace
- Auth.js内部Error
- Backend Exception

Authentication Enumeration等の情報漏えいを避けるため、Messageの具体仕様は既存Security設計を正とする。

---

## 16. API / Network Error

認証処理中にNetwork Errorや予期しないErrorが発生した場合は、Credential Errorと区別して利用者向けMessageを表示する。

例:

```text
ログイン処理を完了できませんでした。
時間をおいてもう一度お試しください。
```

Retry可能な状態とする。

---

## 17. Login成功時

Login成功後はFormを表示し続けず、認証後Routeへ遷移する。

基本:

```text
/login
    ↓
Login成功
    ↓
/
```

遷移先の詳細は `03_画面遷移.md` および既存認証仕様を正とする。

---

## 18. 認証状態確認中

既存Sessionの有無を確認している間にLogin Formと認証後Contentを不必要に切り替えない。

概念上:

```text
Authentication State Loading
    ↓
Result
    ├── 未認証 → Login Form
    └── 認証済み → Dashboard
```

認証済みユーザーにLogin Formが一瞬表示される状態を可能な限り避ける。

---

## 19. App Shellとの関係

Login画面では以下を表示しない。

- 認証後Header
- Sidebar
- 認証後Breadcrumb
- User Menu
- Logout

Login画面専用の最小Layoutを利用する。

---

## 20. Navigation

Login画面では認証後Applicationの主要Navigationを表示しない。

未認証状態からEmployee / Skill / Access Control等へ直接NavigationできるUIを提供しない。

---

## 21. Logoutとの関係

Logout成功後は本画面へ遷移する。

```text
認証済み画面
    ↓
Logout
    ↓
/login
```

Logout自体は本画面の責務ではない。

Logout Actionは認証後App ShellのUser Menu等で提供する。

---

## 22. Loading State

Login画面では主に以下のLoadingを扱う。

### 22.1 Authentication State Loading

既存Session確認中。

### 22.2 Login Submit Loading

Credential送信・認証処理中。

両者を区別する。

---

## 23. Empty State

Login画面では通常のEmpty Stateを持たない。

---

## 24. Not Found

Login画面自身のResource Not Found Stateは原則持たない。

存在しないRouteについては共通Not Foundを利用する。

---

## 25. Access Denied

Login画面は未認証ユーザー向け画面であるため、通常Access Deniedを表示しない。

認証済みユーザーがLogin画面へアクセスした場合はDashboardへ遷移する。

---

## 26. Success Feedback

Login成功後は即座に認証後Routeへ遷移するため、Login画面上でSuccess Messageを長時間表示する必要はない。

必要なFeedbackは遷移自体で認識できることを基本とする。

---

### 27.1 Desktop

Login Formを読みやすい幅で中央付近へ配置する。

Viewport全幅までFormを広げない。

```text
+--------------------------------------------------+

|              Application Name                    |
|                                                  |

|              | Login Form       |                |
|              +------------------+                |
|                                                  |
+--------------------------------------------------+
```

---

### 27.2 Tablet

Desktopと同じ情報構造を維持する。

Viewport幅に応じてForm幅と余白を調整する。

---

### 27.3 Mobile

1 Columnを基本とする。

```text
+----------------------------+
|                            |
|      Application Name      |
|                            |
| Label                      |
| [                        ] |
|                            |
| Label                      |
| [                        ] |
|                            |

```

Formは利用可能な横幅を適切に使用する。

---

## 28. Mobile Keyboard

MobileでVirtual Keyboardが表示された場合も、入力中Field・Error Message・Login Buttonへアクセス可能な状態を維持する。

固定Heightへ過度に依存しない。

---

## 29. Accessibility

以下を基本とする。

- Page Titleを明確にする
- Main HeadingをSemanticに設定する
- Inputに明示的なLabelを設定する
- PlaceholderのみをLabelとして使用しない
- Validation ErrorとFieldを関連付ける
- Authentication Errorを支援技術から認識可能にする
- KeyboardのみでForm操作・Submit可能にする
- Focus状態を視認可能にする
- ErrorをColorだけで表現しない
- Submit Loadingを視覚表現だけに依存しない
- Login Buttonへ明確なAccessible Nameを設定する
- 認証失敗後のFocus移動を適切に検討する

---

## 30. Security

Login UIはSecurity Boundaryではない。

Authenticationの最終的な判定は既存Auth.js・Backend認証仕様を正とする。

Frontendのみで認証済み状態を保証しない。

---

## 31. Credential情報

Credential等の秘密情報を以下へ不要に保持・表示しない。

- URL
- Query Parameter
- Error Message
- Log
- Client-side Debug情報

具体的なCredential取扱いは既存Security設計を正とする。

---

## 32. Browser History

Login成功後にBrowser Backを実行した場合でも、認証済みユーザーへLogin Formを再表示し続けない。

認証状態を再評価し、既存認証仕様に従って適切なRouteへ遷移する。

---

## 33. Browser Refresh

`/login` をRefreshした場合も認証状態を安全に再評価する。

```text
/login
    ↓
Refresh
    ↓
Authentication State確認
    ├── 未認証 → Login
    └── 認証済み → /
```

一時的なClient Stateだけで認証状態を判断しない。

---

## 38. MVPで扱わないもの

既存認証要件で必要とされていない限り、Phase 1では以下を必須機能としない。

- 新規User登録
- Password Reset
- Forgot Password
- Remember Me
- Social Login
- MFA設定画面
- Login履歴
- Session一覧
- Device管理
- CAPTCHA
- Login画面のTheme切り替え
- Login専用Animation

必要性が正式仕様として追加された場合に別途設計する。

---

## 39. 本画面で定義しないもの

以下は既存認証設計またはFrontend実装設計を正とする。

- Auth.js Provider構成
- Credential Fieldの具体仕様
- Password Policy
- Session生成方法
- Session保存方法
- CSRF対策の具体実装
- Cookie設定
- Redirect実装
- Authentication Middleware
- Backend Token取得方法
- Sanctum Token管理
- Server / Client Component境界
- Form Library
- Validation Library
- React Component分割
- Tailwind CSS Class
- Login APIの具体Request / Response

Phase 1ではLogin UIの責務・状態・Layout・遷移を定義する。
