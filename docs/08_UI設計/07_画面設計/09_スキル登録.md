# スキル登録

## 1. 目的

スキル一覧から、新しいSkill Masterを登録するDialogとする。

Skill NameとSkill Categoryを入力し、登録成功後はスキル一覧へ反映する。

本機能は独立画面ではなく、`/skills` 上の `SkillCreateDialog` として扱う。

---

## 2. 対象ユーザー・権限

対象ユーザーは、Skill Masterの登録権限を持つ認証済みユーザーとする。

登録権限がないユーザーには、スキル一覧上のスキル登録Actionを表示しないことを基本とする。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. UI種別

本機能は独立画面ではなくDialogとして扱う。

```text
/skills
   |
   | スキル登録
   v
SkillCreateDialog
```

独立したFrontend Routeは持たない。

以下のRouteは設けない。

```text
/skills/create
```

---

## 4. 起点

SkillCreateDialogはスキル一覧からのみ開くことを基本とする。

起点:

```text
/skills
```

他画面から直接SkillCreateDialogを開く導線は設けない。

---

## 5. 背景Context

Dialog表示中もスキル一覧のContextを維持する。

以下は変更しない。

- Current Route
- App Shell
- Header
- Sidebar
- Breadcrumb
- Page Header
- Search / Filter条件
- Pagination状態
- Skill一覧

Current Routeは以下のままとする。

```text
/skills
```

---

## 6. Breadcrumb

Dialogは独立Routeを持たないため、Breadcrumbを変更しない。

```text
Skills
```

現在実行中の登録操作はDialog Titleで表現する。

---

## 7. Dialog構成

基本構造は以下とする。

```text
SkillCreateDialog
├── Dialog Header
│   ├── Title
│   └── Description
│
├── Dialog Content
│   └── Skill Form
│
└── Dialog Footer
    ├── Cancel
    └── Register
```

shadcn/uiの `Dialog` を基本候補とする。

---

## 8. Dialog Header

### 8.1 Title

```text
スキル登録
```

とする。

### 8.2 Description

必要に応じて以下のような補足を表示する。

```text
社員スキルとして利用するスキルを登録します。
```

Descriptionは必須としない。

---

## 9. 登録対象

Skill Masterの登録対象は、既存Skill Domain・API仕様を正とする。

MVPでは主に以下を扱う。

```text
Skill Name
Skill Category
```

UI設計側で新しいSkill属性を追加しない。

---

## 10. Skill Name

Skillを識別する名称を入力する。

例:

```text
Laravel
PHP
PostgreSQL
Docker
```

入力Componentは `Input` を基本とする。

具体的な文字数・文字種・重複制約は既存Skill Domain・API仕様を正とする。

---

## 11. Skill Category

Skill Categoryは既存Skill Category Masterから選択する。

例:

```text
Language
Framework
OS
Middleware
Cloud
Development Tool
```

具体的なCategoryは既存Skill Category Masterを正とする。

入力Componentは `Select` を基本候補とする。

---

## 12. Skill CategoryのInline登録

SkillCreateDialogからSkill Categoryを新規作成しない。

必要なCategoryが存在しない場合は、既存Skill Category管理機能でCategoryを追加した後にSkillを登録する。

```text
SkillCreateDialog
    ↓
既存Skill Categoryを選択
```

以下はMVPでは行わない。

```text
SkillCreateDialog
    ↓
Skill Category新規作成
```

---

## 13. Form構造

基本構造は以下とする。

```text
Skill Form
│
├── Skill Name
├── Skill Category
│
└── Actions
    ├── Cancel
    └── Register
```

入力項目が少ないため、1 Columnを基本とする。

---

## 14. Form Field

各Fieldは以下の構造を基本とする。

```text
Label
Input / Select
Description
Error Message
```

必要な要素のみ表示する。

PlaceholderのみをLabelの代替として利用しない。

---

## 15. 必須項目

必須・任意の扱いは既存Domain / API仕様を正とする。

Skill NameとSkill Categoryは必須項目とし、利用者が必須項目であることを認識できる表示とする。

例:

```text
スキル名 *
```

```text
カテゴリ *
```

必須表現はApplication全体で統一する。

---

## 16. Active状態

新規SkillのActive状態は既存Domain仕様を正とする。

新規登録時に常にActiveで作成される仕様である場合は、Active / Inactiveを選択するFieldを表示しない。

UI都合で不要な選択肢を増やさない。

---

## 17. 重複

Skill Name等の重複可否は既存Skill Domain・Database Constraint・API仕様を正とする。

重複不可である場合はFrontendでも早期検知できる範囲でFeedbackを提供してよいが、最終判定はBackendを正とする。

UI側で独自の重複判定Ruleを追加しない。

---

## 18. Validation

Validation RuleはBackend / Domain仕様を正とする。

Frontendでは入力ミスを早期に把握できる範囲でValidationを行ってよいが、Backend Validationを代替しない。

主な候補:

- Skill Name必須
- Skill Category必須
- Skill Nameの文字数
- Skill Nameの重複制約

実際のRuleは既存仕様を正とする。

---

## 19. Validation Error

Validation Errorは対象Field付近へ表示する。

例:

```text
スキル名
[                    ]

スキル名を入力してください。
```

```text
カテゴリ
[ 選択してください ▼ ]

カテゴリを選択してください。
```

Validation Error発生時はDialogを閉じない。

入力内容を維持する。

---

## 20. 重複Error

Backendから重複Errorが返された場合は、対象Fieldとの関係が分かるFeedbackを表示する。

例:

```text
スキル名
[ Laravel ]

同じ名前のスキルがすでに登録されています。
```

Backendの内部Error Messageをそのまま表示しない。

---

## 21. Dialog全体Error

Field単位で表現できないErrorはDialog内のForm全体Errorとして表示する。

例:

```text
スキルを登録できませんでした。
入力内容を確認してもう一度実行してください。
```

Error発生時はDialogを閉じない。

---

## 22. 登録Action

Primary Actionは以下を基本とする。

```text
登録
```

Application全体でより具体的なLabelを採用する場合は、

```text
スキルを登録
```

としてよい。

最終Labelは他の登録Dialogと統一する。

---

## 23. 登録処理

登録Action実行時はLaravel Backend APIへSkill登録Requestを送信する。

概念上:

```text
SkillCreateDialog
        |
        | Create Skill
        v
Backend API
```

具体的なEndpoint・Request Bodyは既存Skill API仕様を正とする。

---

## 24. 二重送信防止

登録処理中はPrimary Actionを再実行できない状態にする。

例:

```text
[ キャンセル ] [ 登録中... ]
```

処理中であることをVisualだけに依存せず認識可能にする。

---

## 25. 登録成功

登録成功後はDialogを閉じ、スキル一覧を最新状態へ更新する。

```text
/skills
   |
   | SkillCreateDialog
   | 登録成功
   v
/skills
```

Route変更は発生しない。

新しく登録したSkillを一覧上で確認できる状態とする。

---

## 26. Search / Filterとの関係

登録成功後も、ユーザーが指定していたSearch / Filter条件を維持することを基本とする。

新規Skillが現在の検索条件に一致しない場合は、必ずしも一覧上に表示されるとは限らない。

その場合でも登録成功Feedbackを提供する。

UI都合でSearch / Filter条件を自動Resetしないことを基本とする。

---

## 27. Paginationとの関係

登録成功後も、可能な限り現在のPagination Contextを維持する。

ただし、新規登録Skillを確実に一覧表示するためにPage移動が必要となる仕様にはしない。

登録成功の確認はSuccess Feedbackでも提供する。

---

## 28. Success Feedback

登録成功後、利用者が成功を認識できるFeedbackを提供してよい。

例:

```text
スキルを登録しました。
```

具体的なNotification方式は共通UI・UI状態設計に従う。

---

## 29. キャンセル

Cancel ActionではDialogを閉じる。

```text
/skills
   |
   | SkillCreateDialog
   | Cancel
   v
/skills
```

Route変更は発生しない。

入力中の値は破棄する。

---

## 30. Close操作

Dialog HeaderにClose Buttonを設ける場合は、Cancelと同じ意味として扱うことを基本とする。

Escape KeyまたはBackdrop ClickによるCloseを許可するかは、未保存入力の扱いと合わせて決定する。

MVPでは複雑なUnsaved Changes Guardを必須としない。

---

## 31. Dialog Footer

Dialog FooterへActionを配置する。

基本形:

```text
[ キャンセル ] [ 登録 ]
```

Primary ActionとCancelの順序は他のDialogと統一する。

---

## 32. Skill Category Master取得

Skill Category選択肢は既存Skill Category API等から取得する。

Dialog表示時点で既に取得済みのDataを利用できる場合は再利用してよい。

不要なAPI Requestを前提としない。

---

## 33. Skill Category取得中

Category取得が必要な場合は、Category Select等をLoading状態として表示する。

必要なMaster Dataを取得できるまで登録Actionを実行できない状態とする。

---

## 34. Skill Category取得失敗

Skill Category Master取得に失敗した場合は、登録不能な状態であることをDialog内に表示する。

例:

```text
スキルカテゴリを取得できませんでした。

[ 再試行 ]
```

必要なCategoryを取得できない状態でSkill登録を許可しない。

---

## 35. Inactive Category

InactiveなSkill Categoryの扱いは既存Domain仕様を正とする。

新規Skill登録先としてInactive Categoryを利用できない仕様である場合は、選択候補へ表示しないことを基本とする。

既存仕様上選択可能な場合は、その仕様に従う。

UI側だけでRuleを追加しない。

---

### 36.1 shadcn/ui Component

### 36.2 Application共通Component


## 38. UI状態

### 38.1 Default

入力可能なSkill Formを表示する。

---

### 38.2 Master Loading

Skill Category Master取得中。

必要な入力ComponentをLoading状態とする。

---

### 38.3 Submit Loading

登録Request実行中は以下を基本とする。

- Register Actionを再実行不可にする
- 入力内容を維持する
- 処理中であることを表示する
- Dialogを閉じない

---

### 38.4 Validation Error

対象Field付近へErrorを表示する。

Dialogを閉じない。

---

### 38.5 API Error

予期しないAPI Errorの場合もDialogを閉じない。

入力内容を維持し、再試行可能な状態とする。

---

### 38.6 Access Denied

登録権限がないユーザーには、スキル一覧上の登録Actionを表示しないことを基本とする。

登録Request時の最終認可はBackendを正とする。

---

## 39. Responsive

### 39.1 Desktop

Desktopでは中央配置のDialogを基本とする。

入力項目が少ないため、過度に大きなDialogにしない。

Formは1 Columnを基本とする。

---

### 39.2 Tablet

Viewport内に収まるDialog幅を利用する。

Label・Description・Error Messageの可読性を維持する。

---

### 39.3 Mobile

Mobileでも操作の意味としてはSkillCreateDialogとして扱う。

Desktopの固定幅Dialogを単純に縮小しない。

以下を候補とする。

- Viewport幅を広く利用するDialog
- Full-screenに近いDialog
- Sheet / Drawer

具体方式は `09_レスポンシブ設計.md` を正とする。

Formは1 Columnとする。

---

## 40. Mobile Action

MobileではFooter Actionを縦配置してよい。

例:

```text
[ 登録             ]
[ キャンセル       ]
```

Primary Actionを識別しやすい構成を維持する。

---

## 41. Accessibility

以下を基本とする。

- Dialog Titleを支援技術から認識可能にする
- Dialog起動時に適切な要素へFocusを移動する
- Dialog表示中は背景へFocusを移動させない
- Dialog Close後は起動元のスキル登録ActionへFocusを戻す
- 各Form Controlに適切なLabelを設定する
- PlaceholderのみをLabelとして利用しない
- Required / Optionalを認識可能にする
- Validation Errorと対象Fieldを関連付ける
- Keyboardのみで全Fieldを操作可能にする
- Keyboardで登録・キャンセルを実行可能にする
- Focus状態を視認可能にする
- Loading状態をVisualだけで表現しない
- Error MessageをTextで表示する

## 44. MVPで扱わないもの

現時点では以下をSkillCreateDialogの必須機能としない。

- Skill CategoryのInline登録
- Skill CategoryのInline編集
- EmployeeSkill登録
- 複数Skill一括登録
- CSV Import
- Skill Icon設定
- Skill Color設定
- Display Orderの手動設定
- Draft保存
- Auto Save
- DialogのURL同期

必要性が明確になった場合に別途検討する。

---

## 45. APIとの関係

Skill登録項目・Validation Rule・重複制約は既存Skill API仕様を正とする。

Skill Category選択肢は既存Skill Category API仕様を正とする。

UI設計上必要な項目が既存APIと一致しない場合は、UI側だけで追加せずシステム設計との整合を確認する。

---

## 46. 本Dialogで定義しないもの

以下は既存仕様またはFrontend実装の責務とする。

- Skill API Endpoint
- Request Bodyの具体型
- Skill Category API Endpoint
- Form Library
- State管理方式
- Server / Client Component境界
- React Component分割
- API Client実装
- Query Cache更新方式
- Dialog Stateの具体実装
- Tailwind CSS Class
- Design Tokenの具体値
- Database Constraint実装
