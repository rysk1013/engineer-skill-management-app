# スキルカテゴリ一覧

## 1. 目的

Skill Category Masterを一覧表示し、確認・登録・編集を行うための画面とする。

スキルカテゴリ登録・スキルカテゴリ編集は独立画面ではなく、本画面上のDialogとして扱う。

---

## 2. 対象ユーザー・権限

対象ユーザーは、Skill Category Masterの参照権限を持つ認証済みユーザーとする。

Skill Categoryの登録・編集Actionは、それぞれ必要な権限を持つユーザーにのみ表示することを基本とする。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. Route

```text
/skill-categories
```

とする。

スキルカテゴリ登録・編集DialogのOpen / CloseではRouteを変更しない。

以下の独立Routeは設けない。

```text
/skill-categories/create
/skill-categories/[categoryId]/edit
```

---

## 4. 画面種別

本画面はSkill Category Master管理の一覧画面とする。

以下の操作Contextを集約する。

```text
/skill-categories
├── Skill Category一覧
├── SkillCategoryCreateDialog
└── SkillCategoryEditDialog
```

一覧Contextを維持したまま、比較的小規模な登録・編集を行う。

---

## 5. Breadcrumb

基本形は以下とする。

```text
Skill Categories
```

Dialogを開いてもBreadcrumbは変更しない。

---

## 6. Page Header

基本構造:

```text
スキルカテゴリ一覧

[ スキルカテゴリ登録 ]
```

必要に応じてDescriptionを表示する。

例:

```text
スキルを分類するカテゴリマスタを管理します。
```

---

## 7. 画面構成

基本構造は以下とする。

```text
Skill Category List Page
│
├── Breadcrumb
├── Page Header
│   ├── Title
│   ├── Description
│   └── Create Action
│
├── Skill Category List
│   ├── Skill Category Row
│   ├── Skill Category Row
│   └── ...
│
└── Pagination
```

Dialog表示中も一覧画面のContextを維持する。

---

## 8. 一覧表示項目

Skill Category一覧では、既存Skill Category Domain・API仕様に基づく情報を表示する。

主な候補:

```text
Category Name
Actions
```

必要に応じて識別子等を表示してよいが、管理操作に不要な内部情報を過度に表示しない。

---

## 9. Category Name

Skill Categoryを識別する主要情報としてCategory Nameを表示する。

例:

```text
Language
Framework
OS
Middleware
Cloud
Development Tool
```

具体的な名称はSkill Category Masterを正とする。

---

## 10. Actions

各Skill Categoryに対して、権限に応じたActionを提供する。

候補:

```text
編集
```

MVPではActionが少ないため、単一の編集Actionを直接表示する構成を基本候補とする。

将来Actionが増えた場合はDropdown Menu等への変更を検討してよい。

---

## 11. 一覧操作

一覧の基本フローは以下とする。

```text
/skill-categories
   |
   ├── Category登録
   |      ↓
   |  SkillCategoryCreateDialog
   |
   └── Category編集
          ↓
      SkillCategoryEditDialog
```

いずれも通常は一覧Routeを維持する。

---

## 12. Skill Category登録

Page Header等に登録Actionを配置する。

例:

```text
[ スキルカテゴリ登録 ]
```

Action実行時に `SkillCategoryCreateDialog` を開く。

```text
/skill-categories
   |
   | スキルカテゴリ登録
   v
SkillCategoryCreateDialog
```

---

## 13. SkillCategoryCreateDialog

Skill Category登録DialogはFeature固有Componentとして扱う。

概念上:

```text
SkillCategoryCreateDialog
├── Dialog Header
├── Skill Category Form
└── Dialog Footer
```

具体的なForm仕様は `12_スキルカテゴリ登録.md` で定義する。

Dialog Open / CloseではRouteを変更しない。

---

## 14. Skill Category登録成功

登録成功後はDialogを閉じ、Skill Category一覧を最新状態へ更新する。

```text
/skill-categories
   |
   | SkillCategoryCreateDialog
   | 登録成功
   v
/skill-categories
```

新規Categoryが一覧上で確認できる状態とする。

---

## 15. Skill Category登録キャンセル

Cancel時はDialogを閉じる。

```text
/skill-categories
   |
   | SkillCategoryCreateDialog
   | Cancel
   v
/skill-categories
```

Route変更は発生しない。

---

## 16. Skill Category編集

各Skill Categoryに編集Actionを提供する。

例:

```text
[ 編集 ]
```

Action実行時に対象Categoryを指定して `SkillCategoryEditDialog` を開く。

```text
/skill-categories
   |
   | 編集
   v
SkillCategoryEditDialog
```

---

## 17. SkillCategoryEditDialog

Skill Category編集DialogはFeature固有Componentとして扱う。

概念上:

```text
SkillCategoryEditDialog
├── Dialog Header
├── Skill Category Form
└── Dialog Footer
```

具体的なForm仕様は `13_スキルカテゴリ編集.md` で定義する。

Dialog Open / CloseではRouteを変更しない。

---

## 18. Skill Category編集成功

編集成功後はDialogを閉じ、一覧の対象Categoryを最新状態へ更新する。

```text
/skill-categories
   |
   | SkillCategoryEditDialog
   | 更新成功
   v
/skill-categories
```

Route変更は発生しない。

---

## 19. Skill Category編集キャンセル

Cancel時はDialogを閉じる。

未保存の変更は破棄する。

一覧Contextは維持する。

---

## 20. Skill Category削除

MVPではSkill Category Masterを削除する操作をUIとして提供しない。

UI側で独自にDelete Actionを追加しない。

---

## 21. Skillとの関係

Skill Category MasterとSkillを明確に分離する。

```text
Skill Category Master
    ↓
Skill分類の定義

Skill Master
    ↓
Skill Name・Category・Active状態
```

Skill Category一覧画面ではSkill Masterを直接編集しない。

---

## 22. 検索

Skill Category件数や既存API仕様に応じて、Category Nameを対象としたKeyword検索を提供してよい。

例:

```text
[ キーワード                     ] [ 検索 ]
```

MVPで検索が不要な規模・仕様である場合は、必須機能としない。

UI側だけでBackend未対応の検索機能を追加しない。

---

## 23. Pagination

一覧件数が多い場合はPaginationを利用する。

具体的なPage Size・Pagination方式はSkill Category一覧API仕様を正とする。

件数が少なくPagination不要な仕様である場合は導入しない。

---

## 24. Sort

Sortが既存APIで提供される場合は必要に応じてUIを提供する。

候補:

- Category Name

API側にSort仕様がない場合は、UI側だけで高度なSort機能を追加しない。

---

## 25. Loading

Skill Category一覧取得中はPage構造を維持しつつSkeleton等を表示する。

例:

```text
Page Header
Skeleton List
```

Page全体を単一Spinnerだけで置き換えることを標準としない。

---

## 26. Empty State

Skill Categoryが1件も存在しない場合はEmpty Stateを表示する。

例:

```text
スキルカテゴリが登録されていません。

[ スキルカテゴリ登録 ]
```

登録権限がない場合はActionを表示しない。

---

## 27. Search Result Empty

検索を提供する場合、条件に一致するCategoryが存在しない状態はMaster自体が空の状態と区別する。

例:

```text
条件に一致するスキルカテゴリがありません。

検索条件を変更してください。
```

必要に応じて条件Reset Actionを提供する。

---

## 28. Error State

一覧取得に失敗した場合はErrorStateを表示する。

例:

```text
スキルカテゴリ一覧を取得できませんでした。

[ 再試行 ]
```

技術的なBackend Error Messageをそのまま表示しない。

---

## 29. Operation Error

登録・編集等の操作に失敗した場合は、現在のContextを維持したままFeedbackを表示する。

Dialog内部でValidation ErrorまたはAPI Errorが発生した場合は、入力内容を可能な限り維持する。

---

## 30. Success Feedback

操作成功後、必要に応じて成功Feedbackを表示する。

例:

```text
スキルカテゴリを登録しました。
```

```text
スキルカテゴリを更新しました。
```

具体的なNotification方式は共通UI・UI状態設計に従う。

---

## 34. Permission

Skill Category参照権限がない場合は、既存Access Control方針に従う。

登録権限がない場合:

```text
スキルカテゴリ登録Actionを表示しない
```

編集権限がない場合:

```text
編集Actionを表示しない
```

Frontend上のAction非表示はUX上の制御とし、最終認可はBackendを正とする。

---

## 35. Responsive

### 35.1 Desktop

DesktopではTable形式を基本候補とする。

例:

```text
+------------------------------------------+
| Category          | Actions              |
+------------------------------------------+
| Language          | 編集                 |
| Framework         | 編集                 |
| Middleware        | 編集                 |
+------------------------------------------+
```

---

### 35.2 Tablet

利用可能な横幅に応じてColumn幅・Action表示を調整する。

Actionが増える場合はDropdown Menuを利用してよい。

---

### 35.3 Mobile

Mobileでは情報優先度に応じて以下を検討する。

- Column削減
- Card / List表示

Card表示例:

```text
Framework

[ 編集 ]
```

具体方式は `09_レスポンシブ設計.md` を正とする。

---

## 36. Mobile Search

検索を提供する場合、Mobileでは縦配置してよい。

例:

```text
[ キーワード            ]

[ 検索 ]
```

操作数が少ない場合は複雑な検索UIを導入せず、単純なLayoutを優先する。

---

## 37. Dialog Responsive

SkillCategoryCreateDialog / SkillCategoryEditDialogのResponsive方針は共通Dialog設計に従う。

Desktopでは中央Dialogを基本とする。

Mobileでは以下を候補とする。

- Viewport幅を広く利用するDialog
- Full-screenに近いDialog
- Sheet / Drawer

具体方式は `09_レスポンシブ設計.md` を正とする。

---

## 38. Accessibility

以下を基本とする。

- Page Titleを明確にする
- Table HeaderをSemanticに関連付ける
- Row ActionをKeyboardで操作可能にする
- 検索を提供する場合は適切なLabelを設定する
- DialogのFocus Managementを適切に行う
- Dialog Close後は起動元ActionへFocusを戻す
- Loading状態をVisualだけで表現しない
- ErrorをTextで表示する

## 43. MVPで扱わないもの

現時点では以下を本画面の必須機能としない。

- Skill Categoryの削除
- Skill Categoryの無効化・再有効化
- Skill Categoryの一括登録
- Skill Categoryの一括編集
- CSV Import / Export
- Drag & Dropによる並び替え
- SkillのInline登録
- SkillのInline編集
- Category Color設定
- Category Icon設定
- Display Orderの手動設定
- 高度なAdvanced Search
- Saved Search
- DialogのURL同期

必要性が明確になった場合に別途検討する。

---

## 44. APIとの関係

Skill Category一覧・登録・編集の仕様は既存Skill Category APIを正とする。

UI上で必要な操作が既存APIと一致しない場合は、UI側だけで仕様を追加せず、システム設計との整合を確認する。

Skillからの参照関係についても既存Domain・API仕様を正とする。

---

## 45. 本画面で定義しないもの

以下は既存仕様またはFrontend実装の責務とする。

- Skill Category API Endpoint
- Request / Responseの具体型
- Search Parameterの具体名
- Pagination実装
- Sort実装
- Form Library
- State管理方式
- Server / Client Component境界
- React Component分割
- API Client実装
- Query Cache更新方式
- Dialog Stateの具体実装
- Tailwind CSS Class
- Design Tokenの具体値
