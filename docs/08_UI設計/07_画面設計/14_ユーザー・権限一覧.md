# ユーザー・権限一覧

## 1. 目的

Application UserごとのRole・権限関連情報を一覧表示し、Access Controlの状態確認および権限編集画面への遷移を行うための画面とする。

権限変更そのものは一覧画面上でInline編集せず、対象ユーザーごとの独立した権限編集画面で行う。

---

## 2. 対象ユーザー・権限

対象ユーザーは、Access Control情報の参照権限を持つ認証済みユーザーとする。

権限編集Actionは、権限管理を実行可能なユーザーにのみ表示することを基本とする。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. Route

```text
/access-control
```

とする。

権限編集は以下の独立Routeで行う。

```text
/access-control/[userId]/edit
```

一覧から対象ユーザーを選択して遷移する。

---

## 4. 画面種別

本画面はAccess Control管理の一覧画面とする。

以下の責務を持つ。

```text
/access-control
├── User一覧
├── Role確認
├── Permission関連状態確認
└── 権限編集画面への遷移
```

権限変更Form自体は本画面に配置しない。

---

## 5. Breadcrumb

基本形は以下とする。

```text
Access Control
```

権限編集画面へ遷移した場合は、編集画面側でBreadcrumbを追加する。

---

## 6. Page Header

基本構造:

```text
ユーザー・権限一覧
```

必要に応じてDescriptionを表示する。

例:

```text
ユーザーのRoleと権限設定を確認・管理します。
```

一覧画面上に新規作成Actionは設けないことを基本とする。

User作成・Employee作成等の責務とは分離する。

---

## 7. 画面構成

基本構造は以下とする。

```text
Access Control List Page
│
├── Breadcrumb
├── Page Header
│   ├── Title
│   └── Description
│
├── Search / Filter
│
├── User / Permission List
│   ├── User Row
│   ├── User Row
│   └── ...
│
└── Pagination
```

---

## 8. 一覧表示項目

既存User・Access Control Domain・API仕様に基づく情報を表示する。

主な候補:

```text
User
Role
Permission Management
Status
Actions
```

実際に表示する項目は、既存Access Control仕様を正とする。

不要な内部認可情報をそのまま一覧へ露出しない。

---

## 9. User

権限管理対象となるUserを識別可能に表示する。

表示名として何を利用するかは既存User仕様を正とする。

Employeeとの関連が存在する場合でも、UI側で新しい識別Ruleを追加しない。

---

## 10. Role

Userに設定されているRoleを表示する。

既存Roleとして以下を前提とする。

```text
管理者
マネージャー
サブマネージャー
チームリーダー
```

実際の表示Labelは既存UserRole仕様を正とする。

RoleはBadge等を利用して識別しやすくしてよい。

色だけに依存してRoleを表現しない。

---

## 11. Permission Management

権限管理能力を表す既存情報がある場合は、利用者が理解可能な形式で表示する。

特に既存制約である、

```text
ADMINISTRATOR
AND
can_manage_permissions = true
```

を持つユーザーについては、権限管理可能な管理者として識別できることが望ましい。

例:

```text
権限管理
可能
```

または、

```text
権限管理者
```

等の表示を候補とする。

内部Property名をそのままUI Labelとして表示しない。

---

## 12. 最低1人制約

既存Domain Ruleとして、

```text
ADMINISTRATOR
&&
can_manage_permissions = true
```

を満たすユーザーを最低1人維持する。

本一覧では、この制約によって特別なInline制御を行う必要はない。

ただし、権限管理可能な管理者を利用者が識別できる表示を提供する。

実際の変更制約・ValidationはBackendを正とする。

---

## 13. Status

Userに既存Statusが存在し、Access Control上表示する必要がある場合はStatusを表示する。

例:

```text
有効
無効
```

具体的なStatus定義は既存User Domainを正とする。

StatusがAccess Control画面に不要な場合は表示しない。

---

## 14. Actions

各Userに対して、権限と既存仕様に応じたActionを提供する。

MVPの主要Action:

```text
権限編集
```

例:

```text
[ 編集 ]
```

Action数が少ない場合は直接Button / Linkとして表示してよい。

---

## 15. 権限編集

編集Action実行時は、対象Userの権限編集画面へ遷移する。

```text
/access-control
        |
        | 編集
        v
/access-control/[userId]/edit
```

Dialogではなく独立画面とする。

---

## 16. 独立画面を採用する理由

権限編集では以下を扱う可能性がある。

- Role
- `can_manage_permissions`
- Permission関連設定
- 変更による影響
- 最低1人の権限管理可能Administrator制約

通常の小規模なMaster編集より意味・影響が大きいため、一覧Context上のDialogではなく独立した作業Contextを持たせる。

---

## 17. Inline編集

一覧上でRoleやPermissionを直接変更しない。

以下のようなInline操作はMVPでは採用しない。

```text
User A | Role [ Administrator ▼ ]
```

変更は必ず権限編集画面を経由する。

これにより、

- 誤操作防止
- 変更対象の明確化
- Domain Ruleの理解
- Validation Errorの表示
- 権限制約の説明

を行いやすくする。

---

## 18. Search

ユーザー数・既存API仕様に応じてKeyword検索を提供する。

検索対象候補:

- User表示名
- Employee表示名

実際の検索対象は既存Access Control一覧API仕様を正とする。

例:

```text
[ キーワード                     ] [ 検索 ]
```

UI側でBackend未対応の検索対象を独自追加しない。

---

## 19. Role Filter

既存APIが対応する場合はRole Filterを提供してよい。

例:

```text
Role
[ すべて ▼ ]
```

選択肢は既存UserRoleを正とする。

---

## 20. Permission Management Filter

必要性およびAPI対応がある場合は、権限管理可能ユーザーを絞り込むFilterを提供してよい。

例:

```text
権限管理
[ すべて ▼ ]
```

MVPで利用価値が低い場合は必須としない。

---

## 21. Search / Filter配置

検索・Filterを提供する場合は一覧上部に配置する。

例:

```text
+------------------------------------------------------+
| Keyword        | Role            | Permission Mgmt   |
| [          ]   | [ All ▼ ]      | [ All ▼ ]        |
|                                      [ Search ]      |
+------------------------------------------------------+
```

条件が少ない場合は過度に複雑なFilter UIにしない。

---

## 22. Reset

複数検索条件を提供する場合は、必要に応じてReset Actionを提供する。

例:

```text
[ 条件をクリア ]
```

条件が容易に解除可能な場合は必須としない。

---

## 23. Pagination

一覧件数が多い場合はPaginationを利用する。

具体的なPage Size・Pagination方式はAccess Control一覧API仕様を正とする。

UI側で独自のPagination Ruleを追加しない。

---

## 24. Sort

既存APIでSortが提供される場合は必要に応じてUIを提供する。

候補:

- User Name
- Role
- Status

MVPでAPI対応がない場合は、UI側だけで高度なSort機能を追加しない。

---

## 25. 権限管理可能Administratorの表示

最低1人維持制約を持つUserを判別しやすくするため、必要に応じてBadge等を利用する。

例:

```text
山田 太郎

管理者
権限管理者
```

ただし、UI表示だけでDomain Ruleを保証しない。

---

## 26. 自分自身の権限

現在ログインしているUser自身が一覧に含まれる場合も、通常の一覧項目として表示する。

自分自身の権限編集可否は既存Access Control仕様を正とする。

UI側だけで、

```text
自分だから編集可能
```

または、

```text
自分だから編集不可
```

といったRuleを追加しない。

必要であれば、

```text
自分
```

等の補助Labelを表示して識別しやすくしてよい。

---

## 27. 編集不可User

既存権限制約によって特定Userを編集できない場合は、編集Actionを非表示またはDisabledとする。

Disabledを利用する場合は、可能であれば理由を理解できる状態にする。

ただし、Frontendの表示制御のみを認可として扱わない。

---

## 28. Loading

一覧取得中はPage構造を維持しつつSkeleton等を表示する。

例:

```text
Page Header
Search / Filter
Skeleton List
```

Page全体を単一Spinnerだけで置き換えることを標準としない。

---

## 29. Empty State

権限管理対象Userが1件も存在しない場合はEmpty Stateを表示する。

例:

```text
権限管理対象のユーザーがいません。
```

本画面からUserを新規作成するActionは提供しないことを基本とする。

---

## 30. Search Result Empty

検索・Filter条件に一致するUserが存在しない場合は、対象User自体が存在しない状態と区別する。

例:

```text
条件に一致するユーザーがいません。

検索条件を変更してください。
```

必要に応じて条件Reset Actionを提供する。

---

## 31. Error State

一覧取得に失敗した場合はErrorStateを表示する。

例:

```text
ユーザー・権限一覧を取得できませんでした。

[ 再試行 ]
```

技術的なBackend Error Messageをそのまま表示しない。

---

## 32. Access Denied

Access Control情報の参照権限がない場合は、既存Access Control方針に従ってAccess Deniedとして扱う。

```text
/forbidden
```

等の共通Access Denied UIを利用する。

最終的な認可判定はBackendを正とする。

---

## 33. Resource Not Found

一覧画面自体では通常個別Resource Not Foundを扱わない。

一覧取得時に存在しなくなったUser等は最新API Resultを正とする。

編集画面遷移後に対象Userが存在しない場合は、編集画面側でNot Foundとして扱う。

---

## 34. Success Feedback

本画面では通常、権限変更Mutationを直接行わない。

権限編集画面から一覧へ戻った際に必要であれば、更新成功Feedbackを表示してよい。

例:

```text
ユーザー権限を更新しました。
```

具体的なFeedback引き継ぎ方式はFrontend実装設計を正とする。

## 38. Permission

一覧画面におけるAction表示は、現在ログインしているUserの権限に応じて制御する。

例:

```text
参照のみ可能
    ↓
一覧表示
編集Actionなし
```

```text
権限管理可能
    ↓
一覧表示
編集Actionあり
```

具体的な判定Ruleは既存Access Control仕様を正とする。

---

## 39. Backend認可

Frontend上で編集Actionが表示されていても、最終的な権限更新可否はBackendが判定する。

Frontendの表示制御は、

- 誤操作防止
- 利用可能Actionの明確化
- UX改善

を目的とする。

Security Boundaryとして扱わない。

## 41. Tablet

利用可能な横幅に応じてColumn数・表示内容を調整する。

優先度の低い情報は省略またはAction Menu等へ移してよい。

Roleと編集Actionは識別可能な状態を維持する。

## 42. Mobile

MobileではTableをそのまま圧縮せず、以下を検討する。

- Column削減
- Card / List表示

例:

```text
山田 太郎

管理者
権限管理者
有効

[ 権限編集 ]
```

User単位の境界を明確にする。

---

## 43. Mobile Search / Filter

検索・Filterを提供する場合は縦配置してよい。

```text
[ キーワード            ]

[ Role              ▼ ]

[ 検索 ]
```

操作数が少ない場合は複雑なFilter Sheet等を導入しない。

## 44. Accessibility

以下を基本とする。

- Page Titleを明確にする
- Table HeaderをSemanticに関連付ける
- RoleをColorだけで表現しない
- 権限管理可否をColorだけで表現しない
- StatusをColorだけで表現しない
- 編集Actionに対象Userを識別可能なAccessible Nameを設定する
- Keyboardのみで一覧・編集Actionを操作可能にする
- Search / Filterへ適切なLabelを設定する
- Focus状態を視認可能にする
- Disabled Actionの意味を理解可能にする
- Loading状態をVisualだけで表現しない
- ErrorをTextで表示する

同じ「編集」Actionが繰り返されるため、支援技術上は対象Userを含めて識別可能にする。

例:

```text
山田 太郎の権限を編集
```

## 47. MVPで扱わないもの

現時点では以下を本画面の必須機能としない。

- 一覧上でのRole Inline編集
- 一覧上でのPermission Inline編集
- 複数Userの権限一括更新
- CSV Import / Export
- User新規作成
- Employee新規作成
- Permission Definitionそのものの編集
- Role Definitionそのものの編集
- Drag & DropによるRole変更
- 高度なAdvanced Search
- Saved Search

必要性が明確になった場合に別途検討する。

---

## 48. APIとの関係

User / Access Control一覧・検索・Pagination・Permission情報の仕様は既存Access Control APIを正とする。

UI上で必要な表示・操作が既存APIと一致しない場合は、UI側だけで仕様を追加せず、システム設計との整合を確認する。

---

## 49. 本画面で定義しないもの

以下は既存仕様またはFrontend実装の責務とする。

- Access Control API Endpoint
- Request / Responseの具体型
- Search Parameterの具体名
- Pagination実装
- Sort実装
- Permission判定の具体ロジック
- State管理方式
- Server / Client Component境界
- React Component分割
- API Client実装
- Query Cache更新方式
- Tailwind CSS Class
- Design Tokenの具体値
