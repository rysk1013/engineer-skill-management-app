# スキルカテゴリ登録

## 1. 目的

スキルカテゴリ一覧から、新しいSkill Category Masterを登録するDialogとする。

Category Nameを入力し、登録成功後はスキルカテゴリ一覧へ反映する。

本機能は独立画面ではなく、`/skill-categories` 上の `SkillCategoryCreateDialog` として扱う。

---

## 2. 対象ユーザー・権限

対象ユーザーは、Skill Category Masterの登録権限を持つ認証済みユーザーとする。

登録権限がないユーザーには、スキルカテゴリ一覧上の登録Actionを表示しないことを基本とする。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. UI種別

本機能は独立画面ではなくDialogとして扱う。

```text
/skill-categories
        |
        | スキルカテゴリ登録
        v
SkillCategoryCreateDialog
```

独立したFrontend Routeは持たない。

以下のRouteは設けない。

```text
/skill-categories/create
```

---

## 4. 起点

SkillCategoryCreateDialogはスキルカテゴリ一覧からのみ開くことを基本とする。

起点:

```text
/skill-categories
```

他画面から直接SkillCategoryCreateDialogを開く導線は設けない。

---

## 5. 背景Context

Dialog表示中もスキルカテゴリ一覧のContextを維持する。

以下は変更しない。

- Current Route
- App Shell
- Header
- Sidebar
- Breadcrumb
- Page Header
- 検索条件
- Pagination状態
- Skill Category一覧

Current Routeは以下のままとする。

```text
/skill-categories
```

---

## 6. Breadcrumb

Dialogは独立Routeを持たないため、Breadcrumbを変更しない。

```text
Skill Categories
```

現在実行中の登録操作はDialog Titleで表現する。

---

## 7. Dialog構成

基本構造は以下とする。

```text
SkillCategoryCreateDialog
├── Dialog Header
│   ├── Title
│   └── Description
│
├── Dialog Content
│   └── Skill Category Form
│
└── Dialog Footer
    ├── Cancel
    └── Register
```

shadcn/uiの `Dialog` を基本候補とする。

---

## 8. Dialog Header

### 8.1 Title

```text
スキルカテゴリ登録
```

とする。

### 8.2 Description

必要に応じて以下のような補足を表示する。

```text
スキルを分類するカテゴリを登録します。
```

Descriptionは必須としない。

---

## 9. 登録対象

Skill Category Masterの登録対象は、既存Skill Category Domain・API仕様を正とする。

MVPでは以下を扱う。

```text
Category Name
```

UI設計側で新しいSkill Category属性を追加しない。

---

## 10. Category Name

Skill Categoryを識別する名称を入力する。

例:

```text
Language
Framework
OS
Middleware
Cloud
Development Tool
```

入力Componentは `Input` を基本とする。

具体的な文字数・文字種・重複制約は既存Skill Category Domain・API仕様を正とする。

---

## 11. Form構造

基本構造は以下とする。

```text
Skill Category Form
│
├── Category Name
│
└── Actions
    ├── Cancel
    └── Register
```

入力項目が少ないため、1 Columnを基本とする。

---

## 12. Form Field

各Fieldは以下の構造を基本とする。

```text
Label
Input
Description
Error Message
```

必要な要素のみ表示する。

PlaceholderのみをLabelの代替として利用しない。

---

## 13. 必須項目

Category Nameは必須項目とし、利用者が必須項目であることを認識できる表示とする。

例:

```text
カテゴリ名 *
```

または、

```text
カテゴリ名
必須
```

必須表現はApplication全体で統一する。

---

## 14. 重複

Category Nameの重複可否は既存Skill Category Domain・Database Constraint・API仕様を正とする。

Frontendでも早期検知できる範囲でFeedbackを提供してよいが、最終判定はBackendを正とする。

UI側で独自の重複判定Ruleを追加しない。

---

## 15. Validation

Validation RuleはBackend / Domain仕様を正とする。

Frontendでは入力ミスを早期に把握できる範囲でValidationを行ってよいが、Backend Validationを代替しない。

主なRule:

- Category Name必須
- Category Nameの文字数
- Category Nameの重複制約

実際のRuleは既存仕様を正とする。

---

## 16. Validation Error

Validation Errorは対象Field付近へ表示する。

例:

```text
カテゴリ名
[                    ]

カテゴリ名を入力してください。
```

Validation Error発生時はDialogを閉じない。

入力内容を維持する。

---

## 17. 重複Error

Backendから重複Errorが返された場合は、対象Fieldとの関係が分かるFeedbackを表示する。

例:

```text
カテゴリ名
[ Framework ]

同じ名前のスキルカテゴリがすでに登録されています。
```

Backend内部のError Messageをそのまま表示しない。

---

## 18. Dialog全体Error

Field単位で表現できないErrorはDialog内のForm全体Errorとして表示する。

例:

```text
スキルカテゴリを登録できませんでした。
入力内容を確認してもう一度実行してください。
```

Error発生時はDialogを閉じない。

---

## 19. 登録Action

Primary Actionは以下を基本とする。

```text
登録
```

Application全体でより具体的なLabelを採用する場合は、

```text
スキルカテゴリを登録
```

としてよい。

最終Labelは他の登録Dialogと統一する。

---

## 20. 登録処理

登録Action実行時はLaravel Backend APIへSkill Category登録Requestを送信する。

概念上:

```text
SkillCategoryCreateDialog
          |
          | Create Skill Category
          v
Backend API
```

具体的なEndpoint・Request Bodyは既存Skill Category API仕様を正とする。

---

## 21. 二重送信防止

登録処理中はPrimary Actionを再実行できない状態にする。

例:

```text
[ キャンセル ] [ 登録中... ]
```

処理中であることをVisualだけに依存せず認識可能にする。

---

## 22. 登録成功

登録成功後はDialogを閉じ、スキルカテゴリ一覧を最新状態へ更新する。

```text
/skill-categories
        |
        | SkillCategoryCreateDialog
        | 登録成功
        v
/skill-categories
```

Route変更は発生しない。

新しく登録したSkill Categoryを一覧上で確認できる状態とする。

---

## 23. 検索との関係

検索を提供している場合、登録成功後も現在の検索条件を維持することを基本とする。

新規Categoryが現在の検索条件に一致しない場合は、一覧上に表示されない可能性がある。

その場合でも登録成功Feedbackを提供する。

UI都合で検索条件を自動Resetしないことを基本とする。

---

## 24. Paginationとの関係

Paginationを利用している場合、登録成功後も可能な限り現在のPagination Contextを維持する。

新規登録Categoryを確実に表示するためだけにPageを強制移動する仕様にはしない。

登録成功の確認はSuccess Feedbackでも提供する。

---

## 25. Success Feedback

登録成功後、利用者が成功を認識できるFeedbackを提供してよい。

例:

```text
スキルカテゴリを登録しました。
```

具体的なNotification方式は共通UI・UI状態設計に従う。

---

## 26. キャンセル

Cancel ActionではDialogを閉じる。

```text
/skill-categories
        |
        | SkillCategoryCreateDialog
        | Cancel
        v
/skill-categories
```

Route変更は発生しない。

入力中の値は破棄する。

---

## 27. Close操作

Dialog HeaderにClose Buttonを設ける場合は、Cancelと同じ意味として扱うことを基本とする。

Escape KeyまたはBackdrop ClickによるCloseを許可するかは、未保存入力の扱いと合わせて決定する。

MVPでは複雑なUnsaved Changes Guardを必須としない。

---

## 28. Dialog Footer

Dialog FooterへActionを配置する。

基本形:

```text
[ キャンセル ] [ 登録 ]
```

Primary ActionとCancelの順序は他のDialogと統一する。

---

## 29. Skillとの関係

Skill Category登録時にSkillを同時登録しない。

責務は以下のように分離する。

```text
SkillCategoryCreateDialog
    ↓
Skill Category Master登録

SkillCreateDialog
    ↓
既存Skill Categoryを選択してSkill登録
```

Skill Category登録とSkill登録を1つのFormへ統合しない。

---

## 32. UI状態

### 32.1 Default

入力可能なSkill Category Formを表示する。

---

### 32.2 Submit Loading

登録Request実行中は以下を基本とする。

- Register Actionを再実行不可にする
- 入力内容を維持する
- 処理中であることを表示する
- Dialogを閉じない

---

### 32.3 Validation Error

対象Field付近へErrorを表示する。

Dialogを閉じない。

---

### 32.4 API Error

予期しないAPI Errorの場合もDialogを閉じない。

入力内容を維持し、再試行可能な状態とする。

---

### 32.5 Access Denied

登録権限がないユーザーには、スキルカテゴリ一覧上の登録Actionを表示しないことを基本とする。

登録Request時の最終認可はBackendを正とする。

---

## 33. Responsive

### 33.1 Desktop

Desktopでは中央配置のDialogを基本とする。

入力項目が少ないため、過度に大きなDialogにしない。

Formは1 Columnとする。

---

### 33.2 Tablet

Viewport内に収まるDialog幅を利用する。

Label・Description・Error Messageの可読性を維持する。

---

### 33.3 Mobile

Mobileでも操作の意味としてはSkillCategoryCreateDialogとして扱う。

Desktopの固定幅Dialogを単純に縮小しない。

以下を候補とする。

- Viewport幅を広く利用するDialog
- Full-screenに近いDialog
- Sheet / Drawer

具体方式は `09_レスポンシブ設計.md` を正とする。

Formは1 Columnとする。

---

## 34. Mobile Action

MobileではFooter Actionを縦配置してよい。

例:

```text
[ 登録             ]
[ キャンセル       ]
```

Primary Actionを識別しやすい構成を維持する。

---

## 35. Accessibility

以下を基本とする。

- Dialog Titleを支援技術から認識可能にする
- Dialog起動時に適切な要素へFocusを移動する
- Dialog表示中は背景へFocusを移動させない
- Dialog Close後は起動元のスキルカテゴリ登録ActionへFocusを戻す
- Form Controlに適切なLabelを設定する
- PlaceholderのみをLabelとして利用しない
- Required / Optionalを認識可能にする
- Validation Errorと対象Fieldを関連付ける
- Keyboardのみで入力・登録・キャンセルを操作可能にする
- Focus状態を視認可能にする
- Loading状態をVisualだけで表現しない
- Error MessageをTextで表示する

## 38. MVPで扱わないもの

現時点では以下をSkillCategoryCreateDialogの必須機能としない。

- Skill Categoryの無効化・再有効化
- 既存Skill Categoryの再有効化
- SkillのInline登録
- SkillのInline編集
- 複数Category一括登録
- CSV Import
- Category Icon設定
- Category Color設定
- Display Orderの手動設定
- Draft保存
- Auto Save
- DialogのURL同期

必要性が明確になった場合に別途検討する。

---

## 39. APIとの関係

Skill Category登録項目・Validation Rule・重複制約は既存Skill Category API仕様を正とする。

MVPの登録UIではCategory Nameを登録対象とし、Skill Categoryの状態変更操作は扱わない。

UI設計上必要な項目が既存APIと一致しない場合は、UI側だけで追加せずシステム設計との整合を確認する。

---

## 40. 本Dialogで定義しないもの

- Skill Category API Endpoint
- Request Bodyの具体型
- Form Library
- State管理方式
- Server / Client Component境界
- React Component分割
- API Client実装
- Query Cache更新方式
- Dialog Stateの具体実装
- Tailwind CSS Class
- Design Tokenの具体値
- Database Constraint実装
