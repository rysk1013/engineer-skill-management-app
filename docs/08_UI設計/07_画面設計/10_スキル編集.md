# スキル編集

## 1. 目的

スキル一覧から、既存Skill Masterの情報を編集するDialogとする。

本機能は独立画面ではなく、`/skills` 上の `SkillEditDialog` として扱う。

Skill NameやSkill Category等の更新可能項目を編集し、更新成功後はスキル一覧へ反映する。

Skillの無効化・再有効化は通常の情報編集とは分離し、必要に応じてAlert Dialogで扱う。

---

## 2. 対象ユーザー・権限

対象ユーザーは、Skill Masterの更新権限を持つ認証済みユーザーとする。

更新権限がないユーザーには、スキル一覧上の編集Actionを表示しないことを基本とする。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. UI種別

本機能は独立画面ではなくDialogとして扱う。

```text
/skills
   |
   | 編集
   v
SkillEditDialog
```

独立したFrontend Routeは持たない。

以下のRouteは設けない。

```text
/skills/[skillId]/edit
```

---

## 4. 起点

SkillEditDialogはスキル一覧からのみ開くことを基本とする。

起点:

```text
/skills
```

一覧上で編集対象Skillを指定してDialogを開く。

他画面から直接SkillEditDialogを開く導線は設けない。

---

## 5. 背景Context

Dialog表示中もスキル一覧のContextを維持する。

以下は変更しない。

- Current Route
- App Shell
- Header
- Sidebar
- Breadcrumb
- Page Header
- Search / Filter条件
- Pagination状態
- Skill一覧

Current Routeは以下のままとする。

```text
/skills
```

---

## 6. Breadcrumb

Dialogは独立Routeを持たないため、Breadcrumbを変更しない。

```text
Skills
```

現在実行中の編集操作はDialog Titleで表現する。

---

## 7. Dialog構成

基本構造は以下とする。

```text
SkillEditDialog
├── Dialog Header
│   ├── Title
│   └── Description
│
├── Dialog Content
│   └── Skill Form
│
└── Dialog Footer
    ├── Cancel
    └── Save
```

shadcn/uiの `Dialog` を基本候補とする。

---

## 8. Dialog Header

### 8.1 Title

```text
スキル編集
```

とする。

### 8.2 Description

必要に応じて編集対象Skillを識別できる補足を表示する。

例:

```text
Laravelのスキル情報を編集します。
```

Descriptionは必須としない。

---

## 9. 初期データ

Dialogを開く際は、スキル一覧ですでに取得済みのSkill情報を初期値として利用できる場合は再利用することを基本とする。

追加Data取得が必要な場合のみ、Dialog表示後に取得する。

```text
Skill List Data
      ↓
SkillEditDialog
      ↓
Form Initial Values
```

不要な再取得を前提としない。

ただし、更新時点の最新性を保証する必要がある場合は既存Frontend実装方針に従う。

---

## 10. 編集対象

Skill Masterで更新可能と定義されている項目を編集対象とする。

MVPでは主に以下を候補とする。

```text
Skill Name
Skill Category
```

具体的な更新可能項目は既存Skill Domain・API仕様を正とする。

UI設計側で更新可能項目を追加しない。

---

## 11. Skill Name

現在のSkill Nameを初期値として表示する。

例:

```text
スキル名
[ Laravel ]
```

入力Componentは `Input` を基本とする。

文字数・文字種・重複制約は既存Skill Domain・API仕様を正とする。

---

## 12. Skill Category

現在設定されているSkill Categoryを初期値として表示する。

例:

```text
カテゴリ
[ Framework ▼ ]
```

既存Skill Category Masterから選択する。

入力Componentは `Select` を基本候補とする。

---

## 13. Skill CategoryのInline編集

SkillEditDialogからSkill Category Master自体を登録・編集しない。

```text
SkillEditDialog
    ↓
既存Skill Categoryを選択
```

Skill Category Masterの管理は以下で行う。

```text
/skill-categories
```

---

## 14. Form構造

基本構造は以下とする。

```text
Skill Form
│
├── Skill Name
├── Skill Category
│
└── Actions
    ├── Cancel
    └── Save
```

入力項目が少ないため1 Columnを基本とする。

---

## 15. Form Field

各Fieldは以下の構造を基本とする。

```text
Label
Input / Select
Description
Error Message
```

必要な要素のみ表示する。

PlaceholderのみをLabelの代替として利用しない。

---

## 16. Active / Inactive状態

SkillのActive / Inactive変更は通常の情報編集とは分離することを基本とする。

SkillEditDialogではSkill Name・Category等の情報編集を担当する。

状態変更はスキル一覧上の別Actionとして扱う。

```text
SkillEditDialog
    ↓
情報編集

Skill List Action
    ↓
無効化 / 再有効化
```

状態変更の確認が必要な場合はAlert Dialogを利用する。

---

## 17. Inactive Skillの編集

Inactive Skillを編集できるかどうかは既存Skill Domain・API仕様を正とする。

編集可能な場合は、Inactive状態であることをDialog内または背景一覧から認識できるようにする。

例:

```text
Laravel
無効
```

UI側だけで編集可否Ruleを追加しない。

---

## 18. 重複

Skill Name等の重複可否は既存Skill Domain・Database Constraint・API仕様を正とする。

重複不可の場合はFrontendでも早期にFeedbackを提供してよいが、最終判定はBackendを正とする。

UI側だけで独自の重複判定Ruleを追加しない。

---

## 19. Validation

Validation RuleはBackend / Domain仕様を正とする。

Frontendでは入力ミスを早期に通知する補助Validationを行ってよいが、Backend Validationを代替しない。

主な候補:

- Skill Name必須
- Skill Category必須
- Skill Nameの文字数
- Skill Nameの重複制約

実際のRuleは既存仕様を正とする。

---

## 20. Validation Error

Validation Errorは対象Field付近へ表示する。

例:

```text
スキル名
[                    ]

スキル名を入力してください。
```

```text
カテゴリ
[ 選択してください ▼ ]

カテゴリを選択してください。
```

Validation Error発生時はDialogを閉じない。

入力内容を維持する。

---

## 21. 重複Error

Backendから重複Errorが返された場合は、対象Fieldとの関係が分かるFeedbackを表示する。

例:

```text
スキル名
[ Laravel ]

同じ名前のスキルがすでに登録されています。
```

Backend内部のError Messageをそのまま表示しない。

---

## 22. Dialog全体Error

Field単位で表現できないErrorはDialog内のForm全体Errorとして表示する。

例:

```text
スキルを更新できませんでした。
入力内容を確認してもう一度実行してください。
```

Error発生時はDialogを閉じない。

---

## 23. 保存Action

Primary Actionは以下を基本とする。

```text
保存
```

Application全体でより具体的なLabelを採用する場合は、

```text
変更を保存
```

としてよい。

最終Labelは他の編集Dialog・編集画面と統一する。

---

## 24. 更新処理

保存Action実行時はLaravel Backend APIへSkill更新Requestを送信する。

概念上:

```text
SkillEditDialog
      |
      | Update Skill
      v
Backend API
```

具体的なEndpoint・HTTP Method・Request Bodyは既存Skill API仕様を正とする。

---

## 25. 二重送信防止

更新処理中はPrimary Actionを再実行できない状態にする。

例:

```text
[ キャンセル ] [ 保存中... ]
```

処理中であることをVisualだけに依存せず認識可能にする。

---

## 26. 更新成功

更新成功後はDialogを閉じ、スキル一覧を最新状態へ更新する。

```text
/skills
   |
   | SkillEditDialog
   | 更新成功
   v
/skills
```

Route変更は発生しない。

対象Skillの最新情報を一覧へ反映する。

---

## 27. Search / Filterとの関係

更新成功後も、現在のSearch / Filter条件を維持することを基本とする。

変更内容によって対象Skillが現在の検索条件から外れる場合は、更新後に一覧から見えなくなる可能性がある。

例:

```text
Category = Framework
        ↓
Skill CategoryをCloudへ変更
        ↓
現在の一覧から対象Skillが除外される
```

これは検索条件に基づく自然な結果として扱う。

Success Feedbackを表示し、更新失敗と誤認されないようにする。

---

## 28. Paginationとの関係

更新成功後も現在のPagination Contextを維持することを基本とする。

更新によってSort順等が変化し、対象Skillの表示位置が変わる場合は一覧APIの結果を正とする。

UI側で対象Skillを現在Pageへ強制的に残さない。

---

## 29. Success Feedback

更新成功後、利用者が成功を認識できるFeedbackを提供してよい。

例:

```text
スキルを更新しました。
```

具体的なNotification方式は共通UI・UI状態設計に従う。

---

## 30. キャンセル

Cancel ActionではDialogを閉じる。

```text
/skills
   |
   | SkillEditDialog
   | Cancel
   v
/skills
```

Route変更は発生しない。

未保存の変更は破棄する。

---

## 31. Close操作

Dialog HeaderにClose Buttonを設ける場合は、Cancelと同じ意味として扱うことを基本とする。

Escape KeyまたはBackdrop ClickによるCloseを許可するかは、未保存入力の扱いと合わせて決定する。

MVPでは複雑なUnsaved Changes Guardを必須としない。

---

## 32. Dialog Footer

Dialog FooterへActionを配置する。

基本形:

```text
[ キャンセル ] [ 保存 ]
```

Primary ActionとCancelの順序は他のDialogと統一する。

---

## 33. Skill Category Master取得

Skill Category選択肢は既存Skill Category API等から取得する。

スキル一覧画面ですでに利用可能なCategory Dataが存在する場合は再利用してよい。

不要なAPI Requestを前提としない。

---

## 34. Skill Category取得中

Category取得が必要な場合は、Category Select等をLoading状態として表示する。

必要なMaster Dataを取得できるまで保存Actionを実行できない状態とする。

---

## 35. Skill Category取得失敗

Skill Category Master取得に失敗した場合は、更新不能な状態であることをDialog内に表示する。

例:

```text
スキルカテゴリを取得できませんでした。

[ 再試行 ]
```

必要なCategory情報を取得できない状態で保存を許可しない。

---

## 36. Inactive Category

InactiveなSkill Categoryの扱いは既存Domain仕様を正とする。

既存SkillがInactive Categoryを参照している場合は、現在値を識別可能に表示する必要がある。

例:

```text
カテゴリ
Framework
無効
```

新しいCategory選択先としてInactive Categoryを利用できない仕様である場合は、他のInactive Categoryを候補へ表示しないことを基本とする。

現在設定済みのInactive Categoryまで単純に非表示にし、現在値が判別できなくなる状態は避ける。

---

## 37. Resource Not Found

一覧表示後から編集実行までの間に対象Skillが存在しなくなった場合は、Backendの結果を正とする。

更新時にNot Foundが返された場合はDialogを閉じ、一覧を最新化することを候補とする。

必要に応じて以下のFeedbackを提供する。

```text
対象のスキルが見つかりませんでした。
一覧を更新しました。
```

具体的なError変換方針は `08_UI状態設計.md` を正とする。

---

## 38. Concurrent Update

同じSkillが別操作によって更新されていた場合の競合処理が既存仕様に存在する場合は、その仕様に従う。

UI側で独自の楽観Lock・競合Ruleを追加しない。

Backendから競合Errorが返された場合は、利用者が次の操作を理解できるFeedbackを提供する。

---

## 39. 利用中Skill

EmployeeSkillから参照されているSkillのName・Category変更可否は既存Domain仕様を正とする。

UI側だけで変更を禁止または許可しない。

変更によってEmployeeSkill履歴の意味が変わる可能性がある場合は、既存仕様上必要な確認・制約に従う。

---

## 42. UI状態

### 42.1 Default

現在のSkill情報を初期値としてFormへ表示する。

---

### 42.2 Master Loading

Skill Category Master等、編集に必要な追加Data取得中。

---

### 42.3 Submit Loading

更新Request実行中は以下を基本とする。

- Save Actionを再実行不可にする
- 入力内容を維持する
- 処理中であることを表示する
- Dialogを閉じない

---

### 42.4 Validation Error

対象Field付近へErrorを表示する。

Dialogを閉じない。

---

### 42.5 API Error

予期しないAPI Errorの場合もDialogを閉じない。

入力内容を維持し、再試行可能な状態とする。

---

### 42.6 Resource Not Found

対象Skillが存在しない。

一覧の最新化および適切なFeedbackを行う。

---

### 42.7 Access Denied

編集権限がないユーザーには編集Actionを表示しないことを基本とする。

更新Request時の最終認可はBackendを正とする。

---

## 43. Responsive

### 43.1 Desktop

Desktopでは中央配置のDialogを基本とする。

入力項目が少ないため、過度に大きなDialogにしない。

Formは1 Columnを基本とする。

---

### 43.2 Tablet

Viewport内に収まるDialog幅を利用する。

Label・Description・Error Messageの可読性を維持する。

---

### 43.3 Mobile

Mobileでも操作の意味としてはSkillEditDialogとして扱う。

Desktopの固定幅Dialogを単純に縮小しない。

以下を候補とする。

- Viewport幅を広く利用するDialog
- Full-screenに近いDialog
- Sheet / Drawer

具体方式は `09_レスポンシブ設計.md` を正とする。

Formは1 Columnとする。

---

## 44. Mobile Action

MobileではFooter Actionを縦配置してよい。

例:

```text
[ 保存             ]
[ キャンセル       ]
```

Primary Actionを識別しやすい構成を維持する。

---

## 45. Accessibility

以下を基本とする。

- Dialog Titleを支援技術から認識可能にする
- 編集対象Skillを識別可能にする
- Dialog起動時に適切な要素へFocusを移動する
- Dialog表示中は背景へFocusを移動させない
- Dialog Close後は起動元の編集ActionへFocusを戻す
- 各Form Controlに適切なLabelを設定する
- PlaceholderのみをLabelとして利用しない
- Validation Errorと対象Fieldを関連付ける
- Keyboardのみで全Fieldを操作可能にする
- Keyboardで保存・キャンセルを実行可能にする
- Focus状態を視認可能にする
- StatusをColorだけで表現しない
- Loading状態をVisualだけで表現しない
- Error MessageをTextで表示する

## 48. MVPで扱わないもの

現時点では以下をSkillEditDialogの必須機能としない。

- Skill CategoryのInline登録
- Skill CategoryのInline編集
- EmployeeSkill編集
- Skillの物理削除
- Bulk Edit
- Skill Icon編集
- Skill Color編集
- Display Order編集
- Auto Save
- Draft保存
- 高度なConcurrent Editing UI
- DialogのURL同期

必要性が明確になった場合に別途検討する。

---

## 49. APIとの関係

Skill更新項目・Validation Rule・重複制約・更新可能項目は既存Skill API仕様を正とする。

Skill Category選択肢は既存Skill Category API仕様を正とする。

UI設計上必要な操作が既存APIと一致しない場合は、UI側だけで仕様を追加せず、システム設計との整合を確認する。

---

- Query Cache更新方式
- Dialog Stateの具体実装
- Tailwind CSS Class
- Design Tokenの具体値
