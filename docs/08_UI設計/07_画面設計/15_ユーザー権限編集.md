# ユーザー権限編集

## 1. 目的

対象UserのRoleおよび権限管理可否を編集するための独立画面とする。

権限変更はApplication全体の認可に影響する操作であり、通常のMaster編集より重要度が高いため、Dialogではなく独立した作業Contextとして扱う。

---

## 2. 対象ユーザー・権限

対象ユーザーは、他Userの権限を管理できる認証済みユーザーとする。

権限編集Action自体は `/access-control` の一覧画面から提供する。

権限管理権限がないユーザーには編集Actionを表示しないことを基本とする。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. Route

```text
/access-control/[userId]/edit
```

とする。

一覧から対象Userを選択して遷移する。

```text
/access-control
        |
        | 権限編集
        v
/access-control/[userId]/edit
```

---

## 4. 画面種別

本機能は独立画面として扱う。

理由:

- Role変更を扱う
- `can_manage_permissions` を扱う
- Application全体の認可に影響する
- 最低1人の権限管理可能Administrator制約が存在する
- 誤操作時の影響が大きい
- Validation / Domain Errorを明確に説明する必要がある
- 対象Userと変更内容を十分確認できる作業Contextが必要

---

## 5. Breadcrumb

基本形は以下とする。

```text
Access Control > ユーザー名 > 権限編集
```

例:

```text
Access Control > 山田 太郎 > 権限編集
```

`Access Control` は `/access-control` へ戻る導線とする。

---

## 6. Page Header

基本構造は以下とする。

```text
ユーザー権限編集
山田 太郎

[ キャンセル ] [ 保存 ]
```

対象Userを明示し、誰の権限を変更しているか常に判別できる状態とする。

## 8. 対象User情報

編集対象Userを識別するため、必要な情報をReadonlyで表示する。

候補:

```text
User Name
Current Role
Current Permission Management Status
```

Employeeとの関連情報を表示する場合も、Access Control操作に必要な情報へ限定する。

User基本情報そのものは本画面で編集しない。

---

## 9. Role

既存UserRole仕様に従いRoleを編集する。

MVPで扱うRoleは以下とする。

```text
管理者
マネージャー
サブマネージャー
チームリーダー
```

具体的なEnum値・Labelは既存UserRole仕様を正とする。

---

## 10. Role入力

Roleの入力Componentは、選択肢数と操作性を考慮して `Select` を基本候補とする。

例:

```text
Role

[ 管理者 ▼ ]
```

Roleの意味が利用者に分かりにくい場合は補足Descriptionを表示してよい。

---

## 11. 一般社員

一般社員RoleはMVPでは利用しない。

そのため、Access ControlのRole選択肢には一般社員Roleを追加しない。

MVPで選択可能なRoleは以下の4種類とする。

```text
管理者
マネージャー
サブマネージャー
チームリーダー
```

将来利用する可能性だけを理由に、一般社員RoleをMVP UIへ追加しない。

一般社員Roleを将来導入する場合は、要件定義・Domain設計・Access Control API仕様を更新した上でUI設計へ反映する。

---

## 12. Permission Management

既存の `can_manage_permissions` を編集対象とする。

UI上では内部Property名をそのまま表示せず、利用者が理解できるLabelを使用する。

例:

```text
権限管理

[✓] 他ユーザーの権限を管理できる
```

または、

```text
権限管理
[ 有効 ▼ ]
```

具体的なComponentは操作性を考慮して決定する。

---

## 13. Permission Managementの適用条件

`can_manage_permissions` の利用条件は既存Domain仕様を正とする。

既存制約として、

```text
ADMINISTRATOR
&&
can_manage_permissions = true
```

を満たすUserを権限管理可能Administratorとして扱う。

`ADMINISTRATOR` 以外のRoleでは `can_manage_permissions=true` を許可しない。

UI上でもこの制約と矛盾する入力を防止する。

---

## 14. RoleとPermission Managementの連動

Roleを `ADMINISTRATOR` 以外へ変更した場合は、`can_manage_permissions` を有効な状態のまま保持しない。

例:

```text
Role: 管理者
権限管理: 有効
        |
        | Roleをマネージャーへ変更
        v
権限管理: 無効
```

具体的なValue Reset方法はFrontend実装時に決定する。

ただし、UI独自のDomain Ruleを追加せず、既存Domain仕様を正とする。

---

## 15. 最低1人制約

既存Domain Ruleとして、

```text
ADMINISTRATOR
&&
can_manage_permissions = true
```

を満たすUserを最低1人維持する。

この条件を満たすUserが最後の1人である場合、以下のような変更は許可しない。

- Administrator以外へのRole変更
- `can_manage_permissions=false` への変更
- その他、権限管理可能Administratorではなくなる変更

---

## 16. 最後の権限管理可能Administrator

対象Userが最後の権限管理可能Administratorである場合は、その事実を利用者が理解できるようにする。

例:

```text
このユーザーは現在、権限管理が可能な唯一の管理者です。

権限管理可能な管理者が0人になる変更はできません。
```

Warning / Alert等を利用して表示してよい。

---

## 17. 制約時の入力

最後の権限管理可能Administratorに対して、禁止される変更を以下のいずれかで扱う。

候補:

- 該当Optionを選択不可にする
- FieldをDisabledにする
- 入力は可能だが保存時にValidation Errorを表示する

Frontendで事前に判定可能な場合は、明らかに無効な操作を避けられるUIを優先する。

ただし、最終判定はBackendを正とする。

---

## 18. 制約理由

ActionやFieldをDisabledにする場合は、可能な限り理由を理解できるようにする。

例:

```text
権限管理を無効化できません。

権限管理可能な管理者を最低1人維持する必要があります。
```

Disabled状態だけで理由を伝えない。

---

## 19. 自分自身の権限

対象Userが現在ログイン中のUser自身である場合も、既存Access Control仕様に従う。

自分自身のRole・権限管理可否を変更できるかどうかは既存Domain / Authorization仕様を正とする。

UI側だけで独自に許可・禁止しない。

必要に応じて以下の補助表示を行ってよい。

```text
自分
```

---

## 20. 自分自身の権限低下

自身のRole・Permission変更によって、保存後にAccess Control画面へアクセスできなくなる可能性がある場合は、その影響を明確にする。

例:

```text
この変更を保存すると、権限管理機能を利用できなくなる可能性があります。
```

実際に確認UIが必要かどうかは既存Access Control仕様と操作性に基づいて決定する。

## 22. Form Field

各編集Fieldは以下の構造を基本とする。

```text
Label
Control
Description
Error Message
```

権限の意味や影響を理解するために必要なDescriptionは省略しすぎない。

---

## 23. Validation

Validation RuleはBackend / Domain仕様を正とする。

Frontendでは利用者が無効な設定を早期に把握できるよう補助Validationを行ってよい。

主な対象:

- Role必須
- Roleと `can_manage_permissions` の整合性
- 最低1人の権限管理可能Administrator制約
- 対象Userに対する変更権限
- 自己権限変更制約

Backend ValidationをFrontendで代替しない。

---

## 24. Field Validation Error

Field単位で表現できるErrorは対象Field付近へ表示する。

例:

```text
Role
[ マネージャー ▼ ]

このRoleでは権限管理を有効にできません。
```

---

## 25. Domain Error

最低1人制約等、複数FieldにまたがるDomain ErrorはForm全体で表示する。

例:

```text
この変更は保存できません。

権限管理可能な管理者を最低1人維持する必要があります。
```

Error原因と利用者が取るべき対応を理解できる文言とする。

---

## 26. 保存Action

Primary Actionは以下を基本とする。

```text
保存
```

またはApplication全体の方針に応じて、

```text
変更を保存
```

とする。

---

## 27. 変更内容確認

権限変更は影響が大きいため、保存前に確認が必要な変更についてはAlert Dialogを利用してよい。

特に以下を候補とする。

- Administratorから他Roleへの変更
- `can_manage_permissions` の無効化
- 自身の権限低下
- 権限範囲が大きく変化する操作

すべての変更で一律に確認Dialogを出すことは必須としない。

---

## 28. 確認Dialog

確認が必要な場合の概念構造:

```text
Access Control Form
        |
        | Save
        v
Alert Dialog
        |
        | Confirm
        v
Backend API
```

例:

```text
ユーザー権限を変更しますか？

山田 太郎

Role:
管理者 → マネージャー

権限管理:
有効 → 無効

[ キャンセル ] [ 変更する ]
```

変更内容を確認できる表現を優先する。

---

## 29. 保存処理

保存Action実行時はLaravel Backend APIへ権限更新Requestを送信する。

概念上:

```text
Access Control Edit Page
        |
        | Update Permissions
        v
Backend API
```

具体的なEndpoint・HTTP Method・Request Bodyは既存Access Control API仕様を正とする。

---

## 30. 二重送信防止

保存処理中はPrimary Actionを再実行できない状態にする。

例:

```text
[ キャンセル ] [ 保存中... ]
```

処理中であることをVisualだけに依存せず認識可能にする。

---

## 31. 保存成功

保存成功後は `/access-control` へ戻る。

```text
/access-control/[userId]/edit
        |
        | 保存成功
        v
/access-control
```

一覧では更新後のRole・Permission状態を表示する。

---

## 32. Success Feedback

保存成功後、利用者が成功を認識できるFeedbackを提供してよい。

例:

```text
ユーザー権限を更新しました。
```

具体的なNotification方式は共通UI・UI状態設計に従う。

---

## 33. 保存後に権限を失う場合

自身の権限変更によって `/access-control` への参照権限を失った場合は、保存成功後の遷移先を既存認可仕様に従って決定する。

例:

```text
保存成功
   ↓
/access-control への権限なし
   ↓
/forbidden または許可された画面
```

Frontendだけで遷移先Ruleを独自定義しない。

---

## 34. キャンセル

Cancel Actionでは変更を保存せず `/access-control` へ戻る。

```text
/access-control/[userId]/edit
        |
        | Cancel
        v
/access-control
```

未保存の変更は破棄する。

---

## 35. 未保存変更

MVPでは複雑なUnsaved Changes Guardを必須としない。

ただし、権限変更は影響が大きいため、誤操作による変更破棄が問題となる場合は離脱確認を検討してよい。

例:

```text
権限設定の変更が保存されていません。

この画面を離れますか？
```

---

## 36. Resource Not Found

対象Userが存在しない場合はNot Foundとして扱う。

```text
/access-control/[userId]/edit
        ↓
User Not Found
        ↓
Not Found
```

具体的なNot Found UIは共通UI状態設計に従う。

---

## 37. 更新時Resource Not Found

画面表示後から保存までの間に対象Userが存在しなくなった場合は、Backend結果を正とする。

更新時にNot Foundが返された場合は、適切なFeedbackを表示したうえで一覧等へ戻すことを候補とする。

---

## 38. Access Denied

対象画面へのアクセス権限がない場合はAccess Deniedとして扱う。

例:

```text
/forbidden
```

または既存Access Control方針に従った共通UIを利用する。

最終認可はBackendを正とする。

---

## 39. 更新時Access Denied

画面表示後に権限状態が変更され、保存時にAccess Deniedとなる可能性も考慮する。

その場合はBackend結果を正とし、入力内容を安全に扱いつつ適切なFeedbackまたは遷移を行う。

---

## 40. Concurrent Update

同じUserの権限が別操作によって更新された場合の競合処理が既存仕様に存在する場合は、その仕様に従う。

UI側で独自の楽観Lock・Version Ruleを追加しない。

Backendから競合Errorが返された場合は、利用者が次の操作を理解できるFeedbackを提供する。

---

## 41. 権限制約の再評価

画面表示時点では変更可能でも、保存時には他Userの権限変更によって最低1人制約等の判定結果が変化している可能性がある。

そのため、Frontendで保存可能と表示されていてもBackend側で必ずDomain Ruleを再評価する。

Frontend表示だけを整合性保証として扱わない。

---

## 47. Accessibility

以下を基本とする。

- Page Titleを明確にする
- 編集対象Userを認識可能にする
- Role Selectへ適切なLabelを設定する
- Permission Management Controlへ明確なAccessible Nameを設定する
- Constraint / WarningをTextで提供する
- Errorと対象Fieldを関連付ける
- Keyboardのみで全操作を実行可能にする
- Focus状態を視認可能にする
- Disabled状態の理由を理解可能にする
- RoleやPermission状態をColorだけで表現しない
- Loading状態をVisualだけで表現しない
- Alert Dialog利用時はFocus Managementを適切に行う
- 保存後の遷移でFocus Contextが破綻しないようにする

## 50. MVPで扱わないもの

現時点では以下を本画面の必須機能としない。

- 一般社員Role
- Permission Definition自体の編集
- Role Definition自体の編集
- 複数Userの一括権限変更
- Fine-Grained Permission Matrix
- Resource単位Permission設定
- Temporary Permission
- Permission Expiration
- Approval Workflow
- 権限変更理由の入力
- 権限変更履歴の詳細表示
- Auto Save

必要性が明確になった場合に別途検討する。

---

## 51. APIとの関係

User Role・`can_manage_permissions`・権限更新・Validation・Domain制約の仕様は既存Access Control APIを正とする。

MVPで利用するRoleは、管理者・マネージャー・サブマネージャー・チームリーダーとする。

一般社員RoleはMVPのRole選択肢として扱わない。

最低1人の権限管理可能Administrator制約はBackend / Domainで必ず保証する。

UI上で必要な操作が既存APIと一致しない場合は、UI側だけで仕様を追加せず、システム設計との整合を確認する。

---

## 52. 本画面で定義しないもの

以下は既存仕様またはFrontend実装の責務とする。

- Access Control API Endpoint
- Update RequestのHTTP Method
- Request / Responseの具体型
- Backend Policy実装
- Domain Service実装
- Form Library
- State管理方式
- Server / Client Component境界
- React Component分割
- API Client実装
- Query Cache更新方式
- Tailwind CSS Class
- Design Tokenの具体値
- Concurrent Update実装
