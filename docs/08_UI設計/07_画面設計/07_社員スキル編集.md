# 社員スキル編集

## 1. 目的

社員ごとのEmployeeSkillを追加・編集するための独立画面とする。

Employee基本情報の編集とは責務を分離し、社員が保有するSkill・Skill Level・実務経験・経験期間・最終利用時期等を管理する。

複数のEmployeeSkillを継続的に編集する操作Contextを持つため、Dialogではなく独立画面として扱う。

---

## 2. 対象ユーザー・権限

対象ユーザーは、EmployeeSkillの更新権限を持つ認証済みユーザーとする。

社員スキル編集権限がないユーザーには、社員詳細上の社員スキル編集Actionを表示しないことを基本とする。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. Route

```text
/employees/[employeeId]/skills
```

とする。

社員詳細から遷移する。

```text
/employees/[employeeId]
        |
        | 社員スキル編集
        v
/employees/[employeeId]/skills
```

---

## 4. 画面種別

本機能は独立画面として扱う。

理由:

- 複数のEmployeeSkillを扱う
- Skillごとに複数の入力項目が存在する
- 追加・編集を繰り返す可能性がある
- Employee基本情報編集とは異なるResourceを扱う
- Dialogでは操作領域が不足しやすい
- Mobileでも独立した作業Contextを維持した方が操作しやすい

---

## 5. Breadcrumb

基本形は以下とする。

```text
Employees > 社員名 > スキル編集
```

例:

```text
Employees > 山田 太郎 > スキル編集
```

`Employees` は社員一覧へ、社員名は社員詳細へ戻る導線とする。

---

## 6. Page Header

基本構造:

```text
社員スキル編集
山田 太郎

[ キャンセル ] [ 保存 ]
```

またはActionをPage下部にまとめる構成としてもよい。

社員名を明示し、誰のSkillを編集しているか判別できる状態とする。

---

## 7. 画面構成

基本構造は以下とする。


## 8. Employee基本情報

本画面ではEmployee基本情報を編集しない。

必要に応じて対象社員を識別するために以下の情報をReadonlyで表示してよい。

例:

```text
社員名
所属
在籍状態
```

ただし、表示項目を増やしすぎず、EmployeeSkill編集に必要なContextに限定する。

Employee基本情報の変更は `EmployeeEditDialog` で行う。

---

## 9. EmployeeSkill一覧

現在登録されているEmployeeSkillを一覧形式で表示する。

各EmployeeSkillについて、必要な編集Fieldをまとめて表示する。

概念上:

```text
Skill
├── Skill
├── Work Experience
├── Skill Level
├── Experience Period
├── Last Used
└── Remove / Disable Action
```

具体的な項目は既存EmployeeSkill Domain・API仕様を正とする。

---

## 10. Skill選択

EmployeeSkillに登録するSkillは、既存Skill Masterから選択する。

自由入力によるSkill登録は行わない。

Masterに存在しないSkillを登録する必要がある場合は、既存仕様に従って管理者がSkill Masterへ追加した後に選択する。

---

## 11. Skillの重複

同一社員に同一Skillを重複登録できない。

すでに登録済みのSkillは、新規追加時の選択候補から除外することを基本とする。

Frontendでも重複を防止するが、最終的な一意性はBackend / Database Constraintを正とする。

---

## 12. Skill Level

Skill Levelは既存仕様に従い、

```text
Level 1
Level 2
Level 3
Level 4
Level 5
```

を扱う。

具体的なLabelや説明は既存Skill Level仕様を正とする。

UI側で独自のLevelを追加しない。

---

## 13. Work Experience

EmployeeSkillごとに実務経験の有無を管理する。

概念上:

```text
実務経験

○ あり
○ 未経験
```

または既存Enum表現に応じたSelect等を利用する。

UI上の文言は利用者が意味を理解しやすい表現とする。

---

## 14. 未経験の場合

未経験の場合は既存仕様に従い、Skill Levelは `Level 1` のみ選択可能とする。

概念上:

```text
実務経験: 未経験
        ↓
Skill Level: Level 1
```

Level 2〜5を選択できない状態とする。

既にLevel 2〜5が選択されている状態で実務経験を未経験へ変更する場合は、入力値の整合性を保つ。

具体的なValue Reset方法はFrontend実装時に決定する。

---

## 15. 実務経験ありの場合

実務経験ありの場合は、既存仕様に従って以下を入力する。

- Skill Level
- 経験期間
- 最終利用時期

実務経験ありでは、経験期間1か月以上を必須とする。

最終利用時期も必須とする。

---

## 16. 経験期間

実務経験ありの場合、経験期間を入力する。

最低1か月以上を必須とする。

具体的な入力形式は既存EmployeeSkill API・Domain仕様を正とする。

候補:

- 年 / 月を分けて入力
- 月数で入力
- Duration入力Component

UI設計だけでDomain上の保持形式を決定しない。

利用者が経験期間を直感的に入力できる形式を選択する。

---

## 17. 最終利用時期

実務経験ありの場合、最終利用時期を必須とする。

未経験の場合は設定しない。

概念上:

```text
実務経験あり
    ↓
最終利用時期: 必須

未経験
    ↓
最終利用時期: 未設定
```

未経験へ変更した際に既存の最終利用時期が存在する場合は、Domain Ruleに従って値を解除する。

---

## 18. 条件付きField

Work Experienceの選択によって表示・入力可能なFieldを切り替える。

例:

```text
実務経験: あり
├── Skill Level
├── 経験期間
└── 最終利用時期
```

```text
実務経験: 未経験
└── Skill Level: Level 1
```

不要なFieldを表示したままDisabledにするより、意味上不要な場合は非表示にすることを基本とする。

ただし、入力値変更による状態遷移が分かりにくくならないよう配慮する。

---

## 19. EmployeeSkill追加

新しいEmployeeSkillを追加するActionを提供する。

例:

```text
[ スキルを追加 ]
```

Action実行後、新しいEmployeeSkill入力領域を追加する。

独立Dialogを重ねることは基本としない。

---

## 20. 追加時の初期状態

新しいEmployeeSkill追加時は、未入力状態として追加する。

例:

```text
Skill: 未選択
Work Experience: 未選択
Skill Level: 未選択
```

Domain側で明確な初期値が定義されている場合はその仕様を正とする。

UI都合だけでDomain値を自動設定しない。

---

## 21. EmployeeSkill削除

既存EmployeeSkillには削除Actionを配置する。

例:

```text
[ 削除 ]
```

削除は破壊的操作として扱い、実行前に `Alert Dialog` で確認する。

---

## 22. 削除確認

削除前に以下の確認を行う。

```text
この社員スキルを削除しますか？

Skill: Laravel

この操作は元に戻せません。

[ キャンセル ] [ 削除 ]
```

実際に論理削除・物理削除のどちらを採用するかは既存EmployeeSkill仕様を正とする。

UI側で削除方式を決定しない。

---

## 23. 削除成功

削除成功後は社員詳細へ戻る。

```text
/employees/[employeeId]/skills
        ↓
     削除成功
        ↓
/employees/[employeeId]
```

削除成功後、利用者が成功を認識できるFeedbackを提供してよい。

削除失敗時は現在の編集画面を維持し、既存のOperation Error方針に従って再試行可能な状態とする。

---

## 24. 無効化との区別

Skill Master自体の無効化と、EmployeeSkillの削除・解除を混同しない。

```text
Skill Master
    ↓
SkillそのもののActive / Inactive

EmployeeSkill
    ↓
EmployeeとSkillの関連
```

EmployeeSkill画面からSkill MasterのActive状態を変更しない。

---

## 25. 無効化済みSkill

既存EmployeeSkillが無効化済みSkillを参照している場合の表示は、既存仕様に従う。

基本的には履歴情報を失わないよう、登録済みEmployeeSkillとして識別可能に表示する。

例:

```text
Laravel
無効
```

新規追加候補には無効化済みSkillを表示しないことを基本とする。

---

## 26. 表示方式

Desktopでは、EmployeeSkillごとの情報量に応じて以下を候補とする。

- Table
- Card / Section List
- TableとInline Formの組み合わせ

単純なRead-only Tableではなく複数Field編集を伴うため、操作性を優先する。

Phase 1では特定Componentへ固定せず、Wireframe上はSection形式を基本とする。

## 28. Validation

Validation RuleはBackend / Domain仕様を正とする。

Frontendでは利用者が入力ミスを早期に把握できる範囲でValidationを行ってよいが、Backend Validationを代替しない。

主なRuleとして以下をUI上でも表現する。

- Skill必須
- Skill重複不可
- Work Experience必須
- Skill Level必須
- 未経験はLevel 1のみ
- 実務経験ありは経験期間1か月以上
- 実務経験ありは最終利用時期必須
- 未経験は最終利用時期未設定

---

## 29. Validation Error

Errorは対象EmployeeSkill・対象Fieldの近くへ表示する。

例:

```text
経験期間
[ 0年 ] [ 0か月 ]

実務経験がある場合は1か月以上を入力してください。
```

複数EmployeeSkillでErrorが存在する場合でも、どのSkillのどのFieldに問題があるか判別可能にする。

---

## 30. Page全体Error

Field単位で表現できないErrorはPage上部またはAction付近に表示する。

例:

```text
社員スキルを保存できませんでした。
入力内容を確認してもう一度実行してください。
```

技術的なBackend Error Messageをそのまま表示しない。

---

## 31. 保存Action

Primary Actionは以下を基本とする。

```text
保存
```

複数EmployeeSkillの変更をまとめて保存するUIとする場合は、すべての変更内容を1つの保存Actionで反映する。

具体的なAPI Mutation単位は既存API仕様を正とする。

---

## 32. 保存処理

概念上は以下とする。

```text
Employee Skill Edit Page
        |
        | Save
        v
Backend API
```

追加・更新・削除が複数存在する場合のRequest構造・Transaction単位はBackend設計を正とする。

UI側で独自のTransaction Ruleを定義しない。

---

## 33. 二重送信防止

保存処理中はPrimary Actionを再実行できない状態にする。

例:

```text
[ キャンセル ] [ 保存中... ]
```

処理中であることを認識可能にする。

---

## 34. 保存成功

保存成功後は社員詳細へ戻る。

```text
/employees/[employeeId]/skills
        |
        | 保存成功
        v
/employees/[employeeId]
```

社員詳細では最新のEmployeeSkill情報を表示する。

---

## 35. Success Feedback

保存成功後、利用者が成功を認識できるFeedbackを提供してよい。

例:

```text
社員スキルを更新しました。
```

具体的なNotification方式は共通UI・UI状態設計に従う。

---

## 36. キャンセル

Cancel Actionでは社員詳細へ戻る。

```text
/employees/[employeeId]/skills
        |
        | Cancel
        v
/employees/[employeeId]
```

未保存の変更は破棄する。

---

## 37. 未保存変更

MVPでは複雑なUnsaved Changes Guardを必須としない。

ただし、複数EmployeeSkillを編集する画面であるため、誤操作による変更破棄の影響が大きい場合は確認UIを検討してよい。

例:

```text
変更内容が保存されていません。

この画面を離れますか？
```

Phase 1では必須仕様とせず、実装時の操作性確認対象とする。

## 40. UI状態

### 40.1 Loading

初回Data取得中はPage構造を維持しつつSkeleton等を表示する。

対象:

- Employee
- EmployeeSkill一覧
- Skill Master

---

### 40.2 Default

EmployeeSkill一覧を編集可能な状態で表示する。

---

### 40.3 Empty

EmployeeSkillが1件も登録されていない場合はEmpty Stateを表示する。

例:

```text
登録されているスキルはありません。

[ スキルを追加 ]
```

編集権限がない場合はActionを表示しない。

---

### 40.4 Submit Loading

保存中は以下を基本とする。

- Save Action再実行不可
- 入力内容維持
- Loading状態明示
- 不要な追加操作を抑制

---

### 40.5 Validation Error

対象Field付近へErrorを表示する。

入力内容を維持する。

---

### 40.6 API Error

予期しないAPI Errorの場合はPageを維持する。

入力内容を可能な限り保持し、再試行可能な状態とする。

---

### 40.7 Resource Not Found

対象Employeeが存在しない場合はNot Foundとして扱う。

EmployeeSkillのみのResource Not FoundについてはAPI仕様に従い、Page全体または該当項目単位で処理する。

---

### 40.8 Access Denied

編集権限がない場合は、既存Access Control方針に従う。

直接Routeへアクセスした場合の最終認可はBackendを正とする。

---

## 41. Skill Master取得失敗

Skill選択に必要なMaster Data取得に失敗した場合は、EmployeeSkill追加・編集を安全に行えないため、その状態を明示する。

例:

```text
スキル情報を取得できませんでした。

[ 再試行 ]
```

必要なMaster Dataが取得できない状態で新規Skill追加を許可しない。

## 44. Accessibility

以下を基本とする。

- Page Titleを明確にする
- 対象社員名を認識可能にする
- 各EmployeeSkillの境界をSemanticに表現する
- 各Form ControlにLabelを関連付ける
- SkillごとのValidation Errorを対象Fieldへ関連付ける
- KeyboardのみでSkill追加・編集・削除を操作可能にする
- Focus状態を視認可能にする
- Select等のAccessible Nameを明確にする
- ErrorをColorだけで表現しない
- Level制約をDisabled表示だけに依存せず説明可能にする
- Loading状態をVisualだけで表現しない
- 削除確認DialogのFocus Managementを適切に行う

同一Labelが複数EmployeeSkillで繰り返されるため、支援技術上どのSkillのFieldか識別可能にする。

## 47. MVPで扱わないもの

現時点では以下を本画面の必須機能としない。

- Skill MasterのInline登録
- Skill MasterのInline編集
- Skill Category編集
- Skill Level定義の変更
- Employee基本情報編集
- CSV Import
- Bulk EmployeeSkill Import
- Drag & Dropによる並び替え
- Skill表示順のユーザー任意設定
- Auto Save
- Draft保存
- 高度な変更履歴
- 複雑なConcurrent Editing UI

必要性が明確になった場合に別途検討する。

## 48. APIとの関係

EmployeeSkillの登録・更新・削除・Validation Ruleは既存EmployeeSkill API仕様を正とする。

UI設計上必要な操作が既存APIと一致しない場合は、UI側だけで仕様を追加せず、システム設計との整合を確認する。

Skill Master取得についても既存Skill API仕様を正とする。

---

## 49. 本画面で定義しないもの

以下は既存仕様またはFrontend実装の責務とする。

- EmployeeSkill API Endpoint
- Request / Responseの具体型
- 複数EmployeeSkill更新時のAPI構造
- Backend Transaction実装
- Form Library
- State管理方式
- Server / Client Component境界
- React Component分割
- API Client実装
- Query Cache更新方式
- Tailwind CSS Class
- Design Tokenの具体値
- EmployeeSkill Repository実装
- Database Constraint実装
