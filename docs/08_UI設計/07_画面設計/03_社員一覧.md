# 社員一覧

## 1. 目的

社員情報を一覧で確認し、検索・絞り込みを行いながら対象社員を特定できる画面とする。

社員詳細・社員登録・社員編集等の社員管理機能への入口として利用する。

---

## 2. 対象ユーザー・権限

対象ユーザーは、社員情報を閲覧可能な認証済みユーザーとする。

社員登録・編集等のActionはRole / Permissionに応じて表示を制御する。

Frontend上の表示制御はUI制御として扱い、最終的な認可はBackendを正とする。

---

## 3. Route

```text
/employees
```

基本構造は以下とする。


Wireframe上は以下を基本とする。

```text
Employees

[ Keyword Search ] [ Filter ]

+----------------------------------------------------------+
| 氏名 | 所属 | 在籍状態 | ... | Action                 |
+----------------------------------------------------------+
| ...                                                      |
+----------------------------------------------------------+

                         Pagination
```

---

## 5. Breadcrumb

社員一覧は社員管理機能の起点となるため、Breadcrumbは以下を基本とする。

```text
Employees
```

App Shell上のNavigationで現在位置が十分に明確な場合は、UI全体の一貫性を確認した上で省略可能とする。

---

## 6. Page Header

### 6.1 Title

```text
社員一覧
```

とする。

---

### 6.2 Description

必要に応じて以下のような補足を表示する。

```text
社員情報を検索・確認できます。
```

Descriptionは必須としない。

---

### 6.3 Primary Action

社員登録権限がある場合は、

```text
社員登録
```

Actionを表示する。

実行時は社員一覧のContextを維持したまま、社員登録Dialogを開く。

```text
/employees
    ↓
社員登録Dialog
```

Frontend Routeは `/employees` のままとする。

権限がない場合はActionを表示しないことを基本とする。

---

## 7. 一覧表示項目

一覧では、社員を識別・選択するために必要な情報を優先して表示する。

基本候補は以下とする。

- 氏名
- 所属情報
- 在籍状態
- Action

必要に応じて、既存要件・Employee APIで提供される情報から補助項目を追加する。

一覧で判断する必要のない詳細情報は表示せず、社員詳細画面へ分離する。

---

## 8. 氏名

社員を識別するPrimary Informationとして表示する。

氏名から社員詳細へ遷移できる構成を基本とする。

```text
社員名
  ↓
/employees/[employeeId]
```

Row全体をClick可能にするか、氏名をLinkとするかは、Table内のAction構成を踏まえて個別実装時に決定する。

操作の曖昧さが少ない構成を優先する。

---

## 9. 所属情報

既存Employee仕様で保持する所属情報を表示する。

表示項目・表記は既存のDepartment仕様を正とする。

UI設計側で新しい所属概念を追加しない。

---

## 10. 在籍状態

社員の在籍状態を `StatusBadge` で表示することを基本とする。

例:

```text
在籍
退職
```

Domain上のEmployment Statusと表示Labelを対応させる。

色だけに依存せず、必ずTextを表示する。

---

## 11. Search

### 11.1 目的

社員をKeywordで検索できるようにする。

既存Employee APIの検索仕様を正とする。

UI側だけで検索対象項目を拡張しない。

---

### 11.2 基本構造

```text
[ Keyword Search ]
```

検索対象の具体的なFieldはAPI仕様に従う。

---

### 11.3 操作

検索実行後は検索条件を維持した状態で一覧を更新する。

Pagination中に検索条件を変更した場合は、原則として先頭Pageへ戻す。

---

## 12. Filter

Filterは既存Employee APIで利用可能な条件を対象とする。

候補:

- 在籍状態
- 所属

実際に採用するFilterはAPI仕様を確認して決定する。

UIだけでBackend未対応のFilterを追加しない。

---

## 13. Search / Filter領域

Application共通の `SearchFilter` Patternを利用する。

基本構造:

```text
SearchFilter
├── Keyword Search
├── Filter
└── Clear
```

条件が単純な場合は過度に複雑なFilter UIを導入しない。

---

## 14. Clear

検索・Filter条件を初期状態へ戻すActionを必要に応じて提供する。

Clear実行後は一覧の先頭Pageへ戻すことを基本とする。

条件が設定されていない状態では、Clear Actionを無効化または非表示にしてよい。

---

## 15. Employee Table

Application共通の `DataTable` Patternを利用する。

shadcn/ui Tableを基盤とし、SemanticなHTML Tableを維持する。

基本構造:

```text
Table
├── Header
├── Employee Row
│   ├── 氏名
│   ├── 所属
│   ├── 在籍状態
│   └── Action
└── ...
```

---

## 16. Row Action

社員ごとのActionは必要最小限とする。

基本候補:

- 詳細
- 編集

詳細画面が存在するため、一覧上で大量の社員操作を提供しない。

編集Actionを一覧へ直接配置する場合は権限制御を行う。

MVPでは、

```text
一覧
  ↓
詳細
  ↓
編集
```

を基本フローとするため、一覧上の編集Actionは必須としない。

---

## 17. 社員詳細への遷移

対象社員を選択すると以下へ遷移する。

```text
/employees/[employeeId]
```

一覧画面の主な目的は対象社員を見つけ、詳細へ遷移することとする。

---

## 18. Pagination

一覧データは既存APIのPagination仕様に従う。

Application共通のPagination Componentを利用する。

最低限、以下を操作可能とする。

- 前Page
- 次Page
- 現在Pageの確認

総件数・Page番号一覧等はAPI仕様と必要性を踏まえて表示する。

---

## 19. Sort

Sortは既存Employee APIで対応している項目のみ対象とする。

UI設計だけでSort機能を追加しない。

MVP APIにSortが不要または未提供の場合は、Table HeaderをClick可能にしない。

---

## 20. Query State

Search / Filter / Pagination等、一覧状態をURL Query Parameterで保持できる構成を基本候補とする。

例:

```text
/employees?keyword=xxx&page=2
```

具体的なQuery Parameter名は既存Frontend / API仕様を正とする。

これにより以下を実現しやすくする。

- Browser Backで一覧状態へ戻る
- URL共有
- Reload後の条件維持

実装方式はFrontend設計に従う。

---

## 21. 社員詳細から戻る場合

社員詳細から一覧へ戻った場合、可能な範囲で元の一覧状態を維持することを基本とする。

対象:

- Search
- Filter
- Page

具体的なState管理方法はFrontend実装時に決定する。

## 23. UI状態

### 23.1 Default

検索条件に一致する社員一覧を表示する。

---

### 23.2 Initial Loading

初回Data取得中は、共通Layout・Page Header・Search領域を可能な限り維持する。

Table部分ではSkeleton等を利用する。

```text
社員一覧                              [ 社員登録 ]

[ Search ] [ Filter ]

+----------------------------------------------------------+
| ██████████████████████████████████████████████████████ |
| ██████████████████████████████████████████████████████ |
| ██████████████████████████████████████████████████████ |
+----------------------------------------------------------+
```

---

### 23.3 Search / Filter Loading

検索条件変更後に再取得する場合も、一覧領域を対象にLoading状態を表示する。

Page全体を空白へ変更しない。

---

### 23.4 Empty

社員が1件も存在しない場合と、検索結果が0件の場合を区別する。

#### 社員データ自体が存在しない場合

例:

```text
登録されている社員がありません。
```

社員登録権限がある場合:

```text
[ 社員を登録 ]
```

を表示してよい。

#### Search / Filter結果が0件の場合

例:

```text
条件に一致する社員が見つかりませんでした。

検索条件を変更してください。
```

この場合、社員登録Actionを主要Actionとして表示しない。

---

### 23.5 Error

一覧取得に失敗した場合は `ErrorState` を利用する。

例:

```text
社員情報を取得できませんでした。

[ 再試行 ]
```

Navigation・Page Headerは維持する。

---

## 24. 権限制御

### 24.1 閲覧

社員一覧を閲覧可能な権限がない場合は、本画面へアクセスさせない。

直接Routeへアクセスした場合は既存のAccess Denied方針に従う。

---

### 24.2 登録

社員登録権限がない場合は、

```text
社員登録
```

Primary Actionを表示しないことを基本とする。

---

### 24.3 編集

編集Actionを一覧へ表示する場合は、社員更新権限に応じて表示制御する。

---

## 25. Responsive

### 25.1 Desktop

DesktopではTable形式を基本とする。

```text
+----------------------------------------------------------+
| 氏名       | 所属       | 在籍状態 | Action            |
+----------------------------------------------------------+
| 山田 太郎  | 開発部     | 在籍     | ...               |
+----------------------------------------------------------+
```

Search / FilterをPage Header下へ配置する。

---

### 25.2 Tablet

表示可能な横幅に応じてColumn数を調整する。

重要度の低い補助情報が存在する場合は省略を検討する。

主要情報:

- 氏名
- 所属
- 在籍状態

は可能な限り維持する。

---

### 25.3 Mobile

Desktop Tableを単純に縮小しない。

以下を候補とする。

1. Tableの横スクロール
2. Column削減
3. Employee RowをCard形式へ変更

社員一覧は1件あたりの情報量が比較的少ないため、MobileではCard形式も有力候補とする。

例:

```text
+----------------------------+
| 山田 太郎                  |
| 開発部                     |
| 在籍                       |
|                            |
| 詳細 >                     |
+----------------------------+
```

最終方式は `09_レスポンシブ設計.md` で統一する。

---

## 26. Accessibility

以下を基本とする。

- TableにはSemanticな `table` / `thead` / `tbody` / `th` / `td` を利用する
- Search InputへLabelまたはAccessible Nameを提供する
- Filter Controlへ適切なLabelを設定する
- StatusをColorだけで表現しない
- Employee DetailへのLinkをKeyboardで操作可能にする
- PaginationをKeyboardで操作可能にする
- Current Pageを識別可能にする
- Loading状態をVisualだけに依存させない
- Empty / Error MessageをTextで表示する
- Focus Ringを維持する

## 29. MVPで扱わないもの

現時点では以下を社員一覧の必須機能としない。

- Bulk Selection
- Bulk Update
- Bulk Delete
- Drag & Drop
- Column並び替え
- Column表示カスタマイズ
- Saved Search
- Export
- Inline Edit
- Infinite Scroll
- Advanced Data Grid

必要性が明確になった場合に別途検討する。

---

## 30. APIとの関係

一覧表示・Search・Filter・Pagination・Sortは、既存Employee API仕様を正とする。

UI設計側でBackend未対応のQuery機能を暗黙的に追加しない。

画面詳細設計で必要となる情報が既存APIから取得できない場合は、UI側だけで仮定せずシステム設計との整合を確認する。

---

## 31. 本画面で定義しないもの

以下は既存仕様またはFrontend実装の責務とする。

- Employee API Endpoint
- Query Parameterの具体名
- Page Size
- Sortの具体仕様
- State管理方式
- Server / Client Component境界
- React Component分割
- API Client実装
