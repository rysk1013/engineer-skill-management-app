# 共通レイアウト

## 1. 目的

本ドキュメントは、Engineer Skill Management App のMVPにおける共通レイアウトを定義する。

各画面で共通して利用する以下の構造・配置・表示方針を整理し、画面ごとのレイアウト差異を最小限にする。

- App Shell
- Header
- Sidebar
- Main Content
- Breadcrumb
- Page Header
- 一覧画面Layout
- 詳細画面Layout
- Form画面Layout
- Dialog Layout
- Alert Dialog Layout
- Loading / Empty / Error Layout
- Responsive Layout
- Accessibility

本ドキュメントを、個別画面設計およびFrontend実装における共通レイアウトの基準とする。

---

# 2. 基本方針

共通レイアウトは以下を重視する。

- 現在位置が分かりやすい
- 主要機能へ移動しやすい
- 画面ごとのレイアウト差異を減らす
- 情報量が多くても読みやすい
- 操作の優先順位が分かりやすい
- Desktop / Tablet / Mobileで一貫した操作体系を維持する
- MVPに不要な複雑なLayoutを導入しない

認証後画面では、原則として共通のApp Shellを利用する。

Feature固有の詳細なLayoutは `07_画面設計` で定義する。

---

# 3. App Shell

## 3.1 基本構造

認証後画面の基本構造は以下とする。

```text id="4yo3dg"
+----------------------------------------------------------+
| Header                                                   |
+------------------+---------------------------------------+
|                  | Breadcrumb                            |
|                  |                                       |
| Sidebar          | Page Header                           |
|                  |                                       |
|                  | Page Content                          |
|                  |                                       |
+------------------+---------------------------------------+
```

構造としては以下を基本とする。

```text id="qjprbq"
App Shell
├── Header
├── Sidebar
└── Main
    ├── Breadcrumb
    ├── Page Header
    └── Page Content
```

---

## 3.2 対象画面

App Shellは認証後の主要画面で利用する。

対象例:

- Dashboard
- 一覧画面
- 詳細画面
- 登録・編集画面
- Access Denied

ログイン画面ではApp Shellを利用しない。

Not Foundについては、発生Contextに応じて簡易LayoutまたはApp Shell内表示を実装時に判断する。

---

# 4. Header

## 4.1 目的

HeaderはApplication全体に共通する情報・操作を提供する。

主な責務は以下とする。

- Application識別
- Mobile / TabletでのNavigation Menu起動
- Login User情報へのアクセス
- User Menu
- Logout

---

## 4.2 基本構造

Desktopでは以下を基本とする。

```text id="k54ioh"
+----------------------------------------------------------+
| Application Name                              User Menu  |
+----------------------------------------------------------+
```

Tablet / MobileではNavigation起動Actionを追加する。

```text id="0io5bu"
+----------------------------------------------------------+
| Menu | Application Name                       User Menu  |
+----------------------------------------------------------+
```

---

## 4.3 Application Name

HeaderにはApplicationを識別できる名称を表示する。

Application NameからDashboardへ遷移可能とすることを基本候補とする。

---

## 4.4 User Menu

認証済みユーザーに関する操作をUser Menuへ集約する。

MVPでは以下を候補とする。

- Login User表示
- Logout

MVPに不要な設定項目は追加しない。

---

# 5. Sidebar

## 5.1 目的

SidebarはApplication内の主要機能へ移動するためのPrimary Navigationとする。

---

## 5.2 Navigation構成

基本構造は以下とする。

```text id="s2d1oa"
Dashboard

Employee
└── 社員一覧

Skill
├── スキル一覧
└── スキルカテゴリ一覧

Administration
└── アクセス制御
```

実際に表示する項目はRole / Permissionに応じて制御する。

---

## 5.3 Navigation Group

Navigationは機能単位でGroup化してよい。

候補:

- Employee
- Skill
- Administration

Group内に表示可能なNavigation Itemが存在しない場合は、そのGroup自体を表示しない。

---

## 5.4 Active State

現在表示しているFeatureをSidebar上で識別可能にする。

同一Feature配下の一覧・詳細・登録・編集画面では、対応するNavigationをActiveとして扱う。

Dialog表示中はRouteを変更しないため、元画面のActive Stateを維持する。

具体的なRouteとの対応は `03_画面遷移.md` を正とする。

---

# 6. Main Content

## 6.1 基本構造

Main Contentは以下の順序を基本とする。

```text id="oz32nx"
Breadcrumb

Page Header
├── Title
├── Description
└── Actions

Page Content
```

---

## 6.2 Content Width

画面の性質に応じて適切な横幅を利用する。

一覧画面・Dashboard等、横方向の情報量が多い画面では利用可能な横幅を広く使用する。

Formや文章中心の画面では、過度に横長にならないよう適切な最大幅を設定する。

画面ごとに不要に異なる最大幅を設定しない。

---

## 6.3 Spacing

以下の間には一貫したSpacingを設ける。

- BreadcrumbとPage Header
- Page HeaderとPage Content
- Section同士
- Form Field同士
- List / TableとPagination
- ContentとAction領域

具体値は `05_デザインシステム.md` で定義する。

---

# 7. Breadcrumb

## 7.1 基本方針

現在位置と上位画面を把握できるよう、認証後の主要画面でBreadcrumbを利用する。

---

## 7.2 一覧画面

一覧画面ではFeatureの入口を表示する。

例:

```text id="0qawuc"
Employees
```

```text id="qch41n"
Skills
```

---

## 7.3 詳細画面

詳細画面では一覧との階層関係を表示する。

例:

```text id="nrtfop"
Employees > 社員名
```

---

## 7.4 登録・編集画面

独立した登録・編集画面では、親画面と現在操作を表示する。

例:

```text
Employees > 社員名 > スキル編集
```

```text
Access Control > ユーザー名 > 権限編集
```

---

## 7.5 Dialog

Dialogは独立Routeを持たないため、Dialog表示によってBreadcrumb階層を変更しない。

現在実行中の操作はDialog Titleで表現する。

---

# 8. Page Header

## 8.1 目的

Page Headerは現在表示している画面の目的と主要Actionを明確にする。

基本構造:

```text id="ez0hi7"
Page Header
├── Title
├── Description
└── Actions
```

---

## 8.2 Title

画面の主目的を簡潔に表す。

例:

```text id="r6489c"
社員一覧
```

```text id="ycaqse"
スキル一覧
```

```text id="cx1opb"
ユーザー・権限一覧
```

---

## 8.3 Description

補足説明が必要な場合のみ表示する。

説明がなくても目的が明確な場合は省略してよい。

---

## 8.4 Actions

その画面における主要Actionを配置する。

例:

```text id="40yml3"
一覧画面                 [ 登録 ]
```

```text id="899gd4"
詳細画面                 [ 編集 ]
```

権限によって利用できないActionは表示しないことを基本とする。

---

## 8.5 Actionと遷移

Page Header Actionは以下のいずれかを起動できる。

- 独立画面への遷移
- Dialog
- Feature固有Action

具体的な動作は `03_画面遷移.md` および個別画面設計で定義する。

PageHeader自身は遷移・権限・Domain Logicを持たない。

---

# 9. 一覧画面Layout

## 9.1 基本構造

一覧画面は以下を基本とする。

```text id="3zh8q2"
Breadcrumb

Page Header
├── Title
└── Primary Action

Search / Filter

List / Table

Pagination
```

---

## 9.2 一覧表示

DesktopではTableを基本候補とする。

情報量・画面幅に応じてList / Card等を利用してよい。

具体的な表示方式はFeature固有画面設計で定義する。

---

## 9.3 Search / Filter

Search / Filterは一覧対象の絞り込みに利用する。

条件数が少ない場合はPage内へ直接配置する。

条件数が増えた場合のみ、折りたたみ等を検討する。

MVPでは高度なFilter Builderを導入しない。

---

## 9.4 Primary Action

一覧画面から登録操作を行う場合、Page HeaderへPrimary Actionを配置することを基本とする。

ActionはFeatureによって以下のいずれかとなる。

- 登録画面へ遷移
- 登録Dialogを開く

どちらを採用するかは `02_画面一覧.md` を正とする。

---

# 10. 詳細画面Layout

## 10.1 基本構造

詳細画面は以下を基本とする。

```text id="luqrs4"
Breadcrumb

Page Header
├── Resource Name / Title
└── Actions

Primary Information

Related Information
```

---

## 10.2 Section

情報の責務が異なる場合はSectionを分ける。

例:

```text id="nmc4mq"
基本情報

関連情報

状態情報
```

情報量が少ない場合に形式的なSectionを増やさない。

---

## 10.3 Action

詳細画面の編集等の主要ActionはPage Headerへ配置することを基本とする。

関連情報固有のActionは、そのSection Header付近へ配置してよい。

---

# 11. Form画面Layout

## 11.1 基本構造

独立したForm画面は以下を基本とする。

```text id="4qh1mo"
Breadcrumb

Page Header

Form
├── Section
│   ├── Field
│   └── Field
│
└── Actions
    ├── Cancel
    └── Primary Action
```

---

## 11.2 Form Width

Formは可読性・入力性を優先し、不要に画面幅全体へ広げない。

---

## 11.3 Form Section

項目数が多い場合は意味単位でSectionを分ける。

項目数が少ない場合は単一Sectionとしてよい。

---

## 11.4 Form Action

Form末尾へAction領域を配置する。

基本形:

```text id="ylbjr3"
[ キャンセル ] [ 保存 / 登録 ]
```

Primary ActionとCancelの順序はApplication全体で統一する。

---

# 12. Dialog Layout

## 12.1 目的

元画面のContextを維持したまま完結できる比較的小規模な操作に利用する。

---

## 12.2 基本構造

```text id="8l3iyp"
Dialog
├── Header
│   ├── Title
│   └── Description
│
├── Content
│   └── Form / Content
│
└── Footer
    ├── Cancel
    └── Primary Action
```

shadcn/uiの `Dialog` を基本候補とする。

---

## 12.3 背景Context

Dialog表示中も元画面のContextを維持する。

以下は原則として変化させない。

- Header
- Sidebar
- Breadcrumb
- Page Header
- Navigation Active State
- Current Route

---

## 12.4 Dialogを利用する条件

以下を満たす場合にDialogを候補とする。

- 元画面との関連が強い
- 操作が比較的小規模
- 入力項目が多すぎない
- 独立した作業Contextを必要としない

---

## 12.5 独立画面を優先する条件

以下の場合は独立画面を優先する。

- 入力項目が多い
- 複数Sectionを扱う
- 複数Resourceを操作する
- 追加・編集を繰り返す
- Dialogでは十分な操作領域を確保できない
- Mobileで操作性が低下する
- 独立した作業Contextの方が理解しやすい

---

# 13. Dialog Form Layout

## 13.1 Field

Dialog内のFormは1 Columnを基本とする。

```text id="l1c1ek"
Label
[ Input ]

Label
[ Select ]

Label
[ Input ]
```

必要性が明確な場合のみ複数Columnを利用する。

---

## 13.2 Footer

Dialog Footerには以下を基本として配置する。

```text id="bvxtl8"
[ キャンセル ] [ Primary Action ]
```

Application全体で順序を統一する。

---

## 13.3 Scroll

Dialog ContentがViewport Heightを超える場合はScroll可能とする。

HeaderやFooterを固定する場合は、Fieldが隠れないよう配慮する。

---

# 14. Alert Dialog Layout

## 14.1 目的

削除・無効化等、影響の大きい操作を実行する前の確認に利用する。

---

## 14.2 基本構造

```text id="jzchre"
Alert Dialog
├── Title
├── Description
└── Actions
    ├── Cancel
    └── Confirm
```

---

## 14.3 Dialogとの使い分け

```text id="6i0wjj"
登録・編集Form
    ↓
Dialog

重要操作の確認
    ↓
Alert Dialog
```

通常の入力FormをAlert Dialogへ配置しない。

---

# 15. Loading Layout

## 15.1 Page Loading

Data取得中もApp Shellを可能な限り維持する。

```text id="5hwgf8"
App Shell
├── Breadcrumb
├── Page Header
└── Skeleton / Loading Content
```

Page全体を単一Spinnerだけに置き換えることを基本としない。

---

## 15.2 Section Loading

Page内の一部だけData取得中の場合は、そのSectionのみLoading状態とする。

他の利用可能な情報・操作を不要に隠さない。

---

## 15.3 Dialog Loading

Dialog表示後に追加Data取得が必要な場合は、Dialog構造を維持したままContentをLoading状態とする。

---

# 16. Empty State Layout

表示対象が存在しない場合は、空のTableや空白だけを表示せずEmpty Stateを利用する。

基本構造:

```text id="2eif0h"
Empty State
├── Title
├── Description
└── Action
```

ActionはPermission・画面Contextに応じて任意とする。

検索結果0件とResource自体が0件の状態は区別する。

---

# 17. Error State Layout

PageまたはSection単位で情報取得に失敗した場合はError Stateを表示する。

例:

```text id="jslcn8"
情報を取得できませんでした。

[ 再試行 ]
```

App Shellまで不要に破棄しない。

Form Validation Error等のField単位Errorは個別Form内部で扱う。

具体的なError Stateは `08_UI状態設計.md` で定義する。

---

# 18. Success Feedback

登録・更新等の成功時は、必要に応じてSuccess Feedbackを提供する。

Success Feedbackそのものを共通Layoutの固定領域として必須にはしない。

具体的なNotification方式は `06_共通コンポーネント.md` および `08_UI状態設計.md` で定義する。

---

# 19. PermissionとLayout

Permissionによって利用できないActionは非表示を基本とする。

例:

```text id="c07yj5"
操作可能

画面タイトル                        [ Action ]
```

```text id="h1k7g9"
操作不可

画面タイトル
```

Actionが存在しない場合でもPage HeaderのLayoutが崩れないようにする。

Layout Component自身に認可Domain Logicを持たせない。

---

# 20. Responsive

## 20.1 Desktop

DesktopではSidebarを常時表示することを基本とする。

```text id="rmc03j"
+----------------------------------------------------------+
| Header                                                   |
+------------------+---------------------------------------+
| Sidebar          | Main Content                          |
|                  |                                       |
+------------------+---------------------------------------+
```

Page HeaderではTitleとActionを横並びに配置可能とする。

---

## 20.2 Tablet

Tabletでは利用可能な横幅に応じてSidebarを以下のいずれかとする。

- Compact Sidebar
- Collapsible Sidebar
- Overlay Navigation

Navigation構造自体はDesktopと変更しない。

---

## 20.3 Mobile

MobileではSidebarを常時表示しない。

HeaderのMenu操作からNavigationを表示する。

```text id="0jlmyd"
+----------------------------+
| Menu | App | User          |
+----------------------------+
| Breadcrumb                 |
|                            |
| Page Header                |
|                            |
| Page Content               |
+----------------------------+
```

---

# 21. Mobile Page Header

MobileではTitle・Description・Actionを縦方向へ展開してよい。

例:

```text id="3dluqi"
画面タイトル

Description

[ Primary Action ]
```

主要Actionが画面幅不足によって認識しにくくならないよう配慮する。

---

# 22. Mobile Form

Formは1 Columnを基本とする。

```text id="h3ymj7"
Label
[                    ]

Label
[                  ▼ ]

Label
[                    ]

[ Primary Action     ]
[ キャンセル         ]
```

Form Controlは利用可能な横幅を適切に使用する。

---

# 23. Mobile Dialog

## 23.1 基本方針

Desktopと同じ固定幅Modalを単純に縮小しない。

Viewportを有効活用する。

---

## 23.2 表示方式

候補:

- Viewport幅を広く利用するDialog
- Full-screenに近いDialog
- Sheet / Drawer

具体方式は `09_レスポンシブ設計.md` で統一する。

操作の意味・責務はViewportによって変更しない。

---

# 24. Mobile Table / List

横幅が不足する場合は、情報優先度に応じて以下を検討する。

- 表示Column削減
- 横Scroll
- List表示
- Card表示

すべてのTableへ一律同じ変換を適用しない。

具体方式は各個別画面設計で定義する。

---

# 25. Accessibility

共通レイアウトでは以下を考慮する。

- Semantic HTMLを利用する
- Header / Navigation / Mainの役割を明確にする
- KeyboardのみでNavigation可能にする
- Active Stateを色だけで表現しない
- Focus状態を視認可能にする
- Breadcrumbを適切なNavigationとして扱う
- Dialog起動時に適切なFocus Managementを行う
- Dialog Close後は起動元へFocusを戻す
- Dialog表示中に背景へFocusが移動しないようにする
- Dialog Titleを支援技術から認識可能にする
- Alert Dialogの操作内容を明確にする

shadcn/ui / Base UIを利用するだけでAccessibilityが完成すると考えず、Application実装側でも確認する。

# 26. 共通レイアウトとComponent

共通レイアウトでは以下のComponentを利用候補とする。

## shadcn/ui

- Breadcrumb
- Button
- Dropdown Menu
- Separator
- Tooltip
- Dialog
- Alert Dialog
- Sheet

必要なComponentのみ導入する。

---

## Application共通Component

候補:

- AppShell
- AppHeader
- AppSidebar
- PageHeader

一覧・Form・Dialog等の具体的Component責務は `06_共通コンポーネント.md` で定義する。

---

# 27. LayoutとComponentの責務

Layoutは画面全体の構造を担当する。

```text id="oewqbg"
Layout
├── Header
├── Sidebar
└── Main
```

Componentは画面内の機能単位を担当する。

```text id="1sgnxh"
Main
├── Breadcrumb
├── PageHeader
├── Search / Filter
├── Data Display
├── Form
├── Dialog
└── Feedback
```

Domain Rule・API通信・認可判定そのものをLayout Componentへ持たせない。

---

# 28. Feature固有Layoutとの関係

本ドキュメントでは、全Featureへ適用するLayout Patternまでを定義する。

Feature固有の以下の内容は `07_画面設計` で定義する。

- Section構成
- 表示順
- 個別Action配置
- Form Field配置
- Dialog内部の具体的内容
- Table Column
- 個別Mobile Layout
- Wireframe

本ドキュメントへFeature固有のLayoutを重複して定義しない。

---

# 29. MVPで扱わないもの

MVPでは以下を共通レイアウトの必須機能としない。

- UserによるSidebar Layout変更
- Navigation Drag & Drop
- 複数Layout Theme
- Custom Dashboard Layout
- Persistent Split Pane
- Multi-Window Navigation
- DialogのURL同期
- DialogのNested Routing
- 複数Dialogを重ねる複雑な操作
- 全Form共通の未保存変更Guard

必要性が明確になった場合に別途検討する。

---

# 30. 本ドキュメントで定義しないもの

以下は他のUI設計またはFrontend実装設計で定義する。

- Feature固有のRoute
- Feature固有の遷移
- Form Fieldの具体内容
- Table Columnの具体内容
- Dialog固有のField
- Domain Rule
- Permission Ruleそのもの
- API Client実装
- React Component構造
- Tailwind CSS Class
- Design Tokenの具体値
- State管理方式
