# UI状態設計

## 1. 目的

本ドキュメントは、Engineer Skill Management App のMVPで利用する共通UI状態と、その表示・遷移・責務の基本方針を定義する。

各画面で個別に状態設計を重複させるのではなく、Application全体で一貫したUI Stateを扱うための共通基準とする。

主に以下を対象とする。

- Loading
- Empty
- Search Result Empty
- Submit / Mutation Loading
- Validation Error
- API Error
- Operation Error
- Not Found
- Access Denied
- Disabled
- Success Feedback
- Retry
- Dialog State
- Resource状態変化

---

## 2. 基本方針

UI状態は、状態が発生する範囲と責務を明確に分ける。

基本分類:

```text id="7vktn4"
UI State
├── Page State
├── Section State
├── Form State
├── Dialog State
└── Operation State
```

状態が局所的な場合に、Page全体をError画面やLoading画面へ置き換えない。

逆に、Page自体を成立させられない状態を局所Errorだけで済ませない。

---

## 3. 状態の責務範囲

### 3.1 Page State

Page全体の成立可否に関わる状態。

対象例:

- Initial Loading
- Resource Not Found
- Access Denied
- Page-level API Error

---

### 3.2 Section State

Page内の一部分のみで発生する状態。

対象例:

- Dashboard Widget Loading
- 一部Data取得失敗
- 一覧SectionのみEmpty

Page全体を置き換えず、対象Section内でFeedbackする。

---

### 3.3 Form State

Form入力・Validation・Submitに関する状態。

対象例:

- Default
- Dirty
- Validation Error
- Submit Loading
- Submit Error

---

### 3.4 Dialog State

Dialog固有の状態。

対象例:

- Closed
- Open
- Master Data Loading
- Validation Error
- Submit Loading
- API Error

---

### 3.5 Operation State

独立したActionに関する状態。

対象例:

- Skill無効化処理中
- EmployeeSkill削除処理中
- Employee退職処理中
- Retry処理中

Operation単位のLoadingやErrorをPage全体へ拡大しないことを基本とする。

---

# 4. Initial Loading

## 4.1 基本方針

Page表示に必要な初期Data取得中はLoading状態を表示する。

Page構造が分かる場合はSkeletonを基本候補とする。

```text id="h00k4m"
Page Header
Search / Filter
Skeleton Content
```

単一SpinnerだけでPage全体を置き換えることを標準としない。

---

## 4.2 Content Flash防止

AuthorizationやResource取得完了前に、本来表示すべきでないContentを一時表示しない。

```text id="wrbig7"
Loading
    ↓
Result
    ├── Allowed / Found → Content
    ├── Forbidden       → Access Denied
    └── Not Found       → Not Found
```

---

## 4.3 Loading表示範囲

取得対象がSection単位の場合は、そのSectionのみLoadingにする。

Page全体のData依存関係が強い場合のみPage-level Loadingとする。

---

# 5. Section Loading

Pageの一部だけData取得中の場合はSectionのLayoutを維持してLoading状態を表示する。

例:

```text id="mru8zr"
Dashboard
├── Summary Card
├── Skill Distribution
│   └── Skeleton
└── Recent Data
```

他の利用可能なSectionまで操作不能にしない。

---

# 6. Empty

## 6.1 基本方針

Resource自体が0件の場合はEmpty Stateを表示する。

例:

```text id="8a4yai"
スキルが登録されていません。

[ スキル登録 ]
```

Primary Actionは権限がある場合のみ表示する。

---

## 6.2 Empty State構成

基本構造:

```text id="2gec19"
EmptyState
├── Title
├── Description
└── Action
```

Actionは任意とする。

---

## 6.3 EmptyとError

Dataが0件で正常Responseの場合はEmptyとして扱う。

Data取得失敗をEmptyとして扱わない。

```text id="bp7iaf"
200 + 0件
    ↓
Empty

500 / Network Error
    ↓
Error
```

---

# 7. Search Result Empty

Resource自体は存在するが、検索・Filter条件に一致するDataが0件の場合は通常のEmptyと区別する。

例:

```text id="074i02"
条件に一致するスキルがありません。

検索条件を変更してください。

[ 条件をクリア ]
```

登録Actionを主Actionとして強調しすぎない。

---

# 8. Validation Error

## 8.1 Field Error

Field単位のValidation Errorは対象Field付近へ表示する。

```text id="dtsqco"
スキル名
[               ]

スキル名を入力してください。
```

Errorと対象Fieldを視覚的・Semanticに関連付ける。

---

## 8.2 Form Error

複数FieldにまたがるValidationやDomain RuleはForm全体Errorとして表示する。

例:

```text id="00jqay"
この変更は保存できません。

権限管理可能な管理者を最低1人維持する必要があります。
```

---

## 8.3 入力内容

Validation Error時は入力内容を可能な限り維持する。

Error発生を理由にFormを初期化しない。

---

# 9. Submit / Mutation Loading

## 9.1 基本方針

登録・更新・削除・無効化・退職等のMutation実行中は二重実行を防止する。

例:

```text id="1d5g5n"
[ キャンセル ] [ 保存中... ]
```

Operation固有のActionでは、処理内容に対応したLabelを利用してよい。

例:

```text id="ob4h34"
[ キャンセル ] [ 無効化中... ]
```

```text id="mgogv8"
[ キャンセル ] [ 退職処理中... ]
```

---

## 9.2 入力値

Mutation中も入力内容を維持する。

Request開始時にFormをClearしない。

---

## 9.3 操作制御

処理中は、同一Mutationを再実行できない状態とする。

ただし、Page全体を無条件にDisabledにしない。

処理との競合が起こるActionのみ抑制する。

---

# 10. API Error

## 10.1 予期しないError

Network Error、500系等の予期しないErrorは、利用者向けMessageへ変換する。

例:

```text id="5wkb42"
情報を取得できませんでした。

[ 再試行 ]
```

Backend内部Message・Exception・Stack Traceを表示しない。

---

## 10.2 Error表示範囲

ErrorがSectionだけに影響する場合はSection内で表示する。

Page自体が成立しない場合のみPage-level Errorとする。

---

# 11. Operation Error

登録・編集・削除・無効化・退職等のAction失敗は、現在の操作Contextを可能な限り維持する。

例:

```text id="j72h24"
Skill List
    ↓
無効化
    ↓
失敗
    ↓
一覧維持 + Error Feedback
```

Dialog内操作の場合:

```text id="fphf76"
Dialog
    ↓
Submit
    ↓
失敗
    ↓
Dialog維持
```

Routeを持たないActionの場合:

```text id="uwmtta"
現在Page
    ↓
Action実行
    ↓
失敗
    ↓
現在Pageを維持 + Error Feedback
```

Action失敗だけを理由に、無関係なPageへ遷移しないことを基本とする。

---

# 12. Retry

Retry可能なErrorでは、利用者が同じ操作を再実行できるActionを提供してよい。

例:

```text id="zy45ah"
スキル一覧を取得できませんでした。

[ 再試行 ]
```

Retry時は同じ処理の多重実行を防止する。

---

# 13. Success Feedback

## 13.1 基本方針

登録・更新・削除・無効化・退職等が成功した場合、必要に応じて成功Feedbackを表示する。

例:

```text id="a37cwa"
社員を登録しました。
```

```text id="tdxg75"
スキルを更新しました。
```

```text id="n21jos"
スキルを無効化しました。
```

---

## 13.2 遷移あり

成功後に別Pageへ遷移する場合、遷移先でも操作成功を認識できることが望ましい。

例:

```text id="on0bks"
社員登録
    ↓
社員詳細
    ↓
「社員を登録しました」
```

---

## 13.3 遷移なし

Dialogを閉じて一覧を更新する場合も、必要に応じてSuccess Feedbackを提供する。

Routeを持たないAction成功時も、現在Pageを維持しながら最新DataとFeedbackを表示することを基本とする。

---

# 14. Not Found

## 14.1 Page Resource Not Found

Page成立に必要なResourceが存在しない場合は共通Not Foundを利用する。

例:

```text id="k1uf7m"
/employees/[employeeId]
    ↓
Employee Not Found
    ↓
Not Found
```

---

## 14.2 Operation中のNot Found

Dialogや一覧Action実行時に対象Resourceが存在しなくなった場合は、必ずしもPage全体のNot Foundへ遷移しない。

例:

```text id="knp52k"
SkillEditDialog
    ↓
Update
    ↓
404
    ↓
Dialogを閉じる
一覧を更新
Feedback
```

Routeを持たないActionでも、対象Resourceのみが存在しなくなった場合は現在Pageを維持し、Dataの最新化とFeedbackを行うことを候補とする。

---

## 14.3 403 / 404

Access Deniedとの使い分けは既存Security / Authorization設計を正とする。

UI側だけで判断Ruleを変更しない。

---

# 15. Access Denied

## 15.1 Page Access Denied

Page自体への参照権限がない場合は共通Access Deniedを利用する。

---

## 15.2 Action Access Denied

画面は参照可能だがAction権限だけがない場合は、通常はActionを表示しない。

```text id="mx0f92"
参照可能
編集不可
    ↓
編集Actionなし
```

Action単位の権限不足で毎回Access Denied Pageへ遷移しない。

Dialog起動ActionおよびRouteを持たないActionも同じ方針とする。

---

## 15.3 Permission変化

画面表示後にPermissionが変更され、次Requestで403が返る可能性を考慮する。

Backend Responseを正とする。

---

# 16. Disabled

## 16.1 基本方針

Disabledは、利用者が現在その操作を実行できないことを示す。

単なる「権限がない」の代替として常にDisabledを利用しない。

権限がないActionは非表示を基本候補とする。

---

## 16.2 Disabled理由

Disabledにする場合は、可能であれば理由を利用者が理解できるようにする。

例:

```text id="u468ws"
権限管理を無効化できません。

権限管理可能な管理者を最低1人維持する必要があります。
```

---

## 16.3 Readonlyとの区別

情報表示目的ではDisabled Inputを多用しない。

編集不可情報はReadonly Textとして表示することを検討する。

```text id="axqy77"
所属
開発部
```

---

# 17. PermissionによるUI State

Permissionに応じて以下を使い分ける。

```text id="xpib73"
参照権限なし
    ↓
Access Denied

参照可能 / 編集不可
    ↓
Content表示
編集Action非表示

編集可能
    ↓
Content表示
編集Action表示
```

FrontendのPermission StateはUX制御であり、Security Boundaryではない。

---

# 18. Dialog State

## 18.1 Closed

Dialog非表示。

背景Pageが通常操作可能な状態。

---

## 18.2 Open

Dialog表示中。

背景Contextを維持し、背景へのFocus移動を抑制する。

---

## 18.3 Master Loading

Dialog内で必要なMaster Data取得中。

例:

- Department
- Skill Category

必要なDataが取得できるまでPrimary Actionを実行不可とする。

---

## 18.4 Validation Error

Dialogを閉じず、対象FieldへErrorを表示する。

入力値を維持する。

---

## 18.5 Submit Loading

Dialogを閉じず、Mutation処理中であることを表示する。

二重送信を防止する。

---

## 18.6 API Error

予期しないAPI Error時もDialogを閉じないことを基本とする。

入力内容を維持してRetry可能にする。

---

## 18.7 Success

成功時はFeature固有方針に従う。

候補:

```text id="pg17v6"
Dialog Close
    ↓
一覧更新
```

```text id="cse078"
Dialog Close
    ↓
詳細画面へ遷移
```

---

# 19. Alert Dialog State

重要・破壊的操作ではAlert Dialogを利用候補とする。

MVPでの主な対象候補:

- Skill無効化
- EmployeeSkill削除
- Employee退職の最終確認
- 重要な権限変更

確認中は対象Actionの意味と影響を明確にする。

単なる情報編集にAlert Dialogを多用しない。

Alert Dialogの利用有無はFeature固有設計を正とする。

---

# 20. Resource状態変化

## 20.1 Skill無効化

Skill無効化成功後はSkill一覧を最新化する。

対象Skillは既存履歴保持方針に従ってInactive状態として保持し、一覧上でも状態を識別可能にする。

```text id="xg89m9"
Skill
Active
    ↓
無効化
    ↓
Inactive
```

Skillの再有効化はMVPでは扱わない。

Skill Categoryについては、MVPではActive / Inactive状態変更を扱わない。

---

## 20.2 Employee Employment Status

Employeeの退職成功後は社員詳細等を最新化する。

```text id="qdczhq"
Employee
在籍
    ↓
退職
    ↓
退職済み
```

退職は通常のEmployee情報編集ではなく、既存Employee API仕様で定義された専用のDomain Operationとして扱う。

退職によってDashboard対象外になる等のDomain影響は既存仕様を正とする。

---

## 20.3 EmployeeSkill削除

EmployeeSkill削除成功後は社員スキル編集画面の対象一覧を最新化する。

削除済みEmployeeSkillをClient State上だけで残さず、Backendの最新状態を反映する。

具体的な削除後の表示・Feedbackは個別画面設計を正とする。

---

# 21. Master Data Error

Formに必要なMaster Dataが取得できない場合は、Formを不完全な状態でSubmitできないようにする。

例:

```text id="yktah5"
スキルカテゴリを取得できませんでした。

[ 再試行 ]
```

必要Dataがないまま登録・更新を許可しない。

---

# 22. Concurrent Update

同一Resourceが別操作で更新された場合の競合処理はBackend仕様を正とする。

Backendから競合Errorが返る場合は、利用者が次の操作を理解できるFeedbackを提供する。

例:

```text id="cpawwg"
情報が更新されています。

最新の内容を確認して、もう一度操作してください。
```

UI側で独自の競合Ruleを追加しない。

---

# 23. Stateの優先順位

複数状態が同時に成立し得る場合は、Page成立可否を優先して判断する。

概念上:

```text id="3zcm8c"
Authentication
    ↓
Authorization
    ↓
Resource existence
    ↓
Data loading / error
    ↓
Normal content
```

例:

```text id="c8uz07"
未認証
    ↓
Authentication Flow
```

```text id="oxkheq"
認証済み + 権限なし
    ↓
Access Denied
```

```text id="qh4m7v"
認証済み + 権限あり + Resourceなし
    ↓
Not Found
```

具体的な403 / 404順序は既存Security設計を正とする。

---

# 24. Error Message方針

Error Messageは以下を満たす。

- 利用者向けの言葉を使用する
- 原因が分かる範囲で説明する
- 次の操作があれば示す
- 内部Exceptionを露出しない
- Backend実装名を露出しない
- Permission Codeを露出しない
- Stack Traceを露出しない

---

# 25. Loading Message方針

処理中であることを必要に応じてTextでも伝える。

例:

```text id="w2zg1p"
保存中...
```

```text id="ymb70m"
登録中...
```

```text id="uyxzwv"
無効化中...
```

Loading Indicatorだけに依存しない。

---

# 26. 状態とURL

通常のDialog Open / CloseではRouteを変更しない。

Routeを持たない主要Actionの確認UIでもRouteを変更しない。

以下の状態をURLへ無理に同期しない。

- Dialog Open
- Alert Dialog Open
- Validation Error
- Submit Loading
- Operation Loading
- Temporary Error Message
- Success Feedback

MVPでは高度なUI State URL Syncを必須としない。

---

# 27. Browser History

Page遷移を伴わないUI State変更で不要なBrowser Historyを追加しない。

Dialogを開閉するだけでBack Button Historyを増やさないことを基本とする。

Routeを持たないActionの確認UIについても同様とする。

---

# 28. Refresh

Browser Refresh後もPage-level Stateを安全に再評価できる構成とする。

一時的なClient Stateだけに依存して、

- Access Denied
- Not Found
- Resource取得
- Resourceの最新状態

を判定しない。

---

# 29. Responsive

状態の意味はViewportによって変更しない。

```text id="91gxqy"
Desktop
Tablet
Mobile
```

で共通の状態意味を維持する。

ただし、表示方式は調整可能とする。

例:

```text id="ysolmb"
Desktop
Empty State + 横並びAction

Mobile
Empty State + 縦並びAction
```

---

# 30. Accessibility

UI状態では以下を基本とする。

- LoadingをVisualだけで表現しない
- ErrorをColorだけで表現しない
- SuccessをColorだけで表現しない
- Resource状態をColorだけで表現しない
- Disabled理由を必要に応じて説明する
- Validation ErrorとFieldを関連付ける
- DialogのFocus Managementを適切に行う
- Dialog Close後は起動元へFocusを戻す
- Alert DialogのActionと影響を支援技術から認識可能にする
- Page-level Error / Not Found / Access DeniedではHeadingを明確にする
- 状態変化を支援技術から認識可能にすることを検討する

---

# 31. 共通Componentとの関係

状態表示には既存Application共通Componentを利用する。

候補:

```text id="fy9tr3"
EmptyState
ErrorState
StatusBadge
FormField
ConfirmDialog
```

Loadingではshadcn/uiのSkeleton等を利用候補とする。

重要・破壊的操作の確認には、共通Component設計に従ってAlert Dialogまたは対応する共通確認Componentを利用する。

専用Componentを状態ごとに過剰に増やさない。

---

# 32. 個別画面との責務分離

本ドキュメントでは状態の共通意味と表示方針を定義する。

個別画面では以下のみを追加定義する。

- その画面で発生するState
- State発生条件
- Feature固有Message
- 成功後の遷移
- Retry対象
- Feature固有Resourceへの影響

共通状態Ruleを個別画面で再定義しない。

Feature固有のDomain Operationの有無は個別画面設計および既存API仕様を正とする。

共通UI状態設計だけを根拠として、新しいDomain Operationを追加しない。

---

# 33. 状態一覧

MVPの主なUI状態を以下とする。

| State | 主な範囲 | 基本対応 |
|---|---|---|
| Loading | Page / Section / Dialog | Skeleton等を表示 |
| Empty | List / Section | EmptyState |
| Search Result Empty | List | 条件変更・Reset導線 |
| Validation Error | Form | Field付近へ表示 |
| Submit Loading | Form / Dialog | 二重送信防止 |
| Operation Loading | Action | 対象Actionの二重実行防止 |
| API Error | Page / Section / Dialog | Error + Retry |
| Operation Error | Action | Context維持 + Feedback |
| Not Found | Page / Resource | 共通Not Found |
| Access Denied | Page | 共通Access Denied |
| Disabled | Control | 理由を必要に応じて明示 |
| Success | Operation | Feedback + Data更新 |
| Concurrent Update | Form / Resource | 最新化・再確認導線 |

---

# 34. 本ドキュメントで定義しないもの

以下はFrontend実装設計または既存システム仕様を正とする。

- React State管理方法
- Server / Client Component境界
- Suspense利用方法
- Error Boundary実装
- Toast Library
- Form Library
- Query Cache
- Retry回数
- Exponential Backoff
- HTTP StatusからUI Stateへの具体Mapping実装
- Backend Error Code
- Logging
- Monitoring
- Telemetry
- Tailwind CSS Class
- Design Token具体値
- Domain Operationの追加・変更
- Backend Resource状態遷移Rule

Phase 1ではUI上の状態意味・責務・共通表示方針を定義する。
