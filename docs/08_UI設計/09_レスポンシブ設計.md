# レスポンシブ設計

## 1. 目的

本ドキュメントは、Engineer Skill Management App のMVPにおけるResponsive Designの共通方針を定義する。

Desktop / Tablet / Mobileで画面の意味やFeature責務を変えず、Viewportに応じてLayout・情報密度・Navigation・Action配置を最適化するための共通基準とする。

主に以下を対象とする。

- Desktop First方針
- Breakpointの考え方
- App Shell
- Header
- Sidebar / Mobile Navigation
- Main Content
- Page Header
- Breadcrumb
- Table / List
- Search / Filter
- Form
- Dialog
- Alert Dialog
- Page Action
- Loading / Empty / Error
- 独立編集画面
- Feature固有画面
- Accessibility

---

## 2. 基本方針

MVPではDesktop Firstを基本とする。

主な利用環境としてDesktopを想定しつつ、Tablet / Mobileでも主要な閲覧・操作を完了できる構成とする。

```text
Desktop
    ↓
基本Layout

Tablet
    ↓
情報密度・Navigationを調整

Mobile
    ↓
1 Column中心へ再構成
```

Desktop Layoutを単純に縮小するだけのResponsive対応にはしない。

---

## 3. Responsiveで変更しないもの

Viewportによって以下を変更しない。

- Domain Rule
- Permission Rule
- Validation Rule
- Feature責務
- Resource構造
- Routeの意味
- Actionの意味
- Errorの意味
- Loadingの意味
- Dialog / 独立画面の採用判断

Responsive対応はPresentation Layer上の変化として扱う。

---

## 4. Responsiveで変更可能なもの

Viewportに応じて以下を変更してよい。

- Layout
- Column数
- Component幅
- Navigation表示方式
- Action配置
- Table / Card表示
- Search / Filter配置
- Dialog幅
- Text wrapping
- 情報の優先表示
- Sticky UI

---

# 5. Viewport区分

MVPでは概念上、以下の3区分で考える。

```text
Desktop
Tablet
Mobile
```

具体的なBreakpoint値はTailwind CSS v4の既存Breakpointを基本候補とする。

Phase 1ではApplication独自のBreakpoint値を固定しない。

実装時は、実際のLayout崩れ・情報量・操作性を基準にBreakpointを決定する。

---

## 6. Breakpoint設計方針

Breakpointは特定Device名ではなく、Layoutが成立するかどうかで判断する。

```text
Layout成立
    ↓
現在のLayoutを維持

Layout成立しない
    ↓
Responsive Layoutへ切り替え
```

iPhone・iPad等の特定Device Widthへ過度に依存しない。

---

# 7. App Shell

## 7.1 Desktop

Desktopでは以下を基本とする。

```text
+--------------------------------------------------+
| Header                                           |
+------------------+-------------------------------+
| Sidebar          | Main Content                  |
|                  |                               |
|                  |                               |
+------------------+-------------------------------+
```

Sidebarは常時表示を基本とする。

---

## 7.2 Tablet

TabletではViewport Widthに応じてSidebar幅を縮小するか、Mobile Navigation方式へ切り替える。

```text
Header
Main Content
```

または、

```text
Header
Sidebar
Main Content
```

のどちらが操作しやすいかで判断する。

---

## 7.3 Mobile

MobileではSidebarを常時表示しない。

HeaderからNavigationを開く方式を基本候補とする。

```text
Header
├── Menu Trigger
├── Application Name
└── User Menu
```

Menu TriggerからSheet等でNavigationを表示する。

---

# 8. Mobile Navigation

Mobile Navigationはshadcn/uiの `Sheet` 等を基本候補とする。

概念上:

```text
Menu Button
    ↓
Navigation Sheet
├── Dashboard
├── Employee
├── Skill
├── Skill Category
└── Access Control
```

実際に表示するNavigation ItemはPermissionに従う。

Mobile専用の別Navigation構造をDomain上作成しない。

---

# 9. Header

## 9.1 Desktop

Desktopでは以下を候補とする。

```text
Application Name
Utility / User Menu
```

Sidebarと役割が重複しないようにする。

---

## 9.2 Mobile

Mobileでは横幅が限られるため、表示内容を絞る。

候補:

```text
Menu
Application Name
User Menu
```

長いApplication Nameは省略表示等を検討してよい。

---

# 10. Main Content

## 10.1 Desktop

十分な横幅を利用しつつ、Contentが過度に横長にならないよう最大幅を検討する。

特にForm・詳細情報は読みやすいLine Lengthを優先する。

---

## 10.2 Mobile

Main Contentは1 Columnを基本とする。

左右Paddingを確保しつつ、利用可能なViewport Widthを有効活用する。

固定Pixel幅のContainerを前提としない。

---

# 11. Page Header

## 11.1 Desktop

基本構造:

```text
Title / Description                  Actions
```

Primary Actionを右側へ配置することを基本候補とする。

---

## 11.2 Tablet

横幅が不足する場合はActionsを下段へ移動してよい。

```text
Title / Description

Actions
```

---

## 11.3 Mobile

Mobileでは縦配置を基本候補とする。

```text
Title
Description

Primary Action
Secondary Action
```

Actionが1つの場合はFull Width Buttonを利用してよい。

---

# 12. Breadcrumb

## 12.1 Desktop

階層を理解できるようBreadcrumbを表示する。

例:

```text
Employees > 山田 太郎 > スキル編集
```

---

## 12.2 Mobile

階層が深い場合は折り返しを許容するか、表示情報を簡略化してよい。

ただし現在位置を理解できなくなる省略は避ける。

例:

```text
Employees
> 山田 太郎
> スキル編集
```

または、上位階層の一部を省略する方式を実装時に検討してよい。

---

# 13. List / Table

## 13.1 Desktop

一覧画面はTable形式を基本候補とする。

```text
+-----------------------------------------------------+
| Name        | Category    | Status | Actions         |
+-----------------------------------------------------+
| Laravel     | Framework   | 有効   | ...             |
+-----------------------------------------------------+
```

---

## 13.2 Tablet

Viewportに応じて以下を検討する。

- Column幅調整
- 低優先度Column非表示
- ActionsをDropdown Menuへ集約
- 横Scroll

---

## 13.3 Mobile

MobileではTableを単純に縮小しない。

以下を候補とする。

- Column削減
- Horizontal Scroll
- Card / List表示

Featureごとの情報優先度で判断する。

---

# 14. Mobile List / Card

MobileではResourceごとにまとまりを持たせる。

例:

```text
Laravel

Framework
有効

[ 編集 ] [ その他 ]
```

User一覧:

```text
山田 太郎

管理者
権限管理者
有効

[ 権限編集 ]
```

Resource間の境界を明確にする。

---

# 15. TableからCardへの変更基準

以下の場合はMobileでCard / List化を検討する。

- Column数が多い
- 横Scrollしないと主要情報が読めない
- Row Actionが操作しづらい
- Field Labelが必要
- Resource単位で情報をまとめた方が理解しやすい

単純にMobileだからすべてCard化するわけではない。

---

# 16. Search / Filter

## 16.1 Desktop

Desktopでは横方向に配置してよい。

例:

```text
[ Keyword ] [ Category ▼ ] [ Status ▼ ] [ Search ]
```

---

## 16.2 Tablet

横幅に応じて折り返す。

```text
[ Keyword ] [ Category ▼ ]
[ Status ▼ ] [ Search ]
```

---

## 16.3 Mobile

1 Columnを基本とする。

```text
[ Keyword            ]

[ Category       ▼ ]

[ Status         ▼ ]

[ Search             ]
```

Filter数が多い場合はSheet等の利用を検討してよい。

MVPでは必要以上に高度なFilter UIにしない。

---

# 17. Form

## 17.1 Desktop

Formは1 Columnを基本とする。

Field同士の関連性が高く、十分な横幅がある場合のみ2 Column等を検討する。

例:

```text
[ Year ] [ Month ]
```

---

## 17.2 Tablet

Desktopで複数Columnを利用している場合は、必要に応じてColumn数を減らす。

---

## 17.3 Mobile

1 Columnを基本とする。

```text
Label
[ Input ]

Label
[ Select ]
```

横並びFieldも、意味が損なわれない範囲で縦配置へ変更してよい。

---

# 18. Form Action

## 18.1 Desktop

Form下部またはPage HeaderにActionを配置する。

例:

```text
[ キャンセル ] [ 保存 ]
```

---

## 18.2 Mobile

Primary Actionを認識しやすくするため縦配置してよい。

```text
[ 保存             ]
[ キャンセル       ]
```

Application全体で順序を統一する。

---

# 19. 独立編集画面

以下は独立画面としてResponsive対応する。

- EmployeeSkill編集
- Access Control編集

MobileでもDialog化しない。

```text
Independent Page
    ↓
Responsive Layout変更
```

Viewportが小さいことだけを理由にUI種別を変更しない。

---

# 20. EmployeeSkill編集

## 20.1 Desktop

EmployeeSkill単位で複数Fieldをまとめる。

Card / Section形式を基本候補とする。

```text
Laravel
├── 実務経験
├── Skill Level
├── 経験期間
└── 最終利用時期
```

---

## 20.2 Mobile

EmployeeSkillごとに1 Columnで表示する。

```text
Laravel

実務経験
[ あり ▼ ]

Skill Level
[ Level 3 ▼ ]

経験期間
[ 2年 ]
[ 6か月 ]

最終利用時期
[ 2026/09 ]

[ 削除 ]
```

複数Skill間の境界を明確にする。

---

## 20.3 Action

Skill数が多くSave Actionまで距離が長くなる場合はSticky Action Areaを検討してよい。

ただしMVPで必須としない。

---

# 21. Access Control編集

## 21.1 Desktop

Role・Permission Management・Constraint Messageを読みやすい幅に配置する。

過度に横長なFormにしない。

---

## 21.2 Mobile

1 Columnを基本とする。

```text
ユーザー
山田 太郎

Role
[ 管理者 ▼ ]

権限管理
[✓] 権限管理を許可

Warning

[ 保存 ]
[ キャンセル ]
```

権限変更の意味を説明するDescriptionをViewport都合で削除しない。

---

# 22. Dialog

## 22.1 Desktop

中央配置Dialogを基本とする。

入力項目が少ないCreate / Edit Dialogでは、Contentに応じた適切な幅とする。

過度に大きなDialogにしない。

---

## 22.2 Tablet

Viewport内へ収まる幅に調整する。

ContentがViewport Heightを超える場合はDialog内部をScroll可能にする。

---

## 22.3 Mobile

Desktop用固定幅Dialogを単純に縮小しない。

以下を候補とする。

- Viewport幅を広く利用するDialog
- Full-screenに近いDialog
- Sheet / Drawer

Feature責務はDialogのまま維持する。

---

# 23. Mobile Dialogの採用判断

以下の場合はFull-screenに近いDialogを優先してよい。

- Input Fieldが複数ある
- Keyboard表示時にContent領域が狭くなる
- Error Messageを表示する必要がある
- Scroll量が多い

以下の場合は通常幅Dialogでもよい。

- 確認中心
- Field数が非常に少ない
- Contentが短い

---

# 24. Dialog Scroll

Dialog HeightがViewportを超える場合は、

```text
Dialog Header
Scrollable Content
Dialog Footer
```

の構成を候補とする。

Footerを固定する場合も、Form FieldやErrorが隠れないようにする。

---

# 25. Dialog Action

Desktop:

```text
[ キャンセル ] [ 保存 ]
```

Mobile:

```text
[ 保存             ]
[ キャンセル       ]
```

としてよい。

Action順序の意味はApplication全体で統一する。

---

# 26. Alert Dialog

Alert DialogはViewportによって操作の意味を変更しない。

Desktopでは中央配置を基本とする。

MobileではViewport Widthを利用し、MessageとActionを読みやすくする。

破壊的ActionとCancelを誤操作しにくい配置とする。

---

# 27. Confirmation Message

MobileだからといってConfirmation Messageを省略しない。

特に以下は影響を十分説明する。

- 無効化
- 削除
- 権限変更
- 最後の権限管理可能Administratorに関する操作

---

# 28. Loading

Loading Stateの意味はViewportに依存しない。

Desktop:

```text
Table Skeleton
```

Mobile:

```text
Card Skeleton
```

のように表示形式を変えてよい。

---

# 29. Empty State

Desktopでは中央寄せまたはContent領域内に表示する。

Mobileでは1 Columnで表示する。

Actionがある場合はFull Width Buttonを利用してよい。

---

# 30. Error State

Error MessageとRetry ActionはViewportに関係なく認識可能にする。

Mobileでは長い技術説明を詰め込まず、必要な情報とActionを優先する。

---

# 31. Access Denied / Not Found

DesktopではMain Content中央付近に表示する。

Mobileでは1 Columnで表示する。

例:

```text
Icon

アクセスできません

このページを表示する
権限がありません。

[ ダッシュボードへ ]
[ 戻る ]
```

Statusの意味・ActionはDesktopと同じとする。

---

# 32. Dashboard

Dashboardは複数WidgetをGrid表示する場合、Viewportに応じてColumn数を変更する。

概念上:

```text
Desktop
3 Columns

Tablet
2 Columns

Mobile
1 Column
```

具体的なColumn数はWidget内容を基準に決定する。

固定で3 / 2 / 1にすることを必須としない。

---

# 33. Detail Page

Desktopでは情報Sectionを必要に応じてGrid配置してよい。

Mobileでは1 Columnを基本とする。

ActionはPage Header下部等へ移動してよい。

---

# 34. Employee詳細

DesktopではEmployee基本情報・Skill概要等をSectionとして配置する。

MobileではSectionを縦積みする。

Employee Skill編集Action等の主要Actionが見つけやすい状態を維持する。

---

# 35. Skill / Skill Category一覧

DesktopではTable形式を基本候補とする。

MobileではCard / List形式を優先候補とする。

Create ActionはPage Header下部等へ配置してよい。

登録・編集DialogのUI種別はViewportによって変更しない。

---

# 36. Access Control一覧

DesktopではTable形式を基本候補とする。

MobileではUser単位のCard / List形式を候補とする。

Role・Permission Management状態・編集Actionを優先表示する。

低優先度情報は省略してよい。

---

# 37. 情報優先順位

Mobileではすべての情報をDesktopと同じ密度で表示する必要はない。

以下の順に優先する。

1. Resource識別情報
2. 状態
3. Primary Action
4. 操作判断に必要な情報
5. 補助情報

省略した情報が重要な判断に必要な場合は、Detail画面等で確認できるようにする。

---

# 38. 非表示にしてよい情報

Mobileで非表示にする場合は以下を満たす。

- Primary情報ではない
- 操作判断に必須ではない
- 別画面で確認できる
- Accessibility上意味が欠落しない

単に横幅に収まらないという理由だけで重要情報を削除しない。

---

# 39. Text Overflow

長い文字列では以下を検討する。

- Wrap
- Truncate
- Tooltip
- Detail画面で全文表示

Resource Name等、識別に重要なTextを安易に切り捨てない。

---

# 40. Button

MobileではTap Targetを十分確保する。

Icon-only Buttonを利用する場合はAccessible Nameを必須とする。

Primary Actionは小さすぎるIcon Buttonにしない。

---

# 41. Dropdown Menu

MobileでもDropdown Menuを利用できるが、頻繁に利用するPrimary ActionをMenu内へ隠しすぎない。

例:

```text
[ 編集 ] [ その他 ]
```

Primary ActionとSecondary Actionを分離する。

---

# 42. Touch操作

MobileではMouse Hoverを前提としない。

Hoverでしか表示されない重要情報・Actionを作らない。

Tooltipは補助情報として扱い、操作成立に必須としない。

---

# 43. Keyboard表示

Mobile FormではVirtual Keyboard表示時に、

- Focus中Field
- Error Message
- Primary Action

が操作不能にならないようにする。

固定Footer等を採用する場合はKeyboardとの競合を確認する。

---

# 44. Scroll

MobileではPage Scrollを基本とする。

Nested Scrollを必要以上に増やさない。

Dialog等、Overlay内でのみ必要なScrollを利用する。

---

# 45. Sticky UI

以下ではSticky UIを検討してよい。

- 長いEmployeeSkill編集
- Mobileの重要Save Action
- Table Header

ただし、Viewportを圧迫する場合は採用しない。

MVPで一律のSticky方針を必須としない。

---

# 46. Modal / Sheetの多重表示

Mobile・Desktopを問わず、Dialog上からさらに通常Dialogを重ねることを基本としない。

例外として、重要操作の確認にAlert Dialogを利用する場合は許容する。

```text
Edit Dialog
    ↓
Alert Dialog
```

多重Overlayを常態化させない。

---

# 47. Orientation

Mobile / TabletのPortrait / Landscapeで基本Featureを利用可能とする。

特定Orientationだけを前提としない。

Landscape専用UIはMVPでは必須としない。

---

# 48. Zoom

Browser ZoomやOS ScalingによってLayoutが破綻しにくい構成とする。

固定Height・固定Widthへ過度に依存しない。

---

# 49. Accessibility

Responsive対応でもAccessibility要件を維持する。

以下を基本とする。

- Keyboard操作可能
- Focus可視化
- Accessible Name維持
- Semantic構造維持
- TableからCardへ変更してもLabel関係を維持
- Colorだけに依存しない
- LoadingをVisualだけで表現しない
- Touch Target確保
- Text Zoomへの対応
- Dialog Focus Management
- Reading Orderの維持

---

# 50. DOM順序

Visual OrderをResponsiveで変更する場合でも、Keyboard Focus・Screen ReaderのReading Orderが不自然にならないようにする。

CSSだけで大きく順序を入れ替える場合は注意する。

---

# 51. Desktop / Mobile間の機能差

MVPでは、Mobileだから主要Featureを利用できない状態を作らないことを基本とする。

例:

```text
Desktop
EmployeeSkill編集可能

Mobile
EmployeeSkill編集不可
```

のような機能差は原則設けない。

表示方式は異なっても、主要操作は完了可能とする。

---

# 52. Responsive Component責務

Application共通ComponentはViewportによるPresentation変更を担当してよい。

例:

```text
PageHeader
Desktop → 横配置
Mobile  → 縦配置
```

Feature ComponentはDomain Contextを維持する。

Responsive都合でDomain Ruleを持たせない。

---

# 53. Feature固有Responsive設計

本ドキュメントではApplication共通のResponsive方針を定義する。

各 `07_画面設計` では以下を追加定義する。

- 情報優先順位
- Mobileで省略するColumn
- Card / Tableどちらを使うか
- Feature固有Action配置
- 長いFormの扱い
- Feature固有DialogのContent量

共通ルールを各画面で再定義しない。

---

# 54. Breakpoint追加判断

Application独自Breakpointを追加する場合は以下を確認する。

1. Tailwind標準Breakpointで対応できないか
2. 特定Device専用になっていないか
3. 複数Componentで共通して必要か
4. Layout上の明確な切替理由があるか

Breakpoint数を必要以上に増やさない。

---

# 55. Responsive Test観点

Frontend実装時には少なくとも以下を確認する。

- Navigationが操作可能
- Main ContentがViewportからはみ出さない
- 横Scrollが意図しない箇所で発生しない
- Table / Cardが読める
- Form Fieldが操作可能
- Validation Errorが読める
- DialogがViewport内で操作可能
- Save / Cancelが操作可能
- Keyboard Navigationが成立する
- Mobile Touch操作が成立する

---

# 56. MVPで扱わないもの

現時点では以下をResponsive Designの必須対象としない。

- Native Mobile App専用UI
- Tablet専用Feature
- Deviceごとの個別Layout
- Userが選択するCompact Mode
- Userが選択するDensity Mode
- Custom Breakpoint大量追加
- Gesture専用操作
- Mobile専用Bottom Navigation
- Desktop専用Keyboard Shortcut体系
- Foldable Device専用Layout

必要性が明確になった場合に別途検討する。

---

# 57. 本ドキュメントで定義しないもの

以下はFrontend実装設計を正とする。

- Tailwind CSSの具体的なBreakpoint値
- Media Queryの具体実装
- CSS Class
- Container Widthの具体値
- Dialog Widthの具体値
- Grid Columnの具体値
- Sticky Positionの具体値
- React Component実装
- Server / Client Component境界
- Browser Support Matrix
- Visual Regression Test Tool
- E2E Test実装

Phase 1ではResponsive UIの意味・Layout変化・判断基準を定義する。
