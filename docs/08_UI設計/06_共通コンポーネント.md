# 共通コンポーネント

## 1. 目的

本ドキュメントは、Engineer Skill Management App のMVPで共通して利用するUI ComponentおよびUI Patternを定義する。

主に以下を整理する。

- 採用するshadcn/ui Component
- Application共通Component
- Componentの責務
- Componentの利用基準
- Variant
- Accessibility
- Responsive時の基本方針

個別画面固有のComponentについては `07_画面設計/` で定義する。

---

## 2. 基本方針

UI Componentは以下の構成を基本とする。

```text
Application画面
      ↓
Application共通Component
      ↓
shadcn/ui
      ↓
Base UI
      ↓
Tailwind CSS v4
      ↓
Design Token
```

すべてのUIをApplication共通ComponentでWrappingすることはしない。

単純なButton・Input等については、shadcn/ui Componentを直接利用してよい。

Application固有の意味・振る舞い・複数Componentの組み合わせを共通化する必要がある場合に、Application共通Componentを作成する。

---

## 3. Component追加ルール

新しいUI Componentが必要になった場合は、以下の順序で検討する。

1. 既存のshadcn/ui Componentで実現できるか
2. 既に導入済みのApplication共通Componentで実現できるか
3. 複数のshadcn/ui Componentを組み合わせれば実現できるか
4. Base UIを直接利用する必要があるか
5. 新しいLibraryが本当に必要か

shadcn/ui Componentは一括導入しない。

必要性が確認できたComponentのみ追加する。

---

## 4. shadcn/ui Component一覧

MVPで利用するComponentを以下の分類で管理する。

```text
Action
├── Button

Form
├── Input
├── Textarea
├── Select
├── Checkbox
├── Radio Group
└── Label

Navigation
├── Breadcrumb
├── Dropdown Menu
└── Pagination

Data Display
├── Table
├── Badge
├── Card
└── Separator

Feedback
├── Alert
├── Skeleton
└── Tooltip

Overlay
├── Dialog
├── Alert Dialog
└── Sheet
```

この一覧はMVPで利用する可能性が高いComponentを整理したものであり、実装開始時に全Componentを一括導入することを意味しない。

---

## 5. Button

### 5.1 用途

ButtonはActionを実行する操作に利用する。

例:

- 登録
- 保存
- 編集
- キャンセル
- 検索
- Filter
- 無効化

Navigationのみを目的とする場合は、ButtonではなくLinkを優先する。

---

### 5.2 Variant

基本的に以下の意味を区別する。

```text
Primary
Secondary
Destructive
Ghost
Icon-only
```

具体的なshadcn/ui Variant名とApplication上の意味は実装時に対応付ける。

---

### 5.3 Primary Action

画面内で最も重要なActionに利用する。

例:

- 社員登録
- 保存
- スキル登録

同一領域にPrimary Actionを複数並べすぎない。

---

### 5.4 Destructive Action

以下のような影響の大きいActionに使用する。

- 無効化
- 削除
- 重要な権限変更

Domain上の意味が「無効化」である場合は、Button Labelを「削除」としない。

---

### 5.5 Icon-only Button

IconのみのButtonは、表示領域上の理由等でTextを併記できない場合に限定する。

Accessible Nameを必須とする。

---

## 6. Input

Inputは1行Text入力に利用する。

例:

- 社員名
- スキル名
- 検索Keyword

以下を基本とする。

```text
Label
Input
Description
Error Message
```

必要な要素のみ表示する。

PlaceholderのみをLabelの代替として利用しない。

---

## 7. Textarea

Textareaは複数行Textが必要な場合のみ利用する。

MVPで対象項目が存在しない場合は導入しない。

単に将来必要になる可能性だけを理由として導入しない。

---

## 8. Select

Selectは、あらかじめ定義された候補から単一値を選択する場合に利用する。

想定例:

- Role
- Skill Category
- Skill Level
- Employment Status

選択肢が少なく、一覧性が重要な場合はRadio Groupの方が適切か検討する。

---

## 9. Checkbox

Checkboxは独立したBoolean値に利用する。

想定例:

```text
権限管理可能
can_manage_permissions
```

複数候補から1つだけ選択する用途には使用しない。

---

## 10. Radio Group

相互排他的な少数の選択肢から1つを選ぶ場合に利用する。

Selectより選択肢を常時確認できることに価値がある場合に採用する。

想定例:

- 実務経験あり / なし

ただし、個別画面の情報量を踏まえてSelect等との比較を行う。

---

## 11. Label

Form Controlには原則としてLabelを関連付ける。

Labelの表示だけでは必須・任意や入力条件が不明な場合は、Description等を併用する。

Semanticな `label` との関連付けを維持する。

---

## 12. Breadcrumb

Breadcrumbは現在位置と親画面を示すために利用する。

`04_共通レイアウト.md` で定義した構造を基準とする。

例:

```text
Employees > 社員名 > 編集
```

現在ページ以外で遷移可能な項目はLinkとする。

現在ページはLinkにしない。

---

## 13. Dropdown Menu

Dropdown Menuは、関連する複数Actionを省スペースで提供する場合に利用する。

想定例:

- User Menu
- Secondary Action群

Primary ActionをDropdown Menu内に隠すことは避ける。

---

## 14. Pagination

一覧データのページ切り替えに利用する。

Paginationでは以下を利用者が把握できるようにする。

- 現在ページ
- 前後への移動
- 必要に応じて総ページまたは総件数

具体的なPage SizeやAPI Query ParameterはAPI仕様を正とする。

---

## 15. Table

### 15.1 基本方針

一覧形式のStructured DataにはTableを利用する。

可能な限りSemanticなHTML Tableを維持する。

---

### 15.2 Table構造

基本構造は以下とする。

```text
Table
├── Header
├── Row
│   ├── Data
│   └── Action
└── ...
```

Action Columnを設ける場合は、データColumnと区別できる構成とする。

---

### 15.3 Row Action

編集等のActionが1つだけの場合は、明示的なActionを配置してよい。

複数Actionがある場合はDropdown Menu等への整理を検討する。

Row全体Clickと個別Buttonを混在させる場合は、操作の曖昧さに注意する。

---

### 15.4 Empty

データが存在しない場合に空Tableだけを表示しない。

Application共通の `EmptyState` を利用する。

---

## 16. Badge

Badgeは短い状態・分類情報を表示する。

想定例:

- 在籍
- 退職
- 有効
- 無効
- Role
- Skill Level

状態はTextを必ず含め、Colorだけに依存しない。

---

## 17. Card

Cardは関連する情報をGroup化する必要がある場合に利用する。

想定例:

- Dashboard Widget
- Employee Detailの情報Group

すべての情報をCardで囲むことは避ける。

SpacingやHeadingだけで十分に区別できる場合はCardを利用しない。

---

## 18. Separator

Separatorは視覚的に情報Groupを区切る必要がある場合に利用する。

Spacingだけで十分な場合は利用しない。

---

## 19. Alert

Alertは画面内で継続して表示する必要がある重要情報に利用する。

例:

- Error
- Warning
- 注意事項
- 権限制約

一時的な操作成功通知とは責務を分ける。

---

## 20. Skeleton

SkeletonはData取得中にContentの構造を維持しながらLoadingを示す場合に利用する。

利用候補:

- Table
- Detail
- Dashboard

短時間の単純なButton処理等でSkeletonを使用しない。

---

## 21. Tooltip

Tooltipは補助情報に利用する。

Tooltipがなければ操作の意味を理解できないUIは避ける。

Accessible NameやLabelの代替として利用しない。

---

## 22. Dialog

Dialogは、現在の画面Contextを維持したまま補助操作を行う場合に利用する。

想定例:

- 補足情報
- 小規模な操作

入力項目の多い登録・編集FormをDialogへ押し込むことは避け、独立した画面を基本とする。

---

## 23. Alert Dialog

Alert Dialogは、利用者による明示的な確認が必要な重要Actionに利用する。

想定例:

- スキル無効化
- スキルカテゴリ無効化
- 重要な権限変更
- 復元困難な削除操作

単純な保存・通常更新に毎回Alert Dialogを表示しない。

---

## 24. Sheet

SheetはDesktop以外でのNavigationや補助UIに利用する候補とする。

主な利用候補:

```text
Mobile Navigation
```

Desktopの主要ContentをSheetへ配置することは基本としない。

採用可否はResponsive設計で最終決定する。

---

# 25. Application共通Component

Application固有の共通Componentは以下を基本候補とする。

```text
AppShell
AppHeader
AppSidebar

PageHeader

DataTable
SearchFilter

EmptyState
ErrorState

StatusBadge

ConfirmDialog

FormField
```

実装段階で責務が十分に共通化できないことが判明した場合は、無理に共通Component化しない。

---

## 26. AppShell

### 26.1 責務

認証後画面の共通Layoutを提供する。

構造:

```text
AppShell
├── AppHeader
├── AppSidebar
└── Main
```

Layoutの詳細は `04_共通レイアウト.md` を正とする。

---

## 27. AppHeader

App全体のHeaderを提供する。

主な責務:

- Application表示
- Mobile Navigation Toggle
- User Menu

User Menuにはshadcn/ui Dropdown Menuの利用を基本候補とする。

---

## 28. AppSidebar

主要Navigationを提供する。

主な責務:

- Navigation表示
- Active状態
- Role / Permissionによる表示制御
- Navigation Group

Backend認可の代替とはしない。

---

## 29. PageHeader

### 29.1 責務

各画面の共通Page Header構造を提供する。

構造:

```text
PageHeader
├── Title
├── Description
└── Action
```

---

### 29.2 利用例

```text
社員一覧                         [社員登録]
社員情報を検索・確認できます
```

DescriptionやActionが存在しない場合にも利用可能な構造とする。

---

## 30. DataTable

### 30.1 責務

Applicationで利用する一覧Tableの共通Patternを提供する。

shadcn/ui Tableを基盤とする。

---

### 30.2 対象

想定画面:

- 社員一覧
- スキル一覧
- スキルカテゴリ一覧
- ユーザー・権限一覧

---

### 30.3 共通化対象

以下を共通Patternとして扱う。

- Header
- Row
- Empty State
- Action Column
- Responsive時のContainer
- Loading表示との連携

Search・Filter・PaginationをDataTable自身へ過度に内包しない。

それぞれの責務を分離する。

---

## 31. SearchFilter

### 31.1 責務

一覧画面で利用する検索・Filter領域の共通Layoutを提供する。

想定構造:

```text
SearchFilter
├── Keyword
├── Filter
└── Clear
```

画面ごとにFilter項目が異なるため、具体的Fieldを固定しない。

---

### 31.2 利用対象

想定:

- 社員一覧
- スキル一覧

必要のない画面へ形式的に配置しない。

---

## 32. EmptyState

### 32.1 責務

データが存在しない状態を共通表現する。

基本構造:

```text
EmptyState
├── Icon
├── Title / Message
├── Description
└── Action
```

必要な要素のみ利用する。

---

### 32.2 例

```text
登録されている社員がありません。

[ 社員を登録 ]
```

ユーザーに登録権限がない場合は、登録Actionを表示しない。

---

## 33. ErrorState

### 33.1 責務

画面またはSection単位でData取得等に失敗した状態を表現する。

基本構造:

```text
ErrorState
├── Message
├── Description
└── Retry Action
```

再試行できない場合はRetry Actionを表示しない。

---

### 33.2 Field Errorとの違い

FormのValidation Errorには使用しない。

```text
ErrorState
    ↓
画面 / Section

Form Error
    ↓
Field
```

として責務を分ける。

---

## 34. StatusBadge

### 34.1 責務

Domain上の状態をApplication全体で統一したBadgeとして表示する。

想定対象:

- Employment Status
- Skill有効 / 無効
- Skill Category有効 / 無効
- User Status
- Role

---

### 34.2 基本方針

同じDomain状態は全画面で同じLabel・表現を使用する。

例:

```text
EmploymentStatus.ACTIVE
        ↓
      在籍
```

```text
EmploymentStatus.RETIRED
        ↓
      退職
```

Domain上異なる状態を同一の表示名へ安易にまとめない。

---

## 35. ConfirmDialog

### 35.1 責務

Applicationで影響の大きいActionを確認する共通Dialog Patternを提供する。

shadcn/ui Alert Dialogを基盤とする。

---

### 35.2 基本構造

```text
ConfirmDialog
├── Title
├── Description
├── Cancel
└── Confirm
```

Confirm ActionがDestructiveな場合は、視覚的にも区別する。

---

### 35.3 Message

確認Messageでは、可能な限り以下を明確にする。

- 何を変更するか
- 対象は何か
- 実行するとどうなるか

抽象的な、

```text
本当に実行しますか？
```

だけで済ませない。

---

## 36. FormField

### 36.1 責務

Form Fieldの共通構造を統一する。

基本構造:

```text
FormField
├── Label
├── Control
├── Description
└── Error Message
```

すべてのFieldを独自ComponentとしてWrapper化すること自体を目的としない。

利用するForm Libraryや実装方式との整合を踏まえて、実装段階で最終構造を決定する。

---

## 37. Notification

登録・更新等の成功を一時的に通知する仕組みが必要となる。

想定例:

```text
社員を登録しました
社員情報を更新しました
スキルを無効化しました
```

ただし、具体的なNotification / Toast Componentは、この段階では確定しない。

shadcn/uiおよび既存Frontend技術構成で利用可能な選択肢を、実装前に確認して決定する。

重要なErrorを一時的なNotificationだけで伝えることは避ける。

---

## 38. Loading Component

Loadingは処理範囲に応じて使い分ける。

```text
Page Loading
Section Loading
Table Loading
Action Loading
```

全種類を1つの共通Componentに統一することはしない。

Skeleton、ButtonのDisabled / Loading State等を組み合わせる。

---

## 39. Page Loading

Page Header等の構造を可能な限り維持し、Page Content側でLoadingを表現することを基本とする。

画面全体を単一Spinnerへ置き換えることは避ける。

---

## 40. Action Loading

登録・更新等のAction実行中は、二重送信を防止する。

基本方針:

- 対象ActionをDisabledにする
- 実行中であることを識別可能にする
- Form全体を必要以上に操作不能にしない

---

## 41. Componentと権限

共通Component自身へApplication全体の認可ロジックを過度に持たせない。

例:

```text
PageHeader
```

自体がRoleを判定して社員登録Buttonを生成するのではなく、

```text
画面側
  ↓
Permission判定
  ↓
表示するActionを決定
  ↓
PageHeaderへ渡す
```

構成を基本とする。

これによりComponentの責務をPresentationへ限定する。

---

## 42. ComponentとDomain

共通ComponentへDomain Ruleを直接実装しない。

例:

```text
SkillLevel Select
```

について、未経験時はLevel 1のみというRuleをSelect Componentそのものへ埋め込まず、個別画面・Form Logic側で制御する。

共通ComponentはUI表現を担当する。

---

## 43. ComponentとAPI

共通UI Componentから直接Backend APIを呼び出すことを基本としない。

```text
UI Component
    ↓
Application Logic
    ↓
BFF / API Client
```

という責務分離を維持する。

---

## 44. Responsive

ComponentはResponsive時に利用不能にならない構造とする。

特に以下を確認する。

- Button
- PageHeader
- SearchFilter
- DataTable
- Dialog
- Navigation
- Form

Mobile固有の大幅な構造変更については `09_レスポンシブ設計.md` で定義する。

---

## 45. Accessibility

共通Componentでは、shadcn/ui / Base UIが提供するAccessibilityを活用しつつ、Application側でも以下を担保する。

- Semantic HTML
- Label
- Accessible Name
- Keyboard Operation
- Focus
- Error Message
- Disabled State
- Loading State

shadcn/uiを利用するだけでAccessibility対応が完了したものとは扱わない。

---

## 46. Component命名

Application共通Componentは、その責務が分かる名称を利用する。

例:

```text
PageHeader
DataTable
EmptyState
ErrorState
StatusBadge
ConfirmDialog
```

以下のような抽象度が高すぎる名称は避ける。

```text
CommonComponent
BaseComponent
CustomComponent
```

---

## 47. Component配置

具体的なDirectory構成はFrontend Architectureを正とする。

UI設計側では、

```text
shadcn/ui Component
```

と、

```text
Application共通Component
```

の責務を区別する。

UI設計だけを理由として既存Frontend Architectureを変更しない。

---

## 48. MVPで導入しないもの

現時点では、以下をMVPの共通UIとして前提としない。

- Drag & Drop
- Rich Text Editor
- Complex Data Grid
- Tree View
- Carousel
- Command Palette
- Multi-Step Wizard
- 高度なChart Library
- Animation Library

個別要件が発生した場合に改めて検討する。

---

## 49. shadcn/ui導入候補まとめ

現時点のMVP設計から、導入候補を以下とする。

| Component | 主な用途 | 導入判断 |
| --- | --- | --- |
| Button | Action | 必要 |
| Input | Text入力・検索 | 必要 |
| Select | 選択入力 | 必要 |
| Checkbox | Boolean入力 | 必要 |
| Radio Group | 少数選択肢 | 必要時 |
| Label | Form Label | 必要 |
| Breadcrumb | 現在位置 | 必要 |
| Dropdown Menu | User Menu等 | 必要 |
| Pagination | 一覧Pagination | 必要 |
| Table | 一覧 | 必要 |
| Badge | Status | 必要 |
| Card | Dashboard等 | 必要時 |
| Separator | 情報区切り | 必要時 |
| Alert | Error / Warning | 必要 |
| Skeleton | Loading | 必要 |
| Tooltip | 補助情報 | 必要時 |
| Dialog | 補助操作 | 必要時 |
| Alert Dialog | 重要操作確認 | 必要 |
| Sheet | Mobile Navigation | Responsive設計で判断 |
| Textarea | 複数行入力 | 要件発生時 |

「必要」としているComponentについても、実装開始時に必要になったタイミングで追加する。

---

## 50. Application共通Componentまとめ

MVPで以下を基本候補とする。

| Component | 主な責務 |
| --- | --- |
| AppShell | 認証後共通Layout |
| AppHeader | Header / User Menu |
| AppSidebar | Main Navigation |
| PageHeader | Page Title / Description / Action |
| DataTable | Application一覧Table Pattern |
| SearchFilter | Search / Filter領域 |
| EmptyState | Empty表示 |
| ErrorState | Page / Section Error |
| StatusBadge | Domain Status表示 |
| ConfirmDialog | 重要Action確認 |
| FormField | Form Field共通構造 |

実装前または個別画面設計時に共通性がないと判断したものは、Application共通Componentから除外してよい。

---

## 51. 技術構成まとめ

共通Componentの構成は以下を基本とする。

```text
Individual Page
      ↓
Application Common Component
      ↓
shadcn/ui Component
      ↓
Base UI
      ↓
Tailwind CSS v4
      ↓
CSS Variables / Design Token

      +

Lucide / lucide-react

      +

cn
```

複数のUI Component Library、Primitive Library、Icon Libraryを理由なく併用しない。

---

## 52. 今後の設計との関係

本ドキュメントで定義した共通Componentを基準として、個別画面設計を進める。

```text
06_共通コンポーネント
    ↓
07_画面設計
    ↓
08_UI状態設計
    ↓
09_レスポンシブ設計
```

個別画面設計中に新しい共通Patternが複数画面で必要と判明した場合は、本ドキュメントへの追加を検討する。

一方、1画面のみで利用するUIを将来利用する可能性だけを理由として共通化しない。
