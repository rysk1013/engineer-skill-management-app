# 共通コンポーネント

## 1. 目的

本ドキュメントは、Engineer Skill Management App のMVPで利用する共通UIコンポーネントの設計方針を定義する。

以下を整理する。

- shadcn/ui Componentの利用方針
- Component分類
- Application共通Component
- Feature固有Component
- Form Component
- Data Display Component
- Feedback Component
- Dialog / Alert Dialog
- Permissionとの責務分離
- API連携との責務分離
- Responsive対応
- Accessibility
- Component追加・共通化の判断基準

本ドキュメントを、Frontend実装におけるComponent設計の共通基準とする。

---

# 2. 基本方針

UI Componentは以下の階層で構成する。

```text
Application Page
    ↓
Feature Component
    ↓
Application共通Component
    ↓
shadcn/ui
    ↓
Base UI
    ↓
Tailwind CSS
    ↓
Design Token
```

すべてのUIを独自実装せず、shadcn/uiを基本として利用する。

一方、Application固有の責務を持つUIは、必要に応じてApplication共通ComponentまたはFeature固有Componentとして定義する。

共通化そのものを目的とせず、責務が明確な単位でComponentを分割する。

---

# 3. Component分類

MVPではComponentを以下の3種類に分類する。

```text
UI Primitive / Base Component
    └── shadcn/ui

Application共通Component
    └── 複数Feature・複数画面で共通利用するUI

Feature固有Component
    └── 特定FeatureのDomain・操作Contextに依存するUI
```

---

## 3.1 UI Primitive / Base Component

汎用的なUI Primitiveとしてshadcn/uiを利用する。

例:

- Button
- Input
- Select
- Dialog
- Table
- Badge

Application固有のDomain Logicは持たせない。

---

## 3.2 Application共通Component

複数Feature・複数画面で同じ責務を持つUIをApplication共通Componentとして扱う。

例:

- AppShell
- PageHeader
- DataTable
- EmptyState
- ErrorState

---

## 3.3 Feature固有Component

特定FeatureのDomain・操作Contextに依存するComponentとする。

例:

- EmployeeCreateDialog
- EmployeeEditDialog
- SkillCreateDialog
- SkillEditDialog
- SkillCategoryCreateDialog
- SkillCategoryEditDialog
- AccessControlForm

Feature固有Componentを無理にApplication共通Componentへ昇格させない。

---

# 4. shadcn/ui利用方針

## 4.1 基本方針

shadcn/uiをApplication UI Componentの基本とする。

必要なComponentのみ追加する。

MVP開始時にすべてのshadcn/ui Componentを一括導入しない。

---

## 4.2 Component追加

各画面・Feature実装時に必要になったComponentを追加する。

例:

```text
一覧画面実装
    ↓
Tableが必要
    ↓
Tableを追加
```

```text
登録Dialog実装
    ↓
Dialogが必要
    ↓
Dialogを追加
```

将来利用する可能性だけを理由にComponentを追加しない。

---

## 4.3 Customization

shadcn/ui ComponentはApplication Sourceとして管理されるため、必要に応じて変更可能とする。

ただし、場当たり的な変更を避け、以下を優先する。

- Design Token
- Variant
- Application共通Component
- Feature固有Component
- Tailwind CSS

shadcn/ui Component本体へDomain固有ロジックを追加しない。

# 6. Application共通Component

Application全体または複数Featureで共通利用するComponentをApplication共通Componentとして定義する。

候補は以下とする。

```text
Application共通Component
├── AppShell
├── AppHeader
├── AppSidebar
├── PageHeader
├── DataTable
├── SearchFilter
├── EmptyState
├── ErrorState
├── StatusBadge
├── ConfirmDialog
└── FormField
```

共通化は、見た目が似ていることだけを理由に行わない。

複数箇所で同じ責務・同じ操作意味を持つ場合に共通化する。

---

# 7. AppShell

## 7.1 責務

認証後画面の共通Layoutを提供する。

```text
AppShell
├── AppHeader
├── AppSidebar
└── Main Content
```

以下はAppShellの責務としない。

- Domain Data取得
- Permission判定そのもの
- Feature固有Action
- Form State
- API通信

---

# 8. AppHeader

## 8.1 責務

Application Headerを提供する。

主な責務:

- Application Name
- Navigation Menu起動
- User Menu
- Logoutへの導線

Feature固有ActionはAppHeaderへ配置しない。

---

# 9. AppSidebar

## 9.1 責務

主要Navigationを提供する。

表示候補:

```text
Dashboard

Employee
└── 社員一覧

Skill
├── スキル一覧
└── スキルカテゴリ一覧

Administration
└── アクセス制御
```

Navigation Itemの表示可否は上位のApplication Logicから与えられた状態を利用する。

AppSidebar自身に認可Domain Logicを持たせない。

---

# 10. PageHeader

## 10.1 責務

各PageのTitle・Description・Primary Actionを統一したLayoutで表示する。

基本構造:

```text
PageHeader
├── Title
├── Description
└── Actions
```

---

## 10.2 利用例

一覧画面:

```text
社員一覧                         [ 社員登録 ]
```

```text
スキル一覧                     [ スキル登録 ]
```

```text
スキルカテゴリ一覧             [ カテゴリ登録 ]
```

詳細画面:

```text
山田 太郎                           [ 編集 ]
```

---

## 10.3 Action

PageHeaderはActionの表示領域のみ担当する。

以下の責務は持たない。

- Permission判定
- Dialog State管理
- Backend API呼び出し
- Domain Rule

Action自体はPageまたはFeature Componentから渡す。

---

# 11. DataTable

## 11.1 責務

一覧画面で共通利用するTable表示を提供する。

候補:

- Header
- Row
- Empty State
- Loading State
- Paginationとの配置

---

## 11.2 Domain依存

DataTable自身に特定DomainのRuleを持たせない。

例:

```text
Employee Feature
    ↓
Employee Column定義
    ↓
DataTable
```

```text
Skill Feature
    ↓
Skill Column定義
    ↓
DataTable
```

```text
Skill Category Feature
    ↓
Skill Category Column定義
    ↓
DataTable
```

表示内容・Action・状態判定はFeature側で決定する。

---

# 12. SearchFilter

## 12.1 責務

一覧画面で利用する検索・Filter領域の共通Layoutを提供する。

候補:

- Keyword Input
- Select Filter
- Search Action
- Reset Action

---

## 12.2 Domain依存

具体的な検索条件はFeature側で定義する。

SearchFilter内部へEmployee・Skill等の検索仕様を直接持たせない。

---

# 13. EmptyState

## 13.1 責務

表示対象が存在しない状態を分かりやすく表現する。

基本構造:

```text
EmptyState
├── Title
├── Description
└── Action
```

Actionは任意とする。

---

## 13.2 利用例

```text
対象データが登録されていません。

[ 登録 ]
```

登録権限がない場合はActionを表示しない。

検索結果0件の場合は、Resourceそのものが存在しない状態と区別する。

---

# 14. ErrorState

## 14.1 責務

PageまたはSection単位で情報取得に失敗した場合のFeedbackを提供する。

基本構造:

```text
ErrorState
├── Message
└── Retry Action
```

技術的なBackend Error Messageをそのまま表示しない。

---

# 15. StatusBadge

## 15.1 責務

状態値を視覚的に分かりやすく表示する。

対象候補:

- Employee Employment Status
- Skill Active / Inactive
- Skill Category Status
- User Status

---

## 15.2 Semantic State

状態表示はDesign SystemのSemantic Colorを利用する。

色だけで状態を表現せず、Text Labelを併用する。

具体的な状態とVisualの対応はFeature側で決定する。

---

# 16. FormField

## 16.1 目的

Form Fieldに必要な要素を一貫したLayoutで表示する。

```text
Label
Control
Description
Error Message
```

---

## 16.2 基本構造

```text
FormField
├── Label
├── Input / Select / etc.
├── Description
└── Validation Error
```

---

## 16.3 共通化方針

Form Library・Validation Libraryの採用状況によって、最終的なComponent構造が変わる可能性がある。

Phase 1では責務のみ定義し、特定Libraryに強く依存するWrapperを確定しない。

Field単位の共通化が実装を複雑にする場合は、無理にWrapper化しない。

---

# 17. Form設計

## 17.1 基本方針

FormはFeature固有のUse Caseを表現するため、Form全体をApplication共通Componentとして扱うことを基本としない。

例:

- Employee登録Form
- Employee編集Form
- Skill登録Form
- Skill編集Form
- Skill Category登録Form
- Skill Category編集Form
- Access Control編集Form

それぞれのDomain・Validation・Submit処理はFeature側で管理する。

---

## 17.2 共通化対象

Form全体ではなく、以下のようなUI責務を共通化する。

- FormField Layout
- Label
- Input
- Select
- Error Message
- Action Layout

---

## 17.3 Create / Edit

CreateとEditは異なるUse Caseとして扱う。

Fieldが共通している場合でも、初期段階からForm全体を1つへ統合しない。

実装時に重複が明確になった場合のみ共通Field Component等を検討する。

---

# 18. Feature固有Component

## 18.1 基本方針

Domainまたは操作Contextに依存するUIはFeature固有Componentとして扱う。

例:

```text
Employee
├── EmployeeCreateDialog
└── EmployeeEditDialog

Skill
├── SkillCreateDialog
└── SkillEditDialog

Skill Category
├── SkillCategoryCreateDialog
└── SkillCategoryEditDialog

Access Control
└── AccessControlForm
```

Employee Skillについては独立画面上のFeature固有Formとして扱う。

具体的なComponent構造は各個別画面設計およびFrontend実装時に決定する。

---

## 18.2 Application共通Componentとの境界

Feature固有ComponentはApplication共通Componentを組み合わせて利用する。

```text
Feature Component
├── PageHeader
├── FormField
├── StatusBadge
├── Dialog
└── Button
```

Application共通Component側からFeature固有Domainへ依存しない。

---

# 19. Dialog

## 19.1 目的

元画面のContextを維持したまま完結できる比較的小規模な登録・編集操作に利用する。

MVPではEmployee・Skill・Skill Categoryの一部登録・編集操作で利用する。

---

## 19.2 利用判断

以下を満たす操作ではDialogを候補とする。

- 元画面との関連が強い
- 入力項目が比較的少ない
- 操作が単純
- 完了後に元画面または関連画面へ戻る
- 独立した作業Contextを必要としない

---

## 19.3 Dialogを利用しない場合

以下の場合は独立画面を優先する。

- 入力項目が多い
- 複数Sectionを扱う
- 複数Resourceを操作する
- 複数項目の追加・編集を繰り返す
- Dialog内では操作領域が不足する
- Mobileで操作性が著しく低下する
- 独立した作業Contextを持たせた方が理解しやすい
- 権限変更等、操作の意味・影響・制約を十分確認する必要がある

---

## 19.4 Primitive

shadcn/uiの `Dialog` を基本候補とする。

---

## 19.5 基本構造

```text
Dialog
├── Dialog Header
│   ├── Title
│   └── Description
│
├── Dialog Content
│   └── Form / Content
│
└── Dialog Footer
    ├── Cancel
    └── Primary Action
```

---

## 19.6 Route

通常のDialog Open / CloseによってFrontend Routeを変更しないことを基本とする。

Dialog StateをQuery ParameterやParallel Route等と同期する高度なRoutingはMVPの必須要件としない。

---

# 20. Dialog State

## 20.1 Open / Close

DialogのOpen StateはPageまたはFeature Componentが管理することを基本とする。

```text
Page
  ↓
Feature Dialog
```

---

## 20.2 Validation Error

Validation Error発生時はDialogを閉じない。

対象Field付近へErrorを表示し、入力内容を可能な限り維持する。

---

## 20.3 API Error

予期しないAPI Error発生時もDialogを閉じないことを基本とする。

入力内容を維持し、再試行可能な状態とする。

---

## 20.4 Submit Loading

Submit中はPrimary Actionの二重実行を防止する。

例:

```text
[ キャンセル ] [ 登録中... ]
```

```text
[ キャンセル ] [ 保存中... ]
```

---

## 20.5 Success

正常完了時はFeature固有の遷移・再取得方針に従う。

候補:

- Dialogを閉じて現在画面を再取得
- Dialogを閉じて関連する詳細画面へ遷移
- Dialogを閉じて一覧を更新

具体的な動作は個別画面設計で定義する。

---

# 21. Dialog Close

Dialogを閉じる操作として以下を想定する。

- Cancel
- Close Button
- Escape
- Backdrop Click
- Submit Success

Escape / Backdrop Clickを常に許可するかは、未保存入力の扱いと合わせて個別に決定する。

MVPでは複雑なUnsaved Changes Guardを全Dialogへ一律導入しない。

---

# 22. Alert Dialog

## 22.1 目的

破壊的または影響の大きい操作について、実行前確認を行う。

利用候補:

- 無効化
- 削除
- 再有効化
- 重要な状態変更

---

## 22.2 Primitive

shadcn/uiの `Alert Dialog` を基本候補とする。

---

## 22.3 基本構造

```text
Alert Dialog
├── Title
├── Description
├── Cancel
└── Confirm
```

---

## 22.4 Domain依存

Alert Dialog自体に特定Domainの処理を持たせない。

MessageやActionはFeature側から与える。

---

# 23. DialogとAlert Dialogの使い分け

以下を基本とする。

```text
通常の登録・編集Form
    ↓
Dialog

破壊的・重要操作の確認
    ↓
Alert Dialog
```

通常の入力Form全体をAlert Dialogで実装しない。

単なる情報表示のためだけにDialogを多用しない。

---

# 24. ConfirmDialog

## 24.1 目的

複数Featureで同じ確認UIが必要になる場合は、Application共通Componentとして `ConfirmDialog` を検討する。

---

## 24.2 責務

```text
ConfirmDialog
├── Title
├── Description
├── Cancel Label
├── Confirm Label
└── Action Variant
```

特定のDomain Ruleは持たせない。

---

## 24.3 共通化判断

Alert Dialogを直接利用するだけで十分な場合は、ConfirmDialogを追加しない。

複数Featureで同じ責務が実際に発生してから共通化する。

---

# 25. Table / List

## 25.1 基本方針

一覧表示は情報量・Viewportに応じてTableまたは別のList表現を利用する。

DesktopではTableを基本候補とする。

---

## 25.2 Mobile

Mobileで横幅が不足する場合は以下を検討する。

- 表示Column削減
- 横Scroll
- Card / List表示

すべてのTableを自動的にCardへ変換する共通Componentは作成しない。

各Featureの情報優先度に応じて判断する。

---

# 26. Pagination

Paginationは一覧画面で共通利用する。

具体的なPage SizeやPagination方式はBackend API仕様を正とする。

UI側で独自のPagination Ruleを追加しない。

---

# 27. Loading

## 27.1 Page / Section Loading

Data取得中はSkeletonを基本候補とする。

```text
Page
├── Header
└── Skeleton
```

単一SpinnerのみでPage全体を置き換えることを標準としない。

---

## 27.2 Action Loading

登録・更新等のAction実行中は以下を基本とする。

- Primary Actionの二重実行防止
- Loading状態の明示
- 入力内容の維持

---

# 28. Feedback

## 28.1 Error

Errorの種類に応じて以下を使い分ける。

```text
Field Validation Error
    ↓
Form Field付近

Section / Page Error
    ↓
ErrorState / Alert

Operation Error
    ↓
現在Context内のFeedback
```

---

## 28.2 Success

登録・更新等の成功を通知する場合は、Application共通Feedback UIとして扱う。

例:

```text
登録しました。
```

```text
更新しました。
```

具体的なNotification / Toast ComponentはFrontend実装時点で採用技術の現行状況を確認して決定する。

Phase 1では特定Componentへ固定しない。

---

# 29. PermissionとComponent

ComponentはPermission判定そのものを担当しない。

例:

```text
Page / Feature Logic
    |
    | Permission判定
    v
Actionを表示する / しない
```

PageHeader・DataTable・Dialog等のPresentation Component内部にDomain認可Ruleを埋め込まない。

Frontendの表示制御はUX上の制御であり、最終的な認可はBackendを正とする。

---

# 30. Domain RuleとComponent

汎用ComponentへDomain Ruleを埋め込まない。

悪い例:

```text
DataTable
└── Employeeが退職済みなら独自処理
```

推奨:

```text
Employee Feature
    ↓
表示状態を決定
    ↓
DataTable
```

同様に、

```text
StatusBadge
Dialog
FormField
ConfirmDialog
```

へ特定DomainのRuleを直接持たせない。

---

# 31. API呼び出し

shadcn/ui ComponentおよびApplication共通Presentation ComponentからBackend APIを直接呼び出さない。

概念上は以下とする。

```text
Page / Feature Logic
       ↓
API Client / BFF
       ↓
Backend
```

UI Componentは表示・操作UIを担当する。

Feature Componentにおける通信責務の具体的なLayer配置はFrontend実装設計を正とする。

---

# 32. State管理

UI Component内へApplication全体のState管理責務を過剰に持たせない。

以下を区別する。

- Local UI State
- Form State
- Server State
- Application State

具体的なState管理方式はFrontend実装設計で決定する。

Phase 1ではComponent責務のみ定義する。

---

# 33. Responsive

## 33.1 Application共通Component

Application共通ComponentはDesktop / Tablet / Mobileで利用可能な構造とする。

例:

```text
AppSidebar

Desktop
    ↓
常時表示

Mobile
    ↓
Sheet等によるNavigation
```

---

## 33.2 Form

Desktopでは内容に応じて複数Columnを利用可能とする。

Tablet / Mobileでは1 Columnを基本とする。

---

## 33.3 Dialog

Desktopでは中央配置Dialogを基本とする。

MobileではViewportを有効活用する。

候補:

- 幅を広く利用するDialog
- Full-screenに近いDialog
- Sheet / Drawer

具体的な方式は `09_レスポンシブ設計.md` で統一する。

Featureの意味・責務はViewportによって変更しない。

---

## 33.4 Table

Mobileでは情報優先度に応じて以下を検討する。

- Column削減
- 横Scroll
- List / Card表示

具体方式は各画面設計で定義する。

---

# 34. Accessibility

共通ComponentではAccessibilityを必須要件として扱う。

以下を基本とする。

- Semantic HTML
- Keyboard操作
- Focus可視化
- LabelとForm Controlの関連付け
- Validation Errorとの関連付け
- Accessible Name
- Colorだけに依存しない状態表現
- DialogのFocus Management
- Dialog Close後のFocus復帰
- Dialog表示中の背景Focus抑制
- Alert Dialogでの適切な操作説明
- Loading状態をVisualだけで表現しない

shadcn/ui / Base UIを利用するだけでAccessibilityが自動的に完成すると考えず、Application側の実装でも確認する。

---

# 35. Naming

Component名は責務が分かる名称を使用する。

Application共通Component例:

```text
PageHeader
DataTable
SearchFilter
EmptyState
ErrorState
StatusBadge
ConfirmDialog
```

Feature固有Component例:

```text
EmployeeCreateDialog
EmployeeEditDialog

SkillCreateDialog
SkillEditDialog

SkillCategoryCreateDialog
SkillCategoryEditDialog

AccessControlForm
```

曖昧な名称を避ける。

非推奨例:

```text
CommonModal
CommonForm
BaseBox
CommonComponent
```

用途が広すぎる名称で過度な共通化を行わない。

```text
共通UI
    ↓
Application共通Component

Feature
    ↓
Feature固有Component
```

例:

```text
Common
├── PageHeader
├── DataTable
└── EmptyState

Employee
├── EmployeeCreateDialog
└── EmployeeEditDialog

Skill
├── SkillCreateDialog

Skill Category
```

# 37. Component追加判断

新しいApplication共通Componentを作成する前に以下を確認する。

1. shadcn/uiで実現できないか
2. Tailwind CSSだけで十分ではないか
3. 複数箇所で同じ責務が存在するか
4. Domain固有Componentではないか
5. 共通化によって条件分岐が増えすぎないか

共通化そのものを目的にしない。

---

# 38. Feature固有Component追加判断

Feature固有Componentは以下の場合に作成する。

- Pageから責務を分離したい
- 同一Feature内で再利用する
- UIと操作のまとまりが明確
- Domain Contextを持つ
- FormやDialogとして独立した責務を持つ

Feature固有ComponentはApplication全体の共通Componentへ無理に昇格させない。

---

# 39. 共通化判断

共通化は以下の条件を満たす場合に検討する。

- 複数箇所で利用される
- 責務が同じ
- 操作意味が同じ
- Domainに依存しない
- Propsや条件分岐が過度に増えない

---

## 39.1 共通化しない例

見た目が似ていても責務が異なる場合は分離する。

```text
Create Form
Edit Form
```

```text
Create Dialog
Edit Dialog
```

```text
通常Dialog
破壊的操作確認
```

```text
Employee Table
Skill Table
```

共通Primitiveを利用しつつ、Feature固有責務は分離する。

---

# 40. MVPで過剰に共通化しないもの

MVP開始時点では以下を無理に共通化しない。

- すべてのForm
- すべてのDialog
- Create / Edit Form全体
- Create / Edit Dialog全体
- Resource固有Table
- Domain固有Status Logic
- Resource固有Action Menu
- 複雑なPermission UI
- Feature固有のMutation処理

重複が実際に確認されてから共通化を検討する。

---

# 41. Component責務まとめ

基本的な責務分離は以下とする。

```text
Page
│
├── Feature Logic
│   ├── Data取得
│   ├── Permissionに応じた表示判断
│   ├── Action処理
│   └── Feature State
│
├── Feature Component
│   ├── Domain固有表示
│   ├── Domain固有Form
│   └── Feature固有Dialog
│
├── Application共通Component
│   ├── PageHeader
│   ├── DataTable
│   ├── EmptyState
│   ├── ErrorState
│   └── FormField
│
└── shadcn/ui
    ├── Button
    ├── Input
    ├── Select
    ├── Dialog
    ├── Table
    └── ...
```

下位Componentから上位FeatureのDomainへ依存しない。
