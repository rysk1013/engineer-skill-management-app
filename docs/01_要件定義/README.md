# 要件定義

Engineer Skill Management App の目的、対象範囲、MVP、ユーザー要求、受け入れ条件、画面、Epicを管理するディレクトリです。

要件に関する判断はこのディレクトリへ集約し、アーキテクチャやシステム設計を変更するときの前提として使用します。

## ディレクトリ構成

| ディレクトリ | 内容 |
| --- | --- |
| [`01_要件定義書`](./01_要件定義書/要件定義書.md) | アプリケーション全体の背景、目的、利用者、機能要件、非機能要件を管理します。 |
| [`02_MVP`](./02_MVP/MVP.md) | MVPの対象範囲、User Story、Acceptance Criteria、画面を管理します。 |
| [`03_Epic`](./03_Epic/Epic一覧.md) | 機能を業務領域ごとのEpicに整理し、MVPと後続Iterationの境界を管理します。 |
| [`90_検討記録`](./90_検討記録/) | 要件確定までの質問、確認事項、チェックリストなどの検討経緯を保管します。 |

## 要件の関係

要件は次の粒度で具体化します。

```text
要件定義書
  └── Epic
       └── User Story
            ├── Acceptance Criteria
            └── 画面・画面遷移
```

- 要件定義書で、アプリケーション全体の目的と制約を定義します。
- Epicで、機能を業務領域ごとに分類します。
- User Storyで、利用者が実現したいことを定義します。
- Acceptance Criteriaと画面設計で、実装・検証可能な粒度まで具体化します。

## 推奨する読み順

1. [要件定義書](./01_要件定義書/要件定義書.md)で、背景、目的、利用者、対象機能を確認する。
2. [Epic一覧](./03_Epic/Epic一覧.md)で、機能領域とMVPの境界を把握する。
3. [MVP検討チェックリスト](./02_MVP/MVP検討チェックリスト.md)で、スコープ決定の根拠を確認する。
4. [User Story](./02_MVP/User-Story.md)で、利用者ごとの要求を確認する。
5. [Acceptance Criteria](./02_MVP/Acceptance-Criteria.md)と[画面一覧・画面遷移](./02_MVP/画面一覧・画面遷移.md)で、具体的な振る舞いを確認する。
6. 必要に応じて`reviews/`と`90_検討記録/`を参照し、判断の経緯を確認する。

## 文書管理ルール

- 現在有効な要件は、`01_要件定義書`、`02_MVP`、`03_Epic`の文書へ反映します。
- `reviews/`と`90_検討記録/`は判断の経緯を確認するための記録であり、現在の要件そのものとしては扱いません。
- 過去バージョンは内容を上書きせず、`archive/`へ保管します。
- 要件を変更した場合は、関連するEpic、User Story、Acceptance Criteria、画面、および設計文書との整合性を確認します。
