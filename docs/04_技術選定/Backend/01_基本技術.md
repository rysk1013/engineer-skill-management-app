# Backend 技術・Library選定 - 基本技術

## 1. 目的

本ドキュメントでは、Engineer Skill Management App の Backend 開発における基本技術と Dependency 管理方針を定義する。

個別の Library / Package については後続ドキュメントで選定し、本ドキュメントでは Backend 全体に適用する共通方針を扱う。

Backend Architecture として採用している以下の方針を前提とする。

- Clean Architecture
- Domain-Driven Design（DDD）
- Lightweight CQRS
- Laravel を Framework として利用
- Domain Layer の Framework 非依存
- Eloquent を Infrastructure の詳細として扱う
- Repository Pattern
- Mapper Pattern
- 1 UseCase = 1 Transaction

---

| 項目 | 採用 |
|---|---|
| Language | PHP 8.5 |
| Framework | Laravel 13 |
| Dependency Manager | Composer 2.x |

| ORM | Eloquent ORM |

## 3. PHP

### 3.1 採用 Version

PHP 8.5 を採用する。

```text
PHP 8.5.x
```

開発開始時点で利用可能な最新 Stable Patch Version を使用する。

Beta / RC などの Pre-release Version は使用しない。

### 3.2 PHP の利用方針

Modern PHP の Language Feature を積極的に利用する。

主に以下を活用する。

- Strict Types
- Type Declaration
- Return Type
- Union Type
- Nullable Type
- Enum
- `readonly`
- `readonly class`
- Constructor Property Promotion
- Attributes
- Match Expression
- First-class Callable Syntax
- Named Arguments（Pure PHP コードでは必要に応じて利用）

各 PHP ファイルでは原則として以下を宣言する。

```php
<?php

declare(strict_types=1);
```

型で表現可能な制約については、可能な限り型として表現する。

### 3.3 Domain Layer

Domain Layer では PHP 標準機能を中心に使用する。

```text
Domain
├── Entity / Aggregate
├── Value Object
├── Domain Service
├── Domain Exception
├── Repository Interface
└── Enum
```

Domain Model を Laravel / Eloquent / HTTP などの Framework 詳細へ依存させない。

---

## 4. Laravel

### 4.1 採用 Version

Laravel 13 を採用する。

```text
Laravel 13.x
```

開発開始時点で利用可能な最新 Stable Patch Version を使用する。

### 4.2 Laravel 利用方針

Clean Architecture を採用するが、Laravel 自体を避けることは目的としない。

Framework を利用して問題ない Layer では Laravel 標準機能を積極的に利用する。

基本方針は以下とする。

```text
Presentation
    ↓
Laravel を積極的に利用

Application
    ↓
Laravel 依存を必要最小限に抑える

Domain
    ↓
Pure PHP
Laravel 非依存

Infrastructure
    ↓
Laravel / Eloquent を積極的に利用
```

### 4.3 Layer ごとの Laravel 依存

| Layer | Laravel 依存 | 方針 |
|---|---|---|
| Presentation | 許可 | Laravel を積極的に利用 |
| Application | 制限 | Laravel 依存を必要最小限に抑える |
| Domain | 禁止 | Pure PHP とする |
| Infrastructure | 許可 | Laravel / Eloquent を利用 |

Presentation Layer では主に以下を利用する。

- Routing
- Controller
- Form Request
- API Resource
- Policy / Gate
- Middleware

Infrastructure Layer では主に以下を利用できる。

- Eloquent
- Query Builder
- Database Connection
- Cache
- Queue
- Logging
- External Service Integration

Application Layer では Service Container など、Application の責務を壊さない範囲で必要最小限の Laravel 機能のみ利用する。

Domain Layer では Laravel 固有機能を使用しない。

## 5. Laravel 標準機能優先

Laravel で標準提供されている機能については、原則として外部 Package より Laravel 標準機能を優先する。

| 機能 | 基本方針 |
|---|---|
| Routing | Laravel Routing |
| Controller | Laravel Controller |
| HTTP Validation | Form Request |
| Authorization | Policy / Gate |
| ORM | Eloquent |
| Migration | Laravel Migration |
| Transaction | Laravel Database |
| Pessimistic Lock | Query Builder / Eloquent |
| DI | Laravel Service Container |
| Cache | Laravel Cache |
| Queue | Laravel Queue |
| Scheduler | Laravel Scheduler |
| Logging | Laravel Logging |
| Serialization | API Resource 等を用途に応じて利用 |

外部 Package は Laravel 標準機能では不足する場合に検討する。

## 6. Composer

### 6.1 採用 Version

Composer 2.x の最新 Stable Version を使用する。

```text
Composer 2.x latest stable
```

### 6.2 composer.json

`composer.json` では Project が許容する Dependency Version を定義する。

基本的な Version 指定は以下を基準とする。

```json
{
    "require": {
        "php": "^8.5",
        "laravel/framework": "^13.0"
    }
}
```

実際の Dependency は各技術選定完了後に追加する。

### 6.3 composer.lock

`composer.lock` は Git 管理する。

```text
composer.json
    ↓
許容する Dependency Version

composer.lock
    ↓
実際に利用する Dependency Version
```

Local / CI / Staging / Production では原則として同一の `composer.lock` を利用する。

通常の環境構築・Deployment では以下を使用する。

```bash
composer install
```

`composer update` は Dependency を更新する明示的な作業として実施する。

## 7. Dependency 選定の優先順位

機能を実装する場合、以下の順番で解決方法を検討する。

```text
1. PHP 標準機能
        ↓
2. Laravel 標準機能
        ↓
3. Laravel First-party Package
        ↓
4. 外部 Package
        ↓
5. Project 固有実装
```

単に「便利だから Package を導入する」のではなく、

> どの問題を解決するために Dependency を追加するのか

を明確にしてから導入する。

---

## 8. 外部 Package 選定基準

外部 Package を導入する場合、以下の基準で評価する。

### 8.1 Maintenance

- 現在も Maintenance されている
- Release が継続している
- Issue / Pull Request が適切に管理されている

### 8.2 Compatibility

- 採用 PHP Version に対応している
- 採用 Laravel Version に対応している
- Upgrade Path が明確である

### 8.3 Security

- 既知の重大な脆弱性がない
- Security Update が期待できる
- Dependency Tree が過度に大きくない

### 8.4 License

Project で利用可能な License であることを確認する。

### 8.5 Architecture

以下を確認する。

- Domain Layer を Framework へ依存させない
- Architecture を Package 都合で変更しない
- Package 固有 Model を Domain へ流入させない
- Vendor Lock-in が過度に強くない

### 8.6 Necessity

Package 導入によって得られる Benefit が、導入・維持 Cost を上回ることを確認する。

```text
Benefit
    >
Dependency 追加
+ Maintenance
+ Upgrade 対応
+ Security Risk
+ Learning Cost
+ Vendor Lock-in
```

## 9. Package を原則導入しない領域

Architecture の基本構造については、専用 Framework / Package を原則導入しない。

対象は以下とする。

- Domain Entity
- Aggregate
- Value Object
- Domain Service
- Repository Pattern
- Mapper
- Command
- Query
- Handler
- UseCase
- Domain Exception
- CQRS の基本構造

これらは PHP の通常の Class / Interface として実装する。

例：

```php
final readonly class CreateEmployeeCommand
{
    // ...
}

final class CreateEmployeeHandler
{
    public function handle(
        CreateEmployeeCommand $command,
    ): EmployeeId {
        // ...
    }
}
```

---

## 10. CQRS Framework

CQRS 専用 Framework は採用しない。

本 Project では Lightweight CQRS を採用する。

```text
Write

Command
    ↓
Command Handler
    ↓
Domain
    ↓
Repository


Read

Query
    ↓
Query Handler / Query Service
    ↓
Read Model
```

MVP では以下を採用しない。

- Full CQRS Framework
- Command Bus
- Event Sourcing
- Event Store
- Saga
- Outbox Pattern

将来的に明確な必要性が発生した場合のみ再検討する。

---

## 11. DDD Framework

DDD 専用 Framework は採用しない。

DDD は Library として導入するのではなく、Architecture / Modeling の設計方針として適用する。

```text
Domain
├── Aggregate
├── Entity
├── Value Object
├── Domain Service
├── Domain Exception
└── Repository Interface
```

これらを Pure PHP として実装する。

---

## 12. DTO Library

DTO Library は基本技術として固定しない。

まずは PHP 標準機能を使用する。

例：

```php
final readonly class CreateEmployeeCommand
{
    public function __construct(
        public string $name,
        public DepartmentId $departmentId,
    ) {
    }
}
```

PHP 標準機能で十分な場合は外部 DTO Library を導入しない。

Validation / Serialization / OpenAPI 連携などで明確な Benefit が確認できた場合のみ、後続の技術選定で導入を再検討する。

---

## 13. Named Arguments

Project が管理する Pure PHP Class については、必要に応じて Named Arguments を利用できる。

```php
new Employee(
    id: $employeeId,
    name: $name,
);
```

一方、Laravel Framework API の Parameter Name については Backward Compatibility を前提としない。

そのため Laravel API に対する Named Arguments への依存は原則避ける。

## 14. Version 管理

Version は以下の3段階で管理する。

```text
Docker
│
└── PHP Runtime Version

composer.json
│
└── 許容する Dependency Version

composer.lock
│
└── 実際に使用する Dependency Version
```

例：

```text
Docker
└── PHP 8.5

composer.json
├── php: ^8.5
└── laravel/framework: ^13.0

composer.lock
├── Laravel 13.x.y
├── Symfony ...
├── Carbon ...
└── その他 Dependency
```

## 15. Runtime 環境の統一

以下の環境で可能な限り同じ PHP Runtime を使用する。

```text
Local
└── Docker

CI
└── Docker / 同一 PHP Version

Staging
└── Container

Production
└── Container
```

特に PHP Major / Minor Version は環境間で統一する。

Patch Version についても原則統一し、意図しない環境差分を防止する。

---

## 16. Dependency Update

Dependency Update は定期的に実施する。

対象は以下とする。

- PHP
- Laravel
- Composer
- Composer Packages
- Docker Base Image

Patch Update は積極的に取り込む。

Minor / Major Update については以下を確認する。

1. Release Notes
2. Upgrade Guide
3. Breaking Changes
4. Security Changes
5. Deprecated API
6. Automated Test
7. Static Analysis

Update 後は CI によって品質を確認する。

---

## 17. 基本方針

Backend の技術選定では、

> Framework や Library を増やすことではなく、必要な Dependency だけを利用して Architecture を単純に保つ

ことを基本方針とする。

特に Domain / Application の中心部分については、可能な限り PHP の Language Feature を利用する。

Dependency の選択では以下の優先順位を基本とする。

```text
PHP Standard Library
        ↓
Laravel Standard
        ↓
Laravel First-party
        ↓
External Package
        ↓
Project-specific Implementation
```

Laravel を利用する部分と Pure PHP として維持する部分を明確に分離し、Laravel の Productivity と Clean Architecture / DDD による Domain 分離を両立する。
