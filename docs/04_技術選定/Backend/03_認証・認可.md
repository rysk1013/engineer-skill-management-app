# Backend 技術・Library選定 - 認証・認可

## 1. 目的

本ドキュメントでは、Engineer Skill Management App の Backend における認証・認可方式と関連技術を定義する。

本Projectでは以下を前提とする。

- Browser認証はBetter Authが担当する
- Browser SessionはBetter Authで管理する
- Better Auth Session StoreにはRedisを利用する
- Backend CredentialはRedisで管理する
- Better Auth SessionとBackend CredentialはKey NamespaceおよびRedis ACLを分離する
- Backend CredentialはBetter Auth Session単位で1:1に管理する
- Laravel APIの認証にはLaravel Sanctumを利用する
- BrowserからLaravel APIを直接呼ばない
- Next.js BFFからLaravel APIを呼び出す
- Next.jsからPostgreSQLへ直接アクセスしない
- Laravel側の認可にはPolicy / Gateを利用する
- Roleだけでなく担当社員Relationも認可条件に含める
- Domain / ApplicationのBusiness RuleとHTTP Authorizationを分離する

---

## 2. 全体Architecture

認証・認可の基本構成は以下とする。

```text
Browser
    │
    │ Better Auth Session Cookie
    ▼
Next.js BFF
    │
    │ Better Auth Session検証
    ▼
Redis
    ├── Better Auth Session
    └── Backend Credential
              │
              │ Sanctum Token取得
              ▼
Next.js BFF
    │
    │ Authorization: Bearer <sanctum-token>
    ▼
Laravel API
    │
    ▼
auth:sanctum
    │
    ▼
Authenticated User
    │
    ▼
Policy / Gate
    │
    ▼
Application Handler
    │
    ▼
Domain
```

認証と認可の責務を明確に分離する。

```text
Authentication
「誰であるか」
    ↓
Better Auth / Laravel Sanctum

Authorization
「その操作を許可するか」
    ↓
Laravel Policy / Gate

Business Rule
「その操作がDomain上成立するか」
    ↓
Application / Domain
```

## 3. Browser認証

Browser側のAuthenticationはBetter Authが担当する。

LaravelはBrowser向けLogin Sessionを管理しない。

以下はLaravel側では提供しない。

```text
Laravel Browser Login Session
Laravel Session Cookie Authentication
Better AuthによるBrowser Session管理
```

BrowserとNext.js間ではBetter Auth Session Cookieを利用する。

```text
Browser
    ↓
Better Auth Session Cookie
    ↓
Next.js
```

BrowserとNext.js間のAuthenticationではBetter Auth Sessionを利用する。

一方、Laravel Backend APIではLaravel Sanctum TokenをAuthenticationの根拠とする。

```text
Browser Authentication
    ↓
Better Auth Session

Backend API Authentication
    ↓
Laravel Sanctum Token
```

---

## 4. Laravel Sanctum

### 4.1 採用

Laravel APIのAuthenticationにはLaravel Sanctumを採用する。

```text
採用
└── Laravel Sanctum
```

以下は採用しない。

```text
不採用
├── Laravel Passport
├── JWT Authentication Package
├── OAuth2 Server
└── 独自Authentication Guard
```

今回必要なのはBFFからLaravel APIへの比較的単純なToken Authenticationであり、OAuth2 Authorization Serverは不要とする。

### 4.2 Sanctum利用方式

SanctumのBearer API Token Authenticationを利用する。

```http
Authorization: Bearer <token>
```

SanctumのSPA Cookie Authenticationは利用しない。

```text
Sanctum API Token Authentication
    → 採用

Sanctum SPA Cookie Authentication
    → 不採用
```

BrowserがSanctum Tokenを直接保持する構成にはしない。

---

## 5. BFF → Laravel Authentication

Next.js BFFはBetter Auth Sessionを検証したうえで、そのSessionに対応するBackend CredentialをRedisから取得し、Laravel APIへRequestする。

```text
Browser Request
    ↓
Next.js BFF
    ↓
Better Auth Session検証
    ↓
Redis
    ↓
Sessionに対応するBackend Credential取得
    ↓
Next.js BFF
    ↓
Laravel API Request
```

Laravel APIへのRequestには以下を設定する。

```http
Authorization: Bearer <sanctum-token>
```

Sanctum TokenはServer-to-Server Credentialとして扱う。

---

## 6. Sanctum TokenをBrowserへ公開しない

Sanctum TokenはBrowserへ渡さない。

禁止事項は以下とする。

```text
localStorageへの保存
sessionStorageへの保存
Browser Cookieへの直接保存
Client Componentへの受け渡し
API Responseへの含有
HTMLへの埋め込み
Browser JavaScriptからの参照
Application Logへの出力
```

TokenはNext.js Server Sideのみで扱う。

```text
Browser
    ↓
Better Auth Session Cookie

Next.js Server
    ↓
Redis
    ↓
Backend Credential
    ↓
Laravel
```

これによりLaravel Sanctum Tokenの露出範囲をBFF Server Sideに限定する。

---

## 7. SessionとBackend Credentialの関係

Backend CredentialはBetter Auth Session単位で管理する。

基本関係は以下とする。

```text
1 Better Auth Session
        ↓
1 Backend Credential
        ↓
1 Sanctum Token
```

同一Userが複数Deviceまたは複数BrowserからLoginした場合は、Sessionごとに独立したBackend Credentialを持つ。

```text
User
├── Session A
│   └── Backend Credential A
│       └── Sanctum Token A
│
├── Session B
│   └── Backend Credential B
│       └── Sanctum Token B
│
└── Session C
    └── Backend Credential C
        └── Sanctum Token C
```

複数Session間でBackend Credentialを共有しない。

これにより、特定Sessionのみを独立して失効できる。

User単位で1つの共有Sanctum Tokenを利用しない。

---

## 8. Backend Credential Lifecycle

Backend CredentialおよびSanctum TokenはBetter Auth SessionのLifecycleと対応させる。

Login時の基本フローは以下とする。

```text
Login
    ↓
Laravel Authentication
    ↓
Sanctum Token発行
    ↓
Backend CredentialとしてRedisへ保存
    ↓
Better Auth Session作成
    ↓
SessionとBackend Credentialを関連付け
```

Logout時は以下とする。

```text
Logout
    ↓
Better Auth Session特定
    ↓
対応するBackend Credential取得
    ↓
Sanctum Token Revoke
    ↓
Backend Credential削除
    ↓
Better Auth Session失効
```

以下の場合もCredential / Token失効を検討する。

- Session Expiration
- 強制Logout
- User無効化
- Account停止
- Security Incident
- Credential Rotation

Sanctum TokenおよびBackend Credentialを無期限に放置しない。

SessionとBackend Credentialの不整合が発生した場合は、安全側へ処理する。

---

## 9. Credential Expiration

Sanctum TokenにはExpirationを設定する。

Better Auth SessionとBackend Credentialは、それぞれの責務に応じた有効期限を持つ。

少なくとも以下の整合性を考慮する。

```text
Better Auth Session Lifetime
        +
Sanctum Token Lifetime
        +
Backend Credential TTL
```

Better Auth Sessionが失効したにもかかわらず、対応するBackend CredentialやSanctum Tokenだけが長期間利用可能になる構成を避ける。

Session失効時には、対応するBackend CredentialおよびSanctum Tokenを不要な認証情報として扱う。

具体的な有効期間は認証方式全体のSecurity設計で決定する。

---

## 10. Backend Credential保存

Sanctum TokenはBackend CredentialとしてNext.jsのServer Sideからのみ利用する。

Backend Credentialの保存先にはRedisを利用する。

Better Auth SessionとBackend Credentialは同一Redis Instance上で管理するが、責務を分離する。

```text
Redis
├── Better Auth Session Namespace
└── Backend Credential Namespace
```

以下を分離する。

- Key Namespace
- Redis User
- Redis Credential
- Redis ACL
- Access Responsibility

Better Auth Session管理用ClientとBackend Credential管理用Clientは、それぞれ必要なKey Namespaceのみにアクセスできる構成を基本とする。

Backend CredentialはBetter Auth Session単位で関連付ける。

概念的には以下とする。

```text
Better Auth Session
├── session identifier
└── Backend Credential Reference

Backend Credential
├── Sessionとの対応情報
└── Sanctum Token
```

Next.jsからPostgreSQLへBackend Credentialを保存しない。

Better Auth SessionもPostgreSQLへ保存しない。

具体的なRedis Key Naming、TTL、ACL設定については認証・Redis詳細設計で定義する。

---

## 11. Laravel Authentication Middleware

LaravelのProtected APIには`auth:sanctum`を利用する。

```php
Route::prefix('v1')
    ->middleware('auth:sanctum')
    ->group(function (): void {
        Route::get('/employees', ListEmployeesController::class);
    });
```

Authentication済みUserはLaravel標準のAuthentication Contextから取得する。

```php
$request->user();
```

独自MiddlewareでSanctum相当のAuthentication処理を再実装しない。

---

## 12. AuthenticationとAuthorizationの分離

AuthenticationとAuthorizationを明確に分離する。

```text
Sanctum
    ↓
Authenticated Userを特定

Policy / Gate
    ↓
操作可能か判定
```

Controller内でRole判定を直接大量に記述しない。

以下のような実装を増やさない。

```php
if ($user->role === UserRole::Manager) {
    // ...
}
```

Role / Relationship / Permissionの判定はPolicy / Gateへ集約する。

---

## 13. Authorization

### 13.1 採用技術

Laravel標準のPolicy / Gateを採用する。

```text
採用
├── Laravel Policy
└── Laravel Gate
```

外部Authorization Frameworkは原則導入しない。

### 13.2 Policy

Resource単位のAuthorizationにはPolicyを利用する。

主な対象：

- Employee
- EmployeeSkill
- Skill
- SkillCategory
- Department
- User
- Permission Management

例：

```php
final class EmployeePolicy
{
    public function view(
        User $user,
        Employee $employee,
    ): bool {
        // ...
    }

    public function update(
        User $user,
        Employee $employee,
    ): bool {
        // ...
    }
}
```

### 13.3 Gate

特定Resourceへ直接紐付かないSystem-wide PermissionにはGateを利用できる。

例：

```text
Permission Management
Administrative Operation
System-wide Configuration
```

ただしRole判定の大部分をGateへ集中させず、Resource AuthorizationはPolicyを優先する。

---

## 14. Role

RoleはPHP Enumで表現する。

```php
enum UserRole: string
{
    case Administrator = 'administrator';
    case Manager = 'manager';
    case SubManager = 'sub_manager';
    case TeamLeader = 'team_leader';
}
```

Magic StringでRoleを扱わない。

```php
$user->role === UserRole::Manager
```

のように型として扱う。

---

## 15. Role体系

本ProjectのRoleは以下とする。

| Role | 基本権限 |
|---|---|
| Administrator | 全体管理 |
| Manager | 全社員を操作可能 |
| Sub Manager | 担当社員のみ操作可能 |
| Team Leader | 担当社員のみ閲覧可能 |
| General Employee | Application利用不可 |

General EmployeeはLogin対象Userとして扱わない。

---

## 16. RBACとRelationship-based Authorization

本ProjectのAuthorizationは単純なRBACだけでは表現できない。

以下を組み合わせる。

```text
Role
    +
Employee Assignment
    +
Special Permission
```

つまり、

```text
RBAC
    +
Relationship-based Authorization
```

を採用する。

例：

```text
Administrator
    → 全体

Manager
    → 全Employee

Sub Manager
    → AssignmentされたEmployeeのみ

Team Leader
    → AssignmentされたEmployeeを閲覧のみ
```

担当EmployeeとのRelationをPolicyで評価する。

---

## 17. Sub Manager Authorization

Sub Managerは担当Employeeのみ操作可能とする。

Employee Assignment Relationを利用して判定する。

```text
Sub Manager
    ↓
Assignment存在確認
    ↓
Employee操作許可
```

1 Employeeに複数Sub Managerを割り当てられる仕様を維持する。

Roleだけで許可判定しない。

---

## 18. Team Leader Authorization

Team Leaderは担当Employeeのみ閲覧可能とする。

```text
Team Leader
    ↓
Assignment存在
    ↓
view
    → 許可

update
create skill
delete
    → 拒否
```

UI側で操作Buttonを非表示にしていても、Laravel側Policyで必ず検証する。

---

## 19. Administrator

Administratorは全体管理を担当する。

ただしPermission管理については追加Flagを必要とする。

```text
role = Administrator
        +
can_manage_permissions = true
```

の場合のみPermission管理を許可する。

```php
return $user->role === UserRole::Administrator
    && $user->canManagePermissions;
```

---

## 20. Permission Management Invariant

以下のBusiness Ruleを維持する。

> Permission管理可能なAdministratorを最低1人維持する。

つまり、

```text
Administrator
+
can_manage_permissions = true
```

のUser数を0にしてはならない。

このRuleはPolicyだけで保証しない。

責務を以下のように分離する。

```text
Policy
    ↓
現在のUserがPermission変更を開始できるか

Application / Domain
    ↓
変更後も管理可能Administratorが1人以上残るか
```

Concurrency対策としてTransaction + Pessimistic Lockを利用する。

```text
Transaction
    ↓
SELECT ... FOR UPDATE
    ↓
管理可能Administrator数確認
    ↓
変更
```

最後の管理可能Administrator自身を無効化・降格する操作を防止する。

---

## 21. PolicyとBusiness Ruleの境界

Policyは、

> UserがUseCaseを開始してよいか

を判断する。

Domain / Applicationは、

> UseCaseを実行した結果がBusiness Ruleを満たすか

を保証する。

処理順序は以下とする。

```text
HTTP Request
    ↓
Sanctum
    ↓
Policy
    ↓
Application Handler
    ↓
Domain Invariant
    ↓
Repository
```

AuthorizationとDomain Invariantを同一の仕組みに混在させない。

---

## 22. Sanctum Abilities

Sanctum Token AbilitiesはAuthorizationの中心には使用しない。

以下のような細かいPermissionをAbilitiesとして管理しない。

```text
employees:view
employees:update
skills:create
permissions:update
```

詳細なAuthorizationはPolicyで行う。

Token AbilityはBFF Tokenとしての粗いScopeに限定する。

例：

```text
bff
```

概念例：

```php
$user->createToken(
    'authjs-session',
    ['bff'],
);
```

役割は以下のように分離する。

```text
Sanctum Ability
    ↓
Token用途の粗いScope

Policy / Gate
    ↓
Business Authorization
```

MVPでAbility自体が不要であれば、無理に細分化しない。

---

## 23. Role / Permission Package

`spatie/laravel-permission`は採用しない。

理由は、本ProjectのAuthorizationが以下を含むためである。

```text
Role
+
Employee Assignment
+
can_manage_permissions
+
Domain-specific Rule
```

単純な、

```text
User
↓
Role
↓
Permission
```

だけでは完結しない。

Laravel標準Policy / GateとProject固有Relationで十分に表現できるため、RBAC専用Packageを追加しない。

---

## 24. Authentication UserとDomain User

SanctumではLaravelのAuthenticatable Modelを利用する。

Laravel Authentication用User ModelはInfrastructure / Framework側の詳細として扱う。

```text
Laravel
    ↓
Authenticatable User Model
    ↓
Sanctum
```

Domain Entityへ以下を持ち込まない。

- `Authenticatable`
- `HasApiTokens`
- Laravel Authentication Contract
- HTTP Request
- Sanctum Token

Domain側のUser / UserIdとは必要に応じてMapperやIDを介して接続する。

```text
Authenticated Laravel User
    ↓
UserId
    ↓
Application
```

---

## 25. Frontend Authorization

Frontend / BFF側でもUX目的のAuthorization判定を行うことはできる。

例：

- 編集Button非表示
- Permission管理Menu非表示
- 閲覧専用表示
- Route Guard

ただしFrontend AuthorizationをSecurity Boundaryにはしない。

```text
Frontend Authorization
    ↓
UX

Backend Policy
    ↓
Security Boundary
```

最終的なAuthorizationは必ずLaravel側で実施する。

---

## 26. 401 Unauthorized

Authenticationできない場合は`401 Unauthorized`を返す。

主なケース：

- Bearer Tokenなし
- Tokenが不正
- Tokenが期限切れ
- TokenがRevoke済み
- Authentication Userが無効

```text
Authentication Failed
    ↓
401 Unauthorized
```

---

## 27. 403 Forbidden

Authenticationには成功しているが、操作Permissionがない場合は`403 Forbidden`を返す。

例：

```text
Team Leader
    ↓
Employee Update
    ↓
403 Forbidden
```

`401`と`403`を混同しない。

```text
401
→ Who are you? が成立しない

403
→ Who are you? は成立しているが操作不可
```

この区別をOpenAPIにも定義する。

---

## 28. Token Security

Sanctum Tokenについて以下を禁止する。

- Browserへの公開
- LocalStorage保存
- SessionStorage保存
- Client-side JavaScriptへの埋め込み
- Application Logへの出力
- Exception Messageへの出力
- Access Logへの平文記録
- Monitoring Toolへの平文送信

TokenはSecretとして扱う。

---

## 29. Transport Security

BFFとLaravel間の通信はProduction環境ではHTTPSを必須とする。

```text
Next.js BFF
    │
    │ HTTPS
    ▼
Laravel API
```

Productionで平文HTTPによるBearer Token送信を許可しない。

---

## 30. Logging

Authentication / AuthorizationのSecurity Eventは必要に応じて記録する。

例：

- Authentication失敗
- Forbidden操作
- Permission変更
- Role変更
- Token Revoke
- User無効化

ただしTokenそのものはLogへ出力しない。

Audit Logの詳細は`09_Log・Audit.md`で定義する。

---

## 31. Authentication Failure Handling

Authentication / Authorization ErrorをControllerごとに処理しない。

Laravel Exception Handlingへ集約する。

```text
AuthenticationException
AuthorizationException
        ↓
Laravel Exception Handler
        ↓
統一API Error Response
```

Response形式については`07_Exception・Error-Handling.md`で詳細を定義する。

## 34. 最終方針

認証・認可は以下の責務分離を基本とする。

```text
Browser
    │
    │ Better Auth Session Cookie
    ▼
Next.js BFF
    │
    │ Better Auth Session Authentication
    ▼
Redis
    ├── Better Auth Session
    └── Backend Credential
              │
              │ Sanctum Token
              ▼
Next.js BFF
    │
    │ Authorization: Bearer <sanctum-token>
    ▼
Laravel API
    │
    │ auth:sanctum
    ▼
Authentication
    │
    ▼
Policy / Gate
    │
    ▼
Authorization
    │
    ▼
Application Handler
    │
    ▼
Domain Invariant
```

Browser AuthenticationとLaravel API Authenticationを分離し、Laravel Sanctum TokenをBrowserへ公開しない。

Better Auth SessionとBackend CredentialはRedisで管理し、PostgreSQLへ保存しない。

MVPでは同一Redis Instanceを利用するが、Better Auth SessionとBackend CredentialはKey NamespaceおよびRedis ACLによって責務を分離する。

Backend CredentialはBetter Auth Session単位で1:1に管理し、複数Session間で共有しない。

Authorizationについては、

```text
Role
+
Assignment
+
Special Permission
```

をLaravel Policy / Gateで表現する。

一方、

```text
最後のPermission管理可能Administratorを削除できない
```

などのBusiness InvariantはPolicyへ押し込まず、Application / Domain + Transactionによって保証する。

外部RBAC FrameworkやOAuth2 Serverを導入せず、

> Better Auth + Redis + Laravel Sanctum + Laravel Policy / Gate + Project固有Domain Rule

という構成を採用する。
