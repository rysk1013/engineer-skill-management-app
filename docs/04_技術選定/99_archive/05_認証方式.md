# 認証方式

## 1. 概要

エンジニアスキル管理アプリでは、Frontend / BFFとBackend APIを分離し、それぞれ異なる認証方式を利用する。

採用構成は以下とする。

    Browser
        ↓
    Next.js BFF
        ↓
    Laravel API

認証方式：

    Browser
        ↓ Auth.js Session
    Next.js BFF
        ↓ Laravel Sanctum Token
    Laravel API

つまり、

- Browser ↔ Next.js：Auth.js Session
- Next.js BFF ↔ Laravel API：Laravel Sanctum

を採用する。

---

## 2. 決定事項

### Browser → Next.js

Auth.jsによるSession認証を採用する。

    Browser
        ↓
    Auth.js Session
        ↓
    Next.js

BrowserはAuth.js Sessionを利用して認証状態を維持する。

---

### Next.js BFF → Laravel API

Laravel SanctumによるToken認証を採用する。

    Next.js BFF
        ↓
    Sanctum Token
        ↓
    Laravel API

Sanctum TokenはServer-to-Server認証に利用する。

---

### Sanctum TokenをBrowserへ公開しない

Sanctum TokenはNext.js BFF内部でのみ利用する。

採用：

    Browser
        ↓ Auth.js Session
    Next.js BFF
        ↓ Sanctum Token
    Laravel API

採用しない：

    Browser
        ↓ Sanctum Token
    Laravel API

BrowserからLaravel APIへSanctum Tokenを直接送信する構成にはしない。

---

## 3. BFF構成

Next.jsをBFF（Backend for Frontend）として利用する。

Browserは原則としてNext.jsを経由してBackend APIへアクセスする。

    Browser
        ↓
    Next.js
        ↓
    Laravel

Next.jsは以下を担当する。

- Auth.js Sessionの管理
- Login状態の確認
- Laravel APIへの認証情報付与
- Sanctum Tokenの安全な管理
- BrowserとLaravel APIの境界

---

## 4. Session Store

Auth.js Session StoreにはPostgreSQLを採用する。

    Auth.js
        ↓
    PostgreSQL
        ↓
    auth_sessions

Database-backed Sessionを利用する。

SessionをServer側で管理できる構成とする。

---

## 5. Auth.js SessionとSanctum Token

基本関係は、

    1 Auth.js Session
        =
    1 Sanctum Token

とする。

SessionごとにLaravel APIアクセス用のSanctum Tokenを対応付ける。

これにより、Session失効時に対応するSanctum Tokenも失効させやすくする。

---

## 6. Sanctum Tokenの保存

Sanctum TokenはAuth.js Sessionに関連付けてPostgreSQLへ保存する。

保存先：

    auth_sessions

Sanctum Tokenの平文保存は行わない。

TokenはApplication側で暗号化して保存する。

概念：

    Sanctum Token
        ↓
    Encrypt
        ↓
    auth_sessions
        ↓
    Decrypt
        ↓
    Next.js BFF
        ↓
    Authorization Header
        ↓
    Laravel API

具体的なColumn構成・暗号化方式はDatabase / Authentication設計側で管理する。

---

## 7. Laravel Sanctum

Laravel APIの認証にはLaravel Sanctumを採用する。

Sanctumは、

    Browser Session認証

ではなく、

    Next.js BFF
        ↓
    Laravel API

間のAPI Token認証として利用する。

---

## 8. Auth.js

Next.js側の認証・Session管理にはAuth.jsを採用する。

Auth.jsは主に、

- Browser側Session管理
- Login状態管理
- Session生成
- Session失効
- PostgreSQL Session Storeとの連携

を担当する。

Laravelの認証SessionをBrowser認証には利用しない。

---

## 9. 認証責務の分離

認証責務は以下のように分離する。

### Browser

保持するもの：

    Auth.js Session Cookie

保持しないもの：

    Sanctum Token

---

### Next.js BFF

担当：

    Auth.js Session確認
    Sanctum Token取得
    Laravel APIへのToken付与

---

### Laravel API

担当：

    Sanctum Token検証
    API利用者の認証

---

### PostgreSQL

保持：

    Auth.js Session
    暗号化されたSanctum Token
    Laravel Sanctum Token管理情報

---

## 10. Domain Userとの分離

Password / Session / Tokenなどの認証情報管理は、Domain Userから分離する。

Domain Userへ、

- Auth.js Session
- Session Token
- Sanctum Token
- Cookie
- Password Hash管理
- HTTP Authentication情報

などを持ち込まない。

Domainは、

    Laravel Auth
    Auth.js
    Sanctum
    Cookie
    HTTP

へ依存しない。

---

## 11. AuthenticationとDomainの関係

Authenticationは今回のCore Domainとして扱わない。

Core Domain：

    Skill Management

Authentication：

    Infrastructure寄りのTechnical Concern

として扱う。

ただし、認証済み利用者をApplication Layerで利用する場合は、Laravel/Auth.js固有Objectをそのまま渡さない。

必要な情報へ変換してApplicationへ渡す。

例：

    Authentication
        ↓
    ActorContext
        ↓
    Application

---

## 12. AuthenticationとAuthorizationの分離

AuthenticationとAuthorizationを分離して考える。

Authentication：

    「誰であるか」

Authorization：

    「その利用者がその操作を実行できるか」

Laravel Sanctumによる認証成功だけで、業務操作を許可したことにはしない。

Authorizationは別途、

- Laravel Policy
- Application Layer
- Domain Policy / Business Invariant

等、それぞれの責務に応じて保証する。

---

## 13. Laravel Policy

Laravel PolicyはHTTP側Authorization Adapterとして利用する。

重要な権限制御についてはApplication Layerでも確認する。

Domain / ApplicationをLaravel Authへ直接依存させない。

---

## 14. Session失効

Auth.js Sessionが失効・削除された場合、そのSessionに対応するSanctum Tokenも利用不能にすることを基本方針とする。

これにより、

    Sessionは無効
    Sanctum Tokenだけ有効

という状態を可能な限り残さない。

---

## 15. Logout

Logout時は、

    Auth.js Session
        ↓
    Sanctum Token
        ↓
    Session

の関連を考慮して失効処理を行う。

基本方針：

    Logout
        ↓
    Auth.js Session無効化
        +
    対応するSanctum Token無効化

とする。

具体的なLogout Flowは認証詳細設計で定義する。

---

## 16. Security

以下を基本方針とする。

- Sanctum TokenをBrowserへ公開しない
- Sanctum Tokenを平文でDatabase保存しない
- SessionとTokenのLifecycleを対応させる
- HTTPSを前提とする
- Session Cookieへ適切なSecurity属性を設定する
- AuthenticationとAuthorizationを分離する
- Domainへ認証Frameworkの概念を持ち込まない

詳細なSecurity要件は非機能要件および認証詳細設計で定義する。

---

## 17. 採用しない構成

MVPでは以下を採用しない。

### BrowserからLaravel APIへのSanctum Token直接送信

採用しない。

    Browser
        ↓ Sanctum Token
    Laravel

BFFを経由する。

---

### Sanctum TokenのBrowser保存

以下へのSanctum Token保存は行わない。

    localStorage
    sessionStorage
    JavaScriptから直接管理するCookie

---

### Laravel SessionによるBrowser認証

Browser側Session管理はAuth.jsへ統一する。

Laravel SessionとAuth.js SessionをBrowser認証用途で二重管理しない。

---

### JWT中心の独自認証基盤

MVPでは独自JWT Authentication Systemを構築しない。

Auth.js + Laravel Sanctumを利用する。

---

## 18. 技術選定と詳細設計の境界

このドキュメントでは、

**どの認証技術・認証構成を採用するか**

を管理する。

具体的な、

- `auth_sessions`のColumn
- Sanctum Token暗号化方式
- Session生成Flow
- Login / Logout Flow
- Token発行・失効Flow
- Cookie設定
- Error Handling
- Laravel / Next.js実装方法

については、

    docs/03_システム設計/02_認証・認可/

および関連するDatabase設計で管理する。

---

# 最終決定

認証構成は以下とする。

    ┌──────────────┐
    │   Browser    │
    └──────┬───────┘
           │
           │ Auth.js Session
           ▼
    ┌──────────────┐
    │ Next.js BFF  │
    └──────┬───────┘
           │
           │ Laravel Sanctum Token
           ▼
    ┌──────────────┐
    │ Laravel API  │
    └──────────────┘

Session Store：

    PostgreSQL

Token管理：

    1 Auth.js Session
        =
    1 Sanctum Token

Sanctum Token：

    Browserへ公開しない
    ↓
    auth_sessionsへ暗号化保存
    ↓
    Next.js BFFのみが利用

責務：

    Auth.js
        → Browser Session

    Next.js
        → BFF / SessionとAPI Tokenの橋渡し

    Laravel Sanctum
        → Laravel API Authentication

    Laravel Policy / Application
        → Authorization

    Domain
        → Auth.js / Sanctum / Laravel Authへ依存しない

以上をMVPの認証方式として採用する。
