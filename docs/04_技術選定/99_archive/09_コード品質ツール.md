# コード品質ツール 技術決定

## 1. 採用ツール

### Frontend / BFF

- [x] ESLint
- [x] Prettier
- [x] TypeScript Type Check

### Backend API

- [x] Laravel Pint
- [x] PHPStan
- [x] Larastan

---

## 2. 全体方針

コード品質ツールは以下の役割で分ける。

    Frontend / BFF
    ├── ESLint
    │   └── Code Quality / Bug Detection
    │
    ├── Prettier
    │   └── Code Formatting
    │
    └── TypeScript
        └── Static Type Check

    Backend API
    ├── Laravel Pint
    │   └── Code Formatting
    │
    └── PHPStan + Larastan
        └── Static Analysis

FormatterとStatic Analysisの責務を分離する。

---

## 3. ESLint

### 用途

Next.js / TypeScriptコードのLintに利用する。

主な対象：

- React Component
- Server Component
- Client Component
- Route Handler
- Server Action
- BFF処理
- Utility
- TypeScriptコード

### 主な目的

- 潜在的なBugの検出
- 不適切なReactコードの検出
- Next.js固有の問題の検出
- 未使用コードの検出
- コーディングルールの統一

Next.js向けESLintルールを利用する。

---

## 4. Prettier

### 用途

Frontend / BFFのコードフォーマットに利用する。

主な対象：

- TypeScript
- TSX
- JavaScript
- JSON
- Markdown
- CSS等

### 基本方針

コードスタイルに関する議論を減らし、
自動Formatへ任せる。

例：

    npm run format

    npm run format:check

具体的なScript名はProject Setup時に決定する。

---

## 5. ESLintとPrettierの責務

ESLint：

    Code Quality
    Bug Detection
    React / Next.js Rules

Prettier：

    Formatting

Formatter目的のRuleをESLintへ過度に追加しない。

ESLintとPrettierで同じ責務を持たせない。

---

## 6. TypeScript Type Check

TypeScript Compilerによる型チェックをCIで実行する。

主な対象：

- Component Props
- API Request
- API Response
- Form Data
- BFF処理
- Utility
- Auth.js関連

例：

    tsc --noEmit

Next.js Buildだけに型チェックを依存せず、
Type Check用Commandを用意することを検討する。

---

## 7. Frontendの品質チェック

Pull Request前に最低限以下を実行できるようにする。

    ESLint
       ↓
    Prettier Check
       ↓
    Type Check
       ↓
    Vitest

想定Command：

    npm run lint

    npm run format:check

    npm run typecheck

    npm test

具体的なScriptはpackage.jsonで統一する。

---

## 8. Laravel Pint

### 用途

Laravel Backend APIのCode Formatterとして利用する。

主な対象：

- Controller
- Form Request
- Model
- Service
- Policy
- Test
- Migration
- Seeder
- Factory

### 採用理由

- Laravelとの相性がよい
- Laravel標準のCode Styleへ合わせやすい
- 設定を増やさず開始できる
- 自動Fixできる
- CIでFormat Checkを行える

---

## 9. Pintの基本方針

Laravel標準のPresetを基本とする。

独自Ruleを大量に追加しない。

まずLaravel標準Styleを利用し、
明確な理由がある場合のみ設定を追加する。

実行例：

    ./vendor/bin/pint

Docker：

    docker compose exec backend ./vendor/bin/pint

CIでは変更せずCheckのみ行う方式を利用する。

---

## 10. PHPStan

### 用途

PHPのStatic Analysisに利用する。

主な対象：

- Type Error
- 未定義Method / Property
- 不正なReturn Type
- Nullableの扱い
- 不正な引数
- 到達不能Code
- その他静的に検出可能な問題

PHPStanはTestを実行せずに、
Code上の問題を検出するために利用する。

---

## 11. Larastan

LaravelではPHPStan単体ではFramework固有の動的処理を正しく解析できない場合がある。

そのためLarastanを追加する。

LarastanはLaravel向けPHPStan Extensionとして利用する。

対象例：

- Eloquent Model
- Relation
- Collection
- Facade
- Container
- Laravel固有の型推論

構成：

    PHPStan
       +
    Larastan
       ↓
    Laravel Static Analysis

---

## 12. PHPStan Level

PHPStanには複数の解析Levelが存在する。

最初から最大Levelへ設定することを目的にしない。

MVPでは現実的なLevelから開始し、
Codebaseの状態を見ながら段階的に上げる。

例：

    Initial
    Level 5〜6

        ↓

    Stable

    Level 7〜8

        ↓

    必要に応じてさらに厳格化

具体的な開始LevelはProject Setup時に決定する。

---

## 13. Static Analysisの方針

以下を重視する。

- Native Type Hintを優先する
- Return Typeを明示する
- Parameter Typeを明示する
- Nullableを明確にする
- PHPDocはNative Typeで表現できない情報の補助として利用する

PHPStan Errorを大量にignoreして通すことを目的にしない。

必要な場合は原因を確認したうえでignoreする。

---

## 14. Backendの品質チェック

Pull Request前に最低限以下を実行できるようにする。

    Pint
       ↓
    PHPStan / Larastan
       ↓
    PHPUnit / Laravel Feature Test

想定Command：

    ./vendor/bin/pint --test

    ./vendor/bin/phpstan analyse

    php artisan test

Docker：

    docker compose exec backend ./vendor/bin/pint --test

    docker compose exec backend ./vendor/bin/phpstan analyse

    docker compose exec backend php artisan test

---

## 15. Frontend / Backendの役割比較

| 対象 | Formatter | Lint / Static Analysis | Test |
| --- | --- | --- | --- |
| Next.js | Prettier | ESLint + TypeScript | Vitest / RTL |
| Laravel | Pint | PHPStan + Larastan | PHPUnit |

---

## 16. Editor Integration

Editor上でも可能な範囲で以下を利用する。

### Frontend

- ESLint
- Prettier
- TypeScript Language Server

### Backend

- Pint
- PHPStan / Larastan
- PHP Language Server

ただしEditorだけで品質を保証しない。

CIでも同じ品質チェックを実行する。

---

## 17. Format on Save

FrontendではPrettier、
BackendではPintによるFormatを利用できる構成を検討する。

ただし個人のEditor設定へ依存しない。

最終的なCode StyleはCIでも確認する。

---

## 18. CI

Pull Request時に以下を実行する。

### Frontend

    ESLint
    Prettier Check
    Type Check
    Vitest

### Backend

    Pint Check
    PHPStan / Larastan
    PHPUnit

Failureした場合は原則としてMergeできない構成を目指す。

---

## 19. Pre-commit Hook

MVPではPre-commit Hookを必須にしない。

理由：

- Local環境の複雑化を避ける
- CIを品質保証の最終地点とする
- Hook導入自体を目的にしない

必要性が出た場合に以下を検討する。

- lefthook
- husky
- lint-staged
- その他

---

## 20. 採用しないもの

MVPでは以下を追加しない。

### Frontend

- 複数のFormatter
- ESLint以外のLint Toolを重複導入
- 過度な独自ESLint Rule

### Backend

- PHP CS FixerをPintと別に直接運用
- 複数のPHP Formatter
- 複数のStatic Analyzerを重複導入

Toolを増やしすぎず、
責務を明確にする。

## 22. 品質チェックの基本フロー

開発：

    Code
      ↓
    Formatter
      ↓
    Lint / Static Analysis
      ↓
    Test
      ↓
    Pull Request

CI：

    Pull Request
      ↓
    Frontend Quality Check
      +
    Backend Quality Check
      ↓
    Test
      ↓
    Merge

---

## 23. 決定事項

### Frontend Formatter

Prettierを採用する。

### Frontend Lint

ESLintを採用する。

### Frontend Static Type Check

TypeScriptを利用する。

### Backend Formatter

Laravel Pintを採用する。

### Backend Static Analysis

PHPStan + Larastanを採用する。

### 基本方針

- FormattingとLint / Static Analysisを分離する
- Laravel標準Styleを優先する
- Type情報を積極的に付ける
- CIで品質チェックを必ず行う
- Toolを必要以上に増やさない
- Code CoverageやRule数そのものを目的にしない
