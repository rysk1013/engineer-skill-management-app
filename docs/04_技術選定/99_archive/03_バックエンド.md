# Backend API 技術決定

## 1. 採用技術

- [x] PHP
- [x] Laravel
- [ ] Node.js / TypeScript
- [ ] Go

---

## 2. Laravelの役割

LaravelはBackend APIとして使用する。

LaravelからHTMLを生成する構成にはせず、Frontend / BFFはNext.jsが担当する。

基本構成：

    Browser
       ↓
    Next.js
    Frontend / BFF
       ↓
    Laravel
    Backend API
       ↓
    Database

---

## 3. Laravelの責務

Laravelは以下を担当する。

- Backend APIの提供
- 認証されたユーザーの検証
- 認可
- 業務ロジック
- バリデーション
- データアクセス
- トランザクション管理
- データ整合性の保証
- 権限制御

---

## 4. 業務ルール

業務上重要なルールはLaravel側で必ず保証する。

例：

- 実務経験なしの場合はLevel 1のみ
- 実務経験なしの場合は経験年数0年0か月
- 実務経験なしの場合は最終利用時期を設定しない
- 実務経験ありの場合は経験年数1か月以上
- 実務経験ありの場合はLevel 1〜5
- 実務経験ありの場合は最終利用時期必須
- 同一社員への同一スキルの重複登録禁止
- 権限に応じた社員の閲覧・編集制限

Frontendでも入力補助として同様の制御を行うことはできるが、
最終的なデータ整合性はLaravel側で保証する。

---

## 5. Next.jsとの責務分離

### Next.js Frontend

- UI
- 画面遷移
- フォーム
- ユーザー操作
- クライアント側入力補助

### Next.js BFF

- Browserからのリクエスト受付
- Laravel APIの呼び出し
- 認証情報の取り扱い
- Frontend向けレスポンスへの変換
- 必要に応じたAPIレスポンスの集約

### Laravel Backend API

- 認可
- 業務ロジック
- バリデーション
- データアクセス
- データ整合性の保証

---

## 6. API境界

Next.jsとLaravelの間はAPIによって明確に分離する。

Laravel固有の内部構造をAPI利用側へ露出させない。

例えば以下をそのままAPI仕様としない。

- Eloquent Modelの内部構造
- Laravel固有のClass名
- Laravel固有の例外
- Databaseのテーブル構造

Request / ResponseをAPIの契約として定義する。

---

## 7. 将来のBackend変更

将来的に必要性が生じた場合、

    Laravel

から

    Node.js / TypeScript

など別のBackend実装へ変更できる境界を維持する。

そのため、Frontend / BFFはLaravelそのものではなく、
Backend APIの契約へ依存する。

将来の移行を前提として過度な抽象化を行うことはしない。

---

## 8. API仕様

Next.js BFFとLaravel Backend API間のAPI仕様を明確にする。

API仕様の管理方法についてはAPI設計時に決定する。

候補：

- OpenAPI
- その他

---

## 9. Laravelバージョン

開発開始時点の安定版を使用する。

具体的なバージョンはプロジェクトセットアップ時に決定する。

---

## 10. 決定事項

### Backend

PHP + Laravelを採用する。

### Laravelの用途

Backend APIとして使用する。

### 基本構成

    Browser
       ↓
    Next.js Frontend / BFF
       ↓
    Laravel Backend API
       ↓
    Database

### 基本方針

- LaravelからFrontendを提供しない
- 業務ロジックはLaravelを主体とする
- Laravelで最終的な認可を行う
- Laravelで最終的なバリデーションを行う
- Laravelでデータ整合性を保証する
- Next.jsとLaravelの境界をAPIとして明確にする
- Laravel固有の内部構造をAPI契約へ漏らさない
- 将来Backendを別技術へ変更できる境界を維持する
