# Next.js BFF構成 決定

## 1. 採用構成

Next.jsをフロントエンドアプリケーション兼BFFとして利用する。

基本構成は以下とする。

    Browser
       |
       v
    Next.js
    Frontend + BFF
       |
       | HTTP / API
       v
    Backend API
       |
       v
    Database

ブラウザからBackend APIを直接呼び出すことは原則として行わない。

BrowserからのリクエストはNext.jsのBFFを経由し、Backend APIへ転送する。

---

## 2. アプリケーション構成

モノレポ内に以下の2つのアプリケーションを配置する。

    engineer-skill-management/
    ├── frontend/
    │   └── Next.js
    │       ├── Frontend
    │       └── BFF
    │
    ├── backend/
    │   └── Backend API
    │
    ├── docs/
    └── README.md

Next.jsとBackend APIはそれぞれ独立したアプリケーションとして扱う。

---

## 3. 通信経路

基本的な通信経路は以下とする。

    Browser
       |
       | 1. Request
       v
    Next.js BFF
       |
       | 2. Backend API Request
       v
    Backend API
       |
       | 3. Data Access
       v
    Database
       |
       | 4. Result
       v
    Backend API
       |
       | 5. API Response
       v
    Next.js BFF
       |
       | 6. Frontend Response
       v
    Browser

BrowserからDatabaseへ直接アクセスしない。

BrowserからBackend APIへの直接アクセスも原則として行わない。

---

## 4. Next.jsの責務

Next.jsはFrontendとBFFの責務を持つ。

### Frontend

以下を担当する。

- 画面表示
- 画面遷移
- フォーム
- ユーザー操作
- クライアント側入力補助
- ローカル状態管理
- BFFの呼び出し
- APIレスポンスの表示
- 権限に応じたUI表示

### BFF

以下を担当する。

- Browserからのリクエスト受付
- Backend APIの呼び出し
- 認証情報の取り扱い
- Backend APIへの認証情報の受け渡し
- Frontend向けレスポンスへの変換
- 必要に応じた複数Backend APIの集約
- Backend APIのURLや内部構造をFrontendから隠蔽する

---

## 5. Backend APIの責務

Backend APIはシステムの業務処理を担当する。

主な責務は以下とする。

- 認証された利用者の検証
- 認可
- 業務ロジック
- バリデーション
- データアクセス
- データ整合性の保証
- 権限制御

以下のような業務ルールはBackend APIで必ず保証する。

- 実務経験なしの場合はLevel 1のみ
- 実務経験なしの場合は経験年数0年0か月
- 実務経験なしの場合は最終利用時期を設定しない
- 実務経験ありの場合は経験年数1か月以上
- 実務経験ありの場合はLevel 1〜5
- 実務経験ありの場合は最終利用時期必須
- 同一社員への同一スキルの重複登録禁止
- 権限に応じた社員の閲覧・編集制限

---

## 6. BFFに業務ロジックを持たせない

BFFには原則としてドメイン固有の業務ロジックを持たせない。

例えば以下の処理をBFFだけで判断してはならない。

    実務経験なし
        ↓
    Level 1のみ許可

このルールはFrontendでも入力補助として利用できるが、最終的な検証はBackend APIで行う。

責務は以下のように分ける。

    Frontend
      ↓
    入力しやすいUIを提供

    BFF
      ↓
    Backend APIとの通信を仲介

    Backend API
      ↓
    業務ルールを保証

---

## 7. Route Handlers

BFFのHTTPエンドポイントにはNext.js App RouterのRoute Handlersを利用することを基本候補とする。

例：

    app/
    └── api/
        ├── employees/
        │   └── route.ts
        │
        ├── employees/
        │   └── [employeeId]/
        │       └── route.ts
        │
        ├── skill-categories/
        │   └── route.ts
        │
        └── skills/
            └── route.ts

具体的なAPI構成はAPI設計時に決定する。

---

## 8. Server Components

Server ComponentsからBackend APIのデータを取得する場合、必ずしもRoute Handlerを経由する必要はない。

以下のような構成も許可する。

    Server Component
          |
          v
    Backend API

Server Componentはサーバー側で実行されるため、Backend APIを直接呼び出すことができる。

一方、Client ComponentからBackend APIを直接呼ぶことは原則として行わない。

---

## 9. Browserからのデータ更新

Browserから発生する登録・編集などの操作は、Next.jsのサーバー側処理を経由する。

候補として以下を利用する。

- Route Handlers
- Server Actions

具体的な使い分けはフロントエンド設計時に決定する。

---

## 10. Route HandlerとServer Actionの基本方針

### Route Handler

以下のような用途で使用する。

- Client ComponentからHTTPで呼び出す必要がある
- BFFとして明確なHTTPエンドポイントが必要
- HTTPメソッドによるAPI設計を行いたい
- Backend APIとの通信をFrontendから隠蔽したい

### Server Action

以下のような用途で検討する。

- フォーム送信
- Next.js内部からのみ呼び出す更新処理
- UIと密接なMutation

ただし、Backend APIが業務処理の主体であることは変えない。

---

## 11. 認証

認証情報はNext.js BFFで安全に取り扱う。

想定する基本構成：

    Browser
       |
       | Session Cookie
       v
    Next.js BFF
       |
       | Authentication Information
       v
    Backend API

具体的な認証方式については認証技術選定時に決定する。

BrowserにBackend API用の認証情報を不要に露出しない構成を優先する。

---

## 12. 認可

BFFでUI上のアクセス制御を行うことは可能だが、Backend APIでも必ず認可を行う。

例えばサブマネージャーの場合：

    Browser
       ↓
    Next.js
       ↓
    担当社員のみ表示

に加えて、

    Backend API
       ↓
    対象社員が担当社員か検証

を行う。

FrontendやBFFの制御だけを認可の根拠としない。

---

## 13. Backend APIの非公開化

可能であれば、Backend APIはBrowserから直接アクセスすることを前提としない。

構成イメージ：

    Internet / Browser

           |
           v

       Next.js
    Public Endpoint

           |
           v

     Backend API
    Internal Endpoint

           |
           v

       Database

実際にBackend APIをネットワークレベルで非公開にできるかどうかは、インフラ設計時に決定する。

---

## 14. BFFのメリット

今回のアプリでBFFを採用する主なメリットは以下とする。

- Backend APIの詳細をFrontendから隠蔽できる
- BrowserがBackend APIを直接利用しなくてよい
- 認証情報をサーバー側で管理しやすい
- Frontend専用のレスポンス形式へ変換できる
- 将来的に複数APIを集約できる
- Backend APIの変更影響をBFFで吸収できる
- FrontendとBackendの責務を分離できる

---

## 15. 注意点

BFFを導入することで通信経路が1段増える。

    Browser
       ↓
    BFF
       ↓
    Backend API

そのため以下に注意する。

- 不必要なAPI中継処理を増やさない
- Backend APIのレスポンスを単純にコピーするだけのBFFを大量に作らない
- 業務ロジックをBFFへ分散させない
- Frontend専用の処理が必要な場合にBFFを利用する
- エラー処理の責務を明確にする
- 認証・認可の責務を明確にする

---

## 16. MVPでの方針

MVPでもNext.jsをBFFとして利用する。

ただし、BFFを過度に複雑化しない。

MVPでは主に以下を担当する。

- Backend APIへのリクエスト
- Backend APIレスポンスの受け取り
- 認証情報の受け渡し
- Frontendへのレスポンス返却

以下は必要になった場合のみ実装する。

- 複数APIレスポンスの集約
- 複雑なレスポンス変換
- BFF独自キャッシュ
- BFF独自の高度な状態管理

---

## 17. 決定事項

### Frontend

Next.js + TypeScript + App Routerを採用する。

### BFF

Next.jsをBackend for Frontendとして利用する。

### Backend

独立したBackend APIを構築する。

### Repository

Monorepoを採用する。

### 通信

基本的な通信経路を以下とする。

    Browser
       ↓
    Next.js Frontend / BFF
       ↓
    Backend API
       ↓
    Database

### 責務

    Next.js Frontend
    └── UI

    Next.js BFF
    └── Frontend向けBackend連携

    Backend API
    └── Business Logic / Authorization / Data Access

### 基本原則

- BrowserからBackend APIを直接利用しない
- Next.jsからDatabaseへ直接アクセスしない
- 業務ロジックの主体はBackend APIとする
- BFFへ業務ロジックを分散させない
- Backend APIでも必ず認可を行う
