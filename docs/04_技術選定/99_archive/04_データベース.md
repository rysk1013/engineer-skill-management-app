# データベース技術 比較・決定

## 1. 比較対象

- [x] PostgreSQL
- [ ] MySQL

---

## 2. 今回のシステム要件

データベースでは主に以下の情報を管理する。

- 社員
- 所属部署
- 在籍状態
- スキルカテゴリ
- 技術・スキルマスタ
- 社員スキル
- 実務経験
- 経験年数
- スキルレベル
- 最終利用時期
- 利用者権限
- サブマネージャーと担当社員の関係
- チームリーダーと担当社員の関係

将来的には以下も扱う。

- 複数スキル検索
- スキルごとの社員検索
- 技術保有人数集計
- 権限に応じた社員絞り込み
- 資格管理

---

## 3. PostgreSQL

### メリット

- Laravelから利用できる
- リレーショナルデータの管理に適している
- JOINを利用した複雑な検索に対応できる
- 集計処理を行いやすい
- 外部キーや一意制約などによるデータ整合性を保証しやすい
- トランザクションを利用できる
- 高度なSQL機能を利用できる
- JSON / JSONBを利用できる
- JSONBに対してインデックスを利用できる
- 将来的な検索・分析機能の拡張に対応しやすい

### デメリット

- MySQLに慣れている場合は一部SQLや型の違いを意識する必要がある
- PostgreSQL固有機能を多用すると将来的なDB移行が難しくなる

---

## 4. MySQL

### メリット

- Laravelとの相性がよい
- CRUD中心のWebアプリケーションに十分な機能を持つ
- 利用実績が多い
- 学習資料が豊富
- JSON型を利用できる
- トランザクションを利用できる
- 一般的な検索・集計は問題なく実現できる

### デメリット

- PostgreSQLと比較すると、高度なSQLや分析系機能を使う場合に選択肢が異なる
- 将来的に複雑な検索要件が増えた場合、PostgreSQLの方が扱いやすいケースがある

## 6. 今回のデータ構造との相性

今回のシステムでは、多くのデータがリレーショナルな関係を持つ。

例：

    Employee
       |
       +--- EmployeeSkill
       |        |
       |        +--- Skill
       |               |
       |               +--- SkillCategory
       |
       +--- SubManagerAssignment
       |
       +--- TeamLeaderAssignment

そのため、リレーショナルデータベースを採用する。

PostgreSQLとMySQLのどちらでも実現可能だが、
今回の検索・集計・将来拡張を考慮してPostgreSQLを採用する。

## 7. 複数スキル検索

将来的に以下のような検索を行う。

    PHP
    AND
    Laravel
    AND
    AWS

    PHP
    経験3年以上

    AND

    Laravel
    Level 3以上

    AND

    AWS
    実務経験あり

このような検索では、

などを利用する可能性がある。

PostgreSQLはこのような検索要件との相性がよい。

- PHP保有社員数

- AWS保有社員数

## 9. JSONの利用方針

PostgreSQLではJSON / JSONBを利用できる。

ただし、今回の主要データをJSONへまとめて保存することはしない。

例えば以下は通常のリレーショナルデータとして管理する。

- 社員
- スキル
- 経験年数
- スキルレベル
- 権限
- 担当社員

JSONBは、将来的に柔軟な追加属性が必要になった場合の選択肢として扱う。

基本方針：

    Relational Data
        ↓
    通常のColumn / Relation

    柔軟な補足データ
        ↓
    必要な場合のみJSONB

JSONBを安易に利用しない。

---

## 10. データ整合性

アプリケーション側のValidationだけでなく、
データベースでも可能な範囲で整合性を保証する。

利用を検討するもの：

- PRIMARY KEY
- UNIQUE
- FOREIGN KEY
- NOT NULL
- CHECK

例えば以下の制約を検討する。

    社員番号
    → UNIQUE

    社員 + 技術・スキル
    → UNIQUE

Backend APIのValidationとDatabase Constraintを組み合わせてデータ整合性を保証する。

---

## 11. Laravelとの関係

LaravelからPostgreSQLへアクセスする。

基本構成：

    Browser
       ↓
    Next.js Frontend / BFF
       ↓
    Laravel Backend API
       ↓
    PostgreSQL

Next.jsからPostgreSQLへ直接アクセスしない。

データアクセスはLaravel Backend APIを通して行う。

---

## 12. PostgreSQL固有機能の利用方針

PostgreSQLを採用するが、必要性がない段階からPostgreSQL固有機能へ強く依存しない。

MVPでは主に標準的なリレーショナル機能を使用する。

- Table
- Column
- Primary Key
- Foreign Key
- Unique Constraint
- Index
- Transaction

以下は必要性が確認された場合のみ利用する。

- JSONB
- GIN Index
- Full Text Search
- Materialized View
- Array
- その他PostgreSQL固有機能

---

## 13. バージョン方針

開発開始時点でサポートされている安定版PostgreSQLを使用する。

具体的なバージョン番号はプロジェクトセットアップ時に決定する。

Preview版・開発版は原則として使用しない。

---

## 14. 決定事項

### Database

PostgreSQLを採用する。

### 採用理由

- Laravelとの相性がよい
- リレーショナルデータ管理に適している
- 複雑な検索に対応しやすい
- 集計機能との相性がよい
- データ整合性を強く保証できる
- 将来的な検索・分析要件へ対応しやすい

### 基本構成

    Browser
       ↓
    Next.js
    Frontend / BFF
       ↓
    Laravel
    Backend API
       ↓
    PostgreSQL

### 基本方針

- PostgreSQLを主要データストアとする
- Next.jsからDatabaseへ直接アクセスしない
- LaravelからPostgreSQLへアクセスする
- 主要データはリレーショナルモデルとして管理する
- JSONBは必要になった場合のみ利用する
- Laravel ValidationとDatabase Constraintの両方で整合性を保証する
- PostgreSQL固有機能への不必要な依存は避ける
