# アプリケーション構成 決定

## 1. 採用構成

- [ ] モノリス
- [x] フロントエンド / バックエンド分離

リポジトリについては以下とする。

- [x] フロントエンドとバックエンドを1つのリポジトリで管理する
- [ ] フロントエンドとバックエンドを別リポジトリで管理する

---

## 2. 構成方針

フロントエンドアプリケーションとバックエンドAPIを別々のアプリケーションとして構成する。

ただし、ソースコードは1つのGitリポジトリで管理する。

この構成をモノレポ構成とする。

概念上の構成：

    engineer-skill-management/
    ├── frontend/
    ├── backend/
    ├── docs/
    └── README.md

フロントエンドとバックエンドは、それぞれ独立したアプリケーションとして扱う。

---

## 3. フロントエンドの責務

フロントエンドは主に以下を担当する。

- 画面表示
- ユーザー操作
- 入力フォーム
- 入力状態管理
- バックエンドAPIの呼び出し
- APIレスポンスの表示
- クライアント側の入力補助
- 権限に応じたUI表示制御

ただし、業務上重要な権限制御やバリデーションをフロントエンドだけに依存しない。

---

## 4. バックエンドの責務

バックエンドは主に以下を担当する。

- API提供
- 認証
- 認可
- 業務ロジック
- バリデーション
- データ管理
- 権限制御
- 社員スキルの業務ルール適用

例えば以下のルールはバックエンドで必ず保証する。

- 実務経験なしの場合はLevel 1のみ
- 実務経験なしの場合は経験年数0年0か月
- 実務経験なしの場合は最終利用時期なし
- 実務経験ありの場合は経験年数1か月以上
- 実務経験ありの場合は最終利用時期必須
- 同じ社員に同じスキルを重複登録できない
- 権限に応じて操作可能な社員を制限する

---

## 5. モノレポを採用する理由

### メリット

- フロントエンドとバックエンドを1つのリポジトリで管理できる
- IssueやPull Requestをまとめて管理できる
- 1つの機能変更をフロント・バックまとめてレビューしやすい
- API変更とフロントエンド変更を同じPRで扱える
- ドキュメントを同じリポジトリで管理できる
- CI/CD設定を集約しやすい
- MVP規模ではリポジトリ管理がシンプルになる

### デメリット

- リポジトリが将来的に大きくなる可能性がある
- フロントエンドとバックエンドで異なる開発環境を管理する必要がある
- CIで不要なアプリケーションまで実行しないよう工夫が必要になる
- ディレクトリ・責務の境界を明確にする必要がある

---

## 6. リポジトリ構成案

初期段階では以下のような構成を想定する。

    engineer-skill-management/
    ├── frontend/
    │   └── フロントエンドアプリケーション
    │
    ├── backend/
    │   └── バックエンドAPI
    │
    ├── docs/
    │   ├── requirements/
    │   ├── stories/
    │   └── design/
    │
    ├── .github/
    │   └── workflows/
    │
    └── README.md

具体的なディレクトリ構成は採用技術決定後に確定する。

---

## 7. APIによる連携

フロントエンドとバックエンドはAPIを通して通信する。

基本的な構成：

    Browser
       |
       v
    Frontend Application
       |
       | HTTP / API
       v
    Backend API
       |
       v
    Database

フロントエンドからデータベースへ直接アクセスしない。

---

## 8. 独立性

フロントエンドとバックエンドは以下の観点で独立したアプリケーションとして扱う。

- 起動方法
- 依存パッケージ
- テスト
- ビルド
- 設定
- デプロイ

一方で、以下はリポジトリ内で共有して管理する。

- 要件定義
- User Story
- Acceptance Criteria
- API仕様
- 開発ルール
- CI/CD設定
- プロジェクトドキュメント

---

## 9. MVPでの方針

MVPでもフロントエンドとバックエンドを分離する。

ただし、過度に複雑な分散構成にはしない。

以下はMVPでは行わない。

- マイクロサービス化
- 複数バックエンドサービスへの分割
- イベント駆動アーキテクチャ
- API Gatewayの導入
- 複雑なサービス間通信

バックエンドAPIは1つのアプリケーションとして構成する。

---

## 10. 決定事項

### アプリケーション構成

**フロントエンド / バックエンド分離構成を採用する。**

### リポジトリ構成

**モノレポ構成を採用する。**

### 基本構成

    Monorepo
    ├── Frontend Application
    └── Backend API

### 方針

- フロントエンドとバックエンドは別アプリケーションとする
- ソースコードは1つのGitリポジトリで管理する
- フロントエンドとバックエンドはAPIで通信する
- バックエンドAPIはMVPでは1アプリケーションとする
- 業務ロジック・認証・認可はバックエンド側で保証する
- フロントエンドはUIとユーザー操作を中心に担当する
