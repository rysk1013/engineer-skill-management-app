# テストツール 技術決定

## 1. 採用ツール

### Frontend / BFF

- [x] Vitest
- [x] React Testing Library
- [x] Playwright

### Backend API

- [x] PHPUnit
- [x] Laravel Feature Test

---

## 2. 全体方針

テストツールは以下の役割で使い分ける。

    Frontend Unit / Component
        ↓
    Vitest
    +
    React Testing Library

    BFF
        ↓
    Vitest

    Backend API
        ↓
    PHPUnit
    +
    Laravel Feature Test

    E2E
        ↓
    Playwright

テストツールを増やしすぎず、それぞれの責務を明確にする。

---

## 3. Vitest

### 用途

VitestはNext.js側のUnit Test / Integration TestのTest Runnerとして利用する。

主な対象：

- Utility
- Helper
- Form Logic
- BFF Logic
- Route Handler周辺の処理
- Server側の小さな処理
- React Component Testの実行

### 採用理由

- TypeScriptを扱いやすい
- JSX / TSXを扱える
- Jestに近いAPIを利用できる
- Mock機能を利用できる
- Watch Modeを利用できる
- Frontend開発との相性がよい

---

## 4. React Testing Library

### 用途

React Componentのテストに利用する。

主な対象：

- Form
- Button
- Input
- Select
- Validation Message
- Skill Form
- Employee Form
- 権限による表示切り替え

実装内部ではなく、ユーザーから見える振る舞いを中心にテストする。

### 例

社員スキル登録フォーム：

    実務経験
        ↓
    なしを選択
        ↓
    Level 1のみ選択可能
        ↓
    最終利用時期が入力不可

このようなUIの振る舞いをテストする。

### 基本方針

Component内部のstateやprivateな実装詳細ではなく、

- 表示されているか
- 操作できるか
- 入力できるか
- Validation Messageが表示されるか

を中心に確認する。

---

## 5. Frontendのテスト構成

基本構成：

    Vitest
       |
       +-- Utility Test
       |
       +-- Form Logic Test
       |
       +-- Component Test
               |
               +-- React Testing Library

例：

    frontend/
    └── tests/
        ├── unit/
        └── components/

具体的なDirectory構成はFrontend設計時に決定する。

---

## 6. Frontendで重点的にテストするもの

MVPでは以下を重点的にテストする。

### 社員フォーム

- 必須項目
- 任意項目
- Validation表示

### 社員スキルフォーム

実務経験なし：

- Level 1のみ選択可能
- Level 2〜5を選択できない
- 経験年数は0年0か月
- 最終利用時期は入力不可

実務経験あり：

- Level 1〜5を選択可能
- 経験年数を入力可能
- 最終利用時期を入力可能

---

## 7. BFF Test

Next.js BFFのテストにはVitestを利用する。

主な対象：

- Auth.js Session確認
- 未認証時の処理
- Laravel API Request生成
- Sanctum Bearer Token付与
- Laravel API Response処理
- Error Mapping
- 401 Unauthorized
- 403 Forbidden
- 422 Validation Error
- 500 Server Error

---

## 8. BFFでテストしないもの

BFFには業務ロジックを持たせないため、以下はLaravel側でテストする。

例：

    実務経験なし
        ↓
    Level 1のみ

    実務経験あり
        ↓
    経験年数1か月以上

BFFではBackend APIとの通信とFrontend向けの処理を中心に確認する。

---

## 9. PHPUnit

### 用途

Laravel Backend APIのTest FrameworkとしてPHPUnitを採用する。

Laravel標準のTesting機能と組み合わせて使用する。

実行例：

    php artisan test

または：

    vendor/bin/phpunit

Docker環境では：

    docker compose exec backend php artisan test

---

## 10. Laravel Feature Test

Backend APIではFeature Testをテストの中心とする。

主な対象：

- HTTP Request
- Authentication
- Authorization
- Validation
- Business Rule
- Database
- API Response

今回のアプリではFeature Testを最も重視する。

## 12. Backend業務ルールテスト

以下のルールはLaravel Feature Testで必ず確認する。

### 実務経験なし

- 経験年数0年0か月
- Level 1のみ許可
- Level 2は拒否
- Level 3は拒否
- Level 4は拒否
- Level 5は拒否
- 最終利用時期は設定不可

### 実務経験あり

- 経験年数1か月以上
- 0年0か月は拒否
- Level 1〜5を許可
- 最終利用時期必須

### 重複スキル

- 同じ社員 + 同じスキルを重複登録できない

---

## 13. Laravel Unit Test

Unit Testは必要な箇所のみ作成する。

対象例：

- 純粋な業務ロジック
- Value Object
- Serviceの小さな計算
- Utility

Laravel FrameworkやDatabaseを利用する処理を無理にUnit Testへ分離しない。

今回のBackendはFeature Testを優先する。

---

## 14. Playwright

### 用途

E2E TestにはPlaywrightを採用する。

Browserから実際のアプリケーションを操作し、

    Browser
       ↓
    Next.js
       ↓
    BFF
       ↓
    Laravel
       ↓
    PostgreSQL

まで含めた主要業務フローを確認する。

---

## 15. Playwrightを採用する理由

- 実Browserを利用したE2E Testができる
- Chromium / Firefox / WebKitに対応できる
- TypeScriptを利用できる
- Auto Wait機能を利用できる
- ScreenshotやTraceを利用できる
- CIとの相性がよい

MVPではすべての画面をE2E化せず、主要なUser Storyに限定する。

## 17. テストツールの役割分担

| 対象 | ツール | 主な目的 |
| --- | --- | --- |
| TypeScript Utility | Vitest | Unit Test |
| React Component | Vitest + React Testing Library | Component Test |
| Next.js BFF | Vitest | Integration Test |
| Laravel Unit | PHPUnit | Unit Test |
| Laravel API | PHPUnit + Laravel Feature Test | Feature / Integration Test |
| 全体 | Playwright | E2E Test |

---

## 18. テストの優先順位

MVPでは以下の順で重要視する。

1. Laravel Feature Test
2. Frontend Component Test
3. BFF Test
4. Playwright E2E Test
5. Unit Test

業務ルールを持つLaravel Backend APIのテストを最優先とする。

---

## 19. Test Coverage

Coverage率そのものを開発目標にしない。

例えば、

    Coverage 100%

を目指すことより、

    重要な業務ルールがTestされている

ことを重視する。

特に以下のCoverageを優先する。

- Authentication
- Authorization
- Validation
- Business Rule
- User Story
- Acceptance Criteria

---

## 20. Mock方針

### Frontend

必要に応じてAPI ResponseをMockする。

候補：

- Mock Function
- MSW

MSWの採用は必要性を確認してから決定する。

### BFF

Laravel API ClientをMockし、

- Request
- Response
- Error

を確認する。

### Backend

可能な限りLaravel ApplicationとTest Databaseを利用する。

Repository等を過度にMockしない。

---

## 21. Test Database

Laravel Feature Testでは専用のTest Databaseを利用する。

Database：

    PostgreSQL

開発用DatabaseとTest Databaseを分離する。

例：

    Development
    engineer_skill

    Test
    engineer_skill_test

具体的なDatabase名はDatabase設計時に決定する。

---

## 22. Dockerでのテスト

すべてDocker内でテストを実行できるようにする。

Frontend：

    docker compose exec frontend npm test

Backend：

    docker compose exec backend php artisan test

E2E：

    docker compose exec frontend npx playwright test

具体的なCommandはpackage.json等で統一する。

---

## 23. CI

Pull Request時に以下を実行することを基本方針とする。

### Frontend

- Lint
- Type Check
- Vitest

### Backend

- Formatter / Lint
- Static Analysis
- PHPUnit / Laravel Test

### E2E

Playwrightについては実行時間を考慮し、

- Pull Request
- Main Branch
- Release前

のどこで実行するかをCI設計時に決定する。

## 24. 採用しない候補

### Jest

MVPでは採用しない。

VitestをFrontend Test Runnerとして統一する。

### Cypress

MVPでは採用しない。

E2E TestはPlaywrightへ統一する。

### Pest

MVPでは採用しない。

Laravel BackendはPHPUnitへ統一する。

将来的に必要性があれば再検討する。

---

## 25. 決定事項

### Frontend Unit / Component Test

Vitest + React Testing Libraryを採用する。

### BFF Test

Vitestを採用する。

### Backend Test

PHPUnit + Laravel Feature Testを採用する。

### E2E Test

Playwrightを採用する。

### Test Database

PostgreSQLを利用する。

### 基本方針

- Laravel Feature Testを最重視する
- React Componentはユーザー視点でテストする
- BFFでは通信・Session・Error処理をテストする
- E2Eは主要業務フローに限定する
- Coverage 100%を目標にしない
- User Story / Acceptance CriteriaをTestの基準とする
