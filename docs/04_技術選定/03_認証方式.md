# 認証方式

## 1. 概要

Engineer Skill Management Appでは、
Frontend / BFFとBackend APIを分離し、
それぞれの境界に適したAuthenticationを利用する。

基本構成：

```text
Browser
   ↓
Next.js
Frontend / BFF
   ↓
Laravel
Backend API
   ↓
PostgreSQL
```

Authenticationは以下のように分離する。

```text
Browser
   ↓ Better Auth Session
Next.js BFF
   ↓ Laravel Sanctum Token
Laravel API
```

採用方式：

| 境界 / 用途 | 採用技術 |
| --- | --- |
| Browser ↔ Next.js | Better Auth |
| Session Store | Redis |
| Application User Authentication | Laravel |
| Next.js ↔ Laravel API | Laravel Sanctum |
| Application Database | PostgreSQL |
| Authorization | Laravel Policy / Application Layer / Domain Rule |

Browser Session、Application User Authentication、
Backend API Authenticationを別の責務として扱う。

---

## 2. Auth.jsからBetter Authへの変更

従来はBrowserとNext.js間のSession管理に
Auth.jsを採用していた。

MVP実装開始前に認証技術を再評価し、
新規実装ではBetter Authを採用する。

変更：

```text
Before

Browser
   ↓
Auth.js
   ↓
Next.js BFF


After

Browser
   ↓
Better Auth
   ↓
Next.js BFF
```

LaravelをApplication User Authenticationの主体とする方針、
Laravel SanctumをBackend API Authenticationへ利用する方針は
変更しない。

旧Auth.js前提の技術選定はArchiveとして保持し、
現行仕様の根拠には使用しない。

---

## 3. Session Storeの変更

従来はAuth.js Database Sessionの保存先として
PostgreSQLを採用していた。

Better Authへの変更に合わせ、
Session StoreをRedisへ変更する。

```text
Before

Next.js / Auth.js
   ↓
PostgreSQL


After

Next.js / Better Auth
   ↓
Redis
```

理由：

- Next.jsからApplication Databaseへ直接接続しないため
- PostgreSQLへの直接接続をLaravel Backendへ限定するため
- Sessionは有効期限を持つ一時的なAuthentication Stateであるため
- Session単位の失効をServer Sideで行うため
- 強制Logoutへ対応するため
- 複数端末Sessionを管理するため
- TTLを利用したSession期限管理と相性がよいため
- Application DataとAuthentication StateのOwnershipを明確に分離するため

---

## 4. Authentication全体構成

MVPのAuthentication Architecture：

```text
┌──────────────┐
│   Browser    │
└──────┬───────┘
       │
       │ Better Auth Session Cookie
       ▼
┌──────────────────┐
│     Next.js      │
│ Frontend / BFF   │
└─────┬──────┬─────┘
      │      │
      │      │ Session
      │      ▼
      │   ┌───────────┐
      │   │   Redis   │
      │   └───────────┘
      │
      │ Laravel Sanctum Token
      ▼
┌──────────────────┐
│   Laravel API    │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│   PostgreSQL     │
└──────────────────┘
```

BrowserはSanctum Tokenを保持しない。

Next.jsはPostgreSQLへ直接接続しない。

---

## 5. 採用技術

### Browser Session Management

**Better Auth**

BrowserとNext.js間の
Authentication State / Session Managementに利用する。

### Session Store

**Redis**

Better Auth SessionをServer Sideで管理する。

### Application User Authentication

**Laravel**

Application UserのCredential検証を担当する。

### Backend API Authentication

**Laravel Sanctum**

Next.js BFFからLaravel Backend APIへの
Authenticationに利用する。

### Application Database

**PostgreSQL**

Application DataおよびLaravelが所有するDataを管理する。

PostgreSQLへ直接接続するApplication Componentは
Laravel Backendのみとする。

### Authorization

以下を責務に応じて利用する。

- Laravel Policy
- Application Layer
- Domain Rule

---

## 6. Login Credential

ApplicationへのLoginには以下を使用する。

```text
login_id
password
```

Application User：

```text
users
├── login_id
└── password
```

Login Form：

```text
ログインID
[                 ]

パスワード
[                 ]

[ ログイン ]
```

`users.name`はLogin Credentialとして使用しない。

`users.name`はApplication上の表示名として利用する。

---

## 7. Application User Authentication

Application User Authenticationの主体はLaravelとする。

基本フロー：

```text
Browser
   ↓
login_id + password
   ↓
Next.js BFF
   ↓
Laravel Login API
   ↓
users.login_idでUser特定
   ↓
users.passwordをHash検証
   ↓
users.is_active確認
   ↓
Authentication成功
```

無効User：

```text
users.is_active = false
```

はLoginできない。

Password HashのOwnershipはLaravel側とする。

Better AuthへPassword Credentialを保存しない。

---

## 8. Better Authの役割

Better AuthはBrowserとNext.js間の
Session Managementを担当する。

主な責務：

- Session作成
- Session取得
- Session検証
- Session更新
- Session失効
- Session Cookie管理
- Session有効期限管理
- Redis Session Storeとの連携
- Server SideでのAuthentication State取得

Better AuthはLaravelに代わって
Application UserのPasswordを検証しない。

---

## 9. Better Authで採用しないAuthentication方式

MVPではBetter Authのbuilt-in email/password Authenticationを
Application Loginには使用しない。

Better Auth Username Pluginも
Application Loginの主体として使用しない。

理由：

- Application Loginは`login_id + password`である
- ApplicationではメールアドレスをUser属性として管理しない
- Password HashはLaravel側で管理する
- CredentialをNext.jsとLaravelで二重管理しない
- Application User Authenticationの主体をLaravelへ統一する

採用しない構成：

```text
Browser
   ↓
Better Auth
   ↓ email / password Authentication
```

採用する構成：

```text
Browser
   ↓ login_id + password
Next.js BFF
   ↓
Laravel
   ↓ Authentication
Next.js
   ↓
Better Auth Session
```

---

## 10. Browser → Next.js

Browser Authentication Stateの管理には
Better Authを利用する。

```text
Browser
   ↓
Better Auth Session Cookie
   ↓
Next.js
```

BrowserはBetter Authが管理するSession Cookieを利用して
Authentication状態を維持する。

BrowserからRedisへ直接アクセスしない。

Laravel SessionをBrowser Authenticationには利用しない。

---

## 11. Next.js → Laravel API

Next.js BFFからLaravel APIへのAuthenticationには
Laravel Sanctumを利用する。

```text
Next.js BFF
   ↓
Authorization: Bearer <Sanctum Token>
   ↓
Laravel API
```

SanctumはBrowser Session Authenticationではなく、

```text
Next.js BFF
    ↕
Laravel Backend API
```

間のAPI Authenticationとして利用する。

Sanctum TokenはNext.js Server Sideでのみ扱う。

---

## 12. BFF方針

Next.jsをBFF（Backend for Frontend）として利用する。

Browserは原則としてNext.jsを経由して
Laravel APIへアクセスする。

```text
Browser
   ↓
Next.js BFF
   ↓
Laravel API
```

Next.js BFFのAuthentication責務：

- Better Auth Session確認
- Browser Authentication State確認
- Laravel Login API呼び出し
- Backend API Credential取得
- Laravel APIへのAuthentication Header付与
- Backend Credentialの安全な管理
- BrowserとLaravel APIのSecurity Boundary

---

## 13. PostgreSQL Access Boundary

PostgreSQLへの直接接続は
Laravel Backendのみとする。

採用する構成：

```text
Next.js
   ↓ HTTP
Laravel API
   ↓
PostgreSQL
```

採用しない構成：

```text
Next.js
   ↓
PostgreSQL
```

Next.jsがAuthentication処理を担当することを理由として、
PostgreSQLへ直接接続しない。

---

## 14. Application Data Access

Application Dataの取得・更新は
必ずLaravel APIを経由する。

```text
Next.js
   ↓
Laravel API
   ↓
PostgreSQL
```

対象：

- users
- employees
- departments
- skill_categories
- skills
- employee_skills
- Access Control Data
- その他Application Data

Next.jsからこれらのTableを直接操作しない。

---

## 15. Redisの役割

RedisはAuthenticationに必要な
短命なServer Side Stateの管理に利用する。

MVPではRedisを1台使用する。

概念：

```text
Redis
├── Better Auth Session
└── Backend API Credential
```

ただし、
SessionとBackend Credentialは
論理的・権限的に分離する。

RedisをApplication DataのPrimary Storeとして使用しない。

---

## 16. RedisをSession Storeに採用する理由

主な理由：

- Next.jsからPostgreSQLへ接続する必要がない
- PostgreSQL Access Boundaryを維持できる
- Sessionは短命なStateである
- TTLによる有効期限管理と相性がよい
- Session Lookupに適している
- Session単位でServer Sideから削除できる
- 強制Logoutに対応しやすい
- 複数端末Sessionを管理しやすい
- Next.jsを複数Instanceで実行してもSessionを共有できる

---

## 17. Redis Instance

MVPではRedisを2台へ分離しない。

```text
Redis Instance
├── Better Auth
└── BFF Credential Store
```

Infrastructure追加コストを抑えるため、
1 Redis Instanceを共用する。

ただし、

```text
同じRedisを使う
```

ことと、

```text
同じ責務・同じ権限で扱う
```

ことは分けて考える。

---

## 18. Redis Key Namespace

Better Auth SessionとBackend Credentialは
Key Namespaceを分離する。

概念：

```text
better-auth:*
```

Better Auth管理領域。

```text
backend-credential:*
```

BFF Credential管理領域。

具体的なKey Schemaは
Authentication詳細設計で決定する。

Better Authが管理するKeyへ
独自Credential情報を混在させない。

---

## 19. Redis ACL

Better AuthとBackend Credential Storeでは
Redis Access権限を分離する。

概念：

```text
Better Auth Redis User
   ↓
better-auth:* のみ


BFF Credential Redis User
   ↓
backend-credential:* のみ
```

Least Privilegeを基本とする。

Better Auth用Redis Credentialから
Backend Credential Namespaceを
参照できない構成を基本とする。

BFF Credential用Redis Credentialからも、
不要なBetter Auth Keyへアクセスさせない。

具体的なRedis User名・ACL Ruleは
Infrastructure詳細設計で決定する。

---

## 20. Better Auth Secondary Storage

Better AuthのSession Storeとして
Redis Secondary Storageを利用する。

概念：

```text
Better Auth
   ↓
Redis Secondary Storage
   ↓
better-auth:*
```

Better Auth公式のRedis Storage Integrationを
第一候補とする。

Better AuthからPostgreSQLへ
Sessionを保存しない。

SessionのPrimary StorageはRedisとする。

---

## 21. Session Cookie

Browser側には
Better Auth Session Cookieのみを保持する。

基本Security属性：

- `HttpOnly`
- Production / Stagingでは`Secure`
- 適切な`SameSite`
- 必要最小限の`Path`
- 適切な有効期限

Production / StagingではHTTPSを利用する。

Cookieへ以下を保存しない。

- Sanctum Token
- Password
- Encryption Key
- Server Side Secret

---

## 22. Cookie Cache

MVPではBetter AuthのSession Cookie Cacheを
基本的に使用しない。

理由：

- Redis上のSession失効を速やかに反映するため
- 強制Logoutの意味を明確にするため
- Session StateのSource of TruthをRedisへ置くため
- 初期構成を単純にするため

基本構成：

```text
Request
   ↓
Session Cookie
   ↓
Next.js / Better Auth
   ↓
Redis Session Lookup
```

Performance上の必要性が確認された場合に
Cookie Cacheの利用を再検討する。

---

## 23. Session有効期限

Sessionには有効期限を設定する。

Redis TTLと
Better Auth Session Expirationを整合させる。

概念：

```text
Better Auth Session Expiration
        =
Redis Session TTL
```

詳細設計では以下を決定する。

- Maximum Session Lifetime
- Session Renewal
- Idle Timeoutの有無
- Session Rotation
- Redis TTL
- Sanctum Token Lifetime
- Session / Token Expirationの整合性

具体的な時間はSecurity詳細設計で決定する。

---

## 24. Better Auth SessionとApplication User

Application UserはLaravel管理の、

```text
users
```

とする。

Better Auth Sessionは
Application Userを識別できる必要がある。

概念：

```text
Better Auth Session
        ↓
Application User ID
        ↓
users.id
```

ただし、Next.jsから`users` Tableを直接参照しない。

Login時にLaravelから返された
認証済みApplication User情報を利用する。

Better Auth内部で必要となるUser表現・Session Payloadについては
Authentication詳細設計で決定する。

---

## 25. Better Auth User Model

Better Auth標準の永続User Tableを
Application User Tableとして採用しない。

以下を避ける。

```text
Better Auth User Table
        =
Application users Table
```

理由：

- Application UserはDomain上のEntityである
- Application UserのOwnershipはLaravelにある
- `users`には`login_id` / `password` / `employee_id`等の業務上の意味がある
- Better Auth内部SchemaへApplication Entityを依存させない
- Next.jsからPostgreSQLへ接続しない方針を維持する

Better AuthがLaravel認証結果を用いて
Sessionを成立させる具体方式は
Authentication詳細設計で確定する。

---

## 26. Login Flow

基本Login Flow：

```text
1. Browser
   ↓
   login_id + password

2. Next.js BFF
   ↓
   Laravel Login API

3. Laravel
   ↓
   users.login_idでUser検索
   password Hash検証
   is_active確認

4. Laravel
   ↓
   Authentication成功
   Sanctum Token発行

5. Laravel
   ↓
   認証済みUser情報
   +
   Sanctum Token

6. Next.js
   ↓
   Better Auth Session作成

7. Better Auth
   ↓
   SessionをRedisへ保存

8. Next.js BFF
   ↓
   Sanctum Token暗号化

9. BFF Credential Store
   ↓
   Redisへ保存

10. Browser
    ↓
    Better Auth Session Cookie

11. Login完了
```

Session作成とCredential保存の
失敗時処理・Rollbackは
Authentication詳細設計で決定する。

---

## 27. Backend API Request Flow

Login後：

```text
Browser
   |
   | Better Auth Session Cookie
   v
Next.js / Better Auth
   |
   | Session Lookup
   v
Redis
   |
   | Session Valid
   v
Next.js BFF
   |
   | Backend Credential Lookup
   v
Redis
   |
   | Encrypted Sanctum Token
   v
Next.js BFF
   |
   | Decrypt
   |
   | Authorization: Bearer <token>
   v
Laravel API
   |
   | Sanctum Authentication
   v
Application Processing
```

BrowserからLaravel Backend APIを
直接呼び出さない。

---

## 28. Sanctum Token Storage

Sanctum Tokenは
Better Auth Session Dataへ直接含めない。

Better Auth Session Storeとは
別Namespaceで管理する。

概念：

```text
Redis

better-auth:*
└── Session

backend-credential:*
└── Sanctum Token
```

Better Auth内部Session Structureへ
Sanctum Tokenを追加しない。

---

## 29. Backend Credential

Backend API Credentialとして
Laravel Sanctum Tokenを保持する。

SessionとCredentialは
論理的な対応関係を持つ。

通常のLogin完了後：

```text
1 Better Auth Session
        │
        │ 1 : 1
        ▼
1 Backend API Credential
  (Sanctum Token)
```

複数端末Login時：

```text
Browser A
   ↓
Session A
   ↓
Sanctum Token A


Browser B
   ↓
Session B
   ↓
Sanctum Token B
```

各SessionのCredentialを独立させる。

---

## 30. Sanctum Token暗号化

Sanctum TokenはSecretとして扱う。

Redisへ平文のまま保存しない。

Application Level Encryptionを利用する。

保存時：

```text
Sanctum Token
   ↓
Encrypt
   ↓
backend-credential:*
```

利用時：

```text
backend-credential:*
   ↓
Decrypt
   ↓
Authorization Header
```

暗号化・復号は
Next.js Server Sideで行う。

Encryption KeyをRedisへ保存しない。

Encryption KeyをSource Codeへ保存しない。

環境変数またはSecret Management Serviceを利用する。

---

## 31. Sanctum TokenをBrowserへ公開しない

Sanctum Tokenは
Next.js Server Sideでのみ使用する。

以下への保存を禁止する。

- localStorage
- sessionStorage
- Client Side State
- Browser JavaScriptから参照可能なCookie
- Better Auth Session Cookie

以下への出力も禁止する。

- Application Log
- Error Response
- Analytics
- Client Component Props

---

## 32. Session / Credential Key Relation

Better Auth SessionとBackend Credentialを
関連付ける識別方法を定義する。

概念：

```text
Session Identifier
        ↓
Backend Credential Key
```

Backend Credential Keyに
Sanctum Tokenそのものを含めない。

具体的なKey設計は
Authentication詳細設計で決定する。

---

## 33. Credential TTL

Backend Credentialにも有効期限を設定する。

基本方針：

```text
Credential TTL
<=
対応するSession有効期間
```

Session失効後にCredentialだけが
長期間Redisへ残らないようにする。

Laravel Sanctum Token自体の有効期限とも
整合させる。

---

## 34. Logout

Logout時：

```text
1. Better Auth Session特定

2. Backend Credential特定

3. Sanctum Token復号

4. LaravelへToken失効Request

5. Laravel側Sanctum Token失効

6. backend-credential:* 削除

7. Better Auth Session失効

8. better-auth:* Session削除

9. Browser Session Cookie無効化
```

Credential連携済みSessionについて、
Better Auth Sessionだけを削除して
Laravel Tokenを残さない。

具体的な実行順序、
Error Handling、
Retryは詳細設計で決定する。

---

## 35. 強制Logout

Server SideからSessionを失効可能とする。

対象例：

- User無効化
- Security Incident
- Administratorによる強制Logout
- Credential漏洩の疑い
- Permission変更に伴う再認証

基本処理：

```text
Session特定
   ↓
Sanctum Token失効
   ↓
Backend Credential削除
   ↓
Better Auth Session削除
```

---

## 36. User無効化

Application User：

```text
users.is_active = false
```

となった場合、

- 新規Loginを禁止する
- 既存Sessionを失効対象とする
- 対応するSanctum Tokenを失効させる
- Backend Credentialを削除する

ことを基本方針とする。

具体的な連携方式は
Authentication詳細設計で決定する。

---

## 37. 複数端末Login

複数Sessionを許可する。

```text
User A
├── Browser Session A
│      └── Sanctum Token A
│
└── Browser Session B
       └── Sanctum Token B
```

Session単位でLogout可能とする。

全端末Logoutでは、
対象Userに関連するすべてのSessionとCredentialを失効する。

---

## 38. Session Lifecycle

以下の状態を考慮する。

- Login
- Logout
- 強制Logout
- Session有効期限切れ
- User無効化
- Permission変更
- Security Incident
- Redis TTL Expiration

SessionとBackend CredentialのLifecycleを
可能な限り対応させる。

---

## 39. Session失効

Better Auth Sessionが失効した場合、
対応するBackend Credentialも
利用不能にすることを基本方針とする。

避ける状態：

```text
Better Auth Session
→ Invalid

Sanctum Token
→ Valid
```

完全なDistributed Transactionは前提としない。

失効処理はIdempotentに設計する。

---

## 40. Redis障害時

Redisが利用できない場合、
Authentication Stateを安全側に倒す。

基本方針：

```text
Sessionを確認できない
        ↓
Authenticatedとして扱わない
```

Redis障害時に
未検証のSessionを有効として扱わない。

Application DataはPostgreSQLに保持されるため、
Redis障害によって業務データが失われる構成にはしない。

必要に応じてUserへ再Loginを要求する。

---

## 41. Redis Persistence

RedisをApplicationの永続的な業務データStoreとして扱わない。

Redisで保持するData：

- Better Auth Session
- Backend API Credential
- Authenticationに必要な短命Data

Redis Dataが失われた場合に
業務Dataが失われる構成にはしない。

Redis Persistence / Backupの具体方式は
Infrastructure設計で決定する。

---

## 42. AuthenticationとAuthorizationの分離

AuthenticationとAuthorizationを
明確に分離する。

### Authentication

```text
Who are you?
```

担当：

```text
Application Credential Authentication
└── Laravel

Browser Session
└── Better Auth

Backend API Authentication
└── Laravel Sanctum
```

### Authorization

```text
Are you allowed to do this?
```

担当：

- Laravel Policy
- Application Layer
- Domain Policy
- Domain Invariant

Frontend UI制御のみで
Authorizationを保証しない。

---

## 43. Domainとの分離

Authentication Infrastructure情報を
Domainへ持ち込まない。

Domain Userに以下を保持させない。

- Better Auth Session
- Session Token
- Sanctum Token
- Redis Key
- Cookie
- Better Auth Object
- Laravel Auth Object

Domainは以下へ依存しない。

```text
Better Auth
Redis
Sanctum
Laravel Auth
Cookie
HTTP
```

AuthenticationはTechnical Concernとして扱う。

---

## 44. Security方針

Authenticationでは以下を基本方針とする。

- HTTPSを前提とする
- Session CookieはHttpOnlyとする
- Production / StagingではSecure Cookieを使用する
- Sanctum TokenをBrowserへ公開しない
- Sanctum TokenをClient Side Storageへ保存しない
- Sanctum TokenをRedisへ平文保存しない
- Better Auth SessionとBackend CredentialをNamespace分離する
- Redis ACLでLeast Privilegeを適用する
- Better Auth用Redis CredentialからBackend Credentialを参照させない
- Session TokenをLogへ出力しない
- Sanctum TokenをLogへ出力しない
- Encryption KeyをRepositoryへ保存しない
- AuthenticationとAuthorizationを分離する
- PostgreSQLへNext.jsから直接接続しない
- Frontend UI制御だけにAuthorizationを依存しない

---

将来的に以下のIdentity Providerを
利用する可能性を考慮する。

- Microsoft Entra ID
- Okta
- Google Workspace
- その他OIDC Provider

将来的にAuthentication方式が変更されても、

```text
Browser
   ↓
Next.js / Better Auth
   ↓
```

## 51. 決定事項

### Authentication Architecture

```text
Browser
   ↓
Better Auth Session Cookie
   ↓
Next.js Frontend / BFF
   ├── Better Auth Session → Redis
   └── Backend Credential → Redis
   ↓
Laravel Sanctum Token
   ↓
Laravel Backend API
   ↓
PostgreSQL
```

### Application Login

```text
login_id + password
        ↓
Laravel
```

LaravelをApplication User Authenticationの主体とする。

### Browser Session Management

**Better Authを採用する。**

### Session Store

**Redisを採用する。**

```text
Better Auth
   ↓
Redis
```

### Redis構成

**MVPではRedis 1 Instanceを利用する。**

```text
Redis
├── better-auth:*
└── backend-credential:*
```

Key NamespaceとACLで責務を分離する。

### Better Auth Storage

Better Auth SessionをRedisへ保存する。

Better AuthからPostgreSQLへ直接接続しない。

### Cookie Cache

MVPでは基本的に使用しない。

Redis上のSession Stateを
認証判断の基準とする。

### Application Database

**PostgreSQLを採用する。**

PostgreSQLへの直接接続は
Laravel Backendのみに限定する。

### Backend API Authentication

**Laravel Sanctumを採用する。**

```text
Next.js BFF
   ↓
Sanctum Token
   ↓
Laravel API
```

### Backend Credential Store

Sanctum Tokenは
Better Auth Sessionとは別Namespaceで
Redisへ保存する。

```text
backend-credential:*
```

Application Level Encryptionを利用する。

### Better Auth Session / Credential Relation

通常のLogin完了後：

```text
1 Better Auth Session
        │
        │ 1 : 1
        ▼
1 Backend API Credential
  (Sanctum Token)
```

### Redis ACL

Better Auth SessionとBackend Credentialでは
Redis Access権限を分離する。

Least Privilegeを適用する。

### Authorization

```text
Authentication
├── Laravel
├── Better Auth
└── Laravel Sanctum

Authorization
├── Laravel Policy
├── Application Layer
└── Domain Rule
```

### 責務

```text
Browser
└── Better Auth Session Cookie

Next.js / Better Auth
├── Browser Session Management
├── Authentication State
└── Redis Session

Next.js BFF
├── Laravel Login API連携
├── Backend API Credential Management
├── Credential Encryption / Decryption
└── Browser / Laravel Security Boundary

Redis
├── Better Auth Session
└── Encrypted Backend Credential

Laravel
├── Application User Authentication
├── login_id / password検証
├── User有効状態確認
└── Application Processing

Laravel Sanctum
└── Backend API Authentication

PostgreSQL
└── Laravel所有Data

Laravel Policy / Application
└── Authorization

Domain
└── Authentication Frameworkに依存しない
```

以上をMVPのAuthentication基本方針として採用する。
