# Frontend 技術選定 基本方針

## 1. 目的

本ドキュメントでは、Engineer Skill Management AppのFrontendおよびBFFで利用する技術・Libraryを選定する際の基本方針を定義する。

個別の技術・Libraryについては `Frontend/` 配下の各技術選定ドキュメントで管理する。

Frontendのレイヤー構成、Server / Client境界、データ取得、状態管理などのArchitectureについてはFrontend Architectureで管理し、本ドキュメントでは技術選定における判断基準を扱う。

---

## 2. 基本原則

FrontendはNext.js + React + TypeScriptを中心として構成する。

技術・Libraryの選定では以下を基本原則とする。

- Next.js / React標準機能を優先する
- TypeScriptを前提とする
- OpenAPIをAPI契約のSource of Truthとする
- Server Firstを基本とする
- 状態の種類ごとに管理方法を分ける
- Libraryの責務を重複させない
- Headless / ComposableなLibraryを優先する
- 型安全性を重視する
- Libraryを増やしすぎない
- MVPと将来拡張を分ける
- Architectureと技術選定を分離する

---

## 3. Next.js / React標準機能を優先する

Next.jsまたはReactの標準機能で十分に実現できる場合は、追加Libraryを安易に導入しない。

特に以下についてはNext.js App RouterおよびReactの機能を優先的に検討する。

- Server Components
- Client Components
- Route Handlers
- Server Actions
- Cache / Revalidation
- Error Handling
- Loading UI
- React標準のState管理

追加Libraryは、標準機能だけでは要件を十分に満たせない場合や、導入による明確なメリットがある場合に採用する。

---

## 4. TypeScriptを前提とする

FrontendおよびBFFのアプリケーションコードはTypeScriptで実装する。

JavaScriptによるアプリケーションコードは原則として作成しない。

TypeScriptの型安全性を活用し、可能な限りコンパイル時または開発時に不整合を検出する。

特に以下の境界で型安全性を重視する。

    Backend API
        ↓
    OpenAPI
        ↓
    API Client
        ↓
    Application
        ↓
    Form / UI

TypeScriptでは `strict` を有効にすることを基本とし、`any` の安易な利用を避ける。

---

## 5. OpenAPIをAPI契約のSource of Truthとする

FrontendとBackend API間のAPI契約はOpenAPIで管理する。

APIのRequest / Response型やAPI Clientについては、OpenAPI Schemaからの自動生成を積極的に利用する。

以下のような型の手動二重管理を原則として行わない。

    OpenAPI Schema

         ↓ Generate

    TypeScript Type
    API Client

Frontend側でBackend APIのRequest / Response型を独自に再定義することを避ける。

OpenAPI全体の管理・運用方針については、別途API・OpenAPI技術選定ドキュメントで管理する。

---

## 6. Server Firstを基本とする

Next.js App RouterではServer Componentsを基本として利用する。

Client Componentは、クライアント側での処理が必要な場合に限定する。

主な利用ケースは以下とする。

- ユーザー操作を伴うInteractive UI
- Browser APIの利用
- Local Stateの管理
- Client-side Data Fetching
- Client-side Server State管理
- Client側でのみ利用できるLibrary

不要な `"use client"` を避け、Client Componentの範囲を必要最小限にする。

ただし、Server Componentを利用すること自体を目的とはせず、UIの責務や実装の単純さを考慮して適切に使い分ける。

---

## 7. 状態の種類ごとに管理方法を分ける

すべての状態をGlobal State Libraryへ集約しない。

状態の性質に応じて管理方法を分ける。

主に以下の状態を区別する。

### Server State

Backend APIなどサーバー側をSource of Truthとするデータ。

### URL State

検索条件、Pagination、Sort、FilterなどURLで表現することが適切な状態。

### Form State

フォーム入力値、Validation Error、送信状態などフォーム固有の状態。

### Local UI State

Modal、Dropdown、ToggleなどComponentまたはFeature内で完結する状態。

### Global Client State

複数の独立した画面・Component間で共有する必要があり、他の状態管理方法では適切に表現できないClient State。

Global Client State Libraryは最初から導入せず、必要性が明確になった場合に採用を検討する。

---

## 8. Libraryの責務を重複させない

同じ問題を解決する複数のLibraryを原則として併用しない。

例えば以下のような重複を避ける。

- 複数のForm Library
- 複数のSchema Validation Library
- 複数のServer State Library
- 複数のGlobal State Library
- 複数のUI Component Library
- 複数のDate Library
- 複数のToast Library

Libraryごとの責務を明確にし、どの問題をどのLibraryで解決するかを判断できる状態を維持する。

---

## 9. Headless / ComposableなLibraryを優先する

UI関連Libraryについては、特定のデザインや実装方式への依存が強いものより、必要に応じて組み合わせやカスタマイズができるHeadless / Composableな構成を優先する。

これにより、Application固有のUI要件へ対応しやすい構成を目指す。

ただし、Headlessであること自体を目的とはしない。

以下も考慮して選定する。

- Accessibility
- 開発効率
- 保守性
- カスタマイズ性
- Documentation
- Community / Ecosystem
- TypeScriptとの親和性

自前実装を増やすことで保守性が低下する場合は、適切なComponent Libraryの利用を優先する。

---

## 10. 型安全性を重視する

Library選定ではTypeScriptとの親和性を重要な評価基準とする。

以下を優先する。

- TypeScriptを正式にサポートしている
- 型定義が十分に提供されている
- Genericなどを利用して型安全に扱える
- 不必要なType Assertionを要求しない
- OpenAPIなど既存の型情報と連携できる

Runtime Validationが必要な境界では、TypeScriptのStatic Typeだけに依存せずSchema Validationの利用を検討する。

---

## 11. Libraryを増やしすぎない

便利という理由だけでLibraryを導入しない。

Libraryを追加する場合は、少なくとも以下を確認する。

- Next.js / React標準機能で代替できないか
- Application内で継続的に利用するか
- 導入によるメリットが明確か
- TypeScriptとの親和性が高いか
- Maintenanceが継続されているか
- Documentationが十分か
- Ecosystemが安定しているか
- Bundle Sizeへの影響が妥当か
- 他Libraryと責務が重複しないか
- 将来的なMigration Costが過度に高くないか

依存Packageが増えること自体を避けるのではなく、導入コストに対して十分な価値があるかを判断する。

---

## 12. MVPと将来拡張を分ける

MVPでは必要な技術・Libraryのみ導入する。

「将来的に必要になる可能性がある」という理由だけでMVPからLibraryを導入しない。

例えば以下のようなLibraryは、実際の必要性を確認してから採用する。

- Global State Library
- 高度なAnimation Library
- 複雑なData Visualization Library
- 高度なClient-side Cache Library
- その他MVPで利用用途が明確でないLibrary

将来的にLibraryを追加できるArchitectureを維持しつつ、初期構成は可能な限り単純にする。

---

## 13. Architectureと技術選定を分離する

Frontend ArchitectureとFrontend技術選定では責務を分離する。

    Frontend Architecture
        ↓
    どう設計するか

    Frontend技術選定
        ↓
    何を使うか

Frontend Architectureでは主に以下を管理する。

- Layer構成
- Server / Client境界
- Component設計
- データ取得方針
- 状態管理方針
- API連携方針
- Error Handling方針
- Cache方針
- Test Strategy

Frontend技術選定では主に以下を管理する。

- 採用する技術
- 採用するLibrary
- 採用理由
- 利用範囲
- 採用しない候補
- 採用しない理由

Architecture上の要求を実現するために適切な技術・Libraryを選定する。

---

## 14. Library選定時の評価基準

個別のLibraryを比較する場合は、必要に応じて以下の観点から評価する。

| 評価項目 | 確認内容 |
| --- | --- |
| 要件適合性 | 必要な機能を満たしているか |
| Next.jsとの親和性 | App RouterやServer Componentsと組み合わせやすいか |
| Reactとの親和性 | Reactの設計思想と大きく競合しないか |
| TypeScript | 型安全に利用できるか |
| 保守性 | 継続的にMaintenanceされているか |
| 安定性 | Production利用に適しているか |
| Documentation | 公式Documentationが十分か |
| Ecosystem | Communityや周辺Toolが充実しているか |
| Accessibility | UI Libraryの場合、Accessibilityを考慮しているか |
| Performance | Runtime / Bundle Sizeへの影響が妥当か |
| Developer Experience | 実装・Test・Debugが行いやすいか |
| Lock-in | Libraryへの過度な依存が発生しないか |
| Migration Cost | 将来的な変更が極端に困難にならないか |
| MVP適合性 | 現時点で導入する必要性があるか |

すべてのLibraryについて機械的に全項目を比較する必要はない。

重要度の高いLibraryや複数の有力候補が存在する場合に、必要な評価項目を利用する。

---

## 15. 技術選定の記録方法

個別の技術・Libraryについて、必要に応じて以下を記録する。

    候補
      ↓
    比較
      ↓
    採用
      ↓
    採用理由
      ↓
    利用範囲
      ↓
    採用しない候補と理由

比較する意味が小さい基本技術については、不要な比較を行わず採用方針のみ記録する。

また、Libraryの具体的なPatch Versionは原則として技術選定ドキュメントでは固定しない。

実際のVersionは `package.json`、Lockfile、Dockerfileなどのリポジトリ内の設定をSource of Truthとして管理する。

---

## 16. 決定事項

Frontendの技術・Library選定では以下を基本方針とする。

1. Next.js / React標準機能を優先する
2. TypeScriptを前提とする
3. OpenAPIをAPI契約のSource of Truthとする
4. Server Firstを基本とする
5. 状態の種類ごとに管理方法を分ける
6. Libraryの責務を重複させない
7. Headless / ComposableなLibraryを優先する
8. 型安全性を重視する
9. Libraryを増やしすぎない
10. MVPと将来拡張を分ける
11. Architectureと技術選定を分離する

Libraryを導入すること自体を目的とせず、ArchitectureおよびApplicationの要件を実現するために必要な技術を選定する。
