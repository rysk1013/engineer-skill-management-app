# テスト

## 1. 目的

本ドキュメントでは、FrontendにおけるTest Strategyおよび各Test Toolの使い分けを定義する。

対象：

- Unit Test
- Component Test
- Integration Test
- E2E Test
- Storybook
- API Mock
- Test Data
- Accessibility Test
- Error / Boundary Test
- Coverage
- CI

横断的なTest Tool選定については `08_テストツール.md`、
Frontend Architecture上のTest方針についてはFrontend ArchitectureのTest Strategy、
UI開発については `11_UI開発.md` に従う。

---

# 2. 基本方針

Frontend Testでは、

> Implementation DetailではなくUserから観測できるBehaviorを検証する

ことを基本とする。

例えば、

避ける：

    useStateの内部値を直接確認する
    Private Functionを直接Testする
    Component内部構造へ強く依存する

推奨：

    Userが入力する
        ↓
    Buttonを押す
        ↓
    Validationが表示される
        ↓
    Requestが送信される
        ↓
    Resultが表示される

Test Portfolio：

    Unit
      ↓
    Component
      ↓
    Integration
      ↓
    E2E

下位Testほど多く、
上位TestほどCritical Flowへ限定する。

---

# 3. Test Portfolio

基本構成：

    Pure Logic
        → Vitest

    UI Behavior
        → Vitest
        + React Testing Library
        + user-event

    HTTP Boundary
        → MSW

    UI State / Visual
        → Storybook

    Browser User Flow
        → Playwright

役割を重複させすぎない。

---

## 3.1 Testの優先順位

以下の順に優先する。

1. Business上重要なBehavior
2. Regression Riskが高い処理
3. Boundary Condition
4. User Interaction
5. Error / Recovery
6. Critical User Flow

単純な表示だけのComponentを
Coverage目的で大量にTestしない。

---

# 4. Unit Test

## 4.1 採用

Unit Test Runnerには
**Vitest** を利用する。

---

## 4.2 対象

Unit Testは主に、

- Pure Function
- Utility
- Formatter
- Parser
- Mapper
- Validation Logic
- State Transformation
- Date Calculation
- Query Parameter変換

を対象とする。

---

## 4.3 例

本Projectでは例えば、

- Experience Duration Format
- Year-Month Validation
- URL Parameter Parse
- API → View Model変換
- Form Values → API Request変換

などが対象になる。

---

## 4.4 Test対象にしないもの

単純なLanguage Featureまで
Testしない。

例えば、

    value ?? "-"

のような自明な処理だけのために
Testを追加しない。

---

# 5. Component Test

## 5.1 採用

Component Testには、

- Vitest
- React Testing Library
- `@testing-library/user-event`

を利用する。

---

## 5.2 基本方針

DOM Structureではなく
Userが認識できるUIを基準にTestする。

優先するQuery：

- Role
- Accessible Name
- Label
- Text

Implementation-specific Selectorを
Defaultにしない。

---

## 5.3 推奨

例えば、

    screen.getByRole("button", { name: "保存" })

のようなUser-facingなQueryを利用する。

---

## 5.4 避ける

可能な限り、

- Class Name
- Internal Component Name
- Internal State
- DOM Tree Depth
- Test専用ID

への依存を避ける。

`data-testid` は
他の適切なQueryがない場合のみ利用する。

---

# 6. Integration Test

## 6.1 基本方針

複数ComponentやLibraryが連携するBehaviorは
Integration Testとして検証する。

例：

    Form
      +
    React Hook Form
      +
    Zod
      +
    Mutation
      +
    MSW

---

## 6.2 対象

例えば、

- Form Submit
- Search / Filter
- Pagination
- Mutation Success
- Mutation Error
- Server Validation Mapping
- Query Refetch
- Dialog Interaction

などを検証する。

---

## 6.3 Mock

Integration Testでは
Implementation Functionを細かくMockするより、
HTTP BoundaryをMSWでMockすることを優先する。

---

# 7. E2E Test

## 7.1 採用

E2E Testには
**Playwright** を採用する。

---

## 7.2 目的

E2Eでは実際のBrowserを利用し、

    Browser
       ↓
    Next.js
       ↓
    BFF
       ↓
    Laravel
       ↓
    Database

を通したCritical User Flowを検証する。

---

## 7.3 対象

MVPでは例えば以下を優先する。

- Login
- Employee一覧
- Employee登録
- Employee編集
- Skill登録
- Employee Skill登録
- Skill Level変更
- Practical Experience登録
- Permission別Access
- Unauthorized Access
- Important Validation
- Important Error Flow

---

## 7.4 E2Eを増やしすぎない

すべての入力Patternを
E2Eで網羅しない。

例えばSkill Level Validationの細かなBoundaryは、
Unit / Component Testで検証する。

E2Eでは代表的なCritical Scenarioへ限定する。

---

## 7.5 Stable Selector

Playwrightでも、

- Role
- Label
- Accessible Name

を優先する。

Test専用Selectorは
必要な場合のみ利用する。

---

# 8. Storybookとの役割分担

## 8.1 Storybook

Storybookは、

- UI Development
- UI State
- Visual確認
- Interaction確認
- Accessibility確認

を主に担当する。

---

## 8.2 Component Test

Component Testは、

- Behavior
- User Interaction
- State Transition
- Validation
- Error Handling

を担当する。

---

## 8.3 E2E

E2Eは、

- Real Routing
- Authentication
- Authorization
- BFF
- Backend
- Database
- Full User Flow

を担当する。

---

## 8.4 重複を許容する場合

Critical Behaviorについては
複数LevelでTestしてよい。

ただし同じDetailを
すべてのTest Levelで完全に重複させない。

---

# 9. Mock方針

## 9.1 基本方針

Mockは最小限にする。

Implementation Detailを
Mockだらけにしない。

---

## 9.2 優先順位

基本：

    Pure Function
        → Mockなし

    UI + API
        → MSW

    Browser E2E
        → 原則Real System

---

## 9.3 vi.mock

`vi.mock()` は、

- Browser API
- Time
- Randomness
- External SDK
- Test困難なBoundary

などに限定する。

Application内部Moduleを
大量にMockしない。

---

## 9.4 Mockしすぎる問題

Mockを増やしすぎると、

- Real Integrationとの差が広がる
- Refactorに弱くなる
- Testだけ成功する
- False Confidenceが増える

ため避ける。

---

# 10. API Mock

## 10.1 採用

HTTP API Mockには
**MSW** を採用する。

---

## 10.2 基本方針

`fetch` やOrval Generated Functionそのものを
Mockするのではなく、
Network BoundaryをMockする。

構成：

    Component
       ↓
    Generated API Client
       ↓
    fetch
       ↓
    MSW

---

## 10.3 利点

これにより、

- Generated Client
- Request Parameter
- Error Handling
- Serialization
- HTTP Status

を含んだ形でTestできる。

---

## 10.4 Handler

HandlerはFeature / Resource単位で整理する。

巨大なGlobal Handler Fileへ
すべて詰め込まない。

---

## 10.5 Error Scenario

MSWでは、

- 200
- 401
- 403
- 404
- 409
- 422
- 429
- 500
- Network Error

等の重要Scenarioを再現できるようにする。

---

# 11. Server Component / Client ComponentのTest

## 11.1 基本方針

Server ComponentとClient Componentで
Test Strategyを分ける。

---

## 11.2 Client Component

Client Componentは
React Testing LibraryでBehavior Testする。

---

## 11.3 Server Component

Server Componentは、
単純なData Fetch Wrapperまで
無理にComponent Testしない。

以下へ責務を分ける。

    Data Transformation
        → Unit Test

    Interactive UI
        → Component Test

    RouteとしてのIntegration
        → E2E

---

## 11.4 Server Component Testの過剰化防止

Next.js内部挙動まで
Unit Testで再現しない。

Framework Integrationは
必要に応じてE2Eで確認する。

---

# 12. Form Test

## 12.1 基本方針

FormではUser Behaviorを中心に検証する。

---

## 12.2 対象

主に、

- Required
- Invalid Value
- Conditional Field
- Submit
- Server Validation
- Pending
- Error
- Success

をTestする。

---

## 12.3 Domain Rule

例えばEmployeeSkillでは、

未経験：

    Skill Level = Level 1

経験あり：

    Experience >= 1 month
    Last Used Year-Month required

などの重要RuleをFrontend Testでも確認する。

ただしDomain Invariantの最終Testは
Backend側でも行う。

---

## 12.4 422 Error

Backend 422 ResponseをMSWで再現し、

    Response
       ↓
    setError()
       ↓
    Field Error

まで確認する。

---

# 13. TanStack Query Test

## 13.1 基本方針

TanStack Query内部をTestしない。

Applicationが期待するBehaviorをTestする。

---

## 13.2 対象

例えば、

- Initial Fetch
- Loading
- Success
- Error
- Mutation
- Invalidation後の再取得
- Background Refetch

など。

---

## 13.3 QueryClient

各Testで独立した
Test用QueryClientを利用する。

Test間でCacheを共有しない。

---

## 13.4 Retry

Testでは不要なRetryによる遅延を避けるため、
Test用設定でRetryを無効化または最小化できる。

Production設定と混同しない。

---

# 14. Table・一覧UI Test

## 14.1 基本方針

TanStack Table内部Logicではなく
一覧画面としてのBehaviorをTestする。

---

## 14.2 対象

例えば、

- Row表示
- Pagination
- Sort操作
- Filter
- Search
- Empty
- No Results
- Error
- Row Action

など。

---

## 14.3 Server-side一覧

Server-side Pagination / Sort / Filterでは、
User操作後に期待するAPI Requestが発生し、
Response結果が表示されることを確認する。

---

## 14.4 URL State

重要な一覧では、

- Search Params反映
- Reload相当の復元
- Sort / Page変更

などをTest対象にできる。

---

# 15. Accessibility Test

## 15.1 基本方針

Accessibilityは、

- Automated Test
- Component Test
- Storybook
- Manual Check

を組み合わせる。

---

## 15.2 対象

特に、

- Form
- Dialog
- Alert
- Toast
- Table
- Navigation
- Error Message

を重点的に確認する。

---

## 15.3 Automated Test

Automated Checkだけで
Accessibility Complianceを保証しない。

Keyboard NavigationやFocus Flowは
Manual Testも行う。

---

# 16. Error・Boundary Test

## 16.1 基本方針

Happy Pathだけでなく
重要なError ScenarioをTestする。

---

## 16.2 対象

例えば、

    401
    403
    404
    409
    422
    429
    500
    Network Error

を対象とする。

---

## 16.3 Error Boundary

Unexpected Render Errorについては、
必要に応じてBoundary UIが表示されることを確認する。

---

## 16.4 Recovery

Error表示だけでなく、

- Retry
- Back
- Re-submit
- Login Redirect

等のRecoveryも重要な場合はTestする。

---

# 17. Test Data / Factory

## 17.1 基本方針

Test Dataは、

- Explicit
- Small
- Deterministic
- Readable

を基本とする。

---

## 17.2 Factory

重複が増えた場合のみFactoryを導入する。

例えば、

    createEmployee()
    createSkill()
    createEmployeeSkill()

など。

---

## 17.3 Override

FactoryはDefault値を持ちつつ、
必要なFieldだけOverrideできる構成が扱いやすい。

---

## 17.4 Random Data

Random Generatorを
Defaultにしない。

Failureを再現しづらくなるためである。

Randomnessが必要なTestでは
Seedを固定する。

---

## 17.5 Production Data

Production DataをFixtureとして利用しない。

---

# 18. Coverage

## 18.1 基本方針

Coverage Percentageを
Qualityそのものとして扱わない。

---

## 18.2 Coverageの目的

Coverageは、

> 重要なLogicがまったくTestされていない箇所を発見するための補助指標

として利用する。

---

## 18.3 100% Coverage

100% Coverageを目標にしない。

Coverage達成のためだけの
価値の低いTestを増やさない。

---

## 18.4 優先

重要なのは、

- Core Logic
- Business Rule
- Boundary
- Error Flow
- Critical User Flow

がTestされていることである。

---

## 18.5 Threshold

Coverage Thresholdを導入する場合は、
Project実績を確認してから設定する。

初期段階で高すぎるGlobal Thresholdを設定しない。

---

# 19. CI

## 19.1 基本方針

Frontend TestはCIで自動実行する。

---

## 19.2 基本Flow

概念：

    Install
      ↓
    Lint
      ↓
    Type Check
      ↓
    Unit / Component Test
      ↓
    Storybook Build
      ↓
    E2E

---

## 19.3 Fast Feedback

Unit / Component Testは
比較的早い段階で実行する。

E2EはCostが高いため
Job分離してよい。

---

## 19.4 Pull Request

Pull Requestでは最低限、

- Lint
- Type Check
- Unit / Component Test
- Storybook Build

を実行する。

E2Eについては
Critical FlowをPR時に実行する構成を推奨する。

---

## 19.5 Failure

Flaky Testを
「たまに失敗するもの」として放置しない。

原因を修正するか、
一時的に隔離してIssue化する。

---

# 20. 採用技術一覧

| 分類 | 採用技術 / 方針 |
|---|---|
| Test Runner | Vitest |
| Component Test | React Testing Library |
| User Interaction | `@testing-library/user-event` |
| HTTP Mock | MSW |
| UI Development / State | Storybook |
| E2E | Playwright |
| Unit対象 | Pure Function / Utility / Transformation |
| Component対象 | User-visible Behavior |
| Integration対象 | Form / Query / API Interaction |
| E2E対象 | Critical User Flow |
| Mock基本方針 | HTTP Boundary優先 |
| Test Data | Explicit / Deterministic |
| Factory | 必要になってから導入 |
| Coverage | 補助指標 |
| CI | Unit / Component / Storybook / E2E |

---

## 20.1 非推奨

| 方針 | 理由 |
|---|---|
| Implementation Detail Test | Refactorに弱い |
| Internal State直接Test | User Behaviorを保証しない |
| DOM Structureへの強い依存 | UI Refactorで壊れやすい |
| `data-testid` の乱用 | Accessible Queryを優先 |
| Application Moduleの大量Mock | Real Behaviorとの差が大きくなる |
| `fetch`の直接MockをDefault | HTTP BoundaryをMSWでMockする |
| E2Eですべて網羅 | Cost / Flaky Riskが高い |
| StorybookだけでBehavior保証 | Test責務が異なる |
| Random FixtureをDefault | Reproducibilityが低い |
| Production Data Fixture | Security / Privacy上不適切 |
| 100% Coverage目標 | Test価値を歪める |
| Flaky Test放置 | CI Reliabilityを下げる |

---

# 21. 決定事項

Frontend Test Stackとして、

- Vitest
- React Testing Library
- `@testing-library/user-event`
- MSW
- Storybook
- Playwright

を採用する。

基本：

    Logic
      → Vitest

    UI Behavior
      → React Testing Library

    HTTP Boundary
      → MSW

    UI State
      → Storybook

    Full User Flow
      → Playwright

以下をProject標準方針とする。

1. Frontend TestではImplementation DetailよりUser-visible Behaviorを優先する。
2. Unit Test RunnerにはVitestを利用する。
3. Component TestにはReact Testing Libraryを利用する。
4. User Interactionには `@testing-library/user-event` を利用する。
5. HTTP MockにはMSWを利用する。
6. E2EにはPlaywrightを利用する。
7. StorybookはUI State / Visual / Accessibility確認を担当する。
8. Unit TestはPure Logic / Utility / Transformationを中心とする。
9. Component TestはUserが認識・操作できるBehaviorを検証する。
10. Role / Label / Accessible NameによるQueryを優先する。
11. `data-testid` をDefault Selectorにしない。
12. Integration Testでは複数Library間の連携Behaviorを検証する。
13. HTTP BoundaryのMockをApplication内部Module Mockより優先する。
14. `fetch` やOrval Generated Functionを直接Mockする方式をDefaultとしない。
15. MSWで重要なHTTP Status / Error Scenarioを再現する。
16. Server Componentを無理に細かくUnit Testしない。
17. Server ComponentのData TransformationはPure Logicへ分離してTestできるようにする。
18. Framework Integrationは必要に応じてE2Eで確認する。
19. Form TestではUser入力・Validation・Submit・Server Errorを確認する。
20. EmployeeSkillの重要なFrontend RuleもTestする。
21. Backend Domain Invariantの最終保証はBackend Testで行う。
22. TanStack Query内部実装をTestしない。
23. Query / MutationのApplication BehaviorをTestする。
24. Testごとに独立したQueryClientを利用する。
25. Table TestではTanStack Table内部ではなく一覧Behaviorを検証する。
26. Server-side Pagination / Sort / FilterではRequestと表示結果を確認する。
27. CriticalなURL State Behaviorを必要に応じてTestする。
28. AccessibilityはAutomated Testだけに依存しない。
29. 401 / 403 / 404 / 409 / 422 / 429 / 5xx等の重要Error FlowをTestする。
30. Error表示だけでなく重要なRecovery FlowもTestする。
31. E2EはCritical User Flowへ限定する。
32. 細かなBoundary PatternをすべてE2Eへ持ち込まない。
33. Test DataはSmall / Explicit / Deterministicを基本とする。
34. Test Factoryは重複が実際に増えてから導入する。
35. Random Test DataをDefaultにしない。
36. Production DataをFixtureとして利用しない。
37. CoverageをQualityそのものとして扱わない。
38. 100% Coverageを目標にしない。
39. Coverage ThresholdはProject実績を確認してから設定する。
40. CIでUnit / Component Testを自動実行する。
41. CIでStorybook Buildを確認する。
42. Critical E2E FlowをCIで実行する。
43. Fast Feedbackを得るため軽量Testを先に実行する。
44. Flaky Testを放置しない。
45. Test Level間で同じDetailを過剰に重複検証しない。
46. Business Riskに応じてTest LevelとTest量を決定する。

以上を `Frontend/12_テスト.md` の決定版とする。
