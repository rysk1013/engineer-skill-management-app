# UI開発

## 1. 目的

本ドキュメントでは、FrontendにおけるUI Component開発・確認環境の技術選定および運用方針を定義する。

対象：

- Storybook
- Component Story
- Mock Data
- UI State
- shadcn/ui Component
- Design Token
- Design System
- Visual Regression
- Accessibility Check
- Application Testとの責務分担
- Directory / Naming
- CI

UI ComponentのArchitectureについてはFrontend Architecture、
UI / Stylingについては `03_UI・Styling.md`、
Feedback UIについては `10_Feedback・Error-UI.md`、
Test全体については `12_テスト.md` に従う。

---

# 2. 基本方針

UI Componentの独立した開発・確認環境として
**Storybook** を採用する。

基本構成：

    Application
        ↓
    Page / Feature
        ↓
    Component
        ↑
    Storybook

役割：

    Application
        → Routing
        → Real Data Flow
        → Authentication
        → Server State
        → User Flow

    Storybook
        → Component単体確認
        → UI State確認
        → Mock Data
        → Accessibility確認
        → Visual確認
        → Component Documentation

StorybookをApplicationそのものの代替にはしない。

---

# 3. Storybook

## 3.1 採用

UI Component開発環境として
**Storybook** を採用する。

Next.js / React / TypeScript構成へ統合する。

---

## 3.2 採用理由

主な理由：

- Applicationから独立してComponentを確認できる
- UI Stateを再現できる
- Mock Dataを利用できる
- Componentの仕様を視覚的に確認できる
- Accessibility確認と組み合わせやすい
- Regression Testへ発展させやすい
- Team内でUI仕様を共有しやすい
- Loading / Empty / Error等を再現しやすい

---

## 3.3 Storybookの位置付け

StorybookはMVPでは、

**UI Development Environment**

として利用する。

最初から完全なDesign System Platformとして運用しない。

---

# 4. Component Storyの対象

## 4.1 基本方針

すべてのComponentへ
Story作成を義務付けない。

Storyを作る価値が高いComponentを選択する。

---

## 4.2 Story作成を推奨するComponent

以下を優先する。

### Shared UI

例：

- Button Wrapper
- Form Field
- Badge
- Status
- Empty State
- Error State
- Loading State
- Pagination
- DataTable関連Component

### 複数Stateを持つComponent

例えば：

    Default
    Loading
    Disabled
    Error
    Empty
    Selected

などを持つComponent。

### InteractionがあるComponent

例：

- Dialog
- Alert Dialog
- Dropdown
- Combobox
- Select
- Pagination
- Table Action

### Business UI

複雑なBusiness Stateを表示するComponent。

例：

- Skill Level表示
- Employee Skill表示
- Permission状態表示
- Experience表示

---

## 4.3 Story不要なComponent

以下は機械的にStoryを作らない。

- 単純なLayout Wrapper
- 1画面だけで利用する薄いWrapper
- Server ComponentでData取得だけを担当するComponent
- UIをほとんど持たないContainer
- Storyを作っても仕様理解に寄与しないComponent

---

## 4.4 判断基準

Storyを作るか迷った場合は、

> このComponentをApplicationから切り離して状態確認できることに価値があるか？

で判断する。

---

# 5. Mock Data

## 5.1 基本方針

Storybookでは
Production Backendへ依存しない。

Storyを表示するために
Laravel APIやStaging APIへ接続しない。

---

## 5.2 Component Props

Propsだけで表現できるComponentでは
単純なMock Objectを利用する。

例：

    Employee
    Skill
    EmployeeSkill

などのTest Dataを用意する。

---

## 5.3 Mock Dataの原則

Mock Dataは、

- Small
- Explicit
- Deterministic
- Readable

を基本とする。

Random DataをDefaultにしない。

---

## 5.4 Generated Type

OpenAPI / Orval Generated Typeを
Mock Dataの型として利用できる。

これによりAPI Contract変更を
TypeScript Compilerで検知できる。

---

## 5.5 Factory

複数Story / Testで同じData生成が必要になった場合は
Factoryを導入できる。

概念：

    createEmployee()
    createSkill()
    createEmployeeSkill()

ただしMVP開始時点から
巨大なFixture Frameworkを構築しない。

---

## 5.6 Sensitive Data

Production Dataを
Storybook Fixtureへコピーしない。

Mock Dataには
架空のDataのみ利用する。

---

# 6. UI StateのStory化

## 6.1 基本方針

StorybookではComponentそのものだけでなく
**重要なUI State** を明示的にStory化する。

---

## 6.2 基本State

必要に応じて以下を用意する。

    Default
    Loading
    Empty
    Error
    Disabled

---

## 6.3 Feature固有State

Featureによっては、

    Experienced
    Inexperienced

    Active
    Inactive

    Allowed
    Forbidden

などをStoryとして表現する。

---

## 6.4 Boundary State

UI崩れが起きやすいBoundaryも
必要に応じてStory化する。

例：

- Long Text
- Long Skill Name
- 0件
- Maximum Value
- Missing Optional Value
- Many Tags

---

## 6.5 State Matrixの過剰化

すべてのState Combinationを
Story化しない。

重要なRepresentative Stateを選択する。

組み合わせ爆発を避ける。

---

# 7. shadcn/ui Componentの扱い

## 7.1 基本方針

shadcn/uiから追加した
すべてのPrimitive Componentへ
Storyを作る必要はない。

---

## 7.2 Storyを作る場合

Application側で、

- Stylingを大きく変更した
- Behaviorを追加した
- Wrapper Componentを作成した
- Design Ruleを追加した

場合はStory作成を検討する。

---

## 7.3 Source Ownership

shadcn/ui Componentは
Application Sourceとして管理する。

必要なComponentだけ追加する。

Storybook専用に
不要なshadcn/ui Componentを導入しない。

---

## 7.4 Base UI

Base UI Primitiveを直接利用した
Application固有Componentについても、
UI State確認に価値がある場合はStoryを作成する。

---

# 8. Design Tokenとの連携

## 8.1 基本方針

StorybookでもApplicationと同じ
Design Tokenを利用する。

別のTheme / CSS Variableを
Storybook専用に定義しない。

---

## 8.2 Token

`03_UI・Styling.md` で定義した、

- background
- foreground
- primary
- secondary
- muted
- accent
- destructive
- border
- input
- ring

等のSemantic Tokenを共有する。

---

## 8.3 Global CSS

ApplicationとStorybookで
同じGlobal CSS / Tailwind CSS設定を利用する。

Storybookだけ見た目が異なる状態を避ける。

---

# 9. Design System化の範囲

## 9.1 MVP

MVPでは独立した
Design System Projectを構築しない。

Application Repository内で、

    Design Token
        +
    Shared UI
        +
    Storybook

を管理する。

---

## 9.2 Shared UI

複数Featureで実際に再利用されるUIのみ
Shared Componentへ昇格させる。

最初から将来の再利用を予測して
大量のGeneric Componentを作らない。

---

## 9.3 Design Systemへの発展

以下の状況になった場合は
Design System化を再検討する。

- 複数Frontend Application
- Component数の大幅増加
- Designer / Frontend Teamの拡大
- Brand Ruleの複雑化
- Independent Releaseが必要
- Component Packageとして配布する必要

---

## 9.4 Package分離

MVPではShared UIを
独立npm Packageへ分離しない。

Monorepo内で実際に複数Applicationから
共有する必要が生じた場合に再評価する。

---

# 10. Visual Regression Test

## 10.1 基本方針

Visual Regression Testは
将来的な導入候補とする。

MVP開始時点では必須としない。

---

## 10.2 導入候補

以下が増えた場合に導入を検討する。

- Shared Component
- Complex Table
- Complex Form
- Responsive UI
- Design Token変更
- Regression Riskの高いComponent

---

## 10.3 Test対象

Visual Regressionを導入した場合も
すべてのStoryをScreenshot Test対象にしない。

重要なUIへ限定する。

---

## 10.4 External Service

Visual Regression SaaS等は
必要になった段階で比較・選定する。

MVPでは特定Serviceへ依存しない。

---

# 11. Accessibility Check

## 11.1 基本方針

Storybookを
Accessibility確認にも利用する。

---

## 11.2 Automated Check

StorybookのAccessibility Addon等を利用して
自動Checkを実施できる構成とする。

主な対象：

- Accessible Name
- ARIA
- Contrast
- Form Label
- Semantic Structure

---

## 11.3 Manual Check

Automated Checkだけで
Accessibilityを保証しない。

必要に応じて、

- Keyboard Navigation
- Focus
- Dialog
- Screen Reader Flow

を手動確認する。

---

## 11.4 Error UI

特に、

- Validation Error
- Alert
- Dialog
- Toast
- Loading
- Table

はAccessibility確認を重視する。

---

# 12. StorybookとApplication Testの責務分担

## 12.1 Storybook

Storybookは主に、

- Component Development
- Visual Confirmation
- UI State
- Interaction確認
- Accessibility確認
- Documentation

を担当する。

---

## 12.2 Unit / Component Test

Test Frameworkでは、

- Utility
- Business UI Logic
- Component Behavior
- State Transition

を検証する。

---

## 12.3 E2E

E2E Testでは、

    Login
      ↓
    Page
      ↓
    User Operation
      ↓
    BFF
      ↓
    Laravel
      ↓
    Result

というApplication全体のUser Flowを検証する。

---

## 12.4 Storybookで検証しないもの

Storybookだけで、

- Authentication
- Authorization全体
- Routing
- Real API Integration
- Database
- Full User Flow

を保証しない。

---

# 13. Directory・Naming

## 13.1 Story配置

Storyは対象Componentの近くへ配置する
**Colocation** を基本とする。

概念：

    employee-status/
      employee-status.tsx
      employee-status.stories.tsx
      employee-status.test.tsx

---

## 13.2 理由

ComponentとStoryを近くに配置することで、

- Component変更時にStoryを発見しやすい
- Ownershipが明確
- Feature削除時に一緒に削除できる
- Directory Navigationが分かりやすい

という利点がある。

---

## 13.3 Story Naming

Story Nameは
UI Stateを表す名前とする。

例：

    Default
    Loading
    Empty
    Error
    Disabled
    LongName

`Story1` や `Test` のような
意味のない名前を利用しない。

---

## 13.4 Category

Storybook上のCategoryは
ApplicationのComponent構造に合わせる。

例えば：

    UI/Button
    UI/Alert
    Employee/EmployeeStatus
    Skill/SkillLevel
    Table/Pagination

過度に深いCategory Treeを作らない。

---

# 14. CIでの扱い

## 14.1 Storybook Build

CIでStorybook Buildが
成功することを確認する。

これにより、

- Import Error
- Type Error
- Configuration Error
- Story Definition Error

等を検知する。

---

## 14.2 基本Flow

概念：

    Install
       ↓
    Lint
       ↓
    Type Check
       ↓
    Test
       ↓
    Storybook Build

実際のCI Job分割は
CI / CD設計で決定する。

---

## 14.3 Storybook Deploy

MVPではStorybookの
常時Public Deployを必須としない。

必要になった場合は、

- Internal Hosting
- Preview Environment
- Visual Regression Service

等を検討する。

---

## 14.4 Security

StorybookをDeployする場合は
内部情報の露出に注意する。

含めない：

- Production Credential
- API Token
- Session
- Production Data
- Sensitive Environment Variable

---

# 15. 採用技術一覧

| 分類 | 採用技術 / 方針 |
|---|---|
| UI Development Environment | Storybook |
| Framework | React / Next.js Integration |
| Language | TypeScript |
| UI | shadcn/ui |
| Primitive | Base UI |
| Styling | Tailwind CSS v4 |
| Theme | CSS Variables / Semantic Token |
| Story Data | Explicit Mock Data |
| Mock Type | OpenAPI / Orval Generated Type利用可 |
| Story配置 | Component Colocation |
| UI State | Representative StateをStory化 |
| Accessibility | Storybook Accessibility Check + Manual |
| Visual Regression | 将来導入候補 |
| Storybook Build | CIで検証 |
| Design System | MVPでは独立System化しない |

---

## 15.1 MVPで採用しないもの

| 技術 / 方針 | 理由 |
|---|---|
| 全ComponentのStory必須化 | Maintenance Costが高い |
| 独立Design System Repository | MVPでは過剰 |
| Shared UIのnpm Package化 | 現時点で必要ない |
| Storybook専用Design Token | Applicationとの乖離を生む |
| Production API接続 | StoryがExternal Environmentへ依存する |
| Production Data Fixture | Security / Privacy上不適切 |
| Random MockをDefault利用 | Storyの再現性が下がる |
| 全State CombinationのStory化 | Combination Explosion |
| 全StoryのVisual Regression | Costに対して効果が低い |
| Visual Regression SaaSの初期導入 | 必要性を確認してから選定 |
| StorybookによるE2E代替 | 責務が異なる |
| 巨大Fixture Framework | MVPでは過剰 |

---

# 16. 決定事項

UI Component開発・確認環境として
**Storybook** を採用する。

基本構成：

    Application
        │
        ├── Page / Feature
        │
        └── Component
                 ↑
                 │
             Storybook
                 │
                 ├── UI State
                 ├── Mock Data
                 ├── Interaction
                 ├── Accessibility
                 └── Visual Confirmation

以下をProject標準方針とする。

1. UI開発環境としてStorybookを採用する。
2. StorybookをApplicationから独立したComponent確認環境として利用する。
3. StorybookをApplication Testの代替にしない。
4. MVPではStorybookをUI Development Environmentとして位置付ける。
5. 最初から完全なDesign System Platformとして運用しない。
6. すべてのComponentへStory作成を義務付けない。
7. Shared UIはStory作成を優先する。
8. 複数Stateを持つComponentはStory作成を優先する。
9. Interactionを持つComponentはStory作成を検討する。
10. Business上重要なUI ComponentはStory作成を検討する。
11. 単純なWrapperには機械的にStoryを作らない。
12. StorybookからProduction / Staging Backendへ依存しない。
13. Propsで表現できる場合はExplicit Mock Dataを利用する。
14. Mock DataはDeterministicにする。
15. Production DataをFixtureとして利用しない。
16. OpenAPI / Orval Generated TypeをMock型として利用できる。
17. Factoryは実際に再利用性が出てから導入する。
18. Default / Loading / Empty / Error等の重要StateをStory化する。
19. Feature固有の重要StateもStory化できる。
20. Long Text等のUI Boundaryを必要に応じてStory化する。
21. 全State CombinationをStory化しない。
22. shadcn/ui PrimitiveすべてにStoryを作らない。
23. Application固有Wrapper / CustomizationにStoryを優先する。
24. StorybookとApplicationで同じTailwind / CSS / Design Tokenを利用する。
25. Storybook専用Themeを作らない。
26. MVPでは独立Design Systemを構築しない。
27. Shared UIは実際の再利用を確認してから共通化する。
28. MVPではShared UIを独立npm Packageへ分離しない。
29. Visual Regression Testは将来導入候補とする。
30. Visual Regression導入時も重要Componentへ対象を限定する。
31. StorybookをAccessibility確認に利用する。
32. Automated Accessibility CheckだけでAccessibilityを保証しない。
33. Keyboard / Focus等は必要に応じてManual Checkする。
34. StorybookはUI State / Visual / Interaction / Accessibilityを主に担当する。
35. Unit / Component TestはBehavior / Logicを主に担当する。
36. E2EはApplication全体のUser Flowを担当する。
37. Storyは対象Componentの近くへColocationする。
38. Story NameはUI Stateを表す意味のある名前にする。
39. Storybook Categoryを過度に複雑化しない。
40. CIでStorybook Buildを検証する。
41. Storybookの常時DeployをMVP要件としない。
42. StorybookをDeployする場合もCredential / Production Dataを含めない。

以上を `Frontend/11_UI開発.md` の決定版とする。
