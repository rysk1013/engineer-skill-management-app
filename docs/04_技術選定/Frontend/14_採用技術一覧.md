# 採用技術一覧

## 1. 目的

本ドキュメントでは、
Engineer Skill Management AppのFrontend / BFFで採用する技術を一覧化する。

本ドキュメントはTechnology StackのIndexとして利用し、
各技術の詳細な選定理由・設計・運用方針は個別ドキュメントへ委譲する。

目的：

- 採用技術を一か所で確認する
- 各技術の責務を明確にする
- 責務の重複を防ぐ
- 新規Dependency導入時の判断基準とする
- ArchitectureとTechnology Selectionを対応付ける
- Project Onboardingを容易にする

---

# 2. Frontend / BFF 全体構成

FrontendとBFFは
同一Next.js Applicationとして構成する。

基本：

    Browser
       ↓
    Next.js
    Frontend + BFF
       ↓
    Laravel API
       ↓
    PostgreSQL

BrowserからLaravel APIへ
直接Accessしない。

Next.jsからBusiness Databaseへ
直接Accessしない。

責務：

    Browser
        → UI
        → User Interaction

    Next.js
        → Frontend
        → BFF
        → Authentication Session
        → Backend API Client

    Laravel
        → Application Use Case
        → Domain
        → Authorization
        → Business Rule

    PostgreSQL
        → Persistent Data

# 8. 状態管理

Stateの種類ごとに
利用技術を分離する。

| State | 採用技術 |
|---|---|
| Server State | TanStack Query |
| URL State | Next.js URL / Search Params |
| Form State | React Hook Form |
| Local UI State | `useState` / `useReducer` |
| Shared UI State | React Context |
| Global Client State | MVPでは専用Libraryなし |

基本：

> どのState Management Libraryを使うかではなく、
> まずStateの種類を判断する。

Server StateをZustandやContextへ
コピーしない。

巨大なGlobal Storeを作らない。

# 15. Package Management

Package Managerとして
**pnpm** を利用する。

基本：

- `pnpm-lock.yaml` をCommitする
- `packageManager` でpnpm Versionを固定する
- CIではFrozen Lockfileを利用する
- Workspace / Monorepo機能を利用できる構成にする

標準Commandは
`package.json` Scriptとして提供する。

代表例：

    pnpm dev
    pnpm build
    pnpm lint
    pnpm format
    pnpm format:check
    pnpm typecheck
    pnpm test
    pnpm test:e2e
    pnpm storybook
    pnpm storybook:build
    pnpm knip
    pnpm api:generate

必要に応じて、

    pnpm check

のような統合Quality Check Commandを用意する。

Project全体として、

> Standard機能を優先し、Libraryの責務を重複させず、
> 必要なTechnologyだけを明確な責務を持って導入する

ことをFrontend Technology Selectionの基本原則とする。

また、

> Architectureは「どう設計するか」、
> Technology Selectionは「何を使うか」

を扱うものとして両者を分離する。

新しいLibraryを導入する場合は、

1. 解決するRequirementが存在するか
2. Platform / Framework標準機能で解決できないか
3. 既存Libraryと責務が重複しないか
4. TypeScriptとのIntegrationは十分か
5. Maintenance状況に問題がないか
6. Bundle / Performanceへの影響は許容できるか
7. Test可能か
8. Security Riskは許容できるか
9. Lock-in / Migration Costは許容できるか
10. MVPで本当に必要か

を確認する。
