# 状態管理

## 1. 目的

本ドキュメントでは、FrontendにおけるStateの分類、管理方法、および利用する技術を定義する。

対象：

- Server State
- URL State
- Form State
- Local UI State
- Shared UI State
- Global Client State
- Derived State
- State Ownership
- State Persistence

状態を1つのState Management Libraryへ集約するのではなく、Stateの性質ごとに適切な管理方法を選択する。

---

# 2. 基本方針

Frontend Stateは責務ごとに分類して管理する。

基本：

    State
    ├── Server State
    ├── URL State
    ├── Form State
    ├── Local UI State
    └── Global Client State

採用方針：

    Server State
        → TanStack Query

    URL State
        → URL / Next.js Search Params

    Form State
        → React Hook Form

    Local UI State
        → React useState / useReducer

    Shared UI State
        → React Context

    Global Client State
        → MVPでは専用Libraryを採用しない

State Management Libraryを先に導入してから用途を探すのではなく、必要になったStateに対して最小の仕組みを選択する。

---

# 3. State分類

## 3.1 Server State

Backendなど外部SourceがSource of TruthとなるData。

例：

- Employee一覧
- Employee詳細
- Skill一覧
- Skill Category
- Department
- User情報

特徴：

- Remote Data
- Async
- Cache可能
- Refetchが必要
- Staleになる可能性がある

TanStack Queryで管理する。

---

## 3.2 URL State

URLで表現できるApplication State。

例：

- Search Keyword
- Filter
- Sort
- Pagination
- Selected Tab
- Page

URL / Search Paramsで管理する。

---

## 3.3 Form State

User Inputを中心とした一時的なState。

例：

- Input Value
- Validation Error
- Dirty State
- Touched State
- Submit State

React Hook Formで管理する。

---

## 3.4 Local UI State

特定Componentや局所的なUIだけで利用するState。

例：

- Dialog Open / Close
- Dropdown Open / Close
- Accordion
- Local Toggle
- Hover以外の一時UI状態

React Stateで管理する。

---

## 3.5 Global Client State

複数Featureを跨いで共有され、
Server / URL / Formでは表現できないClient固有State。

MVPでは原則として発生させない。

本当に必要になった場合のみ専用State Libraryを検討する。

---

# 4. Server State

## 4.1 採用

Server Stateには **TanStack Query** を採用する。

Server StateをReact ContextやGlobal State Libraryへ複製しない。

避ける：

    API
     ↓
    TanStack Query
     ↓
    Zustand
     ↓
    Component

基本：

    API
     ↓
    TanStack Query
     ↓
    Component

---

## 4.2 Source of Truth

Backend APIを最終的なSource of Truthとする。

TanStack Query Cacheは一時的なClient-side Representationとして扱う。

---

## 4.3 Server Stateの複製

取得したServer Dataを、

    useState
    Context
    Global Store

へ理由なくコピーしない。

Copyすると、

- Synchronization
- Stale Data
- Dual Source of Truth

の問題が発生する。

---

## 4.4 Mutation

Server State変更はTanStack Query Mutationを通す。

基本：

    Mutation
       ↓
    Backend
       ↓
    invalidateQueries
       ↓
    Refetch

Optimistic Updateは必要な場合のみ利用する。

---

# 5. URL State

## 5.1 基本方針

URLで表現できるStateはURLへ配置する。

例：

    /employees?page=2&keyword=php&department=3

対象：

- Search
- Filter
- Sort
- Pagination
- Tab
- View Mode

---

## 5.2 採用技術

Next.js App Routerの、

- Search Params
- Path Params
- Navigation API

を利用する。

専用URL State LibraryはMVPでは採用しない。

---

## 5.3 URLを利用する理由

URL Stateには以下のメリットがある。

- ReloadしてもStateが維持される
- Bookmark可能
- Link共有可能
- Browser Back / Forwardに対応
- Server Componentから参照可能

---

## 5.4 URLに置かないState

以下は通常URLへ置かない。

- Password
- Authentication Token
- Sensitive Data
- Form入力途中の全Data
- 一時的なTooltip State
- Security-sensitive State

---

# 6. Form State

Form Stateには **React Hook Form** を利用する。

詳細は `06_Form・Validation.md` に従う。

    Form State
        ↓
    React Hook Form

Form DataをGlobal Stateへ保存しない。

Wizardなど複数画面に跨るFormが必要になった場合は別途設計する。

---

# 7. Local UI State

## 7.1 採用

Local UI StateにはReact標準機能を利用する。

主に：

- `useState`
- `useReducer`

を利用する。

---

## 7.2 useState

単純なStateでは `useState` を利用する。

例：

    const [open, setOpen] = useState(false)

対象：

- Modal
- Toggle
- Selected UI Item
- Temporary Local State

---

## 7.3 useReducer

State Transitionが複雑な場合のみ `useReducer` を利用する。

対象：

- 複数Stateが同時に変化
- 明確なAction / Transitionが存在
- State Machineに近い処理

単純なStateに `useReducer` を利用しない。

---

## 7.4 StateのLocality

Stateは可能な限り利用箇所の近くへ配置する。

避ける：

    App Root
       ↓
    State
       ↓
    5階層下のComponentだけが利用

可能なら、

    Feature
       ↓
    Component
       ↓
    Local State

とする。

---

# 8. Global Client State

## 8.1 MVP方針

MVPではGlobal Client State Libraryを採用しない。

以下を組み合わせることで大半のStateを管理する。

    Server State
        → TanStack Query

    URL State
        → URL

    Form State
        → React Hook Form

    Local State
        → React State

    Shared UI State
        → React Context

---

## 8.2 専用Library導入条件

以下の条件が実際に発生した場合のみ導入を検討する。

- 複数Featureで共有
- Client-only State
- URLに適さない
- Server Stateではない
- Contextでは管理が複雑
- Frequent Updateがある
- Deep Component Treeで広く参照される

---

## 8.3 候補

将来候補：

- Zustand

必要になった場合の第一候補とする。

---

## 8.4 Redux

Redux Toolkitは成熟した選択肢ではあるが、
本ProjectのMVPでは規模・要件に対して過剰と判断する。

採用しない。

---

## 8.5 Zustand

Zustandは軽量でGlobal Client State用途に適しているため、
将来的な第一候補とする。

ただし、

    「Zustandが便利だから入れる」

ではなく、

    「Global Client Stateが実際に必要になった」

場合に導入する。

---

# 9. React Context

## 9.1 基本方針

React ContextはState Management Libraryの代替として乱用しない。

主に、

- Dependency的な値
- UI-wide Configuration
- Limited Shared State

へ利用する。

---

## 9.2 利用候補

例：

- Theme Configuration
- Feature Scope Context
- Component Tree内の共有設定

---

## 9.3 避ける用途

以下をContextへ置かない。

- Server State
- Large Mutable State
- High-frequency State
- API Cache
- Form State

---

## 9.4 Context分割

巨大な、

    AppContext

を作らない。

Contextが必要な場合は責務単位で分割する。

---

# 10. Zustand等のGlobal State Library

## 10.1 MVP

MVPでは採用しない。

---

## 10.2 将来導入

Global Client Stateが明確になった場合は
Zustandを第一候補とする。

導入時にもStoreを巨大化させない。

避ける：

    useAppStore
      ├── user
      ├── employees
      ├── skills
      ├── dialogs
      ├── forms
      ├── cache
      └── everything

Feature / Responsibility単位で分離する。

---

## 10.3 Server Stateを入れない

将来Zustandを採用した場合も、
TanStack Query DataをZustandへコピーしない。

    Server State
        → TanStack Query

    Client Global State
        → Zustand

と責務を分ける。

---

# 11. Derived State

## 11.1 基本方針

他Stateから計算できる値を、
別Stateとして保持しない。

避ける：

    firstName
    lastName
    fullName

の3つすべてをStateで保持する。

基本：

    fullName =
        firstName + lastName

と計算する。

---

## 11.2 useMemo

Derived Valueを計算するためだけに
無条件で `useMemo` を利用しない。

計算CostやReferential Equalityが問題になる場合のみ利用する。

---

## 11.3 Server Data

Backend Dataから導出できるDisplay Valueも、
可能な限りRender時に計算する。

複製Stateを作らない。

---

# 12. State配置・Ownership

## 12.1 基本方針

StateはそのStateを所有する最も狭いScopeへ配置する。

原則：

    Local
      ↓
    Feature
      ↓
    Page
      ↓
    Global

の順で必要性を評価する。

最初からGlobalへ置かない。

---

## 12.2 Lift State Up

複数Sibling ComponentがStateを共有する場合は、
必要最小限のCommon ParentまでStateを引き上げる。

Application Rootまで引き上げない。

---

## 12.3 Server / Client Boundary

Server Componentで管理できるDataは
無理にClient State化しない。

Client Stateが必要なのは主に、

- Interaction
- Browser API
- Local UI
- Client-side Server State

が必要な場合とする。

---

## 12.4 Feature Ownership

Feature固有StateはFeature内部へ配置する。

別Featureから直接内部Stateを変更させない。

必要なら明示的なAPI / Component Boundaryを設ける。

---

# 13. Persistence

## 13.1 基本方針

Client Stateを安易にPersistent Storageへ保存しない。

まず以下を検討する。

    Server
    URL
    Cookie
    Session

Browser Storageは最後の選択肢の1つとする。

---

## 13.2 Local Storage

Local Storageは必要な場合のみ利用する。

利用候補：

- Non-sensitive UI Preference
- Temporary Client-only Preference

---

## 13.3 保存しないData

以下はLocal Storageへ保存しない。

- Authentication Token
- Laravel API Credential
- Sensitive User Data
- Permission情報のSource of Truth
- Server Data Cacheの恒久保存

Authentication詳細は認証設計に従う。

---

## 13.4 Session Storage

Tab単位の一時的なPersistenceが必要な場合のみ検討する。

Defaultでは利用しない。

---

## 13.5 Browser Storage Validation

Browser Storageから読み込む値は
外部入力として扱う。

    Storage
      ↓
    unknown
      ↓
    Runtime Validation
      ↓
    Application

型Assertionだけで信頼しない。

---

## 13.6 Versioning

Persistent Client Stateを導入する場合は、
Schema変更に備えてVersioning / Migrationを検討する。

MVPでは不要なPersistenceを作らないことを優先する。

---

# 14. 採用技術一覧

| State分類 | 採用技術 |
|---|---|
| Server State | TanStack Query |
| URL State | Next.js URL / Search Params |
| Form State | React Hook Form |
| Local UI State | React `useState` |
| Complex Local State | React `useReducer` |
| Shared UI State | React Context |
| Global Client State | MVPでは専用Libraryなし |
| 将来のGlobal State候補 | Zustand |
| Derived State | 通常のJavaScript / React計算 |
| Persistent State | Server / URLを優先 |
| Browser Storage | 必要な場合のみ |

---

## 14.1 不採用

| 技術 / 方針 | 理由 |
|---|---|
| Redux Toolkit | MVP要件に対して過剰 |
| Zustandの初期導入 | Global Client State要件がまだない |
| Jotai | 現時点で導入理由がない |
| MobX | 現時点で導入理由がない |
| Server StateをGlobal Storeへ複製 | Dual Source of Truthになる |
| Form StateをGlobal Store管理 | React Hook Formへ責務を分離 |
| Filter / PaginationをGlobal Store管理 | URL Stateを優先 |
| 巨大React Context | Re-render・責務肥大化を避ける |
| 巨大Global Store | State Ownershipが不明確になる |
| Local Storageへの認証情報保存 | Security上避ける |
| Derived Stateの重複保持 | Synchronization問題を避ける |

---

# 15. 決定事項

Frontend State Managementは、
1つのLibraryへ統一せずStateの性質ごとに分離する。

基本構成：

    Frontend State
    │
    ├── Server State
    │      ↓
    │   TanStack Query
    │
    ├── URL State
    │      ↓
    │   Next.js URL / Search Params
    │
    ├── Form State
    │      ↓
    │   React Hook Form
    │
    ├── Local UI State
    │      ↓
    │   useState / useReducer
    │
    └── Shared / Global Client State
           ↓
       React Context
           ↓
       必要になった場合のみZustand

以下をProject標準方針とする。

1. Server StateはTanStack Queryで管理する。
2. Server DataをGlobal Storeへ理由なく複製しない。
3. URLで表現可能なStateはURLへ配置する。
4. Search / Filter / Sort / Paginationは原則URL Stateとする。
5. Form StateはReact Hook Formで管理する。
6. Form StateをGlobal Storeへ保存しない。
7. Component固有Stateは `useState` を利用する。
8. 複雑なLocal State Transitionには必要に応じて `useReducer` を利用する。
9. Stateは利用箇所に最も近いScopeへ配置する。
10. 最初からGlobal Stateへ持ち上げない。
11. React Contextは限定されたShared State / Configuration用途に利用する。
12. 巨大なAppContextを作らない。
13. MVPではGlobal State Libraryを導入しない。
14. Global Client Stateが実際に必要になった場合のみ専用Libraryを導入する。
15. 将来のGlobal State Library第一候補はZustandとする。
16. Zustand導入後もServer StateはTanStack Queryで管理する。
17. Redux ToolkitはMVPでは採用しない。
18. Derived Stateを別Stateとして重複保持しない。
19. `useMemo` をState Management目的で乱用しない。
20. Server Componentで完結するDataを無理にClient State化しない。
21. Feature固有StateはFeature内部でOwnershipを持つ。
22. Persistenceが必要な場合はServer / URLを優先する。
23. Browser Storageは必要な場合のみ利用する。
24. Authentication Token / API CredentialをLocal Storageへ保存しない。
25. Browser Storageから取得するDataはUntrusted DataとしてValidationする。
26. Client Persistenceを将来導入する場合はSchema Versioningを検討する。
27. 「どのLibraryで管理するか」より先に「何のStateか」を判断する。

以上を `Frontend/07_状態管理.md` の決定版とする。
