# データベース

## 1. 比較対象

- [x] PostgreSQL
- [ ] MySQL

---

## 2. 今回のシステム要件

Database では主に以下の情報を管理する。

- 社員
- 所属部署
- 在籍状態
- スキルカテゴリ
- 技術・スキルマスタ
- 社員スキル
- 実務経験
- 経験期間
- スキルレベル
- 最終利用時期
- 利用者権限
- サブマネージャーと担当社員の関係
- チームリーダーと担当社員の関係
- Laravel Sanctum Token 関連データ

将来的には以下も扱う。

- 複数スキル検索
- スキルごとの社員検索
- 技術保有人数集計
- 権限に応じた社員絞り込み
- 資格管理

主要な Application Data は相互に強い Relation を持つため、Relational Database を採用する。

---

## 3. PostgreSQL

### メリット

- Laravel から利用できる
- Laravel Sanctum の Token Persistence に利用できる
- Relational Data の管理に適している
- JOIN を利用した複雑な検索に対応できる
- 集計処理を行いやすい
- Foreign Key や Unique Constraint などによるデータ整合性を保証しやすい
- Transaction を利用できる
- Row Lock による排他制御を利用できる
- 高度な SQL 機能を利用できる
- JSON / JSONB を利用できる
- JSONB に対して Index を利用できる
- 将来的な検索・分析機能の拡張に対応しやすい

### デメリット

- MySQL に慣れている場合は、一部 SQL や Data Type の違いを意識する必要がある
- PostgreSQL 固有機能を多用すると将来的な Database 移行が難しくなる

---

## 4. MySQL

### メリット

- Laravel との相性がよい
- CRUD 中心の Web Application に十分な機能を持つ
- 利用実績が多い
- 学習資料が豊富
- JSON 型を利用できる
- Transaction を利用できる
- 一般的な検索・集計は問題なく実現できる

### デメリット

- PostgreSQL と比較すると、高度な SQL や分析系機能を利用する場合に選択肢が異なる
- 将来的に複雑な検索要件が増えた場合、PostgreSQL の方が扱いやすいケースがある

## 5. 今回の要件との比較

| 観点 | PostgreSQL | MySQL |
|---|---|---|
| Laravel との相性 | ◎ | ◎ |
| CRUD | ◎ | ◎ |
| JOIN | ◎ | ◎ |
| Foreign Key・Constraint | ◎ | ◎ |
| Transaction | ◎ | ◎ |
| Row Lock | ◎ | ◎ |
| 複雑な検索 | ◎ | ○〜◎ |
| 集計 | ◎ | ◎ |
| 高度な SQL | ◎ | ○ |
| JSON | ◎ | ◎ |
| 将来の分析機能 | ◎ | ○〜◎ |
| MVP との相性 | ◎ | ◎ |
| 将来拡張 | ◎ | ◎ |

PostgreSQL と MySQL のどちらでも MVP は実現可能である。

そのうえで、検索・集計・Constraint・将来的な拡張性を考慮し PostgreSQL を採用する。

## 6. 今回のデータ構造との相性

今回のシステムでは、多くのデータが Relational な関係を持つ。

例：

```text
Employee
   |
   +--- EmployeeSkill
   |        |
   |        +--- Skill
   |               |
   |               +--- SkillCategory
   |
   +--- Department
   |
   +--- SubManagerAssignment
   |
   +--- TeamLeaderAssignment
```

そのため、Relational Database を採用する。

PostgreSQL と MySQL のどちらでも実現可能だが、今回の検索・集計・整合性・将来拡張を考慮して PostgreSQL を採用する。

## 7. データ所有方針

PostgreSQL は Laravel Backend が一元管理する。

Application Data と Laravel Sanctum Token は PostgreSQL に保存する。

```text
PostgreSQL
└── Laravel Backend
    ├── Application Data
    └── Sanctum personal_access_tokens
```

### Application Data

Laravel Backend が所有する。

対象には以下を含む。

- Employee
- Department
- SkillCategory
- Skill
- EmployeeSkill
- User
- Access Control 関連データ
- Assignment 関連データ

Application Data の Schema、Migration、Constraint、Data Lifecycle は Laravel 側で管理する。

### Laravel Sanctum Token

Laravel Backend が所有する。

Sanctum Token は PostgreSQL の `personal_access_tokens` Table で管理する。

Token の発行・検証・失効は Laravel が担当する。

### Session / Credential Data

Better Auth Session と Backend Credential は Redis に保存する。

```text
Redis
├── better-auth:*
│   └── Better Auth Session
│
└── backend-credential:*
    └── Encrypted Backend Credential
```

Better Auth Session は Better Auth が管理する。

Backend Credential は Next.js BFF が管理する。

Backend Credential は Application Level Encryption を適用して保存し、Browser へ公開しない。

Redis は MVP で 1 Instance とし、Namespace と ACL によって Access 権限を分離する。

Redis は Application Data の Primary Database として使用しない。

PostgreSQL への直接アクセスは Laravel Backend に限定する。

---

## 8. Database Access 方針

基本構成は以下とする。

```text
Browser
   ↓
Next.js
Frontend / BFF
   ↓
Laravel
Backend API
   ↓
PostgreSQL
Application Data
```

Application Data について、Next.js から PostgreSQL へ直接アクセスしない。

```text
NG

Next.js
   ↓
Application Tables
```

Application Data へのアクセスは Laravel Backend API を通して行う。

```text
OK

Next.js
   ↓
Laravel API
   ↓
Application Tables
```

PostgreSQL への直接アクセスは Laravel Backend に限定する。

Next.js から PostgreSQL へ直接接続しない。

Better Auth Session と Backend Credential は PostgreSQL に保存せず、Redis を利用する。

```text
Next.js
   ↓
Redis
├── better-auth:*
└── backend-credential:*
```

---

## 9. Migration Ownership

Migration は Data Ownership に従って管理する。

```text
Migration
└── PostgreSQL Tables
    └── Laravel
```

PostgreSQL Schema と Migration は Laravel Backend が一元管理する。

Better Auth Session と Backend Credential は Redis に保存するため、Frontend / Better Auth 側で PostgreSQL Migration を管理しない。

1つの Table を複数 Application から Migration しない。

基本方針：

```text
1 Table
   ↓
1 Owner
   ↓
1 Migration Responsibility
```

これにより Schema 変更の責務を明確にする。

## 10. 複数スキル検索

将来的に以下のような検索を行う。

```text
PHP
AND
Laravel
AND
AWS
```

さらに各 Skill に条件を指定する可能性がある。

```text
PHP
経験3年以上

AND

Laravel
Level 3以上

AND

AWS
実務経験あり
```

このような検索では、以下を利用する可能性がある。

- JOIN
- EXISTS
- GROUP BY
- HAVING
- Subquery

PostgreSQL はこのような検索要件との相性がよい。

実際の Query Pattern に応じて Index を設計する。

## 11. 集計

将来的に以下のような集計を行う。

- PHP 保有社員数
- Laravel 保有社員数
- AWS 保有社員数
- Category 別 Skill 数
- Skill Level 別社員数

例：

```text
PHP        20人
Laravel    15人
AWS        12人
Go          5人
```

PostgreSQL の Aggregation 機能を利用して実現する。

Dashboard の集計対象は在籍社員を基本とする。

## 12. JSON の利用方針

PostgreSQL では JSON / JSONB を利用できる。

ただし、今回の主要データを JSON にまとめて保存しない。

例えば以下は通常の Relational Data として管理する。

- 社員
- スキル
- 経験期間
- スキルレベル
- 権限
- 担当社員

基本方針：

```text
Relational Data
    ↓
Column / Relation

柔軟な補足データ
    ↓
必要な場合のみ JSONB
```

JSONB を安易に利用しない。

将来的に柔軟な追加属性が必要になった場合の選択肢として扱う。

---

## 13. データ整合性

Application 側の Validation だけでなく、Database でも可能な範囲で整合性を保証する。

利用する主な Constraint は以下とする。

- PRIMARY KEY
- UNIQUE
- FOREIGN KEY
- NOT NULL
- CHECK

例えば以下を Database Level でも保証する。

```text
社員番号
→ UNIQUE

Employee + Skill
→ UNIQUE
```

基本方針は以下とする。

```text
Application Validation
        +
Domain Rule
        +
Database Constraint
        ↓
   Data Integrity
```

Database Constraint を最後の防衛線として利用する。

ただし、複雑な業務ルールを Database に集約しない。

---

## 14. Domain Rule と Database の責務

業務ルールは Laravel Domain / Application 側で管理する。

例えば EmployeeSkill に関する以下のルールは Backend で保証する。

- 実務未経験の場合は Level 1 のみ
- 実務経験ありの場合は経験期間1か月以上
- 実務経験ありの場合は最終利用年月必須

Database では安全に保証できる範囲を Constraint で二重防御する。

基本方針：

```text
Domain Rule
→ Laravel

Data Integrity
→ PostgreSQL Constraint
```

Stored Procedure や Trigger を中心に業務ルールを実装する構成は採用しない。

---

## 15. Transaction 方針

Application Data の Transaction Boundary は Laravel Application Layer で管理する。

基本方針：

```text
1 UseCase
    =
1 Transaction
```

Isolation Level は PostgreSQL の `READ COMMITTED` を基本とする。

必要以上に強い Isolation Level は利用しない。

---

## 16. Concurrent Update 方針

同時更新によって Domain Invariant が壊れる可能性がある処理では、必要に応じて PostgreSQL の Pessimistic Lock を利用する。

例えば以下の条件を満たす管理ユーザーを最低1人維持する処理などを対象とする。

```text
role = ADMINISTRATOR
AND
can_manage_permissions = true
```

複数 Record を Lock する場合は、原則として ID 昇順で Lock する。

MVP では Version Column を利用した Optimistic Lock は採用しない。

通常の更新競合については Last Write Wins を許容する。

---

## 17. ID 方針

Application Data の Primary Key は原則 `bigint` とする。

```text
Primary Key
└── bigint
```

新規 Aggregate の ID が処理途中で必要になる場合に対応するため、PostgreSQL Sequence を利用して事前に ID を取得できる構成とする。

```text
Application
   ↓
ID Generator
   ↓
Infrastructure
   ↓
PostgreSQL Sequence
```

ID Generator は Application Port として定義し、PostgreSQL 依存の実装は Infrastructure に配置する。

Sequence の欠番は許容する。

MVP では UUID / ULID を Primary Key として採用しない。

---

## 18. Index 方針

Index は実際の Query Pattern に基づいて設計する。

主に以下を対象とする。

- Primary Key
- Foreign Key を利用した検索
- JOIN 条件
- Search / Filter 条件
- Sort 条件
- Unique Constraint

必要以上に Index を作成しない。

Performance 問題が発生した場合は `EXPLAIN` / `EXPLAIN ANALYZE` を利用して Query Plan を確認する。

詳細な Index 設計は Database 設計ドキュメントで管理する。

---

## 19. PostgreSQL 固有機能の利用方針

PostgreSQL を採用するが、必要性がない段階から PostgreSQL 固有機能へ強く依存しない。

MVP では主に標準的な Relational 機能を利用する。

- Table
- Column
- Primary Key
- Foreign Key
- Unique Constraint
- Check Constraint
- Index
- Transaction
- Sequence
- Row Lock

以下は必要性が確認された場合のみ利用する。

- JSONB
- GIN Index
- Full Text Search
- Materialized View
- Array
- その他 PostgreSQL 固有機能

---

## 20. 日時の基本方針

日時データは Application 全体の日時方針に従って管理する。

瞬間を表す日時については UTC を基準として扱う。

表示時に必要な Timezone へ変換する。

一方、以下のような Domain Value は「瞬間」として扱わない。

- 最終利用年月
- 対象年月
- 年月のみを意味する値

Data Type は値の意味に応じて決定する。

具体的な Column Type は Database 設計で管理する。

## 21. 開発・Test 環境

Local Development では Docker 上の PostgreSQL を利用する。

```text
Docker
├── frontend
├── backend
└── postgres
```

Host OS に PostgreSQL を直接インストールすることを前提としない。

Backend Test でも本番と同じ PostgreSQL を利用することを基本とする。

```text
Production
└── PostgreSQL

Test
└── PostgreSQL
```

SQLite を Backend Test の標準 Database として利用しない。

これにより PostgreSQL 固有の Constraint、Transaction、Lock、SQL の差異による問題を減らす。

---

## 22. バージョン方針

開発開始時点でサポートされている Stable Version の PostgreSQL を使用する。

具体的な Version は Project Setup 時に決定する。

Preview Version・Development Version は原則として使用しない。

Version 選定時には以下を確認する。

- PostgreSQL の Support 状況
- 利用する Hosting / Managed Database の Support 状況
- Laravel / Driver との互換性
- Security Update の提供状況

---

## 23. 採用しない構成

MVP では以下を採用しない。

- MySQL / MariaDB
- SQLite を Production Database とする構成
- SQLite を Backend Test Database の標準とする構成
- NoSQL を Application Data の Primary Database とする構成
- Next.js から PostgreSQL へ直接アクセスする構成
- Better Auth Session を PostgreSQL に保存する構成
- Backend Credential を PostgreSQL に保存する構成
- Stored Procedure / Trigger を中心とした Domain Logic
- Database per Service
- Read / Write Database の物理分離

Lightweight CQRS を採用するが、Read Database / Write Database は分離しない。

```text
Command ─┐
         ├── PostgreSQL
Query ───┘
```

## 25. 決定事項

### Database

**PostgreSQL を採用する。**

### 採用理由

- Laravel との相性がよい
- Relational Data 管理に適している
- 複雑な検索に対応しやすい
- Aggregation との相性がよい
- Database Constraint によって Data Integrity を強く保証できる
- Transaction / Lock を利用できる
- 将来的な検索・分析要件へ対応しやすい

### Data Ownership

```text
PostgreSQL
└── Laravel Backend
    ├── Application Data
    └── Sanctum personal_access_tokens

Redis
├── better-auth:*
│   └── Better Auth Session
│
└── backend-credential:*
    └── Encrypted Backend Credential
```

### 基本構成

```text
Browser
   ↓
Next.js
Frontend / BFF
   ↓
Laravel
Backend API
   ↓
PostgreSQL
Application Data
```

Better Auth Session と Backend Credential については以下とする。

```text
Next.js
   ↓
Redis
├── better-auth:*
│   └── Better Auth Session
│
└── backend-credential:*
    └── Encrypted Backend Credential
```

### 基本方針

- PostgreSQL を Application Data の Primary Data Store とする
- PostgreSQL Schema と Migration は Laravel Backend が一元管理する
- Application Data は Laravel が所有する
- Laravel Sanctum Token は PostgreSQL の `personal_access_tokens` Table で管理する
- Better Auth Session は Redis の `better-auth:*` Namespace で管理する
- Backend Credential は暗号化し、Redis の `backend-credential:*` Namespace で管理する
- Next.js から PostgreSQL へ直接接続しない
- Redis は Application Data の Primary Database として使用しない
- 主要データは Relational Model として管理する
- JSONB は必要になった場合のみ利用する
- Application Validation / Domain Rule / Database Constraint を組み合わせて Data Integrity を保証する
- 1 UseCase = 1 Transaction を基本とする
- Isolation Level は `READ COMMITTED` を基本とする
- 必要な箇所では Pessimistic Lock を利用する
- Primary Key は `bigint` を基本とする
- PostgreSQL Sequence による ID 事前取得を利用できる構成とする
- Backend Test でも PostgreSQL を利用する
- PostgreSQL 固有機能への不必要な依存は避ける

この方針を今後の Database 設計・Backend 実装・認証実装における基本方針とする。
