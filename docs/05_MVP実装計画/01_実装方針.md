# MVP実装方針

## 1. 目的

本ドキュメントは、Engineer Skill Management App のMVPを実装する際の基本方針を定義する。

要件定義、アーキテクチャ、システム設計、技術選定、非機能要件で決定した内容を実装へ落とし込み、Frontend、BFF、Backend、Database、OpenAPIを一貫した方針で開発することを目的とする。

詳細な実装順序は [`02_実装フェーズ.md`](./02_実装フェーズ.md)、API単位の具体的な進め方は [`03_API実装サイクル.md`](./03_API実装サイクル.md) で定義する。

---

## 2. 基本方針

MVP実装では、以下を基本方針とする。

1. MVP Scope First
2. Vertical Slice
3. Incremental OpenAPI First
4. API / UseCase単位でEnd-to-Endに完成させる
5. 既存のArchitecture・設計を実装都合で安易に崩さない
6. 小さく実装し、小さく検証する
7. MVP外の機能追加を原則として行わない

実装対象をFrontend、Backendなどの技術レイヤー単位で分割して完成させるのではなく、ユーザー価値を提供できる機能単位でEnd-to-Endに実装する。

```text
避ける進め方

Backend全体
    ↓
BFF全体
    ↓
Frontend全体
    ↓
統合


採用する進め方

API / UseCase
    ↓
OpenAPI
    ↓
Backend
    ↓
BFF
    ↓
Frontend
    ↓
Test
    ↓
そのSliceを完成
```

---

## 3. MVP Scope First

実装対象は、MVPとして定義された機能を優先する。

実装中に追加機能や改善案が発生した場合でも、その場でMVPへ追加することは原則として行わない。

```text
追加要求・改善案
       │
       ▼
MVP要件か
 ┌─────┴─────┐
Yes           No
 │             │
 ▼             ▼
実装対象      Backlog / 将来対応
```

MVPのスコープ変更が必要な場合は、実装都合だけで変更せず、要件・設計への影響を確認した上で明示的に判断する。

ただし、本プロジェクトにはアーキテクチャや技術の学習目的も含まれるため、MVPのユーザー価値に直接必要でなくても、学習効果が高く将来の保守性を著しく損なわないものについては「学習目的の技術的投資」として採用できる。

その場合も、目的を明確にし、無制限な抽象化や機能追加は行わない。

---

## 4. Vertical Slice

MVPはVertical Sliceを基本として実装する。

Frontend、BFF、Backend、Databaseをそれぞれ独立して完成させるのではなく、機能をEnd-to-Endで動作させる。

```text
User
 │
 ▼
Frontend
 │
 ▼
Next.js BFF
 │
 ▼
Laravel Backend API
 │
 ▼
PostgreSQL
```

1つのSliceを可能な限り小さく完成させ、その後に次のSliceへ進む。

例えばEmployee機能では、Employee全体を一括実装するのではなく、必要に応じて以下のようなAPI / UseCase単位へ分割する。

```text
Employee一覧取得
      ↓
Employee詳細取得
      ↓
Employee登録
      ↓
Employee更新
      ↓
その他のEmployee UseCase
```

ただし、分割によって不自然な一時実装や過剰な手戻りが発生する場合は、密接に関連する複数のUseCaseを同一Sliceとして扱ってよい。

---

## 5. 実装の基本単位

実装の基本単位は **API / UseCase** とする。

BackendのApplication Layerで定義されるCommand / Queryを、実装単位を判断する際の基準の1つとする。

```text
API
 │
 ▼
UseCase
 │
 ├── Command
 │      └── CommandHandler
 │
 └── Query
        └── QueryHandler / QueryService
```

ただし、HTTP EndpointとUseCaseを機械的に1対1にすることを目的とはしない。

Domainの責務、トランザクション境界、ユーザー操作、API契約を考慮して適切な単位を決定する。

---

## 6. Incremental OpenAPI First

Backend APIの契約はOpenAPIをSource of Truthとする。

API実装より先にOpenAPIで契約を定義し、その契約に基づいてLaravel BackendとNext.js BFFを実装する。

標準的な流れは以下とする。

```text
API設計
   ↓
OpenAPI定義
   ↓
Redocly CLI
Lint / Bundle
   ↓
openapi-typescript
   ↓
TypeScript型生成
   ↓
Laravel Backend
   ↓
Next.js BFF
   ↓
Frontend
```

ただし、MVP全APIのOpenAPI仕様を最初に完成させてから実装へ進む方式は採用しない。

機能またはAPI単位で、

```text
OpenAPI
   ↓
実装
   ↓
検証
   ↓
次のAPI
```

を繰り返す **Incremental OpenAPI First** とする。

OpenAPI変更が必要になった場合は、実装のみを先に変更するのではなく、原則としてOpenAPI契約を先に更新する。

---

## 7. Backend実装方針

BackendはLaravelを使用し、既存のBackend Architectureに従う。

基本的な依存方向は以下とする。

```text
Presentation
     ↓
Application
     ↓
Domain
```

InfrastructureはDomain / Applicationで定義されたInterfaceを実装し、Framework、Database、外部I/Oなどの技術詳細を担当する。

### Domain

Domain LayerはLaravel、Eloquent、HTTPなどのFramework詳細へ依存させない。

Aggregate、Entity、Value Object、Domain Serviceなどを使用し、Domain InvariantをDomain Modelで表現する。

Domain Modelの状態変更はBehaviorを通して行い、Generic Setterは使用しない。

### Application

Application LayerはUseCaseを実行する。

Lightweight CQRSを採用し、Command / Query / Handlerを基本構造とする。

原則として1 UseCaseを1 Transaction境界とする。

### Infrastructure

Eloquent、Repository実装、Mapper、ID Generator、Databaseアクセスなどの技術詳細を配置する。

Eloquent ModelをDomain Modelとして扱わない。

Repository InterfaceはDomain側に定義し、Infrastructure側で実装する。

### Presentation

ControllerはSingle Action Controllerを基本とし、HTTP処理へ責務を限定する。

Form RequestでHTTP Validationを行い、AuthorizationはPolicy等の既存設計に従う。

ControllerへDomain LogicやUseCase Logicを持たせない。

---

## 8. Frontend / BFF実装方針

FrontendはNext.js App Routerを使用する。

BrowserからLaravel Backend APIを直接呼び出さず、Next.js BFFを経由する。

```text
Browser
   │
   ▼
Next.js Frontend
   │
   ▼
Next.js BFF
   │
   ▼
Laravel Backend API
```

Backend APIとの通信にはOpenAPIから生成した型を利用する。

```text
OpenAPI
   ↓
Generated Type
   ↓
API Client
   ↓
BFF
   ↓
Frontend
```

Server Component / Client Component、状態管理、Form、Validation、Error Handling、Cache等については既存のFrontend ArchitectureおよびFrontend技術選定に従う。

Backend APIの仕様をFrontend側で独自定義しない。

---

## 9. 認証・認可

認証経路は既存の認証設計に従う。

```text
Browser
   ↓
Auth.js Session
   ↓
Next.js BFF
   ↓
Sanctum Token
   ↓
Laravel Backend
```

Browser側の認証状態はAuth.js Sessionで管理する。

BFFからLaravel BackendへのAPIアクセスにはSanctum Tokenを使用する。

認可はFrontend表示制御だけに依存せず、Backend側でも必ず実施する。

Frontend側の表示制御はUX向上を目的とし、セキュリティ境界として扱わない。

---

## 10. Database・Migration

DatabaseにはPostgreSQLを使用する。

Schema変更は既存のDatabase設計およびMigration Ownershipに従い、Laravel Migrationで管理する。

整合性については、

```text
Domain Invariant
        +
Application Validation
        +
Database Constraint
```

による多層防御を基本とする。

Databaseで保証可能な整合性については、必要に応じて以下を使用する。

- PRIMARY KEY
- FOREIGN KEY
- UNIQUE
- CHECK
- NOT NULL

Application側で検証していることだけを理由にDatabase Constraintを省略しない。

一方で、DatabaseへDomain Logicを過剰に持たせない。

---

## 11. テスト・品質

実装とテストを別フェーズとして分離せず、各Sliceの実装サイクルへ含める。

```text
OpenAPI
   ↓
Backend実装
   ↓
Backend Test
   ↓
BFF / Frontend実装
   ↓
Frontend Test
   ↓
Integration / E2E確認
```

各レイヤーのテスト戦略については既存のBackend / Frontend Architectureおよび技術選定に従う。

最低限、以下の観点を継続的に確認する。

- Domain Invariant
- UseCase
- API契約
- Validation
- Authorization
- Database Constraint
- BFFとBackendの連携
- 主要なユーザーフロー

Lint、Static Analysis、Formatter、OpenAPI検証等の自動化可能な品質確認は可能な限りCIへ組み込む。

---

## 12. 実装順序

MVP全体では、依存関係を考慮して以下を基本順序とする。

```text
開発基盤
   ↓
認証・認可基盤
   ↓
Employee
   ↓
Skill
   ↓
EmployeeSkill
   ↓
Access Control
   ↓
Dashboard
   ↓
MVP統合・E2E
```

EmployeeSkillはSkill Managementの中心となるAggregateであり、EmployeeとSkillへの参照を必要とするため、それらの基盤を先に実装する。

Dashboardは複数DomainのRead Modelを利用するため、主要な登録・参照機能の後に実装する。

詳細なPhaseおよび依存関係は `02_実装フェーズ.md` で定義する。

この順序は依存関係を示すものであり、各Phaseを完全に終了しなければ次へ進めないWaterfall型の工程として扱わない。

安全に並行できる作業や共通基盤については、必要に応じて前後または並行して実装できる。

---

## 13. 設計変更の扱い

実装中に既存設計では対応できない問題が判明した場合、実装側だけで局所的に回避しない。

影響範囲を確認し、必要に応じて以下を更新する。

```text
要件
 ↓
Architecture
 ↓
System Design
 ↓
OpenAPI
 ↓
Implementation
```

すべての変更で全ドキュメントを更新する必要はなく、実際に影響するSource of Truthのみを更新する。

設計と実装の乖離を放置しない。

---

## 14. 過剰設計の扱い

本プロジェクトではClean Architecture、DDD、Lightweight CQRSなどを実践的に学習する目的があるため、一般的な小規模MVPよりも一定の設計コストを許容する。

ただし、以下は原則として避ける。

- 利用予定のない抽象化
- 将来必要になるかもしれないという理由だけの機能
- 不要な汎用Framework化
- Domain価値のない過度なDomain Model化
- 不要なRepository
- 不要なDomain Service
- Full CQRS
- Event Sourcing
- Microservices
- Saga
- Outbox

設計パターンは目的ではなく、Domain Logicの表現、変更容易性、テスト容易性、学習効果を得るための手段として使用する。

---

## 15. 完成の考え方

「コードを書いた」ことを実装完了とはしない。

各Sliceは、原則として以下が成立した状態を完成とする。

```text
OpenAPI契約
     +
Backend
     +
BFF
     +
Frontend
     +
必要なDatabase変更
     +
Test
     +
主要動作確認
     =
Slice完成
```

詳細な完了条件およびMVP全体のDefinition of Doneは `05_MVP完了条件.md` で定義する。

---

## 16. 実装原則まとめ

MVP実装では、以下の4つを最上位の実装原則とする。

### MVP Scope First

MVPとして必要な価値を優先し、不要なスコープ拡大を避ける。

### Vertical Slice

技術レイヤー単位ではなく、ユーザー価値をEnd-to-Endで完成させる。

### Incremental OpenAPI First

API契約をOpenAPIで先に定義し、小さな単位で仕様・実装・検証を繰り返す。

### API / UseCase単位でEnd-to-Endに完成させる

巨大な機能を一括実装せず、小さなAPI / UseCase単位で動作する状態まで完成させてから次へ進む。

これらをMVP実装全体の判断基準とする。
