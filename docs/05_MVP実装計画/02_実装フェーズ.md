# MVP実装フェーズ

## 1. 目的

本ドキュメントは、Engineer Skill Management App のMVPを実装する順序、各Phaseの目的、依存関係、実装対象、完了条件を定義する。

実装の基本原則は [`01_実装方針.md`](./01_実装方針.md) に従い、Vertical SliceおよびIncremental OpenAPI Firstを基本として、小さな単位でEnd-to-Endに完成させる。

API単位の詳細な実装手順は [`03_API実装サイクル.md`](./03_API実装サイクル.md) で定義する。

---

## 2. 全体フェーズ

MVP実装は以下のPhaseで進める。

```text
Phase 0: 開発基盤
    ↓
Phase 1: UI設計
    ↓
Phase 2: 認証・認可基盤
    ↓
Phase 3: Employee
    ↓
Phase 4: Skill
    ↓
Phase 5: EmployeeSkill
    ↓
Phase 6: Access Control
    ↓
Phase 7: Dashboard
    ↓
Phase 8: MVP統合・E2E
    ↓
Staging
```

この順序は主な依存関係を表す。

各Phaseを完全に終了しなければ次のPhaseへ進めないWaterfall型の工程とはしない。

依存関係を満たしており、安全に並行できる作業については前後または並行して実施できる。

ただし、未完成の前提機能へ依存する一時的な実装を大量に作ることは避ける。

---

# Phase 0: 開発基盤

## 目的

MVP機能を継続的に実装・検証できるローカル開発基盤を構築する。

このPhaseでは業務機能の完成を目的とせず、Frontend、Backend、Database、OpenAPI、Test、CIを開発できる最低限の土台を成立させる。

## 実装対象

主に以下を対象とする。

- Monorepo基本構成
- Next.js初期構築
- Laravel初期構築
- PostgreSQL
- Docker / Docker Compose
- 環境変数管理
- Frontend / Backend間の基本疎通
- Laravel / PostgreSQL間の接続
- Redocly CLI
- OpenAPI基本構成
- openapi-typescript
- TypeScript型生成
- Frontend Test環境
- Backend Test環境
- Formatter
- Linter
- Static Analysis
- CIの基本構成

CIはこのPhaseで完成形まで構築せず、最低限の骨格を作成する。

```text
Phase 0
   ↓
CI基本構成

各Feature Phase
   ↓
必要な検証を追加

Phase 8
   ↓
MVPとして必要なCI完成
```

## 到達イメージ

```text
Browser
   ↓
Next.js
   ↓
Laravel
   ↓
PostgreSQL

+

OpenAPI
   ↓
Lint / Bundle
   ↓
TypeScript型生成

+

Test / Lint / Static Analysis / CI
```

## 対象外

- Employee等の本格的な業務機能
- Dashboard
- Access Control管理機能
- CI/CDの最終完成
- Stagingへの本格デプロイ

## 完了条件

以下を満たした状態をPhase 0完了の目安とする。

- Next.jsがローカルで起動できる
- Laravelがローカルで起動できる
- PostgreSQLへ接続できる
- Next.jsからLaravelへの基本的な疎通を確認できる
- OpenAPIをLint / Bundleできる
- OpenAPIからTypeScript型を生成できる
- Frontend / BackendのTestを実行できる
- 基本的なLint / Static Analysisを実行できる
- CIで最低限の自動検証を実行できる

# Phase 1: UI設計

## 目的

MVPで実装する画面、画面遷移、共通レイアウト、Design System、共通Component、UI状態、Responsive対応の基本方針を定義し、後続Featureで一貫したFrontend UIを実装できる状態にする。

このPhaseではFrontendの業務機能そのものを完成させることを目的とせず、後続Featureで参照するUI設計を確立する。

UI設計の詳細は [`../08_UI設計`](../08_UI設計) をSource of Truthとする。

## 前提

- Phase 0の開発基盤が利用可能である
- MVPで必要な主要機能および画面要件が整理されている

## 設計対象

主に以下を対象とする。

- UI設計方針
- 画面一覧
- 画面遷移
- App Shell
- 共通レイアウト
- Design System
- shadcn/uiを前提とした共通Component方針
- Loading / Empty / Error / NotFound等のUI状態
- Permissionによる表示・操作制御方針
- Responsive Design
- Accessibility
- Dialog / 独立画面の使い分け
- 各画面の基本設計

## 対象外

このPhaseでは、原則として以下を完成させない。

- Better Authによる認証機能
- Laravel SanctumによるBackend認証
- Employee等の業務API
- Backend UseCase / Repository等の業務実装
- 各画面の本番機能実装
- Dashboardの本番データ表示

実際の機能実装は後続PhaseでVertical Sliceとして行う。

## 後続Phaseとの関係

Phase 1で定義したUI設計は、後続の各PhaseでFrontendを実装する際の共通基準として利用する。

```text
Phase 1: UI設計
        │
        ├── Phase 2: 認証・認可基盤
        ├── Phase 3: Employee
        ├── Phase 4: Skill
        ├── Phase 5: EmployeeSkill
        ├── Phase 6: Access Control
        └── Phase 7: Dashboard
```

画面固有の詳細について実装時に不足が判明した場合は、既存のUI設計との整合性を保ちながら必要な設計を追加・更新する。

## 完了条件

- MVP対象画面が整理されている
- 主要な画面遷移が定義されている
- App Shellおよび共通レイアウト方針が定義されている
- Design Systemの基本方針が定義されている
- 共通Componentの利用方針が定義されている
- Loading / Empty / Error / NotFound等のUI状態が定義されている
- Responsive Designの基本方針が定義されている
- Accessibilityの基本方針が定義されている
- 後続Featureを一貫したUI方針で実装できる状態になっている

# Phase 2: 認証・認可基盤

## 目的

後続のすべての業務APIで利用する認証・認可の共通基盤を成立させる。

BrowserとNext.js間のSession管理、Next.js BFFとLaravel Backend API間の認証連携、Laravel側のAuthorizationまでをEnd-to-Endで構築する。

## 前提

- Phase 0の開発基盤が利用可能である
- Phase 1のUI設計が利用可能である
- Next.js / Laravel / PostgreSQL間の基本疎通が成立している
- Redisを認証基盤から利用できる

## 実装対象

主に以下を対象とする。

- User
- Better Auth
- Better Auth Session
- Redis Session Store
- Backend Credential
- Redis Key Namespace
- Redis ACL
- ログイン
- ログアウト
- Session作成・取得・更新・失効
- Next.js BFFの認証処理
- Laravel Sanctum
- Sanctum Token
- BFFからLaravelへの認証付きAPIアクセス
- Laravel側のAuthentication
- Roleの基礎
- Policy等のAuthorization基盤
- 未認証時のエラー処理
- 権限不足時のエラー処理

Better Auth SessionとBackend Credentialは同一Redis上で管理する。

ただし、それぞれの責務を分離するため、Key NamespaceおよびRedis ACLを分離する。

Backend CredentialはBetter Auth Session単位で1:1に対応させ、複数Session間で共有しない。

Next.jsからPostgreSQLへ直接アクセスしない。

認証経路は以下とする。

```text
Browser
   │
   │ Better Auth Session Cookie
   ▼
Next.js Frontend / BFF
   │
   ├── Redis
   │    ├── Better Auth Session
   │    └── Backend Credential
   │
   │ Authorization: Bearer <Sanctum Token>
   ▼
Laravel Backend
   │
   ▼
PostgreSQL
```

Laravel Sanctum TokenはBackend CredentialとしてNext.js Server側で管理し、BrowserやClient Componentへ露出させない。

## 対象外

このPhaseではAccess Controlの業務管理機能そのものは完成させない。

例えば以下はPhase 6で扱う。

- 権限変更
- 担当社員割当
- Sub Manager管理
- Team Leader管理
- 管理ユーザー最低1人維持の業務処理

また、MVPでは以下を対象外とする。

- Auth.js
- Better Auth SessionをPostgreSQLへ保存する構成
- Backend CredentialをPostgreSQLへ保存する構成
- Next.jsからPostgreSQLへ直接アクセスする構成
- Session用RedisとBackend Credential用Redisの物理分離

Phase 2では、後続APIを安全に利用するための認証・認可基盤を構築する。

## 完了条件

- ユーザーが認証できる
- Better Auth Sessionを利用できる
- Better Auth SessionがRedisで管理されている
- BFFから認証済みユーザーを識別できる
- Backend CredentialがBetter Auth Session単位で管理されている
- Better Auth SessionとBackend CredentialのKey NamespaceおよびACLが分離されている
- BFFからSanctum Tokenを利用してLaravel APIを呼び出せる
- Backend CredentialがBrowserやClient Componentへ露出しない
- Laravelで認証済みユーザーを識別できる
- 基本的なRole / PolicyによるAuthorizationが機能する
- 未認証・権限不足を適切に処理できる
- ログアウト時にSanctum Token、Backend Credential、Better Auth Sessionを適切に失効できる

## 目的

## 前提

- Phase 1のUI設計が利用可能である
- Phase 2の認証・認可基盤が利用可能である

## 実装対象

[`../03_システム設計/03_API/08_Access-Control-API.md`](../03_システム設計/03_API/08_Access-Control-API.md) で定義したMVP APIを対象とする。

主に以下を扱う。

- Administrator
- Manager
- Sub Manager
- Team Leader
- `can_manage_permissions`
- SubManagerAssignment
- TeamLeaderAssignment
- 担当社員管理
- Role変更
- 権限管理
- Authorization
- 必要な管理UI
- Transaction
- Lock
- Test

## 重要なInvariant

権限管理可能なAdministratorを最低1人維持する。

```text
role = ADMINISTRATOR
        +
can_manage_permissions = true
        ↓
最低1人必須
```

0人になる更新を許可しない。

競合更新によってInvariantが破壊されないよう、既存設計に従って悲観ロックを使用する。

ロック順序が複数存在する場合は、既存のTransaction / Concurrency設計に従う。

## Phase 2との責務分離

```text
Phase 2
認証・認可基盤

「誰なのか」
「APIへアクセス可能か」
を判定するための基盤


Phase 6
Access Control

「誰にどのRole・担当範囲を設定するか」
を管理する業務機能
```

## 完了条件

# 3. Phase間の依存関係

主要な依存関係は以下とする。

```text
Phase 0: 開発基盤
        │
        ▼
Phase 1: UI設計
        │
        ▼
Phase 2: 認証・認可基盤
        │
        ├─────────────┐
        ▼             │
Phase 3: Employee     │
        │             │
        ▼             │
Phase 4: Skill        │
        │             │
        ▼             │
Phase 5: EmployeeSkill│
        │             │
        ▼             │
Phase 6: Access Control
        │
        ▼
Phase 7: Dashboard
        │
        ▼
Phase 8: MVP統合・E2E
```

厳密にはすべてが直列依存するわけではない。

主な論理依存は以下である。

```text
開発基盤
 └── すべてのPhase

UI設計
 └── Frontend UIを実装する後続Phase

認証・認可基盤
 └── すべての業務API

Employee
 ├── EmployeeSkill
 ├── Access Control
 └── Dashboard

Skill
 ├── EmployeeSkill
 └── Dashboard

EmployeeSkill
 └── Dashboard
```

そのため、実装状況によってはEmployee完成後にSkillとAccess Controlの一部を並行して進めるなどの調整を許容する。

ただし、個人開発では並行作業によるWork in Progressの増加を避け、原則として1つのVertical Sliceを完成させてから次へ進む。

# 4. 各Feature Phaseの共通実装方法

Phase 3〜7では、Feature全体を一度に実装しない。

API / UseCase単位で以下を繰り返す。

```text
対象API / UseCaseを選択
        ↓
OpenAPI契約を定義・更新
        ↓
OpenAPI Lint / Bundle
        ↓
TypeScript型生成
        ↓
Laravel Backend実装
        ↓
Backend Test
        ↓
Next.js API Client / BFF実装
        ↓
Frontend実装
        ↓
Frontend Test
        ↓
Integration確認
        ↓
Slice完成
        ↓
次のAPI / UseCase
```

詳細は [`03_API実装サイクル.md`](./03_API実装サイクル.md) で定義する。

---

# 5. Phase完了の考え方

Phase完了は、ファイルやコードが存在することではなく、そのPhaseの目的が達成されていることを基準とする。

特にFeature Phaseでは、

```text
OpenAPI
   +
Backend
   +
Database
   +
BFF
   +
Frontend
   +
Test
   +
主要動作確認
   ↓
Featureとして利用可能
```

となっていることを基本とする。

未完成のレイヤーを大量に残した状態で次のFeatureへ進むことは避ける。

---

# 6. 実装フェーズまとめ

MVP実装では以下の順序を基本とする。

| Phase | 対象 | 主な目的 |
|---|---|---|
| Phase 0 | 開発基盤 | 継続的に実装・検証できる土台を作る |
| Phase 1 | UI設計 | 後続Featureで利用するUI設計の共通基準を確立する |
| Phase 2 | 認証・認可基盤 | 後続API共通の認証・認可経路を成立させる |
| Phase 3 | Employee | 最初の業務Vertical Sliceを完成させる |
| Phase 4 | Skill | Skill Masterを成立させる |
| Phase 5 | EmployeeSkill | Core Domainを完成させる |
| Phase 6 | Access Control | Role・担当社員・権限管理を完成させる |
| Phase 7 | Dashboard | Read Modelを利用した集計・表示を完成させる |
| Phase 8 | MVP統合・E2E | MVP全体を統合しStagingへ進める状態にする |

各Phaseは独立したWaterfall工程として扱わず、依存関係を守りながらVertical Sliceを小さく完成させる。

実装中はWork in Progressを必要以上に増やさず、原則として現在のSliceをEnd-to-Endで利用可能な状態にしてから次のSliceへ進む。
