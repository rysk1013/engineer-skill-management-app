# テスト・品質確認

## 1. 目的

本ドキュメントは、Engineer Skill Management App のMVP実装におけるテストおよび品質確認の横断的な方針を定義する。

Backend / Frontendそれぞれの詳細なテスト戦略や使用ツールを再定義するものではなく、MVP実装において、

- いつ確認するか
- 何を確認するか
- どのレイヤーで確認するか
- 何を自動化するか
- MVP全体としてどこまで確認するか

を整理することを目的とする。

詳細なテスト設計・使用技術については、既存のArchitecture、技術選定、非機能要件をSource of Truthとする。

---

## 2. 基本方針

MVPのテスト・品質確認では以下を基本方針とする。

1. テストを実装と分離しない
2. 各Vertical Slice内で必要な品質を確認する
3. 責務を最も適切なレイヤーでテストする
4. E2E Testですべてを検証しない
5. 自動化可能な品質確認は可能な限りCIへ組み込む
6. 自動テストと手動確認を適切に使い分ける
7. Phase 7をテスト開始地点にしない
8. Coverageの数値自体を目的にしない
9. Security / AuthorizationはMVPでも重点的に確認する
10. 不具合は原因となるレイヤーまで戻って修正する

基本的な流れは以下とする。

```text id="w7s8fx"
API / UseCase選択
       ↓
実装
       ↓
各レイヤーのTest
       ↓
Integration確認
       ↓
Slice完成

       × N

       ↓
Phase 7
MVP横断品質確認
```

---

## 3. 品質確認のタイミング

品質確認は3段階で実施する。

### Level 1: API / UseCase

各Vertical Sliceの実装中に確認する。

```text id="4hclmj"
OpenAPI
   ↓
Backend
   ↓
Backend Test
   ↓
BFF
   ↓
Frontend
   ↓
Frontend Test
   ↓
Integration
```

問題をできるだけ実装対象に近いタイミングで検出する。

### Level 2: Feature

Employee、Skill、EmployeeSkill等のFeature単位で、そのFeature全体が成立していることを確認する。

```text id="r51tbr"
API / UseCase
      +
API / UseCase
      +
API / UseCase
      ↓
Feature完成確認
```

個々のAPIが正常でも、Featureとして組み合わせた際に問題がないか確認する。

### Level 3: MVP

Phase 7で複数Featureを横断する品質確認を実施する。

```text id="b7d40a"
Authentication
      +
Employee
      +
Skill
      +
EmployeeSkill
      +
Access Control
      +
Dashboard
      ↓
MVP横断確認
```

Phase 7では、それまで未実施だったテストをまとめて開始するのではなく、個別に確認済みのFeatureをシステム全体として再確認する。

---

## 4. Backend

Backendでは、責務に応じて適切なレイヤーでTestを行う。

```text id="v1kt9u"
Domain
    ↓
Domain Test

Application
    ↓
Application Test

Presentation
    ↓
Feature / API Test

Infrastructure
    ↓
必要なIntegration Test
```

すべての処理を同じ種類のTestで確認しない。

---

### Domain Test

Domain InvariantおよびDomain Modelの振る舞いを確認する。

特にCore DomainであるEmployeeSkillでは重点的に実施する。

例：

```text id="ntt4yu"
実務未経験
    ↓
Level 1のみ
    ↓
経験期間なし
    ↓
最終利用年月なし
```

```text id="vnipqu"
実務経験あり
    ↓
経験期間 >= 1か月
    ↓
最終利用年月必須
    ↓
Level 1〜5
```

不正な状態をDomain Modelとして生成・更新できないことを確認する。

---

### Application Test

UseCaseの振る舞いを確認する。

主な対象は以下とする。

- Command / Query
- Handler
- Repositoryとの連携
- Domain Errorの扱い
- Application上の重複確認
- Transaction境界
- UseCase固有の分岐

Application TestではHTTPやFramework固有の処理を必要以上に含めない。

---

### Feature / API Test

HTTP境界を確認する。

主な対象は以下とする。

- Authentication
- Authorization
- Request Validation
- HTTP Status
- Response Schema
- Error Response
- JSON Serialization
- Date / Time表現

OpenAPI契約との整合性を意識して確認する。

---

### Infrastructure Test

Infrastructure固有の振る舞いを確認する必要がある場合に実施する。

主な対象は以下とする。

- Repository Implementation
- Mapper
- Query Service
- Database Constraint
- Transaction
- Pessimistic Lock
- Concurrency

単純なFramework動作そのものを確認するためだけのTestは増やさない。

---

## 5. Frontend

Frontendでは内部実装の詳細より、ユーザーから見た振る舞いを重視する。

主な確認対象は以下とする。

- Component表示
- User Interaction
- Form入力
- Validation Error
- Loading
- Error UI
- Feedback
- 一覧・詳細表示
- 権限に応じた表示制御
- BFFとの連携

必要に応じて以下を使い分ける。

```text id="a8f9i7"
Unit Test
    ↓
小さなUtility / Logic

Component Test
    ↓
Componentの振る舞い

Integration Test
    ↓
複数Component / BFF連携
```

Frontendの権限制御はUXのための表示制御として扱う。

```text id="4hrc4g"
Frontend
→ 表示・操作を適切に制御

Backend
→ 実際のAuthorizationを保証
```

ボタンが非表示であることだけをAuthorizationの保証とはしない。

---

## 6. API / OpenAPI

OpenAPIはBackend API契約のSource of Truthであるため、品質確認対象として明示的に扱う。

各API / UseCaseの実装サイクルで以下を確認する。

```text id="xkxflv"
OpenAPI
   ↓
Redocly Lint
   ↓
Bundle
   ↓
TypeScript型生成
   ↓
Backend / BFF
```

主な確認対象は以下とする。

- OpenAPI Syntax
- API共通仕様との整合
- Schema参照
- Request Schema
- Response Schema
- Error Response
- Authentication定義
- Validation Constraint
- operationId
- TypeScript型生成

Generated Typeは手動変更せず、OpenAPI変更後に再生成する。

### 実装との整合性

以下の整合性を確認する。

```text id="3jycy1"
OpenAPI
   ↕
Laravel Backend
   ↕
Next.js BFF
```

Phase 7ではMVP API全体について重大な契約乖離がないことを横断確認する。

---

## 7. Integration

各Vertical Sliceで、FrontendからDatabaseまでの主要経路を確認する。

```text id="6iwkvj"
Browser
   ↓
Next.js Frontend
   ↓
Next.js BFF
   ↓
Laravel Backend
   ↓
Application
   ↓
Domain / Query Service
   ↓
Infrastructure
   ↓
PostgreSQL
```

正常系だけでなく、そのAPIで定義されている主要な異常系も確認する。

例：

- 400 Bad Request
- 401 Unauthorized
- 403 Forbidden
- 404 Not Found
- 409 Conflict
- 422 Unprocessable Entity
- 500 Internal Server Error

すべてのStatus CodeをすべてのAPIで確認するのではなく、対象APIで発生し得るものを確認する。

---

## 8. E2E

E2E Testは、個別APIではなく主要なUser Story / User Flowを中心に実施する。

すべてのValidationやDomain InvariantをE2E Testで網羅することは目的としない。

基本的な役割分担は以下とする。

```text id="dnfw6b"
Domain Invariant
    ↓
Domain Test

UseCase
    ↓
Application Test

HTTP
    ↓
Feature / API Test

Frontend Behavior
    ↓
Component / Integration Test

主要User Flow
    ↓
E2E Test
```

E2E対象の例として、以下のような複数Featureを横断するフローを想定する。

```text id="fbpnkv"
ログイン
   ↓
Employee確認
   ↓
Skill確認
   ↓
EmployeeSkill登録
   ↓
登録結果確認
   ↓
Dashboard反映確認
```

Access Controlについても、Roleごとの主要フローをE2E対象として検討する。

E2E Testは実行コストや保守コストが高くなりやすいため、重要なユーザーフローへ集中させる。

---

## 9. Database

DatabaseはApplicationとは独立した最終防衛線として品質確認対象に含める。

主な確認対象は以下とする。

### Constraint

- PRIMARY KEY
- FOREIGN KEY
- UNIQUE
- CHECK
- NOT NULL

Application側でValidationしていることを理由にDatabase Constraintの確認を省略しない。

### Migration

以下を確認する。

- Migrationが正常に適用できる
- Schemaが設計と一致している
- Foreign Keyが正しい
- Constraintが正しい
- Migration順序が正しい

必要に応じてクリーンなDatabaseからMigrationを適用できることも確認する。

### Transaction / Concurrency

必要なUseCaseでは以下を確認する。

- Transaction境界
- Rollback
- Pessimistic Lock
- Lock順序
- Concurrent Update

特にAccess Controlの、

```text id="7l2y0p"
ADMINISTRATOR
+
can_manage_permissions = true
        ↓
最低1人維持
```

については、競合更新時にもInvariantが破壊されないことを確認する。

---

## 10. Security / Authorization

SecurityおよびAuthorizationはMVPでも重点的に確認する。

対象Roleは以下とする。

- Administrator
- Manager
- Sub Manager
- Team Leader

主な確認観点は以下とする。

```text id="c5r3yo"
閲覧可能か
作成可能か
更新可能か
管理可能か
担当範囲外へアクセスできないか
権限昇格できないか
```

特にSub Manager / Team Leaderでは担当社員の範囲を確認する。

Frontendで操作UIが非表示であっても、Backend APIを直接呼び出した場合に拒否されることを確認する。

Authenticationについても以下を確認する。

- Sessionなし
- 無効な認証情報
- Sanctum Tokenなし
- 無効なToken
- 権限不足

Securityの詳細要件については非機能要件をSource of Truthとする。

---

## 11. 非機能要件

非機能要件そのものは本ドキュメントで再定義しない。

`07_非機能要件` をSource of Truthとし、MVP実装中の確認タイミングを整理する。

| 項目 | 主な確認タイミング |
|---|---|
| 可用性・信頼性 | Phase 7中心 |
| 性能・スケーラビリティ | Feature実装 + Phase 7 |
| セキュリティ | 各Slice + Phase 7 |
| データ保護・バックアップ | 開発・運用構築 + Phase 7 |
| ログ・監査 | 対象Slice + Phase 7 |
| Observability | Phase 0から段階導入 + Phase 7 |
| 保守性・品質 | 各Slice + CI |
| API品質 | 各API Slice + Phase 7 |
| デプロイ・運用 | Phase 7 / Staging |
| ユーザビリティ・アクセシビリティ | UI実装 + Phase 7 |
| 互換性・動作環境 | Phase 7 |
| 国際化・日時 | 各対象Slice + Phase 7 |

すべてをPhase 7へ後回しにせず、実装時に確認できる項目は各Sliceで確認する。

---

## 12. Static Quality

自動化可能な静的品質確認を継続的に実施する。

### Frontend

主に以下を対象とする。

- Formatter
- Lint
- Type Check
- Test
- Build
- Complexity等の既存品質チェック

### Backend

主に以下を対象とする。

- Formatter / Code Style
- Static Analysis
- Test
- Complexity
- 既存のコード品質チェック

### OpenAPI

主に以下を対象とする。

- Redocly Lint
- Bundle
- TypeScript型生成

静的品質確認は可能な限りCIでも再現できるようにする。

---

## 13. Code Coverage

Code Coverageは品質を把握するための補助指標として利用する。

Coverage率そのものをMVP完了条件にはしない。

例えば、

```text id="py1p63"
Coverage 80%以上
```

のような単一の数値目標を達成するためだけにTestを追加することは避ける。

Coverageは主に、

- 重要な未テスト領域の発見
- Test不足の把握
- 変更によるTest範囲の変化

などに利用する。

重要なDomain Invariant、Authorization、UseCaseについてはCoverage率に関係なく明示的にTestする。

---

## 14. CI

自動化可能な品質確認は段階的にCIへ追加する。

```text id="dn4abn"
Phase 0
│
├── OpenAPI基本チェック
├── Frontend基本チェック
├── Backend基本チェック
└── Test実行
        ↓
Phase 2〜6
│
├── Feature Test追加
├── Static Analysis強化
├── Build
└── 必要な品質チェック追加
        ↓
Phase 7
│
└── MVP CI完成
```

MVP時点では、少なくとも以下をCIで継続的に検証できる状態を目指す。

```text id="hslsv2"
OpenAPI
├── Lint
├── Bundle
└── Type Generation

Frontend
├── Lint
├── Type Check
├── Test
└── Build

Backend
├── Code Quality
├── Static Analysis
└── Test
```

具体的なCI PlatformやWorkflow構成については `06_開発・運用` をSource of Truthとする。

---

## 15. Manual Test

すべての品質確認を自動化することは目的としない。

人間による確認の方が適している項目についてはManual Testを利用する。

主な対象は以下とする。

- UIの見た目
- 操作性
- Keyboard操作
- Focus
- Responsive表示
- Loading表示
- Error表示
- Feedback
- Accessibilityの一部
- 実際のユーザーフロー

基本的な考え方は以下とする。

```text id="c1ff4n"
安定して自動化できる
        ↓
Automated Test

人間による判断が適している
        ↓
Manual Check
```

同じ手動確認を頻繁に繰り返している場合は、自動化する価値があるか検討する。

---

## 16. 不具合発見時

不具合を発見した場合は、症状が現れたレイヤーだけで回避せず、原因となるレイヤーを特定する。

```text id="f8p4ay"
問題発見
   ↓
原因分析
   │
   ├── OpenAPI
   ├── Frontend
   ├── BFF
   ├── Presentation
   ├── Application
   ├── Domain
   ├── Infrastructure
   └── Database
          ↓
      原因箇所修正
          ↓
        Test
          ↓
   Integration再確認
```

修正時には可能な限り再発防止Testを追加する。

ただし、同じ問題を既存Testが十分に保証している場合や、自動化が適切でない場合は機械的にTestを追加しない。

## 17. Phase 7でのMVP最終品質確認

Phase 7ではMVP全体を横断して最終確認する。

主な確認対象は以下とする。

### Functional

- Authentication
- Employee
- Skill
- EmployeeSkill
- Access Control
- Dashboard

### API

- OpenAPI整合性
- Request / Response
- Error Response
- Authentication
- Authorization

### Database

- Migration
- Constraint
- Transaction
- Lock
- Date / Time

### Quality

- Backend Test
- Frontend Test
- Integration Test
- E2E Test
- Static Analysis
- Lint
- Build
- OpenAPI Validation

### Non-Functional

- Security
- Performance
- Logging / Audit
- Observability
- Accessibility
- Compatibility
- Date / Time
- Error Handling

### CI

MVPとして必要なCIチェックがすべて成功することを確認する。

## 18. 品質確認の役割分担

テスト対象と主な確認レイヤーを以下のように整理する。

| 確認対象 | 主な確認方法 |
|---|---|
| Domain Invariant | Domain Test |
| UseCase | Application Test |
| HTTP / API | Feature / API Test |
| Repository / Mapper | 必要なInfrastructure Test |
| DB Constraint | Database / Integration Test |
| Frontend Behavior | Component / Integration Test |
| API Contract | OpenAPI Validation + API Test |
| Frontend ↔ Backend | Integration確認 |
| 主要User Flow | E2E Test |
| Authorization | Backend API Test + 必要なE2E |
| UI / UX | Frontend Test + Manual Check |
| Static Quality | Lint / Static Analysis / Type Check |
| System全体 | Phase 7横断確認 |

1つの振る舞いを複数レイヤーで無条件に重複テストするのではなく、リスクと責務に応じて必要なTestを配置する。

---

## 19. 品質確認まとめ

MVPの品質確認は以下の構造とする。

```text id="rxgip9"
Level 1
API / UseCase
    │
    └── Slice内でTest・Integration
             ↓
Level 2
Feature
    │
    └── Feature全体を確認
             ↓
Level 3
MVP
    │
    └── Phase 7で横断確認
             ↓
         Staging
```

品質確認の目的はTest数やCoverage率を増やすことではなく、MVPとして重要な振る舞いと制約が継続的に保証されている状態を作ることである。

そのため、

```text id="sbgv83"
Test Early
    +
Test per Slice
    +
Automated Quality Check
    +
Manual Check where appropriate
    +
Final Cross-Cutting Verification
```

を基本とする。

Phase 7は品質確認を開始する場所ではなく、それまで各Vertical Sliceで積み重ねた品質をMVP全体として最終確認する場所とする。
