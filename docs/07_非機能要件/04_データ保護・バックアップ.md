# データ保護・バックアップ

## 1. 目的

本ドキュメントでは、Engineer Skill Management App におけるデータ保護、データ保持、バックアップおよびリストアに関する非機能要件を定義する。

障害、誤操作、データ破損等が発生した場合でも、定められたRPO / RTOの範囲内でデータおよびサービスを復旧できることを目的とする。

---

## 2. 基本方針

以下を基本方針とする。

- Production Dataを適切に保護する。
- Backup DataもProduction Dataと同等の機密情報として扱う。
- 定期的なBackupを取得する。
- Backupを取得するだけでなく、実際にRestore可能であることを確認する。
- Production Dataを開発環境へ原則持ち込まない。
- データの重要度および保持要件に応じて適切に削除する。
- Application CodeやContainer等、再構築可能なものと永続データを分離して考える。

---

## 3. 復旧目標

`可用性・信頼性.md` で定義した以下の目標を適用する。

| 項目 | 目標 |
|---|---:|
| RPO（Recovery Point Objective） | 24時間以内 |
| RTO（Recovery Time Objective） | 4時間以内 |

### 3.1 RPO

重大なDatabase障害等が発生した場合でも、最大24時間以内のデータ損失に抑えることを目標とする。

このため、最低1日1回Backupを取得する。

### 3.2 RTO

重大障害発生後、4時間以内にサービスを通常利用可能な状態へ復旧することを目標とする。

---

## 4. 保護対象データ

MVPでは主にPostgreSQLに保存されるデータを保護対象とする。

主な対象:

- Employee
- Department
- Skill
- SkillCategory
- EmployeeSkill
- User
- Role / Permission関連データ
- Sub Manager Assignment
- Team Leader Assignment
- Laravel Sanctum Token関連データ
- その他PostgreSQL上の業務データ

Better Auth SessionおよびBackend CredentialはRedisで管理し、PostgreSQL上の業務データとは重要度を分けて扱う。

---

## 5. Production Dataの保護

Production Databaseについて以下を必須とする。

- Internetへ直接公開しない。
- Application専用DB Userを使用する。
- DB Userには必要最小限の権限のみ付与する。
- Database CredentialをSecretとして管理する。
- Production DBへのDeveloperの直接アクセスを最小限とする。
- 通信経路ではTLS等による暗号化を利用する。

Production Dataへのアクセスは、業務または運用上必要な場合に限定する。

---

## 6. Production Dataの開発利用

Production DataをLocal Development環境やDeveloper PCへコピーすることを原則禁止する。

```text
Production DB
     │
     └──→ Developer PC

          原則禁止
```

開発・テスト環境では以下を利用する。

- Factory
- Faker
- Seeder
- Fixture
- その他のDummy Data

障害調査等によりProduction Dataの利用がどうしても必要な場合は、目的およびアクセス範囲を明確にし、必要に応じてMasking / Anonymization等を行う。

---

## 7. データ保持

### 7.1 在籍Employee

在籍中のEmployee Dataはシステム利用に必要な期間保持する。

### 7.2 退職Employee

退職Employee Dataは **退職後3年間保持する**。

3年経過後も自動的に削除しない。

管理ユーザーが対象を確認したうえで削除する。

### 7.3 Skill

Skillは物理削除しない。

不要となったSkillは無効化して保持する。

既存データとの参照関係を維持する。

### 7.4 Session / Backend Credential

期限切れとなったBetter Auth SessionはRedisから削除可能とする。

Sessionに対応するBackend CredentialもLifecycleを整合させて削除する。

Session / Backend Credentialについて、業務データと同じ長期保持は要求しない。

### 7.5 Log / Audit Log

Application LogおよびAudit Logの保持期間については `ログ・監査.md` で別途定義する。

---

## 8. Backup対象

MVPで必須となるBackup対象は以下とする。

```text
PostgreSQL
```

将来的にFile Storage / Object Storage等を導入した場合は、必要に応じてBackup対象へ追加する。

---

## 9. Backup対象外

以下は原則としてBackup対象としない。

- Docker Container
- Application Build Artifact
- Local Development Environment

Application CodeはGit Repositoryから、Container Image等はContainer RegistryまたはCI/CD Pipelineから再構築できる状態を維持する。

Infrastructureについても可能な限りCodeまたはConfigurationから再構築可能な状態を目指す。

---

## 10. Backup方式

MVPではManaged Databaseが提供するBackup機能を優先して利用する。

基本的な優先順位は以下とする。

```text
Managed Database Backup
          │
          ▼
Provider Snapshot / PITR
          │
          ▼
必要に応じて pg_dump
```

利用するHosting / Cloud Providerによって利用可能な機能が異なるため、具体的な方式はInfrastructure決定時に確定する。

`pg_dump` による論理Backupも利用可能とする。

---

## 11. Backup頻度

RPO 24時間を満たすため、最低 **1日1回** Backupを取得する。

```text
Backup Frequency
    Daily
```

Providerがより短い間隔のBackupやPITRを提供する場合は、その利用を許可・推奨する。

---

## 12. Backup保持期間

Daily Backupは **30日間保持する**。

```text
Daily Backup
    │
    └── Retention: 30 days
```

これにより以下のような問題への復旧可能性を確保する。

- 誤操作
- データ破損
- Migration障害
- 数日後に発覚したデータ不整合

保持期間経過後のBackupは削除可能とする。

---

## 13. Backup保存場所

BackupはProduction Databaseそのものとは独立したStorageまたはManaged Backup機能へ保存する。

以下を必須とする。

- Production Database障害と同時にBackupが失われない構成とする。
- BackupをPublic Access可能にしない。
- Backupへのアクセスを最小権限とする。
- Backup StorageへのCredentialをSecretとして管理する。

同一Database Server上だけにBackupを保存する構成は避ける。

---

## 14. Backup暗号化

Backup Dataについて以下を必須とする。

### 保存時

Backup Dataを保存時に暗号化する。

### 転送時

Backup DataをNetwork経由で転送する場合はTLS等を利用する。

### Key管理

Encryption KeyおよびCredentialはSecretとして管理する。

Backup Dataを平文のままPublic Storage等へ保存することを禁止する。

---

## 15. Backup Access Control

Backup Dataへのアクセス権限は必要最小限とする。

通常のApplication Userや一般DeveloperがBackup Dataへ直接アクセスできる状態を避ける。

Backupへのアクセス操作についても、利用するPlatformでAudit可能な場合は記録を有効化する。

---

## 16. Restore

BackupからDatabaseをRestore可能な状態を維持する。

Restore時には最低限以下を確認する。

1. Backup Dataが取得可能であること
2. PostgreSQLへRestoreできること
3. Schemaが正常であること
4. 必要なDataが存在すること
5. Migrationとの整合性が取れていること
6. ApplicationからDatabaseへ接続できること
7. 主要機能が正常に動作すること

---

## 17. Restore手順

Restore手順をドキュメント化する。

最低限以下を含める。

- 対象Backupの選択方法
- Database作成・準備方法
- Restore方法
- Migration確認方法
- Application接続確認方法
- Restore後の動作確認方法
- 問題発生時の対応方法

特定の担当者だけが復旧方法を把握している状態を避ける。

---

## 18. Restore Test

### 本番導入前

本番導入前に最低1回Restore Testを実施する。

### 本番運用開始後

本番運用開始後は **半年に1回** を目安としてRestore Testを実施する。

Restore Testでは、単にDatabaseへDataを投入できるだけではなく、Applicationから正常に利用できることまで確認する。

---

## 19. DB Migration

Database Migrationではデータ損失リスクを考慮する。

特に以下のような破壊的変更では注意する。

```sql
DROP TABLE
DROP COLUMN
ALTER COLUMN
DELETE
```

破壊的Migrationを実施する場合は、最低限以下を確認する。

- 影響範囲
- Data Lossの可能性
- Backup取得状況
- Restore方法
- Rollback方法
- Application Versionとの互換性

---

## 20. 段階的Migration

可能な場合は破壊的変更を一度に行わず、段階的なMigrationを優先する。

基本的な考え方として以下を利用できる。

```text
Expand
   │
   ▼
Migrate
   │
   ▼
Contract
```

例:

```text
新Column追加
    ↓
Applicationを新旧対応
    ↓
Data Migration
    ↓
Applicationを新Columnへ完全移行
    ↓
旧Column削除
```

MVPではZero Downtime Migration自体を必須としないが、安全に変更可能な方法を優先する。

---

## 21. 誤削除対策

Application上の重要な削除処理について、必要に応じて確認操作を設ける。

既存仕様として以下を維持する。

```text
Skill
  ↓
無効化
（物理削除しない）
```

```text
退職Employee
  ↓
3年間保持
  ↓
管理ユーザー確認
  ↓
削除
```

DBへの直接操作によるデータ削除を通常運用としない。

大量データを削除する処理については特に慎重に扱う。

---

## 22. Backupとデータ削除

Application上でデータを削除しても、過去のBackupにはRetention期間中そのデータが存在する可能性がある。

```text
Application Data削除
        │
        ├── Current DB → 削除
        │
        └── Existing Backup → Retention期間中保持
```

Application上の削除とBackupからの即時削除は同義ではないものとする。

原則としてBackup Retention満了によってBackup上のデータも削除される。

法令、契約、Privacy Policy等によって即時削除が要求される場合は、別途対応方法を検討する。

---

## 23. Backup障害

Backup処理が失敗した場合、それを検知できる状態とする。

最低限以下を確認可能とする。

- 最終Backup成功日時
- Backup Jobの成功 / 失敗
- Backup Dataの存在

Backup失敗が継続し、RPO 24時間を満たせなくなる状態を放置しない。

具体的な監視・通知方法については `監視・Observability.md` で定義する。

---

## 24. Point-in-Time Recovery

PITR（Point-in-Time Recovery）はMVPでは必須としない。

利用するManaged Databaseで容易に利用可能な場合は採用を検討する。

システム規模やデータ重要度が高まった場合は、RPOの短縮と合わせて正式導入を検討する。

---
