# セキュリティ

## 1. 目的

本ドキュメントでは、Engineer Skill Management App におけるセキュリティに関する非機能要件を定義する。

本システムは社内向けシステムであるが、社員情報、スキル情報、認証情報、権限情報を扱うため、MVP段階から適切なセキュリティ対策を実施する。

---

## 2. 基本方針

以下をセキュリティの基本方針とする。

- HTTPSを必須とする。
- 認証済みユーザーのみシステムを利用可能とする。
- BackendでAuthorizationを必ず実施する。
- 最小権限の原則を採用する。
- Defense in Depthを基本とする。
- Security by Defaultを採用する。
- SecretやCredentialをSource Codeへ含めない。
- Browser、BFF、API、Databaseの各Layerで必要な防御を行う。
- Frontendの表示制御のみをSecurity Boundaryとしない。

---

## 3. システム境界

基本的な通信経路は以下とする。

```text
Browser
   │
   │ HTTPS
   ▼
Next.js
Frontend / BFF
   │
   │ HTTPS + Sanctum Token
   ▼
Laravel API
   │
   ▼
PostgreSQL
```

原則としてBrowserからLaravel APIを直接呼び出さない。

Laravel APIへのアクセスはNext.js BFFを経由する。

---

## 4. HTTPS

Production環境ではすべての通信をHTTPSとする。

対象:

- Browser → Next.js
- Next.js BFF → Laravel API
- 外部サービスとの通信

HTTPによるProduction通信は許可しない。

---

## 5. Authentication

### 5.1 Browser → Next.js

Browserからのユーザー認証には **Auth.js** を使用する。

以下を基本構成とする。

- Auth.js
- Session方式
- Session Store: PostgreSQL
- BrowserではSession Cookieを利用

認証されていないユーザーは保護された画面およびAPIを利用できない。

### 5.2 Session

Sessionについて以下を満たすこととする。

- Server側でSessionの有効性を確認する。
- 無効または期限切れSessionでは再認証を要求する。
- Logout時にSessionを無効化する。
- Sessionには必要最小限の情報のみ保持する。
- Session IDをログへ出力しない。

Sessionの具体的なDatabase設計については、Auth.js Session設計ドキュメントに従う。

### 5.3 BFF → Laravel API

Next.js BFFからLaravel APIへの認証には **Laravel Sanctum Token** を使用する。

Tokenについて以下を必須とする。

- Browserへ公開しない。
- Client-side JavaScriptへ渡さない。
- Next.js Server側のみで利用する。
- HTTPSで送信する。
- ログへ出力しない。
- Source Codeへ直接記述しない。
- 必要最小限の権限とする。
- 漏洩時にRotate可能とする。

---

## 6. Authorization

AuthorizationはBackendで必ず実施する。

Frontendによる画面・Button等の表示制御はUX向上を目的とするものであり、Security Boundaryとして扱わない。

### 6.1 Role

以下のRoleを使用する。

- Administrator
- Manager
- Sub Manager
- Team Leader

### 6.2 基本方針

- Laravel側でAuthorizationを実施する。
- Policy等を利用してアクセス制御を集約する。
- RoleだけでなくResource Scopeも確認する。
- 権限のないResourceへのアクセスは拒否する。
- URLやRequest Parameterの変更による権限回避を許可しない。

### 6.3 Administrator

権限変更は、権限管理可能なAdministratorのみ実行できる。

以下のDomain Ruleを必ず維持する。

```text
Administrator
AND
can_manage_permissions = true
```

を満たすユーザーを最低1人存在させる。

この条件を満たす最後のAdministratorから権限を解除する操作は禁止する。

重要な権限変更ではTransactionおよび悲観ロックを利用し、同時操作によるInvariant違反を防止する。

### 6.4 Sub Manager / Team Leader

Sub ManagerおよびTeam Leaderについては担当EmployeeのScopeを必ず確認する。

例えば、

```text
/employees/123
```

へアクセスできることだけを理由としてEmployee `123` の閲覧・操作を許可してはならない。

以下をBackendで確認する。

- User
- Role
- 対象Employee
- 担当関係
- 操作権限

IDを書き換えることで担当外Employeeへアクセスできる状態を禁止する。

---

## 7. IDOR / Broken Access Control対策

すべてのResource Accessについて、Resource IDの存在確認だけではなくAuthorizationを実施する。

特に以下を重点的に保護する。

- Employee
- EmployeeSkill
- Skill
- Department
- User
- Role
- 担当者Assignment

APIのRequest ParameterやPath Parameterは信頼せず、Backend側でアクセス可能範囲を確認する。

---

## 8. Cookie Security

Production環境のSession Cookieでは以下を適切に設定する。

- `HttpOnly`
- `Secure`
- `SameSite`

Session CookieはClient-side JavaScriptから直接アクセスさせない。

Cookie値をログへ出力しない。

---

## 9. CSRF

Cookieを利用するState-changing RequestについてCSRF対策を行う。

以下を基本とする。

- Auth.js / Next.jsの標準的なSecurity Mechanismを利用する。
- 必要に応じてOriginを検証する。
- GET Requestではデータを変更しない。
- State-changing Requestは適切なHTTP Methodを使用する。

---

## 10. XSS

Cross-Site Scripting対策として以下を実施する。

- React / Next.jsの標準Escape機能を利用する。
- ユーザー入力HTMLを原則そのまま描画しない。
- `dangerouslySetInnerHTML` は原則使用しない。
- 使用が必要な場合はSanitizeを必須とする。
- ユーザー入力をScriptとして評価しない。
- Error Message等へユーザー入力を不用意に埋め込まない。

---

## 11. SQL Injection

Database Accessでは以下を必須とする。

- EloquentまたはQuery BuilderのParameter Bindingを利用する。
- ユーザー入力をSQL文字列へ直接連結しない。
- Raw SQLは必要最小限とする。
- Raw SQLを使用する場合もParameter Bindingを行う。
- Sort ColumnやTable Name等へユーザー入力を直接使用しない。

---

## 12. Input Validation

HTTP BoundaryではRequest Validationを必ず実施する。

LaravelではForm Request等を利用する。

主なValidation対象:

- Type
- Required / Optional
- String Length
- Numeric Range
- Enum
- Date
- ID
- Resource existence
- Array Size
- Pagination Limit

ただしHTTP ValidationのみでDomain Ruleを保証しない。

以下の多層防御を基本とする。

```text
HTTP Validation
        │
        ▼
Domain Invariant
        │
        ▼
Database Constraint
```

各Layerがそれぞれの責務に応じてデータの妥当性を保証する。

---

## 13. Secret管理

以下の情報をSecretとして扱う。

- Database Password
- Sanctum Token
- Auth Secret
- API Key
- Encryption Key
- Production Credential
- その他外部サービスCredential

### 禁止事項

- GitへのCommit
- Source CodeへのHard Coding
- Docker Imageへの埋め込み
- Application Logへの出力
- Client-side JavaScriptへの公開

### 管理方法

Local Development:

```text
.env
```

`.env.example` にはSecretそのものを記載せず、必要なKeyのみ定義する。

Staging / ProductionではHosting PlatformまたはCloud Providerが提供するSecret管理機能を利用する。

`.env` はGit管理対象外とする。

---

## 14. Password

アプリケーション独自のPassword認証を採用する場合、以下を必須とする。

- 平文Passwordを保存しない。
- 適切なPassword Hashingを使用する。
- Passwordをログへ出力しない。
- PasswordをAPI Responseへ含めない。
- Passwordを不要にApplication内で保持しない。

外部Identity Providerを利用する場合は、可能な限りアプリケーション側でPasswordを保持しない。

---

## 15. Error Handling

Production環境では内部情報を利用者へ公開しない。

以下をResponseへ含めない。

- Stack Trace
- SQL
- Database Credential
- File / Server Path
- Environment Variable
- Secret
- Token
- 詳細な内部Exception情報

Clientには一般化されたError Responseを返す。

調査に必要な詳細情報はServer-side Logへ記録する。

---

## 16. Security Headers

Production環境では最低限、以下のSecurity Headerを適切に設定する。

- `Content-Security-Policy`
- `X-Content-Type-Options`
- `Referrer-Policy`
- `Permissions-Policy`
- `Strict-Transport-Security`

Clickjacking対策はCSPの `frame-ancestors` を基本とし、必要に応じて `X-Frame-Options` との併用を検討する。

---

## 17. CORS

Laravel APIのCORS設定ではAllowed Originを明示的に制限する。

以下を基本とする。

- Productionで `*` を原則使用しない。
- Originを限定する。
- HTTP Methodを限定する。
- 必要なHeaderのみ許可する。
- Development / Staging / Productionで適切に設定を分離する。

可能であればLaravel APIはNext.js BFFからのみアクセス可能なNetwork構成とする。

---

## 18. Rate Limiting

MVPからRate Limitingを導入する。

主な対象:

- Login関連Endpoint
- Authentication関連Endpoint
- API全般
- 高負荷な検索・集計Endpoint

Laravel等が提供するRate Limiting機能を利用する。

具体的なRequest数・時間Windowについては、実装およびInfrastructure構成時に決定する。

---

## 19. Database Security

PostgreSQLについて以下を必須とする。

- Internetへ直接公開しない。
- Application専用DB Userを使用する。
- DB Userには必要最小限の権限のみ付与する。
- DB CredentialをSecretとして管理する。
- Production DBへのDeveloperの直接アクセスを最小限とする。
- Backup DataもProduction Dataと同等に保護する。

---

## 20. Logging Security

以下をApplication Logへ出力しない。

- Password
- Session ID
- Cookie
- Authorization Header
- Sanctum Token
- API Key
- Secret
- Database Credential

社員情報等についても、障害調査に必要な範囲を超えてログへ記録しない。

詳細なLogging / Audit方針については `ログ・監査.md` で定義する。

---

## 21. Dependency Security

以下を脆弱性管理の対象とする。

- npm Package
- Composer Package
- Docker Image
- GitHub Actions
- OS Package

最低限、以下の仕組みを利用する。

- `npm audit`
- `composer audit`
- Dependabot等のDependency Update / Vulnerability Detection

Critical / High Severityの脆弱性を優先して確認・対応する。

---

## 22. Docker Security

Docker Containerについて以下を基本とする。

- 可能な限りNon-root Userで実行する。
- 不要なPackageをInstallしない。
- Production Imageを最小化する。
- SecretをImageへ埋め込まない。
- `.env` をImageへCOPYしない。
- Base ImageのVersionを管理する。
- Base Imageを定期的に更新する。
- 不要なPortを公開しない。

---

## 23. 監査対象

Security上重要な操作についてAudit Logを記録する。

主な対象:

- Role変更
- 権限管理権限の付与
- 権限管理権限の解除
- Employee削除
- Skill無効化
- Sub Manager Assignment変更
- Team Leader Assignment変更

具体的な記録内容、保存期間等については `ログ・監査.md` で定義する。

---

## 24. File Upload

MVPではFile Upload機能を対象外とする。

将来的にプロフィール画像等のUpload機能を導入する場合、以下を別途定義する。

- MIME Type Validation
- Extension Validation
- File Size Limit
- Storage
- Access Control
- Executable File禁止
- Malware対策

---

## 25. Security Test

MVPでは最低限、以下を確認する。

- Authentication Test
- Authorization Test
- IDOR / Broken Access Control Test
- Input Validation Test
- CSRF対策確認
- XSS対策確認
- SQL Injection対策確認

特にRoleおよび担当Employee Scopeに関するAuthorizationについてはFeature Testを重点的に実施する。
