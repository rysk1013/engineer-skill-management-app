# ユーザビリティ・アクセシビリティ

## 1. 目的

本ドキュメントでは、Engineer Skill Management App におけるユーザビリティおよびアクセシビリティに関する非機能要件を定義する。

利用者が迷わず、安全かつ効率的に操作できるUIを提供するとともに、Keyboard操作や支援技術等を考慮したアクセシブルなWeb Applicationを実現することを目的とする。

---

## 2. 基本方針

以下を基本方針とする。

- 一貫したUI / UXを提供する。
- 主要操作を迷わず実行できる状態を目指す。
- 入力Errorの原因と修正方法を理解できるようにする。
- Loading / Success / Empty / Error等の状態を明示する。
- Keyboardだけでも主要操作を実行可能にする。
- 色だけに情報を依存させない。
- Semantic HTMLを優先する。
- Accessibilityを後付けではなく設計・実装時から考慮する。
- WCAG 2.2 Level AAを設計・実装上の目標とする。
- Frontend上の表示制御をSecurity Boundaryとして扱わない。

---

## 3. 対象デバイス

MVPでは **Desktop First** とする。

| Device | Support方針 |
|---|---|
| Desktop | 主要Support |
| Tablet | 利用可能 |
| Smartphone | 基本操作可能 |

社員・Skillの検索、一覧表示、編集等は情報量が多いため、Desktopでの利用を主要なUse Caseとする。

SmartphoneについてDesktopと完全に同等の操作性をMVPでは要求しない。

ただし、画面が崩れて基本操作が不可能になる状態は避ける。

---

## 4. Responsive Design

Responsive Designを採用する。

以下のUIについて画面幅に応じて利用可能な状態を維持する。

- Navigation
- Form
- Table
- Search
- Filter
- Pagination
- Dialog
- Alert

固定Widthだけに依存したLayoutを避ける。

大量Columnを持つTableでは必要に応じて以下を利用可能とする。

- Horizontal Scroll
- 表示Column削減
- Responsive Column
- Detail画面への情報分離

SmartphoneでDesktop Tableを無理に完全再現することは要求しない。

---

## 5. Navigation

Application全体でNavigationの位置および操作方法を可能な限り統一する。

利用者が最低限以下を理解できる状態とする。

- 現在どの画面にいるか
- どの画面へ移動できるか
- 前の画面または上位画面へどう戻るか

Role / Permissionによって利用できない機能はNavigationから非表示にすることができる。

ただし、Navigationの非表示のみをAuthorizationとして扱わない。

Backend Authorizationを必須とする。

---

## 6. UIの一貫性

同じ意味を持つ操作について、画面ごとに異なるUI Patternを乱用しない。

以下について可能な限り共通化する。

- Button
- Input
- Select
- Checkbox
- Dialog
- Table
- Pagination
- Alert
- Toast
- Error表示
- Loading表示

同じActionには同じLabel、Icon、Interaction Patternを利用することを基本とする。

---

## 7. Form

Formでは以下を必須とする。

- Inputに対応するLabelを明示する。
- Required項目を識別可能にする。
- 入力Formatが分かりにくい場合は補足を表示する。
- Validation Errorを対象Field付近に表示する。
- Error Messageから修正内容を理解できるようにする。
- PlaceholderだけをLabelの代わりとして使用しない。

例:

```text id="ueo6ki"
最終利用年月 *

[ 2026-09 ]

実務経験がある場合は必須です。
```

---

## 8. Validation Error

Validation Errorでは、単に「入力値が不正」と表示するのではなく、可能な限り原因と修正方法を明示する。

避ける例:

```text id="4qev32"
入力値が不正です。
```

推奨例:

```text id="00pprq"
実務経験がある場合、
経験期間は1か月以上入力してください。
```

複数のValidation Errorが存在する場合、それぞれどのFieldに対応しているか識別可能にする。

Server-side Validation ErrorについてもFrontendで適切なFieldへ関連付けて表示できるようにする。

---

## 9. Application Error

Application Error発生時には可能な範囲で以下を利用者へ伝える。

- 何が起きたか
- 操作を再試行できるか
- 次に何をすればよいか

Productionでは以下を利用者へ表示しない。

- Stack Trace
- Exception Class
- SQL
- Server内部Path
- Secret
- Credential
- その他内部実装情報

予期しないErrorでは、必要に応じてRequest IDを表示可能な設計とする。

---

## 10. Loading State

Network Request等により処理待ちが発生する場合、Loading状態を利用者が認識できるようにする。

主な対象:

- 一覧取得
- 検索
- Filter
- 保存
- 削除
- Role変更
- Permission変更
- Assignment変更

例:

```text id="b94u60"
[ 保存中... ]
```

処理中であることが分からない状態を避ける。

---

## 11. 二重送信防止

保存・更新・削除等の状態変更処理では二重送信を防止する。

必要に応じて以下を利用する。

- Button Disable
- Loading State
- Request実行中の再操作防止

Frontendによる二重送信防止だけをData Integrity保証として扱わず、必要な整合性はBackend / Databaseでも保証する。

---

## 12. Success Feedback

利用者が操作成功を判断しにくい処理について、成功したことを確認できるFeedbackを提供する。

例:

```text id="cq9iqf"
スキル情報を更新しました。
```

Feedback方法は操作内容に応じて以下を使い分ける。

- Toast
- Alert
- Inline Message
- 画面状態の変更

すべての操作に不要なSuccess Messageを表示することは要求しない。

---

## 13. Empty State

Dataが存在しない場合、単なる空白画面を表示しない。

例:

```text id="ahmy9h"
登録されているスキルはありません。
```

検索結果が0件の場合:

```text id="bb3n2f"
条件に一致する社員が見つかりませんでした。
```

可能な場合は、利用者が次に実行可能なActionも分かるようにする。

---

## 14. UI State

主要な画面・Componentでは最低限以下の状態を考慮する。

```text id="8h81eu"
Loading

Success

Empty

Error

Disabled
```

一覧画面では概念的に以下の状態を考慮する。

```text id="57ulru"
Initial
   │
   ▼
Loading
   │
   ├── Success
   │      ├── Dataあり
   │      └── Empty
   │
   └── Error
```

UI Stateを実装時に場当たり的に追加するのではなく、設計時から考慮する。

---

## 15. Confirmation

取り消しが困難または影響の大きい操作についてConfirmationを設ける。

主な対象:

- Employee削除
- Permission解除
- 重要なRole変更
- Skill無効化
- Assignment解除

Confirmationでは可能な限り、何が変更・削除されるのかを理解できるようにする。

すべての操作へConfirmation Dialogを表示することは避ける。

---

## 16. Keyboard操作

主要機能はKeyboardだけでも操作可能とする。

最低限以下の標準的なKeyboard操作を阻害しない。

- `Tab`
- `Shift + Tab`
- `Enter`
- `Space`
- `Escape`

独自Keyboard ShortcutはMVPでは必須としない。

BrowserおよびOS標準のKeyboard操作を不用意に上書きしない。

---

## 17. Focus

Keyboard操作時に現在のFocus位置を視覚的に確認可能とする。

主な対象:

- Link
- Button
- Input
- Select
- Checkbox
- Dialog内操作
- その他Interactive Element

Focus Indicatorを理由なく削除しない。

以下のようにFocus表示だけを消す実装を避ける。

```css id="4h5ibd"
outline: none;
```

Custom Focus Styleを使用する場合は、十分に識別可能な表示を提供する。

---

## 18. Dialog / Modal

Dialog / ModalではFocus Managementを考慮する。

最低限以下を満たす。

- Dialog表示時に適切なElementへFocusを移動する。
- Keyboardで操作可能とする。
- Focusが不自然にDialog外へ移動しないようにする。
- Escapeで閉じる設計の場合は一貫して対応する。
- Dialog終了後は原則として呼び出し元ElementへFocusを戻す。

DialogのClose Buttonにも適切なAccessible Nameを設定する。

---

## 19. Semantic HTML

可能な限りNative HTML Elementを使用する。

主な例:

```html id="lwx8fn"
<button>
<a>
<label>
<input>
<select>
<table>
<nav>
<main>
```

`div` + `onClick`等でNative Button / Link相当の機能を不用意に再実装しない。

Semantic HTMLで表現可能な場合はSemantic HTMLを優先する。

---

## 20. ARIA

ARIAはSemantic HTMLだけでは十分に意味を表現できない場合に補助的に利用する。

不要なARIA属性を大量に追加しない。

以下を基本とする。

```text id="6ln5uq"
Semantic HTML
      ↓
不足する場合
      ↓
ARIA
```

ARIAを利用する場合は、Role / State / Accessible Name等が実際のUI挙動と一致するようにする。

---

## 21. 色

情報を色だけで表現しない。

例えばError / Success / Warningでは、色に加えて以下を組み合わせる。

- Text
- Icon
- Label
- Symbol

例:

```text id="yj55nx"
⚠ Error
保存に失敗しました。
```

```text id="w75e7b"
✓ Success
保存しました。
```

色を認識できない場合でも情報を理解できる状態を目指す。

---

## 22. Contrast

Text、Interactive Element、Focus Indicator等について十分なContrastを確保する。

WCAG 2.2 Level AAのContrast要件を設計・実装上の目標とする。

Design変更時にもContrastを考慮する。

---

## 23. Table

Employee / Skill等の一覧で使用するTableについてAccessibilityを考慮する。

最低限以下を実施する。

- Headerを明確にする。
- Column名を理解可能にする。
- 適切なTable構造を使用する。
- Sort状態を視覚的・意味的に表現する。
- Keyboardから主要Actionへアクセス可能にする。
- Row全体のMouse Clickだけに操作を依存させない。

大量DataについてはPaginationを利用する。

---

## 24. Search / Filter

Search / Filterでは最低限以下を利用者が認識可能にする。

- 現在の検索条件
- 現在のFilter条件
- 条件を解除する方法
- Loading状態
- 検索結果
- 0件状態

Filter適用後に何が変更されたか分からないUIを避ける。

---

## 25. PermissionによるUI制御

Role / Permissionによって利用できないActionについては、用途に応じて以下を使い分ける。

```text id="96iwn8"
非表示

または

Disabled + 理由表示
```

例えば、利用者に機能自体を知らせる必要がない場合は非表示とできる。

機能は存在するが現在操作できない理由を伝える必要がある場合はDisabled表示等を利用できる。

FrontendのPermission制御はUX改善を目的とする。

Security BoundaryはLaravel BackendのAuthorizationとする。

---

## 26. 共通UI Component

主要なUI Elementは可能な限り共通Componentとして管理する。

主な対象:

- Button
- Input
- Select
- Checkbox
- Dialog
- Table
- Pagination
- Alert
- Toast
- Form Error
- Loading Indicator

共通Componentによって以下を統一する。

- Design
- Interaction
- Keyboard操作
- Focus
- Accessibility
- Error表示

画面ごとに同じComponentを独自実装することを避ける。

---

## 27. WCAG

MVPでは **WCAG 2.2 Level AAを設計・実装上の目標** とする。

```text id="3ev3vs"
WCAG 2.2 Level AA
        ↓
設計・実装上の目標
```

MVPでは正式なAccessibility Auditや第三者認証による完全準拠の保証までは要求しない。

ただし、既知の重大なAccessibility問題を意図的に放置しない。

---

## 28. Accessibility確認

MVPでは複数の方法を組み合わせてAccessibilityを確認する。

### Static Check

ESLint Plugin等による静的Checkを利用可能とする。

### Automated Tool

以下のようなToolを利用可能とする。

- Lighthouse
- axe
- Browser DevTools

### Manual Check

主要User FlowについてKeyboard操作による手動確認を行う。

最低限以下を確認する。

- Keyboardだけで主要操作を実行できる。
- Focus位置を確認できる。
- Dialogを操作できる。
- Form Errorを理解できる。
- 重要な情報が色だけに依存していない。

---

## 29. Screen Reader

MVPでは全画面を対象とした詳細なScreen Reader Testを必須とはしない。

ただしSemantic HTML、Accessible Name、Form Label、ARIA等を適切に使用し、支援技術が利用可能な構造を維持する。

将来的にAccessibility要件が高まった場合はScreen Readerによる正式なTestを追加する。

---

## 30. Accessibility Regression

共通UI Component変更時はAccessibility Regressionに注意する。

特に以下の変更ではKeyboard / Focus等を確認する。

- Dialog
- Navigation
- Form Component
- Select / Combobox
- Table
- Pagination

Automated Accessibility E2E TestはMVPでは必須としないが、将来導入を検討する。

---

## 31. UsabilityとSecurity

Usability向上のためにSecurity要件を弱めない。

例えば、

```text id="4p09d1"
FrontendでButton非表示
        │
        └── UX

Backend Authorization
        │
        └── Security
```

と責務を分離する。

Confirmation DialogやButton Disable等もServer-side Data Integrity / Authorizationの代替とはしない。
