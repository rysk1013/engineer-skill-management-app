# 国際化・日時

## 1. 目的

本ドキュメントでは、Engineer Skill Management App における言語、Locale、文字コード、Timezone、日時表現および将来的な国際化に関する非機能要件を定義する。

日時・地域情報をApplication全体で一貫して扱い、環境差異やTimezone境界による不具合を防止するとともに、将来的な多言語化や海外利用を不必要に妨げない設計を維持することを目的とする。

---

## 2. 基本方針

以下を基本方針とする。

- MVPのUI言語は日本語とする。
- 標準Localeは `ja-JP` とする。
- 文字コードはUTF-8へ統一する。
- MVPでは多言語切替機能を必須としない。
- 将来のInternationalizationを不必要に妨げる実装を避ける。
- Instantを表す日時はUTCを内部基準とする。
- APIのDateTimeはISO 8601形式を使用する。
- MVPの表示Timezoneは `Asia/Tokyo` とする。
- Date / DateTime / YearMonthを明確に区別する。
- Server / ContainerのLocal TimezoneへBusiness Logicを依存させない。
- Calendar Dateを基準とするBusiness Ruleでは `Asia/Tokyo` を使用する。

---

## 3. 対応言語

MVPの正式対応言語は **日本語のみ** とする。

```text
MVP
└── Japanese
    └── ja-JP
```

MVPでは以下を必須としない。

- English UI
- Language Selector
- Translation Management System
- UserごとのLanguage設定

将来的に利用者や利用地域が拡大した場合、多言語化を検討する。

---

## 4. Locale

MVPの標準Localeは以下とする。

```text
ja-JP
```

Localeは主に以下の表示・表現に利用する。

- 日付
- 時刻
- 曜日
- 月
- 数値
- UI Message
- その他Locale依存の表示

LocaleとTimezoneは別の概念として扱う。

```text
Locale
  └── ja-JP

Timezone
  └── Asia/Tokyo
```

LocaleからTimezoneを暗黙的に決定しない。

---

## 5. Character Encoding

文字コードは **UTF-8** を基本とする。

主な対象:

- HTML
- HTTP
- JSON
- Source Code
- OpenAPI
- Database
- Log
- Configuration
- 将来的なCSV等のData Exchange

System間で不要な文字コード変換を発生させない。

---

## 6. Unicode

社員名、Department名、Skill名等のText DataについてUnicodeを扱えることを前提とする。

例:

```text
山田 太郎

髙橋

JavaScript

C#

.NET

Node.js
```

文字列Length Validationでは、要件に応じて文字数とByte数を混同しないようにする。

日本語等のMulti-byte Characterを扱うことを前提として設計する。

---

## 7. Timezone基本方針

Instantを表す日時について、Application内部ではUTCを基本とする。

```text
Browser
   │
   │ Asia/Tokyoで表示
   ▼
Next.js
   │
   ▼
Laravel
   │
   │ UTC
   ▼
PostgreSQL
```

利用者向け表示時に `Asia/Tokyo` へ変換する。

---

## 8. MVP表示Timezone

MVPの標準表示Timezoneは以下とする。

```text
Asia/Tokyo
```

利用者ごとのTimezone設定はMVPでは持たない。

以下のようなProfile設定はMVP対象外とする。

```text
User
└── timezone
```

将来的に海外利用が必要になった場合、User単位またはOrganization単位のTimezone対応を検討する。

---

## 9. Timezone識別

Timezoneを扱う場合は原則としてIANA Time Zone IDを使用する。

例:

```text
Asia/Tokyo
```

Timezoneを単純な固定Offsetだけで表現することを基本としない。

例えば以下だけに依存した設計を避ける。

```text
UTC+09:00
```

IANA Time Zone IDを利用することで、将来的なDST対応や海外Timezone対応を容易にする。

---

## 10. Server / Container Timezone

Server、Container、Hosting EnvironmentのLocal TimezoneへBusiness Logicを依存させない。

以下のような暗黙的な処理を避ける。

```text
ServerがJSTだから
now()をJSTとして扱う
```

Application上で扱っている値が以下のどちらなのかを明確にする。

```text
UTC Instant

または

Asia/Tokyo Calendar Date / Time
```

Environment変更によってBusiness Logicの結果が変化しないようにする。

---

## 11. DateTime

時刻まで意味を持つ値はDateTimeとして扱う。

主な例:

- `created_at`
- `updated_at`
- Login日時
- Audit Log発生日時
- Security Event発生日時
- その他Event発生日時

DateTimeはInstantとして扱い、内部ではUTCを基本とする。

APIではTimezone情報を含むISO 8601形式を利用する。

例:

```text
2026-09-03T15:00:00Z
```

このInstantを `Asia/Tokyo` で表示すると以下となる。

```text
2026/09/04 00:00
```

---

## 12. Date

時刻を持たない「日付そのもの」はDateとして扱う。

例:

```text
2026-09-30
```

Dateは特定のInstantを表す値ではなく、Calendar Dateとして扱う。

例えば退職日が、

```text
2026-09-30
```

の場合、これを以下のように解釈しない。

```text
2026-09-30 00:00 UTC
```

不要なTimezone変換によってCalendar Dateが変化する状態を避ける。

---

## 13. YearMonth

年月だけに意味を持つ値は **YearMonth** として扱う。

主な対象:

- 最終利用年月
- その他年月単位のDomain Value

以下を明確に区別する。

```text
DateTime
2026-09-04T12:30:00Z

Date
2026-09-04

YearMonth
2026-09
```

YearMonthをDomain上、「月初日のDate」等として擬似的に表現しない。

具体的なDatabase保存方式は `Date・Time設計.md` で定義する。

---

## 14. API DateTime形式

APIでInstantを表すDateTimeにはISO 8601形式を使用する。

MVPではUTC `Z` 表記を基本とする。

```text
2026-09-04T01:30:00Z
```

Timezone情報を持たない以下のようなDateTime形式は原則使用しない。

```text
2026-09-04T10:30:00
```

API Contractで必要となる場合はOffset付きISO 8601形式も利用可能とする。

例:

```text
2026-09-04T10:30:00+09:00
```

---

## 15. API Date形式

Dateは以下の形式とする。

```text
YYYY-MM-DD
```

例:

```text
2026-09-04
```

OpenAPI SchemaでDateTimeと区別する。

---

## 16. API YearMonth形式

YearMonthは以下の形式とする。

```text
YYYY-MM
```

例:

```text
2026-09
```

OpenAPI上でもDate / DateTimeとは異なるDomain Valueであることを明示する。

---

## 17. UI DateTime表示

日本語UIではDateTimeを利用者が読みやすい形式へ変換する。

基本形式:

```text
YYYY/MM/DD HH:mm
```

例:

```text
2026/09/04 10:30
```

画面の文脈によっては自然な日本語表記を利用可能とする。

例:

```text
2026年9月4日 10:30
```

API FormatとUI表示Formatは分離する。

```text
API
2026-09-04T01:30:00Z
        │
        ▼
Frontend表示
2026/09/04 10:30
```

---

## 18. UI Date表示

日本語UIのDateは以下を基本形式とする。

```text
YYYY/MM/DD
```

例:

```text
2026/09/04
```

画面上の文脈に応じて以下も利用可能とする。

```text
2026年9月4日
```

同一画面内で不必要に複数のDate Formatを混在させない。

---

## 19. UI YearMonth表示

YearMonthは以下を基本形式とする。

```text
YYYY/MM
```

例:

```text
2026/09
```

必要に応じて以下のような表示も利用可能とする。

```text
2026年9月
```

Domain上の値そのものはYearMonthとして維持する。

---

## 20. 時刻表示

MVPでは時刻を **24時間表記** とする。

例:

```text
09:30

18:45
```

AM / PM形式を標準表示としない。

管理Applicationとして日時の曖昧性を減らすことを優先する。

---

## 21. 日付・年月入力

Date / YearMonth入力では可能な限り適切なUI Componentを利用する。

例:

```text
Date
  ↓
Date Picker
```

```text
YearMonth
  ↓
Month Picker
```

利用者へFormatを手入力させる必要がある場合は、期待するFormatを明示する。

例:

```text
YYYY-MM
```

曖昧な日付入力を避ける。

---

## 22. 現在日時

「現在日時」を意味する値を扱う場合、Application内部ではUTCのInstantとして扱う。

```text
Current Instant
      ↓
UTC
```

一方で、「今日」のようなCalendar上の概念が必要なBusiness Ruleでは `Asia/Tokyo` へ変換したうえで判定する。

```text
UTC Instant
     │
     ▼
Asia/Tokyo
     │
     ▼
今日のCalendar Date
```

UTCのDateと日本国内業務上の「今日」を同一視しない。

---

## 23. 日付境界

Calendar Dateを基準とするBusiness Ruleでは `Asia/Tokyo` を基準とする。

主な対象:

- 退職日
- 退職後3年間保持の判定
- 「今日」を基準とする処理
- 月単位・年単位のBusiness Rule

例えば日本では9月4日でもUTCでは9月3日となる時間帯が存在する。

```text
Asia/Tokyo
2026-09-04

UTC
2026-09-03
```

Server TimezoneやUTCの日付だけを利用してBusiness Ruleの判定結果がずれないようにする。

---

## 24. 退職社員保持期間

退職Employeeの3年間保持等、Calendar Dateベースの保持期間判定では `Asia/Tokyo` をBusiness Timezoneとする。

概念的には以下のように扱う。

```text
退職日
  ↓
Calendar Date

+ 3 years
  ↓
Asia/Tokyo基準で判定
```

日時のInstant計算として扱わない。

具体的な削除処理・Schedule設計については関連するDomain / Application設計で定義する。

---

## 25. DST

MVPの標準Timezoneである `Asia/Tokyo` では現在DSTを利用しない。

ただし将来の海外利用を考慮し、Timezone処理を固定Offsetだけに依存させない。

```text
Asia/Tokyo
```

等のIANA Time Zone IDを利用する。

将来的にDSTを採用する地域をSupportした場合でも、Timezone Library等を利用して適切に変換可能な設計を維持する。

---

## 26. Databaseとの責務分離

Database上の具体的な型および保存方法は `技術選定/データベース/Date・Time設計.md` で定義する。

本ドキュメントでは、Systemとして以下を区別することを要求する。

```text
DateTime

Date

YearMonth
```

責務は以下のように分離する。

```text
非機能要件
国際化・日時.md
       │
       └── 何を保証するか


技術設計
Date・Time設計.md
       │
       └── PostgreSQL等でどう実現するか
```

---

## 27. 内部値と表示Label

Role、Status、Enum等の内部識別子を日本語表示Labelそのもので保存することを避ける。

例:

```text
Domain / Database
ACTIVE

        ↓

Japanese UI
在籍
```

内部識別子はLocale非依存とする。

UI表示時にLocaleに応じたLabelへ変換可能な構造を維持する。

---

## 28. Error CodeとLocalization

API ErrorはMachine-readableなError Codeを持つ既存方針を維持する。

例:

```json
{
  "error": {
    "code": "EMPLOYEE_NOT_FOUND",
    "message": "Employee was not found."
  }
}
```

BFF / FrontendがError Message本文そのものをApplication Logicの判定条件として利用することを避ける。

```text
Error Code
    ↓
Application識別

Message
    ↓
利用者向け表示
```

これにより将来的なLocalizationを容易にする。

---

## 29. UI Message

MVPでは日本語UIを基本とする。

UI MessageをSource Codeへ記述すること自体をMVPでは禁止しない。

ただし、同一Messageを大量に重複定義することや、Message本文をBusiness Logic上のIdentifierとして利用することを避ける。

将来的な多言語化が必要になった場合、i18n Resourceへ移行可能な構造を維持する。

---

## 30. 日本語検索・Sorting

MVPでは高度な日本語固有のNormalization / Sortingを必須としない。

以下はMVPで保証対象外とする。

- 読み仮名を考慮した五十音順
- 漢字の読みを考慮したSorting
- ひらがな / カタカナの完全同一視
- 全角 / 半角の完全同一視
- 高度な日本語形態素解析
- Typo補正

通常の社員・Skill検索として必要な範囲を実装する。

高度な日本語検索要件が発生した場合は検索機能のRequirementとして別途定義する。

---

## 31. Locale依存Formatting

Date / Time / Number等のFormatting Logicを画面ごとに無秩序に実装しない。

Frontend側では共通Utility / Formatter等によって可能な限り統一する。

例:

```text
formatDate()

formatDateTime()

formatYearMonth()
```

具体的なImplementation名はArchitecture / Frontend設計時に決定する。

---

## 32. Test

日時に関する重要なBusiness RuleではTimezone境界を含むTestを実施する。

特に以下をTest対象とする。

- UTC → Asia/Tokyo変換
- 日付境界
- 月境界
- 年境界
- 退職後3年間保持の判定
- Date / DateTimeの混同防止
- YearMonth Validation

必要に応じてCurrent TimeをTestから制御可能な設計とする。

System Clockへ直接強く依存したDomain Testを避ける。
