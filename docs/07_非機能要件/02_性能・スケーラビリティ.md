# 性能・スケーラビリティ

## 1. 目的

本ドキュメントでは、Engineer Skill Management App における性能およびスケーラビリティに関する非機能要件を定義する。

MVPでは大規模トラフィックを前提とせず、以下を基本方針とする。

- 通常操作をストレスなく利用できること
- データ量の増加によって急激な性能劣化が発生しないこと
- 不要な複雑性を導入せず、必要になった段階でスケールできること
- 将来的な水平スケールを妨げない設計とすること

---

## 2. 性能目標

### 2.1 画面表示

主要画面について、以下を目標とする。

| 対象 | 目標 |
|---|---:|
| 主要画面 | 2秒以内 |
| 初回表示・集計等の比較的重い画面 | 3秒以内 |

ネットワーク環境や外部サービスによる遅延については、アプリケーション単体の性能評価とは分けて扱う。

### 2.2 APIレスポンスタイム

Laravel APIについて、以下を目標とする。

| API | 目標 |
|---|---:|
| 通常CRUD | 500ms以内 |
| 検索・一覧 | 1秒以内 |
| 集計 | 1秒以内 |

性能評価は原則として **p95（95パーセンタイル）** を使用する。

平均値だけでは判断せず、一部リクエストの著しい性能劣化も検出できるようにする。

### 2.3 性能目標の位置付け

上記のレスポンスタイムはSLAとして保証する値ではなく、開発・性能改善・運用上の目標値とする。

---

## 3. 想定規模

MVPの設計および性能検証では、以下を想定規模とする。

| データ・利用者 | 想定規模 |
|---|---:|
| 在籍社員 | 〜1,000人 |
| Skill Master | 〜5,000件 |
| EmployeeSkill | 〜100,000件 |
| アプリケーション利用者 | 〜100人 |
| 同時利用者 | 〜20人 |
| 瞬間的なAPIリクエスト | 数十req/s程度 |

これらはシステム上のハードリミットではなく、MVPにおける設計・性能検証の基準値とする。

想定規模を大きく超えることが見込まれる場合は、性能要件を再評価する。

---

## 4. 検索性能

社員、スキル等の検索・絞り込みについては **1秒以内** のレスポンスを目標とする。

主な対象は以下とする。

- 社員一覧
- 社員検索
- スキル一覧
- スキル検索
- スキルによる社員検索
- Departmentによる絞り込み
- その他ダッシュボード等の集計

検索条件やSort条件を考慮して適切なIndexを設計する。

---

## 5. Pagination

一覧APIでは原則としてPaginationを使用する。

### MVP方針

- Offset Paginationを採用する。
- 1ページあたり **20〜50件程度** を基本とする。
- APIごとに適切なデフォルト件数を設定する。
- API側で最大取得件数を制限する。
- クライアントから無制限な件数を要求できないようにする。

大量データによってOffset Paginationの性能が問題となった場合は、Cursor Paginationへの移行を検討する。

---

## 6. Database Query

### 6.1 基本方針

以下を原則とする。

- 不要な全件取得を避ける。
- N+1 Queryを発生させない。
- 必要なColumnのみ取得する。
- 不要なRelation取得を避ける。
- 大量データをApplication Memoryへ読み込まない。
- DBで実行すべきFilter / Sort / AggregateをApplication側で行わない。

`SELECT *` は必要性が明確な場合を除いて避ける。

### 6.2 Index

以下をIndex設計の対象とする。

- Foreign Key
- 検索条件
- Sort条件
- JOIN条件
- UNIQUE制約
- 高頻度で使用される複合検索条件

Indexは闇雲に追加せず、実際のQueryと実行計画を確認したうえで設計する。

### 6.3 Query分析

性能問題の調査では必要に応じて以下を使用する。

- `EXPLAIN`
- `EXPLAIN ANALYZE`

Slow Queryを特定できる状態を維持する。

---

## 7. CQRS Read Model

一覧、検索、集計などのRead処理では、Domain Aggregateの完全な復元を必須としない。

Lightweight CQRSの方針に従い、以下を利用する。

- Query Service
- Read Model
- 専用DTO

例えば社員検索では `EmployeeSearchQueryService` のようなQuery Serviceを利用できる。

Read処理では表示に必要なデータを効率的に取得し、一覧表示のために大量のAggregateを復元することを避ける。

---

## 8. Timeout

BFF → Laravel API間の通信には明示的なTimeoutを設定する。

以下を原則とする。

- 無制限にレスポンスを待機しない。
- 長時間同期処理を可能な限り作らない。
- Timeout発生時は適切なエラーとして処理する。
- Timeout値は実装・インフラ構成決定時に具体値を設定する。

外部サービスとの通信についても同様にTimeoutを設定する。

---

## 9. Cache

MVPではCacheを必須としない。

性能問題が発生した場合、以下の順序を基本として改善する。

1. Queryの確認
2. N+1の確認
3. Indexの確認
4. Query / Read Modelの最適化
5. 必要に応じてCache導入

最初からCacheによって非効率なQueryを隠蔽しない。

Redis等のCache Storeは、必要性が確認された段階で導入を検討する。

---

## 10. 非同期処理

MVPではQueue等による非同期処理を必須としない。

同期処理ではレスポンスタイムを維持できない処理が発生した場合、Queue化を検討する。

対象例:

- 大量データ処理
- CSV等のExport
- 大量通知
- 外部サービス連携
- 長時間実行される集計処理

---

## 11. Applicationのスケーラビリティ

Next.jsおよびLaravel Applicationは、将来的な水平スケールを妨げない設計とする。

### 基本方針

- Application Server固有のローカル状態へ依存しない。
- 永続データはPostgreSQL等の外部Storeで管理する。
- Session等の共有が必要なデータをApplication Instance内だけに保持しない。
- 複数Application Instanceで動作可能な設計を維持する。

MVPでは複数Instanceによる水平スケールを必須としない。

---

## 12. Databaseのスケーラビリティ

MVPでは単一PostgreSQL構成を基本とする。

まず以下による性能改善を優先する。

1. Query最適化
2. Index最適化
3. Schema見直し
4. DB Instanceの垂直スケール

以下はMVPでは必須としない。

- Read Replica
- Database Cluster
- Sharding
- Database水平分割

必要性が発生した段階で導入を検討する。

---

## 13. 垂直スケール

MVP初期では、必要に応じて以下のResource増強による垂直スケールを許容する。

- CPU
- Memory
- Database Instance Size

複雑な分散構成を導入する前に、垂直スケールで十分対応可能かを確認する。

---

## 14. 性能劣化防止

開発時には以下を意識する。

- 適切なDB Index
- N+1 Query防止
- 不要なEager Loading防止
- 不要な全件取得防止
- Pagination利用
- Query実行計画確認
- 大量データのMemory展開防止
- Read Model / Query Serviceの活用
- Domain Aggregateの不要な大量復元防止

性能最適化は推測だけで行わず、計測結果を基に実施する。
