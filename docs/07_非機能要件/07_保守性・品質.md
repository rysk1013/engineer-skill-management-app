# 保守性・品質

## 1. 目的

本ドキュメントでは、Engineer Skill Management App における保守性およびソフトウェア品質に関する非機能要件を定義する。

継続的な機能追加や仕様変更に対して、安全かつ効率的に変更できる状態を維持し、Regression、Architecture劣化、Security問題および不要な複雑化を防止することを目的とする。

---

## 2. 基本方針

以下を基本方針とする。

- Coding Standardを統一する。
- Formatter / Linterを自動化する。
- Static Analysisを実施する。
- Complexityを継続的に監視する。
- Automated Testを整備する。
- CIによるQuality Gateを設ける。
- Architecture Ruleを明文化する。
- Dependencyを継続的に管理する。
- 設計上重要な意思決定を記録する。
- Technical Debtを可視化する。
- 大規模なRefactorを避け、継続的に改善する。
- 品質指標の数値だけを目的化しない。

---

## 3. Frontend品質

Next.js / TypeScriptでは以下を基本とする。

- TypeScriptを使用する。
- TypeScript `strict` Modeを有効にする。
- ESLintを使用する。
- Prettierを使用する。
- Type ErrorをCIで検出する。
- 未使用変数・未使用Import等を検出する。
- React Hooks Ruleを遵守する。
- `any` の乱用を避ける。
- Server Component / Client Componentの責務を明確にする。
- Client Componentを必要最小限にする。

---

## 4. Backend品質

Laravel / PHPでは以下を基本とする。

- PSR-12等のCoding Standardに準拠する。
- Laravel Pintを使用する。
- PHPStan / Larastanを使用する。
- Static AnalysisをCIで実行する。
- PHPMD等を利用してComplexity / Code Smellを確認可能にする。
- Controllerを薄く保つ。
- Eloquent ModelへBusiness Logicを集中させない。
- Eloquent Model Event / ObserverへDomain Ruleを記述しない。
- Domain LayerをFramework非依存とする。

---

## 5. Formatter

FormattingはDeveloper個人の手作業に依存させず、自動化する。

### Frontend

```text id="92wzc7"
Prettier
```

### Backend

```text id="jy92r1"
Laravel Pint
```

CIではFormatting違反を検出する。

Formatting差分が残った状態でMergeしない。

---

## 6. Lint

FrontendではESLintを利用する。

最低限以下を検出する。

- Syntax Error
- 未使用Code
- React Hooks Rule違反
- 不適切なCoding Pattern
- その他設定したProject Rule違反

Lint Errorが存在する場合はCIを失敗させる。

---

## 7. Static Analysis

Static AnalysisをMVPから必須とする。

### Frontend

以下を使用する。

```text id="jfwcdg"
TypeScript Typecheck
ESLint
```

### Backend

以下を使用する。

```text id="57gb6q"
PHPStan / Larastan
```

Static Analysis Errorが存在する場合はCIを失敗させる。

---

## 8. Complexity

Code Complexityを継続的に確認する。

主な確認対象:

- Cyclomatic Complexity
- Method Length
- Class Size
- Nesting
- Parameter数
- Responsibility過多

特に以下が巨大化しないよう注意する。

- Application Handler
- Domain Service
- Controller
- Query Service
- React Component

Complexityの数値のみで機械的に設計を判断せず、異常に複雑な箇所を発見するための指標として利用する。

BackendではPHPMD等の利用を推奨する。

---

## 9. Test方針

MVPでは以下のTest Layerを使用する。

```text id="18oxhg"
E2E Test
     │
Feature / API Test
     │
Integration Test
     │
Unit Test
```

各Test Layerの責務を明確にし、同じ内容を不必要に重複してTestしない。

---

## 10. Unit Test

Unit Testでは主にApplication Infrastructureへ依存しないLogicを検証する。

主な対象:

- Domain Model
- Value Object
- Domain Policy
- Domain Service
- Domain Invariant
- Application Logicのうち単体検証可能なもの

特に重要なDomain RuleについてUnit Testを必須とする。

---

## 11. Integration Test

Integration Testでは複数Component間の連携を確認する。

主な対象:

- Repository実装
- PostgreSQLとの連携
- Mapper
- Infrastructure Adapter
- Database Constraint
- Transaction
- Query Service

Database固有の挙動を検証する場合は、可能な限りProductionと同じPostgreSQLを使用する。

---

## 12. Feature / API Test

Feature / API TestではHTTP Boundaryを含むApplication動作を検証する。

主な対象:

- API Endpoint
- Authentication
- Authorization
- Request Validation
- HTTP Status
- Error Response
- Transaction
- IDOR / Broken Access Control対策

Authorizationについては特に重点的にTestする。

---

## 13. E2E Test

E2E Testは主要なUser Flowを対象とする。

すべての画面・操作をE2Eで網羅することはMVPでは要求しない。

主な対象例:

```text id="9fdc44"
Login
  ↓
Employee検索
  ↓
Employee詳細
  ↓
Skill登録 / 更新
```

必要に応じて以下も対象とする。

- Role変更
- Permission変更
- Assignment変更

E2E ToolとしてPlaywright等を利用可能とする。

---

## 14. 重要Test対象

以下についてはCoverage値に関係なくTestを必須とする。

### EmployeeSkill

- 実務未経験の場合Level 1のみ選択可能
- 実務経験ありの場合経験期間1か月以上
- 実務経験ありの場合最終利用年月必須
- 重複登録防止

### Permission

- RoleによるAuthorization
- 権限管理可能AdministratorのみPermission変更可能
- 権限管理可能Administratorを最低1人維持
- 同時更新時にもInvariantを維持

### Assignment

- Sub Managerは担当Employeeのみ操作可能
- Team Leaderは担当Employeeのみ閲覧可能
- 担当外Employeeへのアクセス禁止

### Security

- Authentication
- Authorization
- IDOR / Broken Access Control
- Request Validation

### Database

- UNIQUE Constraint
- CHECK Constraint
- Transaction
- 必要なConcurrency Control

---

## 15. Test Coverage

Test Coverageは品質状態を把握するための補助指標として使用する。

MVPでは以下を目標とする。

| 対象 | Coverage目標 |
|---|---:|
| Backend | 80% |
| Frontend | 70% |

Coverage目標は原則としてLine Coverageを基準とし、利用するToolで取得可能な指標に応じてBranch Coverage等も参考とする。

Coverage目標を達成すること自体を最終目的としない。

```text id="v9qf0h"
Coverage 80%
    ≠
品質保証
```

重要なDomain Rule、AuthorizationおよびSecurity LogicについてはCoverage値に関係なくTestを必須とする。

## 17. Quality Gate

以下のいずれかが失敗した場合は原則としてMergeを禁止する。

- Lint
- Format Check
- Typecheck
- Static Analysis
- Automated Test
- Production Build
- OpenAPI Validation

```text id="2pp10c"
Pull Request
     │
     ▼
     CI
     │
     ├── Lint
     ├── Format
     ├── Static Analysis
     ├── Test
     ├── Build
     └── OpenAPI Validation
              │
              ▼
          All Success
              │
              ▼
            Merge
```

CI Errorを無視してMergeすることを通常運用としない。

## 18. Architecture Rule

Backendでは以下の依存方向を基本とする。

```text id="sk86fp"
Presentation
      │
      ▼
Application
      │
      ▼
Domain
```

InfrastructureはApplication / Domainで定義されたInterfaceを実装する。

Domain Layerは以下へ依存しない。

- Laravel
- Eloquent
- HTTP
- Database
- Infrastructure Service

---

## 19. Architecture禁止事項

以下を原則禁止する。

- Domain → Laravel依存
- Domain → Eloquent依存
- Domain → HTTP依存
- Domain → Database依存
- ControllerへのBusiness Logic記述
- Eloquent Model Event / ObserverへのBusiness Rule記述
- Generic SetterによるDomain状態変更
- RepositoryからEloquent Modelを外部へ公開
- Read処理で不要なAggregateを大量復元
- PresentationからDatabaseへ直接アクセス

Architecture上の例外が必要な場合は、理由および影響範囲を明確にする。

---

## 20. Architecture Test

Architecture Ruleを自動検証するArchitecture TestはMVPでは必須としない。

将来的に以下のようなRuleの自動検証を検討する。

- Domain NamespaceからLaravelへの依存禁止
- DomainからEloquentへの依存禁止
- Layer間依存方向
- Infrastructureへの不正依存

Architecture劣化が問題となる前に導入を検討する。

---

## 21. Code Review

Pull Requestは原則Code Reviewを必須とする。

主なReview観点:

- Requirementを満たしているか
- Acceptance Criteriaを満たしているか
- Domain Ruleを壊していないか
- Architecture Ruleを守っているか
- Authorization漏れがないか
- Security上の問題がないか
- 必要なTestが存在するか
- Database Migrationが安全か
- Performance問題がないか
- 不要な複雑性がないか
- Documentation更新が必要ではないか

---

## 22. Pull Request

Pull Requestは可能な限り小さく保つ。

以下を基本とする。

- 1 PR = 1目的
- 無関係なRefactorを混在させない。
- 大量変更は可能な範囲で分割する。
- Breaking Changeを明示する。
- Database Migrationを含む場合は影響範囲を明示する。
- Reviewerが理解可能な大きさを維持する。

---

## 23. Dependency管理

以下を継続的に管理する。

- npm / JavaScript Package
- Composer Package
- Docker Base Image
- GitHub Actions
- OS Package

Dependabot等のDependency管理機能を利用する。

Updateは以下を区別して扱う。

```text id="vmhh0v"
Security Update

Patch / Minor Update

Major Update
```

Critical / High SeverityのSecurity Updateは優先して対応する。

Major Version UpdateはBreaking Changeを確認したうえで実施する。

---

## 24. Version管理

Development / CI / Production間の再現性を高めるため、主要RuntimeおよびDependencyのVersionを明示する。

対象例:

- Node.js
- PHP
- PostgreSQL
- Composer
- npm / pnpm等
- Docker Base Image

Lock FileをGit Repositoryで管理する。

---

## 25. ADR

重要なArchitecture DecisionについてADR（Architecture Decision Record）を作成する。

例:

```text id="qgikz6"
docs
└── adr
    ├── 0001-nextjs-bff.md
    ├── 0002-laravel-backend.md
    ├── 0003-clean-architecture.md
    └── 0004-lightweight-cqrs.md
```

ADRでは最低限以下を記録する。

- Context
- Decision
- Reason
- Alternatives
- Consequences

単に「何を採用したか」だけではなく、「なぜその判断をしたか」を残す。

軽微な実装判断についてADRを作成する必要はない。

---

## 26. Technical Debt

Technical Debtを完全に排除することは目標としない。

必要なTechnical Debtは明示的に管理する。

以下を基本とする。

- TODO Commentだけで長期間放置しない。
- 必要に応じてIssue / Backlogへ登録する。
- Debtが発生した理由を記録する。
- 優先度を設定する。
- 定期的に見直す。

意図的な妥協と偶発的な品質劣化を区別できる状態を維持する。

---

## 27. Refactoring

大規模な一括Refactorより、継続的な小規模Refactorを優先する。

以下を基本とする。

```text id="z3x85n"
Small Change
    ↓
Test
    ↓
Review
    ↓
Merge
    ↓
Next Improvement
```

Refactorと機能変更を可能な限り分離する。

---

## 28. Documentation

実装変更によって設計・仕様が変更される場合、関連Documentationも更新する。

主な対象:

- 要件定義
- API仕様
- OpenAPI
- Database設計
- Architecture
- ADR
- 非機能要件
- 運用手順

CodeとDocumentationの不一致を長期間放置しない。

---

## 29. Definition of Done

User Story / Taskは、原則として以下を満たした状態をDoneとする。

```text id="nbw7kt"
Implementation
     │
     ▼
Automated Test
     │
     ▼
Lint / Format
     │
     ▼
Static Analysis
     │
     ▼
CI Success
     │
     ▼
Code Review
     │
     ▼
必要なDocumentation更新
     │
     ▼
Done
```

具体的には以下を確認する。

- Acceptance Criteriaを満たしている。
- Implementationが完了している。
- 必要なAutomated Testが存在する。
- Testが成功している。
- Lint / Format Checkが成功している。
- Static Analysisが成功している。
- Production Buildが成功している。
- 必要なCode Reviewが完了している。
- 必要なDocumentationが更新されている。
