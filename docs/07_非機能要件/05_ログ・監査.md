# ログ・監査

## 1. 目的

本ドキュメントでは、Engineer Skill Management App におけるログおよび監査に関する非機能要件を定義する。

ログは、障害調査、性能調査、セキュリティ監視および重要操作の追跡を可能にすることを目的とする。

特に、通常のApplication Logと、重要な業務操作を記録するAudit Logを明確に分離する。

---

## 2. 基本方針

以下を基本方針とする。

- 障害調査に必要な情報を記録する。
- Security Eventを追跡可能にする。
- 重要な業務操作について「誰が・いつ・何をしたか」を追跡可能にする。
- SecretやCredentialをログへ記録しない。
- 個人情報を必要以上にログへ記録しない。
- Structured Loggingを基本とする。
- Request IDによりBFFとBackend間の処理を追跡可能にする。
- Audit Logは通常のApplication Logと分離する。
- Audit Logは原則Append Onlyとする。

---

## 3. ログ分類

MVPでは以下の4種類のログを扱う。

| 種類 | 主目的 |
|---|---|
| Application Log | Application動作・障害調査 |
| Access Log | HTTP Accessの確認 |
| Security Log | Authentication / Authorization等のSecurity Event確認 |
| Audit Log | 重要な業務操作の追跡 |

Application LogとAudit Logは目的および保持方法を分離する。

```text
Application Log
    │
    └── なぜ問題が発生したか？

Audit Log
    │
    └── 誰が、いつ、何をしたか？
```

---

## 4. Application Log

Next.jsおよびLaravelのServer-side処理について、障害調査に必要な情報を記録する。

主な記録対象:

- Application Error
- Exception
- Database接続エラー
- Timeout
- 外部サービス通信エラー
- 想定外のApplication状態
- Background Jobエラー（将来導入時）

### 4.1 Log Level

Productionでは主に以下を使用する。

- `ERROR`
- `WARN`
- `INFO`

`DEBUG` LogはProductionで常時大量出力しない。

障害調査等で一時的に有効化する場合は、出力内容に機密情報が含まれないことを確認する。

---

## 5. Access Log

HTTP Accessについて最低限以下を記録可能とする。

- Timestamp
- HTTP Method
- Request Path
- HTTP Status Code
- Response Time
- Request ID

Query ParameterやRequest Bodyを無条件に記録しない。

特に機密情報や個人情報が含まれる可能性のあるRequestについて、Request全体をそのまま保存しない。

---

## 6. Security Log

Security上重要なEventをSecurity Logとして記録する。

主な対象:

- Login成功
- Login失敗
- Logout
- Authentication失敗
- Authorization失敗
- Rate Limit超過
- 異常なRequest
- Security関連Error

Security LogはAudit Logとは分離する。

通常のAuthentication / Authorization失敗によってAudit Logが大量に生成されることを避ける。

---

## 7. Structured Logging

Application Log、Access Log、Security Logは可能な限りJSON等のStructured Loggingを使用する。

概念例:

```json
{
  "timestamp": "2026-08-30T01:30:00Z",
  "level": "ERROR",
  "service": "backend",
  "request_id": "01...",
  "message": "Failed to update employee skill"
}
```

構造化することで以下を容易にする。

- Log検索
- Filtering
- Aggregation
- Alert
- 将来的なLog Platform / SIEM連携

---

## 8. Request ID

すべての主要なRequestについてRequest IDを付与する。

Request IDによって、一連の処理を複数Service間で追跡可能にする。

```text
Browser
   │
   ▼
Next.js BFF
   │
   │ Request ID
   ▼
Laravel API
   │
   ▼
Database
```

### 8.1 基本方針

- Request単位で一意なIDを使用する。
- Next.js BFFからLaravel APIへRequest IDを引き継ぐ。
- Application LogへRequest IDを含める。
- Access LogへRequest IDを含める。
- Security Logへ必要に応じてRequest IDを含める。
- Audit LogへRequest IDを含める。

ClientからRequest IDが送信された場合、その値を無条件に信頼する設計は避ける。

---

## 9. Correlation

MVPではRequest IDを主要なCorrelation手段として利用する。

以下の関連を追跡できる状態を目標とする。

```text
Frontend / BFF Request
          │
          ▼
Backend Request
          │
          ├── Application Log
          ├── Access Log
          ├── Security Log
          └── Audit Log
```

Distributed TracingはMVPでは必須としない。

---

## 10. 機密情報のログ出力禁止

以下をログへ出力してはならない。

- Password
- Session ID
- Cookie
- Authorization Header
- Sanctum Token
- API Key
- Secret
- Database Credential
- Encryption Key

ProductionではRequest / Response全体を無条件にDumpするLoggingを禁止する。

---

## 11. 個人情報

社員情報についても必要以上にログへ記録しない。

可能な場合は以下のようなIdentifierを利用する。

```text
employee_id
user_id
```

氏名等の直接的な情報を障害調査目的だけで大量に記録することを避ける。

ログに必要な情報は、そのログの目的を達成するための最小限とする。

---

## 12. Log Masking

外部LibraryやFramework等によって機密情報が自動的にログへ含まれる可能性を考慮する。

必要に応じて以下をMasking / Redaction対象とする。

- Authentication Header
- Cookie
- Token
- Password関連Field
- Secret関連Field
- Credential関連Field

Production導入前に実際のログ内容を確認する。

---

## 13. Audit Log

Securityおよび業務上重要な操作についてAudit Logを記録する。

Audit Logは通常のApplication Logとは別に管理する。

MVPではPostgreSQLの専用Tableを使用する。

```text
audit_logs
```

---

## 14. Audit対象操作

MVPでは最低限以下をAudit対象とする。

### Permission / Role

- Role変更
- `can_manage_permissions` の付与
- `can_manage_permissions` の解除

### Assignment

- Sub Manager Assignment追加
- Sub Manager Assignment解除
- Team Leader Assignment追加
- Team Leader Assignment解除

### Employee

- Employee削除

### Skill Master

- Skill追加
- Skillの重要な変更
- Skill無効化
- Skill再有効化

将来的に必要性が確認された場合、Audit対象を追加する。

EmployeeSkillの通常更新等、頻繁に発生する一般操作についてはMVPでは一律Audit対象としない。

---

## 15. Audit Log記録内容

Audit Logでは最低限以下を記録する。

| 項目 | 内容 |
|---|---|
| Timestamp | 操作日時 |
| Actor User ID | 操作者 |
| Action | 実行した操作 |
| Target Type | 操作対象種別 |
| Target ID | 操作対象ID |
| Result | 操作結果 |
| Request ID | 関連Request |

概念例:

```text
actor_user_id = 10
action        = "permission_management_granted"
target_type   = "user"
target_id     = 25
result        = "success"
request_id    = "..."
```

---

## 16. Before / After

重要な変更では、必要に応じて変更前・変更後の値を記録する。

例:

```text
before:
  role = TEAM_LEADER

after:
  role = SUB_MANAGER
```

Entity全体を無条件に保存せず、原則として変更されたFieldのみを記録する。

以下をBefore / Afterへ含めない。

- Password
- Token
- Secret
- Credential
- Session情報

---

## 17. Audit Logの不変性

Audit Logは原則 **Append Only** とする。

通常のApplication処理では以下を禁止する。

```text
INSERT → 許可

UPDATE → 禁止

DELETE → 禁止
```

Audit Logを通常の管理画面等から編集できる機能は提供しない。

保持期間満了による削除のみ、管理された運用処理として許可する。

---

## 18. Audit LogとTransaction

重要な業務変更とAudit Logは、原則として同一Database Transaction内で保存する。

例:

```text
BEGIN
   │
   ├── Permission変更
   │
   ├── Audit Log INSERT
   │
COMMIT
```

Audit Logの保存に失敗した場合はTransactionをRollbackする。

```text
Permission変更成功
        +
Audit Log失敗

        ↓

ROLLBACK
```

以下のような状態を避ける。

```text
重要操作は成功した
しかし
Audit Logは存在しない
```

---

## 19. Audit Log保存失敗

Audit対象となる重要操作では、Audit Logの保存失敗を無視しない。

Audit Logの保存に失敗した場合、対象となる業務処理も失敗させる。

エラー内容はApplication Logへ記録する。

---

## 20. Application Log保存失敗

通常のApplication Log出力失敗については、原則として業務処理そのものを失敗させない。

ただしLogging Infrastructure全体の障害については監視対象とする。

---

## 21. Timestamp

すべてのLogでTimestampを記録する。

保存時のTimezoneは **UTC** を基本とする。

```text
Storage
  ↓
UTC

Display
  ↓
Asia/Tokyo
```

利用者向け画面や運用画面で表示する場合は `Asia/Tokyo` を基本とする。

---

## 22. Log保持期間

MVPでは以下を保持期間とする。

| Log | 保持期間 |
|---|---:|
| Application Log | 90日 |
| Access Log | 90日 |
| Security Log | 90日 |
| Audit Log | 3年 |

保持期間を超えたLogは削除可能とする。

法令、契約、Security Policy等によって別途保持期間が要求された場合は見直す。

---

## 23. Log Rotation

Application Log、Access Log、Security LogについてLog Rotationを行う。

以下を必須とする。

- 無制限にDiskへ蓄積しない。
- Retention期間を超えたLogを削除する。
- Disk容量を圧迫しない。
- Docker Container内部だけを永続的なLog保存先としない。

ProductionではHosting Platform / Cloud Provider等が提供するLogging Infrastructureの利用を優先する。

---

## 24. Audit Logの保持・削除

Audit Logは3年間保持する。

保持期間満了後は、管理されたRetention処理によって削除可能とする。

通常のApplication Userによる削除は許可しない。

Retention処理そのものについても、必要に応じて運用ログへ記録する。

---

## 25. Log Access Control

Production LogおよびAudit Logへのアクセスは必要最小限とする。

特に以下へのアクセスを一般Application Userへ許可しない。

- Application Log
- Security Log
- Raw Access Log
- Audit Logの管理機能

運用上必要な担当者のみアクセス可能とする。

---

## 26. Log Storage

MVPでは以下を基本とする。

### Application / Access / Security Log

Hosting PlatformまたはCloud Providerが提供するLogging機能を優先する。

### Audit Log

PostgreSQLの専用 `audit_logs` Tableへ保存する。

```text
Application / Access / Security
             │
             ▼
     Logging Platform


Audit
             │
             ▼
        PostgreSQL
        audit_logs
```

---

## 27. Audit Log Table設計

具体的なDatabase Column設計はDatabase設計時に定義する。

最低限、以下を保持可能な構造とする。

```text
id
occurred_at
actor_user_id
action
target_type
target_id
result
before
after
request_id
```

`before` / `after` は必要に応じてJSON等で保持できる構造を検討する。

Audit LogはDomain Aggregateとして扱う必要はなく、監査記録としての責務を優先する。

---

## 28. Log監視

最低限以下を監視可能とする。

- HTTP 5xx増加
- Application Error増加
- Authentication失敗増加
- Authorization失敗増加
- Rate Limit超過
- Logging Infrastructure異常

具体的なMetric、Threshold、Alert方法については `監視・Observability.md` で定義する。
