# 可用性・信頼性

## 1. 目的

本ドキュメントでは、Engineer Skill Management App における可用性、障害復旧、データ整合性、および信頼性に関する非機能要件を定義する。

MVPでは、高可用性構成を過度に追求するのではなく、社内向けシステムとして通常業務に支障なく利用でき、障害発生時に現実的な時間内で復旧できることを目標とする。

---

## 2. 可用性

### 2.1 目標稼働率

- 目標稼働率は **99.5%** とする。
- SLAとして外部に保証する値ではなく、内部運用上の目標値とする。
- 計画停止時間は稼働率の評価対象外とする。

### 2.2 利用可能時間

- 原則として **24時間利用可能** とする。
- メンテナンス、デプロイ、DB Migration、インフラ更新等による計画停止を許容する。

### 2.3 計画停止

- 計画停止を許容する。
- 可能な限り事前に利用者へ告知する。
- MVPでは Zero Downtime Deployment を必須要件としない。
- 将来的に利用規模や業務上の重要度が高まった場合、無停止デプロイを検討する。

### 2.4 冗長化

- MVPではアプリケーションおよびインフラの完全な冗長構成を必須としない。
- 一部の単一障害点を許容する。
- 本番利用規模や重要度の拡大に応じて、冗長化や自動フェイルオーバーを検討する。

### 2.5 外部サービス障害

- 認証、ホスティング等の外部サービス障害による一時的な利用不可を許容する。
- アプリケーション側では可能な範囲で適切なエラーハンドリングを行う。
- 外部サービス障害時に無限Retryを行わない。

---

## 3. 障害復旧

### 3.1 RTO

RTO（Recovery Time Objective）は **4時間以内** を目標とする。

重大障害発生後、4時間以内にサービスを通常利用可能な状態へ復旧することを目標とする。

### 3.2 RPO

RPO（Recovery Point Objective）は **24時間以内** を目標とする。

重大なDB障害等が発生した場合でも、最大24時間分以内のデータ損失に抑えることを目標とする。

### 3.3 復旧方法

障害内容に応じて、以下の方法で復旧する。

- 原因調査
- アプリケーションの再起動
- 直前の安定バージョンへのRollback
- PostgreSQL BackupからのRestore
- 必要に応じたDB Migrationの復旧
- 外部サービス復旧後の再接続

### 3.4 復旧手順

- 障害復旧手順をドキュメント化する。
- BackupからのRestore手順を明文化する。
- 本番導入前に最低1回、Restore手順を検証する。
- 手順変更時は必要に応じて再検証する。

---

## 4. データ整合性

### 4.1 DB制約

データ整合性を保証するため、PostgreSQLの以下の制約を積極的に利用する。

- PRIMARY KEY
- FOREIGN KEY
- UNIQUE
- CHECK
- NOT NULL

業務ルールについてはDomain Layerでも保証し、アプリケーションとDBの二重防御を基本とする。

### 4.2 Transaction

- 原則として **1 UseCase = 1 Transaction** とする。
- Application LayerでTransaction境界を管理する。
- 処理途中で例外が発生した場合はRollbackする。
- 中途半端な状態でデータを確定させない。

### 4.3 同時更新

一般的な編集処理については **Last Write Wins** を許容する。

ただし、以下のような重要な整合性保証が必要な処理では悲観ロックを利用する。

- 権限管理可能な管理ユーザーを最低1人維持する処理
- 同時実行によって業務ルール違反が発生する可能性のある処理

悲観ロックを利用する場合、デッドロック回避のため、可能な限りID昇順でLockを取得する。

### 4.4 重複登録防止

重複が許可されないデータについては、以下の二重防御を行う。

1. Application Layerで事前確認
2. DatabaseのUNIQUE制約で最終保証

### 4.5 DB接続障害

DBアクセスに失敗した場合、不完全な状態で処理を継続しない。

- TransactionをRollbackする
- エラーとして処理を終了する
- エラー内容をログに記録する

---

## 5. 冪等性

MVPでは、すべてのCRUD APIに冪等性を強制しない。

ただし、以下のような二重実行が問題となる処理については個別に冪等性を検討する。

- 同一処理の重複実行によってデータ不整合が起こる処理
- 外部サービスとの連携処理
- 将来的な非同期処理
- 将来的なWebhook受信処理

必要に応じて以下を利用する。

- UNIQUE制約
- Idempotency Key
- 処理済み状態管理

---

## 6. Retry

Retryは必要な箇所に限定して使用する。

### 方針

- 無限Retryは禁止する。
- Retry回数には上限を設定する。
- Retryしても改善しないエラーには使用しない。
- DB整合性エラーやValidationエラーは原則Retryしない。
- 一時的なネットワーク障害や外部サービス障害のみ対象とする。

---

## 7. データ損失防止

### 7.1 Backup

- PostgreSQLの定期Backupを取得する。
- RPO 24時間を満たせる頻度でBackupを取得する。
- Backupの保存方法、保存先、保持期間は「データ保護・バックアップ」で別途定義する。

### 7.2 Restore

- Backupから復元可能な手順を用意する。
- 本番導入前にRestore Testを実施する。

### 7.3 削除処理

重要データを削除する場合は、誤操作防止のため必要に応じて確認操作を設ける。

以下の既存仕様を維持する。

- Skillは物理削除せず無効化する。
- 退職社員データは3年間保持する。
- 保持期間経過後、管理ユーザーが確認したうえで削除する。

### 7.4 DB Migration

本番環境でDB Migrationを実施する場合、以下を満たすことを原則とする。

- Migration内容を事前確認する。
- データ損失が発生する可能性を確認する。
- 必要に応じて事前Backupを取得する。
- 復旧またはRollback可能な手段を用意する。

---

## 8. 障害検知

### 8.1 Health Check

Health Check Endpointを用意する。

最低限、以下を確認できることとする。

- アプリケーションが応答可能であること
- 必要に応じてDB接続状態

### 8.2 エラー監視

以下を監視対象とする。

- HTTP 5xx
- Application Error
- DB接続異常
- Health Check失敗

### 8.3 死活監視

本番環境では最低限の外形または死活監視を実施する。

### 8.4 高度な監視

以下はMVP必須要件としない。

- APM
- Distributed Tracing
- 自動フェイルオーバー
- 高度なSLO / Error Budget管理

必要に応じて将来導入する。
