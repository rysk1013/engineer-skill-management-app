# 互換性・動作環境

## 1. 目的

本ドキュメントでは、Engineer Skill Management App におけるClient / Serverの対応環境、Browser Compatibility、Device SupportおよびRuntime Versionに関する非機能要件を定義する。

Support対象を明確にし、過度なLegacy Compatibilityを避けながら、主要な利用環境で安定してApplicationを利用できる状態を維持することを目的とする。

---

## 2. 基本方針

以下を基本方針とする。

- Modern BrowserをSupport対象とする。
- Legacy BrowserをSupport対象としない。
- Desktopを主要動作環境とする。
- Tablet / Smartphoneでは定義した範囲の操作性を提供する。
- 特定OSへの不要な依存を避ける。
- Browser標準機能を優先する。
- JavaScriptおよびCookieを利用可能な環境を前提とする。
- Server-side Runtime Versionを明示する。
- Development / CI / Production間のRuntime差異を可能な限り小さくする。
- EOLとなったRuntimeをProductionで継続利用しない。
- Support対象を無制限に拡大しない。

---

## 3. 対応Browser

MVPでは以下のDesktop Browserを正式Support対象とする。

```text id="gjl9jp"
Google Chrome

Microsoft Edge

Safari

Firefox
```

Chromium系Browserだけに依存した実装を避け、主要Browserで利用可能なWeb Applicationとする。

---

## 4. Browser Version Policy

Support対象Browserについて以下を基本とする。

```text id="j4sxh5"
Latest Stable Major Version

+

Previous Stable Major Version
```

すなわち **Latest + Previous Major** をSupport範囲とする。

特定のBrowser Version番号を非機能要件へ固定し続ける方式は採用しない。

Browser Releaseに伴いSupport対象Versionは自動的に移動するものとする。

---

## 5. Legacy Browser

以下はMVPの正式Support対象外とする。

- Internet Explorer
- Vendor Supportが終了したBrowser
- 長期間UpdateされていないBrowser
- Legacy Browser
- 特殊なEmbedded Browser
- 特殊なWebView

Legacy Browser対応のみを目的としたPolyfillやCompatibility Layerの導入は原則行わない。

---

## 6. Unsupported Browser

Support対象外BrowserからのAccess自体を必ず禁止する必要はない。

```text id="4hkv0k"
Unsupported
     ≠
Access禁止
```

Support対象外環境では正常動作を保証しない。

問題が発生した場合はSupport対象Browserへの切り替えを案内できる状態とする。

---

## 7. Desktop OS

Web Applicationであるため、Compatibility BoundaryはOSよりBrowserを基本とする。

主要利用OSとして以下を想定する。

```text id="r2xkyk"
Windows

macOS
```

Support対象Browserが利用可能なLinux Desktopについても基本的に利用可能とする。

ただしMVPではLinux Distributionごとの正式な動作保証およびOS別Test Matrixを要求しない。

---

## 8. Device Support

Device Supportについて以下とする。

| Device | Support方針 |
|---|---|
| Desktop | 主要Support |
| Tablet | 利用可能 |
| Smartphone | 基本操作可能 |

Desktopを主要Use Caseとする。

Tablet / Smartphoneについては `ユーザビリティ・アクセシビリティ.md` の要件に従う。

SmartphoneでDesktopと完全に同等の操作性をMVPでは要求しない。

---

## 9. Mobile Browser

Mobile環境では主に以下を想定する。

- Safari on iOS
- Safari on iPadOS
- Chrome on Android

Mobile BrowserについてもVendor Support期間内のVersionを利用することを前提とする。

すべてのMobile Browser / Device Combinationで完全な動作保証を行うことはMVPでは要求しない。

---

## 10. Responsive Design

Responsive Designを必須とする。

Desktop以外の画面幅でもApplicationが完全に利用不能となるLayoutを避ける。

具体的なResponsive Design要件については `ユーザビリティ・アクセシビリティ.md` に従う。

---

## 11. JavaScript

Application利用にはJavaScriptが有効であることを必須とする。

```text id="5jfrkk"
JavaScript Enabled
        ↓
     Required
```

JavaScript無効環境でApplication全体が正常動作することはMVPでは保証しない。

Next.js Server Component等を利用する場合でも、Application全体としてJavaScript不要を要件とはしない。

---

## 12. Cookie

Authentication / Session管理にCookieを利用するため、Cookieを利用可能なBrowserを必須動作環境とする。

```text id="4iy1zq"
JavaScript
   ↓
Required

Cookie
   ↓
Required
```

Applicationに必要なCookieを完全に拒否している環境は正式Support対象外とする。

---

## 13. Desktop Viewport

Desktopでは一般的なLaptop / Desktop Resolutionで利用可能とする。

設計・Test上の主要Viewportの目安を以下とする。

```text id="m8ntjd"
1280px以上
```

1024px程度のViewportについても主要な基本操作が不可能にならないことを目標とする。

特定の1つのResolutionだけで正常に利用できるLayoutを避ける。

---

## 14. Browser Zoom

Accessibilityを考慮し、Browser Zoomによる拡大時にも主要操作が利用可能な状態を目指す。

MVPでは以下を目標とする。

```text id="5y2hmg"
200% Zoom
    ↓
主要Content / 操作を利用可能
```

200% Zoom時にDesktopと完全に同一のLayoutを維持することは要求しない。

Contentが利用不能になることを避ける。

---

## 15. OS依存

Applicationの主要機能を特定Client OSへ依存させない。

以下への不要な依存を避ける。

- OS固有File Path
- OS固有Command
- OS固有Font
- OS固有Keyboard Shortcut
- OS固有Browser Extension

可能な限りBrowser Standard APIを利用する。

---

## 16. Font

特定OS固有Fontが存在しない場合にLayoutや主要機能が破綻する設計を避ける。

以下を利用可能とする。

- System Font Stack
- Web Font
- Fallback Font

Web Font等の読み込みに失敗した場合でも基本操作が可能なFallbackを設定する。

---

## 17. Server-side Runtime

Server-sideで利用する主要Runtime / MiddlewareのVersionを明示する。

主な対象:

- Node.js
- PHP
- PostgreSQL
- Redis
- Composer
- JavaScript Package Manager
- Docker Base Image

具体的なVersionはRepository内のConfigurationをSingle Source of Truthとして管理する。

非機能要件DocumentへPatch Versionを固定し続ける方式は採用しない。

---

## 18. Runtime Version Policy

Productionでは原則として以下のいずれかを利用する。

```text id="40rt47"
Active LTS

または

Vendor / Projectの
公式Support期間内Stable Version
```

EOLとなったRuntimeをProductionで長期間継続利用しない。

Version Upgrade時は最低限以下を確認する。

- Security
- Framework Compatibility
- Dependency Compatibility
- Breaking Change
- Migration Requirement

---

## 19. Runtime Version固定

実際に利用するRuntime VersionはRepository内で明示する。

対象例:

```text id="0u7vqf"
Node.js

PHP

PostgreSQL

Composer

npm / pnpm等

Docker Base Image
```

Developerごとに任意のMajor Versionを利用する状態を避ける。

Version固定方法は各Technologyに適したConfigurationを利用する。

---

## 20. Development / CI / Production

Development / CI / Productionでは可能な限り同じMajor Versionを使用する。

```text id="mpcd3h"
Development
     │
     ▼
     CI
     │
     ▼
Production
```

特に以下のMajor Version差異を避ける。

- Node.js
- PHP
- PostgreSQL

Environment間のVersion差異によってのみ発生するBugを最小化する。

---

## 21. PostgreSQL

Development / Integration Test / Staging / Productionでは可能な限り同一Major VersionのPostgreSQLを利用する。

```text id="a9pqjy"
Development
      │
      ▼
Integration Test
      │
      ▼
Staging
      │
      ▼
Production

PostgreSQL Major Version
      ↓
可能な限り統一
```

ProductionがPostgreSQLであるにもかかわらず、Database固有のIntegration TestをSQLite等だけで代替することは避ける。

---

## 22. Docker

Development環境ではDocker / Docker Composeを利用する。

Server RuntimeをContainer化することで以下の差異を最小化する。

- Runtime Version
- System Dependency
- Extension
- Package
- Environment Configuration

Docker Engine / Docker Desktop等についてもSupport終了Versionを長期間利用しない。

---

## 23. Framework Compatibility

Framework / Library Update時には関連RuntimeとのCompatibilityを確認する。

主な対象:

- Next.js
- React
- Better Auth
- Laravel
- Laravel Sanctum
- PostgreSQL Driver
- Redis Client
- PHP Extension

特にMajor Version Update時はRuntime RequirementおよびBreaking Changeを確認する。

---

## 24. Dependency Compatibility

Dependency Updateは単独Packageだけで判断せず、関連ComponentとのCompatibilityを確認する。

例:

```text id="10h1b9"
Next.js
  ↕
React
  ↕
Node.js
```

```text id="7v8kpb"
Laravel
  ↕
PHP
  ↕
Composer Package
```

Dependency管理の詳細は `保守性・品質.md` に従う。

---

## 25. Browser Compatibility確認

MVPではChromeおよびSafariを主要な手動確認対象とする。

特に以下の変更ではBrowser Compatibilityを確認する。

- Layout変更
- Form Component変更
- Dialog変更
- Table変更
- Browser API利用
- Authentication関連変更
- File操作等のBrowser依存機能

Edge / Firefoxも正式Support対象とするが、すべてのPull Requestで4 Browserすべての手動Testを必須とはしない。

主要Releaseや影響の大きいUI変更時に必要に応じて確認する。

---

## 26. E2E Browser

MVPの主要E2E環境にはChromiumを使用する。

```text id="4s5x0p"
MVP E2E
   ↓
Chromium
```

Playwright等を利用する場合、将来的に以下へ拡張可能な構成を推奨する。

```text id="l2dz8x"
Chromium

Firefox

WebKit
```

---

## 27. Cross-browser E2E

MVPではすべてのE2E Testを複数Browser Engineで実行することを必須としない。

将来的には例えば以下の運用を検討できる。

```text id="jz4xen"
Pull Request
     ↓
Chromium

Release
     ↓
Chromium
Firefox
WebKit
```

Browser Compatibility問題の発生状況およびCI実行時間を考慮して導入を判断する。

---

## 28. CompatibilityとAccessibility

Compatibility対応によってAccessibility要件を弱めない。

Browser / Device差異が存在する場合でも、主要Support環境では以下を維持する。

- Keyboard操作
- Focus Indicator
- Form Label
- Error表示
- Responsive Design
- Semantic HTML

詳細は `ユーザビリティ・アクセシビリティ.md` に従う。

---

## 29. Support Policy見直し

Browser / Runtime / DeviceのSupport Policyは定期的に見直す。

特に以下の場合にReviewする。

- BrowserのEOL
- RuntimeのEOL
- Framework Major Update
- Security Support終了
- 利用環境の変化
- 新しいDevice Requirement
- Compatibility Issueの増加

Support終了環境を無期限に維持しない。
