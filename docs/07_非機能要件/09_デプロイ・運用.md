# デプロイ・運用

## 1. 目的

本ドキュメントでは、Engineer Skill Management App におけるデプロイおよび運用に関する非機能要件を定義する。

Development / Staging / Production間の環境差異を抑え、安全かつ再現可能なDeploy、Database Migration、RollbackおよびProduction運用を実現することを目的とする。

---

## 2. 基本方針

以下を基本方針とする。

- Dockerを利用して環境差異を最小化する。
- Development / Staging / Productionを明確に分離する。
- Application Codeおよび設定をGitで管理する。
- CI成功をDeployの前提とする。
- Production Deployを再現可能な手順とする。
- Production環境への手作業を最小限にする。
- SecretをSource Codeへ含めない。
- Database MigrationをDeploy Processの一部として管理する。
- Deploy失敗時にRollback可能な状態を維持する。
- Productionで稼働しているVersionを追跡可能にする。
- 運用手順をRunbookとしてDocumentation化する。

---

## 3. Environment

最低限以下の3環境を使用する。

```text id="ngjs6y"
Development

Staging

Production
```

各Environmentの責務を明確に分離する。

---

## 4. Development

Development環境はDeveloperによる実装・Test・検証に使用する。

基本構成:

```text id="59ip2z"
Docker Compose
      │
      ├── Next.js
      ├── Laravel
      └── PostgreSQL
```

DevelopmentではProduction Dataを原則利用しない。

Test Dataには以下を使用する。

- Factory
- Faker
- Seeder
- Fixture
- Dummy Data

Developer間で可能な限り同一のDevelopment環境を再現できる状態を維持する。

---

## 5. Staging

StagingはProduction Deploy前の確認環境として使用する。

最低限以下を確認可能とする。

- Application起動
- Next.js → Laravel API通信
- Authentication
- Authorization
- PostgreSQL接続
- Database Migration
- Environment Variable
- Health Check
- 主要User Flow
- 必要なE2E Test

Productionと完全に同一のResource Sizeを要求しないが、Architectureおよび主要Component構成の差異を可能な限り小さくする。

Production DataはStagingで原則利用しない。

---

## 6. Production

Productionでは以下を適用する。

- Production専用Database
- Production専用Secret
- Production Monitoring
- Production Backup
- Production Logging
- Production Access Control

Development / StagingとCredentialやSecretを共有しない。

---

## 7. Environment分離

最低限以下をEnvironmentごとに分離する。

| 項目 | 分離 |
|---|---|
| Database | 必須 |
| Database Credential | 必須 |
| Application Secret | 必須 |
| Authentication Secret | 必須 |
| API Token | 必須 |
| Environment Variable | 必須 |
| Backup | 必須 |
| Monitoring設定 | 必要に応じて分離 |

Production CredentialをDevelopment / Stagingで利用しない。

---

## 8. Docker

Application実行環境にはDockerを採用する。

主な対象:

- Next.js
- Laravel

DevelopmentではPostgreSQLもDockerで実行する。

ProductionではManaged PostgreSQL等を利用可能とし、DatabaseをDocker Containerとして運用することは必須としない。

---

## 9. Production Container Image

Production Imageでは以下を基本とする。

- Multi-stage Build
- 不要なBuild DependencyをRuntime Imageへ含めない。
- 不要Packageを含めない。
- 可能な限りNon-root Userで実行する。
- Runtime / Base Image Versionを明示する。
- Reproducible Buildを意識する。
- Development用ToolをProduction Imageへ不要に含めない。

---

## 10. Image Version

Productionで使用するContainer ImageはVersionを一意に識別可能にする。

以下のいずれか、または組み合わせを利用する。

```text id="j15e5v"
Release Version

Git Commit SHA

Immutable Image Digest
```

Production Deployを`latest` Tagだけに依存させない。

過去の安定Imageを特定できる状態を維持する。

---

## 11. CI / CD

Pull RequestおよびMerge後にCIを実行する。

CI要件については `保守性・品質.md` に従う。

Deploy Pipelineは概念的に以下を基本とする。

```text id="j3udk1"
Pull Request / Merge
        │
        ▼
        CI
        │
        ▼
       Build
        │
        ▼
 Container Image
        │
        ▼
  Staging Deploy
        │
        ▼
 Staging Verification
        │
        ▼
 Production Approval
        │
        ▼
 Production Deploy
```

CIが失敗しているVersionを通常のProduction Deploy対象としない。

---

## 12. Staging Deploy

Production Deploy前に原則としてStagingへDeployする。

Stagingでは最低限以下を確認する。

- Container起動
- Health Check
- API疎通
- Database接続
- Migration
- Authentication
- Authorization
- 主要User Flow
- 重大なApplication Errorが発生していないこと

---

## 13. Production Deploy

Production DeployはCIを通過したArtifactを使用する。

MVPではProduction Deployの完全自動化を必須としない。

Production Deploy前に手動Approvalを設けることを許可・推奨する。

```text id="mpak9n"
Staging OK
    │
    ▼
Manual Approval
    │
    ▼
Production
```

Stagingで確認したArtifactとProductionへDeployするArtifactを可能な限り同一にする。

---

## 14. Deployment方式

MVPではZero Downtime Deploymentを必須としない。

短時間の計画停止を許容する。

ただしDeploy中に長時間Applicationが不整合な状態となることを避ける。

将来的にAvailability要件が高まった場合は以下を検討する。

- Rolling Deployment
- Blue / Green Deployment
- Canary Deployment

---

## 15. Database Migration

Database Schema変更はMigration FileとしてGit管理する。

Production Databaseへの仕様変更目的の手動DDLを通常運用としない。

Migrationについて以下を必須とする。

- Git管理
- Code Review
- Stagingでの事前実行
- 影響範囲確認
- Applicationとの互換性確認
- 必要に応じたBackup確認
- Rollback / Restore方法確認

---

## 16. Migration Flow

基本的なMigration Flowは以下とする。

```text id="ag8j0j"
Migration作成
      │
      ▼
Code Review
      │
      ▼
CI / Test
      │
      ▼
Staging Migration
      │
      ▼
Staging Verification
      │
      ▼
Production Safety確認
      │
      ▼
Production Migration
      │
      ▼
Application確認
```

Migrationに失敗した場合はDeploy Processを中断する。

---

## 17. 破壊的Migration

以下のような変更は破壊的Migrationとして特に慎重に扱う。

```sql id="x4olhb"
DROP TABLE
DROP COLUMN
ALTER COLUMN
DELETE
```

実施前に最低限以下を確認する。

- Data Lossの可能性
- Applicationへの影響
- Backup取得状況
- Rollback可能性
- Restore方法
- 旧Application Versionとの互換性

---

## 18. 段階的Migration

可能な場合は以下のような段階的Migrationを優先する。

```text id="xglbcu"
Expand
   │
   ▼
Migrate
   │
   ▼
Contract
```

例:

```text id="whqv68"
新Column追加
     ↓
新旧Schema対応Application Deploy
     ↓
Data Migration
     ↓
新Columnへ完全移行
     ↓
旧Column削除
```

Zero Downtimeを必須としない場合でも、安全なSchema変更方法として利用する。

---

## 19. Migration Rollback

Migration Fileに`down()`が存在することだけをRollback保証とはみなさない。

特に以下は単純なRollbackが困難な場合がある。

- Data Migration
- Column削除
- Table削除
- Data削除
- Data Type変更

Migrationごとに必要に応じて以下のどちらを利用するか判断する。

```text id="tl3d89"
Migration Rollback

または

Backup Restore
```

---

## 20. Application Rollback

Production Deploy後に重大な問題が発生した場合、直前の安定VersionへRollback可能な状態を維持する。

Rollback対象Versionを以下から識別できるようにする。

- Git Commit
- Release Version
- Container Image Tag
- Container Image Digest

Application Rollback後もDatabase Schemaとの互換性が維持されることを確認する。

---

## 21. Rollback判断

以下のような問題が発生した場合はRollbackを検討する。

- Applicationが起動しない。
- Health Checkが継続的に失敗する。
- 重大なHTTP 5xxが発生する。
- Authentication / Authorizationが正常に動作しない。
- Data Integrityへ影響する問題が発生する。
- 主要機能が利用不能となる。

軽微な問題についてはFix Forwardを選択可能とする。

---

## 22. Release識別

Productionで現在稼働しているApplication Versionを追跡可能にする。

最低限以下のいずれかをDeployment情報として記録する。

```text id="q7qgzd"
Git Commit SHA

Release Version
```

Container Imageとの対応関係を確認可能にする。

---

## 23. Secret管理

SecretをGit Repositoryへ保存しない。

主なSecret:

- Database Password
- Better Auth Secret
- Backend Credential暗号化用Secret
- Sanctum関連Credential
- API Token
- External Service Credential
- Encryption Key

ProductionではCloud / Hosting Provider等のSecret管理機能を優先する。

---

## 24. `.env` 管理

実際のSecretを含む`.env` FileをGit管理しない。

`.env.example`等には必要なEnvironment Variable名のみ定義し、Production Secret値を記載しない。

例:

```text id="ax3zx8"
DATABASE_URL=

AUTH_SECRET=

BACKEND_API_TOKEN=
```

Environment Variable追加・削除時はSample Configurationも更新する。

---

## 25. Production Access Control

Production Environmentへのアクセス権限は必要最小限とする。

主な対象:

- Production Deploy
- Production Database
- Secret
- Log
- Backup
- Monitoring Configuration

一般Developer全員がProduction Resourceへ自由にアクセスできる状態を避ける。

---

## 26. Production直接変更

以下を原則禁止する。

```text id="cs6zme"
Production Server上で
Application Codeを直接編集
```

```text id="abtyau"
Production Databaseへ
仕様変更目的の手動SQLを直接実行
```

変更は原則として、

```text id="z0cn2e"
Git
 ↓
Review
 ↓
CI
 ↓
Deploy
```

または、

```text id="abkg2s"
Migration
 ↓
Review
 ↓
CI
 ↓
Deploy
```

を経由する。

---

## 27. 緊急変更

重大障害等でProductionへの緊急操作が必要となる場合は例外を許可する。

ただし以下を必須とする。

- 操作内容を記録する。
- 影響範囲を確認する。
- 必要に応じてBackupを取得する。
- 作業後にGit / Migration / Documentationへ正式反映する。
- 恒久対応を別途実施する。

緊急変更を通常運用としない。

---

## 28. Deploy後確認

Production Deploy後は最低限以下を確認する。

- Health Check
- Next.js応答
- Laravel API応答
- Database接続
- Authentication
- 主要機能
- HTTP 5xx発生状況
- Application Log

必要に応じて主要User FlowのSmoke Testを実施する。

---

## 29. Deploy失敗

Deploy途中で問題が発生した場合、不完全なVersionを正常なProduction Versionとして扱わない。

以下を確認する。

- Deploy状態
- Container状態
- Health Check
- Migration状態
- Database Schema
- Application Version
- Log

必要に応じてApplication RollbackまたはDatabase Restoreを実施する。

---

## 30. Runbook

運用上重要な手順をRunbookとしてDocumentation化する。

最低限以下を対象とする。

- Production Deploy
- Application Rollback
- Database Migration
- Migration失敗時対応
- Backup Restore
- Secret Rotation
- 障害復旧

特定の担当者だけが手順を把握している状態を避ける。

---

## 31. Infrastructure as Code

Development環境ではDocker Compose等によるCode化を必須とする。

```text id="f9cqva"
Development
    ↓
Docker Compose
```

Production InfrastructureについてはMVPではIaCを必須としないが、採用を推奨する。

AWSを利用する場合の候補として以下を検討可能とする。

- Terraform
- AWS CDK
- CloudFormation

Infrastructureが複雑化した場合はProduction IaCを必須化することを検討する。

---

## 32. Infrastructure変更

IaC導入後はInfrastructure変更についても以下のFlowを基本とする。

```text id="t1v4g3"
Infrastructure Code
        ↓
Pull Request
        ↓
Review
        ↓
Plan / Validation
        ↓
Apply
```

Production Infrastructureへの手動変更を可能な限り減らす。

---

## 33. Deployと監視

Deploy後の状態確認には `監視・Observability.md` で定義した監視を利用する。

特に以下を確認する。

- Health Check
- HTTP 5xx
- Response Time
- CPU / Memory
- Container Restart
- Database Error

Deploy直後の異常を早期に検知できる状態を維持する。
