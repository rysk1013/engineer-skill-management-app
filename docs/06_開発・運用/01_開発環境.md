# 開発環境 技術決定

## 1. 採用方式

開発環境はDockerを基本とし、プロジェクト固有のRuntime・MiddlewareはDocker Container上で実行する。

- [x] Next.jsをDockerで実行する
- [x] LaravelをDockerで実行する
- [x] PostgreSQLをDockerで実行する
- [ ] Node.jsをHostへ直接インストールして利用する
- [ ] PHP / ComposerをHostへ直接インストールして利用する
- [ ] PostgreSQLをHostへ直接インストールして利用する

Host PCにはプロジェクト固有Runtimeを原則として直接導入しない。

---

## 2. 基本構成

```text
Host PC
   |
   └── Docker Compose
       |
       ├── frontend
       │   ├── Node.js
       │   ├── Next.js
       │   ├── TypeScript
       │   └── Auth.js
       │
       ├── backend
       │   ├── PHP
       │   ├── Composer
       │   ├── Laravel
       │   └── Sanctum
       │
       └── postgres
           └── PostgreSQL
```

MVPでは、

```text
frontend
backend
postgres
```

の3 Containerを基本構成とする。

---

## 3. Container構成

### frontend

担当：

- Node.js Runtime
- Next.js
- TypeScript
- Auth.js
- Frontend
- BFF

BrowserからのApplication Entry Pointとする。

### backend

担当：

- PHP Runtime
- Composer
- Laravel
- Sanctum
- Backend API
- Application / Domain Logic
- 認可
- Validation

Frontend / BFFからBackend APIとして利用する。

### postgres

担当：

- Laravelの業務データ
- Auth.jsのSession Store

MVPではLaravelとAuth.jsで同一PostgreSQL Instanceを利用する。

論理的なデータ管理責務はApplicationごとに分離する。

---

## 4. Container間通信

Container間通信はDocker ComposeのService Nameを利用する。

```text
frontend
   |
   | http://backend:8000
   v
backend
   |
   | postgres:5432
   v
postgres
```

Container間通信では`localhost`を使用しない。

Container内の`localhost`は、そのContainer自身を指すためである。

例：

```text
frontend → backend

http://backend:8000
```

```text
backend → PostgreSQL

host=postgres
port=5432
```

---

## 5. Hostからのアクセス

開発時の基本構成は以下とする。

```text
Browser
   |
   | http://localhost:3000
   v
frontend
   |
   | http://backend:8000
   v
backend
   |
   | postgres:5432
   v
postgres
```

### frontend

Hostへ公開する。

```text
http://localhost:3000
```

Browserは原則としてNext.jsへアクセスする。

### backend

開発・API確認用途のためHostへ公開する。

```text
http://localhost:8000
```

以下の用途を想定する。

- API単体の動作確認
- curl等による確認
- OpenAPI仕様との動作確認
- Debug

Browser Applicationからの通常アクセスはNext.js BFF経由を基本とする。

### postgres

原則としてHostへ公開しない。

```text
backend
   ↓
postgres:5432
```

で利用する。

DB Client等からHost経由で直接接続する必要が発生した場合のみ、開発用途としてPort公開を追加する。

---

## 6. Source Code

Source CodeはHost側で管理し、ContainerへBind Mountする。

```text
Host
   |
   | Bind Mount
   v
Container
```

EditorはHost側で利用する。

例：

- Neovim
- VS Code
- その他

Editor自体をContainer内で実行することは前提としない。

Git操作もHost側を基本とする。

---

## 7. frontendのVolume

frontendのSource CodeをContainerへMountする。

```text
./frontend
    ↓
/app
```

`node_modules`はHostと共有せず、Docker Volumeで管理することを基本とする。

概念例：

```yaml
volumes:
  - ./frontend:/app
  - frontend_node_modules:/app/node_modules
```

目的：

- macOSとLinux Containerの依存関係を分離する
- Native ModuleのPlatform差異を避ける
- Host側へ大量の`node_modules`を配置しない
- Container内のNode.js環境で依存関係を統一する

---

## 8. backendのVolume

backendのSource CodeをContainerへMountする。

```text
./backend
    ↓
/app
```

`vendor`はHostと共有せず、Docker Volumeで管理することを基本とする。

概念例：

```yaml
volumes:
  - ./backend:/app
  - backend_vendor:/app/vendor
```

Composer CommandはContainer内で実行する。

例：

```bash
docker compose exec backend composer install
```

```bash
docker compose exec backend composer require ...
```

目的：

- PHP依存関係をContainer側で管理する
- Host側PHP環境への依存を避ける
- Container Runtimeとの整合性を保つ

---

## 9. PostgreSQL

PostgreSQLのData DirectoryにはDocker Volumeを利用する。

```text
postgres_data
    ↓
PostgreSQL Data
```

通常のContainer停止・削除ではDatabase Dataを保持する。

```bash
docker compose down
```

Volumeまで削除した場合はDatabase Dataも削除される。

```bash
docker compose down -v
```

開発データを初期化する場合など、意図的にVolumeを削除する場合のみ`-v`を利用する。

---

## 10. Docker Compose

Monorepo Rootに`compose.yaml`を配置する。

```text
engineer-skill-management-app/
├── frontend/
│   └── Dockerfile
│
├── backend/
│   └── Dockerfile
│
├── docs/
│
├── compose.yaml
└── README.md
```

`compose.yaml`から開発環境全体を起動・停止できるようにする。

Docker ComposeはLocal Development Environment全体のOrchestrationを担当する。

---

## 11. Healthcheck・起動依存

Containerが起動した状態と、ApplicationやDatabaseが利用可能な状態は区別する。

特にPostgreSQLについてHealthcheckを設定する。

```text
postgres
   |
   | healthcheck
   v
backend
   |
   v
frontend
```

BackendがPostgreSQLを必要とする場合は、PostgreSQLのHealthcheckを利用して起動依存関係を管理する。

必要に応じてBackendにもHealthcheckを設定する。

ただし、Docker Composeの起動順序だけにApplicationの可用性を依存させない。

Application側でも一時的な接続失敗が発生し得ることを前提とする。

---

## 12. 開発環境起動

基本コマンド：

```bash
docker compose up -d
```

初回またはImageを再Buildする場合：

```bash
docker compose up -d --build
```

状態確認：

```bash
docker compose ps
```

ログ確認：

```bash
docker compose logs -f
```

特定Serviceのログ確認：

```bash
docker compose logs -f frontend
```

```bash
docker compose logs -f backend
```

停止：

```bash
docker compose down
```

---

## 13. Laravel Command

Laravel Commandは`backend` Container内で実行する。

例：

```bash
docker compose exec backend php artisan migrate
```

```bash
docker compose exec backend php artisan test
```

```bash
docker compose exec backend php artisan tinker
```

その他のPHP / Composer関連Commandについても原則として`backend` Container内で実行する。

---

## 14. Next.js Command

Node.js関連Commandは`frontend` Container内で実行する。

例：

```bash
docker compose exec frontend npm install
```

```bash
docker compose exec frontend npm run lint
```

```bash
docker compose exec frontend npm test
```

採用するPackage ManagerはProject Setup時に決定する。

候補：

- npm
- pnpm

採用したPackage ManagerのLock FileはGitでVersion Controlする。

例：

```text
npm
→ package-lock.json
```

```text
pnpm
→ pnpm-lock.yaml
```

CIや再現可能な依存関係InstallではLock Fileを利用する。

---

## 15. Source Code変更の反映

開発時はSource CodeをBind Mountし、Next.js / LaravelのSource Code変更をContainerへ反映する。

### Next.js

Development ServerのHot Reload / Fast Refreshを利用する。

### Laravel

PHP Source Codeの変更はBind Mountを通してContainerへ反映し、次回Requestから変更後のCodeを利用する。

通常のSource Code変更ではDocker Imageの再Buildを必要としない。

以下を変更した場合は再Buildを行う。

- Dockerfile
- Runtime Version
- OS Package
- PHP Extension
- Node.js Runtime構成
- Container Imageに含めるSystem Dependency

例：

```bash
docker compose build frontend
```

```bash
docker compose build backend
```

または、

```bash
docker compose up -d --build
```

---

## 16. Host環境

Host PCへプロジェクト固有Runtimeを直接導入することを前提としない。

最低限必要なもの：

- Docker
- Git
- Editor

以下はContainer内で管理する。

- Node.js
- npm / pnpm等
- PHP
- Composer
- PostgreSQL

Host環境への依存を減らし、開発者間で可能な限り同じRuntimeを利用できる状態を維持する。

---

## 17. Version管理

各RuntimeのVersionはDocker Imageで管理する。

```text
Node.js
→ frontend/Dockerfile
```

```text
PHP
→ backend/Dockerfile
```

```text
PostgreSQL
→ compose.yaml
```

Runtime Versionは`latest`等へ暗黙的に追従させず、Projectで利用するVersionを明示する。

具体的なVersionはProject Setup時に決定する。

Application Dependencyについては各Package ManagerのManifest / Lock Fileで管理する。

例：

```text
frontend
├── package.json
└── package-lock.json / pnpm-lock.yaml
```

```text
backend
├── composer.json
└── composer.lock
```

Lock FileはGitでVersion Controlする。

---

## 18. MVPで導入しないもの

MVPでは必要性がない限り、以下をDocker Composeへ追加しない。

- Redis
- nginx
- Mailpit
- MinIO
- Message Queue
- Worker専用Container
- Scheduler専用Container

必要性が発生した段階で追加する。

将来利用する可能性があることを理由として、MVP時点で先行導入しない。

---

## 19. CIとの関係

DockerでRuntime Versionや依存環境を明確にし、LocalとCIの環境差異を減らす。

CIでも以下のVersionをLocal Development Environmentと一致させることを基本とする。

- Node.js
- PHP
- PostgreSQL
- その他主要Runtime

ただし、CIでLocal用Docker Composeをそのまま利用することは必須としない。

CIの具体的な実行方式はCI/CD設計で決定する。

重要なのはDocker Compose自体を共有することではなく、Runtime Version・Dependency・実行条件の差異を最小化することである。

---

## 20. Productionとの関係

開発環境ではDockerを採用する。

ただし、Local Development用Docker Compose構成をProduction環境へそのまま適用することは前提としない。

ProductionについてはDeployment先に応じて以下を別途設計する。

- Production用Container Image
- Runtime構成
- Network
- Database
- Secret管理
- Storage
- Logging
- Monitoring
- Scaling
- Healthcheck
- Deployment方式

ProductionでDocker / Containerを利用するかどうかについてもDeployment Architectureに従う。

Local Development EnvironmentとProduction Environmentでは目的が異なるため、それぞれに適した構成を採用する。

---

## 21. 採用理由

Docker中心の開発環境を採用する理由：

- Next.jsとLaravelで異なるRuntimeを統一的に管理できる
- Node.js Versionを統一できる
- PHP Versionを統一できる
- PostgreSQL Versionを統一できる
- Host環境を汚しにくい
- Host OSとの差異によるDependency問題を減らせる
- 新規開発者のSetupを簡単にできる
- Monorepoとの相性がよい
- CIとの環境差異を減らせる
- Runtime VersionをCodeとして管理できる
- 開発環境をProject単位で起動・停止できる
- 作業終了時に開発環境全体を停止できる

## 22. 決定事項

### 開発環境

プロジェクト固有Runtime・MiddlewareはDockerで構築する。

### Container

MVPでは以下の3 Containerを基本構成とする。

```text
frontend
backend
postgres
```

### Docker Compose

Monorepo Rootの`compose.yaml`で開発環境全体を管理する。

### Host

HostにはProject Runtimeを原則として直接導入しない。

Hostでは主に以下を利用する。

- Docker
- Git
- Editor

### Network

Container間通信ではDocker ComposeのService Nameを利用する。

```text
frontend → backend:8000
backend  → postgres:5432
```

### Host公開

```text
frontend
→ localhost:3000

backend
→ localhost:8000

postgres
→ 原則Hostへ公開しない
```

### Database

PostgreSQL DataはDocker Volumeで永続化する。

### Source Code

Source CodeはHostからContainerへBind Mountする。

### Dependency

`node_modules`と`vendor`はHostと共有せず、Container側のDocker Volumeで管理することを基本とする。

### Command

Node.js / PHP / Composer / Laravel関連Commandは原則として各Container内で実行する。

### Version

Runtime VersionはDockerfile / Docker Imageで明示的に固定する。

Application DependencyはManifest / Lock Fileで管理する。

### Healthcheck

PostgreSQLを中心にHealthcheckを設定し、Container起動とService利用可能状態を区別する。

### MVP

Redis等の追加Middlewareは必要性が発生してから導入する。

### Production

Local Development用Docker ComposeをProductionへそのまま適用することは前提としない。

Production環境はDeployment先に応じて別途設計する。

### 基本方針

- Docker Composeで開発環境を一括管理する
- MVPでは必要最小限のContainer構成とする
- HostへのProject Runtime導入を最小化する
- Runtime VersionをDockerで固定する
- Source CodeはHost、RuntimeとDependencyはContainerを基本とする
- Local / CI間の環境差異を可能な限り減らす
- Productionとは責務を分離する
- Redis等の追加Middlewareは必要になってから導入する
