# 開発環境 技術決定

## 1. 採用方式

開発環境はDockerを基本とし、プロジェクト固有のRuntime・MiddlewareはDocker Container上で実行する。

- [x] Next.jsをDockerで実行する
- [x] LaravelをDockerで実行する
- [x] PostgreSQLをDockerで実行する
- [ ] Node.jsをHostへ直接インストールして利用する
- [ ] PHP / ComposerをHostへ直接インストールして利用する
- [ ] PostgreSQLをHostへ直接インストールして利用する

Host PCにはプロジェクト固有Runtimeを原則として直接導入しない。

---

## 2. 基本構成

```text
Host PC
   |
   └── Docker Compose
       |
       ├── frontend
       │   ├── Node.js
       │   ├── Next.js
       │   ├── TypeScript
       │   └── Auth.js
       │
       ├── backend
       │   ├── PHP
       │   ├── Composer
       │   ├── Laravel
       │   └── Sanctum
       │
       └── db
           └── PostgreSQL
```

MVPでは、

```text
frontend
backend
db
```

の3 Containerを基本構成とする。

---

## 3. Container構成

### frontend

担当：

- Node.js Runtime
- Next.js
- TypeScript
- Auth.js
- Frontend
- BFF

BrowserからのApplication Entry Pointとする。

### backend

担当：

- PHP Runtime
- Composer
- Laravel
- Sanctum
- Backend API
- Application / Domain Logic
- 認可
- Validation

Frontend / BFFからBackend APIとして利用する。

### db

担当：

- Laravelの業務データ
- Auth.jsのSession Store

MVPではLaravelとAuth.jsで同一PostgreSQL Instanceを利用する。

論理的なデータ管理責務はApplicationごとに分離する。

## 4. Container間通信

Container間通信はDocker ComposeのService Nameを利用する。

Container間の通信経路を制限するため、用途ごとにDocker Networkを分離する。

```text
frontend
   |
   | frontend network
   | http://backend:8000
   v
backend
   |
   | backend network
   | db:5432
   v
db
```

各Containerが参加するNetworkは以下とする。

| Container | frontend network | backend network |
| --- | --- | --- |
| frontend | ○ | - |
| backend | ○ | ○ |
| db | - | ○ |

以下の通信を許可する。

```text
frontend → backend : 許可
backend  → db      : 許可
frontend → db      : 許可しない
```

FrontendからDatabaseへ直接アクセスさせず、DatabaseへのアクセスはBackendを経由する。

Container間通信では`localhost`を使用しない。

Container内の`localhost`は、そのContainer自身を指すためである。

例：

```text
frontend → backend

http://backend:8000
```

```text
backend → PostgreSQL

host=db
port=5432
```

---

## 5. Hostからのアクセス

開発時の基本構成は以下とする。

```text
Browser
   |
   | http://localhost:3000
   v
frontend
   |
   | frontend network
   | http://backend:8000
   v
backend
   |
   | backend network
   | db:5432
   v
db
```

### frontend

Hostへ公開する。

```text
http://localhost:3000
```

Browserは原則としてNext.jsへアクセスする。

### backend

開発・API確認用途のためHostへ公開する。

```text
http://localhost:8000
```

以下の用途を想定する。

- API単体の動作確認
- curl等による確認
- OpenAPI仕様との動作確認
- Debug

Browser Applicationからの通常アクセスはNext.js BFF経由を基本とする。

### db

原則としてHostへ公開しない。

```text
backend
   |
   | backend network
   v
db:5432
```

で利用する。

DB Client等からHost経由で直接接続する必要が発生した場合のみ、開発用途としてPort公開を追加する。

## 6. Source Code

Source CodeはHost側で管理し、ContainerへBind Mountする。

```text
Host
   |
   | Bind Mount
   v
Container
```

EditorはHost側で利用する。

例：

- Neovim
- VS Code
- その他

Editor自体をContainer内で実行することは前提としない。

Git操作もHost側を基本とする。

---

## 7. frontendのVolume

frontendのSource CodeをContainerへMountする。

```text
./frontend
    ↓
/app
```

`node_modules`はHostと共有せず、Docker Volumeで管理する。

概念例：

```yaml
volumes:
  - ./frontend:/app
  - frontend_node_modules:/app/node_modules
```

目的：

- macOSとLinux Containerの依存関係を分離する
- Native ModuleのPlatform差異を避ける
- Host側へ大量の`node_modules`を配置しない
- Container内のNode.js環境で依存関係を統一する

---

## 8. backendのVolume

backendのSource CodeをContainerへMountする。

```text
./backend
    ↓
/app
```

`vendor`はHostと共有せず、Docker Volumeで管理する。

概念例：

```yaml
volumes:
  - ./backend:/app
  - backend_vendor:/app/vendor
```

Composer CommandはContainer内で実行する。

例：

```bash
docker compose exec backend composer install
```

```bash
docker compose exec backend composer require ...
```

目的：

- PHP依存関係をContainer側で管理する
- Host側PHP環境への依存を避ける
- Container Runtimeとの整合性を保つ

---

## 9. PostgreSQL

PostgreSQLのData DirectoryにはDocker Volumeを利用する。

```text
postgres_data
    ↓
PostgreSQL Data
```

通常のContainer停止・削除ではDatabase Dataを保持する。

```bash
docker compose down
```

Volumeまで削除した場合はDatabase Dataも削除される。

```bash
docker compose down -v
```

開発データを初期化する場合など、意図的にVolumeを削除する場合のみ`-v`を利用する。

PostgreSQLは原則としてHostへPort公開せず、`backend` Network内からService Name `db` を利用して接続する。

## 10. Docker Compose

Monorepo Rootに`compose.yaml`を配置する。

```text
engineer-skill-management-app/
├── frontend/
│   ├── Dockerfile
│   └── .dockerignore
│
├── backend/
│   ├── Dockerfile
│   └── .dockerignore
│
├── docs/
│
├── compose.yaml
└── README.md
```

`compose.yaml`から開発環境全体を起動・停止できるようにする。

Docker ComposeはLocal Development Environment全体のOrchestrationを担当する。

---

## 11. Network

Docker Composeでは以下の2 Networkを定義する。

```text
frontend
backend
```

### frontend network

Frontend / BFFとBackend API間の通信に利用する。

参加Container：

```text
frontend
backend
```

### backend network

Backend APIとDatabase間の通信に利用する。

参加Container：

```text
backend
db
```

Backendは両方のNetworkへ参加し、FrontendとDatabaseの境界として機能する。

```text
                  frontend network
frontend <────────────────────────> backend
                                      |
                                      | backend network
                                      v
                                     db
```

`frontend` Containerは`backend` Networkへ参加させない。

`db` Containerは`frontend` Networkへ参加させない。

これにより、FrontendからDatabaseへの直接通信を許可しない。

## 12. Healthcheck・起動依存

Containerが起動した状態と、ApplicationやDatabaseが利用可能な状態は区別する。

PostgreSQLにはHealthcheckを設定する。

```text
db
 |
 | healthcheck
 v
backend
```

BackendがPostgreSQLを必要とする場合は、PostgreSQLのHealthcheckを利用して起動依存関係を管理する。

Docker Composeでは、必要に応じて以下のように依存関係を定義する。

```yaml
depends_on:
  db:
    condition: service_healthy
```

必要に応じてBackendにもHealthcheckを設定する。

ただし、Docker Composeの起動順序だけにApplicationの可用性を依存させない。

Application側でも一時的な接続失敗が発生し得ることを前提とする。

## 13. 開発環境起動

基本コマンド：

```bash
docker compose up -d
```

初回またはImageを再Buildする場合：

```bash
docker compose up -d --build
```

状態確認：

```bash
docker compose ps
```

ログ確認：

```bash
docker compose logs -f
```

特定Serviceのログ確認：

```bash
docker compose logs -f frontend
```

```bash
docker compose logs -f backend
```

```bash
docker compose logs -f db
```

停止：

```bash
docker compose down
```

Databaseを含めたVolumeを意図的に削除する場合：

```bash
docker compose down -v
```

通常の停止では`-v`を使用しない。

---

## 14. Laravel Command

Laravel Commandは`backend` Container内で実行する。

例：

```bash
docker compose exec backend php artisan migrate
```

```bash
docker compose exec backend php artisan test
```

```bash
docker compose exec backend php artisan tinker
```

Database接続状態を確認する場合：

```bash
docker compose exec backend php artisan db:show
```

その他のPHP / Composer関連Commandについても原則として`backend` Container内で実行する。

---

## 15. Next.js Command

Node.js関連Commandは`frontend` Container内で実行する。

例：

```bash
docker compose exec frontend npm install
```

```bash
docker compose exec frontend npm run lint
```

```bash
docker compose exec frontend npm run build
```

Package Managerはnpmを採用する。

Lock Fileは以下をGitでVersion Controlする。

```text
package-lock.json
```

CIや再現可能な依存関係InstallではLock Fileを利用する。

---

## 16. Source Code変更の反映

開発時はSource CodeをBind Mountし、Next.js / LaravelのSource Code変更をContainerへ反映する。

### Next.js

Development ServerのHot Reload / Fast Refreshを利用する。

### Laravel

PHP Source Codeの変更はBind Mountを通してContainerへ反映し、次回Requestから変更後のCodeを利用する。

通常のSource Code変更ではDocker Imageの再Buildを必要としない。

以下を変更した場合は再Buildを行う。

- Dockerfile
- Runtime Version
- OS Package
- PHP Extension
- Node.js Runtime構成
