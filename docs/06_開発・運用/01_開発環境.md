# 開発環境 技術決定

## 1. 採用方式

開発環境はDockerを基本とし、プロジェクト固有のRuntime・MiddlewareはDocker Container上で実行する。

- [x] Next.jsをDockerで実行する
- [x] LaravelをDockerで実行する
- [x] NginxをDockerで実行する
- [x] PostgreSQLをDockerで実行する
- [x] OpenAPI ToolingをDockerで実行する
- [ ] Node.jsをHostへ直接インストールして利用する
- [ ] PHP / ComposerをHostへ直接インストールして利用する
- [ ] PostgreSQLをHostへ直接インストールして利用する

Host PCにはプロジェクト固有Runtimeを原則として直接導入しない。

Development / Productionでは主要なRuntimeとApplication通信経路を可能な限り共通化する。

Development固有のSource Code Bind Mount、Development Dependency、Hot Reload等はDevelopment環境に限定し、ProductionではBuild済みApplicationとProduction Dependencyを含むContainer Imageを利用する。

---

## 2. 基本構成

Local DevelopmentではDocker Composeを利用し、以下のContainerを構成する。

```text
Host PC
   |
   └── Docker Compose
       |
       ├── frontend
       │   ├── Node.js
       │   ├── Next.js
       │   ├── TypeScript
       │   └── Better Auth
       │
       ├── nginx
       │   └── Nginx
       │
       ├── backend
       │   ├── PHP-FPM
       │   ├── Composer
       │   ├── Laravel
       │   └── Sanctum
       │
       ├── db
       │   └── PostgreSQL
       │
       ├── redis
       │   └── Redis
       │
       ├── test-db
       │   └── PostgreSQL
       │
       └── openapi
           ├── Node.js
           ├── Redocly CLI
           └── openapi-typescript
```

Application Runtimeの基本通信経路は以下とする。

```text
Browser / Host
   |
   | HTTP
   v
frontend
Next.js / BFF
   |
   | HTTP
   v
nginx
   |
   | FastCGI
   v
backend
PHP-FPM / Laravel
   |
   | PostgreSQL Protocol
   v
db
PostgreSQL
```

BackendではDevelopment / ProductionともにPHP-FPMを利用する。

`php artisan serve` はApplication Runtimeとして使用しない。

NginxをLaravel Backend APIのHTTP Entry Pointとし、NginxからFastCGI経由でPHP-FPMへRequestを転送する。

MVPでは以下をApplication Runtime Serviceとして利用する。

```text
frontend
nginx
backend
db
```

Backend Testでは以下のTest Database Serviceを利用する。

```text
test-db
```

`test-db` はBackend Test専用のPostgreSQL Serviceとし、Development Databaseとは分離する。

OpenAPI Toolingには以下のServiceを利用する。

```text
openapi
```

`openapi` ContainerはApplication Runtimeには含めず、Development / CI用Toolingとして利用する。

## 3. Container構成

### frontend

担当：

- Node.js Runtime
- Next.js
- TypeScript
- Better Auth
- Frontend
- BFF
- Browser Session Management
- Backend Credential Management

BrowserからのApplication Entry Pointとする。

DevelopmentではNext.js Development Serverを利用する。

ProductionではNext.js Standalone Outputを利用し、Build済みApplicationをNode.jsで実行する。

Frontend / BFFからLaravel Backend APIへアクセスする場合は、NginxをHTTP Entry Pointとして利用する。

### nginx

担当：

- Laravel Backend APIのHTTP Entry Point
- HTTP Requestの受付
- Laravel `public` Directoryの公開
- FastCGIによるPHP-FPMへのRequest転送

NginxからPHP-FPMへの接続先は以下とする。

```text
backend:9000
```

Development / Productionの両方でNginxを利用する。

DevelopmentではLaravel `public` DirectoryとNginx ConfigurationをBind Mountできる構成とする。

ProductionではNginx ConfigurationとLaravel `public` DirectoryをContainer Imageへ含め、Source Code Bind Mountを必要としない。

### backend

担当：

- PHP-FPM Runtime
- Composer
- Laravel
- Sanctum
- Backend API
- Application / Domain Logic
- 認可
- Validation

Laravel ApplicationはPHP-FPM上で実行する。

HTTP Serverとして `php artisan serve` は使用しない。

NginxからFastCGI経由でRequestを受け付ける。

Development / ProductionともにPHP-FPMを利用し、Runtime差異を抑える。

### db

担当：

- LaravelのApplication Data
- Laravel Sanctumの`personal_access_tokens`

PostgreSQLへの直接アクセスはLaravel Backendに限定する。

Next.js / Better AuthからPostgreSQLへ直接接続しない。

### redis

担当：

- Better Auth Session Store
- Backend Credential Store

MVPでは1つのRedis Instanceを利用し、NamespaceとACLによってAccess権限を分離する。

```text
Redis
├── better-auth:*
│   └── Better Auth Session
└── backend-credential:*
    └── Encrypted Backend Credential
```

Backend CredentialはApplication Level Encryptionを適用して保存する。

### test-db

担当：

- Backend Integration Test用Database
- Backend Feature TestでDatabaseが必要な場合のTest Database
- Migrationを含むPostgreSQL依存処理の検証

Production / Developmentと同じPostgreSQLを利用し、Database Engine差異によるTest結果の差を避ける。

Development Databaseとは分離し、Test実行によってDevelopment Dataへ影響を与えない構成とする。

Test Databaseは永続化を前提とせず、Docker Volumeを割り当てない。

Backend TestからはDocker ComposeのService Name `test-db` を利用して接続する。

### openapi

担当：

- OpenAPI Lint
- OpenAPI Bundle
- TypeScript型生成
- OpenAPI開発環境の再現

利用Tool：

- Redocly CLI
- openapi-typescript

OpenAPI ToolingのDependencyは `openapi/package.json` で管理する。

FrontendのNode.js Dependencyとは分離する。

`openapi` ContainerはApplication通信には参加せず、OpenAPI SpecificationとGenerated Artifactを対象としたTooling専用Containerとして利用する。

Production Runtimeには含めない。

## 4. Container間通信

Container間通信はDocker ComposeのService Nameを利用する。

Container間の通信経路を制限するため、用途ごとにDocker Networkを分離する。

```text
frontend
   |
   | frontend network
   | http://nginx/api/v1
   v
nginx
   |
   | backend network
   | FastCGI
   | backend:9000
   v
backend
   |
   | backend network
   ├───────────────┐
   |               |
   | db:5432       | test-db:5432
   v               v
db              test-db
```

各Containerが参加するNetworkは以下とする。

| Container | frontend network | backend network |
| --- | --- | --- |
| frontend | ○ | - |
| nginx | ○ | ○ |
| backend | - | ○ |
| db | - | ○ |
| test-db | - | ○ |
| openapi | - | - |

以下の通信を許可する。

```text
frontend → nginx   : 許可
nginx    → backend : 許可
backend  → db      : 許可
backend  → test-db : Test時のみ許可

frontend → backend : 直接通信させない
frontend → db      : 許可しない
frontend → test-db : 許可しない
```

FrontendからDatabaseへ直接アクセスさせず、DatabaseへのアクセスはBackendを経由する。

FrontendからPHP-FPMへ直接接続せず、Backend APIへのHTTP RequestはNginxを経由する。

`test-db` はBackend Test専用とし、Frontendから直接アクセスさせない。

`openapi` ContainerはApplication間通信を必要としないため、Application用Networkへ参加させない。

Container間通信では `localhost` を使用しない。

Container内の `localhost` は、そのContainer自身を指すためである。

例：

```text
frontend → nginx

http://nginx/api/v1
```

```text
nginx → backend

backend:9000
```

```text
backend → Development PostgreSQL

host=db
port=5432
```

```text
backend → Test PostgreSQL

host=test-db
port=5432
```

### Backend API接続先

Frontend / BFFからLaravel Backend APIへの接続先は、Server-only環境変数で設定する。

Local Developmentでは以下を利用する。

```text
BACKEND_API_URL=http://nginx/api/v1
```

Docker Compose内部ではContainer側のPortを利用する。

NginxのHost向けPort Mappingが以下の場合でも、

```text
localhost:8000 → nginx:80
```

Frontend ContainerからはHost側の `8000` ではなく、Service NameとContainer側Portを利用する。

```text
http://nginx/api/v1
```

環境変数はRepository Rootの `.env` からDocker Composeを経由して `frontend` Containerへ渡す。

```text
.env
   ↓
Docker Compose
   ↓
frontend Container
   ↓
process.env.BACKEND_API_URL
   ↓
Nginx
   ↓
Laravel Backend API
```

Application CodeへBackend APIのHost名やBase URLをHard Codingせず、環境ごとに接続先を変更できる構成とする。

`BACKEND_API_URL` はNext.js Server / BFFからのみ利用する。

Browserへ公開する環境変数ではないため、`NEXT_PUBLIC_` Prefixは付与しない。

`BACKEND_API_URL` はRuntime環境変数として解決し、Production ImageのBuild時に環境固有のBackend URLを埋め込まない。

Repositoryでは `.env` をGit管理せず、設定例として `.env.example` をGit管理する。

開発時の基本構成は以下とする。

```text
Browser
   |
   | http://localhost:3000
   v
frontend
   |
   | frontend network
   | http://nginx/api/v1
   v
nginx
   |
   | backend network
   | FastCGI backend:9000
   v
backend
   |
   | backend network
   | db:5432
   v
db
```

### frontend

Hostへ公開する。

```text
http://localhost:3000
```

Browserは原則としてNext.jsへアクセスする。

### nginx

開発・API確認用途のためHostへ公開する。

```text
http://localhost:8000
```

Host側Port `8000` をNginx ContainerのPort `80` へMappingする。

```text
localhost:8000
    ↓
nginx:80
```

Backend APIのBase URLは以下とする。

```text
http://localhost:8000/api/v1
```

以下の用途を想定する。

- API単体の動作確認
- curl等による確認
- OpenAPI仕様との動作確認
- Debug

Browser Applicationからの通常アクセスはNext.js BFF経由を基本とする。

### backend

PHP-FPMのPort `9000` はHostへ公開しない。

PHP-FPMはNginxからDocker Network経由で利用する。

```text
nginx
   |
   | FastCGI
   v
backend:9000
```

### db

原則としてHostへ公開しない。

```text
backend
   |
   | backend network
   v
db:5432
```

で利用する。

DB Client等からHost経由で直接接続する必要が発生した場合のみ、開発用途としてPort公開を追加する。

### test-db

Hostへ公開しない。

```text
backend
   |
   | backend network
   v
test-db:5432
```

Backend Testからのみ利用する。

### openapi

HostへPort公開しない。

`openapi` ContainerはHTTP Serviceを提供せず、OpenAPI ToolingをCommandとして実行するために利用する。

## 6. Development / Production共通方針

Development / Productionで主要RuntimeとApplication通信経路を可能な限り共通化する。

共通するRuntime：

```text
Frontend
└── Node.js / Next.js

Backend HTTP Entry Point
└── Nginx

Backend Application Runtime
└── PHP-FPM / Laravel
```

Backendの通信経路はDevelopment / Productionともに以下とする。

```text
HTTP
 ↓
Nginx
 ↓ FastCGI
PHP-FPM
 ↓
Laravel
```

Development / Productionの主な差異は以下とする。

| 項目 | Development | Production |
| --- | --- | --- |
| Frontend Runtime | Next.js Development Server | Next.js Standalone |
| Frontend Source | Bind Mount | ImageへCOPY |
| Frontend Dependency | Development Dependencyを含む | Build済みStandalone Runtime |
| Backend Runtime | PHP-FPM | PHP-FPM |
| Backend Source | Bind Mount | ImageへCOPY |
| Composer Dependency | Development Dependencyを含む | `--no-dev` |
| Nginx | Nginx | Nginx |
| Nginx Public Files | Bind Mount | ImageへCOPY |
| Nginx Configuration | Bind Mount | ImageへCOPY |
| PostgreSQL | Docker Compose | Production環境のDatabase |
| OpenAPI | Development / CI Tooling | Runtimeには含めない |

Development固有の利便性を維持しながら、Productionとの差異をSource Code Mount、Dependency、Build Artifact、環境設定等へ限定する。

## 7. Source Code

### Development

DevelopmentではSource CodeをHost側で管理し、ContainerへBind Mountする。

```text
Host
   |
   | Bind Mount
   v
Container
```

EditorはHost側で利用する。

例：

- Neovim
- VS Code
- その他

Editor自体をContainer内で実行することは前提としない。

Git操作もHost側を基本とする。

### Production

ProductionではSource Code Bind Mountを利用しない。

Applicationの実行に必要なFileはDocker Image Build時にImageへ含める。

```text
Source Code
   |
   | docker build
   v
Container Image
   |
   | deploy
   v
Production Runtime
```

Production ContainerはHost側Repositoryの存在を前提としない。

## 8. frontendのVolume

DevelopmentではfrontendのSource CodeをContainerへMountする。

```text
./frontend
    ↓
/app
```

`node_modules` はHostと共有せず、Docker Volumeで管理する。

概念例：

```yaml
volumes:
  - ./frontend:/app
  - frontend_node_modules:/app/node_modules
```

目的：

- macOSとLinux Containerの依存関係を分離する
- Native ModuleのPlatform差異を避ける
- Host側へ大量の `node_modules` を配置しない
- Container内のNode.js環境で依存関係を統一する

ProductionではSource Codeおよび `node_modules` のBind Mountを利用しない。

---

## 9. backendのVolume

DevelopmentではbackendのSource CodeをContainerへMountする。

```text
./backend
    ↓
/app
```

`vendor` はHostと共有せず、Docker Volumeで管理する。

概念例：

```yaml
volumes:
  - ./backend:/app
  - backend_vendor:/app/vendor
```

Composer CommandはContainer内で実行する。

例：

```bash
docker compose exec backend composer install
```

```bash
docker compose exec backend composer require ...
```

目的：

- PHP依存関係をContainer側で管理する
- Host側PHP環境への依存を避ける
- Container Runtimeとの整合性を保つ

ProductionではSource Codeおよび `vendor` のBind Mountを利用しない。

Production Image Build時にComposer DependencyをInstallし、Development Dependencyは含めない。

LaravelがRuntimeで書き込みを必要とする以下のDirectoryは、PHP-FPM Workerが書き込み可能なPermissionを設定する。

```text
storage
bootstrap/cache
```

---

## 10. NginxのVolume

DevelopmentではLaravelの `public` DirectoryとNginx ConfigurationをBind Mountする。

```text
./backend/public
    ↓
/app/public
```

```text
./backend/docker/nginx/default.conf
    ↓
/etc/nginx/conf.d/default.conf
```

ProductionではBind Mountを利用せず、Nginx Imageへ以下をCOPYする。

```text
backend/public
backend/docker/nginx/default.conf
```

Development / Productionで同じNginx ConfigurationとHTTP / FastCGI通信方式を利用する。

## 11. OpenAPIのVolume

OpenAPI Specificationを `openapi` ContainerへMountする。

```text
./openapi
    ↓
/app
```

OpenAPI Toolingの `node_modules` はHostと共有せず、Docker Volumeで管理する。

TypeScript Generated Typeの出力先としてFrontend側のGenerated DirectoryをMountする。

概念例：

```yaml
volumes:
  - ./openapi:/app
  - ./frontend/src/lib/api/generated:/frontend/src/lib/api/generated
  - openapi_node_modules:/app/node_modules
```

これにより、OpenAPI Specificationから生成したTypeScript型を以下へ出力する。

```text
frontend/src/lib/api/generated/schema.d.ts
```

OpenAPI Bundleは以下へ生成する。

```text
openapi/dist/openapi.yaml
```

Git管理方針：

```text
openapi/dist/
→ Git管理しない

frontend/src/lib/api/generated/schema.d.ts
→ Git管理する
```

OpenAPI ContainerはDevelopment / CI用Toolingであり、Production Runtimeには含めない。

## 12. PostgreSQL

### Development Database

PostgreSQLのData DirectoryにはDocker Volumeを利用する。

```text
postgres_data
    ↓
PostgreSQL Data
```

通常のContainer停止・削除ではDatabase Dataを保持する。

```bash
docker compose down
```

Volumeまで削除した場合はDatabase Dataも削除される。

```bash
docker compose down -v
```

開発データを初期化する場合など、意図的にVolumeを削除する場合のみ `-v` を利用する。

PostgreSQLは原則としてHostへPort公開せず、`backend` Network内からService Name `db` を利用して接続する。

### Test Database

Backend TestではDevelopment Databaseとは分離したPostgreSQLを利用する。

Docker Composeでは以下のServiceを利用する。

```text
test-db
```

Test Database名：

```text
engineer_skill_management_test
```

Backend Testからは以下の接続先を利用する。

```text
host=test-db
port=5432
```

Test DatabaseはTest実行専用とし、Development Database `db` をBackend Testから利用しない。

`test-db` にはDocker Volumeを割り当てず、Test Dataの永続化を前提としない。

LaravelのTest環境設定は以下で管理する。

```text
backend/.env.testing
```

`.env.testing` にはLocal / CI Test専用の設定のみを定義し、Production Secretを含めない。

Development環境では `backend/.env`、Test環境では `backend/.env.testing` を利用する。

```text
Development
backend/.env
    ↓
db
    ↓
engineer_skill_management

Testing
backend/.env.testing
    ↓
test-db
    ↓
engineer_skill_management_test
```

`.env` はGit管理せず、`.env.example` と `.env.testing` はGit管理する。

Production DatabaseのProvisioning、Managed PostgreSQL、Backup、Availability等はLocal Development用Docker Composeの責務には含めない。

## 13. Dockerfile

### frontend

Frontend DockerfileはMulti-stage Buildを利用する。

主なStage：

```text
base
dependencies
development
builder
production
```

Developmentでは `development` Stageを利用する。

ProductionではNext.jsをBuildし、Standalone OutputをProduction ImageへCOPYする。

Production Runtimeは以下を利用する。

```text
node server.js
```

Production ImageはDevelopment Source Bind Mountを必要としない。

### backend

Backend DockerfileはMulti-stage Buildを利用する。

主なStage：

```text
base
development
production
```

Development / ProductionともにPHP-FPMをRuntimeとして利用する。

DevelopmentではDevelopment Dependencyを含めてComposer Installを行う。

Productionでは以下の方針でComposer DependencyをInstallする。

```text
--no-dev
--prefer-dist
--optimize-autoloader
```

Production ImageはSource Code Bind Mountを必要としない。

### nginx

Nginx用Dockerfileは以下で管理する。

```text
backend/docker/nginx/Dockerfile
```

Nginx Configurationは以下で管理する。

```text
backend/docker/nginx/default.conf
```

Nginx ImageにはLaravelの `public` DirectoryとNginx Configurationを含める。

Developmentでは必要なFileをBind MountしてImage内のFileを上書きできる構成とする。

ProductionではImage内のFileをそのまま利用する。

### openapi

OpenAPI DockerfileはDevelopment / CI Tooling用として利用する。

Production Runtime用Imageとしては利用しない。

## 14. Docker Compose

Monorepo RootにDevelopment / Production相当環境用のDocker Compose定義を配置する。

```text
engineer-skill-management-app/
├── frontend/
│   ├── Dockerfile
│   └── .dockerignore
│
├── backend/
│   ├── Dockerfile
│   ├── .dockerignore
│   ├── docker/
│   │   └── nginx/
│   │       ├── Dockerfile
│   │       └── default.conf
│   ├── .env.example
│   └── .env.testing
│
├── openapi/
│   ├── Dockerfile
│   ├── .dockerignore
│   ├── openapi.yaml
│   ├── redocly.yaml
│   ├── package.json
│   └── pnpm-lock.yaml
│
├── scripts/
│   ├── lib/
│   │   └── common.sh
│   ├── dev-setup.sh
│   ├── dev-up.sh
│   ├── dev-down.sh
│   ├── dev-reset.sh
│   ├── prod-build.sh
│   ├── prod-up.sh
│   ├── prod-down.sh
│   └── smoke-test.sh
│
├── docs/
│
├── .env.example
├── .env.production.example
├── compose.yaml
├── compose.production.yaml
└── README.md
```

`compose.yaml` はLocal Development環境全体のOrchestrationを担当する。

以下を管理する。

```text
frontend
nginx
backend
db
test-db
openapi
```

Development固有のSource Code Bind Mount、Development Dependency、Hot Reload、Test Database、OpenAPI Tooling等を含む。

`compose.production.yaml` はProduction向けContainer ImageとRuntime構成をLocal環境で検証するために利用する。

以下を管理する。

```text
frontend
nginx
backend
db
```

Production相当環境では以下を利用しない。

- Source Code Bind Mount
- Development Dependency
- `test-db`
- `openapi`
- Next.js Development Server

Production向けFrontend / BackendではDockerfileの `production` Stageを利用する。

Docker ComposeによるProduction相当環境は、Production ImageとApplication Runtime構成をLocalで検証するためのものであり、Production Infrastructureそのものとして利用することは前提としない。

実際のProduction Infrastructureでは、将来RenderやAWS ECS等のContainer実行環境へProduction Imageを展開する。

Development / Production相当環境ではDocker Compose Projectを分離する。

Project Nameは各Compose Fileのトップレベル `name` で定義する。

```text
Development
compose.yaml
└── name: engineer-skill-management-app-dev

Production相当
compose.production.yaml
└── name: engineer-skill-management-app-prod
```

Projectを分離することで、Development / Production相当環境間のDocker Resource衝突を防ぐ。

主な対象：

- Container
- Image
- Network
- Volume

Local Development固有の環境変数はRepository Rootの `.env` からDocker Composeへ読み込む。

```text
.env
```

Production相当環境では以下を利用する。

```text
.env.production
```

実値を含む `.env` / `.env.production` はGit管理しない。

必要な環境変数の例は以下で管理する。

```text
.env.example
.env.production.example
```

Laravel BackendのDevelopment環境設定は以下で管理する。

```text
backend/.env
```

Laravel BackendのTest環境設定は以下で管理する。

```text
backend/.env.testing
```

Production SecretやCredentialはContainer Imageへ埋め込まず、Runtime環境変数として注入する。

Production Infrastructure側の以下の要素はLocal Docker Composeの責務には含めない。

- Managed PostgreSQL
- Load Balancer
- TLS終端
- Domain / DNS
- Secret Management
- Container Orchestration
- Auto Scaling
- Cloud固有Network
- Production Monitoring

## 15. Network

Docker Composeでは以下の2 Networkを定義する。

```text
frontend
backend
```

### frontend network

Frontend / BFFとNginx間のHTTP通信に利用する。

参加Container：

```text
frontend
nginx
```

### backend network

Nginx、Laravel Backend、Database間の通信に利用する。

参加Container：

```text
nginx
backend
db
test-db
```

BackendのPHP-FPMはContainer内部のPort `9000` でFastCGI Requestを受け付ける。

Docker ComposeではBackend Serviceの内部通信Portを明示するため、`expose` に `9000` を定義する。

```yaml
backend:
  expose:
    - "9000"
```

`9000` はHostへ公開せず、`backend` Network内からのみ利用する。

NginxからPHP-FPMへは以下の接続先を利用する。

```text
backend:9000
```

Nginxは両方のNetworkへ参加し、Frontend側HTTP通信とBackend側FastCGI通信の境界として機能する。

```text
                   frontend network
frontend <──────────────────────────> nginx
                                        |
                                        | backend network
                                        | FastCGI backend:9000
                                        v
                                     backend
                                        |
                                        | backend network
                              ┌─────────┴─────────┐
                              v                   v
                             db                test-db
```

`frontend` Containerは `backend` Networkへ参加させない。

`backend` Containerは `frontend` Networkへ参加させない。

`db` および `test-db` Containerは `frontend` Networkへ参加させない。

これにより、FrontendからPHP-FPMやDatabaseへの直接通信を許可しない。

`test-db` はBackend Test専用として利用する。

`openapi` ContainerはApplication用Networkへ参加させない。

---

## 16. Healthcheck・起動依存

Containerが起動した状態と、ApplicationやDatabaseが利用可能な状態は区別する。

PostgreSQLにはHealthcheckを設定する。

```text
db
 |
 | healthcheck
 v
backend
```

BackendがDevelopment PostgreSQLを必要とする場合は、PostgreSQLのHealthcheckを利用して起動依存関係を管理する。

Docker Composeでは以下のように依存関係を定義する。

```yaml
depends_on:
  db:
    condition: service_healthy
```

Backend Test用の `test-db` にもPostgreSQL Healthcheckを設定する。

ただし、通常のBackend Application起動は `test-db` に依存させない。

`test-db` はBackend Test実行時に利用するTest専用Serviceとして扱う。

NginxはBackend PHP-FPMの起動後に起動する構成とする。

必要に応じてApplication ServiceにもHealthcheckを追加する。

ただし、Docker Composeの起動順序だけにApplicationの可用性を依存させない。

Application側でも一時的な接続失敗が発生し得ることを前提とする。

`openapi` ContainerはApplication Serviceへの起動依存を持たない。

## 17. Development環境操作

Development環境の通常操作は `scripts/` 配下のShell Scriptを利用する。

Docker Compose Commandを利用者が毎回直接組み立てるのではなく、環境操作のEntry PointをScriptへ統一する。

### 初回構築

新規Clone後など、Development環境を初期構築する場合：


```text

        ↓
backend/.env確認・生成
        ↓
Docker Compose Configuration検証
        ↓
Development Image Build
        ↓
Container起動
        ↓
Laravel APP_KEY確認・生成
        ↓
Database Migration
        ↓
OpenAPI検証・型生成
        ↓
Smoke Test
```

`.env` が存在しない場合は `.env.example` から生成する。

`backend/.env` が存在しない場合は `backend/.env.example` から生成する。

Laravel `APP_KEY` は未設定の場合のみ生成し、既存のKeyを不用意に変更しない。

### 起動

Development環境を起動する場合：

```bash
./scripts/dev-up.sh
```

Development Compose Projectとして以下を利用する。

```text
engineer-skill-management-app-dev
```

Project Nameは `compose.yaml` のトップレベル `name` で定義する。

`dev-up.sh` は `.env` の存在を確認し、Docker Compose Configurationを検証した後、Development Containerを起動する。

### 停止

Development環境を停止する場合：

```bash
./scripts/dev-down.sh
```

通常停止ではDocker Volumeを削除しない。

Database DataやDependency Volumeは保持する。

### 初期化

Development環境を完全に初期化して再構築する場合：

```bash
./scripts/dev-reset.sh
```

`dev-reset.sh` はDevelopment用Container、Network、Named Volumeを削除した後、`dev-setup.sh` を実行してDevelopment環境を再構築する。

概念的な処理：

```text
Container停止
      ↓
Container削除
      ↓
Network削除
      ↓
Named Volume削除
      ↓
dev-setup.sh
      ↓
Development環境再構築
```

Named Volumeを削除するため、以下を含むDevelopment Dataは削除される。

```text
PostgreSQL Data
frontend node_modules
backend vendor
openapi node_modules
```

一方、以下は削除しない。

```text
Source Code
.env
backend/.env
Docker Image
```

`dev-reset.sh` はDevelopment Databaseを削除する破壊的操作を含むため、実行時にWarningを表示する。

### 状態確認

必要に応じてDocker Composeを直接利用して状態を確認する。

```bash
docker compose ps
```

ログ確認：

```bash
docker compose logs -f
```

特定Serviceのログ確認：

```bash
docker compose logs -f frontend
```

```bash
docker compose logs -f nginx
```

```bash
docker compose logs -f backend
```

```bash
docker compose logs -f db
```

Docker Composeの直接操作は、通常の起動・停止用途ではなく、状態確認・Debug・個別Service操作等に利用する。

### Frontend / BFF・Backend API疎通確認

Development / Production相当環境の基本的な疎通確認には以下を利用する。

```bash
./scripts/smoke-test.sh
```

Defaultでは以下を確認する。

```text

http://localhost:3000

Backend Health Check
http://localhost:8000/api/v1/health
```

Frontend / Backend URLは環境変数で上書き可能な構成とする。

```text
Browser / Host
   |
   | GET http://localhost:3000/api/health

Next.js Route Handler

Nginx

Laravel Backend API

200 OK
{"status":"ok"}
```

Backend API単体を確認する場合：

Browser ApplicationからLaravel Backend APIを直接呼び出す用途には使用せず、通常のApplication通信はNext.js BFFを経由する。

## 19. 環境操作Script

Development / Production相当環境の操作ScriptはRepository Rootの `scripts/` で管理する。

```text
scripts/
├── lib/
│   └── common.sh
├── dev-setup.sh
├── dev-up.sh
├── dev-down.sh
├── dev-reset.sh
├── prod-build.sh
├── prod-up.sh
├── prod-down.sh
└── smoke-test.sh
```

各Scriptの責務：

| Script | 責務 |
| --- | --- |
| `dev-setup.sh` | Development環境の初期構築 |
| `dev-up.sh` | Development環境の起動 |
| `dev-down.sh` | Development環境の停止 |
| `dev-reset.sh` | Development環境の初期化・再構築 |
| `prod-build.sh` | Production ImageのBuild |
| `prod-up.sh` | Production相当環境の起動 |
| `prod-down.sh` | Production相当環境の停止 |
| `smoke-test.sh` | Frontend / Backendの基本疎通確認 |
| `lib/common.sh` | Docker Compose操作等の共通処理 |

Shell Scriptでは以下を基本とする。

```bash
set -euo pipefail
```

Command失敗時は非0終了コードを返し、後続処理を継続しない。

環境ごとの差異は各Entry Point Scriptで管理し、共通するDocker Compose操作のみ `scripts/lib/common.sh` へ切り出す。

Development / Production相当環境の入口Scriptは分離する。

```text
dev-*.sh
prod-*.sh
```

単一Script内でDevelopment / Productionを大量の条件分岐によって切り替える構成は採用しない。

Shell ScriptのSyntax Checkは以下でまとめて実行できる。

```bash
find scripts -type f -name '*.sh' -print0 | xargs -0 -n1 bash -n
```

### Frontend Formatting

## 23. Source Code変更の反映

DevelopmentではSource CodeをBind Mountし、Next.js / Laravel / Nginx / OpenAPIの変更をContainerへ反映する。

### Next.js

Development ServerのHot Reload / Fast Refreshを利用する。

Next.js Source Codeのみを変更した場合は、通常Containerの再起動を必要としない。

### Laravel

PHP Source Codeの変更はBind Mountを通してContainerへ反映し、次回Requestから変更後のCodeを利用する。

PHP-FPMをDevelopment Runtimeとして利用するため、`php artisan serve` の再起動は必要としない。

### Nginx

Nginx Configurationを変更した場合は、NginxのConfiguration ReloadまたはContainer再起動を行う。

例：

```bash
docker compose restart nginx
```

### OpenAPI

OpenAPI SpecificationはBind Mountされるため、変更後にOpenAPI Commandを再実行することで最新のSpecificationを検証・生成する。

### 環境変数

Docker ComposeからContainerへ渡す環境変数を変更した場合は、対象Containerを再作成して変更を反映する。

例：

```bash
docker compose up -d --force-recreate frontend
```

通常のSource CodeやOpenAPI Specification変更ではDocker Imageの再Buildを必要としない。

以下を変更した場合は再Buildを行う。

- Dockerfile
- `.dockerignore`
- Runtime Version
- OS Package
- PHP Extension
- Node.js Runtime構成
- Composer Dependency
- Node.js Dependency
- OpenAPI ToolingのRuntime構成
- Production Build構成

Development環境全体を再構築する必要がある場合は、以下を利用する。

```bash
./scripts/dev-reset.sh
```

## 24. Production Runtime方針

ProductionではLocal検証用 `compose.production.yaml` をそのままProduction InfrastructureとしてDeploymentすることを前提としない。

Production向けにBuildしたContainer ImageをContainer実行環境へDeployする。

Localの `compose.production.yaml` は、Production ImageとApplication Runtime構成をProduction Deployment前に確認するために利用する。

基本Runtime構成は以下とする。

```text
Client
   |
   | HTTP / HTTPS
   v
Next.js
Standalone Runtime
   |
   | HTTP
   v
Nginx
   |
   | FastCGI
   v
PHP-FPM
Laravel
   |
   v
PostgreSQL
```

Development / Productionで以下を共通化する。

- Node.js / Next.js
- Nginx
- PHP-FPM
- Laravel
- PostgreSQL
- Nginx → PHP-FPMのFastCGI通信
- Next.js BFF → Backend APIのHTTP通信

Productionでは以下を利用しない。

- Source Code Bind Mount
- Development専用Dependency
- Next.js Development Server
- `php artisan serve`
- OpenAPI Tooling Container
- Test Database Container
- Local Development固有設定

LocalのProduction相当環境ではRuntime構成の検証用としてDocker Compose上のPostgreSQLを利用する。

実ProductionではProduction Infrastructure側でProvisionしたManaged PostgreSQL等を利用する。

環境固有のURL、Credential、Secret等はContainer Imageへ埋め込まず、Runtime環境から注入する。

Production Infrastructureとして必要となる以下の構成は、Deployment先の設計で別途定義する。

- Container実行基盤
- Managed PostgreSQL
- Load Balancer
- TLS
- DNS
- Secret Management
- Logging / Monitoring
- Scaling
- Backup / Recovery

Docker Imageは特定のProduction Platformへ強く依存させず、RenderやAWS ECS等のContainer実行環境へ展開可能な構成を基本とする。
