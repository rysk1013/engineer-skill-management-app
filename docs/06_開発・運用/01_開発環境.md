# 開発環境 技術決定

## 1. 採用方式

開発環境はDockerを基本とし、プロジェクト固有のRuntime・MiddlewareはDocker Container上で実行する。

- [x] Next.jsをDockerで実行する
- [x] LaravelをDockerで実行する
- [x] PostgreSQLをDockerで実行する
- [x] OpenAPI ToolingをDockerで実行する
- [ ] Node.jsをHostへ直接インストールして利用する
- [ ] PHP / ComposerをHostへ直接インストールして利用する
- [ ] PostgreSQLをHostへ直接インストールして利用する

Host PCにはプロジェクト固有Runtimeを原則として直接導入しない。

---

## 2. 基本構成

```text id="ngy9o2"
Host PC
   |
   └── Docker Compose
       |
       ├── frontend
       │   ├── Node.js
       │   ├── Next.js
       │   ├── TypeScript
       │   └── Auth.js
       │
       ├── backend
       │   ├── PHP
       │   ├── Composer
       │   ├── Laravel
       │   └── Sanctum
       │
       ├── db
       │   └── PostgreSQL
       │
       └── openapi
           ├── Node.js
           ├── Redocly CLI
           └── openapi-typescript
```

MVPでは以下のApplication / Middleware Containerを常駐Serviceとして利用する。

```text id="6eg0xc"
frontend
backend
db
```

OpenAPI Toolingには以下のServiceを利用する。

```text id="5duklb"
openapi
```

`openapi` Containerは開発Serverとして常駐させず、Lint・Bundle・Type Generation等を実行する際に一時Containerとして起動する。

---

## 3. Container構成

### frontend

担当：

- Node.js Runtime
- Next.js
- TypeScript
- Auth.js
- Frontend
- BFF

BrowserからのApplication Entry Pointとする。

### backend

担当：

- PHP Runtime
- Composer
- Laravel
- Sanctum
- Backend API
- Application / Domain Logic
- 認可
- Validation

Frontend / BFFからBackend APIとして利用する。

### db

担当：

- Laravelの業務データ
- Auth.jsのSession Store

MVPではLaravelとAuth.jsで同一PostgreSQL Instanceを利用する。

論理的なデータ管理責務はApplicationごとに分離する。

### openapi

担当：

- OpenAPI Lint
- OpenAPI Bundle
- TypeScript型生成
- OpenAPI開発環境の再現

利用Tool：

- Redocly CLI
- openapi-typescript

OpenAPI ToolingのDependencyは `openapi/package.json` で管理する。

FrontendのNode.js Dependencyとは分離する。

`openapi` ContainerはApplication通信には参加せず、OpenAPI SpecificationとGenerated Artifactを対象としたTooling専用Containerとして利用する。

---

## 4. Container間通信

Container間通信はDocker ComposeのService Nameを利用する。

Container間の通信経路を制限するため、用途ごとにDocker Networkを分離する。

```text id="81ifjh"
frontend
   |
   | frontend network
   | http://backend:8000
   v
backend
   |
   | backend network
   | db:5432
   v
db
```

各Containerが参加するNetworkは以下とする。

| Container | frontend network | backend network |
| --- | --- | --- |
| frontend | ○ | - |
| backend | ○ | ○ |
| db | - | ○ |
| openapi | - | - |

以下の通信を許可する。

```text id="gzpf25"
frontend → backend : 許可
backend  → db      : 許可
frontend → db      : 許可しない
```

FrontendからDatabaseへ直接アクセスさせず、DatabaseへのアクセスはBackendを経由する。

`openapi` ContainerはApplication間通信を必要としないため、Application用Networkへ参加させない。

Container間通信では`localhost`を使用しない。

Container内の`localhost`は、そのContainer自身を指すためである。

例：

```text id="xspaxf"
frontend → backend

http://backend:8000
```

```text id="5om5ms"
backend → PostgreSQL

host=db
port=5432
```

## 5. Hostからのアクセス

開発時の基本構成は以下とする。

```text id="yqeh4a"
Browser
   |
   | http://localhost:3000
   v
frontend
   |
   | frontend network
   | http://backend:8000
   v
backend
   |
   | backend network
   | db:5432
   v
db
```

### frontend

Hostへ公開する。

```text id="k8znq3"
http://localhost:3000
```

Browserは原則としてNext.jsへアクセスする。

### backend

開発・API確認用途のためHostへ公開する。

```text id="gh5mcj"
http://localhost:8000
```

以下の用途を想定する。

- API単体の動作確認
- curl等による確認
- OpenAPI仕様との動作確認
- Debug

Browser Applicationからの通常アクセスはNext.js BFF経由を基本とする。

### db

原則としてHostへ公開しない。

```text id="bhhx09"
backend
   |
   | backend network
   v
db:5432
```

で利用する。

DB Client等からHost経由で直接接続する必要が発生した場合のみ、開発用途としてPort公開を追加する。

### openapi

HostへPort公開しない。

`openapi` ContainerはHTTP Serviceを提供せず、OpenAPI ToolingをCommandとして実行するために利用する。

## 6. Source Code

Source CodeはHost側で管理し、ContainerへBind Mountする。

```text id="iz4g4v"
Host
   |
   | Bind Mount
   v
Container
```

EditorはHost側で利用する。

例：

- Neovim
- VS Code
- その他

Editor自体をContainer内で実行することは前提としない。

Git操作もHost側を基本とする。

---

## 7. frontendのVolume

frontendのSource CodeをContainerへMountする。

```text id="r7yfbp"
./frontend
    ↓
/app
```

`node_modules`はHostと共有せず、Docker Volumeで管理する。

概念例：

```yaml id="cmn9ns"
volumes:
  - ./frontend:/app
  - frontend_node_modules:/app/node_modules
```

目的：

- macOSとLinux Containerの依存関係を分離する
- Native ModuleのPlatform差異を避ける
- Host側へ大量の`node_modules`を配置しない
- Container内のNode.js環境で依存関係を統一する

---

## 8. backendのVolume

backendのSource CodeをContainerへMountする。

```text id="n8h8bv"
./backend
    ↓
/app
```

`vendor`はHostと共有せず、Docker Volumeで管理する。

概念例：

```yaml id="rhv2ai"
volumes:
  - ./backend:/app
  - backend_vendor:/app/vendor
```

Composer CommandはContainer内で実行する。

例：

```bash id="ax7t0k"
docker compose exec backend composer install
```

```bash id="n1c5z7"
docker compose exec backend composer require ...
```

目的：

- PHP依存関係をContainer側で管理する
- Host側PHP環境への依存を避ける
- Container Runtimeとの整合性を保つ

---

## 9. OpenAPIのVolume

OpenAPI Specificationを `openapi` ContainerへMountする。

```text id="rvjqzc"
./openapi
    ↓
/app
```

OpenAPI Toolingの `node_modules` はHostと共有せず、Docker Volumeで管理する。

TypeScript Generated Typeの出力先としてFrontend側のGenerated DirectoryをMountする。

概念例：

```yaml id="0r7ykh"
volumes:
  - ./openapi:/app
  - ./frontend/src/generated/api:/frontend/src/generated/api
  - openapi_node_modules:/app/node_modules
```

これにより、OpenAPI Specificationから生成したTypeScript型を以下へ出力する。

```text id="y14afj"
frontend/src/generated/api/schema.d.ts
```

OpenAPI Bundleは以下へ生成する。

```text id="pb5emv"
openapi/dist/openapi.yaml
```

Git管理方針：

```text id="fv0y7n"
openapi/dist/
→ Git管理しない

frontend/src/generated/api/schema.d.ts
→ Git管理する
```

## 10. PostgreSQL

PostgreSQLのData DirectoryにはDocker Volumeを利用する。

```text id="wdy1zo"
postgres_data
    ↓
PostgreSQL Data
```

通常のContainer停止・削除ではDatabase Dataを保持する。

```bash id="uvg7q7"
docker compose down
```

Volumeまで削除した場合はDatabase Dataも削除される。

```bash id="l2dwp5"
docker compose down -v
```

開発データを初期化する場合など、意図的にVolumeを削除する場合のみ`-v`を利用する。

PostgreSQLは原則としてHostへPort公開せず、`backend` Network内からService Name `db` を利用して接続する。

## 11. Docker Compose

Monorepo Rootに`compose.yaml`を配置する。

```text id="vd3wkb"
engineer-skill-management-app/
├── frontend/
│   ├── Dockerfile
│   └── .dockerignore
│
├── backend/
│   ├── Dockerfile
│   └── .dockerignore
│
├── openapi/
│   ├── Dockerfile
│   ├── openapi.yaml
│   ├── redocly.yaml
│   ├── package.json
│   └── package-lock.json
│
├── docs/
│
├── compose.yaml

```

`compose.yaml`から開発環境全体を管理できるようにする。

Docker ComposeはLocal Development Environment全体のOrchestrationを担当する。

Application開発用の常駐Serviceと、必要時にCommandとして実行するTooling Serviceの両方をDocker Composeで管理する。

## 12. Network

Docker Composeでは以下の2 Networkを定義する。

```text id="r30ad8"
frontend
backend
```

### frontend network

Frontend / BFFとBackend API間の通信に利用する。

参加Container：

```text id="tbxthn"
frontend
backend
```

### backend network

Backend APIとDatabase間の通信に利用する。

参加Container：

```text id="rw7x1q"
backend
db
```

Backendは両方のNetworkへ参加し、FrontendとDatabaseの境界として機能する。

```text id="w5fawh"
                  frontend network
frontend <────────────────────────> backend
                                      |
                                      | backend network
                                      v
                                     db
```

`frontend` Containerは`backend` Networkへ参加させない。

`db` Containerは`frontend` Networkへ参加させない。

これにより、FrontendからDatabaseへの直接通信を許可しない。

`openapi` ContainerはApplication用Networkへ参加させない。

## 13. Healthcheck・起動依存

Containerが起動した状態と、ApplicationやDatabaseが利用可能な状態は区別する。

PostgreSQLにはHealthcheckを設定する。

```text id="0wp78b"
db
 |
 | healthcheck
 v
backend
```

BackendがPostgreSQLを必要とする場合は、PostgreSQLのHealthcheckを利用して起動依存関係を管理する。

Docker Composeでは、必要に応じて以下のように依存関係を定義する。

```yaml id="3oz4wy"
depends_on:
  db:
    condition: service_healthy
```

必要に応じてBackendにもHealthcheckを設定する。

ただし、Docker Composeの起動順序だけにApplicationの可用性を依存させない。

Application側でも一時的な接続失敗が発生し得ることを前提とする。

`openapi` ContainerはApplication Serviceへの起動依存を持たない。

## 14. 開発環境起動

Application開発環境の基本コマンド：

```bash id="jz4v65"
docker compose up -d
```

初回またはImageを再Buildする場合：

```bash id="k0jzlm"
docker compose up -d --build
```

状態確認：

```bash id="4i3kpc"
docker compose ps
```

ログ確認：

```bash id="p60mt3"
docker compose logs -f
```

特定Serviceのログ確認：

```bash id="ewxzd6"
docker compose logs -f frontend
```

```bash id="62spn4"
docker compose logs -f backend
```

```bash id="m5lcbf"
docker compose logs -f db
```

停止：

```bash id="v15z9d"
docker compose down
```

Databaseを含めたVolumeを意図的に削除する場合：

```bash id="hl2lfy"
docker compose down -v
```

通常の停止では`-v`を使用しない。

`openapi` Serviceは通常の開発環境として常駐させる必要はない。

## 15. Laravel Command

Laravel Commandは`backend` Container内で実行する。

例：

```bash id="iwavsn"
docker compose exec backend php artisan migrate
```

```bash id="p7g6g1"
docker compose exec backend php artisan test
```

```bash id="dzs6p7"
docker compose exec backend php artisan tinker
```

```bash id="gw2hcx"

```

その他のPHP / Composer関連Commandについても原則として`backend` Container内で実行する。

## 16. Next.js Command

Node.js関連Commandは`frontend` Container内で実行する。

例：

```bash id="cmobtu"
docker compose exec frontend npm install
```

```bash id="03rrp5"
docker compose exec frontend npm run lint
```

```bash id="mnvqnl"
docker compose exec frontend npm run build
```

Package Managerはnpmを採用する。

Lock Fileは以下をGitでVersion Controlする。

```text id="9hs8ve"
package-lock.json
```

CIや再現可能な依存関係InstallではLock Fileを利用する。

---

## 17. OpenAPI Command

OpenAPI関連Commandは`openapi` Containerで実行する。

OpenAPI全体を検証する場合：

```bash id="tkkdyh"
docker compose run --rm openapi npm run check
```

Lintのみ実行する場合：

```bash id="qgbw4g"
docker compose run --rm openapi npm run lint
```

Bundleのみ実行する場合：

```bash id="98gf77"
docker compose run --rm openapi npm run bundle
```

TypeScript型生成のみ実行する場合：

```bash id="9zkc8v"
docker compose run --rm openapi npm run generate:types
```

BundleとTypeScript型生成を実行する場合：

```bash id="vq89ab"
docker compose run --rm openapi npm run generate
```

OpenAPI ToolingのPackage Managerはnpmを利用する。

OpenAPI ToolingのDependencyとLock Fileは以下で管理する。

```text id="fdh4d3"
openapi/package.json
openapi/package-lock.json
```

OpenAPI Specification変更後は、原則として以下を実行してLint・Bundle・Type Generationをまとめて確認する。

```bash id="ycvibf"
docker compose run --rm openapi npm run check
```

## 18. Source Code変更の反映

開発時はSource CodeをBind Mountし、Next.js / Laravel / OpenAPIの変更をContainerへ反映する。

### Next.js

Development ServerのHot Reload / Fast Refreshを利用する。

### Laravel

PHP Source Codeの変更はBind Mountを通してContainerへ反映し、次回Requestから変更後のCodeを利用する。

### OpenAPI

OpenAPI SpecificationはBind Mountされるため、変更後にOpenAPI Commandを再実行することで最新のSpecificationを検証・生成する。

通常のSource CodeやOpenAPI Specification変更ではDocker Imageの再Buildを必要としない。

以下を変更した場合は再Buildを行う。

- Dockerfile
- Runtime Version
- OS Package
- PHP Extension
- Node.js Runtime構成
- OpenAPI ToolingのRuntime構成
