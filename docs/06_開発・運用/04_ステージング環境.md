# ステージング環境 インフラ選定・基本方針

## 1. 目的

本ドキュメントでは、Engineer Skill Management AppにおけるStaging Environmentの目的、基本要件、Infrastructure候補および現時点の選定方針を定義する。

Staging EnvironmentはProduction Deployment前に、Productionに近い環境でApplicationおよびDeployment Processを検証するために利用する。

主な目的：

- Container ImageのDeployment検証
- Application起動確認
- Database Migration検証
- Authentication / Authorization確認
- Environment Variable / Secret設定確認
- Frontend / BFF / Backend間通信確認
- Database接続確認
- E2E Test
- Network構成確認
- Logging / Monitoring確認
- CD Pipeline検証
- Production Deployment前の最終確認

---

## 2. 現在の方針

Staging EnvironmentのDeployment先は現時点では確定しない。

Production Environmentも現時点では未確定だが、Productionの決定を待たず、Staging単体として必要な要件を定義してInfrastructure候補を評価する。

現時点では以下を第一候補とする。

```text id="6eqdqy"
AWS ECS
  +
AWS Fargate
  +
Amazon RDS for PostgreSQL
```

実際にStaging Environmentを構築する段階で、以下を再評価して最終決定する。

- Cost
- Infrastructure Complexity
- Operational Load
- Learning Value
- Productionへの移行可能性
- Security
- Network要件
- Observability
- Deployment要件

## 3. Staging Environmentの基本要件

Staging Environmentでは以下を満たすことを基本とする。

### Application

- Next.js Frontend / BFFをDeployできる
- Laravel Backend APIをDeployできる
- PostgreSQLを利用できる
- Frontend / Backendを独立してDeployできる

### Deployment

- Container Imageを利用できる
- Immutable ArtifactをDeployできる
- Git CommitとArtifactを追跡できる
- Database Migrationを実行できる
- GitHub ActionsからDeploymentできる構成を検討できる

### Security

- Laravel Backend APIをPublic Internetへ直接公開しない
- PostgreSQLをPublic Internetへ直接公開しない
- SecretをSource Codeへ保存しない
- Staging専用Credentialを利用する

### Quality

- E2E Testを実行できる
- Authentication / Authorizationを確認できる
- Production Deployment前のVerification Environmentとして利用できる

### Operations

- Application Logを確認できる
- Health Checkを実行できる
- 必要なMonitoringを導入できる
- Deployment Failureを調査できる

## 6. ECSを第一候補とする理由

AWS ECS + Fargateを第一候補とする主な理由：

- Local DevelopmentですでにDockerを採用している
- Next.jsとLaravelを独立したContainerとして扱いやすい
- MonorepoからFrontend / Backendを別ImageとしてBuildできる
- FargateによりEC2 Instance管理を避けられる
- Amazon ECRでContainer Imageを管理できる
- RDS PostgreSQLと組み合わせやすい
- NetworkやSecurity Groupを細かく設計できる
- Backend APIをPrivate Networkへ配置できる構成を検討できる
- Production Environment候補としても評価できる
- Container Infrastructureの設計・運用を学習できる
- ECS / Fargate / ECR / RDS / VPC等のAWS Infrastructureを実践的に学習できる
- 将来的なIaC導入へ発展させやすい

単にStagingを最短で公開することだけではなく、Infrastructure / Container / Network / Security / Deploymentを学習することも選定理由とする。

## 9. Public / Private Network方針

以下を基本原則とする。

```text id="5nj9jd"
Internet
   │
   ▼
Next.js
Public Entry Point
   │
   │ Private
   ▼
Laravel Backend
   │
   │ Private
   ▼
PostgreSQL
```

### Next.js

BrowserからアクセスするためのPublic Entry Pointを持つ。

### Laravel Backend API

Public Internetへ直接公開しない構成を基本とする。

Next.js BFFからPrivate Network経由でアクセスする。

### PostgreSQL

Public Internetへ直接公開しない。

Laravel BackendからPrivate Network経由でアクセスする。

この原則はDeployment Platformが変更された場合も可能な限り維持する。

## 11. PostgreSQL Network方針

RDS PostgreSQLを採用する場合、Public Internetから直接接続できない構成を基本とする。

概念：

```text id="z60pwa"
Internet
   │
   X
   │
RDS PostgreSQL
   ▲
   │
Private Network
   │

```

RDSのPublic Accessを前提としない。

Local MachineからDatabaseへ直接接続する必要が発生した場合でも、Databaseを安易にPublic化せず、安全な管理経路を別途設計する。

## 12. Container Image

Frontend / Backendはそれぞれ独立したContainer ImageとしてBuildする。

```text id="wtmh2a"
Monorepo
   │
   ├── frontend/
   │      ↓
   │   Next.js Image
   │
   └── backend/
          ↓
       Laravel Image
```

Container ImageはImmutable Artifactとして扱う。

Mutableな`latest` Tagだけに依存しない。

Git Commitを追跡可能なIdentifierを付与する。

概念：

```text id="bih6pn"
Git Commit
    ↓
Container Image
    ↓
Commit SHA
```

例：

```text id="p5j9e6"
frontend:<commit-sha>
backend:<commit-sha>
```

Production Deploymentへ進む場合も、どのSource Codeから生成されたArtifactか追跡できる状態を維持する。

---

## 13. Build Once / Deploy Same Artifact

`03_CICD方針.md`で定義したBuild Once / Deploy Same ArtifactをStagingでも適用する。

概念：

```text id="cph1h6"
main
 ↓
CI
 ↓
Container Image Build
 ↓
Amazon ECR
 ↓
Immutable Image
 ↓
Staging
```

将来ProductionへDeployする場合：

```text id="r8yn9b"
Amazon ECR
    │
    └── Image: <commit-sha>
             │
             ├── Staging
             │      ↓
             │  Verification
             │
             └── Production
```

Stagingで検証したArtifactとProductionへDeployするArtifactを可能な限り同一にする。

EnvironmentごとにApplication ImageをBuildし直すことを基本としない。

## 15. GitHub ActionsからAWSへの認証

GitHub ActionsからAWSへ接続する場合はOIDCを第一候補とする。

概念：

```text id="chhz0g"
GitHub Actions
      │
      ▼
     OIDC
      │
      ▼
AWS IAM Role
      │
      ▼
Temporary Credential
```

長期間有効なAWS Access KeyをGitHub Secretsへ保存する方式を原則として避ける。

GitHub Actionsへ付与するAWS PermissionはLeast Privilegeとする。

具体的なIAM Role / PolicyはInfrastructure設計時に決定する。

## 16. Database Migration

Database MigrationはDeployment Process内の明示的なStepとして扱う。

Application Container起動時に各Containerが暗黙的にMigrationを実行する構成は基本としない。

概念：

```text id="szb5eq"
Artifact
   ↓
Deployment Process
   ↓
Migration
   ↓
Application Deployment
   ↓
Health Check
```

実際のMigration実行方式はECS / Deployment設計時に決定する。

候補：

- ECS One-off Task
- GitHub ActionsからMigration Task実行
- Deployment Pipeline内の専用Step
- その他Deployment Platform固有方式

Migration Failure時にApplication Deploymentを継続しない構成を基本とする。

MigrationとRollbackの関係についてもProduction Deployment設計時に検討する。

---

## 17. Staging Data

StagingではProduction Dataをそのまま利用しないことを基本とする。

基本候補：

```text id="1avfkm"
Staging Database
├── Seed Data
├── Test Data
└── Synthetic Data
```

以下を目的とする。

- 個人情報の不要な複製を防ぐ
- Production Dataへの依存を避ける
- Testを再現可能にする
- Staging Environmentを安全にResetできるようにする

Production DataをStagingで利用する必要が生じた場合は、匿名化・Masking・Access Control等を別途設計する。

---

## 18. Secret・Environment Variable

StagingではStaging専用Secretを利用する。

```text id="tg5dyz"
Development
    │
    ├── Development Secrets
    │
Staging
    │
    ├── Staging Secrets
    │
Production
    │
    └── Production Secrets
```

StagingとProductionでSecretを共有しないことを基本とする。

対象例：

- Auth.js Secret
- Laravel `APP_KEY`
- Database Credential
- API Credential
- その他Secret

SecretをContainer Imageへ埋め込まない。

Runtimeで安全に注入する構成とする。

具体的なSecret管理方式はInfrastructure設計時に決定する。

## 26. StagingとProductionの関係

StagingとProductionはApplication ArchitectureおよびDeployment原則を可能な限り近づける。

### 可能な限り共通化するもの

- Application Architecture
- Container Image
- Runtime
- Database Engine
- Migration
- Environment Variable構造
- Deployment Process
- Health Check
- Network Securityの基本原則

### 異なってよいもの

- CPU
- Memory
- Desired Count
- Database Instance Size
- Storage Size
- Scaling設定
- Availability構成
- Backup保持期間
- Monitoring / Alerting Level
- Cost Optimization

概念：

```text id="hrcr8b"
Staging
   │
   │ Same Architecture Principle
   │ Same Artifact
   │ Same Runtime
   ▼
Production

Resource Size / Availability
        ≠
必ずしも同一ではない
```

StagingとProductionを完全に同一構成にすることを目的とはしない。

重要なのはProductionで発生する問題をStagingで可能な限り事前検証できることである。

## 28. MVPで過度に行わないこと

Staging初期構築では以下を過度に作り込まない。

- Multi-Region
- Multi-Cloud
- 高度なAuto Scaling
- Blue / Green Deployment
- Canary Release
- Production同等の冗長化
- 過度なMonitoring / Alerting
- 複雑なNetwork構成
- 複雑なArtifact Promotion System
- 不要なAWS Service追加

まず以下を優先する。

```text id="w92s6u"
Deployできる
      ↓
動作確認できる
      ↓
安全に接続できる
      ↓
問題を調査できる
      ↓
再現可能にDeployできる
```
