# ステージング環境 インフラ選定状況

## 1. 現在の方針

ステージング環境のデプロイ先は現時点では確定しない。

本番環境も未定のため、
ステージング環境についても候補を保持した状態で設計を進める。

ただし、現時点ではAWS ECSを第一候補とする。

## 4. ECSを第一候補とする理由

- 開発環境ですでにDockerを採用している
- Next.jsとLaravelを独立したContainerとして扱いやすい
- MonorepoでもFrontend / Backendを別ImageとしてBuildできる
- Fargateを利用すればEC2 Instance管理を避けられる
- Amazon ECRでContainer Imageを管理できる
- RDS PostgreSQLと組み合わせやすい
- NetworkやSecurity Groupを細かく制御できる
- Backend APIをPrivate Network側へ配置する構成を検討できる
- Production環境の候補としても利用できる
- AWS Container Infrastructureの知識をそのまま活用できる

## 11. App Runnerとの位置付け

AWS App Runnerも候補として残す。

App RunnerはECSより構成が単純なため、

- Stagingを早く作りたい
- Infrastructure管理を減らしたい

という要件が強くなった場合に再検討する。

ただし現時点ではECSを優先する。

---

## 12. Renderとの位置付け

Renderも候補として残す。

ただしFree PostgreSQL等の制約があるため、
長期的なStaging環境の第一候補とはしない。

短期間のMVP公開・検証用途では再検討可能とする。

---

## 13. Productionとの関係

StagingでECSを採用した場合でも、
Productionを必ずECSにする必要はない。

ただし、

    Staging
    ECS + Fargate + RDS

で運用実績を得られた場合、

    Production
    ECS + Fargate + RDS

を有力候補として評価できる。
