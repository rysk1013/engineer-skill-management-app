# 複雑度監視 技術決定

## 1. 方針

Frontend / Backendの両方でサイクロマチック複雑度を監視する。

採用ツール：

### Frontend / BFF

- ESLint
- ESLint `complexity` Rule

### Backend API

- PHPMD

---

## 2. 目的

複雑なFunction / Methodを早期に検出し、
以下のリスクを抑える。

- 条件分岐の増加
- テストケースの増大
- 変更影響範囲の把握困難
- 可読性低下
- 保守性低下
- Bug混入リスクの増加

複雑度そのものを品質目標にはせず、
リファクタリングを検討するための指標として利用する。

---

## 3. Frontend / BFF

Frontend / BFFではESLintの `complexity` Ruleを利用する。

対象：

- React Component
- Server Component
- Client Component
- Route Handler
- Server Action
- BFF処理
- Utility
- Form Logic

---

## 4. Frontendで監視する例

以下のように条件分岐が増えた処理を検出する。

    function getSkillFormState(skill) {
        if (...) {
            ...
        }

        if (...) {
            ...
        }

        if (...) {
            ...
        }
    }

特に以下のような処理を重点的に確認する。

- Form状態制御
- 実務経験による入力切り替え
- 権限による表示制御
- BFF Error Handling
- API Response変換

---

## 5. Frontendの基本方針

MVPでは複雑度の計測・警告を目的とする。

初期段階から厳格なCI失敗条件にはしない。

例：

    Code
      ↓
    ESLint
      ↓
    complexity Rule
      ↓
    複雑なFunctionを検出
      ↓
    Review時に確認

---

## 6. Backend API

Backend APIではPHPMDを利用する。

主な監視対象：

- Cyclomatic Complexity
- NPath Complexity
- Method Length
- Class Length
- Parameter Count
- Coupling
- その他のCode Smell

---

## 7. Backendで重点的に確認する箇所

今回のアプリでは以下の処理が複雑になりやすい。

- Authorization
- 社員スキル登録
- 社員スキル編集
- 実務経験によるValidation
- 権限管理
- 担当社員判定
- マスタ統合
- 複数スキル検索

---

## 8. PHPMDの役割

PHPMDはコードスメルと複雑度の検出を担当する。

PHPStan / Larastanとは役割を分ける。

### Pint

担当：

- Formatting

### PHPStan + Larastan

担当：

- Static Analysis
- Type Safety

### PHPMD

担当：

- Complexity
- Code Smell
- Maintainability

### PHPUnit

担当：

- Behavior
- Business Rule
- API Test

---

## 9. Frontend / Backendの役割比較

| 対象 | ツール | 主な目的 |
| --- | --- | --- |
| Frontend / BFF | ESLint complexity | Cyclomatic Complexity |
| Backend API | PHPMD | Complexity / Code Smell |
| Frontend | TypeScript | Type Safety |
| Backend | PHPStan + Larastan | Static Analysis |
| Frontend | Prettier | Formatting |
| Backend | Pint | Formatting |

---

## 10. CIでの扱い

MVPでは複雑度を監視するが、
厳格な品質ゲートにはしない。

### Phase 1：MVP

    ESLint complexity
         +
    PHPMD
         ↓
    Complexityを計測
         ↓
    Review時に確認

### Phase 2：運用安定後

実際のCodebaseを確認し、
適切なThresholdを決定する。

    Threshold超過
         ↓
    Warning

### Phase 3：必要な場合

重大なThreshold超過についてのみ、

    CI Failure

とすることを検討する。

---

## 11. Threshold

初期段階ではThresholdを過度に厳しくしない。

具体的な値はProject Setup時または
一定量のCodeが蓄積された段階で決定する。

候補例：

    Cyclomatic Complexity

    1 - 5
    シンプル

    6 - 10
    Review対象

    11以上
    リファクタリング検討

この数値を絶対的な品質基準にはしない。

---

## 12. リファクタリング判断

複雑度が高い場合は以下を検討する。

- Method分割
- Component分割
- Conditionの整理
- Early Return
- Policyへの責務移動
- Service / UseCaseへの責務分離
- Value Objectの利用
- Strategy等の設計パターン
- 重複処理の共通化

ただし、複雑度を下げるためだけの過度な抽象化は行わない。

---

## 13. Frontendでの注意

React Componentの複雑度が高い場合、

    UI
    +
    State
    +
    Validation
    +
    API処理
    +
    Permission

が1Componentに集中している可能性がある。

必要に応じて以下へ分離する。

- Component
- Hook
- Utility
- Form Schema
- API Client

---

## 14. Backendでの注意

Laravelで複雑度が高い場合、

    Controller
       ↓
    Validation
    Authorization
    Business Logic
    Database Access

が集中していないか確認する。

Controllerへ業務処理を詰め込みすぎない。

必要に応じて以下へ責務を分離する。

- Form Request
- Policy
- Service / UseCase
- Model / Domain
- Repository

---

## 15. 可視化

MVPでは専用Dashboardによる複雑度可視化は導入しない。

以下で確認できれば十分とする。

- ESLint Output
- PHPMD Report
- CI Log
- Pull Request Review

将来的に必要になった場合は以下を検討する。

- SonarQube
- SonarCloud
- Code Climate
- その他Code Quality Platform

---

## 18. CI品質チェック

Pull Request時に以下を実行することを基本とする。

### Frontend

- Prettier Check
- ESLint
- Complexity Check
- TypeScript Type Check
- Vitest

### Backend

- Pint Check
- PHPStan / Larastan
- PHPMD
- PHPUnit

---

## 19. 基本方針

- Frontend / Backendの両方で複雑度を監視する
- FrontendはESLint complexityを利用する
- BackendはPHPMDを利用する
- MVPでは計測・警告を中心とする
- 初期段階では複雑度だけでCIを失敗させない
- Codebaseの傾向を見てThresholdを調整する
- 複雑度を絶対的な品質指標として扱わない
- 複雑度低減のための過度な抽象化を避ける
- Review / Test / Static Analysisと組み合わせて判断する

---

## 20. 決定事項

### Frontend / BFF Complexity

ESLint `complexity` Ruleを採用する。

### Backend Complexity

PHPMDを採用する。

### MVP

複雑度を計測・監視する。

### CI

MVPでは複雑度超過のみを理由としたCI Failureを原則行わない。

### 将来

実際のCodebaseを確認したうえでThresholdを決定し、
必要に応じてWarningまたはCI Quality Gateへ変更する。
