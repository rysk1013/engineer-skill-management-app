# 開発環境 技術決定

## 1. 採用方式

開発環境はすべてDockerコンテナ上で構築する。

- [x] Next.jsをDockerで実行する
- [x] LaravelをDockerで実行する
- [x] PostgreSQLをDockerで実行する
- [ ] Node.jsをホストへ直接インストールして利用する
- [ ] PHP / Composerをホストへ直接インストールして利用する
- [ ] PostgreSQLをホストへ直接インストールして利用する

---

## 2. 基本構成

    Host PC
       |
       └── Docker Compose
           |
           ├── frontend
           │   ├── Node.js
           │   ├── Next.js
           │   ├── TypeScript
           │   └── Auth.js
           │
           ├── backend
           │   ├── PHP
           │   ├── Composer
           │   ├── Laravel
           │   └── Sanctum
           │
           └── postgres
               └── PostgreSQL

---

## 3. コンテナ構成

### frontend

担当：

- Next.js
- TypeScript
- Auth.js
- Frontend
- BFF

### backend

担当：

- PHP
- Laravel
- Sanctum
- Backend API
- 業務ロジック
- 認可
- バリデーション

### postgres

担当：

- Laravelの業務データ
- Auth.jsのSession Store

---

## 4. 通信

コンテナ間通信はDocker ComposeのService Nameを利用する。

例：

    frontend
       |
       | http://backend:8000
       v
    backend
       |
       | postgres:5432
       v
    postgres

コンテナ間通信でlocalhostを使用しない。

---

## 5. Hostからのアクセス

開発時の想定：

    Next.js
    http://localhost:3000

    Laravel API
    http://localhost:8000

    PostgreSQL
    localhost:5432

Laravel APIやPostgreSQLをHostへ公開する必要性については、
開発用途に応じて決定する。

Browserは基本的にNext.jsへアクセスする。

---

## 6. Source Code

Source CodeはHost側で管理し、ContainerへVolume Mountする。

    Host
       |
       | Volume Mount
       v
    Container

EditorはHost側で利用する。

例：

- Neovim
- VS Code
- その他

Editor自体をContainer内で実行することは前提としない。

---

## 7. frontendのVolume

frontendのSource CodeをContainerへMountする。

    ./frontend
        ↓
    /app

node_modulesはHostと共有せず、
Docker Volumeで管理することを基本とする。

目的：

- macOSとLinux Containerの依存関係を分離する
- Native Moduleの問題を避ける
- Host側へ大量のnode_modulesを配置しない

---

## 8. backendのVolume

backendのSource CodeをContainerへMountする。

    ./backend
        ↓
    /app

vendorについてもContainer側で管理することを基本とする。

Composer CommandはContainer内で実行する。

例：

    docker compose exec backend composer install

    docker compose exec backend composer require ...

---

## 9. PostgreSQL

PostgreSQLのData DirectoryにはDocker Volumeを利用する。

    postgres_data
        ↓
    PostgreSQL Data

以下の場合でもデータを保持する。

    docker compose down

以下の場合はVolumeも削除されるため、
Database Dataも削除される。

    docker compose down -v

---

## 10. Docker Compose

Monorepo Rootにcompose.yamlを配置する。

例：

    engineer-skill-management/
    ├── frontend/
    │   └── Dockerfile
    │
    ├── backend/
    │   └── Dockerfile
    │
    ├── docs/
    │
    ├── compose.yaml
    └── README.md

compose.yamlから開発環境全体を起動できるようにする。

---

## 11. 開発環境起動

基本コマンド：

    docker compose up -d

状態確認：

    docker compose ps

ログ確認：

    docker compose logs -f

停止：

    docker compose down

---

## 12. Laravel Command

Laravel Commandはbackend Container内で実行する。

例：

    docker compose exec backend php artisan migrate

    docker compose exec backend php artisan test

    docker compose exec backend php artisan tinker

---

## 13. Next.js Command

Node.js Commandはfrontend Container内で実行する。

例：

    docker compose exec frontend npm install

    docker compose exec frontend npm run lint

    docker compose exec frontend npm test

---

## 14. Hot Reload

開発時はSource CodeをVolume Mountし、
Next.js / Laravelの変更をContainerへ即時反映できる構成とする。

通常のSource Code変更ではDocker Imageの再Buildを必要としない。

DockerfileやRuntime依存関係を変更した場合は再Buildする。

例：

    docker compose build frontend

    docker compose build backend

---

## 15. ホスト環境

Host PCへプロジェクト固有Runtimeを直接導入することを前提としない。

最低限必要なもの：

- Docker
- Git
- Editor

以下はContainer内で管理する。

- Node.js
- npm等
- PHP
- Composer
- PostgreSQL

---

## 16. バージョン管理

各RuntimeのVersionはDocker Imageで管理する。

例：

    Node.js
    → frontend/Dockerfile

    PHP
    → backend/Dockerfile

    PostgreSQL
    → compose.yaml

具体的なVersionはProject Setup時に決定する。

---

## 17. MVPで導入しないもの

MVPでは必要性がない限り、以下をDocker Composeへ追加しない。

- Redis
- nginx
- Mailpit
- MinIO
- Message Queue
- Worker Container
- Scheduler専用Container

必要性が発生した段階で追加する。

---

## 18. CIとの関係

DockerでRuntime Versionや依存環境を明確にし、
LocalとCIの環境差異を減らす。

CIの具体的な実行方式はCI/CD設計時に決定する。

CIでDocker Composeをそのまま利用することは必須としない。

---

## 19. Productionとの関係

開発環境でDockerを利用しても、
Production環境をDockerへ限定しない。

Deployment先に応じて最適な構成を選択する。

---

## 20. 採用理由

全部Dockerを採用する理由：

- Next.jsとLaravelで異なるRuntimeを統一管理できる
- Node.js Versionを統一できる
- PHP Versionを統一できる
- PostgreSQL Versionを統一できる
- Host環境を汚しにくい
- 新規開発者のSetupを簡単にできる
- Monorepoとの相性がよい
- CIとの環境差異を減らせる
- 作業終了時に開発環境全体を停止できる

---

## 21. 決定事項

### 開発環境

すべてDockerで構築する。

### Container

    frontend
    backend
    postgres

の3ContainerをMVPの基本構成とする。

### Host

HostにはProject Runtimeを原則直接導入しない。

### Database

PostgreSQL DataはDocker Volumeで永続化する。

### Source Code

HostからContainerへVolume Mountする。

### 基本方針

- Docker Composeで開発環境を一括管理する
- MVPでは必要最小限のContainer構成とする
- Runtime VersionをDockerで固定する
- Redis等の追加Middlewareは必要になってから導入する
