# コード品質・複雑度監視 技術決定

## 1. 目的

本ドキュメントでは、Engineer Skill Management AppにおけるCode QualityおよびComplexity / Maintainabilityの監視方針を定義する。

Code Qualityは単一のMetricではなく、以下を組み合わせて評価する。

```text
Code Quality
├── Formatting
├── Lint
├── Static Analysis
├── Type Safety
├── Complexity
├── Maintainability
├── Test
├── Code Review
└── Architecture
```

本ドキュメントでは特にComplexity / Maintainabilityの監視方法と、CIにおける扱いを定義する。

---

## 2. 基本方針

Frontend / Backendの両方でComplexityを監視する。

採用Tool：

### Frontend / BFF

- ESLint
- ESLint `complexity` Rule

### Backend API

- PHPMD

Complexityそのものを品質目標にはしない。

以下を組み合わせて総合的に判断する。

```text
Complexity
    +
Static Analysis
    +
Type Safety
    +
Test
    +
Code Review
    +
Architecture
    ↓
Code Quality
```

ComplexityはRefactoringを検討するためのSignalとして利用する。

---

## 3. Complexity監視の目的

複雑なFunction / Method / Componentを早期に検出し、以下のリスクを抑える。

- 条件分岐の増加
- Test Caseの増大
- 変更影響範囲の把握困難
- 可読性低下
- 保守性低下
- 責務集中
- Bug混入リスクの増加

Complexityが高いことだけを理由としてCode Qualityが低いと判断しない。

逆にComplexityが低いことだけを理由として良い設計であるとも判断しない。

---

## 4. Code Quality Toolの役割

各Toolの責務を分離する。

| 対象 | Tool | 主な責務 |
| --- | --- | --- |
| Frontend / BFF | Prettier | Formatting |
| Frontend / BFF | ESLint | Lint / Code Quality |
| Frontend / BFF | ESLint `complexity` | Cyclomatic Complexity |
| Frontend / BFF | TypeScript | Type Safety |
| Frontend / BFF | Vitest | Behavior / Unit / Application Test |
| Backend API | Laravel Pint | Formatting |
| Backend API | PHPStan / Larastan | Static Analysis / Type Safety |
| Backend API | PHPMD | Complexity / Code Smell / Maintainability |
| Backend API | PHPUnit / Laravel Test | Behavior / Business Rule / API / Integration Test |

各Toolの責務を過度に重複させない。

---

## 5. CIでの分類

`03_CICD方針.md`に従い、CI Checkを以下へ分類する。

```text
CI Check
├── Blocking Check
└── Monitoring Check
```

### Blocking Check

Codeの正しさ・Build可能性・Type Safety等を保証するため、違反時は原則CI Failureとする。

### Monitoring Check

Code Qualityの傾向を観測し、Code ReviewやRefactoring判断に利用する。

MVP初期では違反のみを理由としてCI Failureにしない。

---

## 6. MVPでのQuality Gate

MVPでは以下を基本とする。

| Check | MVPでの扱い |
| --- | --- |
| Prettier | Blocking |
| ESLint通常Rule | Blocking |
| TypeScript Type Check | Blocking |
| Vitest | Blocking |
| Next.js Build | Blocking |
| Laravel Pint | Blocking |
| PHPStan / Larastan | Blocking |
| PHPUnit / Laravel Test | Blocking |
| ESLint `complexity` | Monitoring |
| PHPMD Complexity / Maintainability | Monitoring |

Complexity関連CheckはMVP初期ではMonitoringを基本とする。

PHPMDのすべてのRuleを一律Monitoringとするわけではない。

将来PHPMDでComplexity / Maintainability以外のRuleを採用する場合は、RuleごとにBlocking / Monitoringを判断する。

---

## 7. Frontend / BFF Complexity

Frontend / BFFではESLint `complexity` Ruleを利用する。

主な対象：

- React Component
- Server Component
- Client Component
- Route Handler
- Server Action
- BFF処理
- Utility
- Form Logic
- Data Transformation

条件分岐が増加したFunction / Componentを早期に検出する。

例：

```typescript
function getSkillFormState(skill: Skill) {
  if (...) {
    // ...
  }

  if (...) {
    // ...
  }

  if (...) {
    // ...
  }
}
```

Complexity検出をRefactoring検討のTriggerとして利用する。

---

## 8. Frontendで重点的に確認する箇所

今回のApplicationでは以下の処理を重点的に確認する。

- Form状態制御
- 実務経験有無による入力切り替え
- Skill Levelによる入力制御
- Authorizationに基づくUI制御
- BFF Error Handling
- API Response変換
- Form Validation
- Data Transformation

特に以下の責務が1つのComponent / Functionへ集中していないか確認する。

```text
UI Rendering
    +
State
    +
Form Validation
    +
Authorization-based UI
    +
API Communication
    +
Data Transformation
```

Complexity上昇を、責務集中を発見するためのSignalとして利用する。

---

## 9. FrontendのMonitoring方針

MVPではESLint `complexity` RuleをMonitoring Checkとして利用する。

概念：

```text
Code
 ↓
ESLint
 ├── 通常Rule
 │      ↓
 │   Blocking
 │
 └── complexity
        ↓
     Monitoring
```

ESLint通常RuleとComplexity Ruleの扱いを区別する。

`complexity` RuleのThreshold超過のみを理由として、MVP初期からCI全体をFailureにしない。

実際のESLint Configurationでもこの方針を反映する。

---

## 10. FrontendでComplexityが高い場合

Complexityが高い場合は、まず責務が適切に分離されているか確認する。

確認対象：

```text
Component
├── UI Rendering
├── State
├── Form Validation
├── Authorization
├── BFF
├── API Client
└── Data Transformation
```

必要に応じて以下へ責務を分離する。

- Component
- Hook
- Utility
- Form Schema
- BFF
- API Client
- Data Transformation Function

ただし単純にHookやUtilityへ移動するだけでは責務分離にならない場合がある。

「どこへ移動するか」ではなく「その責務をどのLayer / Moduleが持つべきか」を基準に判断する。

---

## 11. Backend API Complexity

Backend APIではPHPMDを利用する。

主な監視対象：

- Cyclomatic Complexity
- NPath Complexity
- Method Size
- Class Size
- Parameter Count
- Coupling
- Code Smell
- Maintainability

PHPMDはPHPStan / Larastanとは異なる責務を持つ。

```text
Laravel Pint
    ↓
Formatting

PHPStan / Larastan
    ↓
Static Analysis / Type Safety

PHPMD
    ↓
Complexity / Code Smell / Maintainability

PHPUnit
    ↓
Behavior / Business Rule / Integration
```

---

## 12. Backendで重点的に確認する箇所

今回のApplicationでは以下の処理が複雑になりやすいため重点的に確認する。

- Authorization
- 社員スキル登録
- 社員スキル編集
- 実務経験有無によるDomain Rule
- Skill Level制約
- 権限管理
- 担当社員判定
- Permission管理
- Skill Master操作
- 複数条件による検索
- Transactionを伴うApplication Handler

Complexityが高い場合は、単純にMethodを分割するだけでなく、Domain Ruleや責務の配置が適切か確認する。

---

## 13. BackendのMonitoring方針

MVPではPHPMDのComplexity / Maintainability関連MetricをMonitoring中心で利用する。

概念：

```text
Backend Code
     ↓
PHPMD
     ↓
Complexity / Maintainability
     ↓
Monitoring
     ↓
Code Review
```

MVP初期ではComplexity / Maintainability Threshold超過のみを理由としてPipeline全体をFailureにしない。

PHPMDの結果は以下で確認できる状態とする。

- Local Development
- CI Log
- Pull Request Review

PHPMDのすべてのRuleを一律Monitoringにすることは決定しない。

追加Ruleを採用する場合は、Ruleの目的に応じてBlocking / Monitoringを個別に判断する。

---

## 14. BackendでComplexityが高い場合

Backendでは既存のClean Architecture / DDD / Lightweight CQRS方針に従って責務を確認する。

概念：

```text
Presentation
     ↓
Application
     ↓
Domain

Infrastructure
     ↓
Interface Implementation
```

Complexityが高い場合は、以下のような責務集中がないか確認する。

```text
Controller
   +
Validation
   +
Authorization
   +
Business Rule
   +
Transaction
   +
Database Access
```

ControllerへBusiness Logicを集中させない。

必要に応じて適切な責務へ分離する。

### Presentation

- Controller
- Form Request
- Policy

### Application

- Command Handler
- Query Handler
- Application Service / UseCase Coordination

### Domain

- Aggregate
- Entity
- Value Object
- Domain Service
- Domain Rule

### Infrastructure

- Repository Implementation
- Mapper
- Eloquent Model
- External Service Adapter

Complexityを下げるためだけにLayerやClassを増やさない。

---

## 15. Refactoring判断

Complexityが高い場合は、以下の順序を基本として確認する。

1. 不要なCondition / Branchを削除できないか
2. Guard Clause / Early Returnで単純化できないか
3. 重複処理を整理できないか
4. Function / Methodを適切に分割できないか
5. Component / Classの責務を分離できないか
6. Domain Ruleを適切なDomain Modelへ移動できないか
7. Value Object / Policy等へ責務を移動できないか
8. 必要な場合のみDesign Patternを検討する

概念：

```text
Simplification
     ↓
Method / Function Separation
     ↓
Responsibility Separation
     ↓
Domain Modeling
     ↓
必要ならDesign Pattern
```

Complexityを下げるためだけの過度な抽象化は行わない。

---

## 16. ComplexityとArchitecture

Complexity MetricだけではArchitectureの良し悪しを判断できない。

例えばComplexityが低いMethodであっても、多数の責務や依存関係を持っている場合は設計上の問題が存在する可能性がある。

逆にBusiness Ruleを明示的に表現した結果、一定のComplexityを持つことが適切な場合もある。

そのため以下を総合的に確認する。

```text
Complexity Metric
       +
Dependency
       +
Responsibility
       +
Domain Rule
       +
Testability
       +
Readability
       ↓
Architecture Review
```

MetricをArchitecture判断の代替として利用しない。

---

## 17. Threshold方針

MVP開始時点ではProject固有の厳格なComplexity Thresholdを確定しない。

一般的な数値をそのままProjectの品質基準として採用しない。

以下の流れでThresholdを決定する。

```text
MVP Development
      ↓
Metric収集
      ↓
Codebase蓄積
      ↓
Complexity傾向確認
      ↓
Review
      ↓
Project固有Threshold検討
```

Thresholdは以下を考慮して決定する。

- Codebaseの規模
- Function / Methodの役割
- Frontend / Backendの違い
- Domain Logicの複雑さ
- Testability
- Maintainability
- Review負荷
- 実際に発生した変更コスト

Thresholdは絶対的な品質基準として扱わない。

## 18. 段階的なQuality Gate

Complexity Monitoringは段階的に導入する。

### Phase 1：MVP

```text
Complexity Check
      ↓
Metric / Violation確認
      ↓
Monitoring
      ↓
Code Review
```

Complexityのみを理由としてCI Failureにしない。

### Phase 2：Codebase蓄積後

```text
Metric蓄積
    ↓
傾向分析
    ↓
Project固有Threshold
    ↓
Warning
```

実際のCodebaseに基づいてThresholdを決定する。

### Phase 3：運用実績蓄積後

必要性が確認できた場合のみ、

```text
重大なThreshold超過
        ↓
Blocking Check
```

への変更を検討する。

Quality Gate強化そのものを目的とせず、実際の保守性向上につながる場合にのみ導入する。

## 20. Local Development

Complexity CheckはCIだけでなくLocal Developmentでも実行できるようにする。

目的：

- Pull Request作成前に問題を確認する
- CIで初めてComplexityを知る状態を避ける
- Refactoring時にMetricを確認する

ただしEditor上で常時Complexity Warningを大量表示することは必須としない。

Developer Experienceを損なわない範囲で利用する。

## 22. MVPで行わないこと

MVPでは以下を過度に行わない。

- Complexity Scoreの最小化
- 一般的なThresholdの無条件採用
- Complexityのみを理由とした厳格なCI Failure
- PHPMD Ruleの大量導入
- Complexityを下げるためだけのClass分割
- 不要なDesign Pattern導入
- 過度な抽象化
- 専用Code Quality Platformの導入
- Metric Dashboardの構築
- Code CoverageとComplexityを組み合わせた複雑なQuality Gate

まず実際のCodebaseを観測し、必要なRule・Threshold・Quality Gateを段階的に導入する。

---

## 23. 基本方針

- Frontend / Backendの両方でComplexityを監視する
- FrontendはESLint `complexity` Ruleを利用する
- BackendはPHPMDを利用する
- ComplexityはCode Qualityを判断するSignalの1つとして扱う
- Complexity単独でCode Qualityを判断しない
- MVPではComplexityをMonitoring Checkとして扱う
- Blocking CheckとMonitoring Checkを明確に分離する
- Codebaseの傾向を確認してからProject固有Thresholdを決定する
- Refactoringではまず単純化と責務分離を検討する
- Design Patternは必要な場合のみ利用する
- Complexity低減のための過度な抽象化を避ける
- Static Analysis / Test / Code Review / Architectureと組み合わせて判断する
- Tool導入そのものを目的としない

## 24. 決定事項

### Code Quality

Formatting / Lint / Static Analysis / Type Safety / Complexity / Test / Code Review / Architectureを組み合わせて評価する。

### Frontend / BFF Complexity

ESLint `complexity` Ruleを採用する。

### Backend Complexity

PHPMDを採用する。

### Blocking Check

MVPでは以下を原則Blockingとする。

- Prettier
- ESLint通常Rule
- TypeScript Type Check
- Vitest
- Next.js Build
- Laravel Pint
- PHPStan / Larastan
- PHPUnit / Laravel Test

### Monitoring Check

MVPでは以下をMonitoring中心とする。

- ESLint `complexity`
- PHPMD Complexity / Maintainability

### PHPMD

PHPMDのすべてのRuleを一律Monitoringとはしない。

追加Ruleを採用する場合はRuleごとにBlocking / Monitoringを判断する。

### Threshold

MVP開始時点ではProject固有の厳格なThresholdを確定しない。

実際のCodebaseを観測してから決定する。

### CI

Complexity Threshold超過のみを理由としたCI FailureをMVP初期では原則行わない。

### Refactoring

以下の順序を基本とする。

```text
Simplification
    ↓
Method / Function Separation
    ↓
Responsibility Separation
    ↓
Domain Modeling
    ↓
必要ならDesign Pattern
```

### 可視化

MVPでは専用Code Quality Platformを導入しない。

ESLint / PHPMD / CI Log / Pull Request Reviewを利用する。

### 将来

Codebaseと運用実績を確認したうえで、

```text
Monitoring
    ↓
Project固有Threshold
    ↓
Warning
    ↓
必要な場合のみBlocking
```

の順にQuality Gateを強化する。
