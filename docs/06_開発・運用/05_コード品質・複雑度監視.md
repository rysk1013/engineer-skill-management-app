# コード品質・複雑度監視 技術決定

## 1. 目的

本ドキュメントでは、Engineer Skill Management AppにおけるCode QualityおよびComplexity / Maintainabilityの監視方針を定義する。

Code Qualityは単一のMetricではなく、以下を組み合わせて評価する。

```text
Code Quality
├── Formatting
├── Lint
├── Static Analysis
├── Type Safety
├── Complexity
├── Maintainability
├── Test
├── Code Review
└── Architecture
```

本ドキュメントでは特にComplexity / Maintainabilityの監視方法と、CIにおける扱いを定義する。

---

## 2. 基本方針

Frontend / Backendの両方でComplexityを監視する。

採用Tool：

### Frontend / BFF

- ESLint
- ESLint `complexity` Rule

### Backend API

- PHP_CodeSniffer
- CleanCode
- Project Ruleset `backend/phpcs.xml`

Complexityそのものを品質目標にはしない。

以下を組み合わせて総合的に判断する。

```text
Complexity
    +
Static Analysis
    +
Type Safety
    +
Test
    +
Code Review
    +
Architecture
    ↓
Code Quality
```

ComplexityはRefactoringを検討するためのSignalとして利用する。

---

## 3. Complexity監視の目的

複雑なFunction / Method / Component / Classを早期に検出し、以下のリスクを抑える。

- 条件分岐の増加
- Test Caseの増大
- 変更影響範囲の把握困難
- 可読性低下
- 保守性低下
- 責務集中
- Bug混入リスクの増加

Complexityが高いことだけを理由としてCode Qualityが低いと判断しない。

逆にComplexityが低いことだけを理由として良い設計であるとも判断しない。

---

## 4. Code Quality Toolの役割

各Toolの責務を分離する。

| 対象 | Tool | 主な責務 |
| --- | --- | --- |
| Frontend / BFF | Prettier | Formatting |
| Frontend / BFF | ESLint | Lint / Code Quality |
| Frontend / BFF | ESLint `complexity` | Cyclomatic Complexity |
| Frontend / BFF | TypeScript | Type Safety |
| Frontend / BFF | Vitest | Behavior / Unit / Application Test |
| Backend API | Laravel Pint | Formatting |
| Backend API | PHPStan / Larastan | Static Analysis / Type Safety |
| Backend API | PHP_CodeSniffer + CleanCode | Complexity / Code Smell / Maintainability |
| Backend API | Pest / Laravel Test | Behavior / Business Rule / API / Integration Test |

各Toolの責務を過度に重複させない。

---

## 5. CIでの分類

`03_CICD方針.md`に従い、CI Checkを以下へ分類する。

```text
CI Check
├── Blocking Check
└── Monitoring Check
```

### Blocking Check

Codeの正しさ・Build可能性・Type Safety等を保証するため、違反時は原則CI Failureとする。

### Monitoring Check

Code Qualityの傾向を観測し、Code ReviewやRefactoring判断に利用する。

MVP初期では違反のみを理由としてCI Failureにしない。

| Vitest | Blocking |

## 9. FrontendのMonitoring方針

MVPではESLint `complexity` RuleをMonitoring Checkとして利用する。

概念：

```text
Code
 ↓
ESLint
 ├── 通常Rule
 │      ↓
 │   Blocking
 │
 └── complexity
        ↓
     Monitoring
```

ESLint通常RuleとComplexity Ruleの扱いを区別する。

`complexity` RuleのThreshold超過のみを理由として、MVP初期からCI全体をFailureにしない。

Localでは以下を標準Commandとする。

```bash
docker compose exec frontend pnpm complexity
```

通常のBlocking Checkは、

```bash
docker compose exec frontend pnpm quality
```

で実行する。

`pnpm quality`にはComplexity Monitoringを含めない。

## 11. FrontendでComplexityが高い場合

Complexityが高い場合は、まず責務が適切に分離されているか確認する。

確認対象：

```text
Component
├── UI Rendering
├── State
├── Form Validation
├── Authorization
├── BFF
├── API Client
└── Data Transformation
```

必要に応じて以下へ責務を分離する。

- Component
- Hook
- Utility
- Form Schema
- BFF
- API Client
- Data Transformation Function

ただし単純にHookやUtilityへ移動するだけでは責務分離にならない場合がある。

「どこへ移動するか」ではなく「その責務をどのLayer / Moduleが持つべきか」を基準に判断する。

## 13. CleanCode採用方針

CleanCode Standard全体をProjectへ適用しない。

Projectで必要なSniffのみを`backend/phpcs.xml`から選択する。

初期採用Rule：

```text
CleanCode.Metrics.CyclomaticComplexity
CleanCode.Metrics.NPathComplexity
CleanCode.Functions.ExcessiveMethodLength
CleanCode.Metrics.ExcessiveClassComplexity
CleanCode.Functions.DisallowBooleanArgumentFlag
CleanCode.DeadCode.UnusedFormalParameter
CleanCode.DeadCode.UnusedPrivateElements
```

CleanCodeにはProject ArchitectureやCoding Policyに対してOpinionatedなRuleも含まれるため、外部Toolの設計思想をそのままProject Ruleとして採用しない。

特に、

```text
Repository Class禁止
Static Member禁止
Conditional禁止
Else禁止
Test File必須
Namespace Naming制約
```

等を無条件に導入しない。

Project Architecture / DDD / Laravel方針を優先する。

## 16. BackendのMonitoring方針

MVPではCleanCodeによるComplexity / Maintainability関連CheckをMonitoringとして利用する。

概念：

```text
Backend Code
     ↓
PHP_CodeSniffer
     ↓
backend/phpcs.xml
     ↓
Selected CleanCode Sniffs
     ↓
Complexity / Maintainability
     ↓
Monitoring
     ↓
Code Review / Refactoring
```

MVP初期ではComplexity / Maintainability Threshold超過のみを理由としてPipeline全体をFailureにしない。

Localでは、

```bash
docker compose exec backend composer complexity
```

で実行する。

BlockingなBackend Code Quality Checkは、

```bash
docker compose exec backend composer quality
```

で実行する。

`composer quality`は、

```text
Laravel Pint
    +
PHPStan / Larastan
```

を対象とし、`composer complexity`は含めない。

これによりCommand Levelでも、

```text
composer quality
    → Blocking

composer complexity
    → Monitoring
```

を明確に分離する。

## 17. CleanCodeのExit Code

CleanCode SniffはPHPCS上でViolationをErrorとして報告するため、Threshold超過時にCommand自体はNon-zero Exit Codeとなり得る。

ただし、

```text
Command Exit Code
    ≠
ProjectとしてのBlocking Policy
```

とする。

`composer complexity`のNon-zero Exit Codeのみを理由としてMVP初期のMergeを禁止しない。

CI上での具体的なNon-blocking実装方法はTASK-10で定義する。

## 18. BackendでComplexityが高い場合

Backendでは既存のClean Architecture / DDD / Lightweight CQRS方針に従って責務を確認する。

概念：

```text
Presentation
     ↓
Application
     ↓
Domain

Infrastructure
     ↓
Interface Implementation
```

Complexityが高い場合は、以下のような責務集中がないか確認する。

```text
Controller
   +
Validation
   +
Authorization
   +
Business Rule
   +
Transaction
   +
Database Access
```

ControllerへBusiness Logicを集中させない。

必要に応じて適切な責務へ分離する。

### Presentation

- Controller
- Form Request
- Policy

### Application

- Command Handler
- Query Handler
- Application Service / UseCase Coordination

### Domain

- Aggregate
- Entity
- Value Object
- Domain Service
- Domain Rule

### Infrastructure

- Repository Implementation
- Mapper
- Eloquent Model
- External Service Adapter

Complexityを下げるためだけにLayerやClassを増やさない。

## 19. Code Smell / Unused Code

BackendではComplexity Metricに加え、一部のCode Smell / Unused CodeもMonitoringする。

### Code Smell

```text
CleanCode.Functions.DisallowBooleanArgumentFlag
```

Boolean FlagによってMethodが複数Behaviorを持っていないか確認するSignalとして利用する。

Boolean Argumentが存在するだけでDesign Errorと判断しない。

### Unused Code

```text
CleanCode.DeadCode.UnusedFormalParameter
CleanCode.DeadCode.UnusedPrivateElements
```

以下を補助的に検出する。

```text
Unused Parameter
Unused Private Property
Unused Private Method
```

ただしCleanCodeだけでDead Codeを完全に検出できるとは考えない。

```text
CleanCode
    +
PHPStan
    +
IDE
    +
Code Review
```

を組み合わせて判断する。

## 20. Refactoring判断

Complexityが高い場合は、以下の順序を基本として確認する。

1. 不要なCondition / Branchを削除できないか
2. Guard Clause / Early Returnで単純化できないか
3. 重複処理を整理できないか
4. Function / Methodを適切に分割できないか
5. Component / Classの責務を分離できないか
6. Domain Ruleを適切なDomain Modelへ移動できないか
7. Value Object / Policy等へ責務を移動できないか
8. 必要な場合のみDesign Patternを検討する

概念：

```text
Simplification
     ↓
Method / Function Separation
     ↓
Responsibility Separation
     ↓
Domain Modeling
     ↓
必要ならDesign Pattern
```

Complexityを下げるためだけの過度な抽象化は行わない。

---

## 21. ComplexityとArchitecture

Complexity MetricだけではArchitectureの良し悪しを判断できない。

例えばComplexityが低いMethodであっても、多数の責務や依存関係を持っている場合は設計上の問題が存在する可能性がある。

逆にBusiness Ruleを明示的に表現した結果、一定のComplexityを持つことが適切な場合もある。

そのため以下を総合的に確認する。

```text
Complexity Metric
       +
Dependency
       +
Responsibility
       +
Domain Rule
       +
Testability
       +
Readability
       ↓
Architecture Review
```

MetricをArchitecture判断の代替として利用しない。

---

## 22. Threshold方針

MVP開始時点ではProject固有の厳格なComplexity Thresholdを確定しない。

Frontend / BackendともにToolのDefault Thresholdを初期観測値として利用する。

```text
Frontend
    → ESLint complexity Default

Backend
    → CleanCode Default
```

Default ThresholdをProjectの品質基準として無条件に採用するわけではない。

以下の流れでProject固有Thresholdを検討する。

```text
MVP Development
      ↓
Metric / Violation収集
      ↓
Codebase蓄積
      ↓
Complexity傾向確認
      ↓
Review
      ↓
Project固有Threshold検討
```

Thresholdは以下を考慮して決定する。

- Codebaseの規模
- Function / Methodの役割
- Frontend / Backendの違い
- Domain Logicの複雑さ
- Testability
- Maintainability
- Review負荷
- False Positive
- 実際に発生した変更コスト

Thresholdは絶対的な品質基準として扱わない。

## 23. 段階的なQuality Gate

Complexity Monitoringは段階的に導入する。

### Phase 1：MVP

```text
Complexity Check
      ↓
Metric / Violation確認
      ↓
Monitoring
      ↓
Code Review
```

Complexityのみを理由としてCI Failureにしない。

### Phase 2：Codebase蓄積後

```text
Metric / Violation蓄積
    ↓
傾向分析
    ↓
Project固有Threshold
    ↓
Warning
```

実際のCodebaseに基づいてThresholdを決定する。

### Phase 3：運用実績蓄積後

必要性が確認できた場合のみ、

```text
重大なThreshold超過
        ↓
Blocking Check
```

への変更を検討する。

Quality Gate強化そのものを目的とせず、実際の保守性向上につながる場合にのみ導入する。

## 28. Tool選定上の補足

Backend Complexity / Maintainability Toolについては、PHPMD、PhpMetrics、CleanCodeを検討した。

### PHPMD

当初の採用候補。

ただし現在のLaravel / Symfony依存関係ではStable版PHPMDの導入にDependency Conflictが発生した。

PHPMD 3系についても関連DependencyのDevelopment Versionが必要となるため、Phase 0時点では採用しない。

### PhpMetrics

現在のPHP Runtimeで利用可能なVersionを検証した。

Complexity Metricsの可視化には利用できるが、今回必要としている、

```text
NPath Complexity
Code Smell
Unused Code
```

等の監視を十分にカバーしないため採用しない。

### CleanCode

PHP_CodeSniffer上で動作し、今回必要な、

```text
Cyclomatic Complexity
NPath Complexity
Method Length
Class Complexity
Code Smell
Unused Code
```

に対応するSniffを選択可能であることを確認した。

現在のBackend Dependencyとも共存可能なため採用する。

ただし比較的新しいToolであることを考慮し、CleanCode Standard全体には依存せず、必要なSniffをProject Rulesetから明示的に選択する。

## 29. 基本方針

- Frontend / Backendの両方でComplexityを監視する
- FrontendはESLint `complexity` Ruleを利用する
- BackendはPHP_CodeSniffer + CleanCodeを利用する
- BackendのRuleは`backend/phpcs.xml`で管理する
- CleanCode Standard全体は利用せず必要なSniffのみ採用する
- ComplexityはCode Qualityを判断するSignalの1つとして扱う
- Complexity単独でCode Qualityを判断しない
- MVPではComplexityをMonitoring Checkとして扱う
- Blocking CheckとMonitoring Checkを明確に分離する
- Tool Default Thresholdは初期観測値として利用する
- Codebaseの傾向を確認してからProject固有Thresholdを決定する
- Refactoringではまず単純化と責務分離を検討する
- Design Patternは必要な場合のみ利用する
- Complexity低減のための過度な抽象化を避ける
- Static Analysis / Test / Code Review / Architectureと組み合わせて判断する
- Tool導入そのものを目的としない

### Threshold

MVP開始時点ではProject固有の厳格なThresholdを確定しない。

Tool Defaultを初期観測値として利用し、実際のCodebaseを観測してから必要に応じて調整する。

### CI

Complexity Threshold超過のみを理由としたCI FailureをMVP初期では原則行わない。

CleanCode / PHPCSのCommandがNon-zero Exit Codeを返す場合でも、それだけを理由としてMerge Blockingとはしない。

具体的なGitHub Actions上のMonitoring実装はTASK-10で決定する。

### Refactoring

以下の順序を基本とする。

```text
Simplification
    ↓
Method / Function Separation
    ↓
Responsibility Separation
    ↓
Domain Modeling
    ↓
必要ならDesign Pattern
```

### 可視化

MVPでは専用Code Quality Platformを導入しない。

ESLint / CleanCode / PHP_CodeSniffer / CI Log / Pull Request Reviewを利用する。
