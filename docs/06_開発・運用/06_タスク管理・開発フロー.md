# タスク管理・開発フロー

## 1. 目的

Engineer Skill Management Appの実装におけるタスク管理方法と、Task単位の開発フローを定義する。

設計・仕様と実装タスクを分離し、以下を実現することを目的とする。

- 実装すべき作業を明確にする
- Taskの進捗をローカルで管理する
- Taskごとの完了条件を明確にする
- 設計から実装までのトレーサビリティを確保する
- 実装前にImplementation Planを確認する
- Test・Lint・Static Analysisを含めてTaskを完了する
- AI Agentを利用する場合も同じ開発フローを適用する

タスク管理には**Backlog.md**を使用する。

---

## 2. 基本方針

タスク管理・開発フローでは以下を基本方針とする。

- 設計・仕様と実装タスクを分離する
- MVPのPhaseを単位としてTaskを整理する
- 実装可能な単位までTaskを分割する
- TaskごとにAcceptance Criteriaを定義する
- 実装前にImplementation Planを作成する
- Implementation Planを確認してから実装する
- Test・Lint・Static AnalysisをTask完了条件に含める
- Taskの状態はBacklog.mdをSource of Truthとする
- Task情報は原則Backlog.md CLI経由で操作する
- Task Markdownを設計ドキュメントの代替として使用しない
- Phase固有の実装手順を`docs/`へ追加しない

設計判断は`docs/`、API契約はOpenAPI、実装作業と進捗はBacklog.md、実装結果はSource Codeで管理する。

---

## 3. 情報管理とSource of Truth

プロジェクト内の情報は責務ごとにSource of Truthを分離する。

| 情報 | Source of Truth |
|---|---|
| 要件 | `docs/01_要件定義/` |
| Architecture | `docs/02_アーキテクチャ/` |
| System Design | `docs/03_システム設計/` |
| Technology Decision | `docs/04_技術選定/` |
| MVP Phase / 実装方針 | `docs/05_MVP実装計画/` |
| 開発・運用ルール | `docs/06_開発・運用/` |
| 非機能要件 | `docs/07_非機能要件/` |
| API Contract | OpenAPI |
| 実装Task・進捗 | Backlog.md |
| 実装結果 | Source Code |

基本的な関係は以下とする。

```text
Requirements / Design
        │
        ▼
      docs/
        │
        ▼
MVP Implementation Plan
        │
        ▼
    Backlog.md
        │
        ▼
Implementation Plan
        │
        ▼
   Source Code
        │
        ▼
Test / Quality Check
```

Taskに設計内容を複製せず、必要な設計ドキュメントをReferenceとして参照する。

## 4. Backlog.md

### 4.1 採用方針

実装タスクの管理にはBacklog.mdを使用する。

Backlog.mdは以下の用途で使用する。

- Task管理
- Status管理
- Milestone管理
- Acceptance Criteria管理
- Definition of Done管理
- Dependency管理
- Reference管理
- Implementation Plan管理
- Implementation Notes管理
- Final Summary管理

Taskの作成・更新・Status変更などは、原則としてBacklog.md CLI経由で行う。

Task Markdownファイルを直接編集する運用には依存しない。

Backlog.md自体の設定については`backlog/config.yml`をSource of Truthとする。

---

### 4.2 管理単位

MVP実装では以下の階層で管理する。

```text
MVP
└── Phase / Milestone
    └── Task
```

PhaseはMVP実装計画上の大きな実装単位とする。

Backlog.mdではPhaseに対応する管理単位としてMilestoneを使用する。

Taskは実際に着手し、単独で完了判定できる実装単位とする。

---

### 4.3 Milestone

MVP実装計画のPhaseをBacklog.mdのMilestoneとして扱う。

例：

```text
Phase 0 - 開発基盤
Phase 1 - Employee
Phase 2 - Skill
Phase 3 - EmployeeSkill
Phase 4 - Access Control
Phase 5 - Dashboard
```

Phaseの詳細な目的・実装順序については`docs/05_MVP実装計画/`をSource of Truthとする。

Milestone側へ設計内容を重複して記載しない。

---

### 4.4 Task

Taskは「1つの目的を持ち、Acceptance Criteriaによって単独で完了判定できる単位」とする。

Task IDはBacklog.mdが管理するIDを使用する。

Task Titleは作業内容が簡潔に理解できる名称とする。

例：

```text
TASK-1 Monorepo初期構成
TASK-2 Docker開発環境構築
TASK-3 Frontend初期構築
TASK-4 Backend初期構築
```

Task IDの番号自体にPhaseなどの意味を持たせない。

Phaseとの関係はMilestoneで管理する。

---

### 4.5 Status

初期Statusは以下の3つとする。

```text
To Do
  ↓
In Progress
  ↓
Done
```

#### To Do

未着手のTask。

Dependencyなどの理由で直ちに着手できないTaskも、初期運用では`To Do`として管理する。

#### In Progress

現在作業中のTask。

#### Done

Acceptance CriteriaおよびDefinition of Doneを満たしたTask。

`Blocked`や`Review`などの追加Statusは、実際に必要になった時点で導入を検討する。

初期段階ではStatusを増やしすぎない。

---

## 5. Task設計

### 5.1 Taskの粒度

Taskは以下を満たす粒度とする。

- 目的が1つに整理されている
- 実装内容を説明できる
- Acceptance Criteriaを定義できる
- 単独で完了判定できる
- 必要なTest・品質確認まで含められる

以下のような大きすぎるTaskは避ける。

```text
NG:
Phase 0の開発環境をすべて構築する
```

一方、単純なファイル作成やコマンド実行だけを個別Taskにするなど、過度な細分化も避ける。

```text
NG:
frontendディレクトリを作成する
package.jsonを作成する
TypeScriptを有効化する
```

これらは必要に応じて1つのTask内のSubtaskやAcceptance Criteriaとして管理する。

---

### 5.2 Taskの基本構成

Taskでは原則として以下を管理する。

```text
Title
Description
Acceptance Criteria
Definition of Done
Dependencies
References
Implementation Plan
Implementation Notes
Final Summary
```

すべての項目を機械的に埋めることは目的としない。

Taskの規模や内容に応じて不要な項目は省略できる。

---

### 5.3 Description

Taskの目的と実施する内容を記載する。

設計仕様そのものを詳細に再記述するのではなく、「何を実現するTaskなのか」が理解できる内容とする。

---

### 5.4 Acceptance Criteria

Acceptance Criteriaは、そのTaskが要求を満たしているかを判断する条件とする。

可能な限り客観的に確認できる内容とする。

例：

```text
- Docker ComposeからFrontendを起動できる
- Docker ComposeからBackend APIを起動できる
- BackendからPostgreSQLへ接続できる
```

Acceptance Criteriaでは「何ができれば要求を満たすか」を定義し、具体的な実装方法そのものを固定しすぎない。

---

### 5.5 Definition of Done

Definition of Doneは、そのTaskを`Done`として扱うための品質条件とする。

Taskの内容に応じて以下を確認する。

- Acceptance Criteriaを満たしている
- 必要なTestが成功する
- Lintが成功する
- Static Analysisが成功する
- Complexity等の品質基準に重大な問題がない
- 関連ドキュメントの更新が必要な場合は更新されている
- 不要なDebug Codeや一時ファイルが残っていない
- 必要なReviewが完了している
- Final Summaryが記録されている

Taskに関係しない検査を形式的に要求することは避ける。

Git / GitHub上のPull RequestやMergeを含む完了条件については、[`07_Git・GitHub運用.md`](./07_Git・GitHub運用.md)に従う。

---

### 5.6 Dependencies

他のTaskが完了していなければ着手または完了できない場合、Dependencyを設定する。

例：

```text
Docker開発環境
    ↓
Frontend初期構築
    ↓
Frontend Test基盤
```

Dependencyは実際に必要なものだけを設定し、不要な直列化を避ける。

---

### 5.7 References

Taskの実装判断に必要な既存資料をReferenceとして紐付ける。

主なReferenceは以下とする。

- `docs/`
- OpenAPI
- 関連するSource Code
- 関連Task
- 必要に応じて外部公式Documentation

Taskへ既存設計をコピーするのではなく、Source of Truthを参照する。

---

## 6. 開発フロー

Taskは原則として以下のフローで実施する。

```text
Task選択
    ↓
関連資料・コード調査
    ↓
Implementation Plan
    ↓
Plan Review
    ↓
Implementation
    ↓
Test
    ↓
Lint / Static Analysis
    ↓
Acceptance Criteria確認
    ↓
Definition of Done確認
    ↓
Final Summary
    ↓
Done
```

Git Branch、Commit、Pull Requestなどはこのフローと並行して使用する。

詳細なGit / GitHub運用については[`07_Git・GitHub運用.md`](./07_Git・GitHub運用.md)を参照する。

---

### 6.1 Task選択

`To Do`から次に実装するTaskを選択する。

選択時に以下を確認する。

- Milestone
- Priority
- Dependencies
- 関連Task

着手するTaskを`In Progress`へ変更する。

原則として同時に多数のTaskを`In Progress`にしない。

個人開発ではコンテキストスイッチを抑えるため、原則として1つの主要Taskへ集中する。

---

### 6.2 関連資料・コード調査

実装前に関連する以下を確認する。

- 要件
- Architecture
- System Design
- Technology Decision
- API仕様
- 非機能要件
- 既存Source Code
- 関連Task

既存設計と矛盾する実装を避ける。

設計変更が必要になった場合は、Task内だけで新しい設計を確定せず、該当するSource of Truthを更新する。

---

### 6.3 Implementation Plan

調査後、実装前にImplementation Planを作成する。

Implementation Planには必要に応じて以下を含める。

- 変更対象
- 実装手順
- 追加・変更する主要ファイル
- Test方針
- Migrationの有無
- OpenAPI変更の有無
- 既存設計への影響

Implementation Planは実装前の確認材料であり、詳細な設計ドキュメントの代替にはしない。

小規模で自明なTaskでは、Taskの規模に応じてImplementation Planを簡潔にしてよい。

---

### 6.4 Plan Review

Implementation Planを確認し、以下をチェックする。

- 既存設計と矛盾していない
- TaskのScopeを超えていない
- 不要な実装を含んでいない
- Test方法が明確である
- Acceptance Criteriaを満たせる計画になっている

必要に応じてPlanを修正してから実装へ進む。

---

### 6.5 Implementation

確認したImplementation Planを基準として実装する。

実装中にPlanから大きく変更する必要が発生した場合は、理由を確認し、必要に応じてPlanを更新する。

Task Scope外の問題を発見した場合、原則として現在のTaskへ無制限に取り込まず、新しいTaskとして管理する。

実装中に設計変更が必要になった場合は、該当するSource of Truthも更新する。

---

### 6.6 Test・品質確認

実装後、Taskに関係するTest・品質確認を実行する。

対象には必要に応じて以下を含める。

```text
Unit Test
Feature / Integration Test
Frontend Test
Type Check
Lint
Formatter
Static Analysis
Complexity Check
OpenAPI Lint
OpenAPI Type Generation
Build
```

具体的な品質基準については以下を参照する。

```text
docs/06_開発・運用/05_コード品質・複雑度監視.md
```

CIが利用可能な段階では、CI上でも必要なチェックが成功することを確認する。

---

### 6.7 完了確認

Acceptance Criteriaを1項目ずつ確認する。

続いてDefinition of Doneを確認する。

すべての必須条件を満たした場合のみTaskを完了できる。

未完了の条件がある場合は`Done`へ変更しない。

Git / GitHubを利用するTaskでは、Pull RequestやMergeを含むGit側の完了条件についても確認する。

---

### 6.8 Final Summary

Task完了時にFinal Summaryを記録する。

Final Summaryには必要に応じて以下を記載する。

- 実装した内容
- 主な変更箇所
- 実行したTest・品質確認
- 設計から変更した点
- 残課題
- 新しく作成したTask

詳細な変更履歴をTaskへ複製する必要はなく、Git履歴やSource Codeと組み合わせて追跡できる粒度とする。

---

## 7. Git / GitHubとの連携

TaskとGit / GitHubは原則として以下の関係とする。

```text
Backlog.md Task
      ↓
Work Branch
      ↓
Commit
      ↓
Pull Request
      ↓
dev
```

基本的な対応関係は以下とする。

```text
1 Task
  ≒
1 Work Branch
  ≒
1 Pull Request
```

Task単位でWork Branchを作成することで、Taskの目的とSource Codeの変更範囲を追跡できるようにする。

Work BranchやPull RequestではBacklog.mdが採番したTask IDを使用し、TaskとGit履歴のトレーサビリティを確保する。

Task内では複数Commitを作成してよい。

Branch命名、Commit Message、Commit粒度、Pull Request、Merge Strategy、GitHub Repository設定などの詳細は[`07_Git・GitHub運用.md`](./07_Git・GitHub運用.md)をSource of Truthとする。

---

## 8. docs・OpenAPIとの関係

### 8.1 docs

`docs/`は要件、設計、技術選定、開発ルールなどのSource of Truthとする。

Taskは実装作業を管理するものであり、設計ドキュメントの代替にはしない。

```text
docs
  ↓
What / Why / Architecture / Rules

Backlog.md
  ↓
Work / Progress / Acceptance

Source Code
  ↓
Implementation
```

実装中に設計変更が発生した場合は、必要に応じて該当する`docs/`を更新する。

Phase固有の進捗や一時的な実装管理を目的として、不要なドキュメントを`docs/`へ追加しない。

---

### 8.2 OpenAPI

Backend API契約についてはOpenAPIをSource of Truthとする。

API実装Taskでは、既存のOpenAPI First方針に従う。

基本サイクルは以下とする。

```text
Task
  ↓
OpenAPI変更
  ↓
OpenAPI Lint
  ↓
Type Generation
  ↓
Backend Implementation
  ↓
BFF Implementation
  ↓
Test
  ↓
Quality Check
  ↓
Done
```

API契約をLaravel ControllerやNext.js実装から逆生成してSource of Truthとする運用は行わない。

---

## 9. AI Agentとの開発フロー

AI Agentを利用する場合も、通常のTask開発フローを変更しない。

基本フローは以下とする。

```text
Human
  ↓
Task選択・要求確認
  ↓
AI Agent
  ↓
関連docs・コード調査
  ↓
Implementation Plan作成
  ↓
Human
  ↓
Plan Review
  ↓
AI Agent / Human
