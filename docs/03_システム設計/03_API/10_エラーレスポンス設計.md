# エラーレスポンス設計

Engineer Skill Management App の Next.js BFF と Laravel Backend API 間におけるエラーレスポンスの共通仕様を定義します。

本ドキュメントでは、HTTP Status Code、Error Code、Validation Error、Domain Error、Exception から HTTP Response への変換、OpenAPI 定義、Client への公開範囲などを扱います。

API 契約の Source of Truth は OpenAPI とし、本ドキュメントはエラー契約を設計・実装するための共通方針を定義するものとします。

---

## 1. 目的

エラーレスポンス設計の目的は、Laravel Backend API と Next.js BFF の間で一貫したエラー契約を提供することです。

以下を実現します。

- API 全体で Error Response の形式を統一する
- HTTP Status Code の使い分けを統一する
- Client が機械的にエラーを判定できるようにする
- Validation Error と Domain Error を区別する
- Domain Exception と HTTP の責務を分離する
- Laravel 固有の Exception を API 契約へ露出させない
- 内部実装や機密情報を Client へ公開しない
- OpenAPI 上で Error Response を明示する
- Next.js BFF が安定して Error Handling できるようにする

---

## 2. 基本方針

以下を基本方針とします。

- Error Response は統一された JSON 形式とする
- HTTP Status Code でエラーの大分類を表現する
- `error.code` で具体的なエラー理由を表現する
- `error.message` は人間が理解するための補助情報とする
- Client は `message` の文字列比較で処理分岐しない
- Field Validation Error は `details` で表現する
- HTTP Validation と Domain Rule 違反を区別する
- Domain Layer は HTTP Status Code を知らない
- Domain Exception は Presentation Layer で HTTP Response へ変換する
- Infrastructure Exception をそのまま Client へ公開しない
- 想定外 Exception は原則 `500 Internal Server Error` とする
- Stack Trace や SQL 等の内部情報を Client へ公開しない
- Error Schema は OpenAPI で定義する

責務の流れは以下を基本とします。

```text
Domain / Application / Infrastructure
                │
                │ Exception
                ▼
        Presentation Layer
                │
                │ Mapping
                ▼
HTTP Status + Error Response
                │
                ▼
          Next.js BFF
```

---

## 3. 共通 Error Response Schema

### 3.1 基本形式

通常の Error Response は以下の形式とします。

```json
{
  "error": {
    "code": "EMPLOYEE_NOT_FOUND",
    "message": "Employee was not found."
  }
}
```

基本構造:

```text
error
├── code
└── message
```

`error` は必須です。

`code` と `message` も必須とします。

---

### 3.2 Validation Error形式

Field Validation Error が存在する場合は `details` を追加します。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid values.",
    "details": [
      {
        "field": "experienceMonths",
        "code": "MIN_VALUE",
        "message": "Experience period must be at least one month."
      }
    ]
  }
}
```

構造:

```text
error
├── code
├── message
└── details[]
    ├── field
    ├── code
    └── message
```

---

### 3.3 detailsの扱い

`details` は Field 単位の Validation Error など、追加の構造化情報が必要な場合のみ使用します。

通常の Domain Error では原則使用しません。

例:

```json
{
  "error": {
    "code": "LAST_PERMISSION_ADMIN_REQUIRED",
    "message": "At least one administrator capable of managing permissions must remain."
  }
}
```

Client に Domain 内部情報を渡す目的で自由形式の `details` を追加することは避けます。

必要な構造化情報が将来発生した場合は、OpenAPI Schema として明示的に定義します。

---

## 4. Error Code設計

### 4.1 命名規則

Error Code は `UPPER_SNAKE_CASE` を使用します。

```text
EMPLOYEE_NOT_FOUND
SKILL_NOT_FOUND
EMPLOYEE_SKILL_ALREADY_EXISTS
LAST_PERMISSION_ADMIN_REQUIRED
VALIDATION_ERROR
```

Error Code は機械可読であり、意味が推測できる名前とします。

---

### 4.2 Error Codeの責務

Error Code は Client がエラー原因を判定するための安定した識別子です。

例えば、

```text
409 Conflict
```

だけでは、

```text
EmployeeSkill重複
最後の権限管理可能Administrator削除
Resource状態競合
```

を区別できません。

そのため、

```text
HTTP Status
+
Error Code
```

の組み合わせでエラーを識別します。

例:

```text
409 Conflict
EMPLOYEE_SKILL_ALREADY_EXISTS
```

```text
409 Conflict
LAST_PERMISSION_ADMIN_REQUIRED
```

---

### 4.3 Messageとの使い分け

`message` は人間向けの説明です。

Client の処理分岐には使用しません。

NG:

```text
if message == "Employee was not found."
```

OK:

```text
if code == "EMPLOYEE_NOT_FOUND"
```

`message` は将来的に文言変更できるものとします。

Error Code の変更は API 契約変更として扱います。

---

## 5. HTTP Status Codeとの対応

主に以下を使用します。

| Status | 用途 |
|---|---|
| `400 Bad Request` | HTTP Request 自体を正常に解釈できない |
| `401 Unauthorized` | Authentication が成立していない |
| `403 Forbidden` | Authentication 済みだが操作権限がない |
| `404 Not Found` | 対象 Resource が存在しない |
| `409 Conflict` | 現在の Resource / Domain 状態と操作が競合する |
| `422 Unprocessable Content` | Request Validation Error |
| `500 Internal Server Error` | 想定外の Server Error |

---

### 5.1 400 Bad Request

Request 自体を正常に処理できない場合に使用します。

例:

- JSON Syntax Error
- Request Body の形式自体が不正
- HTTP Request として解釈不能

```json
{
  "error": {
    "code": "BAD_REQUEST",
    "message": "The request could not be processed."
  }
}
```

通常の Field Validation には使用しません。

---

### 5.2 401 Unauthorized

Authentication が成立していない場合に使用します。

例:

- Sanctum Token が存在しない
- Token が無効
- Authentication 情報を確認できない

```json
{
  "error": {
    "code": "UNAUTHENTICATED",
    "message": "Authentication is required."
  }
}
```

---

### 5.3 403 Forbidden

Authentication は成立しているが、操作権限がない場合に使用します。

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "You do not have permission to perform this operation."
  }
}
```

例:

```text
Team Leader
↓
担当外Employeeを閲覧
↓
403 Forbidden
```

Authorization は Laravel Backend で最終判断します。

---

### 5.4 404 Not Found

対象 Resource が存在しない場合に使用します。

```json
{
  "error": {
    "code": "EMPLOYEE_NOT_FOUND",
    "message": "Employee was not found."
  }
}
```

Resource ごとに Error Code を定義します。

例:

```text
EMPLOYEE_NOT_FOUND
SKILL_NOT_FOUND
SKILL_CATEGORY_NOT_FOUND
DEPARTMENT_NOT_FOUND
EMPLOYEE_SKILL_NOT_FOUND
USER_NOT_FOUND
```

---

### 5.5 409 Conflict

Request 自体は有効ですが、現在の Resource または Domain の状態と操作が競合する場合に使用します。

例:

```text
EmployeeSkill重複
```

```json
{
  "error": {
    "code": "EMPLOYEE_SKILL_ALREADY_EXISTS",
    "message": "The employee already has this skill."
  }
}
```

また、

```text
権限管理可能なAdministratorが1人
↓
そのAdministratorから権限管理能力を外す
```

場合:

```json
{
  "error": {
    "code": "LAST_PERMISSION_ADMIN_REQUIRED",
    "message": "At least one administrator capable of managing permissions must remain."
  }
}
```

Domain の状態に依存する Business Rule 違反は、原則として `409 Conflict` を第一候補とします。

ただし、すべての Domain Error を機械的に `409` にすることはしません。

---

### 5.6 422 Unprocessable Content

HTTP Input Validation Error に使用します。

例:

```text
必須Field不足
型不正
Format不正
許可されていないEnum
最小値・最大値違反
```

Response:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid values.",
    "details": [
      {
        "field": "skillLevel",
        "code": "INVALID_VALUE",
        "message": "The selected skill level is invalid."
      }
    ]
  }
}
```

---

### 5.7 500 Internal Server Error

想定外 Exception に使用します。

```json
{
  "error": {
    "code": "INTERNAL_SERVER_ERROR",
    "message": "An unexpected error occurred."
  }
}
```

Client へ具体的な内部エラー内容は公開しません。

---

## 6. Validation Error設計

### 6.1 HTTP Input Validation

Presentation Layer では、HTTP Request として必要な Validation を行います。

例:

```text
required
string
integer
boolean
format
enum
min
max
```

Laravel では Form Request を利用します。

```text
HTTP Request
    ↓
Form Request
    ↓
Request DTO
    ↓
Application Layer
```

---

### 6.2 Field Error

Field Error は以下の形式とします。

```json
{
  "field": "experienceMonths",
  "code": "MIN_VALUE",
  "message": "Experience period must be at least one month."
}
```

`field` は API の JSON Property 名を使用します。

したがって、

```text
experience_months
```

ではなく、

```text
experienceMonths
```

を返します。

---

### 6.3 複数Error

複数の Validation Error が存在する場合は `details` に複数格納します。

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid values.",
    "details": [
      {
        "field": "skillLevel",
        "code": "INVALID_VALUE",
        "message": "The selected skill level is invalid."
      },
      {
        "field": "experienceMonths",
        "code": "MIN_VALUE",
        "message": "Experience period must be at least one month."
      }
    ]
  }
}
```

可能な範囲で一度の Request で検出できた Validation Error をまとめて返します。

---

### 6.4 Domain Validationとの境界

HTTP Validation と Domain Invariant は分離します。

例えば EmployeeSkill には、

```text
実務未経験
→ Level 1のみ

実務経験あり
→ 経験期間1か月以上
→ 最終利用年月必須
```

という Domain Invariant があります。

Presentation Layer で早期 Validation を行える場合でも、Domain Layer でも Invariant を必ず維持します。

```text
Presentation Validation
        │
        ▼
Application
        │
        ▼
Domain Invariant
```

Presentation Validation は Domain Invariant の代替ではありません。

---

## 7. Domain Error設計

### 7.1 Domain Rule違反

Domain Rule 違反は Domain / Application 側で検出します。

Domain Layer は以下を知りません。

```text
HTTP
409
422
JSON
OpenAPI
```

Domain は Domain の意味だけを表現します。

概念例:

```text
LastPermissionAdministratorRequired
EmployeeSkillAlreadyExists
InvalidEmployeeSkillLevel
```

Presentation Layer がこれを API Error へ変換します。

---

### 7.2 Resource状態競合

現在の状態によって操作できない場合は `409 Conflict` を基本とします。

例:

```text
無効化済みSkillを再度無効化する
EmployeeSkillが既に存在する
最後の権限管理可能Administratorを削除する
現在の状態では実行できないDomain Operation
```

操作ごとの Idempotency の意味を考慮し、同じ操作の再実行を必ず `409` にするわけではありません。

---

### 7.3 Not Foundとの境界

Resource が存在しない場合は `404` とします。

Business Rule 違反と Not Found を混在させません。

```text
Employee自体が存在しない
→ 404 EMPLOYEE_NOT_FOUND

Employeeは存在するが現在の状態では操作できない
→ 409
```

---

### 7.4 Authorizationとの境界

Resource が存在していても操作権限がない場合は原則 `403` とします。

```text
存在しない
→ 404

存在する
+
権限がない
→ 403
```

ただし、Resource の存在自体を権限のない User に知らせることが Security 上望ましくない Endpoint では、`404` として扱うことを許可します。

この判断は Endpoint ごとに明示します。

---

## 8. ExceptionからHTTP Responseへの変換

### 8.1 責務分担

Exception → HTTP Response の変換は Presentation Layer の責務とします。

```text
Domain Exception
Application Exception
Infrastructure Exception
        │
        ▼
Presentation
Exception Mapping
        │
        ▼
HTTP Response
```

Domain / Application Layer が HTTP Response を生成することは禁止します。

---

### 8.2 Presentation Layerでの変換

Laravel の Exception Handling 機構を利用し、API Error Response へ統一的に変換します。

概念例:

```text
EmployeeNotFound
    ↓
404
EMPLOYEE_NOT_FOUND
```

```text
LastPermissionAdministratorRequired
    ↓
409
LAST_PERMISSION_ADMIN_REQUIRED
```

Controller 内で大量の `try/catch` を記述することは避けます。

---

### 8.3 Application / Domain Exception

Application / Domain で想定される Error は明示的に API Error へ Mapping します。

```text
Domain / Application
        │
        ▼
Exception Mapper
        │
        ├── HTTP Status
        ├── Error Code
        └── Message
```

Exception Class 名をそのまま Error Code として自動公開する方式は採用しません。

API Error Code は OpenAPI 契約として独立して管理します。

---

### 8.4 Infrastructure Exception

Infrastructure の具体的な Exception は原則 Client へ公開しません。

例:

```text
PDOException
QueryException
Redis Exception
HTTP Client Exception
```

例えば Unique Constraint 違反が発生した場合でも、

```text
SQLSTATE[23505]
```

を Client へ返しません。

想定可能な競合であれば適切な Domain / Application Error に変換します。

想定外であれば `500 Internal Server Error` とします。

DB 制約は最終防衛線であり、API 契約そのものにはしません。

---

### 8.5 想定外Exception

想定外 Exception は、

```text
500 Internal Server Error
INTERNAL_SERVER_ERROR
```

へ統一します。

具体的な Exception Message は Server Log に記録し、Client には公開しません。

---

## 9. エラー情報の公開範囲

### 9.1 Clientへ公開する情報

Client へ公開する情報は必要最小限とします。

基本的に以下です。

```text
HTTP Status
Error Code
安全なMessage
Validation Field
Validation Code
Validation Message
```

---

### 9.2 Clientへ公開しない情報

以下は Client へ公開しません。

```text
SQL
Database Table名
Database Column名
Stack Trace
File Path
Class内部構造
Environment Variable
Token
Credential
Infrastructure Host
内部Exception Message
```

---

### 9.3 Stack Trace

Production API Response に Stack Trace を含めません。

```text
APP_DEBUG=false
```

を前提とします。

Development 環境でも、API 契約そのものに Stack Trace を含める仕様にはしません。

---

### 9.4 Database / Framework情報

以下のような情報を API Response へ直接公開しません。

```text
Illuminate\Database\QueryException
PDOException
SQLSTATE
PostgreSQL Constraint名
Laravel File Path
```

Laravel / PostgreSQL の実装詳細と API 契約を分離します。

---

## 10. Authentication / Authorization Error

### 10.1 未認証

Authentication が成立しない場合:

```text
401 Unauthorized
UNAUTHENTICATED
```

Response:

```json
{
  "error": {
    "code": "UNAUTHENTICATED",
    "message": "Authentication is required."
  }
}
```

---

### 10.2 権限不足

Authentication 済みだが権限がない場合:

```text
403 Forbidden
FORBIDDEN
```

Response:

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "You do not have permission to perform this operation."
  }
}
```

---

### 10.3 Resource存在秘匿

Resource の存在自体を Unauthorized User に公開することが問題になる場合は、

```text
403
```

ではなく、

```text
404
```

として扱うことを許可します。

ただし、API 全体で無条件に `404` へ統一することはしません。

Endpoint の Security Requirement に応じて決定します。

---

## 11. OpenAPI設計

### 11.1 Error Schema

共通 Error Schema を `components/schemas` に定義します。

概念構成:

```text
components/
└── schemas/
    ├── ErrorResponse
    ├── Error
    ├── ValidationErrorResponse
    └── ValidationErrorDetail
```

---

### 11.2 Validation Error Schema

Validation Error 専用 Schema を定義します。

概念:

```yaml
ValidationErrorDetail:
  type: object
  required:
    - field
    - code
    - message
```

Endpoint ごとに Validation Error の構造を独自定義することは避けます。

---

### 11.3 共通Response

再利用可能な Response を `components/responses` に定義します。

概念:

```text
components/
└── responses/
    ├── BadRequest
    ├── Unauthorized
    ├── Forbidden
    ├── ValidationError
    └── InternalServerError
```

Resource 固有の `404` や Domain 固有の `409` については、Endpoint 契約として Error Code を明示します。

---

### 11.4 Endpointからの参照方法

共通 Response は `$ref` で再利用します。

概念例:

```yaml
responses:
  '401':
    $ref: '#/components/responses/Unauthorized'

  '403':
    $ref: '#/components/responses/Forbidden'

  '422':
    $ref: '#/components/responses/ValidationError'

  '500':
    $ref: '#/components/responses/InternalServerError'
```

Endpoint 固有 Error については、その Endpoint で発生可能な Error Code が分かるように定義します。

---

## 12. Next.js BFF側のError Handling

### 12.1 HTTP Statusによる大分類

BFF はまず HTTP Status によりエラーを大分類できます。

```text
401
→ Authentication

403
→ Authorization

404
→ Not Found

409
→ Conflict

422
→ Validation

5xx
→ Server Error
```

---

### 12.2 error.codeによる分岐

具体的な処理が必要な場合は `error.code` を使用します。

```text
409
+
EMPLOYEE_SKILL_ALREADY_EXISTS
```

などの組み合わせで判断します。

---

### 12.3 messageを分岐条件にしない

以下は禁止します。

```text
if (error.message === "...") {
    ...
}
```

処理分岐には、

```text
error.code
```

を使用します。

---

### 12.4 Frontend表示との境界

Backend の `message` をそのまま最終 UI 文言として表示することを必須としません。

```text
Laravel
    ↓
API Error
    ↓
Next.js BFF
    ↓
Frontend
    ↓
User向けMessage
```

Frontend は Error Code 等をもとに、必要に応じて適切な User 向けメッセージへ変換できます。

これにより、

```text
API内部の説明
```

と

```text
UI/UX上適切な説明
```

を分離します。

---

## 13. Loggingとの関係

### 13.1 Client ResponseとServer Logの分離

Client Response と Server Log は目的を分離します。

Client:

```text
必要最小限
安全
安定したAPI契約
```

Server Log:

```text
原因調査に必要な詳細情報
Exception
Stack Trace
Request Context
```

Client に詳細情報を返す代わりに Server Log を充実させます。

---

### 13.2 Correlation ID / Request ID

障害調査のため、Request 単位で追跡可能な ID を利用します。

非機能要件の Logging / Observability 方針に従い、

```text
Request ID
```

等によって API Request と Log を関連付けられるようにします。

Error Response に Request ID を含める必要性については、Observability 実装時に最終決定します。

MVP の API Error Schema の必須 Property には含めません。

---

### 13.3 5xx Error

`5xx` は Server 側の異常として扱います。

必要な情報を Server Log に記録します。

```text
Request ID
Endpoint
HTTP Method
User Context
Exception
Stack Trace
```

Token や Password 等の機密情報は Log に記録しません。

---

## 14. Error Code一覧の管理方針

### 14.1 共通Error Code

API 全体で使用する Error Code は本ドキュメントで管理します。

MVP の共通 Error Code:

| Error Code | HTTP Status | 用途 |
|---|---:|---|
| `BAD_REQUEST` | 400 | Request 自体が不正 |
| `UNAUTHENTICATED` | 401 | 未認証 |
| `FORBIDDEN` | 403 | 権限不足 |
| `VALIDATION_ERROR` | 422 | HTTP Input Validation |
| `INTERNAL_SERVER_ERROR` | 500 | 想定外 Server Error |

---

### 14.2 Context別Error Code

Business / Resource 固有 Error Code は、それぞれの API / Context 設計で定義します。

例:

```text
Employee Management

EMPLOYEE_NOT_FOUND
DEPARTMENT_NOT_FOUND
```

```text
Skill Management

SKILL_NOT_FOUND
SKILL_CATEGORY_NOT_FOUND
EMPLOYEE_SKILL_NOT_FOUND
EMPLOYEE_SKILL_ALREADY_EXISTS
```

```text
Access Control

LAST_PERMISSION_ADMIN_REQUIRED
```

すべての Domain Error Code を本ファイルへ集約しません。

---

### 14.3 Endpoint固有Error

各 Endpoint の OpenAPI 定義では、その Endpoint から発生し得る Error を明確にします。

例えば、

```text
POST /employee-skills
```

であれば、

```text
401 UNAUTHENTICATED
403 FORBIDDEN
404 EMPLOYEE_NOT_FOUND
404 SKILL_NOT_FOUND
409 EMPLOYEE_SKILL_ALREADY_EXISTS
422 VALIDATION_ERROR
500 INTERNAL_SERVER_ERROR
```

などを契約として明示します。

---

### 14.4 将来の追加ルール

新しい Error Code を追加するときは以下を確認します。

- 既存 Error Code で表現できないか
- Client が区別する必要があるか
- Domain の意味を適切に表現しているか
- HTTP Status が適切か
- 内部実装詳細を表現していないか
- OpenAPI に定義されているか

必要以上に細かい Error Code を増やしません。

### 15.5 Internal Server Error

想定外 Exception:

```http

```

```json
{
  "error": {

  }
```

実際の Exception:

```text
PDOException
QueryException
Stack Trace
SQL
```

等は Server Log のみに記録します。

## 16. 採用しない方針

MVP では以下を採用しません。

- Laravel 標準 Validation Response の無加工公開
- Exception Message の直接公開
- Exception Class 名の Error Code 化
- SQLSTATE の API Error Code 化
- Database Constraint 名の公開
- Stack Trace の API Response への追加
- HTTP Status を常に `200 OK` とする Error Response
- Error Message の文字列比較による Client 分岐
- すべての Domain Error を `422` に統一
- すべての Domain Error を `409` に統一
- 自由形式の `details`
- Endpoint ごとに異なる Error Response 構造
- Domain Layer から HTTP Response を生成
- Eloquent / Database Exception の直接公開
- Error Code の過度な細分化
