# MVP Entity カラム設計 最終版

## 1. 基本方針

MVPでは以下の6 Entityを使用する。

1. User
2. Department
3. Employee
4. SkillCategory
5. Skill
6. EmployeeSkill

基本方針：

- Primary Keyは`bigint`
- Auto Incrementを使用する
- Foreign Key Constraintを設定する
- 業務上重要な整合性はLaravel ValidationだけでなくPostgreSQL Constraintでも保証する
- Soft Deleteは原則使用しない
- 業務上の「無効」は`is_active`で管理する
- `created_at` / `updated_at`を保持する
- Cascade Deleteは原則使用しない
- 一般社員はApplicationを利用しない
- UserとEmployeeは別Entityとして管理する
- Userは必ず1人のEmployeeに紐付く
- EmployeeはUserを持たなくてもよい

---

# 2. Entity Relation

全体の基本Relation：

    Department
        |
        | 1:N
        v
    Employee
        |
        | 1:N
        v
    EmployeeSkill
        ^
        | N:1
        |
       Skill
        ^
        | N:1
        |
    SkillCategory

認証利用者：

    Employee
        |
        | 1 : 0..1
        v
       User

意味：

- 1人のEmployeeは最大1つのUserを持つ
- EmployeeはUserを持たなくてもよい
- Userは必ずEmployeeに紐付く

---

# 3. users

Applicationを利用するUserを管理する。

MVPでは管理ユーザーのみApplicationを利用する。

将来的にはサブマネージャー、チームリーダー等もUserとして管理する。

## Columns

| Column | Type | NULL | Default | Constraint | 説明 |
| --- | --- | --- | --- | --- | --- |
| id | bigint | NOT NULL | Auto Increment | PK | User ID |
| employee_id | bigint | NOT NULL | - | FK, UNIQUE | 対応するEmployee |
| login_id | varchar | NOT NULL | - | UNIQUE | Login ID |
| password | varchar | NOT NULL | - | - | Password Hash |
| name | varchar | NOT NULL | - | - | Application上の表示名 |
| is_active | boolean | NOT NULL | true | - | User利用可否 |
| created_at | timestamp | NOT NULL | - | - | 作成日時 |
| updated_at | timestamp | NOT NULL | - | - | 更新日時 |

## Foreign Key

    users.employee_id
        ↓
    employees.id

## Constraint

    PRIMARY KEY (id)

    UNIQUE (employee_id)

    UNIQUE (login_id)

これにより、1人のEmployeeに複数Userを作成できない。

## Relation

    Employee 1
        |
        | 0..1
        v
       User

## 補足

MVPでは管理ユーザーのみ利用する。

以下は後続の権限設計で追加する。

- 管理ユーザー
- 権限管理可能な管理ユーザー
- サブマネージャー
- チームリーダー

Role / PermissionをどのTable構成で管理するかは別途設計する。

## Constraint

## Relation

    Department 1
        |

## MVP運用

MVPではDepartment管理画面を作成しない。

初期DepartmentはSeederで登録する。

例：

    DepartmentSeeder

社員登録・編集では、

    is_active = true

のDepartmentのみ選択可能とする。

Departmentが無効化されても、既存社員とのRelationは保持する。

# 5. employees

スキル管理対象となる社員を管理する。

Applicationを利用しない一般社員もEmployeeとして保持する。

## Columns

| Column | Type | NULL | Default | Constraint | 説明 |
| --- | --- | --- | --- | --- | --- |
| id | bigint | NOT NULL | Auto Increment | PK | Employee ID |
| employee_number | varchar | NOT NULL | - | UNIQUE | 社員番号 |
| name | varchar | NOT NULL | - | - | 氏名 |
| department_id | bigint | NOT NULL | - | FK | 所属部署 |
| employment_status | varchar | NOT NULL | ACTIVE | CHECK | 在籍状態 |
| retirement_date | date | NULL | NULL | CHECK | 退職日 |
| created_at | timestamp | NOT NULL | - | - | 作成日時 |
| updated_at | timestamp | NOT NULL | - | - | 更新日時 |

## 管理しない社員属性

MVPおよび現時点では以下を管理しない。

- 職種
- 役職
- チーム
- 入社年月
- メールアドレス
- プロフィール画像

---

## Foreign Key

    employees.department_id
        ↓
    departments.id

---

## employee_number

社員番号は一意とする。

    UNIQUE (employee_number)

Database Primary Keyとは別に、
業務上の社員識別子として利用する。

---

## employment_status

以下の値のみ許可する。

    ACTIVE
    LEAVE
    RETIRED

意味：

    ACTIVE
    在籍

    LEAVE
    休職

    RETIRED
    退職

CHECK Constraint：

    CHECK (
        employment_status IN (
            'ACTIVE',
            'LEAVE',
            'RETIRED'
        )
    )

---

## retirement_date

社員の実際の退職日を保存する。

Type：

    date

### ACTIVEの場合

    employment_status = ACTIVE
    retirement_date = NULL

### LEAVEの場合

    employment_status = LEAVE
    retirement_date = NULL

### RETIREDの場合

    employment_status = RETIRED
    retirement_date IS NOT NULL

---

## employment_status / retirement_date CHECK Constraint

概念：

    CHECK (
        (
            employment_status IN ('ACTIVE', 'LEAVE')
            AND retirement_date IS NULL
        )
        OR
        (
            employment_status = 'RETIRED'
            AND retirement_date IS NOT NULL
        )
    )

Laravel側でも同じValidationを行う。

---

## 退職社員の保持

退職社員は、

    retirement_date

を基準として3年間保持する。

例：

    retirement_date <= 基準日 - 3 years

となったEmployeeを削除確認対象とする。

ただし自動削除は行わない。

    退職
      ↓
    3年間保持
      ↓
    削除候補
      ↓
    管理ユーザーが確認
      ↓
    削除

とする。

---

## Index

    PRIMARY KEY (id)

    UNIQUE (employee_number)

    INDEX (department_id)

    INDEX (employment_status)

`retirement_date` のIndexについては、
Employee数・削除候補検索の実Queryを確認して追加を検討する。

Employeeが保有するSkillを管理する。

単純なPivot Tableではなく、

| Column | Type | NULL | Default | Constraint | 説明 |
| --- | --- | --- | --- | --- | --- |

| skill_id | bigint | NOT NULL | - | FK | Skill |

| comment | text | NULL | NULL | - | コメント |
| experience_details | text | NULL | NULL | - | 実績・経験内容 |

# 9. employee_skills Relation

## Employee

    employee_skills.employee_id
        ↓
    employees.id

## Skill

    employee_skills.skill_id
        ↓
    skills.id

Relation：

    Employee 1
        |
        └── N EmployeeSkill

    Skill 1
        |
        └── N EmployeeSkill

したがって、

    Employee N : M Skill

の関係をEmployeeSkillで表現する。

---

# 10. Employee + Skill Unique Constraint

同じEmployeeへ同じSkillを複数登録できない。

    UNIQUE (
        employee_id,
        skill_id
    )

例えば：

    Employee A
      ├── PHP
      └── PHP

は禁止する。

EmployeeSkillを無効化した後に再登録する場合も、
新規Recordを作らず既存Recordを再有効化する。

---

# 11. experience_months

経験年数はDatabaseでは月数で保存する。

例：

    1か月
        ↓
    1

    1年
        ↓
    12

    3年6か月
        ↓
    42

Frontendでは年 + 月として表示する。

例：

    experience_months = 42

        ↓

    3年6か月

検索：

    経験3年以上

は、

    experience_months >= 36

として扱える。

---

# 12. skill_level

スキルレベルは全カテゴリ共通でLevel 1〜5とする。

Databaseでは`smallint`で保存する。

    CHECK (
        skill_level BETWEEN 1 AND 5
    )

スキルレベルは固定値なのでMaster Tableにはしない。

---

# 13. 実務経験なしの場合

    has_work_experience = false

の場合、以下を必須ルールとする。

    experience_months = 0

    skill_level = 1

    last_used_date = NULL

つまり、

    実務経験なし
        ↓
    Level 1のみ

とする。

Level 2〜5は許可しない。

---

# 14. 実務経験ありの場合

    has_work_experience = true

の場合：

    experience_months >= 1

    skill_level BETWEEN 1 AND 5

    last_used_date IS NOT NULL

とする。

実務経験ありかつ、

    experience_months = 0

は禁止する。

---

# 15. last_used_date

要件上の意味：

    実務で最後に利用した年月

Databaseでは`date`型1カラムとして保存する。

例：

    2026年8月
        ↓
    2026-08-01

対象月の1日へ正規化して保存する。

Frontend / APIでは年月として扱う。

例：

    2026-08

Database上の日部分は業務上の意味を持たない。

---

## 実務経験なし

    last_used_date = NULL

## 実務経験あり

    last_used_date IS NOT NULL

---

## 月初日Constraint

`last_used_date` はNULLまたは必ず月初日とする。

概念：

    CHECK (
        last_used_date IS NULL
        OR EXTRACT(DAY FROM last_used_date) = 1
    )

---

# 16. EmployeeSkill Business Rule Constraint

主要な業務ルールをPostgreSQLでも保証する。

概念：

    CHECK (
        (
            has_work_experience = false
            AND experience_months = 0
            AND skill_level = 1
            AND last_used_date IS NULL
        )
        OR
        (
            has_work_experience = true
            AND experience_months >= 1
            AND skill_level BETWEEN 1 AND 5
            AND last_used_date IS NOT NULL
        )
    )

Laravel Validationでも同じルールを保証する。

---

# 17. employee_skills Index

必須：

    PRIMARY KEY (id)

    UNIQUE (
        employee_id,
        skill_id
    )

Foreign Key利用：

    INDEX (employee_id)

    INDEX (skill_id)

以下は実際のQueryを確認して追加を検討する。

- skill_level
- has_work_experience
- is_active
- experience_months
- last_used_date
- skill_id + is_active
- skill_id + experience_months

MVP段階では過剰なIndexを作らない。

# 18. is_active の意味

以下のEntityでは業務上の無効化を`is_active`で管理する。

- users
- departments
- skill_categories
- skills
- employee_skills

`is_active = false` は削除とは異なる。

例えばEmployeeSkill：

    is_active = false

の場合、

- 通常一覧から除外
- 社員検索から除外
- 技術別社員一覧から除外
- Dashboard集計から除外

する。

必要に応じて再有効化できる。

---

# 19. Soft Delete

MVPではLaravelのSoftDeletesを原則使用しない。

つまり、

    deleted_at

を業務上の無効化目的で利用しない。

理由：

    削除

と、

    無効化

は業務上意味が異なるため。

---

# 20. Foreign Key削除方針

Cascade Deleteは原則使用しない。

例えば、

    departments
        ↓
    employees
        ↓
    employee_skills

について、親Record削除によって子Recordまで自動削除する構成にはしない。

削除が必要な場合は業務ルールに従って明示的に処理する。

---

# 21. Primary Key

すべてのMVP Entityで`bigint` Auto Incrementを利用する。

対象：

    users.id
    departments.id
    employees.id
    skill_categories.id
    skills.id
    employee_skills.id

Laravelでは基本的に：

    $table->id();

相当を利用する。

MVPではUUID / ULIDを採用しない。

    updated_at

Laravel標準のTimestamp管理を利用する。

Timezoneの具体的な取り扱いはDate / Time設計で決定する。

# 28. Laravel側で保証するもの

Database Constraintだけに依存せず、
Laravel側でも業務ルールをValidationする。

主な対象：

- Employee Number重複
- Skill重複
- 実務経験と経験月数の整合性
- 実務経験とSkill Levelの整合性
- 実務経験と最終利用年月の整合性
- employment_statusとretirement_dateの整合性
- 無効Departmentの選択禁止
- 無効Skillの新規登録禁止

Database Constraintは最終的なデータ整合性保証として利用する。

# 29. 現時点の決定事項

## User

- Employeeとは別Entity
- UserはEmployeeへ必ず紐付く
- EmployeeはUserを持たなくてもよい
- `users.employee_id` はUNIQUE

## Department

- 独立Entity
- MVPではSeeder運用
- `is_active`で無効化

## Employee

- `job_type`は持たない
- Employee NumberはUNIQUE
- Department必須
- `employment_status`を管理
- `retirement_date`を管理

## SkillCategory

- NameはUNIQUE
- `is_active`で無効化

## Skill

- NameはUNIQUE
- SkillCategory必須
- `is_active`で無効化

## EmployeeSkill

- Employee + SkillはUNIQUE
- 経験年数は月数で保存
- Skill Levelは1〜5
- 実務経験なしはLevel 1のみ
- 最終利用年月は`last_used_date`
- `last_used_date`は月初日として保存
- `is_active`で無効化

## Primary Key

- bigint Auto Increment

## Delete

- Soft Deleteは原則使用しない
- Cascade Deleteは原則使用しない

## Database

- PostgreSQL ConstraintとLaravel Validationの両方で整合性を保証する
