# 認証方式 決定

## 1. 採用方式

BrowserとNext.jsの間はSession Cookieを利用する。

Next.js BFFとLaravel Backend APIの間はトークン認証を利用する。

基本構成：

    Browser
       |
       | HttpOnly Session Cookie
       v
    Next.js Frontend / BFF
       |
       | Access Token
       v
    Laravel Backend API
       |
       v
    PostgreSQL

---

## 2. Browserの責務

BrowserはNext.jsとのセッション情報のみ保持する。

Laravel Backend API用のAccess TokenはBrowserへ直接保持させない。

### 方針

- Session Cookieを利用する
- CookieはHttpOnlyとする
- 本番環境ではSecure属性を利用する
- Laravel API用トークンをlocalStorage等へ保存しない
- BrowserからLaravel Backend APIを直接呼び出さない

---

## 3. Next.js BFFの責務

Next.js BFFはBrowserとの認証セッションを管理する。

主な責務：

- ログイン処理
- ログアウト処理
- Browserとのセッション管理
- セッションから利用者を特定する
- Laravel API用トークンを安全に管理する
- Laravel Backend APIへ認証情報を付与してリクエストする
- Laravel Backend APIの認証エラーをFrontendへ適切に返す

Laravel API用トークンはBrowserへ露出させない。

---

## 4. Laravel Backend APIの責務

LaravelはNext.js BFFから送信されたトークンを検証する。

主な責務：

- Access Tokenの検証
- 利用者の特定
- APIアクセスの認証
- 業務上の認可
- 権限制御
- 担当社員によるアクセス制御
- 業務ロジック
- バリデーション
- データアクセス

LaravelはNext.js側の認証・表示制御だけを信頼せず、
すべての保護対象APIで必要な認可を行う。

---

## 5. 認証と認可

認証と認可を明確に分離する。

### 認証

「誰がアクセスしているか」を確認する。

例：

    user_123 がログインしている

### 認可

「その利用者が対象操作を行えるか」を確認する。

例：

    user_123
    ↓
    管理ユーザー
    ↓
    全社員を編集可能

または、

    user_456
    ↓
    サブマネージャー
    ↓
    担当社員Aは編集可能
    担当外社員Bは編集不可

認可の最終判断はLaravel Backend APIで行う。

---

## 6. 権限制御

Laravelでは以下の権限を判定する。

- 管理ユーザー
- 権限管理可能な管理ユーザー
- サブマネージャー
- チームリーダー

さらに、必要に応じて担当社員との関係を確認する。

### 管理ユーザー

- 全社員を閲覧可能
- 全社員を編集可能

### サブマネージャー

- 担当社員のみ閲覧可能
- 担当社員のみ編集可能

### チームリーダー

- 担当社員のみ閲覧可能
- 編集不可

---

## 7. Frontend側の権限制御

Next.js Frontendでも権限に応じてUIを制御する。

例：

- 編集権限がない場合は編集ボタンを表示しない
- マスタ管理権限がない場合はマスタ管理メニューを表示しない
- 担当外社員へのリンクを表示しない

ただし、Frontend側のUI制御を認可の最終手段としない。

Laravel Backend APIでも必ず認可を行う。

---

## 8. セッション

BrowserとNext.jsの間ではSession Cookieを利用する。

Session Cookieには以下を考慮する。

- HttpOnly
- Secure
- SameSite
- 有効期限
- セッション更新
- セッション破棄

具体的なSession Libraryや実装方法はNext.jsの認証技術選定時に決定する。

---

## 9. Backend API用トークン

Next.js BFFからLaravel Backend APIへAccess Tokenを送信する。

基本形：

    Authorization: Bearer <access-token>

Access Tokenの具体的な発行・失効方式はLaravel側の認証方式選定時に決定する。

候補：

- Laravel Sanctum Personal Access Token
- OAuth 2.0 Access Token
- その他

MVPでは過度に複雑なOAuth Serverの構築は行わない。

---

## 10. ログインフロー

想定フロー：

    1. Browser
       ↓
       Login Request

    2. Next.js BFF
       ↓
       認証処理

    3. Laravel
       ↓
       User Authentication

    4. Laravel
       ↓
       Access Token発行

    5. Next.js BFF
       ↓
       Tokenをサーバー側で保持

    6. Next.js
       ↓
       BrowserへSession Cookie発行

    7. Browser
       ↓
       ログイン状態となる

---

## 11. APIアクセスフロー

ログイン後：

    Browser
       |
       | Session Cookie
       v
    Next.js BFF
       |
       | Session確認
       |
       | Authorization: Bearer <token>
       v
    Laravel Backend API
       |
       | Token検証
       | 認可
       | 業務処理
       v
    PostgreSQL

---

## 12. ログアウトフロー

ログアウト時は以下を行う。

- Next.jsのBrowser Sessionを破棄する
- Laravel Backend API用トークンを失効させる
- BFF側で保持している認証情報を破棄する

Browser Sessionだけ削除してLaravel側トークンを残さない。

---

## 13. セキュリティ方針

以下を基本方針とする。

- Laravel API用トークンをBrowserへ露出させない
- Access TokenをlocalStorageへ保存しない
- CookieはHttpOnlyを利用する
- 本番環境ではHTTPSを利用する
- 本番環境ではSecure Cookieを利用する
- Backend APIでも必ず認証・認可を行う
- Tokenには適切な有効期限を設定する
- ログアウト時にTokenを失効させる
- 認証失敗時に不要な情報を返さない

---

## 14. 将来的なSSO対応

将来的にOIDC / OAuthを利用した社内SSOへ変更する可能性を考慮する。

例：

    Browser
       ↓
    Next.js BFF
       ↓
    Microsoft Entra ID / Okta / Google Workspace
       ↓
    Next.js BFF
       ↓
    Laravel Backend API

BrowserとNext.jsのSession境界を維持することで、
認証元を将来的に変更しやすい構成とする。

---

## 15. 決定事項

### Browser ↔ Next.js

Session Cookieを利用する。

### Next.js ↔ Laravel

Access Tokenによる認証を利用する。

### Token管理

Laravel API用Access TokenはNext.js BFF側で管理し、
Browserへ直接公開しない。

### 認可

Laravel Backend APIで必ず最終的な認可を行う。

### 基本構成

    Browser
       ↓
    Next.js Frontend / BFF
       ↓
    Laravel Backend API
       ↓
    PostgreSQL
