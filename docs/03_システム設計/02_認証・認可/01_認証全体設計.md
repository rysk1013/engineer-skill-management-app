# 認証方式 決定

## 1. 採用方式

BrowserとNext.jsの間はBetter AuthによるSession Cookieを利用する。

Next.js BFFとLaravel Backend APIの間はLaravel Sanctum Personal Access TokenによるBearer Token認証を利用する。

Better Auth SessionおよびLaravel Backend APIへアクセスするためのBackend CredentialはRedisで管理する。

Application DataはLaravel Backend APIからPostgreSQLへアクセスし、Next.jsからPostgreSQLへ直接アクセスしない。

基本構成：

```text
Browser
   |
   | Better Auth Session Cookie
   v
Next.js Frontend / BFF
   |
   +---- Redis
   |      ├── Better Auth Session
   |      └── Backend Credential
   |
   | Authorization: Bearer <Sanctum Token>
   v
Laravel Backend API
   |
   v
PostgreSQL
```

---

## 2. Browserの責務

BrowserはNext.jsとのSession Cookieのみ保持する。

Laravel Backend API用のSanctum TokenはBrowserへ直接保持させない。

### 方針

- Better Auth Session Cookieを利用する
- CookieはHttpOnlyとする
- Production / StagingではSecure属性を利用する
- Laravel API用TokenをlocalStorageへ保存しない
- Laravel API用TokenをsessionStorageへ保存しない
- Laravel API用TokenをJavaScriptから参照可能なCookieへ保存しない
- BrowserからLaravel Backend APIを直接呼び出さない

---

## 3. Next.js BFFの責務

Next.js BFFはBetter Authを利用してBrowserとの認証Sessionを管理する。

主な責務：

- ログイン要求の受付
- ログアウト要求の受付
- BrowserとのSession管理
- Sessionから利用者を特定する
- Laravel Login APIを呼び出す
- Laravelから取得したBackend Credentialを安全に管理する
- Laravel Backend APIへBearer Tokenを付与してリクエストする
- Laravel Backend APIの認証エラーをFrontendへ適切に返す
- 認証状態に応じたFrontend側の表示制御を補助する

Laravel API用TokenはBrowserへ露出させない。

Next.jsからPostgreSQLへ直接アクセスしない。

---

## 4. Redisの責務

RedisはNext.js / BFFの認証状態を管理するために利用する。

MVPではRedis 1台を利用し、以下を同一Redis上で管理する。

```text
Redis
├── Better Auth Session
└── Backend Credential
```

ただし、Better Auth SessionとBackend Credentialは同一の責務として扱わない。

以下を分離する。

- Key Namespace
- Access Responsibility
- Redis ACL

概念：

```text
Better Auth Session
  Namespace A
      ↓
Better Auth / Session管理用アクセス

Backend Credential
  Namespace B
      ↓
BFF Backend API Client用アクセス
```

これにより、同一Redisを利用しながらSession管理とBackend Credential管理の責務境界を維持する。

Redis ACLを利用する場合は、Better Auth Session管理用ClientとBackend Credential管理用ClientでRedis User / Credentialを分離し、それぞれが必要なKey Namespaceのみにアクセスできる構成を基本とする。

---

## 5. Laravel Backend APIの責務

Laravelはユーザー認証、Backend API認証、および業務上の最終的な認可を担当する。

主な責務：

- Login Credentialの検証
- Userの特定
- Laravel Sanctum Personal Access Tokenの発行
- Sanctum Tokenの検証
- Sanctum Tokenの失効
- APIアクセスの認証
- 業務上の認可
- 権限制御
- 担当社員によるアクセス制御
- 業務ロジック
- バリデーション
- PostgreSQLへのデータアクセス

LaravelはNext.js側の認証状態やUI制御だけを信頼せず、すべての保護対象APIで必要な認可を行う。

---

## 6. PostgreSQLの責務

PostgreSQLはApplication DataのPrimary Databaseとして利用する。

主にLaravel Backend APIからアクセスする。

基本方針：

- Application Dataを保持する
- Laravel Sanctumが必要とするToken管理情報を保持する
- Next.jsから直接アクセスしない
- Better Auth Sessionを保存しない
- Next.js側のBackend Credentialを保存しない

概念：

```text
Next.js
  └── PostgreSQLへ直接アクセスしない

Laravel
  └── PostgreSQL
       ├── Application Data
       └── Laravel Sanctum Token管理
```

---

## 7. 認証と認可

認証と認可を明確に分離する。

### 認証

「誰がアクセスしているか」を確認する。

例：

```text
user_123 がログインしている
```

BrowserとNext.js間ではBetter Auth Sessionによって利用者を識別する。

Laravel Backend APIではSanctum Tokenによって利用者を識別する。

### 認可

「その利用者が対象操作を行えるか」を確認する。

例：

```text
user_123
   ↓
管理ユーザー
   ↓
全社員を編集可能
```

または、

```text
user_456
   ↓
サブマネージャー
   ↓
担当社員Aは編集可能
担当外社員Bは編集不可
```

認可の最終判断はLaravel Backend APIで行う。

---

## 8. 権限制御

Laravelでは既存のAccess Control設計に従って権限を判定する。

例：

- 管理ユーザー
- 権限管理可能な管理ユーザー
- マネージャー
- サブマネージャー
- チームリーダー
- 一般社員

さらに、必要に応じて担当社員との関係を確認する。

具体的なRoleごとの権限はAccess Control設計をSource of Truthとする。

---

## 9. Frontend側の権限制御

Next.js Frontendでも権限に応じてUIを制御する。

例：

- 編集権限がない場合は編集操作を表示しない
- マスタ管理権限がない場合は管理メニューを表示しない
- 権限のない画面へのNavigationを制御する

ただし、Frontend側のUI制御を認可の最終手段としない。

Laravel Backend APIでも必ず認可を行う。

---

## 10. Better Auth Session

BrowserとNext.jsの間ではBetter Auth Sessionを利用する。

Session StoreにはRedisを利用する。

Sessionでは以下を考慮する。

- HttpOnly Cookie
- Secure Cookie
- SameSite
- Path
- 有効期限
- Session更新
- Session失効
- Session削除

BrowserにはSessionを識別するために必要なCookieのみを保持させる。

Laravel Sanctum TokenはBetter Auth Session Cookieへ格納しない。

---

## 11. Backend Credential

Next.js BFFからLaravel Backend APIへアクセスするためのSanctum TokenをBackend Credentialとして扱う。

Backend CredentialはRedisへ保存する。

基本方針：

- Browserへ公開しない
- Client Componentへ渡さない
- API Responseへ含めない
- localStorageへ保存しない
- sessionStorageへ保存しない
- PostgreSQLへ保存しない
- Application Logへ出力しない
- Better Auth SessionとはKey Namespaceを分離する
- Redis ACLによってアクセス責務を分離する
- SessionとのLifecycleを対応させる

Laravel APIへは以下の形式で送信する。

```text
Authorization: Bearer <sanctum-token>
```

---

## 12. Better Auth SessionとBackend Credentialの関係

Better Auth SessionとBackend Credentialは関連する認証状態だが、同一データとして管理しない。

概念：

```text
Browser
   |
   | Session Cookie
   v
Better Auth Session
   |
   | User / Sessionを識別
   v
Backend Credential参照
   |
   v
Sanctum Token
   |
   v
Laravel Backend API
```

Redis上ではKey Namespaceを分離する。

概念例：

```text
Redis
├── Better Auth Session Namespace
└── Backend Credential Namespace
```

具体的なKey Naming、TTL、ACLはRedis / Session詳細設計で定義する。

Backend CredentialはBetter Auth Session単位で管理する。

1つのBetter Auth Sessionに対して1つのBackend Credentialを対応させ、
複数Session間でBackend Credentialを共有しない。

概念：

```text
User
├── Session A
│   └── Backend Credential A
└── Session B
    └── Backend Credential B
```

これにより、Session単位でLogoutやCredential失効を行える構成とする。

SessionとBackend Credentialを関連付ける識別子、およびRedis Key Namingの詳細はRedis / Session詳細設計で定義する。

---

## 13. ログインフロー

想定フロー：

```text
1. Browser
   |
   | Login Request
   v

2. Next.js BFF
   |
   | Credentials
   v

3. Laravel Login API
   |
   | Credential検証
   v

4. Laravel
   |
   | Sanctum Token発行
   v

5. Next.js BFF
   |
   | Backend CredentialをRedisへ保存
   v

6. Better Auth
   |
   | SessionをRedisへ作成
   v

7. Next.js
   |
   | Session Cookie発行
   v

8. Browser
   |
   v
Login完了
```

Laravel Sanctum TokenをBrowserへ返さない。

---

## 14. APIアクセスフロー

ログイン後：

```text
Browser
   |
   | Better Auth Session Cookie
   v
Next.js BFF
   |
   | Better Auth Session確認
   v
Redis
   |
   | Backend Credential取得
   v
Next.js BFF
   |
   | Authorization: Bearer <Sanctum Token>
   v
Laravel Backend API
   |
   | Token検証
   | 認可
   | 業務処理
   v
PostgreSQL
```

BrowserからLaravel Backend APIを直接呼び出さない。

---

## 15. ログアウトフロー

ログアウト時は以下を行う。

```text
1. Browser
   |
   | Logout Request
   v

2. Next.js BFF
   |
   | Session特定
   v

3. Redis
   |
   | Backend Credential取得
   v

4. Laravel
   |
   | Sanctum Token失効
   v

5. Redis
   |
   | Backend Credential削除
   | Better Auth Session失効
   v

6. Browser
   |
   | Session Cookie無効化
   v

7. Logout完了
```

Browser Sessionだけを削除してLaravel側のSanctum Tokenを残さない。

---

## 16. SessionとBackend CredentialのLifecycle

Better Auth SessionとBackend Credentialは対応するLifecycleを持つ。

考慮する状態：

```text
Better Auth Session
有効

Backend Credential
失効
```

この場合、Next.js BFFはLaravelからの401 Unauthorizedを検出し、該当する認証状態を利用不能として扱う。

逆にBetter Auth Sessionが失効した場合、そのSessionに対応するBackend Credentialも不要になる。

SessionとBackend Credentialの不整合を長期間残さない設計とする。

---

## 17. Backend Credentialの有効期限

Laravel Sanctum Tokenには適切な有効期限を設定する。

Better Auth SessionとBackend Credentialの有効期限は、それぞれの責務に応じて管理する。

以下を考慮する。

- Better Auth Session有効期限
- Sanctum Token有効期限
- Session更新
- Credential失効
- Logout
- User無効化
- 強制Logout

具体的な有効期限はSecurity / Session詳細設計で決定する。

---

## 18. User無効化

Userが無効化された場合は、原則として以下を行う。

```text
User無効化
   ↓
Sanctum Token失効
   ↓
Backend Credential削除
   ↓
Better Auth Session失効
```

無効化されたUserが既存Sessionを使い続けられないようにする。

具体的な失効処理は関連UseCase設計で定義する。

---

## 19. Redis障害時

Redisは認証状態を管理するため、利用できない場合は認証済み状態を安全側に倒す。

基本方針：

- Sessionを検証できない場合は認証済みとして扱わない
- Backend Credentialを取得できない場合はLaravel APIを認証付きで呼び出さない
- Credentialを推測・再構築しない
- 認証情報をFrontendへフォールバック保存しない

具体的なAvailability / Recovery方針は非機能要件およびRedis詳細設計で定義する。

---

## 20. セキュリティ方針

以下を基本方針とする。

- Better Auth Session CookieはHttpOnlyとする
- Production / StagingではSecure Cookieを利用する
- Production / StagingではHTTPSを利用する
- Laravel Sanctum TokenをBrowserへ露出させない
- Laravel Sanctum TokenをlocalStorageへ保存しない
- Laravel Sanctum TokenをsessionStorageへ保存しない
- Backend CredentialをPostgreSQLへ保存しない
- SessionとBackend CredentialのRedis Key Namespaceを分離する
- Redis ACLによってアクセス責務を分離する
- Backend CredentialをLogへ出力しない
- Backend APIでも必ず認証・認可を行う
- Tokenには適切な有効期限を設定する
- Logout時にSessionとTokenの両方を失効する
- 認証失敗時に不要な情報を返さない
- Next.jsからPostgreSQLへ直接アクセスしない

---

## 21. 将来的なSSO対応

将来的にOIDC / OAuthを利用した社内SSOへ変更する可能性を考慮する。

例：

```text
Browser
   ↓
Next.js / Better Auth
   ↓
Microsoft Entra ID / Okta / Google Workspace
   ↓
Next.js BFF
   ↓
Laravel Backend API
```

BrowserとNext.jsのSession境界を維持することで、認証元を将来的に変更しやすい構成とする。

---

## 22. 責務境界

最終的な責務境界は以下とする。

### Browser

- Better Auth Session Cookieのみ保持する
- Backend Credentialを保持しない

### Better Auth / Next.js

- Browser Session管理
- Login / Logout Flowの制御
- 認証済み利用者の識別
- Frontend側の表示制御

### Redis

- Better Auth Sessionの保存
- Backend Credentialの保存
- Key Namespaceによる責務分離
- ACLによるアクセス境界の維持

### Next.js BFF

- Laravel Backend APIの呼び出し
- Backend Credentialの取得
- Bearer Tokenの付与
- Backend認証エラーのFrontendへの変換

### Laravel Sanctum

- Sanctum Token発行
- Token検証
- Token失効
- Backend API利用者の特定

### Laravel Authorization

- 業務上の最終的な認可
- Role / 担当範囲等によるアクセス制御

### PostgreSQL

- Application Data
- Laravel側の永続データ
- Laravel Sanctumが必要とするToken管理データ

---

## 23. 採用しない構成

MVPでは以下を採用しない。

- Auth.js
- Better Auth SessionをPostgreSQLへ保存する構成
- Backend CredentialをPostgreSQLへ保存する構成
- Next.jsからPostgreSQLへ直接アクセスする構成
- Laravel Sanctum SPA Cookie認証
- BrowserからLaravel Backend APIを直接呼び出す構成
- Laravel Sanctum TokenをBrowserへ保存する構成
- 独自Session管理
- MVP段階でのOAuth Server構築
- Session用RedisとBackend Credential用Redisの物理分離

MVPではRedis 1台を利用し、Key NamespaceとACLによってSessionとBackend Credentialの責務を分離する。

---

## 24. 決定事項

### Browser ↔ Next.js

Better Auth Session Cookieを利用する。

### Session管理

Better Authを採用する。

### Session Store

Redisを採用する。

### Next.js ↔ Laravel

Laravel Sanctum Personal Access TokenによるBearer Token認証を利用する。

### Backend Credential

Redisへ保存する。

### Redis構成

MVPではRedis 1台を利用する。

Better Auth SessionとBackend CredentialはKey NamespaceおよびACLを分離する。

### PostgreSQL

Application DataのPrimary Databaseとして利用する。

Next.jsから直接アクセスしない。

Better Auth SessionおよびBackend Credentialを保存しない。

### 認可

Laravel Backend APIで必ず最終的な認可を行う。

### 基本構成

```text
Browser
   |
   | Better Auth Session Cookie
   v
Next.js Frontend / BFF
   |
   +---- Redis
   |      ├── Better Auth Session
   |      └── Backend Credential
   |
   | Sanctum Bearer Token
   v
Laravel Backend API
   |
   v
PostgreSQL
```
